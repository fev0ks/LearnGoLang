## 1. "Зачем `resizeMu`, если `workersRunning` уже `atomic.Int64`?"

> **Коротко:** atomic защищает **значение** от битого чтения, mutex защищает **операцию целиком** от того, чтобы её увидели посередине. Это разные задачи.

`Resize` делает три шага:

1. прочитать `current`;
2. посчитать `delta`;
3. применить (запустить горутины + обновить счётчик).

Atomic защищает каждый шаг по отдельности, но не **последовательность**. Без mutex два concurrent `Resize(15)`:

- оба читают `current=10`;
- оба считают `delta=+5`;
- оба запускают 5 воркеров → итог **20 вместо 15**.

Каждый `Load`/`Add` сам по себе корректен — сломана последовательность. Mutex делает «прочитать + посчитать + применить» одним участком: второй `Resize` ждёт у двери и видит уже `workersRunning=15`.

**На собесе:** «atomic защищает значение, mutex защищает операцию целиком». Отделяет «знаю синтаксис» от «понимаю, когда что брать».

## 2. "А зачем тогда `atomic.Int64`, если всё под `resizeMu`?"

> **Коротко:** в текущем коде — избыточен. Заложен на вырост под observability (внешний читатель без `resizeMu`).

- Все обращения к `workersRunning` либо в `New` (без конкуренции), либо в `Resize` (под mutex). Обычный `int64` отработал бы так же.
- Atomic понадобится, если счётчик начнёт читать кто-то **снаружи** без `resizeMu` — например, публичный `WorkersRunning() int` для метрик Prometheus. Без atomic там будет гонка данных.
- То есть atomic тут на вырост: появится observability — не надо менять тип. Сейчас работу делает `resizeMu`, atomic лишь страхует будущего внешнего читателя.

**На собесе:** «в текущем коде atomic избыточен, заложен на observability; без таких планов — убрать». Сильнее, чем «ну так положено».

## 3. "`Resize(0)` — это же фактически Shutdown?"

> **Коротко:** нет. `Shutdown` drain'ит буфер, `Resize(0)` погасил бы воркеров с полным буфером → тихий dead-lock. Поэтому `Resize(0)` → `ErrResizeNonPositive`.

- `Shutdown` drain'ит буфер — воркеры дочёрпывают задачи.
- `Resize(0)` без drain'а просто погасил бы воркеров, оставив полный буфер. Следующий `Submit` встал бы намертво в `tasks <- t` — читать некому. Это **тихий dead-lock**.
- Хочешь остановить — вызывай `Shutdown(ctx)`.

**Связанный вопрос:** «почему `New` с `Workers <= 0` паникует, а `Resize(0)` возвращает ошибку?»

- `New` — старт процесса, `Workers = 0` это баг программиста. Паника правильна: процесс не должен подняться с битой конфигурацией.
- `Resize` — живой процесс, аргумент может прийти из админки или автоскейлера. Паника = «один кривой запрос роняет сервис».
- Общий паттерн Go: **panic для багов программиста, error для runtime-ошибок**.

## 4. "Почему `quitOne` не `close`, а N send'ов в цикле?"

> **Коротко:** `close` — broadcast (выйдут все воркеры), а нужно ровно N. Поэтому unbuffered-канал + N точечных send'ов.

- `close` видят **все** воркеры → выйдет весь пул.
- Канал не закрывается, делаем N send'ов. `quitOne` unbuffered: каждый send блокирует до одного receiver'а. Три send'а — три воркера вышли, остальные работают.
- Кто именно выйдет — undefined (Go random select). Это фича: worker affinity нет, все воркеры равны.

**Главная мысль:** `close` = сигнал **всем сразу**, send = **точечно одному**. Когда надо «разбудить ровно N из M» — почти всегда ответ через N send'ов в unbuffered канал.

## 5. "`Submit` и `Shutdown` вызвали одновременно. Что с задачей?"

> **Коротко:** гонка есть и осознанно оставлена. `drainAndExit` покрывает ~99%; теряется только при тайтовом дедлайне `Shutdown(ctx)`.

Как работает:

- `Submit` уже зашёл в основной select. В этот момент `Shutdown` делает `close(stop)`. Готовы оба case'а — `tasks <- t` и `<-p.stop`. Go выбирает случайно. Если выбрал `tasks <- t` — задача в буфере уже после Shutdown'а.
- Но не теряется: воркеры по `<-stop` уходят в `drainAndExit` и дочёрпывают буфер. Задача в хвосте обычно успевает выполниться.
- Теряется только при тайтовом дедлайне на `Shutdown(ctx)`: ctx истёк до того, как воркеры доехали до хвоста → force-stop → остаток дропается молча.

**Почему оставили:** закрыть насмерть можно только сериализацией Submit'а и Shutdown'а (счётчик in-flight, Shutdown ждёт обнуления). Это блокировка на горячем пути Submit'а ради редкого corner case. Не платим.

**Альтернатива с явным контрактом** (если «приняли после Shutdown» недопустимо): `atomic.Bool closed`, который `Submit` проверяет первым и при `true` сразу возвращает `ErrPoolClosed` — задача честно **отвергается**, а не молча теряется. Гонка на грани остаётся (между проверкой и `close(stop)`), но контракт чёткий: «после Shutdown Submit либо принял до закрытия, либо вернул ошибку». Это дешевле полной сериализации (один атомарный `Load`, не лок) и часто то, что нужно вызывающему. Полная гарантия «ноль потерь» — только через счётчик in-flight + `Shutdown`, ждущий обнуления.

**На собесе:** «гонка есть, документирована, `drainAndExit` покрывает 99%; если нужен контракт — `atomic closed` + `ErrPoolClosed` (отвергаем, не теряем); полная гарантия — счётчик in-flight, но это блокировка на каждый Submit».

## 6. "Rate limiter? Token bucket vs leaky bucket?"

> **Коротко:** rate limiter ≠ backpressure. Limiter — «не больше X/сек» (защита downstream), backpressure — «что делать при полной очереди». Выбор bucket'а — по downstream'у.

Разные слои, на собесе путают:

- **Rate limiter** — «не больше X задач в секунду» (защита downstream).
- **Backpressure** — «что делать, когда очередь полная».

**Где жить — и это меняет смысл:** `golang.org/x/time/rate.Limiter.Wait(ctx)`, один лимитер на пул:

- **в `Submit`** — throttling упирается в продьюсера (backpressure уходит вверх по стеку, очередь не растёт);
- **в `runTask`** — ограничиваем именно темп обращений к downstream, но задачи копятся в очереди (нужно следить за её размером).

Виды:

- **Token bucket** — разрешает короткие бёрсты до capacity. Дефолт `x/time/rate`. Подходит, когда downstream ОК с пиками.
- **Leaky bucket** — равномерный поток, бёрсты сглажены. Для чувствительных downstream'ов (legacy SOAP, on-prem).

Два senior-нюанса:

- **`x/time/rate` — per-process.** На флоте из 20 подов получится 20×R. Если лимит общий (квота внешнего API) — нужен **распределённый** лимитер: Redis (token bucket на Lua / sliding-window), либо отдельный gateway/sidecar.
- **Adaptive concurrency** вместо фиксированного R: лимит подстраивается под latency downstream'а (AIMD, как TCP congestion control — Netflix `concurrency-limits`). Когда latency растёт — сами снижаем темп. Сильнее статического числа, которое всё равно угадывается.

**Сильный ответ:** «выбирай по downstream'у; `x/time/rate` per-instance — для общей квоты нужен распределённый лимитер; а статический rate я бы предпочёл adaptive по latency».

## 7. "Observability? Что мерить?"

> **Коротко:** 5 метрик (queue/in-flight/duration/errors/dropped) + структурный `slog` + OTel-трейсинг через `ctx`. Wiring — по месту, не in-memory моки в проде.

**Минимум 5 метрик (Prometheus):**

| Метрика | Тип | Что показывает |
|---|---|---|
| `queue_length` | gauge | `len(p.tasks)` — насколько активен backpressure |
| `tasks_in_flight` | gauge | `+1` в начале `runTask`, `-1` в конце — сколько воркеров реально заняты |
| `task_duration_seconds` | histogram (p50/p95/p99) | latency задач |
| `task_errors_total` | counter (label по типам) | деградация качества |
| `dropped_tasks_total` | counter | наш `DroppedTasks` в Prometheus |

- **Логи:** `slog` со структурой — `task_id`, `worker_id` (через `WorkerID(ctx)`), `duration_ms`. Не printf-style, не `fmt.Println`.
- **Трейсинг:** OpenTelemetry **через ctx**. Воркер видит `t.ctx` — span пропагейтится сам. Критично, когда задача дёргает 3 downstream'а: без trace'а где упало непонятно.

**Каркас, чтобы не сыпать метрики списком:** два метода —

- **RED** (для пула как сервиса): **R**ate (`tasks_total`/сек), **E**rrors (`task_errors_total`), **D**uration (`task_duration_seconds`);
- **USE** (для пула как ресурса): **U**tilization (`tasks_in_flight / workers`), **S**aturation (`queue_length / cap` — ключевой сигнал backpressure; растёт к 1 → пора алертить/скейлить), **E**rrors (`dropped_tasks_total`).

Если связываешь метрики и трейсы — **exemplars** (Prometheus): по всплеску latency на графике прыгаешь прямо в конкретный trace.

**Почему не в коде:** Prometheus + OTel + slog wiring = неделя курса. На собесе нормальный ответ — «знаю что мерить (RED для сервиса, USE для ресурса), инструментацию пишу по месту, не делаю in-memory моки в продовом коде».

## 8. "А когда worker pool вообще не нужен?"

> **Коротко:** ограничить параллелизм — мало для пула, это делает `errgroup.SetLimit`. Standing worker pool оправдан, когда воркеры **долгоживущие и носят состояние/ресурс** или нужна **очередь с backpressure**.

Вопрос ловит «синдром молотка»: junior всё решает пулом, потому что выучил.

**Сначала развенчаем «CPU-bound → нужен пул».** Ограничить число одновременно работающих горутин (хоть для CPU-, хоть для I/O-bound) умеет `errgroup.Group` + `g.SetLimit(n)` или `semaphore.Weighted` — без единой строчки своего пула:

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(runtime.NumCPU())     // bounded concurrency «из коробки»
for _, job := range jobs {
    job := job
    g.Go(func() error { return process(ctx, job) })
}
err := g.Wait()
```

Поэтому «10K задач, не больше N разом» — это **не повод** писать worker pool. Это повод взять `errgroup.SetLimit`.

**Что тогда реально требует пула** — одно из:

1. **Воркер носит дорогой ресурс/состояние, и его нельзя создавать на задачу.** Тогда нужно ровно N долгоживущих воркеров, каждый держит своё: соединение с БД/брокером, CGo- или GPU-хэндл, загруженную в память ML-модель, большой переиспользуемый буфер, сессию к rate-limited API. `errgroup` создаёт горутину **на задачу** — ресурс пришлось бы открывать/закрывать каждый раз.
2. **Долгоживущий сервис, который принимает работу со временем,** а не разовый батч. `errgroup` — это «сделать этот набор и дождаться»; пул — «крутиться и кормиться задачами по мере поступления» (consumer очереди, фоновый обработчик).
3. **Нужна сама очередь с явной политикой переполнения** (bounded queue + backpressure/drop/reject) — то, что в нашем `senior`-коде делает `Config.OnFull`.

Если ни одного из трёх нет — пул это overengineering, бери `errgroup + semaphore`.

| Нужно | Инструмент |
|---|---|
| «N задач, не больше K разом, дождаться всех» (батч) | `errgroup` + `SetLimit` / `semaphore.Weighted` |
| Параллельно + первая ошибка отменяет остальных | `errgroup.WithContext` |
| Долгоживущие воркеры с состоянием/ресурсом, очередь, backpressure | **worker pool** |

**Сильный ответ:** «ограничение параллелизма — это `errgroup.SetLimit`, а не пул. Worker pool оправдан, когда воркер долгоживущий и носит состояние — соединение, модель, буфер — или нужна очередь с backpressure. CPU-vs-IO тут вторично: ось решения — реюз ресурса и время жизни воркера».

## 9. "Зачем своя реализация, если есть `sourcegraph/conc` и `alitto/pond`?"

> **Коротко:** в проде — бери готовое (`pond`). Свой пишут на собесе, чтобы проверить, понимаешь ли механику.

- `golang.org/x/sync/errgroup` — официальная, для bounded fan-out батча (`SetLimit`) + распространение ошибки. Первый кандидат, если не нужны долгоживущие воркеры (см. вопрос 8).
- `sourcegraph/conc` — тонкая обёртка над goroutines + WaitGroup, panic-safe (`conc.Pool`, `conc.Stream` с сохранением порядка). Хорош для коротких параллельных операций.
- `panjf2000/ants` — самый популярный высоконагруженный пул (десятки k⭐): реюз горутин, тюнинг под минимум аллокаций, `Resize`, неблокирующий submit. Когда важен throughput/память на больших объёмах.
- `alitto/pond` — полноценный worker pool с метриками, resize'ом, backpressure. Ближе всего к нашему senior-коду по фичам.

Свой пишут на собесе — чтобы интервьюер понял, **понимаешь ли ты механику**. На реальном проекте: импортируешь `pond`/`ants`, читаешь его API, обвешиваешь метриками — готово.

**Сильный ответ:** «в проде взял бы `pond`. Своя реализация даёт гибкость кастомных стратегий backpressure — но 99% задач закрывает готовая либа. Самое важное — понимать, что внутри: иначе при проблеме не отдебажишь».

## 10. "Priority queue?"

> **Коротко:** сначала спроси, нужна ли (FIFO решает 80%). 2 уровня — два канала + nested select; 3+ — `container/heap`.

Если бизнес-требование явное («OCR клиентских PDF'ов вперёд background batch») — тогда да. Два варианта:

1. **`container/heap`** (~80 LOC) — честная очередь с приоритетом. Вставка/извлечение O(log n). Минус: не вписывается в паттерн `chan task`, надо менять worker'а.
2. **Два канала high/low + nested select** (~10 LOC):
   ```go
   select {
   case t := <-p.high:
       runTask(t)
   default:
       select {
       case t := <-p.high: runTask(t)
       case t := <-p.low:  runTask(t)
       }
   }
   ```
   Внешний select даёт high приоритет: есть задача в high — берём её. Нет (`default`) — вкладываемся в select с low, ждём любую. Грубо, но работает на 2 уровнях.

**Подводный камень строгого приоритета — голодание low.** Если high идёт непрерывным потоком, low-задачи не выполнятся **никогда** (оба варианта выше этим страдают). На собесе это любят: «а если high не кончается?». Лечится **fairness**:

- **Aging:** ждущая low-задача со временем повышает приоритет (двигается в high после порога ожидания);
- **Weighted round-robin:** брать в пропорции, скажем, 4 high : 1 low — low гарантированно получает долю;
- **Дедлайны вместо приоритетов:** EDF (earliest-deadline-first) на `container/heap` по дедлайну, а не по «классу».

**Сильный ответ:** «два уровня — каналы, три и больше — heap. Но строгий приоритет голодает низкий класс, поэтому в проде нужна fairness — aging или weighted RR. И сначала бы я спросил, есть ли реальная разница в SLO между типами задач; если нет — FIFO».

## 11. "Pool of pools / bulkhead?"

> **Коротко:** разные SLO (latency-sensitive vs background batch) — диспетчер + N маленьких пулов по типу задачи. Один лёг — другие живут. Это **bulkhead**.

Проблема: на одном пуле latency-sensitive (запросы пользователя) и background batch (отчёты, ETL) дерутся за слоты — батч забивает очередь, пользовательский запрос ждёт.

**Решение:** диспетчер + **N маленьких пулов** по типу задачи, у каждого свой `Config` (workers, queue size, backpressure). Один пул лежит — другие живут. Это **bulkhead pattern** из Hystrix.

```go
type Dispatcher struct {
    pools map[TaskType]*Pool
}

func (d *Dispatcher) Submit(taskType TaskType, ...) error {
    return d.pools[taskType].Submit(...)
}
```

Изолируется не только **throughput**, но и **отказ**: poison-задача, утечка горутин или взбесившийся downstream в одном пуле не выедают воркеров остальных. Это уже про надёжность, а не только про SLO.

Усиливают двумя вещами:

- **Circuit breaker на downstream** (`sony/gobreaker`): пул-обработчик «битого» сервиса быстро фейлит вместо того, чтобы копить зависшие задачи и держать воркеров.
- **Отдельные backpressure-политики** на пул: пользовательскому — `OnFull=block` (подождать), батчевому — `OnFull=drop`/reject (потерять не страшно).

Цена: больше пулов = больше простаивающих воркеров и точек тюнинга. Не дроби без необходимости — обычно хватает 2–3 классов (interactive / batch / критичный).

**Сильный ответ:** «изоляция SLO и отказов: latency-sensitive отделил бы от background batch, чтобы зависший ETL не выел воркеров пользовательского трафика. Так делают Netflix, Uber; усилил бы circuit breaker'ом на downstream. Мы не Netflix, но паттерн тот же».

## 12. "А если не ограничивать вход? Unbounded-очередь"

> **Коротко:** бывает (unbounded-очередь), но лимит так не исчезает — он переезжает в RAM и latency. Полный буфер не баг: это честный сигнал «вход обгоняет обработку».

Пул по определению ограничивает **число воркеров** — в этом и смысл. А входная очередь может быть разной:

- **bounded** (буфер фикс. размера) — как здесь; полна → нужен `OnFull`;
- **unbuffered** (`cap 0`) — `Submit` блокируется до свободного воркера (очередь «нулевого размера», естественный backpressure);
- **unbounded** — буфер растёт сколько угодно; `Submit` никогда не отвергает.

**`OnFull` не «ломает обработку» — он показывает физический предел.** Если продьюсеры подают быстрее, чем пул переваривает, реакций ровно **три**, четвёртой не существует:

| Реакция | Чем платишь |
|---|---|
| **block** (ждать) | backpressure вверх — продьюсер замедляется до скорости пула; потерь нет |
| **drop / reject** | теряем задачи / отдаём `503`, но latency и память ограничены |
| **буферизировать дальше** (unbounded) | не отвергаем, но очередь растёт **без предела** → растущая latency + рост памяти → **OOM** |

Это закон Литтла (`L = λ·W`): если входящий темп `λ` выше пропускной способности — длина очереди `L` растёт неограниченно. Никакой буфер не «успеет», он лишь **отсрочит** проблему. Поэтому unbounded-пул не убирает лимит, а **меняет быстрый явный отказ на медленную катастрофу** (память + latency → коллапс через N минут). `OnFull` же даёт *выбрать* стратегию осознанно.

**Когда unbounded всё же ОК:** работа **конечна и известна** (обработать фиксированные 10k элементов — очередь упрётся в 10k, а не растёт вечно) или бёрст ограничен сверху. Для **открытого потока** входящих задач unbounded — мина.

**Связь с реальностью:** `net/http`-сервер — это «пул без входного лимита»: горутина на соединение, очереди нет. Поэтому его специально ограничивают (семафор в middleware, `MaxConcurrentStreams`, лимиты на LB) — иначе DoS укладывает по памяти.

**Сильный ответ:** «можно не ограничивать вход — это unbounded-очередь. Но лимит не исчезает, а переезжает в RAM и latency: при `λ > throughput` очередь растёт до OOM (закон Литтла). Полный буфер — не баг, а сигнал перегрузки; честно выбрать block / reject / drop. Unbounded оправдан только для конечной известной работы».

## 13. "Автоскейлинг воркеров по длине очереди?"

> **Коротко:** добавление воркеров поднимает throughput, **только если узкое место — сами воркеры** (I/O-bound, ждут). Для CPU-bound и при боттлнеке в downstream не помогает и усиливает перегрузку. Скейлить надо по latency/utilization с потолком, а не по длине очереди.

Интуиция верная, но как слепое правило «очередь растёт → +воркер» — опасна. Очередь растёт, когда `λ > μ` (закон Литтла, `L = λ·W`), где `μ = воркеры × throughput_одного`. Добавив воркеров, поднимешь `μ` **только если** `throughput_одного` не просядет — т.е. под капотом есть свободный ресурс.

**Когда помогает:**

- **I/O-bound**, воркеры в основном **ждут** сеть/диск → больше воркеров = больше запросов в полёте = выше throughput, пока не упрёшься в downstream/сеть.

**Когда не помогает (и делает хуже):**

- **CPU-bound**, воркеров уже ≈`NumCPU`: новые горутины не добавляют вычислительной мощности, только context-switching. `μ` не растёт, latency хуже. Нужны **ядра/машины**, а не горутины.
- **Боттлнек в downstream** (БД/API на пределе или rate-limited): больше воркеров = больше нагрузки на перегруженный сервис → таймауты, ретраи, **каскадный отказ**. Усиливаешь перегрузку.
- **Контеншен на общем локе/пуле соединений:** воркеры дерутся за тот же ресурс → деградация.

То есть «очередь растёт» само по себе **не** значит «добавь воркеров» — это лишь «вход обгоняет обработку». Что делать вместо наивного правила:

- **Скейлить по utilization, не по длине очереди.** Воркеры простаивают/висят на I/O и очередь растёт → они узкое место, добавляй. Воркеры на 100% CPU → добавление не поможет, нужен горизонтальный скейл подов.
- **Adaptive concurrency (AIMD):** растить concurrency пока latency плоская, откатывать при росте (рост latency = downstream насыщается). Само находит оптимум и **останавливается**, когда добавлять перестало помогать.
- **Обязателен потолок (max workers)** — иначе автоскейл воспроизводит unbounded-проблему (неограниченная нагрузка на downstream + память).
- На пределе локального пула — **backpressure** (reject/block), а поды добавляет оркестратор (k8s HPA по queue depth / CPU), а не один под плодит горутины.

В нашем коде механизм уже есть — `Resize`. Вопрос в **политике** поверх него: смотреть на latency/utilization + cap, а не на голую длину очереди.

**Сильный ответ:** «иногда да — если узкое место сами воркеры (I/O-bound, ждут). Для CPU-bound или боттлнека в downstream добавление воркеров не поднимает throughput (`μ` упёрся в ресурс) и только усиливает перегрузку. Скейлю по latency/utilization (adaptive concurrency) с потолком, а не по длине очереди; на пределе — backpressure + горизонтальный скейл подов».
