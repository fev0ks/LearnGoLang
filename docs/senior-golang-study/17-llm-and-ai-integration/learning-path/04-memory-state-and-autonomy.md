На четвёртом этапе одиночный запрос превращается в процесс, который переживает паузу, падение и подтверждение человеком. Главная задача — отделить полезное состояние от бесконечной истории сообщений.

---

## Задача этапа

`Repository Health Agent` должен уметь:

- сохранить прогресс после каждого значимого перехода;
- продолжить незавершённый запуск после рестарта;
- не повторить уже выполненную операцию;
- приостановиться перед рискованным действием;
- дождаться решения человека и продолжить тот же запуск;
- забыть или сжать данные, которые больше не нужны.

Для учебной практики можно добавить один инструмент записи, например создание draft issue с отчётом. Он не должен публиковать данные без подтверждения человека.

---

## Контекст, память и состояние

| Сущность | Роль | Пример | Срок жизни |
| --- | --- | --- | --- |
| Контекст запроса | данные для текущего решения модели | выбранные change details | один LLM-вызов |
| История запуска | последовательность решений и наблюдений | tool call и его результат | один запуск или срок аудита |
| Память | сведения, которые могут помочь будущим решениям | предпочтения команды, прошлые инциденты | несколько запусков |
| Состояние процесса | источник истины о текущей фазе | `waiting_for_approval` | до завершения процесса |

История не становится памятью автоматически. Если без разбора отправлять все старые сообщения в каждый запрос, растут стоимость, задержка и вероятность того, что устаревшая инструкция повлияет на новое решение.

Состояние процесса должно быть структурированным. Поле `status = waiting_for_approval` надёжнее, чем попытка определить фазу по последней строке диалога.

---

## Виды памяти

**Краткосрочная память** поддерживает текущий запуск: уже прочитанные элементы, промежуточный план и накопленные findings. Обычно это часть состояния запуска.

**Долгосрочная память** хранит устойчивые сведения между запусками: правила команды, выбранные пороги и разрешённые репозитории. Для таких данных важны владелец, версия, источник и срок жизни.

**Эпизодическая память** хранит прошлые случаи: запуск, принятое решение, обратную связь человека и исход. Она помогает находить похожие примеры, но прошлое решение не является автоматическим разрешением повторить действие.

Память нуждается в политике:

- что записывать;
- кто может читать и изменять запись;
- как определить актуальность;
- когда сжимать или удалять;
- как исправить неверную запись;
- как исключить секреты и лишние персональные данные.

Векторный поиск — только один из способов извлечения памяти. Небольшой набор правил команды лучше хранить в обычной структурированной таблице, где доступны точные фильтры и версия записи.

## Жизненный цикл запуска

Минимальная state machine:

```text
created
  -> running
      -> waiting_for_approval
          -> running
      -> completed
      -> failed
      -> cancelled
```

Разрешённые переходы задаёт код. Модель может предложить `request_approval`, но не может сама перевести процесс из `waiting_for_approval` в `running`.

Для каждого перехода сохраняются:

- `run_id`;
- предыдущий и новый статус;
- версия состояния;
- причина перехода;
- инициатор: система, модель, инструмент или человек;
- время и correlation ID.

Оптимистическая версия защищает от двух обработчиков, которые одновременно пытаются продолжить один запуск:

```sql
UPDATE agent_runs
SET status = $new_status,
    version = version + 1
WHERE id = $run_id
  AND version = $expected_version;
```

Если обновлено ноль строк, состояние уже изменилось и обработчик обязан перечитать его, а не продолжать со старой копией.

## Персистентность и восстановление

Сохранять нужно после события, которое нельзя безопасно потерять:

- выбран следующий шаг;
- инструмент начал или закончил работу;
- получено подтверждение человека;
- обновлён бюджет;
- сформирован финальный отчёт.

Запись `decision` и постановка фоновой задачи должны образовывать согласованный переход. Если база обновилась, а сообщение в очередь потерялось, запуск зависнет. Типовые решения — transactional outbox, периодический scanner незавершённых запусков или workflow engine с durable execution.

После рестарта контроллер:

1. Загружает состояние и версию.
2. Определяет последний завершённый шаг.
3. Проверяет, был ли внешний эффект подтверждён.
4. Продолжает только разрешённый переход.
5. Не воспроизводит LLM-вызов или tool call без проверки политики повтора.

Персистентность сама по себе не даёт exactly-once. Она лишь предоставляет факты, на основе которых можно сделать повтор безопасным.

## Идемпотентность и конкурентность

**Идемпотентность** означает, что повтор одной логической операции с тем же ключом не создаёт новый внешний эффект.

Для draft issue ключ можно построить из назначения и версии отчёта:

```text
repository + run_id + action_kind + report_version
```

Ключ хранится рядом с результатом операции. Последовательность `проверить наличие -> выполнить -> записать ключ` имеет race condition. Нужна атомарная резервация через уникальное ограничение, условный `INSERT` или механизм идемпотентности внешнего API.

Полезно разделять три случая:

- LLM-вызов без внешнего эффекта можно повторить, но результат и стоимость изменятся;
- read-only инструмент обычно можно повторить, но данные между вызовами могут измениться;
- инструмент записи повторяется только при доказанной идемпотентности или после сверки фактического эффекта.

Параллельное чтение нескольких изменений ускоряет запуск, но требует ограниченного fan-out. Результаты привязываются к исходным идентификаторам, а не к порядку завершения goroutine.

## Уровни автономности и HITL

Human-in-the-Loop (HITL) — точка, где система запрашивает решение человека и сохраняет его как событие процесса.

Полезная лестница автономности:

| Уровень | Поведение | Пример |
| --- | --- | --- |
| 0 | только предлагает | формирует отчёт |
| 1 | готовит обратимое действие | создаёт локальный draft |
| 2 | выполняет после подтверждения | создаёт issue после approve |
| 3 | выполняет сам в узкой политике | добавляет внутренний label из allowlist |
| 4 | широкая автономность | для учебного проекта не используется |

Уровень определяется риском действия, обратимостью, стоимостью ошибки и качеством evals. Текстовое поле `confidence`, сгенерированное моделью, не является достаточным основанием повысить автономность: его сначала нужно откалибровать на размеченных примерах.

Self-reflection можно использовать как дополнительную проверку: модель ищет противоречия в своём плане или отчёте. Она не заменяет независимую валидацию, потому что та же модель может повторить исходную ошибку.

## Практика

1. Создать таблицы или эквивалентное хранилище `agent_runs`, `run_events` и `action_idempotency`.
2. Реализовать state machine с проверкой допустимых переходов.
3. Сохранять событие до и после вызова инструмента записи.
4. Добавить статус `waiting_for_approval` и endpoint/CLI-команду подтверждения.
5. Защитить подтверждение от повторной обработки версией состояния.
6. Остановить процесс во время tool call и проверить восстановление после рестарта.
7. Запустить два конкурентных resume и доказать, что внешний эффект один.
8. Добавить compaction: сохранять структурированные findings, а не всю историю в каждом новом prompt.

---

## Критерии завершения

- Состояние запуска не выводится из свободного текста.
- Недопустимый переход отклоняется.
- Два resume не создают два внешних эффекта.
- Запуск после рестарта продолжает нужный шаг или безопасно останавливается.
- Подтверждение связано с конкретным действием и версией payload.
- Долгосрочная память имеет источник, владельца и срок жизни.
- Self-reflection не используется вместо программной проверки.

---

## Типичные ошибки

- Называть памятью весь transcript.
- Использовать векторную БД для точного состояния процесса.
- Сначала читать idempotency key, затем неатомарно выполнять действие.
- Держать лок дольше его TTL без продления.
- После рестарта повторять последний tool call вслепую.
- Принимать подтверждение для старой версии действия.
- Давать модели возможность самостоятельно повысить уровень автономности.

## Interview-ready answer

**1. Чем память агента отличается от состояния процесса?**

- Состояние — источник истины о текущей фазе и разрешённых переходах.
- Память — сведения, которые могут помочь будущему решению, но не определяют переход сами по себе.
- Хранилище — состояние требует строгой схемы и конкурентного контроля; память может иметь разные способы извлечения и срок жизни.

**2. Как восстановить агента после сбоя без повторного эффекта?**

- События — сохраняются границы шага и идентификатор внешней операции.
- Идемпотентность — повтор использует тот же ключ или сверяет фактический эффект.
- Конкурентность — версия состояния или lease не даёт двум обработчикам продолжить один запуск.
- Неопределённость — если факт выполнения нельзя доказать, процесс останавливается для сверки, а не повторяет запись вслепую.

**3. Когда нужен Human-in-the-Loop?**

- Риск — перед необратимым, дорогим или чувствительным действием.
- Неуверенность — когда данных недостаточно или система вышла за проверенную область.
- Контракт — подтверждение относится к конкретному payload и не выдаёт общее разрешение на будущие действия.
