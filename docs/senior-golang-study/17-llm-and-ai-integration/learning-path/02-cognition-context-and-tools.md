На втором этапе агент должен перестать получать весь репозиторий одним огромным фрагментом. Он сам выбирает узкие операции чтения, но приложение сохраняет контроль над доступом, форматом данных и бюджетом.

---

## Задача этапа

Нужно расширить `Repository Health Agent`, чтобы он:

- сначала получал краткий список изменений;
- выбирал, какие элементы требуют детального чтения;
- запрашивал детали только для выбранных элементов;
- возвращал отчёт по строгой схеме;
- пытался исправить невалидный ответ ограниченное число раз.

Главный результат этапа — не больше инструментов, а предсказуемая граница между вероятностным решением модели и детерминированным кодом.

---

## Когнитивный и execution-слои

**Когнитивный слой** формирует решение: какой контекст нужен, какой инструмент вызвать и достаточно ли данных для ответа.

**Execution-слой** исполняет допустимое действие: валидирует аргументы, проверяет права, вызывает API, ограничивает размер результата и нормализует ошибку.

| Ответственность | Когнитивный слой | Execution-слой |
| --- | --- | --- |
| Выбрать следующий шаг | да | нет |
| Проверить JSON Schema | нет | да |
| Проверить доступ к репозиторию | нет | да |
| Выполнить HTTP-запрос | нет | да |
| Решить, достаточно ли фактов | да | нет |
| Ограничить таймаут и объём ответа | нет | да |

Модель может предложить действие, но не может выдать себе права. Даже правильный по смыслу tool call отклоняется, если аргументы не проходят схему или пользователь не имеет доступа к ресурсу.

---

## Выбор модели

Модель выбирают по измеряемому сценарию, а не по общему рейтингу. Для Repository Health Agent важны:

- соблюдение схемы результата;
- корректный выбор инструмента;
- способность работать с нужным языком и размером контекста;
- задержка до первого и полного ответа;
- стоимость типичного запуска;
- поддержка необходимых API-возможностей у выбранного провайдера.

Практический процесс выбора:

1. Собрать набор из типичных, сложных и ошибочных входов.
2. Определить метрики: доля валидных отчётов, точность findings, лишние tool calls, задержка и стоимость.
3. Прогнать одинаковый сценарий на кандидатах.
4. Выбрать самую простую и дешёвую модель, которая проходит целевые пороги.
5. Зафиксировать идентификатор модели и версию промпта в trace.

Параметры генерации зависят от API и класса модели. Нельзя строить общую архитектуру на предположении, что каждый провайдер одинаково поддерживает `temperature`, seed или скрытые рассуждения.

## Context engineering

Context engineering — проектирование того, какие данные, в каком порядке и с какими границами попадают в запрос модели.

Контекст состоит не только из текста пользователя:

```text
инструкции системы
  + цель запуска
  + доступные инструменты и их схемы
  + релевантное состояние процесса
  + результаты предыдущих инструментов
  + ограничения на ответ
```

Перед добавлением фрагмента нужно ответить на три вопроса:

1. Нужен ли он для текущего решения?
2. Можно ли заменить его короткой структурой?
3. Какая доверительная граница у источника?

Например, список из ста pull request не нужно сразу дополнять всеми diff. Сначала модель получает идентификатор, заголовок, автора, возраст и статус проверок. Затем она выбирает несколько кандидатов для чтения деталей.

Такая двухфазная стратегия уменьшает контекст и стоимость, но создаёт риск пропустить важный элемент на первом этапе. Этот риск измеряется на eval-наборе: в него добавляются случаи, где значимый сигнал виден только в кратких метаданных.

Сжатие истории также является преобразованием данных. Сводка может потерять факт, поэтому исходные наблюдения должны оставаться доступными по идентификатору, а критические поля лучше хранить структурированно.

---

## Структурированный вывод

Просьба «ответь JSON» не равна гарантии схемы. Надёжная граница состоит из нескольких уровней:

1. Провайдеру передаётся поддерживаемая им схема структурированного ответа.
2. Приложение повторно декодирует и валидирует полученный объект.
3. Предметные инварианты проверяются отдельно: допустимый `kind`, существующий `item_id`, непустое evidence.
4. Невалидный результат попадает в ограниченный repair loop или завершает запуск ошибкой.

Repair loop не должен быть бесконечным. Повтор полезен, если модель получила точное описание нарушения. Если схема или исходный контекст противоречат друг другу, повтор того же запроса только расходует бюджет.

Подробности и Go-пример находятся в [структурированном выводе](../api-integration/02-structured-outputs.md).

## Проектирование инструментов

Хороший инструмент описывает одну предметную операцию с узким контрактом.

| Плохой контракт | Проблема | Более безопасный контракт |
| --- | --- | --- |
| `run_api(method, url, body)` | модель получает почти произвольный HTTP-клиент | `get_change_details(repository, number)` |
| `execute_sql(query)` | обход предметных и авторизационных границ | `list_stale_changes(repository, older_than)` |
| `manage_repository(action, payload)` | слишком много режимов и сложная схема | отдельные read-only операции |
| вернуть полный diff без лимита | контекст и стоимость не ограничены | вернуть метаданные, статистику и ограниченный фрагмент |

У инструмента должны быть:

- короткое описание назначения и условий вызова;
- закрытая схема аргументов без неизвестных полей;
- серверная авторизация;
- таймаут и ограничение размера результата;
- нормализованные категории ошибок;
- идентификатор вызова для trace;
- политика идемпотентности для операций записи.

Слишком крупный инструмент скрывает риск, а десятки микроскопических инструментов усложняют выбор модели. Границу проверяют на реальных сценариях: если модель систематически путает два инструмента, их описания или ответственность пересекаются.

## Роль MCP

Model Context Protocol (MCP) стандартизирует обнаружение и вызов инструментов, ресурсов и других возможностей. Он уменьшает количество собственных адаптеров между хостом агента и поставщиком инструментов.

MCP не решает автоматически:

- авторизацию пользователя;
- безопасность инструмента;
- идемпотентность;
- prompt injection в возвращаемых данных;
- выбор правильной степени гранулярности;
- контроль стоимости и числа вызовов.

Поэтому на учебном этапе сначала полезно реализовать внутренний `Tool`-интерфейс, а затем подключить один инструмент через MCP. Это показывает, какую часть контракта стандартизирует протокол, а какая остаётся ответственностью приложения.

MCP отвечает за подключение инструментов. Соседняя задача — куда положить инструкцию, которая нужна редко, а места в контексте занимает много. Для этого служат навыки: в постоянном контексте висит только описание, а тело подгружается по решению модели.

Связанные материалы: [вызов инструментов](../agents/02-tool-calling.md), [MCP](../agents/05-mcp.md) и [навыки](../agents/06-skills.md).

## Практика

Добавить три read-only инструмента:

```text
list_open_changes(repository, cursor, limit)
get_change_details(repository, number)
get_change_checks(repository, number)
```

Последовательность работы:

1. Описать JSON Schema аргументов и результата каждого инструмента.
2. Ограничить `limit` на стороне кода, даже если модель передала большее число.
3. Нормализовать ошибки в `not_found`, `forbidden`, `rate_limited`, `temporary` и `invalid_request`.
4. Научить агента сначала читать список, а детали — только для выбранных элементов.
5. Добавить итоговую схему отчёта и предметную валидацию.
6. Реализовать один repair-повтор для исправимой ошибки формата.
7. Посчитать число входных и выходных токенов, tool calls и длительность запуска.

## Критерии завершения

- Инструменты нельзя использовать как произвольный HTTP-клиент.
- Авторизация выполняется в коде для каждого вызова.
- Результат большого API ограничивается пагинацией и размером.
- Агент не читает детали каждого элемента без необходимости.
- Невалидный отчёт не попадает пользователю как успешный.
- Repair loop имеет явный лимит и наблюдаемую причину завершения.
- Trace связывает решение модели, tool call, результат и финальный отчёт.

---

## Типичные ошибки

- Передавать модели все доступные данные «на всякий случай».
- Считать context window бесплатным хранилищем.
- Разрешать неизвестные поля в схемах аргументов.
- Возвращать из инструмента HTML или сырой ответ внешнего API без нормализации.
- Доверять `confidence`, который модель написала сама, как откалиброванной вероятности.
- Считать MCP границей безопасности.

## Interview-ready answer

**1. Чем context engineering отличается от prompt engineering?**

- Объект проектирования — prompt engineering формулирует инструкции, context engineering управляет всем набором данных и границами запроса.
- Практика — система выбирает релевантные факты, порядок, формат, историю и результаты инструментов.
- Риск — лишний контекст повышает стоимость и может ухудшить выбор модели, а потерянный контекст лишает её нужных фактов.

**2. Как сделать tool calling безопаснее?**

- Узкий контракт — один инструмент представляет одну предметную операцию со строгой схемой.
- Проверки в коде — аргументы, авторизация, лимиты и идемпотентность не делегируются модели.
- Недоверенный результат — данные инструмента считаются вводом и не получают приоритет над системной политикой.

**3. Что даёт MCP и чего он не даёт?**

- Стандартизация — MCP задаёт общий способ объявлять и вызывать возможности внешнего сервера.
- Переносимость — хосту агента нужно меньше уникальных интеграционных адаптеров.
- Ограничение — протокол не доказывает безопасность инструмента и не заменяет авторизацию, валидацию или observability.
