Третий этап не добавляет новую «магическую» возможность. Он соединяет основы агента, контекст, инструменты и структурированный вывод в один проверяемый вертикальный срез. Именно здесь становится видно, согласованы ли контракты между слоями.

---

## Задача этапа

Нужно собрать работающий сценарий:

```text
запрос на анализ репозитория
  -> список открытых изменений
  -> выбор кандидатов
  -> чтение деталей и проверок
  -> структурированные findings
  -> валидация отчёта
```

Источником данных сначала служит фальшивый `RepositoryReader`, затем реальный GitHub или GitLab adapter. Такой порядок разделяет ошибки агентной логики и ошибки внешнего API.

---

## Почему нужен отдельный воркшоп

Компоненты могут работать отдельно и ломаться при соединении:

- схема инструмента не совпадает с типом Go;
- модель получает один идентификатор, а адаптер ожидает другой;
- ошибка провайдера теряется и выглядит как пустой результат;
- выбранный контекст не содержит факта, который требует итоговая схема;
- repair loop повторяет запрос, но не сообщает модели конкретное нарушение;
- trace не связывает LLM-вызов и внешний HTTP-запрос.

Поэтому воркшоп проверяет не количество написанного кода, а целостность одного request flow.

## Архитектурный контракт

Минимальные интерфейсы могут выглядеть так:

```go
type Model interface {
    Next(ctx context.Context, req ModelRequest) (ModelDecision, error)
}

type Tool interface {
    Name() string
    Execute(ctx context.Context, raw json.RawMessage) (ToolResult, error)
}

type RunStore interface {
    Append(ctx context.Context, runID string, event RunEvent) error
}
```

Это учебный контракт, а не готовая библиотека. Его цель — разделить три причины изменения:

- смена модели не переписывает инструменты;
- новый repository provider не меняет agent loop;
- хранение событий не определяет предметную схему отчёта.

Не стоит создавать универсальный `map[string]any` между всеми слоями. На внешней границе допустим `json.RawMessage`, но после валидации данные переводятся в именованные Go-типы.

## Вертикальный срез

### Шаг 1. Детерминированный baseline

Написать обычную функцию, которая получает список изменений и применяет явные правила: старое изменение без успешных проверок становится finding. Этот baseline нужен для сравнения стоимости и качества агента.

### Шаг 2. Фальшивый источник

Подготовить небольшой набор:

- обычное свежее изменение;
- старое изменение без активности;
- изменение с упавшими проверками;
- изменение с неоднозначным заголовком, для которого нужны детали.

Ожидаемые findings фиксируются до запуска модели.

### Шаг 3. Агентный выбор

Агент получает краткие метаданные и решает, какие детали прочитать. Каждый вызов инструмента записывается как событие запуска.

### Шаг 4. Строгий отчёт

Финальный объект проходит:

1. декодирование JSON;
2. проверку схемы;
3. проверку предметных инвариантов;
4. проверку ссылочной целостности `item_id` относительно прочитанных данных.

### Шаг 5. Реальный адаптер

Только после успешных тестов с фальшивым источником подключается API репозитория. Токен получает минимально необходимые read-only права и не выводится в логи.

## Матрица сценариев

| Сценарий | Ожидаемое поведение | Что проверяется |
| --- | --- | --- |
| Нет открытых изменений | пустой валидный отчёт | отсутствие выдуманных findings |
| Один явный риск | один finding с evidence | базовая точность |
| Нужны детали | один целевой tool call | стратегия выбора контекста |
| Инструмент вернул `rate_limited` | контролируемая ошибка или разрешённый retry | классификация отказа |
| Модель передала неизвестное поле | tool call отклонён | строгая схема |
| Модель вернула несуществующий `item_id` | отчёт отклонён | предметная валидация |
| Достигнут лимит шагов | запуск остановлен | внешний контроль цикла |
| Пользователь просит изменить репозиторий | запрос отклонён | граница read-only этапа |

Матрица становится началом eval-набора. Позже в неё добавляются реальные ошибки и сложные случаи из эксплуатации.

## Разбор наблюдаемого запуска

Для каждого запуска должна восстанавливаться последовательность:

```text
run_id
  1. вход и версия политики
  2. LLM request: модель, размер контекста
  3. решение: get_change_details(42)
  4. tool result: success, 18 KB, 240 ms
  5. LLM request: добавлено наблюдение
  6. final report: validation success
  7. stop reason: completed
```

Содержимое приватного репозитория не нужно бездумно писать в лог. Trace хранит метаданные, хеши или безопасные выборки в зависимости от политики данных. Полный payload можно хранить только при явной необходимости, ограниченном доступе и сроке жизни.

При разборе нужно ответить:

- Почему агент выбрал этот инструмент?
- Какой факт из результата попал в finding?
- Был ли лишний вызов?
- Сколько времени и токенов заняла каждая фаза?
- Почему цикл остановился?

---

## Критерии завершения

- Вертикальный срез проходит на фальшивом и реальном источнике.
- Детерминированный baseline сохранён и сравнивается с агентом.
- Негативные сценарии проверяются автоматически.
- Все внешние ответы имеют ограничение размера и таймаут.
- В trace нет токенов доступа и других секретов.
- Финальный finding ссылается только на данные, которые система действительно прочитала.
- Из одного `run_id` восстанавливается полный ход запуска.

---

## Типичные ошибки

- Подключать реальный API до появления воспроизводимого фальшивого источника.
- Считать успешный HTTP-статус доказательством качественного результата.
- Мокать сам agent loop так глубоко, что тест больше не проверяет оркестрацию.
- Менять prompt, test data и ожидаемый результат одновременно.
- Скрывать ошибки инструментов за пустым списком.
- Пытаться исправить каждый плохой ответ дополнительным prompt вместо проверки контракта и контекста.

## Interview-ready answer

**1. Зачем агентной системе детерминированный baseline?**

- Точка сравнения — baseline показывает, даёт ли агент измеримый выигрыш качества.
- Цена сложности — можно сопоставить точность, задержку, стоимость и операционные риски.
- Деградация — baseline может стать fallback для части запросов при недоступности модели.

**2. Как тестировать agent loop?**

- Фиксированные решения модели — тесты оркестрации подают заранее заданную последовательность tool call и финального ответа.
- Фальшивые инструменты — проверяются аргументы, ошибки, лимиты и события без зависимости от внешнего API.
- Evals — качество выбора и ответа измеряется отдельно на наборе примеров с реальными вызовами модели.

**3. Что должно быть в trace запуска?**

- Корреляция — один идентификатор связывает LLM-вызовы, инструменты, валидацию и остановку.
- Версии — фиксируются модель, prompt или policy и схема результата.
- Ресурсы — измеряются длительность, токены, число шагов, tool calls и категории ошибок.
- Безопасность — секреты и лишние приватные payload не попадают в telemetry.
