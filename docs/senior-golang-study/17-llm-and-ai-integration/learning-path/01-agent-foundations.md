На первом этапе важно не выбрать фреймворк, а провести границу между вызовом LLM и агентной системой. Агент начинается там, где модель выбирает следующий допустимый шаг, а приложение исполняет этот шаг внутри заданных ограничений.

---

## Задача этапа

Нужно построить минимальный `Repository Health Agent`, который отвечает на один вопрос: «Какие открытые изменения требуют внимания?». Агент получает список pull/merge request через read-only инструмент и возвращает структурированный отчёт.

На этом этапе система намеренно не умеет:

- изменять репозиторий;
- хранить долгосрочную память;
- запускаться в фоне;
- делегировать работу другим агентам;
- самостоятельно увеличивать лимит шагов.

Такое ограничение делает agent loop наблюдаемым: любой результат можно связать с исходным запросом, ответом модели и одним вызовом инструмента.

---

## Четыре способа построить систему

| Подход | Кто задаёт шаги | Когда выбирать | Основной риск |
| --- | --- | --- | --- |
| Чат-бот | пользователь задаёт следующий запрос | нужен диалог или генерация текста | история растёт, но действий нет |
| Pipeline | код задаёт линейную последовательность | шаги известны заранее и почти не ветвятся | неудобно поддерживать множество исключений |
| Workflow | код выбирает ветку по явным правилам | процесс имеет известные состояния и переходы | схема усложняется при большом числе веток |
| Агент | модель выбирает следующий разрешённый инструмент | порядок исследования нельзя надёжно определить заранее | стоимость, недетерминизм и риск неверного действия |

LLM внутри pipeline не превращает pipeline в агента. Например, последовательность `получить diff -> суммаризировать -> сохранить отчёт` полностью задана кодом. Модель генерирует один из результатов, но не решает, что делать дальше.

Агентность — не свойство SDK. Один и тот же API можно использовать как для одиночной классификации, так и для agent loop.

## Ментальная модель агента

Минимальный цикл состоит из пяти фаз:

```text
цель
  -> модель предлагает следующий шаг
  -> код проверяет решение
  -> код выполняет разрешённый инструмент
  -> результат возвращается в контекст
  -> модель завершает задачу или предлагает новый шаг
```

Код, а не модель, владеет циклом. Он хранит счётчик шагов, проверяет схему аргументов, применяет авторизацию и решает, можно ли продолжать.

Упрощённый псевдокод:

```go
for step := 0; step < maxSteps; step++ {
    decision, err := model.Next(ctx, history, tools)
    if err != nil {
        return Report{}, err
    }

    if decision.Final != nil {
        return validateReport(*decision.Final)
    }

    result, err := registry.Execute(ctx, decision.ToolCall)
    history = append(history, observation(decision.ToolCall, result, err))
}

return Report{}, ErrStepBudgetExceeded
```

Пример показывает одну идею: владелец цикла ограничивает число шагов. В production к этому добавляются таймаут, бюджет токенов, политика повторов, трассировка и безопасная остановка.

Определение агента и спектр автономности разобраны в [что такое агент](../agents/01-what-is-an-agent.md), подробная механика цикла — в [агентном цикле](../agents/03-agent-loop.md).

## ReAct и Plan → Execute

**ReAct** чередует рассуждение, действие и наблюдение. Следующий шаг выбирается после каждого результата инструмента.

**Plan → Execute** сначала строит план, затем выполняет его шаги. План можно пересматривать, но это отдельное решение, а не скрытое поведение.

| Критерий | ReAct | Plan → Execute |
| --- | --- | --- |
| Неизвестность среды | хорошо адаптируется к новым данным | первоначальный план быстро устаревает |
| Управляемость | сложнее предсказать число шагов | план можно проверить до выполнения |
| Задержка | частые обращения к модели | планирование добавляет один крупный вызов |
| Отладка | нужно читать цепочку наблюдений | проще сравнить план и факт |
| Подходящая задача | исследование репозитория | миграция или анализ с известными фазами |

Для первого агента подходит ограниченный ReAct: среда читается через один инструмент, а максимальное число итераций мало. Число выбирается как конфигурация после измерений, а не как универсальная константа.

## Когда агент не нужен

Перед реализацией нужно ответить на четыре вопроса:

1. Известен ли порядок шагов заранее?
2. Можно ли выразить выбор ветки обычными правилами?
3. Требуется ли адаптация к данным, которые появляются во время выполнения?
4. Оправдывает ли качество результата дополнительную задержку, стоимость и сложность эксплуатации?

Если первые два ответа положительные, обычно достаточно workflow. Если агент только вызывает всегда один и тот же инструмент, а затем форматирует ответ, это pipeline с лишней степенью свободы.

Практическое правило: сначала реализовать детерминированный baseline. Агент имеет смысл, только если на реальном наборе задач baseline систематически проигрывает по измеримому критерию.

## Практика

### Контракт первого инкремента

Вход:

```json
{
  "repository": "org/project",
  "question": "Какие открытые изменения требуют внимания?"
}
```

Выход:

```json
{
  "summary": "Короткий вывод",
  "findings": [
    {
      "kind": "stale_change",
      "item_id": 42,
      "evidence": "Нет обновлений семь дней"
    }
  ]
}
```

Семь дней здесь — пример учебного правила, а не универсальный порог. Реальный порог должен быть конфигурацией и зависеть от процесса команды.

### Шаги

1. Создать интерфейс `RepositoryReader` с методом чтения открытых изменений.
2. Реализовать фальшивый адаптер с тремя заранее заданными изменениями.
3. Объявить единственный инструмент `list_open_changes` со строгой схемой аргументов.
4. Реализовать цикл с лимитом шагов и общим таймаутом.
5. Проверять финальный отчёт по JSON Schema или эквивалентной Go-валидации.
6. Записать trace одного успешного и одного оборванного запуска.

## Критерии завершения

Этап завершён, если:

- можно нарисовать цикл запуска и назвать владельца каждого решения;
- один и тот же инструмент нельзя вызвать с неизвестными полями;
- превышение лимита шагов завершает запуск явной ошибкой;
- финальный ответ не принимается без валидации;
- из логов видно, какой инструмент был вызван и почему запуск остановился;
- разработчик может объяснить, почему эта задача не реализована обычным workflow.

---

## Типичные ошибки

- Называть агентом любой вызов LLM.
- Отдавать модели управление циклом без внешнего лимита.
- Сразу разрешать инструменты записи.
- Смешивать системные инструкции, пользовательский ввод и результат инструмента в одну строку.
- Проверять только красивый happy path.
- Выбирать мультиагентность до появления рабочего одиночного агента.

## Interview-ready answer

**1. Чем агент отличается от workflow?**

- Выбор шага — в workflow ветку выбирает код по правилам, в агенте следующий допустимый шаг предлагает модель.
- Цена — агент лучше адаптируется к неизвестной заранее среде, но добавляет недетерминизм, стоимость и сложность контроля.
- Граница — авторизация, валидация и выполнение действий всё равно остаются в обычном коде.

**2. Из чего состоит минимальный agent loop?**

- Контекст — цель, история наблюдений и описания разрешённых инструментов.
- Решение — финальный ответ или запрос конкретного инструмента со структурированными аргументами.
- Исполнение — код валидирует и выполняет инструмент, затем возвращает наблюдение в цикл.
- Остановка — цикл завершается по результату, ошибке, таймауту или бюджету шагов.

**3. Когда агент является оверинжинирингом?**

- Известный порядок — если шаги заранее заданы, pipeline или workflow проще и надёжнее.
- Нет измеримого выигрыша — агент не оправдан, если baseline решает задачу с нужным качеством.
- Высокий риск — при необратимых действиях степень свободы уменьшают или требуют подтверждение человека.
