## Семейство функций: Print / Sprintf / Fprintf

Имя функции = префикс (**куда**) + есть ли `f`/`ln` (**как**):

| Куда | Без формата | С форматом (`...f`) | С переводом строки (`...ln`) |
|---|---|---|---|
| в stdout | `Print` | `Printf` | `Println` |
| в строку | `Sprint` | `Sprintf` | `Sprintln` |
| в `io.Writer` | `Fprint` | `Fprintf` | `Fprintln` |
| в `error` | — | `Errorf` | — |

```go
s := fmt.Sprintf("%s=%d", k, v)        // собрать строку
fmt.Fprintf(w, "%s\n", line)           // писать в io.Writer (http.ResponseWriter, файл, Builder)
err := fmt.Errorf("open %s: %w", p, e) // ошибка с обёрткой (см. ниже)
```

Различия `Print`/`Println`: `Print` ставит пробелы только между **не-строковыми** операндами; `Println` — всегда пробелы и `\n` в конце. На практике для логов/сообщений берут `Printf`/`Sprintf` — предсказуемее.

## Универсальные глаголы: `%v` `%+v` `%#v` `%T`

Работают с **любым** типом — основной инструмент для отладки.

```go
type Point struct{ X, Y int }
p := Point{1, 2}
```

| Глагол | Что показывает | Вывод для `p` |
|---|---|---|
| `%v` | значение «по умолчанию» | `{1 2}` |
| `%+v` | значение **с именами полей** | `{X:1 Y:2}` |
| `%#v` | Go-синтаксис (как написал бы в коде) | `main.Point{X:1, Y:2}` |
| `%T` | тип значения | `main.Point` |

Указатель на структуру `%v`/`%+v` показывают со знаком `&`:

```go
fmt.Printf("%v\n", &p)   // &{1 2}
fmt.Printf("%+v\n", &p)  // &{X:1 Y:2}
```

Правило выбора:
- **`%+v`** — дефолт для логов и отладки структур (видно, какое поле какое);
- **`%#v`** — когда нужен валидный Go-литерал (тесты, генерация, точный дамп с типами);
- **`%v`** — компактно, когда поля и так понятны;
- **`%T`** — когда важен именно тип (отладка `any`, type switch).

Карты `fmt` печатает с **сортировкой по ключу** (детерминированно):

```go
fmt.Printf("%v\n", map[string]int{"b": 2, "a": 1}) // map[a:1 b:2]
```

## Глаголы по типам

**Строки и байты:**

| Глагол | Делает | Пример (`s="Go"`) |
|---|---|---|
| `%s` | строка как есть | `Go` |
| `%q` | строка в кавычках, с экранированием | `"Go"` |
| `%x` / `%X` | hex-байты | `476f` / `476F` |
| `% x` | hex с пробелами между байтами | `47 6f` |

```go
b := []byte("Hi")
fmt.Printf("%s %v\n", b, b)  // Hi [72 105]  — %s декодирует байты, %v показывает числа
```

**Целые числа:**

| Глагол | Система | `255` → |
|---|---|---|
| `%d` | десятичная | `255` |
| `%b` | двоичная | `11111111` |
| `%o` | восьмеричная | `377` |
| `%x` / `%X` | hex | `ff` / `FF` |
| `%#x` | hex с префиксом | `0xff` |
| `%c` | символ по code point | `ÿ` |
| `%q` | символ в кавычках | `'ÿ'` |
| `%U` | Unicode-нотация | `U+00FF` |

```go
fmt.Printf("%d %c %q %U\n", 'A', 'A', 'A', 'A') // 65 A 'A' U+0041
```

**Числа с плавающей точкой:**

| Глагол | Формат | `3.14159` → |
|---|---|---|
| `%f` | без экспоненты | `3.141590` |
| `%.2f` | 2 знака после точки | `3.14` |
| `%e` / `%E` | экспоненциальная | `3.141590e+00` |
| `%g` | компактная (`%e` или `%f` по ситуации) | `3.14159` |

**Прочее:**

| Глагол | Для чего | Пример |
|---|---|---|
| `%t` | bool | `true` |
| `%p` | адрес указателя | `0x43f68d38e020` |
| `%T` | тип | `int`, `*main.Point` |
| `%%` | литеральный знак `%` | `%` |

## Флаги: ширина, точность, выравнивание

Синтаксис глагола: `%[флаги][ширина][.точность]глагол`.

```go
fmt.Printf("%5d|%-5d|%05d\n", 42, 42, 42)   // "   42|42   |00042"
fmt.Printf("%8.2f\n", 3.14159)               // "    3.14"  (ширина 8, 2 знака)
fmt.Printf("%-10s|\n", "hi")                 // "hi        |" (выравнивание влево)
```

- **ширина** — минимальное число символов (добивает пробелами);
- **`.точность`** — для float число знаков после точки; для строки — обрезка до N символов; для `%d` — минимум цифр;
- **`-`** — выравнивание влево;
- **`0`** — добивать нулями (числа);
- **`+`** — всегда печатать знак (`+42`);
- **пробел** — пробел вместо `+` для положительных;
- **`#`** — «альтернативный» формат (`0x` для hex, Go-синтаксис для `%#v`).

Удобно: `*` берёт ширину/точность из аргумента — `fmt.Printf("%.*f", 2, x)` (точность = 2 из аргумента).

## Интерфейсы: Stringer, Formatter, GoStringer

`fmt` спрашивает у значения, как себя печатать, через интерфейсы — это позволяет задать своё представление.

```go
// Stringer — используется для %v и %s
type Stringer interface{ String() string }

type Color int
func (c Color) String() string { return [...]string{"red", "green", "blue"}[c] }

fmt.Printf("%v %s\n", Color(2), Color(0)) // blue red
```

| Интерфейс | Метод | Когда вызывается |
|---|---|---|
| `fmt.Stringer` | `String() string` | для `%v`, `%s` (и других строковых) |
| `error` | `Error() string` | для `%v`, `%s`, если тип — ошибка |
| `fmt.GoStringer` | `GoString() string` | для `%#v` |
| `fmt.Formatter` | `Format(f State, verb rune)` | полный контроль над **всеми** глаголами |

`%#v` не вызывает `String()` — он показывает структуру/Go-синтаксис. Это важно: если в логе нужен «человеческий» вид — `%v`/`%s`, если сырой — `%#v`.

⚠️ **Бесконечная рекурсия в `String()`:** если внутри `String()`/`Error()` напечатать сам ресивер через `%v`/`%s`, `fmt` снова позовёт `String()` → переполнение стека:

```go
func (c Color) String() string {
    return fmt.Sprintf("%v", c) // ⚠️ infinite recursion → stack overflow
}
```

Лечение: приводи к базовому типу — `fmt.Sprintf("%d", int(c))`.

## Ошибки форматирования и `%w`

`%w` — особый глагол **только для `fmt.Errorf`**: оборачивает ошибку, сохраняя цепочку для `errors.Is`/`As`.

```go
err := fmt.Errorf("load config: %w", io.EOF)
errors.Is(err, io.EOF) // true — связь сохранена
```

`%v` для ошибки лишь подставит текст, **связь потеряется** (`errors.Is` вернёт `false`). Подробно про `%w` vs `%v`, несколько `%w`, кастомные `Error()` — в [01-go-core/05-error-handling](../01-go-core/05-error-handling.md#оборачивание-с-контекстом-правила-w).

## Потокобезопасность: fmt из многих горутин

Много горутин одновременно пишут в консоль через `fmt.Println` — что произойдёт? Вопрос распадается на два разных: будет ли **data race** (порча памяти, срабатывание `-race`) и будет ли **перемешивание вывода** (torn lines — строки, «порванные» чужим выводом). Ответы разные:

| Свойство | Гарантируется? | Кем |
|---|---|---|
| Нет data race при конкурентных вызовах `fmt.Print*` | **да** | внутреннее состояние в `sync.Pool`, общего мутабельного нет |
| Один вызов (`Println`/`Printf`) выводится целиком, не рвётся | **де-факто да** (не документировано) | один `Write` → один сисколл; непрерывность обеспечивает ядро |
| Несколько вызовов подряд атомарны вместе | **нет** | между вызовами вклинивается другая горутина |
| Порядок строк между горутинами | **нет** | планировщик |
| `fmt.Fprintf` в `bufio.Writer` из горутин | **нет — это data race** | `bufio` не синхронизирован |

Важно: в документации `fmt` про потокобезопасность **не написано ничего**. «Строка не рвётся» — свойство реализации плюс поведения ядра, а не контракт API.

### Под капотом: один вызов = один Write

Цепочка `fmt.Println` (go1.26, `src/fmt/print.go`):

```
fmt.Println(a...)
  └─ Fprintln(os.Stdout, a...)
       ├─ p := newPrinter()      // взять *pp из sync.Pool (ppFree)
       ├─ p.doPrintln(a)         // отформатировать ВСЁ в p.buf ([]byte)
       ├─ w.Write(p.buf)         // ОДИН вызов Write всем буфером
       └─ p.free()               // вернуть pp в пул
```

<details>
<summary>Исходники: Fprintln, структура pp, newPrinter/free (go1.26)</summary>

```go
// src/fmt/print.go
var ppFree = sync.Pool{ ... } // пул принтеров *pp — переиспользование без аллокаций

func Fprintln(w io.Writer, a ...any) (n int, err error) {
	p := newPrinter()      // ppFree.Get()
	p.doPrintln(a)         // формирует весь вывод в p.buf
	n, err = w.Write(p.buf) // один Write
	p.free()               // ppFree.Put()
	return
}

func Println(a ...any) (n int, err error) {
	return Fprintln(os.Stdout, a...)
}
```

Сам принтер `pp` — это буфер + всё изменяемое состояние одного вызова. Именно потому, что каждый вызов получает **свой** экземпляр, никакой синхронизации не нужно:

```go
// pp is used to store a printer's state and is reused with sync.Pool to avoid allocations.
type pp struct {
	buf buffer            // type buffer []byte — сюда пишется ВЕСЬ вывод вызова

	arg   any             // текущий печатаемый аргумент
	value reflect.Value   // он же, если печать идёт через reflect

	fmt fmt               // внутренний форматтер (флаги, ширина/точность, intbuf [68]byte)

	reordered  bool       // формат использовал перестановку аргументов (%[1]d)
	goodArgNum bool       // последняя перестановка была корректной
	panicking  bool       // защита от рекурсии panic внутри печати
	erroring   bool       // сейчас печатается ошибка формата (%!d(...)) — не звать методы
	wrapErrs   bool       // формат может содержать %w
	wrappedErrs []int     // индексы аргументов, обёрнутых через %w
}

func newPrinter() *pp {
	p := ppFree.Get().(*pp) // взять из пула (или пул создаст новый)
	p.panicking = false     // сбросить флаги — буфер уже сброшен в free()
	p.erroring = false
	p.wrapErrs = false
	p.fmt.init(&p.buf)      // форматтер пишет прямо в p.buf
	return p
}

func (p *pp) free() {
	// Пул должен хранить записи примерно одинаковой стоимости (issue 23199):
	// раздутый буфер (>64 КБ) выбрасываем, переиспользуем только сам принтер —
	// иначе один Sprintf гигантской строки навсегда «прописал» бы мегабайты в пуле.
	if cap(p.buf) > 64*1024 {
		p.buf = nil
	} else {
		p.buf = p.buf[:0] // обнулить длину, ёмкость сохранить — реюз без аллокаций
	}
	if cap(p.wrappedErrs) > 8 {
		p.wrappedErrs = nil
	}
	p.arg = nil               // не держать ссылки — иначе пул мешал бы GC собрать аргументы
	p.value = reflect.Value{}
	p.wrappedErrs = p.wrappedErrs[:0]
	ppFree.Put(p)
}
```

Попутные детали: буфер возвращается в пул с `cap` до 64 КБ — поэтому повторные `Sprintf` обычно вообще не аллоцируют; `p.arg = nil` обязателен, иначе пул удерживал бы напечатанные значения от GC.
</details>

Два следствия:

1. **Никакого глобального мьютекса в `fmt` нет.** Гонок не возникает потому, что каждый вызов работает со **своим** объектом-принтером `pp` из `sync.Pool` (пул переиспользуемых объектов: `Get` выдаёт свободный или создаёт новый, `Put` возвращает — так экономятся аллокации). Общего изменяемого состояния между вызовами просто нет.
2. **Весь вывод вызова уходит одним `os.Stdout.Write`** → одним сисколлом `write(2)`. Дальше непрерывность куска обеспечивает уже **ядро ОС**: один `write()` оно, как правило, выводит целиком (для pipe это гарантировано POSIX при размере ≤ `PIPE_BUF`, обычно 4 КБ; для терминала и файла — де-факто так же, записи по одному file description сериализуются). Исключение — очень большой буфер: ядро может сделать **partial write**, `os.File.Write` дозапишет остаток вторым сисколлом, и между кусками может вклиниться чужой вывод.

Попутный факт: stdout в Go **не буферизован** — каждый `Println` это отдельный сисколл (в отличие от `printf` в C, где stdio копит в буфер). Поэтому тысячи мелких `Print` в цикле — это тысячи сисколлов.

### Демо: два вызова рвутся, один — нет

Запускаем 8 горутин, каждая в цикле печатает свою строку `[g<номер> iter <i> ]`, но собирает её **двумя** вызовами `fmt` подряд. Идея: между этими двумя вызовами планировщик может переключиться на другую горутину, и её вывод вклинится в середину нашей строки (go1.26.1 darwin/arm64, Apple M3 Max):

```go
func main() {
    var wg sync.WaitGroup
    for g := 0; g < 8; g++ {
        wg.Add(1)
        go func(g int) {
            defer wg.Done()
            for i := 0; i < 2000; i++ {
                fmt.Print("[g", g, " ")     // вызов 1 — начало строки
                fmt.Println("iter", i, "]") // вызов 2 — хвост строки; с вызовом 1 НЕ атомарен
            }
        }(g)
    }
    wg.Wait()
}
```

Ожидали бы 16000 ровных строк вида `[g3 iter 42 ]`, но в выводе попадается такое:

```
[g0 [g1 iter 0 ]     ← горутина 0 напечатала "[g0 ", тут её вытеснили, и горутина 1
                        успела выдать целиком свою "[g1 iter 0 ]"
iter 1 ]             ← а «хвост» строки горутины 0 ("iter 1 ]") вышел только теперь, отдельно
[g7 [g5 iter 3 ]     ← то же самое между g7 и g5
```

Порванных строк: **1268 из 16000**. Теперь та же программа, но строка собирается **одним** вызовом:

```go
for i := 0; i < 2000; i++ {
	fmt.Printf("[g%d iter %d ]\n", g, i) // один вызов = один Write = один сисколл
}
```

Порванных строк: **0 из 16000**. Вывод: перемешивание было не «магией fmt», а тем, что между двумя `fmt`-вызовами есть окно для переключения горутины. Правило «одна логическая строка — один вызов `Printf`» это окно убирает.

### Эксперимент: может ли порваться сама строка? И про порядок горутин

Может ли `go fmt.Print("hello ")` + `go fmt.Print("world\n")` дать `heworld` / `llo` — разрыв **внутри** строки? Проверка: программа из двух горутин, 2000 запусков (go1.26.1 darwin/arm64, M3 Max):

```go
var wg sync.WaitGroup
wg.Add(2)
go func() { defer wg.Done(); fmt.Print("hello ") }()
go func() { defer wg.Done(); fmt.Print("world\n") }()
wg.Wait()
```

| Вывод | Раз | Доля |
|---|---|---|
| `world\nhello ` | 1942 | 97% |
| `hello world\n` | 58 | 3% |
| разрывы внутри строк (`heworld` и т.п.) | **0** | 0% |

Два вывода из эксперимента:

1. **Байты внутри одного вызова не рвутся никогда** — короткая строка уходит одним непрерывным `write(2)`, ядро его не дробит. Перемешивается только **порядок целых кусков**.
2. **Порядок оказался «обратным» интуиции**: в 97% случаев первым вышел `world`, хотя его горутина запущена **второй**. Это не случайность, а деталь планировщика — слот **`runnext`**: свежесозданная горутина кладётся в `runnext` своего P, **вытесняя** оттуда предыдущую (та уходит в локальную очередь). Когда `main` блокируется на `wg.Wait()`, P первым делом берёт `runnext` — то есть последнюю запущенную горутину («world»), и лишь потом очередь («hello»). Итого порядок запуска `go func()` ≠ порядок исполнения — и даже систематически инвертирован для последней запущенной. Подробнее про очереди планировщика — [runtime-scheduler/01-scheduler-and-preemption](../01-go-core/runtime-scheduler/01-scheduler-and-preemption.md).

### Ловушка: bufio.Writer поверх stdout

Обернуть stdout в `bufio.Writer` ради производительности и писать из горутин — уже **настоящий data race**: `bufio` не синхронизирован, конкурентные `Write` бьются за общий буфер (порча данных, а не только порядок). Тот же код под `-race`:

```
WARNING: DATA RACE
Read at 0x00c000190068 by goroutine 9:
  bufio.(*Writer).Available()
  bufio.(*Writer).Write()
  fmt.Fprintf()
```

Нужен свой мьютекс вокруг записи (или писать через `log`, см. ниже).

### Контраст: fmt vs log vs slog для конкурентного вывода

| | `fmt.Println` | `log.Printf` | `slog` |
|---|---|---|---|
| Мьютекс на запись | нет | да (`Logger.outMu`) | да (в хендлере) |
| Целостность строки | де-факто (один Write) | гарантирована | гарантирована |
| Кто отвечает за синхронизацию при записи в любой `io.Writer` (`bytes.Buffer`, `bufio`…) | **сам writer** — `Fprintf` лишь зовёт `w.Write`, с небезопасным writer'ом это data race | **логгер** — сериализует все записи своим мьютексом, writer может быть любым | **логгер** (хендлер) — аналогично |
| Фичи логирования: уровни INFO/ERROR, trace_id из `ctx`, структурный вывод (JSON/key=value) | нет — это только форматирование | только префикс и timestamp | да — всё перечисленное |

`log.Logger` держит явный `sync.Mutex` (`outMu`) вокруг каждого `l.out.Write(*buf)` — поэтому даже потоконебезопасный writer (тот же `bytes.Buffer`) безопасен, если писать в него **через логгер**: к `Write` в один момент времени обращается ровно одна горутина. Для сервисов конкурентный вывод — это всегда `log`/`slog` ([03-slog](./03-slog.md)); `fmt` — для CLI-вывода и отладки.

Про то, что такое data race и happens-before — [01-go-core/concurrency-and-performance/01-memory-model](../01-go-core/concurrency-and-performance/01-memory-model.md).

## Частые ошибки

Когда глагол не подходит типу, `fmt` **не паникует**, а печатает диагностику прямо в вывод:

```go
fmt.Printf("%d %s\n", "str", 42) // %!d(string=str) %!s(int=42)
```

- **`%!verb(type=value)`** — глагол не совпал с типом. `%!d(string=...)` = ждали число, дали строку.
- **`%!(EXTRA ...)`** — аргументов больше, чем глаголов.
- **`%!(MISSING)`** — аргументов меньше, чем глаголов.

Другие распространённые:
- **`%v` от `[]byte`** даёт числа (`[72 105]`), а не текст — для текста нужен `%s`.
- **`%d` от `rune`/`byte`** печатает **число** (code point), не символ — символ это `%c`.
- **`%s` от структуры без `String()`** напечатает `{...}` — для имён полей удобнее `%+v`.
- **`%p` vs `%v` для указателя**: `%p` — адрес, `%v` — `&{значение}`.
- **Забытый `\n`**: `Printf` не добавляет перевод строки (в отличие от `Println`).
- **`go vet`** ловит несовпадение глаголов и аргументов на этапе проверки — не игнорируй его предупреждения про `fmt`.

## Interview-ready answer

**1. Чем отличаются `%v`, `%+v`, `%#v`?**

- `%v` — значение по умолчанию (`{1 2}`); `%+v` — с именами полей (`{X:1 Y:2}`), дефолт для логов; `%#v` — валидный Go-синтаксис с типом (`main.Point{X:1, Y:2}`). `%#v` не вызывает `String()`, остальные — вызывают.

**2. Как `fmt` узнаёт, что печатать для `%v`/`%s`?**

- Если тип реализует `fmt.Stringer` (`String() string`) или `error` (`Error() string`) — зовёт его. Для полного контроля есть `fmt.Formatter`. Для `%#v` — `GoStringer`.

**3. Чем `%w` отличается от `%v` в ошибках?**

- `%w` (только в `Errorf`) оборачивает ошибку, сохраняя цепочку → `errors.Is/As` работают. `%v` лишь вставляет текст, связь теряется.

**4. Что выведет `%d` для строки?**

- `%!d(string=...)` — `fmt` не паникует, а печатает диагностику о несовпадении глагола и типа. `go vet` ловит это статически.

**5. Как напечатать `[]byte` как текст?**

- `%s` (декодирует байты в строку). `%v` покажет числа `[72 105]`.

**6. Как сделать ширину/точность из переменной?**

- Через `*`: `fmt.Printf("%*.*f", width, prec, x)` — берёт ширину и точность из аргументов.

**7. Потокобезопасен ли fmt.Println из многих горутин?**

- Data race нет (у каждого вызова свой принтер из `sync.Pool`, общего состояния и мьютекса в fmt нет), и один вызов де-факто выводится целиком — весь буфер уходит одним `Write`/сисколлом. Но это не документированный контракт: несколько вызовов подряд не атомарны (строки из двух `Print` рвутся чужим выводом), порядок между горутинами не определён, а очень большой буфер может разбиться partial write'ом. Правило: одна строка — один `Printf`; для конкурентного логирования — `log`/`slog` (у них мьютекс и гарантированная целостность записи).

**8. Чем опасна обёртка bufio.Writer над stdout при записи из горутин?**

- `bufio.Writer` не синхронизирован: конкурентные `Fprintf` в него — настоящий data race на общем буфере (ловится `-race`), а не просто перемешанный вывод. Нужен свой мьютекс вокруг записи либо `log.Logger` поверх (он сам сериализует `Write` мьютексом).
