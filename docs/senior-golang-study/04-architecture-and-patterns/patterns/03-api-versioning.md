Задача версионирования — развивать API, не ломая уже работающих клиентов. Сложность в том, что клиент обновляется не по команде поставщика: мобильное приложение живёт на телефоне пользователя, чужой сервис деплоится по своему расписанию, а сообщение в Kafka может быть прочитано через неделю после публикации. Поэтому новая версия контракта обязана какое-то время сосуществовать со старой.

Материал охватывает три среды с разными правилами: HTTP REST, gRPC с Protobuf и событийные системы.

## Стратегии версионирования

| Стратегия | Как выглядит | Плюсы | Минусы |
|---|---|---|---|
| URL path | `/api/v1/users`, `/api/v2/users` | Явно, кешируется | Дублирование кода, URL загрязнение |
| Query param | `/api/users?version=2` | Просто добавить | Легко забыть, плохо кешируется |
| Header | `Accept: application/vnd.myapi.v2+json` | Чистые URL | Менее видимо, сложнее тестировать |
| Content negotiation | `Accept: application/json; version=2` | RESTful | Сложная реализация |
| No versioning (additive only) | Никогда не ломать контракт | Нет версий = нет проблем | Требует строгой backward compat |

**Рекомендация для большинства API:** версия в пути (`/v1/`, `/v2/`).

Причины, по которым этот вариант выигрывает у заголовков, практические:

- Версия видна в логах, трассировках и метриках без разбора заголовков — по маршруту сразу понятно, кто ещё сидит на `/v1/`.
- Кеш и CDN ключуются по URL, поэтому разные версии не смешиваются автоматически. Заголовочная схема требует правильного `Vary`, который легко забыть, — и клиент v1 получит из кеша ответ v2.
- Запрос воспроизводится одной строкой в браузере или `curl` без ручной сборки заголовков.

Плата — дублирование маршрутов и «грязный» URL. Дублирование снимается общим доменным слоем и разными DTO на выходе (пример ниже), а чистота URL здесь стоит дешевле, чем отладка кеша.

## Обратная совместимость: что ломает, что нет

Изменение считается ломающим, если клиент, написанный под старый контракт и не изменившийся ни на строку, начинает работать неправильно. Проверка всегда идёт со стороны такого клиента, а не со стороны кода сервера.

### REST / JSON

**Безопасные изменения (non-breaking):**

```json
// Добавить новое поле в ответ — OK
// v1 клиент просто проигнорирует его
{
  "id": 123,
  "name": "Alice",
  "email": "alice@example.com",  // новое поле — безопасно
  "created_at": "2024-01-01"     // новое поле — безопасно
}
```

```
✓ Добавить новое опциональное поле в ответ
✓ Добавить новый endpoint
✓ Добавить новый опциональный query параметр
✓ Расширить enum новым значением (если клиент делает default case)
✓ Изменить внутреннюю логику без изменения контракта
```

**Ломающие изменения (breaking):**

```
✗ Удалить или переименовать поле
✗ Изменить тип поля (string → int)
✗ Сделать опциональное поле обязательным
✗ Изменить семантику существующего поля
✗ Изменить HTTP статус-код для существующего кейса
✗ Удалить значение из enum
✗ Изменить структуру URL
```

Два пункта из этого списка обычно спорят.

Расширение enum новым значением безопасно только при условии, что клиент обрабатывает неизвестное значение через ветку по умолчанию. Если клиент разбирает статус через `switch` без `default` или через строгий парсер, новое значение `partially_refunded` уронит его так же надёжно, как удаление поля. Поэтому политику «мы можем добавлять значения» фиксируют в документации с самого начала, а не вводят задним числом.

Изменение семантики поля опаснее остальных: контракт формально не менялся, схема проходит валидацию, и поломка не видна ни в одном автотесте. Классический случай — поле `total`, которое раньше содержало сумму без доставки, а теперь с ней. Клиент продолжает читать число и складывать его со стоимостью доставки повторно.

### Protobuf / gRPC

Protobuf специально разработан для прямой и обратной совместимости при соблюдении правил.

Правила эти следуют из формата передачи. В сериализованном сообщении нет имён полей: каждое поле кодируется парой «номер + тип кодирования», а имя существует только в `.proto`-файле на этапе компиляции. Отсюда сразу два вывода. Переименовать поле безопасно — по проводу ничего не меняется. Переиспользовать номер удалённого поля нельзя — старый клиент, встретив номер `2`, прочитает его по своей схеме и молча получит чужие данные в поле `name`.

**Безопасные изменения:**

```protobuf
// v1
message User {
  int64  id   = 1;
  string name = 2;
}

// v2 — safe changes
message User {
  int64  id    = 1;
  string name  = 2;
  string email = 3;  // ✓ новое поле с новым номером
  // int32 age = 4;  // ✓ добавить новое поле
}
```

**Ломающие изменения:**

```protobuf
// Так делать нельзя:
message User {
  int64  id    = 1;
  // string name = 2;  ✗ удалено — старые клиенты сломаются
  string email = 2;    // ✗ номер 2 переиспользован под другое поле и тип
  string name  = 3;    // ✗ изменён номер поля
}

// Правильно при удалении поля:
message User {
  int64  id    = 1;
  reserved 2;          // ✓ зарезервировать номер
  reserved "name";     // ✓ зарезервировать имя
  string email = 3;
}
```

`reserved` не влияет на передачу данных — это защита времени компиляции: попытка снова занять номер `2` или имя `name` не пройдёт сборку `protoc`, и ошибка обнаружится в момент правки схемы, а не в production у клиента.

**Правила Protobuf:**
- Номера полей неизменны навсегда
- Удалённые номера → `reserved`
- Изменить тип поля нельзя, кроме совместимых по кодированию пар: `int32` ↔ `int64` ↔ `uint32` ↔ `uint64` ↔ `bool` (все они пишутся одним и тем же varint), `sint32` ↔ `sint64`, `fixed32` ↔ `sfixed32`, `bytes` ↔ `string` для корректного UTF-8
- Добавлять новые поля всегда можно

Совместимость по кодированию не означает совместимость по значению: `int64` со значением, не влезающим в `int32`, у старого клиента усечётся. Формат не сломается, число будет неверным.

## Версионирование REST API

### Параллельные версии

```go
// router.go
v1 := router.PathPrefix("/api/v1").Subrouter()
v1.HandleFunc("/users/{id}", v1Handler.GetUser)
v1.HandleFunc("/orders", v1Handler.CreateOrder)

v2 := router.PathPrefix("/api/v2").Subrouter()
v2.HandleFunc("/users/{id}", v2Handler.GetUser)  // новая версия
v2.HandleFunc("/orders", v1Handler.CreateOrder)  // v1 повторно используется если не менялось
```

**Версионирование через адаптеры (избегать дублирования):**

```go
// domain модель одна
type Order struct {
    ID         OrderID
    CustomerID UserID
    Items      []OrderItem
    TotalPrice Money
    Status     OrderStatus
    CreatedAt  time.Time
}

// v1 response: старый формат
type OrderResponseV1 struct {
    ID       string `json:"id"`
    Customer string `json:"customer_id"`  // просто ID
    Total    int64  `json:"total_cents"`  // в центах
    Status   string `json:"status"`
}

// v2 response: новый формат
type OrderResponseV2 struct {
    ID         string      `json:"id"`
    Customer   CustomerDTO `json:"customer"`  // объект с деталями
    Total      MoneyDTO    `json:"total"`     // { amount, currency }
    Status     string      `json:"status"`
    CreatedAt  time.Time   `json:"created_at"`
}
```

### API Gateway versioning

```
Client v1 ──► /api/v1/* ──► API Gateway ──► OrderService (внутренний, без версии)
                                               ↑
Client v2 ──► /api/v2/* ──► API Gateway ──────┘ (с трансформацией payload)
```

Версионирование на уровне Gateway позволяет поддерживать несколько внешних версий с одним внутренним сервисом.

## gRPC и Protobuf

### Package versioning

```protobuf
// orders/v1/orders.proto
syntax = "proto3";
package orders.v1;
option go_package = "github.com/myco/api/orders/v1;ordersv1";

service OrderService {
  rpc CreateOrder(CreateOrderRequest) returns (CreateOrderResponse);
  rpc GetOrder(GetOrderRequest) returns (GetOrderResponse);
}

// orders/v2/orders.proto  ← новая версия при breaking change
syntax = "proto3";
package orders.v2;
option go_package = "github.com/myco/api/orders/v2;ordersv2";

service OrderService {
  rpc CreateOrder(CreateOrderRequest) returns (CreateOrderResponse);
  rpc GetOrder(GetOrderRequest) returns (GetOrderResponse);
  rpc BatchGetOrders(BatchGetOrdersRequest) returns (BatchGetOrdersResponse);  // новое
}
```

### gRPC Server reflection + versioning

```go
// Сервер поддерживает обе версии
grpcServer := grpc.NewServer()
ordersv1.RegisterOrderServiceServer(grpcServer, v1Handler)
ordersv2.RegisterOrderServiceServer(grpcServer, v2Handler)
reflection.Register(grpcServer)  // для grpcurl и tooling
```

## Версионирование схем событий

События в брокере — особый случай. В REST старый формат исчезает вместе с выключенной версией сервиса: как только `/v1/` снят, старых ответов больше не существует. Сообщение в Kafka живёт в топике весь срок хранения (`retention`), поэтому потребитель, перечитывающий партицию с начала или разбирающий накопившееся отставание, встретит формат, который производитель перестал писать месяц назад. Обработчик обязан понимать все версии, которые ещё лежат в топике.

### Schema Registry (Avro/Protobuf)

```
Producer ──► Schema Registry ──► Kafka
                  ↑
Consumer ◄────────┘ (валидирует schema при чтении)
```

**Совместимость схем (Confluent Schema Registry):**

| Режим | Правило | Когда использовать |
|---|---|---|
| BACKWARD | Новая схема читает старые данные | Консьюмеры обновляются первыми |
| FORWARD | Старая схема читает новые данные | Продюсеры обновляются первыми |
| FULL | Оба направления | Максимальная безопасность |
| NONE | Без проверок | Dev/staging только |

### Envelope pattern (без Schema Registry)

Идея конверта: неизменная часть события (идентификатор, тип, версия, время) лежит снаружи и читается всегда, а меняющаяся часть — внутри, как ещё не разобранный JSON. Обработчик сначала смотрит на тип и версию, потом выбирает, какой структурой разбирать содержимое.

```go
// Событие с версией в payload
type Event struct {
    ID         string          `json:"id"`
    Type       string          `json:"type"`        // "order.created"
    Version    string          `json:"version"`     // "v1", "v2"
    OccurredAt time.Time       `json:"occurred_at"`
    Payload    json.RawMessage `json:"payload"`     // разбирается по версии
}

// Consumer с multi-version handling
func (h *Handler) Handle(ctx context.Context, event Event) error {
    switch event.Type + "@" + event.Version {
    case "order.created@v1":
        var p OrderCreatedV1
        if err := json.Unmarshal(event.Payload, &p); err != nil {
            return fmt.Errorf("decode order.created@v1 %s: %w", event.ID, err)
        }
        return h.handleV1(ctx, p)
    case "order.created@v2":
        var p OrderCreatedV2
        if err := json.Unmarshal(event.Payload, &p); err != nil {
            return fmt.Errorf("decode order.created@v2 %s: %w", event.ID, err)
        }
        return h.handleV2(ctx, p)
    default:
        // Версия новее той, что знает этот экземпляр обработчика.
        // Пропуск со счётчиком — сознательный выбор: см. пояснение ниже.
        h.metrics.Inc("events.unknown_version", "type", event.Type, "version", event.Version)
        h.log.Warn("unknown event version", "id", event.ID, "type", event.Type, "version", event.Version)
        return nil
    }
}
```

Ветка по умолчанию — место, где принимается решение о поведении при неизвестной версии, и вариантов здесь три:

- **Пропустить со счётчиком** (код выше). Подходит для событий, которые не обязаны быть обработаны каждым потребителем: аналитика, уведомления. Смещение двигается дальше, отставание не растёт, а метрика показывает, что часть событий проходит мимо.
- **Вернуть ошибку и остановиться.** Подходит, когда пропуск события означает потерю денег или рассинхронизацию состояния. Ценой становится остановка партиции: обработчик не двинется дальше, пока его не обновят.
- **Отправить в dead letter queue.** Компромисс: смещение двигается, событие сохраняется для повторной обработки после обновления потребителя.

Молчаливый `return nil` без метрики опаснее всех трёх вариантов: события исчезают, и узнать об этом можно только из расследования по жалобе.

## Вывод версии из эксплуатации

```
Timeline:

v1 launch ──► v2 launch ──► v1 deprecation ──► v1 sunset ──► v1 removed
    │               │               │                │
    │               │         Announce +         Breaking
    │               │         Deprecation         change!
    │               │         header
    │               │
    │         Migrate clients
    │         during overlap
    │
 Clients use v1
```

**Заголовки объявления:**

Два заголовка описывают разные точки на этой шкале и стандартизованы отдельными документами.

| Заголовок | Документ | Значение | Смысл |
| --- | --- | --- | --- |
| `Deprecation` | RFC 9745 (март 2025) | метка времени структурированных полей: `@<unix-time>` | Когда версия объявлена устаревшей |
| `Sunset` | RFC 8594 | HTTP-дата | Когда версия перестанет отвечать |

```http
HTTP/1.1 200 OK
Deprecation: @1735689600
Sunset: Sun, 01 Jun 2025 00:00:00 GMT
Link: <https://api.example.com/v2/users>; rel="successor-version"
```

RFC 9745 требует, чтобы дата в `Sunset` не была раньше даты в `Deprecation`: объявить об устаревании задним числом после отключения бессмысленно.

Ранние черновики заголовка допускали значение `Deprecation: true`, и многие существующие API до сих пор шлют именно его. Клиентский код, который разбирает заголовок, должен быть готов к обеим формам, а новый сервер — отдавать форму из RFC.

**Минимальный период сосуществования версий:**
- Внутренние API: 1-3 месяца
- Публичные API: 6-12 месяцев
- Крупные платформы (AWS, Stripe): 1-2 года

Разброс объясняется не масштабом компании, а тем, кто и как быстро может обновить клиента. Внутренний сервис обновляет своя же команда за спринт. Публичный API вызывают мобильные приложения, где старая версия остаётся на телефонах у части пользователей неограниченно долго, и интеграции, которые никто не сопровождает.

**Наблюдение за использованием устаревшей версии:**

```go
// Счётчик обращений к устаревшему endpoint
func DeprecationMiddleware(version, deprecation, sunset string) Middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            w.Header().Set("Deprecation", deprecation) // "@1735689600"
            w.Header().Set("Sunset", sunset)           // HTTP-дата
            metrics.Inc("api.deprecated.calls",
                "version", version,
                "path", r.URL.Path,
                "client", r.Header.Get("User-Agent"),
            )
            next.ServeHTTP(w, r)
        })
    }
}
```

Метка клиента в метрике важнее самого счётчика. Цифра «на v1 ещё 4% запросов» не позволяет ни выключить версию, ни написать письмо: непонятно, это один забытый скрипт или половина мобильной аудитории. Разбивка по клиенту превращает отключение в список адресатов.

## Contract testing со стороны потребителя

Проблема микросервисов: как убедиться, что изменение не сломает потребителей?

```
Стандартный подход (ненадёжный):
  Service A меняет API → деплоит → Service B ломается в production

Contract testing (Pact):
  1. Service B (consumer) пишет contract: "я ожидаю такой ответ"
  2. Contract публикуется в Pact Broker
  3. Service A (provider) верифицирует свой API против контрактов
  4. CI: Service A не деплоится если нарушает контракт

  Provider ──verify──► Pact Broker ◄──publish── Consumer
```

```go
// Pact consumer test (в Service B)
func TestOrderServiceContract(t *testing.T) {
    pact := dsl.Pact{Consumer: "service-b", Provider: "order-service"}
    
    pact.AddInteraction().
        Given("order 123 exists").
        UponReceiving("a request for order 123").
        WithRequest(dsl.Request{
            Method: "GET",
            Path:   dsl.String("/api/v1/orders/123"),
        }).
        WillRespondWith(dsl.Response{
            Status: 200,
            Body: dsl.Like(map[string]interface{}{
                "id":     "123",
                "status": "pending",
            }),
        })
    // ...
}
```

## Interview-ready answer

**1. Как версионировать REST API?**

- Главное — версия в пути (`/v1/`, `/v2/`): видна в логах и метриках, безопасна для кеша, воспроизводится одной строкой.
- Правило заведения версии — только ломающее изменение; новые опциональные поля и новые endpoint'ы живут в текущей версии.
- Критерий ломающего — клиент, не изменившийся ни на строку, начинает работать неправильно.
- Дублирование кода — снимается общим доменным слоем и отдельными DTO на каждую версию ответа.

**2. Как обеспечивается совместимость в Protobuf?**

- Причина правил — в сериализованном сообщении нет имён полей, только номера и тип кодирования.
- Отсюда — переименование поля безопасно, а переиспользование номера удалённого поля даёт молчаливую подмену данных у старого клиента.
- Защита — `reserved` на номер и имя: повторный захват не пройдёт компиляцию `protoc`.
- Смена типа — допустима только внутри совместимых по кодированию групп, и даже тогда значение может усечься.

**3. Чем версионирование событий отличается от REST?**

- Причина отличия — сообщение живёт в топике весь срок хранения, поэтому старый формат встречается и после того, как его перестали писать.
- Решение без реестра схем — конверт: тип и версия снаружи, содержимое отдельным полем, разбор по версии.
- Решение с реестром — Schema Registry с режимом совместимости BACKWARD или FULL и валидацией при публикации.
- Ветка неизвестной версии — осознанный выбор из трёх: пропустить со счётчиком, остановить партицию, отправить в DLQ.

**4. Как правильно выводить версию из эксплуатации?**

- Шаг 1 — объявить: заголовок `Deprecation` (RFC 9745) с датой объявления и `Sunset` (RFC 8594) с датой отключения.
- Шаг 2 — измерить: счётчик обращений с разбивкой по клиенту, иначе непонятно, кому писать перед отключением.
- Шаг 3 — выждать: от 1-3 месяцев для внутренних API до года и больше для публичных, где клиент физически не обновляется по команде.
- Чего делать нельзя — выключать версию по календарю, не проверив, что трафик на ней действительно кончился.
