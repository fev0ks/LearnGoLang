# Go Code Patterns

Go не поощряет тяжёлую объектную иерархию. Паттерны здесь выглядят проще: маленькие интерфейсы, функции, композиция, явные зависимости и тонкие адаптеры вокруг внешнего мира.

Раздел разбит по **типу проблемы** которую решает паттерн, а не по классической GoF классификации (Creational/Structural/Behavioral) — в Go это менее естественно.

## Обзор паттернов: общая таблица

| Паттерн | Категория | Проблема которую решает | Когда не нужен |
|---|---|---|---|
| Small interface | Зависимости | Coupling к конкретной реализации | Интерфейс используется в одном месте |
| Constructor injection | Зависимости | Скрытые зависимости, global state | Нет внешних зависимостей |
| Functional options | Зависимости | Много необязательных параметров | Параметров ≤ 3, все обязательные |
| Middleware | Обёртки | Дублирование cross-cutting concerns | Одноразовый handler |
| Adapter | Обёртки | Внешний SDK протекает в домен | Простая интеграция без изменений |
| Decorator | Обёртки | Нужно расширить поведение без изменения кода | Добавляешь в одно место |
| Strategy | Домен | Большой `switch` по типу поведения | 2 варианта, не меняются |
| Repository | Домен | SQL/Redis детали в бизнес-логике | Простой CRUD без domain rules |
| Unit of Work | Домен | Несколько операций в одной транзакции | Одиночные операции |
| Context boundaries | Cross-cutting | Управление lifetime запроса, отмена, deadlines | Не используется параллельность или I/O |
| Error wrapping | Cross-cutting | Потеря контекста ошибки и протечка storage деталей | Простые internal библиотеки |

## Категории по типу проблемы

### 1. Зависимости и композиция

Как **передавать** зависимости и **выражать контракты** между компонентами. Основа любого testable Go-кода.

Главная мысль: интерфейсы — у потребителя, конструкторы — явные, опции — функции.

### 2. Обёртки поведения

Как **добавлять поведение** не меняя существующий код. Все три паттерна (middleware, adapter, decorator) — разные виды "обёрток" вокруг существующего объекта/handler'а.

- **Middleware** — для HTTP/gRPC chains
- **Adapter** — для изоляции внешних SDK
- **Decorator** — для расширения через тот же интерфейс

### 3. Домен и доступ к данным

Как **изолировать бизнес-логику** от деталей хранения и менять алгоритмы.

- **Strategy** — изменяемое поведение
- **Repository** — domain language для storage
- **Unit of Work** — транзакционная граница

### 4. Cross-cutting concerns

Технические аспекты которые **пронизывают** весь код.

- **Context** — единая граница lifetime запроса
- **Error wrapping** — преобразование ошибок между слоями

## Interview-ready answer

**1. Какие паттерны реально используются в Go-коде?**

- Small interfaces, constructor injection, middleware, adapter, decorator и repository там, где есть настоящая domain-логика. GoF один-в-один не переносится: интерфейсы, функции и композиция требуют значительно меньше слоёв.

**2. Как отличить хороший паттерн от церемонии?**

- Хороший делает зависимости явными, упрощает тесты и изолирует внешний мир за интерфейсом. Плохой добавляет абстракции, которые ничего не защищают: Repository поверх простого CRUD без domain-правил — лишний слой; Decorator для кеширования или метрик — честная изоляция без изменения основной логики.

**3. Какой главный индикатор проблем с архитектурой кода?**

- Вопрос «можно ли протестировать use case без реальной БД, брокера и внешних сервисов?». Если нет — не хватает правильных интерфейсов или зависимости скрыты.
