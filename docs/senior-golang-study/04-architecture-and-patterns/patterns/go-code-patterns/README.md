# Go Code Patterns

Go не поощряет тяжёлую объектную иерархию. Паттерны здесь выглядят проще: маленькие интерфейсы, функции, композиция, явные зависимости и тонкие адаптеры вокруг внешнего мира.

Раздел разбит по типу проблемы, которую решает паттерн, а не по классификации GoF (порождающие, структурные, поведенческие). Причина в том, что исходная классификация опирается на классы и наследование: в Go «порождающий паттерн» чаще всего оказывается обычной функцией-конструктором, а «структурный» — встраиванием структуры, и деление перестаёт что-либо объяснять.

## Обзор паттернов: общая таблица

| Паттерн | Категория | Проблема которую решает | Когда не нужен |
|---|---|---|---|
| Small interface | Зависимости | Coupling к конкретной реализации | Интерфейс используется в одном месте |
| Constructor injection | Зависимости | Скрытые зависимости, global state | Нет внешних зависимостей |
| Functional options | Зависимости | Много необязательных параметров | Параметров ≤ 3, все обязательные |
| Middleware | Обёртки | Дублирование cross-cutting concerns | Одноразовый handler |
| Adapter | Обёртки | Внешний SDK протекает в домен | Простая интеграция без изменений |
| Decorator | Обёртки | Нужно расширить поведение без изменения кода | Поведение добавляется в одном месте |
| Strategy | Домен | Большой `switch` по типу поведения | Два варианта, которые не меняются |
| Repository | Домен | SQL/Redis детали в бизнес-логике | Простой CRUD без domain rules |
| Unit of Work | Домен | Несколько операций в одной транзакции | Одиночные операции |
| Context boundaries | Cross-cutting | Управление lifetime запроса, отмена, deadlines | Не используется параллельность или I/O |
| Error wrapping | Cross-cutting | Потеря контекста ошибки и протечка storage деталей | Простые internal библиотеки |

## Категории по типу проблемы

### 1. Зависимости и композиция

Как передавать зависимости и выражать контракты между компонентами. Это основа тестируемого кода: компонент, чьи зависимости видны в сигнатуре конструктора, можно собрать в тесте с подменёнными частями.

Главная мысль: интерфейсы объявляет потребитель, конструкторы принимают всё нужное явно, необязательные параметры выражаются функциями-опциями.

### 2. Обёртки поведения

Как добавлять поведение, не меняя существующий код. Middleware, adapter и decorator — три разновидности обёртки вокруг уже существующего объекта или обработчика, различающиеся тем, что именно они оборачивают:

- **Middleware** — цепочка вокруг обработчика запроса в HTTP или gRPC.
- **Adapter** — преобразование чужого интерфейса в свой, чтобы внешний SDK не протекал в домен.
- **Decorator** — расширение поведения через тот же интерфейс, что и у обёрнутого объекта.

### 3. Домен и доступ к данным

Как отделить бизнес-логику от деталей хранения и как менять алгоритмы, не переписывая вызывающий код:

- **Strategy** — сменное поведение вместо ветвления по типу.
- **Repository** — доступ к данным на языке домена, а не на языке таблиц.
- **Unit of Work** — граница транзакции, охватывающая несколько операций.

### 4. Сквозные аспекты

Техника, которая пронизывает все слои и не принадлежит ни одному из них:

- **Context** — единая граница времени жизни запроса, отмены и предельных сроков.
- **Обёртывание ошибок** — преобразование ошибок при переходе между слоями.

## Interview-ready answer

**1. Какие паттерны действительно используются в Go-коде?**

- Основной набор — узкие интерфейсы, передача зависимостей через конструктор, middleware, adapter, decorator и repository там, где есть настоящая доменная логика.
- Почему не GoF целиком — большая часть каталога решает проблемы наследования, которого в Go нет.
- Что заменяет паттерны — функции как значения, неявная реализация интерфейсов и встраивание структур: слоёв нужно меньше.

**2. Как отличить полезный паттерн от церемонии?**

- Признак полезного — он делает зависимости явными, упрощает тест и удерживает внешний мир за интерфейсом.
- Признак церемонии — абстракция, которая ничего не защищает: repository поверх CRUD без доменных правил лишь повторяет операции базы.
- Пример честного применения — decorator для кеша или метрик: поведение добавляется, основная логика не меняется.
- Проверка — назвать изменение, которое благодаря паттерну стало дешевле; если такого изменения нет, паттерн лишний.

**3. Какой главный признак проблем с архитектурой кода?**

- Ключевой вопрос — можно ли протестировать сценарий без реальной базы, брокера и внешних сервисов.
- Отрицательный ответ означает — либо нужного интерфейса нет, либо зависимость создаётся внутри и её нельзя подменить.
- Второй признак — тест требует поднять инфраструктуру, чтобы проверить бизнес-правило, к инфраструктуре отношения не имеющее.
