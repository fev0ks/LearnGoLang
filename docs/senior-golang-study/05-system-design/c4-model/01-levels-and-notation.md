C4 — модель визуализации архитектуры через последовательное приближение.
Она не требует конкретного инструмента или формы коробок. Ценность модели —
в одинаковых уровнях абстракции, явных границах и понятных подписях.

---

## Что такое C4

Название происходит от четырёх слов: `Context`, `Container`, `Component`, `Code`.
Каждая следующая диаграмма приближает один элемент предыдущей:

```text
Software System из Context
    ↓ раскрывается как
Containers на Container diagram
    ↓ один container раскрывается как
Components на Component diagram
    ↓ один component раскрывается как
Code
```

Эта связь важнее оформления. Если на Component diagram внезапно появляется
сервис, которого не было среди containers или внешних систем, читатель не понимает,
откуда он взялся. Если PostgreSQL на одной схеме означает кластер, а на другой —
таблицу, теряется устойчивое значение элемента.

## Четыре статических уровня

### Уровень 1: System Context

**Вопрос диаграммы:** кто использует нашу систему и с какими внешними системами
она взаимодействует?

Показываем:

- одну проектируемую software system в центре;
- людей или роли, которые работают с ней;
- только непосредственно связанные внешние системы;
- направления и смысл взаимодействий.

Не показываем PostgreSQL, Kafka, Redis, микросервисы и Kubernetes. Context должен
быть понятен product manager без расшифровки технологий.

Пример границы: для задачи «спроектировать Low Price Alerts» Price Service и
Push Provider могут быть внешними системами, если ими владеют другие команды.
Для задачи «спроектировать весь маркетплейс» тот же Price Service уже находится
внутри границы. C4 не определяет границу за кандидата — её задаёт scope.

### Уровень 2: Container

**Вопрос диаграммы:** из каких крупных запускаемых приложений и хранилищ состоит
система и как между ними распределены обязанности?

В терминологии C4 container — это приложение или data store, а не обязательно
Docker. Примеры:

- web/backend application;
- mobile application или single-page application;
- API service и background worker, если это отдельные процессы;
- PostgreSQL schema или database;
- Kafka cluster/topic как логическое хранилище/транспорт;
- S3 bucket.

Для каждого container называем ответственность и, если это помогает решению,
основную технологию. Реплики одного и того же API обычно не рисуем отдельными
коробками: `API ×20` — один container с двадцатью экземплярами в deployment.

Container diagram — основной уровень System Design Interview. Именно здесь
видны синхронные запросы, события, источники истины, проекции чтения и внешние
интеграции.

### Уровень 3: Component

**Вопрос диаграммы:** какие крупные части находятся внутри одного выбранного
container и как они совместно реализуют его ответственность?

Component — не отдельный deployable unit. Это значимая внутренняя часть приложения:
handler/API layer, orchestrator, domain service, repository, adapter, scheduler.
На схеме всегда указываем, какой container раскрываем. Остальные containers
остаются внешним окружением выбранного уровня.

На собеседовании этот уровень нужен для deep dive. Например, контейнер Matcher
можно раскрыть на consumer событий цены, защиту версии, планировщик fan-out,
чтение подписок страницами и атомарное создание alert.

### Уровень 4: Code

**Вопрос диаграммы:** как реализован выбранный component на уровне кода?

Это могут быть классы, интерфейсы, пакеты или другая code-level схема. Она быстро
устаревает и редко полезна для системного интервью. Переходить сюда стоит только
по прямому запросу: например, показать интерфейс стратегии шардирования или
структуру state machine. Обычно короткий псевдокод или таблица состояний яснее.

### Сопоставление уровней

| Уровень | Scope одной диаграммы | Основные элементы | Аудитория | На интервью |
| --- | --- | --- | --- | --- |
| System Context | Одна software system и окружение | Люди, наша и внешние системы | Любая | Коротко зафиксировать границу |
| Container | Одна software system | Приложения, workers, хранилища | Техническая | Основная архитектурная схема |
| Component | Один container | Части приложения | Разработчики | Один согласованный deep dive |
| Code | Один component | Классы, пакеты, функции | Разработчики | Только если явно попросили |

## Дополнительные диаграммы

C4 не заканчивается четырьмя статическими уровнями. Для интервью особенно полезны
два дополнительных вида.

### Dynamic diagram

Показывает, как элементы уже определённой статической модели взаимодействуют
для одного сценария во времени. Это может быть sequence diagram или пронумерованный
flow. Она отвечает на вопрос «что происходит после нажатия Reserve?».

Dynamic diagram не является «пятым уровнем». Она не приближает архитектуру,
а накладывает поведение на существующие элементы. Не надо повторять на ней
все связи Container diagram: показываем один happy path или один отказ.

### Deployment diagram

Показывает экземпляры containers и инфраструктуру в конкретном окружении:
регионы, availability zones, узлы, балансировщики, реплики БД и размещение
broker nodes. Здесь уместны `API ×N`, leader/replica и failover.

Это отличается от Container diagram:

| Container diagram | Deployment diagram |
| --- | --- |
| Логическая архитектура | Физическое/виртуальное размещение экземпляров |
| `Subscription API [Container]` | API pods в AZ A и AZ B |
| `PostgreSQL [Container]` | Leader и synchronous replica |
| Обычно не меняется между средами | Отдельная схема для production/staging |

Показывать zones и replicas на основной Container diagram стоит только краткой
пометкой, если доступность — центральный вопрос. Иначе они заслоняют бизнес-flow.

## Как подписывать элементы

Коробка без объяснения роли заставляет интервьюера угадывать. Для статических
диаграмм используем компактный шаблон:

```text
Название
[Тип: технология, если важна]
одна строка ответственности
```

Примеры:

```text
Low Price Alerts
[Software System]
находит низкую цену и создаёт оповещение

Matcher Workers
[Container: Go]
находит подходящие подписки

Alert Creator
[Component]
атомарно создаёт alert и outbox
```

Название должно отражать бизнес-роль. `Backend`, `Service 1` или `Manager`
почти ничего не объясняют. Технология не заменяет ответственность: `Kafka`
не говорит, какие события в ней лежат и зачем они нужны системе.

Цвет помогает отличить категории, но значение нельзя кодировать только цветом.
Текст `[Person]`, `[Container]`, `[External System]` сохраняет смысл в чёрно-белой
печати и на доске без маркеров разных цветов. Если используем несколько форм,
добавляем небольшую легенду.

## Как подписывать отношения

Стрелка должна читаться как предложение:

```text
Marketplace App → Subscription API: создаёт подписку по HTTPS/JSON
Price Service → Event Broker: публикует price.changed
Matcher → PostgreSQL: создаёт alert и outbox одной транзакцией
```

Полезная подпись отвечает хотя бы на один вопрос:

- что передаётся;
- зачем вызывается получатель;
- синхронное это взаимодействие или событие;
- какой протокол важен для решения.

Плохо: `API → DB`, `Service A → Kafka`. Хорошо: `API → PostgreSQL: сохраняет
subscription`, `Price Service → broker: price.changed keyed by offer_id`.

Не рисуем две противоположные стрелки ради каждого request/response. Одна стрелка
описывает отношение; обратный ответ проговариваем. Двунаправленную связь используем,
только если обе стороны независимо инициируют разные взаимодействия.

## Граница системы и уровень абстракции

Перед первой коробкой произносим scope: «Я проектирую сервис оповещений; каталог,
цены, identity и push provider считаю внешними». После этого внешние элементы
располагаются за границей, внутренние — внутри.

На одной схеме держим один основной уровень. Допустимы supporting elements
соседнего уровня: Container diagram содержит людей и внешние systems, Component
diagram — соседние containers. Но нельзя смешивать детали без причины:

```text
Плохо на Container diagram:
User → Cloudflare → Nginx → Kubernetes Service → Pod → Go handler
     → repository → PostgreSQL table → WAL → replica disk

Лучше:
Marketplace App → Subscription API [Container] → PostgreSQL [Container]

Отдельно при вопросе о production:
Deployment diagram → Edge, zones, pod instances, leader и replica
```

Так упрощение не скрывает важное: оно откладывает детали до правильного вопроса.

## Типичные ошибки

- Рисовать одну гигантскую схему вместо двух уровней приближения.
- Называть каждый микросервис «container», но забывать базы, workers и clients.
- Считать container синонимом Docker и рисовать каждый pod отдельной коробкой.
- Помещать таблицы и функции на Container diagram.
- Показывать Kafka, Redis или CDN без ответственности и потока данных.
- Рисовать стрелки без направления и глагола.
- Смешивать текущий logical design с production deployment.
- Раскрывать все сервисы до Components вместо одного выбранного deep dive.
- Считать C4 заменой расчётам, API, consistency и failure analysis. Диаграмма
  показывает решение, но не доказывает, что оно выдерживает нагрузку.

## Interview-ready answer

**1. Что такое C4?**

- Модель — способ описывать архитектуру последовательным приближением: Context, Container, Component и Code.
- Цель — держать на одной диаграмме один уровень абстракции и явно связывать соседние уровни.

**2. Что означает container в C4?**

- Смысл — отдельно запускаемое приложение или хранилище, а не обязательно Docker-контейнер.
- Примеры — API, worker, мобильное приложение, база данных и объектное хранилище.

**3. Какие уровни нужны на System Design Interview?**

- Основа — короткий System Context и подробный Container diagram.
- Углубление — Dynamic flow для сценария и Component diagram только для выбранной части.

**4. Где показывать replicas, zones и load balancer?**

- Место — Deployment diagram, потому что это экземпляры и инфраструктура конкретной среды.
- Исключение — на основной схеме можно оставить краткую пометку, если HA является центральным требованием.
