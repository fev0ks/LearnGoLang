На интервью от кандидата обычно ждут не знания слова C4, а управляемой схемы:
видна граница, компоненты имеют роли, стрелки объясняют flow, а глубина появляется
по запросу. C4 даёт удобный способ поддерживать этот порядок.

---

## Главный принцип

Диаграмма развивается вместе с обсуждением, а не появляется целиком в начале.
Каждая новая коробка должна отвечать на уже названное требование или найденное
ограничение.

```text
requirements → Context → capacity conclusions → Containers
             → один end-to-end flow → один согласованный deep dive
```

Если кандидат сразу рисует Kafka, Redis и десять сервисов, ещё неизвестно,
решают ли они поставленную задачу. Если после требований и расчётов появляется
`Delivery Queue`, можно связать её с конкретным выводом: миллион получателей
нельзя обслуживать внутри запроса изменения цены.

## Порядок рисования

### Шаг 1. Зафиксировать scope словами

До схемы назвать проектируемую software system и то, что считается внешним:

> «Проектируем Low Price Alerts. Каталог и Price Service уже существуют,
> Push Provider внешний. Внутри нашей границы будут управление подписками,
> сопоставление цены и доставка созданного оповещения».

Если интервьюер меняет scope, сначала исправляем границу, а затем контейнеры.

### Шаг 2. Нарисовать System Context за 1–2 минуты

На доске достаточно 4–6 элементов:

- человек или основной клиент;
- проектируемая система;
- 2–4 непосредственные внешние зависимости;
- подписанные направления взаимодействия.

Контекст подтверждает общее понимание задачи. Не тратим на него десять минут
и не перечисляем инфраструктуру.

### Шаг 3. Перейти к Container diagram на новом участке доски

Сначала рисуем happy path слева направо:

```text
Client → API → source of truth
              ↓ outbox / event
           Queue → Worker → External Provider
```

Затем добавляем read path, проекции и отдельные фоновые контуры, если они нужны.
У каждого container сразу подписываем ответственность; технологии выбираем
после объяснения требований к данным и нагрузке.

### Шаг 4. Пройти один сценарий по стрелкам

Нумеруем или проговариваем шаги: где запрос принят, когда он durable, что ответит
клиент, где возможен повтор, что считается успехом. Если для объяснения приходится
придумывать невидимый сервис или хранилище, статическая схема неполна.

### Шаг 5. Предложить deep dive

Вместо самовольного раскрытия всех блоков предлагаем выбор:

> «Общая схема готова. Можем подробнее разобрать конкурентное создание резерва,
> массовый fan-out или восстановление после таймаута провайдера. Я бы выбрал
> fan-out, потому что он следует из рассчитанного hotspot».

Для внутренностей одного container рисуем Component diagram. Для гонки или Saga
может быть полезнее Dynamic diagram, таблица состояний или короткий псевдокод.

### Шаг 6. Deployment добавлять по требованию

Если обсуждают `99.99%`, region failure или failover, показываем экземпляры
containers по зонам и репликацию. Не превращаем логическую схему в карту каждого
Ingress, pod и диска, если вопрос этого не требует.

## Шаблон доски

Для 45–60 минут удобно заранее распределить пространство:

```text
┌───────────────────────┬─────────────────────────────────────┐
│ Scope + requirements  │ System Context (маленький)          │
│ 4–6 bullets           │ user → system ↔ externals           │
├───────────────────────┴─────────────────────────────────────┤
│ Container diagram: основной поток слева направо             │
│ client → API → DB → queue → workers → provider              │
├──────────────────────────────┬──────────────────────────────┤
│ Capacity / invariants        │ Deep dive / dynamic flow     │
│ 6–8 чисел и 2–3 правила      │ только выбранный участок     │
└──────────────────────────────┴──────────────────────────────┘
```

На виртуальной доске уровни лучше разносить по отдельным frames с названиями
`L1 Context`, `L2 Containers`, `Deep dive`. Масштабирование холста не должно
быть единственным способом понять, на каком уровне находится элемент.

## Что говорить во время рисования

Молчаливое рисование выглядит как попытка вспомнить заученную схему. Короткие
фразы показывают причинно-следственную связь:

- «Эта граница — зона ответственности нашей команды».
- «На Context пока не показываю базу: здесь важны пользователи и внешние системы».
- «Приближаю Low Price Alerts и перехожу к containers».
- «API и workers разделяю, потому что у них разные latency и профиль масштабирования».
- «PostgreSQL — источник истины; брокер переносит событие, но не решает конфликт подписок».
- «Отдельно пройду путь price.changed и укажу момент, после которого работа не потеряется».
- «Реплики и availability zones вынесу в Deployment diagram, если пойдём в HA».

Не нужно произносить термин C4 в каждой фразе. Главное — объяснять границу,
ответственность и причину появления элемента.

---

## Когда приближать архитектуру

| Вопрос интервьюера | Лучший следующий вид |
| --- | --- |
| «Кто вообще вызывает эту систему?» | System Context |
| «Какие сервисы и хранилища внутри?» | Container |
| «Что находится внутри Matcher?» | Component выбранного container |
| «Что происходит при одном reserve/checkout?» | Dynamic diagram или sequence |
| «Как переживёте потерю зоны?» | Deployment diagram |
| «Как выглядит таблица/индекс?» | Data model рядом с Component/Dynamic deep dive |
| «Как реализуешь это на Go?» | Псевдокод, интерфейсы или Code diagram по необходимости |

Data model, capacity table и state machine не обязаны быть C4. Не нужно силой
превращать любой артефакт интервью в один тип диаграммы.

## Как проверить готовую схему

### Проверка Context

```text
□ одна явно названная система в scope
□ есть основной пользователь/клиент
□ внешние системы действительно за границей ответственности
□ нет PostgreSQL, Kafka, pod и внутренних сервисов
□ стрелки подписаны глаголами
```

### Проверка Containers

```text
□ все core use cases можно пройти по стрелкам
□ у каждого container одна понятная ответственность
□ видно, где источник истины, кеш и проекция
□ синхронные команды отличаются по смыслу от событий
□ внешние вызовы и граница системы видны
□ нет беспричинных технологий и «Service 1 / Service 2»
```

### Проверка всего ответа

```text
□ у каждого сложного элемента есть число, инвариант или требование
□ схема не обещает exactly once там, где есть внешний эффект
□ назван момент durable commit и способ восстановления
□ hotspot не скрыт средним RPS
□ выбран один deep dive, а не поверхностно раскрыты все блоки
```

## Как тренироваться

Для одного незнакомого кейса поставь таймер на 12 минут:

```text
0–2 мин    scope и Context
2–9 мин    Containers и подписи отношений
9–12 мин   один dynamic flow
```

После таймера убери исходное условие и попроси другого человека объяснить систему
только по рисунку. Каждый вопрос «а это что?» указывает на слабую подпись или
пропущенную границу. Затем попробуй удалить 20% коробок: если смысл не меняется,
они не были нужны на этом уровне.

Для следующего прогона не копируй готовую схему. Используй только каркас уровней,
а containers выводи из новых требований и расчётов.

## Interview-ready answer

**1. С чего начинается C4-схема на интервью?**

- Scope — сначала называю проектируемую систему и внешние зависимости.
- Контекст — за 1–2 минуты показываю пользователя и непосредственные системы вокруг.

**2. Какой уровень является основным?**

- Container diagram — показывает приложения, workers, хранилища и их ответственности.
- Проверка — после неё можно пройти core flow и указать источник истины.

**3. Когда рисовать Component diagram?**

- Момент — после согласования общей архитектуры для одного выбранного container.
- Причина — раскрыть конкретный bottleneck или инвариант, а не перечислить все классы системы.

**4. Как показать отказ или Saga?**

- Вид — Dynamic diagram, sequence или state machine поверх элементов статической модели.
- Содержание — момент durable commit, повторы, неизвестный исход и компенсация.
