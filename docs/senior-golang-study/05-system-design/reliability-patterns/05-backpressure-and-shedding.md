Сервис, получающий больше запросов, чем способен обработать, обязан выбрать, что именно с ними делать. Отсутствие выбора — тоже выбор, и худший из возможных: очередь растёт, задержка растёт вместе с ней, и в какой-то момент отказывают все запросы, включая те, что пришли первыми.

Инструментов два, и они противоположны по направлению воздействия:

- **Backpressure** передаёт сигнал вверх по потоку: отправитель замедляется, пока получатель не справится.
- **Load shedding** отклоняет часть запросов на месте, не пытаясь никого замедлить.

Выбор между ними определяется тем, есть ли у отправителя возможность подождать. Внутренний сервис, читающий из очереди, замедлиться может — здесь работает backpressure. Пользователь с открытой страницей ждать не станет: замедление для него неотличимо от отказа, только дороже. Здесь остаётся отклонять — быстро и с понятным кодом ответа.

## Что происходит без управления перегрузкой

```
Сервис рассчитан на 1000 req/s, latency 50ms

Нагрузка: 2000 req/s
→ Очередь растёт
→ Goroutines накапливаются (каждый запрос ждёт)
→ Память заканчивается
→ GC давление растёт → паузы → latency растёт → очередь растёт быстрее
→ OOM kill или полная деградация

Итог: 0 req/s вместо 1000 req/s — система работала хуже без нагрузки
```

Цель управления перегрузкой формулируется так: при нагрузке в 2000 запросов обрабатывать 1000 с нормальной задержкой и явно отклонять остальные — вместо попытки обработать все и деградации для каждого.

Связь между длиной очереди и задержкой описывается законом Литтла: `L = λ × W`, где `L` — число запросов в системе, `λ` — скорость поступления, `W` — время пребывания одного запроса. В перевёрнутом виде `W = L / λ` он отвечает на практический вопрос: очередь в 1000 запросов при пропускной способности 1000 в секунду означает задержку в одну секунду для каждого, кто в неё попал.

Отсюда следует неочевидное: большая очередь не помогает, а вредит. Она не увеличивает пропускную способность — та определяется числом обработчиков, — зато прибавляет ожидание. Запрос, простоявший в очереди тридцать секунд, будет обработан ровно тогда, когда клиент уже получил таймаут и ушёл: работа выполнена, результат никому не нужен.

## Backpressure

Backpressure — сигнал вверх по потоку: «замедлись, я не успеваю». В Go его роль играет заполненный канал или занятый семафор — отправитель просто блокируется, пока не освободится место.

```go
// Bounded channel как backpressure
requests := make(chan Request, 100)  // буфер = max очередь

// Producer (HTTP handler)
func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    select {
    case h.requests <- parseRequest(r):
        w.WriteHeader(http.StatusAccepted)  // принято в очередь
    default:
        // Очередь полна — backpressure → отклоняем
        w.Header().Set("Retry-After", "1")
        http.Error(w, "service overloaded", http.StatusServiceUnavailable)
    }
}

// Consumer (worker)
func (h *Handler) worker() {
    for req := range h.requests {
        h.process(req)
    }
}
```

Пример выше в чистом виде backpressure не реализует: при заполненной очереди он отклоняет запрос, то есть переходит к отбрасыванию. Настоящий backpressure получился бы при блокирующей отправке `h.requests <- req` без ветки `default` — тогда обработчик ждал бы свободного места и тем самым замедлял приём. Для HTTP это плохой вариант: удерживать соединение клиента ради ожидания в очереди дороже, чем сразу отказать.

Разница между двумя стратегиями в том, кто платит ожиданием. При backpressure платит отправитель, при отбрасывании — отклонённый запрос. Поэтому backpressure уместен там, где отправитель свой и умеет ждать: потребитель очереди, конвейер обработки, поток репликации.

В gRPC и HTTP/2 backpressure встроен в протокол на уровне управления потоком: получатель, не успевающий читать, перестаёт увеличивать окно, и отправитель приостанавливает передачу без участия прикладного кода.

## Load Shedding

Load shedding — намеренный отказ части запросов при перегрузке. В отличие от backpressure, не замедляет upstream, а явно отклоняет с `503`.

### По размеру очереди

```go
type LoadShedder struct {
    inFlight atomic.Int64
    maxLoad  int64
}

// Acquire увеличивает счётчик и откатывает изменение при превышении.
// Раздельные "прочитать и сравнить" плюс "увеличить" здесь не годятся:
// между ними вклинивается другая горутина, и предел превышается
// ровно при той нагрузке, ради которой всё и делалось.
func (ls *LoadShedder) Acquire() bool {
    if ls.inFlight.Add(1) > ls.maxLoad {
        ls.inFlight.Add(-1)
        return false
    }
    return true
}

func (ls *LoadShedder) Release() {
    ls.inFlight.Add(-1)
}

func (ls *LoadShedder) InFlight() int64 {
    return ls.inFlight.Load() // для метрики
}

// Middleware
func LoadShedMiddleware(shedder *LoadShedder) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            if !shedder.Acquire() {
                w.Header().Set("Retry-After", "1")
                http.Error(w, "server overloaded", http.StatusServiceUnavailable)
                return
            }
            defer shedder.Release()
            next.ServeHTTP(w, r)
        })
    }
}
```

### По давлению на сборщик мусора

Соблазнительно принимать решение по нагрузке на процессор или по доле времени, занятой сборщиком мусора. Но у очевидной реализации есть ловушка:

```go
// Так делать нельзя: GCCPUFraction считается за всё время
// жизни процесса, а не за последний интервал. Показатель почти
// не меняется под текущей нагрузкой и на всплеск не реагирует.
func isOverloaded() bool {
    var stats runtime.MemStats
    runtime.ReadMemStats(&stats)
    return stats.GCCPUFraction > 0.2
}
```

Кроме накопительного характера, у `runtime.ReadMemStats` есть второе свойство: он останавливает мир на время сбора статистики. Вызов из обработчика на каждый запрос сам становится источником задержки.

Рабочий вариант — считать изменение показателя между замерами в фоне:

```go
// Фоновый сбор: показатель обновляется раз в секунду,
// обработчики читают готовое значение без остановки мира.
func (m *GCPressureMonitor) run(ctx context.Context) {
    t := time.NewTicker(time.Second)
    defer t.Stop()

    var prev runtime.MemStats
    runtime.ReadMemStats(&prev)

    for {
        select {
        case <-ctx.Done():
            return
        case <-t.C:
            var cur runtime.MemStats
            runtime.ReadMemStats(&cur)

            // Разница накопленного времени пауз за интервал.
            deltaPause := time.Duration(cur.PauseTotalNs - prev.PauseTotalNs)
            m.pauseFraction.Store(deltaPause.Seconds()) // доля секунды в паузах
            prev = cur
        }
    }
}
```

На практике же управлять перегрузкой удобнее по числу запросов в обработке, а не по показателям сборщика: связь с ёмкостью прямая, измерение бесплатное, а превышение обнаруживается раньше, чем начинается давление на память.

### Priority shedding

Отклонять запросы можно не подряд, а по значимости. Пороги задают уровни, на которых начинает отсекаться каждая категория:

```go
type Priority int

const (
    PriorityHigh   Priority = 3
    PriorityNormal Priority = 2
    PriorityLow    Priority = 1
)

type PriorityLoadShedder struct {
    inFlight atomic.Int64
    capacity int64 // полная ёмкость
    normalAt int64 // порог для обычных запросов, ~80% ёмкости
    lowAt    int64 // порог для фоновых запросов, ~60% ёмкости
}

func (s *PriorityLoadShedder) limitFor(p Priority) int64 {
    switch p {
    case PriorityHigh:
        return s.capacity
    case PriorityNormal:
        return s.normalAt
    default:
        return s.lowAt
    }
}

func (s *PriorityLoadShedder) Acquire(p Priority) bool {
    if s.inFlight.Add(1) > s.limitFor(p) {
        s.inFlight.Add(-1)
        return false
    }
    return true
}

func (s *PriorityLoadShedder) Release() { s.inFlight.Add(-1) }
```

Приоритет назначается по последствиям отказа, а не по важности клиента. Оплата и оформление заказа — высокий: отказ означает потерянные деньги. Просмотр каталога — обычный. Предзагрузка рекомендаций, сбор аналитики, обновление счётчиков — низкий: отказ незаметен.

Полезное следствие такой схемы — отбрасывание начинается задолго до исчерпания ёмкости. При 60% загрузки уже отсекается фоновая работа, и высвобожденный запас идёт на обслуживание значимых запросов. Схема без приоритетов ведёт себя иначе: до порога проходит всё, после порога отклоняется всё подряд, включая оплату.

## Bounded concurrency через semaphore

Semaphore — самый прямой способ ограничить параллелизм для конкретного ресурса:

```go
// Semaphore через buffered channel
type Semaphore chan struct{}

func NewSemaphore(n int) Semaphore {
    return make(Semaphore, n)
}

func (s Semaphore) Acquire(ctx context.Context) error {
    select {
    case s <- struct{}{}:
        return nil
    case <-ctx.Done():
        return ctx.Err()
    }
}

func (s Semaphore) Release() {
    <-s
}

// Использование — не более 10 одновременных запросов к базе
type Repo struct {
    pool *pgxpool.Pool
    sem  Semaphore // NewSemaphore(10)
}

func (r *Repo) GetUser(ctx context.Context, id string) (*User, error) {
    if err := r.sem.Acquire(ctx); err != nil {
        return nil, fmt.Errorf("db semaphore: %w", err)
    }
    defer r.sem.Release()

    var u User
    err := r.pool.QueryRow(ctx, "SELECT id, email FROM users WHERE id = $1", id).
        Scan(&u.ID, &u.Email)
    if err != nil {
        return nil, fmt.Errorf("get user %s: %w", id, err)
    }
    return &u, nil
}
```

Здесь семафор ждёт освобождения места, а не отклоняет запрос — это backpressure внутри процесса. Ожидание ограничено контекстом, поэтому запрос с истекающим бюджетом не будет стоять в очереди дольше, чем ему отведено.

Заметная деталь: у пула соединений `pgxpool` уже есть собственное ограничение (`MaxConns`), которое работает точно так же. Отдельный семафор поверх него нужен, когда ограничить требуется не число соединений, а число одновременных операций конкретного вида — например, тяжёлых аналитических запросов, чтобы они не занимали весь пул.

Или через `golang.org/x/sync/semaphore`:
```go
import "golang.org/x/sync/semaphore"

sem := semaphore.NewWeighted(10)

func (r *Repo) Query(ctx context.Context, id string) (*User, error) {
    if err := sem.Acquire(ctx, 1); err != nil {
        return nil, err
    }
    defer sem.Release(1)
    // ...
}
```

## Worker pool как естественный backpressure

Worker pool с bounded input channel автоматически создаёт backpressure:

```go
type WorkerPool struct {
    jobs    chan Job
    results chan Result
    wg      sync.WaitGroup
}

func NewWorkerPool(workers, queueSize int) *WorkerPool {
    p := &WorkerPool{
        jobs:    make(chan Job, queueSize),
        results: make(chan Result, queueSize),
    }
    for i := 0; i < workers; i++ {
        p.wg.Add(1)
        go func() {
            defer p.wg.Done()
            for job := range p.jobs {
                p.results <- process(job)
            }
        }()
    }
    return p
}

// Submit отклоняет задачу, если очередь заполнена.
// Ветка default срабатывает немедленно, поэтому ожидания здесь нет:
// добавлять рядом case <-ctx.Done() бессмысленно — до него дело не дойдёт.
func (p *WorkerPool) Submit(job Job) error {
    select {
    case p.jobs <- job:
        return nil
    default:
        return ErrPoolOverloaded
    }
}

// SubmitWait, наоборот, ждёт освобождения места в пределах контекста —
// это уже backpressure, а не отбрасывание.
func (p *WorkerPool) SubmitWait(ctx context.Context, job Job) error {
    select {
    case p.jobs <- job:
        return nil
    case <-ctx.Done():
        return ctx.Err()
    }
}
```

Смешивать `default` и `<-ctx.Done()` в одном `select` не имеет смысла: `default` выполняется сразу, если ни один канал не готов, поэтому ветка с контекстом остаётся мёртвым кодом. Два метода разделяют два разных поведения явно.

Числа в конструкторе задают разные вещи. `workers` — предел одновременной работы, он определяется ёмкостью получателя: пулом соединений к базе, квотой внешнего API, числом ядер. `queueSize` — предел накопления, и по закону Литтла он же задаёт худшую задержку: очередь в 1000 задач при 100 обработках в секунду означает десять секунд ожидания для последней. Разумное значение обычно невелико — от нуля до нескольких секунд работы пула.

## Adaptive concurrency

Вместо фиксированного лимита — динамически подстраивать concurrency под latency. Алгоритм AIMD (Additive Increase / Multiplicative Decrease):

```go
type AdaptiveLimiter struct {
    mu            sync.Mutex
    limit         int64
    minLimit      int64
    maxLimit      int64
    targetLatency time.Duration
}

// Медленное увеличение: предел растёт на единицу, пока задержка в норме.
func (l *AdaptiveLimiter) onSuccess(latency time.Duration) {
    l.mu.Lock()
    defer l.mu.Unlock()
    if latency < l.targetLatency {
        l.limit = min(l.limit+1, l.maxLimit)
    }
}

// Быстрое снижение: при отказе или превышении задержки предел
// уменьшается сразу на десятую часть.
func (l *AdaptiveLimiter) onFailure() {
    l.mu.Lock()
    defer l.mu.Unlock()
    l.limit = max(int64(float64(l.limit)*0.9), l.minLimit)
}
```

Асимметрия здесь принципиальна и заимствована у управления перегрузкой в TCP. Увеличение медленное, потому что цена ошибки в эту сторону — перегрузка получателя. Снижение быстрое, потому что цена промедления — растущая очередь. Симметричная схема с одинаковым шагом колеблется вокруг предела вместо того, чтобы к нему сходиться.

Главное преимущество подхода — предел не нужно подбирать вручную и пересматривать после каждого изменения. Он находится сам и следует за реальной ёмкостью: за деградацией базы, за уменьшением числа реплик, за ростом тяжести запросов.

Готовые реализации: `netflix/concurrency-limits` (Java, с портами на Go), `platinummonkey/go-concurrency-limits`.

## Антипаттерны

**Неограниченный запуск горутин** — `go processRequest(req)` в обработчике без всяких пределов. Всплеск нагрузки превращается в миллион горутин и остановку по нехватке памяти, причём тем быстрее, чем медленнее отвечает зависимость.

**Очередь без верхнего предела** — большой буфер вместо ограничения. Пропускная способность от этого не растёт, растёт только ожидание: сервис продолжает обрабатывать запросы, отправители которых давно ушли по таймауту.

```go
// Плохо — обрабатываем то, чего уже никто не ждёт
jobs <- job // клиент отключился полминуты назад

// Хорошо — проверять контекст перед началом работы
for job := range jobs {
    if job.ctx.Err() != nil {
        metrics.ExpiredJobs.Inc()
        continue // клиент ушёл, работа бессмысленна
    }
    process(job)
}
```

**Проверка «прочитать и сравнить» вместо атомарной операции** — счётчик проверяют, затем увеличивают. Между двумя действиями вклинивается другая горутина, и предел превышается именно под той нагрузкой, ради которой его вводили.

**Отбрасывание включается только при полном исчерпании ёмкости** — до порога проходит всё, после порога отклоняется всё. Нужен запас: фоновые запросы отсекать заранее, около 60% загрузки, значимые — только у самого предела.

**Решение о перегрузке принимается по показателю сборщика мусора напрямую** — `GCCPUFraction` накапливается за всё время жизни процесса и на текущий всплеск не реагирует, а `runtime.ReadMemStats` на каждый запрос сам останавливает мир.

**Нет метрик на длину очереди и число запросов в обработке** — приближение к пределу невидимо, и первым сигналом становится отказ.

## Interview-ready answer

**1. Чем backpressure отличается от load shedding?**

- Направление воздействия — backpressure замедляет отправителя, load shedding отклоняет запрос на месте.
- Кто платит ожиданием — при backpressure отправитель, при отбрасывании отклонённый запрос.
- Критерий выбора — умеет ли отправитель ждать: внутренний конвейер умеет, пользователь с открытой страницей нет.
- В протоколах — управление потоком HTTP/2 и gRPC реализует backpressure без участия прикладного кода.

**2. Почему большая очередь не решает проблему перегрузки?**

- Закон Литтла — `W = L / λ`: очередь в 1000 запросов при 1000 обработках в секунду даёт секунду ожидания каждому.
- Пропускная способность от размера очереди не зависит — её задаёт число обработчиков.
- Практическое следствие — запрос, простоявший дольше таймаута клиента, будет обработан впустую.
- Правильный размер — единицы секунд работы пула, а не «побольше на всякий случай».

**3. Как отбрасывать запросы правильно?**

- По числу запросов в обработке — связь с ёмкостью прямая, измерение бесплатное.
- Счётчик менять атомарно — сначала увеличить, при превышении откатить; раздельные проверка и увеличение дают гонку.
- По приоритету — фоновые запросы отсекать при 60% загрузки, обычные при 80%, значимые только у предела.
- Приоритет назначать по последствиям отказа, а не по важности клиента: оплата выше просмотра каталога.
- Отвечать `503` с заголовком `Retry-After`, иначе клиент подберёт интервал повтора сам и обычно слишком агрессивно.

**4. Что такое adaptive concurrency?**

- Идея — предел параллелизма не задаётся числом, а находится по обратной связи от задержки.
- Схема AIMD — медленное увеличение на единицу при нормальной задержке, резкое снижение на десятую часть при отказе.
- Причина асимметрии — цена ошибки различна: лишний шаг вверх перегружает получателя, промедление вниз растит очередь.
- Выигрыш — предел следует за реальной ёмкостью и не требует пересмотра после каждого изменения нагрузки.
