Ограничение частоты решает две разные задачи, и их полезно различать с самого начала.

**Защита от перегрузки.** Сервис принимает столько запросов, сколько способен обработать, а остальное отклоняет быстро и дёшево. Без этого превышение ёмкости не приводит к отказу части запросов — оно приводит к росту очередей, задержек и в итоге к отказу всех.

**Справедливое распределение.** Один клиент не может занять всю ёмкость сервиса. Без этого достаточно одного скрипта в цикле, чтобы остальные пользователи получали отказы, хотя сервис работает штатно.

Задачи различаются местом установки предела. Первая требует общего ограничителя на экземпляр или на сервис, вторая — отдельного счётчика на каждого клиента. В реальной системе обычно работают оба.

Отдельно стоит ограничение на исходящие вызовы — когда сервис не защищает себя, а не перегружает чужую систему; ему посвящён раздел в конце.

## Что именно ограничивается

До выбора алгоритма нужно решить, по какому ключу считать. От этого зависит, кого именно отсечёт ограничитель.

| Ключ | Когда подходит | Чем плох |
|---|---|---|
| Идентификатор пользователя | Аутентифицированный API | Не работает до входа: регистрация и вход остаются без защиты |
| Ключ API | Интеграции и партнёры | Требует выдачи ключей, для публичного API неприменим |
| IP-адрес | Публичные эндпоинты, вход, регистрация | За одним адресом сидит целый офис или мобильный оператор через NAT |
| IP плюс эндпоинт | Точечная защита дорогих операций | Больше счётчиков и больше памяти |

Ограничение по IP заслуживает отдельной оговорки. За одним адресом может находиться корпоративная сеть или мобильный оператор с сотнями тысяч абонентов, поэтому строгий предел отсекает добросовестных пользователей вместе с нарушителем. Разумный компромисс — мягкий предел по IP только на операции без аутентификации плюс жёсткий предел по пользователю после входа.

Второй частый промах — брать адрес из `RemoteAddr` за прокси. Тогда весь трафик приходит с адреса балансировщика, счётчик у всех общий, и предел срабатывает для всех сразу. Адрес берут из `X-Forwarded-For`, но доверять этому заголовку можно только в той части, которую записал собственный прокси: клиент может подставить туда что угодно.

## Алгоритмы

### Fixed Window Counter

```
[0s─────10s] запросов: 95   → пропускаем
[0s─────10s] запросов: 100  → предел достигнут
[10s────20s] запросов: 0    → счётчик обнулился
```

Простейший вариант: счётчик на окно, обнуление по его истечении. Проблема — всплеск на границе. Сто запросов в последние 100 мс окна и ещё сто в первые 100 мс следующего дают 200 запросов за 200 мс при пределе 100 за 10 секунд, то есть вдвое больше заявленного.

### Sliding Window Log

Хранятся отметки времени всех запросов, при проверке считается их количество в интервале `[now - window, now]`. Точен полностью — границы окна не существует. Плата — память порядка числа запросов в окне на каждый ключ.

### Sliding Window Counter

Компромисс между первыми двумя: два счётчика фиксированных окон и линейная интерполяция предыдущего:

```
оценка = prev_count * (1 - elapsed/window) + curr_count

Пример: окно 10s, прошло 3s текущего окна,
        в прошлом окне 90 запросов, в текущем 30.
        оценка = 90 * (1 - 0.3) + 30 = 63 + 30 = 93
```

Точность приблизительная — интерполяция предполагает равномерное распределение запросов в прошлом окне, чего в реальности нет. Зато памяти нужно два числа на ключ вместо списка отметок.

### Token Bucket

Ведро с токенами: токены добавляются с постоянной скоростью, каждый запрос забирает один. Нет токенов — отказ или ожидание.

Отличие от предыдущих алгоритмов в том, что ведро накапливает неиспользованную ёмкость. Клиент, молчавший минуту, может потратить накопленное разом — до размера ведра. Это удобно для API, где обращения приходят пачками: скрипт, забирающий отчёт раз в час, не должен растягивать сотню запросов на сотню секунд.

Семантика описывается двумя числами: скорость пополнения и размер ведра, то есть допустимый размер всплеска.

### Leaky Bucket

Очередь фиксированного размера, из которой запросы вынимаются с постоянной скоростью. Переполнение очереди означает отказ.

Отличие от token bucket принципиальное: leaky bucket не допускает всплесков вовсе — выход всегда равномерен. Поэтому он хорош для сглаживания исходящего трафика, где важна постоянная скорость, и неудобен для входящего, где отказ в обслуживании из-за краткого всплеска нежелателен.

**Что выбирать.** Для входящего трафика — token bucket: он допускает естественную неравномерность обращений. Для распределённого учёта через Redis — sliding window log при небольших пределах и counter при больших. Fixed window применим там, где двукратное превышение на границе окна не критично.

## Token Bucket в Go

`golang.org/x/time/rate` — стандартная реализация token bucket:

```go
import "golang.org/x/time/rate"

// 100 requests/sec, burst до 200
limiter := rate.NewLimiter(rate.Limit(100), 200)

// rate.Every — альтернативный способ задать rate
limiter = rate.NewLimiter(rate.Every(10*time.Millisecond), 200)  // 1 req / 10ms = 100/s

// Проверить без блокировки
if !limiter.Allow() {
    return errors.New("rate limit exceeded")
}

// Зарезервировать токен с deadline (рекомендуется)
ctx, cancel := context.WithTimeout(ctx, 1*time.Second)
defer cancel()
if err := limiter.Wait(ctx); err != nil {
    return err  // context cancelled или deadline exceeded
}

// Для множества токенов (batch запросы)
if !limiter.AllowN(time.Now(), 10) {
    return errors.New("rate limit exceeded")
}
```

### Per-key rate limiting (per user, per IP)

```go
type PerKeyLimiter struct {
    mu       sync.Mutex
    limiters map[string]*rate.Limiter
    rate     rate.Limit
    burst    int
}

func NewPerKeyLimiter(r rate.Limit, burst int) *PerKeyLimiter {
    return &PerKeyLimiter{
        limiters: make(map[string]*rate.Limiter),
        rate:     r,
        burst:    burst,
    }
}

func (l *PerKeyLimiter) Allow(key string) bool {
    l.mu.Lock()
    limiter, ok := l.limiters[key]
    if !ok {
        limiter = rate.NewLimiter(l.rate, l.burst)
        l.limiters[key] = limiter
    }
    l.mu.Unlock()
    return limiter.Allow()
}
```

**Проблема**: map растёт неограниченно. В production нужна TTL-очистка или LRU cache:

```go
import "github.com/hashicorp/golang-lru/v2/expirable"

// LRU cache с TTL — старые ключи вытесняются автоматически
cache := expirable.NewLRU[string, *rate.Limiter](10000, nil, 1*time.Hour)

func (l *PerKeyLimiter) Allow(key string) bool {
    limiter, ok := cache.Get(key)
    if !ok {
        limiter = rate.NewLimiter(l.rate, l.burst)
        cache.Add(key, limiter)
    }
    return limiter.Allow()
}
```

## Sliding Window Log на Redis

Точный вариант без границ окна: отметки времени запросов хранятся в отсортированном множестве, устаревшие удаляются перед каждой проверкой.

Скрипт на Lua выполняется целиком атомарно — в этом его смысл. Те же три команды, отправленные по отдельности, оставляют промежутки, в которые вклинится параллельный запрос, и предел будет превышен.

```lua
-- KEYS[1] = ключ вида "ratelimit:{userID}"
-- ARGV[1] = текущее время, мс
-- ARGV[2] = размер окна, мс
-- ARGV[3] = предел
-- ARGV[4] = уникальный идентификатор запроса
local key    = KEYS[1]
local now    = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit  = tonumber(ARGV[3])
local member = ARGV[4]

-- Убрать отметки, вышедшие за окно
redis.call('ZREMRANGEBYSCORE', key, '-inf', now - window)

local count = redis.call('ZCARD', key)
if count < limit then
    redis.call('ZADD', key, now, member)
    redis.call('PEXPIRE', key, window)
    return 1  -- пропустить
end

-- Продлить жизнь ключа даже при отказе, иначе он исчезнет
-- посреди окна и счётчик обнулится раньше времени.
redis.call('PEXPIRE', key, window)
return 0      -- отклонить
```

Уникальный идентификатор передаётся снаружи, а не генерируется внутри через `math.random`. Причина в модели репликации: генератор в Lua инициализируется одинаково на каждом запуске, поэтому одинаковые значения приводят к перезаписи элемента множества, и два разных запроса схлопываются в один.

```go
// redis.NewScript сам делает EVALSHA и повторяет через EVAL,
// если скрипт отсутствует в кэше сервера — например после его перезапуска.
var slidingWindow = redis.NewScript(`...`) // текст скрипта выше

func checkRateLimit(ctx context.Context, rdb *redis.Client, userID string,
    limit int, window time.Duration) (bool, error) {

    key := "ratelimit:" + userID
    member := fmt.Sprintf("%d-%s", time.Now().UnixNano(), uuid.NewString())

    res, err := slidingWindow.Run(ctx, rdb, []string{key},
        time.Now().UnixMilli(), window.Milliseconds(), limit, member).Int()
    if err != nil {
        // Redis недоступен. Выбор режима отказа — ниже по тексту;
        // главное, чтобы он был явным и попадал в метрики.
        metrics.RateLimiterErrors.Inc()
        return true, fmt.Errorf("rate limit check: %w", err)
    }
    return res == 1, nil
}
```

Вызывающий код получает и решение, и ошибку: `true` с непустой ошибкой означает «пропускаем, но проверка не выполнена». Молчаливое `return true, nil` из первоначального варианта скрывает недоступность Redis полностью — ограничитель перестаёт работать, и узнать об этом неоткуда.

**Режим отказа при недоступном Redis.** Пропускать (`fail open`) или отклонять (`fail closed`) — зависит от того, от чего защищает ограничитель:

- Защита от перегрузки и справедливое распределение — пропускать. Иначе сбой Redis превращается в полный отказ сервиса, то есть ограничитель становится единой точкой отказа.
- Защита от подбора паролей, дорогих операций, злоупотребления платными вызовами — отклонять. Здесь снятие ограничения хуже отказа.

Промежуточный вариант — при недоступности Redis переходить на локальный ограничитель в памяти с пределом, поделённым на число экземпляров. Он неточен, но лучше обоих крайних случаев.

## Distributed Rate Limiting через Redis

Локальный ограничитель в памяти при нескольких экземплярах сервиса даёт фактический предел, умноженный на их число: каждый экземпляр считает свой поток независимо. При десяти подах предел «100 запросов в секунду» превращается в тысячу.

Простейший распределённый вариант — счётчик фиксированного окна:

```go
// Fixed window через Redis: INCR со сроком жизни ключа.
func redisFixedWindow(ctx context.Context, rdb *redis.Client, key string,
    limit int, window time.Duration) (bool, error) {

    n, err := rdb.Incr(ctx, key).Result()
    if err != nil {
        return true, fmt.Errorf("rate limit incr: %w", err)
    }
    // Срок жизни выставляется только при создании ключа.
    // Безусловный EXPIRE на каждом запросе продлевал бы его бесконечно,
    // и под непрерывной нагрузкой окно не завершилось бы никогда:
    // счётчик рос бы до предела и оставался там навсегда.
    if n == 1 {
        if err := rdb.Expire(ctx, key, window).Err(); err != nil {
            return true, fmt.Errorf("rate limit expire: %w", err)
        }
    }
    return n <= int64(limit), nil
}
```

Два ограничения этого варианта нужно принимать осознанно. Во-первых, это именно фиксированное окно со всплеском на границе — token bucket'ом его называть неверно, накопления и равномерного пополнения здесь нет. Во-вторых, между `INCR` и `EXPIRE` есть промежуток: если процесс упадёт ровно между ними, ключ останется без срока жизни навсегда. Устраняется это тем же способом, что и выше, — обе команды в одном скрипте Lua.

Готовая библиотека `github.com/go-redis/redis_rate/v10` реализует алгоритм GCRA (вариант leaky bucket) одним атомарным скриптом и сразу отдаёт время до следующей попытки:

```go
import "github.com/go-redis/redis_rate/v10"

limiter := redis_rate.NewLimiter(rdb)

res, err := limiter.Allow(ctx, "user:"+userID, redis_rate.PerSecond(100))
if err != nil {
    // Redis недоступен — применить выбранный режим отказа и записать метрику
    return handleLimiterFailure(err)
}
if res.Allowed == 0 {
    w.Header().Set("Retry-After", strconv.Itoa(int(res.RetryAfter.Seconds())+1))
    http.Error(w, "Too Many Requests", http.StatusTooManyRequests)
    return
}
```

Значение `res.RetryAfter` здесь важнее самого решения: оно позволяет отдать клиенту точное время ожидания вместо угаданной константы.

## gRPC interceptor

```go
func RateLimitInterceptor(limiter *rate.Limiter) grpc.UnaryServerInterceptor {
    return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
        if !limiter.Allow() {
            return nil, status.Errorf(codes.ResourceExhausted, "rate limit exceeded")
        }
        return handler(ctx, req)
    }
}

// Per-user rate limiting
func PerUserRateLimitInterceptor(limiters *PerKeyLimiter) grpc.UnaryServerInterceptor {
    return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
        userID := extractUserID(ctx)
        if !limiters.Allow(userID) {
            return nil, status.Errorf(codes.ResourceExhausted, "rate limit exceeded for user %s", userID)
        }
        return handler(ctx, req)
    }
}
```

## HTTP middleware

```go
func RateLimit(limiter *rate.Limiter) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            if !limiter.Allow() {
                w.Header().Set("Retry-After", "1")
                http.Error(w, "Too Many Requests", http.StatusTooManyRequests)
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}

// chi
r := chi.NewRouter()
r.Use(RateLimit(rate.NewLimiter(100, 200)))
```

## Client-side rate limiting

Не перегружать downstream сервис — ставить limiter на клиент:

```go
type RateLimitedClient struct {
    client  PaymentClient
    limiter *rate.Limiter
}

func (c *RateLimitedClient) Charge(ctx context.Context, req *ChargeRequest) (*ChargeResponse, error) {
    // Ждать токен перед каждым вызовом
    if err := c.limiter.Wait(ctx); err != nil {
        return nil, fmt.Errorf("rate limiter: %w", err)
    }
    return c.client.Charge(ctx, req)
}
```

Особенно это важно в пакетной обработке, где всплеск создаётся случайно — обычный цикл по десяти тысячам записей отправляет их с той скоростью, с какой их читает диск.

```go
// Обработка 10 000 записей со скоростью 100 в секунду
limiter := rate.NewLimiter(100, 100)
sem := make(chan struct{}, 20) // не более 20 обработок одновременно
var wg sync.WaitGroup

for _, record := range records {
    // Wait соблюдает скорость запуска, но не ограничивает
    // число одновременно работающих обработок.
    if err := limiter.Wait(ctx); err != nil {
        break
    }
    select {
    case sem <- struct{}{}:
    case <-ctx.Done():
        return ctx.Err()
    }

    wg.Add(1)
    go func() {
        defer wg.Done()
        defer func() { <-sem }()
        if err := processRecord(ctx, record); err != nil {
            log.Error("process record", "err", err, "id", record.ID)
        }
    }()
}

wg.Wait() // без этого функция вернётся раньше, чем закончится обработка
```

Ограничитель и семафор отвечают за разные вещи, и одного мало. Ограничитель задаёт скорость запуска — сто новых обработок в секунду. Семафор задаёт число одновременных — двадцать. Без семафора обработка, занимающая пять секунд, накопит пятьсот параллельных горутин при формально соблюдённой скорости. Без `WaitGroup` цикл завершится, пока последние записи ещё обрабатываются.

## Антипаттерны

**Ограничитель в памяти при нескольких экземплярах** — фактический предел равен заявленному, умноженному на число подов, и меняется при каждом масштабировании.

**Отказ без `Retry-After`** — клиент не знает, когда повторять, и подбирает интервал сам, обычно слишком агрессивно. Полный набор заголовков снимает вопрос:
```go
w.Header().Set("Retry-After", "1")                    // через сколько секунд можно
w.Header().Set("X-RateLimit-Limit", "100")            // предел
w.Header().Set("X-RateLimit-Remaining", "0")          // остаток
w.Header().Set("X-RateLimit-Reset", strconv.FormatInt(resetAt.Unix(), 10))
```

**Одинаковая квота для всех** — внутренний сервис и анонимный посетитель получают один предел. Обычно нужны разные уровни: анонимный, аутентифицированный, партнёрский, внутренний.

**Режим отказа выбран по умолчанию, а не осознанно** — недоступный Redis либо снимает все ограничения, либо отклоняет весь трафик, и оба варианта могут оказаться неверными для конкретного эндпоинта.

**Ошибка ограничителя не видна в метриках** — при `return true, nil` в ветке ошибки проверка перестаёт работать молча, и обнаруживается это по счёту за трафик.

**Ограничение скорости запуска принято за ограничение параллелизма** — `limiter.Wait` перед запуском горутины задаёт темп, но не число одновременных обработок; рядом нужен семафор.

**Ключ выбран без учёта NAT** — строгий предел по IP отсекает офис или мобильного оператора целиком.

## Interview-ready answer

**1. Зачем нужно ограничение частоты?**

- Две разные задачи — защита от перегрузки и справедливое распределение ёмкости между клиентами.
- Без первой — превышение ёмкости даёт не отказ части запросов, а рост очередей и отказ всех.
- Без второй — один клиент в цикле занимает весь сервис, хотя тот исправен.
- Разное место установки — общий предел на экземпляр против отдельного счётчика на клиента; обычно нужны оба.

**2. Какие алгоритмы существуют и чем различаются?**

- Fixed window — счётчик на окно; прост, но на границе пропускает двойной предел.
- Sliding window log — отметки времени всех запросов; точен полностью, память растёт с числом запросов.
- Sliding window counter — интерполяция между двумя окнами; память постоянна, точность приблизительная.
- Token bucket — накапливает неиспользованную ёмкость и допускает всплеск до размера ведра; настройка по умолчанию для входящего трафика.
- Leaky bucket — всплесков не допускает вовсе, выход равномерен; удобен для исходящего трафика.

**3. Как ограничивать частоту при нескольких экземплярах сервиса?**

- Проблема — локальный счётчик умножает фактический предел на число подов.
- Решение — общее хранилище, обычно Redis, со скриптом Lua для атомарности проверки и увеличения счётчика.
- Почему скрипт — те же команды по отдельности оставляют промежуток, в который вклинивается параллельный запрос.
- Частая ошибка — безусловный `EXPIRE` на каждом запросе: под непрерывной нагрузкой окно не завершается никогда.

**4. Что делать, если хранилище счётчиков недоступно?**

- Выбор осознанный — пропускать или отклонять, в зависимости от назначения ограничителя.
- Пропускать — при защите от перегрузки: иначе Redis становится единой точкой отказа всего сервиса.
- Отклонять — при защите от подбора паролей и дорогих операций: снятие ограничения хуже отказа.
- Промежуточный вариант — локальный ограничитель с пределом, поделённым на число экземпляров.
- В любом случае — метрика на ошибки проверки, иначе отключившийся ограничитель не обнаруживается.

**5. По какому ключу считать?**

- Идентификатор пользователя — основной вариант для аутентифицированных вызовов.
- IP-адрес — единственный доступный до входа, но за ним может быть офис или мобильный оператор через NAT.
- Практичная комбинация — мягкий предел по IP на вход и регистрацию, жёсткий по пользователю после аутентификации.
- Техническая деталь — за прокси адрес берётся из `X-Forwarded-For`, и доверять можно только части, записанной собственным прокси.
