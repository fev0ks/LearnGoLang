Повтор — самый дешёвый способ пережить кратковременный сбой: потерянный пакет, перезапуск пода, короткую недоступность реплики. Ничего сложнее одного цикла он не требует, и поэтому появляется в коде раньше всех остальных приёмов надёжности.

Опасность у него ровно оттуда же. Повтор увеличивает нагрузку именно в тот момент, когда зависимость с ней не справляется: сервис ответил ошибкой из-за перегрузки, клиенты немедленно повторили запросы, нагрузка выросла втрое, восстановление стало невозможным. Дальше в статье разбирается, какими ограничителями этот эффект снимается — паузой, случайным разбросом, ограничением доли повторов и запретом повторять на каждом уровне цепочки.

## Когда retry уместен

Повтор имеет смысл при совпадении двух условий: ошибка временная, а операция идемпотентна.

**Retry безопасен:**
- `503 Service Unavailable` — сервис временно перегружен
- `429 Too Many Requests` — rate limit, отступить и попробовать позже
- Network timeout / connection reset — временный сетевой сбой
- `500 Internal Server Error` — повторять допустимо, только если операция идемпотентна

**Retry опасен / бессмысленен:**
- `400 Bad Request` — данные неверные, retry вернёт то же
- `401 Unauthorized` / `403 Forbidden` — права не изменятся сами
- `404 Not Found` — ресурс не появится
- `409 Conflict` — конфликт состояния, нужна бизнес-логика
- Не идемпотентные операции: `POST /payments` без idempotency key — повторный retry создаст дублирующий платёж

```go
func isRetriable(err error) bool {
    // Отмена вызывающим — не повод повторять: клиент уже ушёл.
    if errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded) {
        return false
    }

    var statusErr interface{ StatusCode() int }
    if errors.As(err, &statusErr) {
        switch statusErr.StatusCode() {
        case http.StatusTooManyRequests,
            http.StatusServiceUnavailable,
            http.StatusBadGateway,
            http.StatusGatewayTimeout:
            return true
        }
        // 500 сознательно отсутствует: без знания об идемпотентности
        // конкретного вызова повтор небезопасен.
        return false
    }

    // Сетевые ошибки
    var netErr net.Error
    if errors.As(err, &netErr) && netErr.Timeout() {
        return true
    }
    return false
}
```

Три решения в этом коде стоят пояснения.

**Отмена контекста исключена из списка.** `context.Canceled` означает, что вызывающий уже не ждёт ответа, а `DeadlineExceeded` — что бюджет исчерпан. Повтор в обоих случаях создаёт нагрузку ради результата, который никто не получит.

**Кода 500 в списке нет.** Прозой выше сказано, что при идемпотентной операции повторять его можно, и это верно, — но функция `isRetriable` не знает, какой именно вызов её породил. Решение об идемпотентности принимается на уровне вызова, а не на уровне классификации ошибок: конкретный клиент с идемпотентным `PUT` добавляет 500 к своему списку сам.

**Сетевой таймаут считается временным условно.** `netErr.Timeout()` не различает случаи «запрос не дошёл» и «запрос выполнен, ответ потерян». Для чтения разницы нет, для записи это ровно та ситуация, где нужен ключ идемпотентности — см. [Idempotency](./06-idempotency.md).

## Exponential backoff

Линейный retry (попробовать немедленно 3 раза) при массовом сбое создаёт всплеск нагрузки точно в момент когда сервис пытается восстановиться.

Exponential backoff увеличивает паузу между попытками экспоненциально:

```
попытка 1: подождать base * 2^0 = 100ms
попытка 2: подождать base * 2^1 = 200ms
попытка 3: подождать base * 2^2 = 400ms
попытка 4: подождать base * 2^3 = 800ms
...
ограничить максимумом: cap = 30s
```

```go
func backoffDuration(attempt int, base, max time.Duration) time.Duration {
    // Сдвиг ограничен: base * (1 << 62) переполняет int64 и даёт
    // отрицательную длительность, то есть паузу нулевой длины.
    if attempt > 62 {
        return max
    }
    d := base << attempt // base * 2^attempt
    if d <= 0 || d > max {
        return max
    }
    return d
}
```

Параметр назван `max`, а не `cap`: `cap` — встроенная функция Go, и локальная переменная с таким именем перекрывает её в пределах функции. Ошибки это не вызывает, но сбивает при чтении.

## Jitter: зачем и какой

Экспоненциальная пауза решает половину задачи. Вторая половина в том, что клиенты, получившие ошибку одновременно, и повторят одновременно: пауза у всех одинаковая, поэтому нагрузка приходит не потоком, а импульсами.

```
Без разброса: сервис восстановился, и через 400 мс в него разом
              приходят 1000 повторов — он падает снова.

С разбросом:  те же 1000 повторов размазаны по интервалу 0-400 мс,
              и приходят потоком в 2.5 запроса на миллисекунду.
```

Случайный разброс (`jitter`) устраняет синхронность. Ниже — три варианта из [статьи AWS про экспоненциальный backoff](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/); все примеры используют `math/rand/v2` (Go 1.22+), где глобальный источник безопасен для одновременного использования и не требует инициализации.

### Full jitter

```go
// пауза = random(0, min(max, base * 2^attempt))
func fullJitter(attempt int, base, max time.Duration) time.Duration {
    ceiling := backoffDuration(attempt, base, max)
    if ceiling <= 0 {
        return 0
    }
    // rand.N паникует на неположительном аргументе — отсюда проверка выше.
    return rand.N(ceiling)
}
```

Распределение равномерное от нуля до потолка: запросы рассредоточены максимально. Обратная сторона — часть повторов уходит почти сразу, поэтому на упавшей зависимости нагрузка снижается медленнее, чем при других вариантах.

### Equal jitter

```go
// пауза = ceiling/2 + random(0, ceiling/2)
func equalJitter(attempt int, base, max time.Duration) time.Duration {
    ceiling := backoffDuration(attempt, base, max)
    half := ceiling / 2
    if half <= 0 {
        return ceiling
    }
    return half + rand.N(half)
}
```

Компромисс: минимальная пауза гарантирована, разброс сохраняется. Подходит, когда мгновенный повтор нежелателен — например, зависимости нужно время на перезапуск.

### Decorrelated jitter

```go
// пауза = random(base, prev*3), ограниченная сверху
func decorrelatedJitter(base, max, prev time.Duration) time.Duration {
    if prev < base {
        prev = base
    }
    span := prev*3 - base
    if span <= 0 { // защита от переполнения при больших prev
        return max
    }
    d := base + rand.N(span)
    if d > max {
        return max
    }
    return d
}
```

Здесь пауза считается от предыдущей, а не от номера попытки, поэтому разброс между клиентами накапливается с каждым шагом. По замерам AWS этот вариант даёт наименьшее суммарное число обращений к восстанавливающемуся сервису, но требует хранить состояние между попытками.

**Что выбрать.** Full jitter — настройка по умолчанию: он простейший и хорошо изучен. Equal jitter — когда нужна гарантированная минимальная пауза. Decorrelated — когда клиентов много и важно минимизировать суммарную нагрузку на восстановление.

## Retry budget

Экспоненциальная пауза и разброс растягивают повторы во времени, но не ограничивают их количество. Если зависимость лежит целиком, каждый запрос всё равно порождает свои три попытки — нагрузка на неё оказывается втрое выше обычной именно тогда, когда она пытается подняться.

Retry budget ограничивает долю повторов от общего потока. Ориентир — 10%: на сто исходных запросов допускается не более десяти повторов. Когда доля исчерпана, повторы прекращаются и ошибка возвращается вызывающему сразу.

Ключевой момент реализации: считать нужно две разные величины. Число исходных запросов растёт при каждом обращении к зависимости, число повторов — только при попытке повторить. Смешав их в одном счётчике, получить долю невозможно.

```go
type RetryBudget struct {
    mu       sync.Mutex
    requests int64
    retries  int64
    ratio    float64       // допустимая доля повторов, 0.1 = 10%
    window   time.Duration // длина окна учёта
    resetAt  time.Time
}

func NewRetryBudget(ratio float64, window time.Duration) *RetryBudget {
    return &RetryBudget{ratio: ratio, window: window, resetAt: time.Now().Add(window)}
}

// RecordRequest вызывается на каждую исходную попытку — она формирует знаменатель.
func (b *RetryBudget) RecordRequest() {
    b.mu.Lock()
    defer b.mu.Unlock()
    b.rotateLocked()
    b.requests++
}

// AllowRetry вызывается только перед повтором и списывает бюджет.
func (b *RetryBudget) AllowRetry() bool {
    b.mu.Lock()
    defer b.mu.Unlock()
    b.rotateLocked()

    // Минимальный запас, чтобы повторы работали на малом трафике:
    // при пяти запросах в окне доля в 10% иначе не даёт ни одного повтора.
    const minRetries = 3
    allowed := float64(b.requests)*b.ratio + minRetries

    if float64(b.retries) >= allowed {
        return false // бюджет исчерпан
    }
    b.retries++
    return true
}

func (b *RetryBudget) rotateLocked() {
    if now := time.Now(); now.After(b.resetAt) {
        b.requests, b.retries = 0, 0
        b.resetAt = now.Add(b.window)
    }
}
```

Жёсткое окно с обнулением — упрощение. В момент сброса бюджет восстанавливается скачком, и на границе окна возможен всплеск повторов. Реализации в service mesh (Envoy, Linkerd) используют вместо этого скользящее среднее с затуханием: бюджет восстанавливается плавно, границы окна нет.

## Retry amplification в цепочке сервисов

Самая опасная проблема: retry на каждом уровне перемножается.

```
Клиент → A (3 retry) → B (3 retry) → C (3 retry) → DB

При одном сбое в DB:
  A делает 3 попытки
  Каждая попытка A → B делает 3 попытки
  Каждая попытка B → C делает 3 попытки
  Итого на DB: 3 × 3 × 3 = 27 запросов вместо 1
```

Число 27 здесь получается перемножением, а не сложением: каждая попытка внешнего уровня целиком запускает все попытки внутренних. При четырёх уровнях по три попытки нагрузка на нижний элемент вырастает в 81 раз — и приходит она в момент, когда он уже не справляется.

Из этого следует главное правило: повторять должен ровно один уровень цепочки. Какой именно — вопрос с двумя рабочими ответами.

**Повтор на нижнем уровне, ближе к сбою.** Реагирует быстрее всех: сбой обнаруживается там, где произошёл, и лечится до того, как о нём узнают верхние уровни. Требует, чтобы бюджет времени нижнего уровня допускал несколько попыток, — иначе повтор не успеет и обернётся таймаутом наверху.

**Повтор на верхнем уровне, у клиента.** Обрабатывает больше видов сбоев: не только отказ конечной зависимости, но и падение любого промежуточного звена. Реагирует медленнее и тратит работу всей цепочки заново.

Промежуточные уровни в обоих случаях ошибку просто пробрасывают. Отдельный ориентир для эксплуатации: заголовок `Retry-After` от вызываемой стороны имеет приоритет над собственным расчётом паузы — сервис знает о своём состоянии больше, чем клиент.

```go
// Проверить Retry-After header перед retry
func retryAfterDelay(resp *http.Response) time.Duration {
    if resp == nil {
        return 0
    }
    h := resp.Header.Get("Retry-After")
    if h == "" {
        return 0
    }
    // Retry-After может быть числом секунд или датой
    if secs, err := strconv.Atoi(h); err == nil {
        return time.Duration(secs) * time.Second
    }
    if t, err := http.ParseTime(h); err == nil {
        return time.Until(t)
    }
    return 0
}
```

## Реализация в Go

```go
type RetryConfig struct {
    MaxAttempts    int
    BaseDelay      time.Duration
    MaxDelay       time.Duration
    AttemptTimeout time.Duration // предел на одну попытку
}

func WithRetry(ctx context.Context, cfg RetryConfig, fn func(ctx context.Context) error) error {
    var lastErr error

    for attempt := 0; attempt < cfg.MaxAttempts; attempt++ {
        if err := ctx.Err(); err != nil {
            return err // бюджет исчерпан или вызывающий ушёл
        }

        // Таймаут на попытку, а не на весь цикл: без него первая же
        // зависшая попытка съест бюджет, и до второй дело не дойдёт.
        attemptCtx, cancel := context.WithTimeout(ctx, cfg.AttemptTimeout)
        lastErr = fn(attemptCtx)
        cancel()

        if lastErr == nil {
            return nil
        }
        if !isRetriable(lastErr) {
            return lastErr
        }
        if attempt == cfg.MaxAttempts-1 {
            break
        }

        delay := fullJitter(attempt, cfg.BaseDelay, cfg.MaxDelay)

        // Если пауза не помещается в оставшийся бюджет, ждать бессмысленно:
        // попытка всё равно начнётся с уже истёкшим контекстом.
        if deadline, ok := ctx.Deadline(); ok && time.Until(deadline) < delay {
            break
        }

        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-time.After(delay):
        }
    }

    return fmt.Errorf("after %d attempts: %w", cfg.MaxAttempts, lastErr)
}

// Использование
err := WithRetry(ctx, RetryConfig{
    MaxAttempts:    3,
    BaseDelay:      100 * time.Millisecond,
    MaxDelay:       5 * time.Second,
    AttemptTimeout: 300 * time.Millisecond,
}, func(ctx context.Context) error {
    return client.Call(ctx, req)
})
```

Числа в этом примере согласованы между собой, и это не случайность. Три попытки по 300 мс плюс паузы до 400 мс дают худший случай около 1.5 секунды — значение должно помещаться в бюджет вызывающего. Обратный порядок («поставим пять попыток на всякий случай») даёт цикл, который в худшем случае не укладывается ни в один разумный SLO, и обрывается он тогда не по своей логике, а по внешнему таймауту — в непредсказуемый момент.

Готовые библиотеки:
- `github.com/cenkalti/backoff/v4` — полнофункциональная библиотека, ExponentialBackOff
- `google.golang.org/grpc/backoff` — стандартный backoff для gRPC reconnect

## Антипаттерны

**Повтор без паузы** — цикл `for { if err = call(); err == nil { break } }` превращает недоступную зависимость в нагрузочный тест против неё же: пока сервис лежит, клиент бьёт в него со скоростью сетевого стека.

**Повтор неидемпотентной операции** — `POST /payments` без ключа идемпотентности. Сетевой таймаут не означает, что платёж не прошёл, и повтор списывает деньги второй раз.

**Игнорирование контекста в цикле** — без проверки `ctx.Err()` перед попыткой сервис продолжает работать на клиента, который уже отключился, и тратит на это соединения и время зависимости.

**Повтор без верхней границы** — без `MaxAttempts` и без бюджета повторов число одновременных попыток растёт вместе с длительностью сбоя, а вместе с ним и число живых горутин.

**Одинаковая пауза без разброса** — тысяча клиентов, получивших ошибку в одну секунду, вернутся ровно через секунду все сразу. Восстанавливающийся сервис получает импульс вместо потока и падает повторно.

**Повтор на каждом уровне цепочки** — три уровня по три попытки дают двадцать семь обращений к нижнему элементу вместо одного.

## Interview-ready answer

**1. Когда повтор уместен?**

- Два условия сразу — ошибка временная и операция идемпотентна; при невыполнении любого повторять нельзя.
- Временные ошибки — 429, 503, 502, 504, сетевые таймауты и сбросы соединения.
- Не временные — 400, 401, 403, 404, 409: повтор вернёт тот же результат и потратит бюджет.
- Отдельный случай — 500: повторять можно, только если конкретный вызов идемпотентен, поэтому в общей классификации ошибок его не держат.
- Отмена контекста — не повод повторять: вызывающий уже ушёл.

**2. Зачем нужна экспоненциальная пауза и разброс?**

- Пауза — снижает частоту обращений к зависимости, которая не справляется; без неё повтор работает как нагрузочный тест против неё.
- Разброс — устраняет синхронность: без него все клиенты возвращаются одновременно и создают импульс вместо потока.
- Варианты — full jitter как настройка по умолчанию, equal jitter при нужной минимальной паузе, decorrelated при большом числе клиентов.
- Приоритет — заголовок `Retry-After` от сервиса важнее собственного расчёта.

**3. Что такое retry amplification и как его избежать?**

- Механика — попытки на разных уровнях перемножаются: три уровня по три попытки дают 27 обращений к нижнему элементу.
- Момент проявления — ровно тогда, когда нижний элемент уже перегружен, то есть усиливает исходный сбой.
- Правило — повторяет ровно один уровень цепочки, остальные пробрасывают ошибку.
- Выбор уровня — нижний реагирует быстрее, верхний покрывает больше видов сбоев.

**4. Что ограничивает число повторов помимо MaxAttempts?**

- Retry budget — доля повторов от общего потока, ориентир 10%; при исчерпании повторы прекращаются.
- Считать нужно две величины — исходные запросы и повторы отдельно, иначе доля не вычисляется.
- Малый трафик — требует минимального запаса, иначе при пяти запросах в окне доля в 10% не даёт ни одного повтора.
- Бюджет времени — пауза, не помещающаяся в оставшийся дедлайн, бессмысленна: попытка начнётся с истёкшим контекстом.
- Таймаут на попытку — обязателен отдельно от общего, иначе первая зависшая попытка израсходует весь бюджет.
