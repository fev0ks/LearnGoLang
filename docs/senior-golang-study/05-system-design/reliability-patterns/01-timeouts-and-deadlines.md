Вызов без таймаута не имеет предела ожидания — и это утверждение стоит понимать буквально. Сервер на другом конце может не ответить никогда: процесс завис, сеть потеряла пакеты без сброса соединения, промежуточный балансировщик держит сокет открытым. Ожидающая горутина при этом жива, занимает память и держит соединение из пула.

Дальше срабатывает механика, из-за которой тема относится к надёжности, а не к удобству. Запросы продолжают приходить, каждый порождает новую ожидающую горутину, пул соединений к базе исчерпывается, и отказывать начинают в том числе те запросы, которые к медленной зависимости отношения не имеют. Отказ одного компонента превращается в отказ всего сервиса — за минуты и без единой ошибки в логах.

## Timeout vs Deadline

**Timeout** — относительная величина: подождать не более 500 мс.

**Deadline** — абсолютная точка во времени: завершиться не позже 14:05:00.500.

В Go `context.WithTimeout` создаёт дедлайн под капотом:
```go
// Эти два вызова эквивалентны:
ctx, cancel := context.WithTimeout(parent, 500*time.Millisecond)
ctx, cancel := context.WithDeadline(parent, time.Now().Add(500*time.Millisecond))
```

Разница проявляется при передаче по цепочке. Относительный таймаут при каждой пересылке начинается заново: сервис A ждёт 500 мс, внутри вызывает B и снова даёт ему 500 мс, B даёт столько же C. Клиент в худшем случае ждёт сумму, а не 500 мс.

Абсолютный дедлайн такого свойства не имеет. Если запрос пришёл с дедлайном 14:05:00.500, а на обработку уже ушло 200 мс, вызов вглубь получает оставшиеся 300 мс, а не новые 500. Именно поэтому в протоколах передают дедлайн, а не таймаут, и `context.Context` хранит `Deadline()`, а не длительность.

## Latency budget

Latency budget (бюджет задержки) — полное время, отведённое на запрос от клиента до ответа. Каждый шаг цепочки расходует часть этого бюджета, и сумма долей не может превышать целое.

```
Клиент → SLO: ответить за 1000ms

HTTP handler (10ms overhead)     → 990ms остаток
  Auth service (max 50ms)        → 940ms остаток
  DB query: get user (max 20ms)  → 920ms остаток
  Payment service (max 200ms)    → 720ms остаток
  DB query: save order (max 20ms)→ 700ms остаток
  Response serialization (5ms)   → буфер: 695ms
```

Расписанный бюджет отвечает на вопрос, откуда взялось конкретное число в конфигурации. Без него значения ставят по интуиции, и типичный результат — таймаут в 30 секунд на каждый вызов при SLO в одну секунду: формально таймаут есть, практически он не срабатывает никогда и от зависания не защищает.

Два свойства бюджета стоит держать в голове.

**Последовательные вызовы складываются, параллельные — нет.** Если авторизация и загрузка профиля идут одновременно, из бюджета вычитается больший из двух таймаутов, а не сумма. Это самый дешёвый способ уложиться в жёсткий бюджет — до попыток ускорять сами вызовы.

**Резерв нужен обязательно.** В примере выше 695 мс остаются незанятыми не по недосмотру: между шагами есть сериализация, ожидание соединения из пула, паузы сборщика мусора и сетевые задержки внутри кластера. Бюджет, расписанный без остатка, нарушается при первом же всплеске.

## Deadline propagation

В распределённой системе дедлайн должен течь через всю цепочку вызовов. В Go это делается через `context.Context`.

```go
// Входящий HTTP запрос — установить корневой дедлайн
func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 1*time.Second)
    defer cancel()

    // ctx передаётся во все downstream вызовы
    user, err := h.authService.GetUser(ctx, userID)
    if err != nil {
        // ...
    }
    order, err := h.paymentService.CreateOrder(ctx, orderReq)
    // ...
}
```

```go
// auth service — принимает ctx с уже уменьшенным бюджетом
func (s *AuthService) GetUser(ctx context.Context, id string) (*User, error) {
    // Новый context.WithTimeout(context.Background(), ...) здесь создавать нельзя:
    // дедлайн вызывающего потеряется, и запрос переживёт ушедшего клиента.

    // Дедлайн можно ужесточить, но не ослабить:
    subCtx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
    defer cancel()

    var u User
    err := s.db.QueryRow(subCtx, "SELECT id, email FROM users WHERE id = $1", id).
        Scan(&u.ID, &u.Email)
    if err != nil {
        return nil, fmt.Errorf("get user %s: %w", id, err)
    }
    return &u, nil
}
```

Слова «ужесточить, но не ослабить» описывают не соглашение, а поведение реализации. `context.WithTimeout` порождает дочерний контекст, который отменяется при отмене родителя. Поэтому `context.WithTimeout(ctx, time.Hour)` при родительском дедлайне через 300 мс даст контекст, истекающий всё равно через 300 мс: более поздний дедлайн просто не наступит раньше родительского.

### gRPC deadline propagation

gRPC автоматически передаёт дедлайн из context в заголовке `grpc-timeout`. Сервер получает его и восстанавливает в context:

```go
// Клиент
ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
defer cancel()
resp, err := client.GetUser(ctx, req)
// Уходит заголовок grpc-timeout: 498m — оставшееся время, а не абсолютная метка

// Сервер получает ctx с уже установленным дедлайном
func (s *Server) GetUser(ctx context.Context, req *pb.GetUserRequest) (*pb.GetUserResponse, error) {
    deadline, ok := ctx.Deadline()
    if ok {
        remaining := time.Until(deadline)
        // remaining ≈ 495ms — немного меньше из-за network latency
    }
    // Передавать ctx дальше — propagation работает автоматически
    return s.repo.Get(ctx, req.Id)
}
```

Существенная деталь: `grpc-timeout` передаёт именно остаток времени, а не момент истечения. Это осознанное решение спецификации — относительная величина не зависит от расхождения часов между машинами. Абсолютная метка при часах, убежавших на секунду вперёд, дала бы уже истёкший дедлайн на принимающей стороне.

### HTTP deadline propagation

В HTTP дедлайн не стандартизирован, его передают собственным заголовком:

```go
// Отправитель
const deadlineHeader = "X-Deadline"

func withDeadlineHeader(ctx context.Context, req *http.Request) *http.Request {
    if deadline, ok := ctx.Deadline(); ok {
        req.Header.Set(deadlineHeader, deadline.Format(time.RFC3339Nano))
    }
    return req.WithContext(ctx)
}

// Получатель (middleware)
func DeadlinePropagation(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if h := r.Header.Get(deadlineHeader); h != "" {
            if deadline, err := time.Parse(time.RFC3339Nano, h); err == nil {
                // Только если дедлайн ещё не истёк
                if time.Until(deadline) > 0 {
                    ctx, cancel := context.WithDeadline(r.Context(), deadline)
                    defer cancel()
                    r = r.WithContext(ctx)
                }
            }
        }
        next.ServeHTTP(w, r)
    })
}
```

У этой реализации есть ограничение, которое стоит осознавать перед внедрением: она передаёт абсолютную метку времени и потому зависит от синхронности часов. Расхождение в секунду между отправителем и получателем означает, что получатель либо сразу отбросит живой запрос, либо будет работать на секунду дольше отведённого.

Практических выходов два. Требовать синхронизации часов через NTP и держать расхождение в пределах десятков миллисекунд — так делают внутри одного кластера. Либо передавать остаток в миллисекундах, как поступает gRPC: тогда точность зависит только от сетевой задержки, а не от настроек времени на машинах.

## Как выбрать значение таймаута

Отправная точка — распределение времени ответа зависимости, а не круглое число.

Разумный порядок действий такой:

1. **Снять фактическое распределение.** Нужны p50, p95, p99 и максимум за период, покрывающий пиковую нагрузку. Среднее здесь бесполезно: оно скрывает именно тот хвост, ради которого ставится таймаут.
2. **Взять p99 с запасом.** Обычный ориентир — p99, умноженный на 1.5-2. Таймаут по p99 без запаса будет обрывать процент нормальных запросов, а каждый оборванный запрос обычно превращается в повтор и добавляет нагрузку.
3. **Сверить с бюджетом.** Если полученное значение не помещается в оставшийся бюджет, проблема не в таймауте: либо вызовы нужно распараллелить, либо зависимость ускорить, либо ответ отдавать без неё.
4. **Пересматривать после изменений.** Значения устаревают вместе с нагрузкой и объёмом данных.

Обратный порядок — «начать со строгого значения и ослаблять по мере жалоб» — работает плохо. Первое включение отсекает часть исправных запросов, а на графике это выглядит как отказ зависимости, а не как ошибка настройки.

Отдельно стоит определить поведение при срабатывании. Таймаут — это не ошибка запроса, а отсутствие ответа: неизвестно, выполнилась операция или нет. Для чтения это неважно, для записи означает, что повтор нужен только при идемпотентности вызова — иначе получится второй платёж вместо одного. Подробнее — в [Idempotency](./06-idempotency.md).

## Настройка таймаутов в Go

### HTTP Client

```go
// http.DefaultClient не имеет таймаута вообще: зависший ответ
// удерживает горутину и соединение неограниченно долго.
client := &http.Client{
    Timeout: 5 * time.Second,  // полный таймаут запроса включая чтение body
    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout:   2 * time.Second,  // TCP соединение
            KeepAlive: 30 * time.Second,
        }).DialContext,
        TLSHandshakeTimeout:   3 * time.Second,
        ResponseHeaderTimeout: 3 * time.Second,  // ждать первый байт ответа
        IdleConnTimeout:       90 * time.Second,
        MaxIdleConns:          100,
        MaxIdleConnsPerHost:   10,
    },
}

// Таймаут на конкретный запрос — через контекст
ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
resp, err := client.Do(req)
```

Уровни в этой настройке не дублируют друг друга, а покрывают разные стадии:

| Параметр | Что ограничивает | Что происходит без него |
|---|---|---|
| `Dialer.Timeout` | Установление TCP-соединения | Недоступный хост держит запрос до таймаута ядра — это минуты |
| `TLSHandshakeTimeout` | Рукопожатие TLS | Сервер, принявший соединение и замолчавший, блокирует запрос |
| `ResponseHeaderTimeout` | Ожидание первого байта ответа | Запрос, принятый и «зависший» на сервере, не обнаруживается |
| `Client.Timeout` | Весь запрос вместе с чтением тела | Медленная передача большого тела длится неограниченно |
| Контекст запроса | То же, что `Client.Timeout`, но на конкретный вызов | Все запросы живут по общему значению вместо своего бюджета |

Существенно, что `Client.Timeout` покрывает и чтение тела ответа. Для потоковых ответов и скачивания больших файлов это означает жёсткий предел на всю передачу: такие вызовы делают отдельным клиентом без общего таймаута, ограничивая только стадии установления соединения, а срок жизни задают контекстом.

### PostgreSQL (pgx)

```go
// Таймаут на соединение
poolConfig.ConnConfig.ConnectTimeout = 5 * time.Second

// Таймаут на конкретный запрос — через context
ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
defer cancel()
row := pool.QueryRow(ctx, "SELECT * FROM users WHERE id = $1", id)
```

### Redis (go-redis)

```go
rdb := redis.NewClient(&redis.Options{
    Addr:         "localhost:6379",
    DialTimeout:  2 * time.Second,
    ReadTimeout:  500 * time.Millisecond,
    WriteTimeout: 500 * time.Millisecond,
    PoolTimeout:  1 * time.Second,  // ждать свободное соединение из пула
})
```

## Антипаттерны

**Создавать новый `context.Background()` вместо передачи родительского** — дедлайн теряется, downstream не знает что пора остановиться.

```go
// плохо — новый background context, дедлайн потерян
result, err := s.db.Query(context.Background(), query)

// хорошо — передать ctx из аргумента
result, err := s.db.Query(ctx, query)
```

**Не вызывать cancel()** — утечка goroutine таймера:
```go
// плохо
ctx, _ := context.WithTimeout(parent, 5*time.Second)

// хорошо
ctx, cancel := context.WithTimeout(parent, 5*time.Second)
defer cancel()
```

**Передавать контекст с истёкшим дедлайном** — вызываемая сторона всё равно вернёт `context.DeadlineExceeded`, но соединение из пула уже будет занято, а на стороне сервера запрос успеет начать выполняться. Проверка перед вызовом экономит и то, и другое:
```go
if err := ctx.Err(); err != nil {
    return nil, err // бюджет уже исчерпан — не тратить ресурсы
}
result, err := callDownstream(ctx, req)
```

**Один глобальный таймаут на всё** — `context.WithTimeout(r.Context(), 30*time.Second)` и дальше тот же контекст везде. Формально таймаут есть, но зависший вызов на десятой секунде отнимает время у всех последующих шагов, и обрывается в итоге не он, а запрос целиком.

**Значение, выбранное без данных** — как слишком строгое, так и слишком мягкое. Строгое отсекает исправные запросы и выглядит на графиках отказом зависимости. Мягкое (те же 30 секунд при SLO в секунду) не срабатывает никогда и существует только в конфигурации.

**Таймаут без решения, что делать дальше** — код получает `DeadlineExceeded` и просто отдаёт ошибку выше. Между тем именно здесь принимается выбор: вернуть частичный ответ без необязательной части, отдать закэшированное значение, поставить задачу в очередь или всё-таки ответить ошибкой. Разбор вариантов — в [Backpressure и Load Shedding](./05-backpressure-and-shedding.md).

## Interview-ready answer

**1. Почему вызов без таймаута опаснее, чем кажется?**

- Причина — отсутствие предела ожидания: зависший ответ удерживает горутину и соединение неограниченно долго.
- Развитие — новые запросы продолжают приходить, пул соединений исчерпывается, отказывать начинают и не связанные с зависимостью запросы.
- Итог — отказ одного компонента превращается в отказ сервиса, причём без ошибок в логах: запросы не падают, а висят.

**2. Чем дедлайн отличается от таймаута и почему передают именно дедлайн?**

- Таймаут относителен, дедлайн абсолютен — это точка во времени, а не длительность.
- Проблема таймаута в цепочке — при каждой пересылке отсчёт начинается заново, и клиент ждёт сумму по всем звеньям.
- Дедлайн передаётся по цепочке и уменьшается сам: потратив 200 мс из 500, сервис отдаёт дальше 300.
- В Go это `context.Context`, который хранит `Deadline()`; ужесточить дочерним контекстом можно, ослабить — нет.
- В gRPC заголовок `grpc-timeout` несёт остаток, а не метку времени — чтобы не зависеть от расхождения часов.

**3. Как выбирается конкретное значение?**

- Основа — распределение времени ответа зависимости: p99 с запасом в полтора-два раза, а не круглое число.
- Ограничение сверху — бюджет задержки: сумма таймаутов последовательных вызовов должна помещаться в SLO с резервом.
- Параллельные вызовы — расходуют максимум из своих таймаутов, а не сумму; это первый способ уложиться в жёсткий бюджет.
- Признак неверного значения — таймаут, который не срабатывает никогда, либо отсекает исправные запросы.

**4. Что делать при срабатывании таймаута?**

- Главное — таймаут не означает, что операция не выполнилась: ответ не пришёл, а состояние на той стороне неизвестно.
- Для чтения — повтор безопасен.
- Для записи — повтор допустим только при идемпотентности вызова, иначе получится дубль операции.
- Помимо повтора — есть варианты ответить без необязательной части, отдать закэшированное значение или поставить задачу в очередь.
