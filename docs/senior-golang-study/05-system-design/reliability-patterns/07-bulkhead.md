Bulkhead (переборка) — изоляция ресурсов по зависимостям. Название пришло из судостроения: корпус разделён водонепроницаемыми переборками, и пробоина в одном отсеке не топит судно целиком.

В сервисе роль воды играет время ожидания. Ресурс, который заполняется, — горутины, соединения, слоты в пуле; медленная зависимость забирает их все и оставляет без ресурсов работу, которая с этой зависимостью не связана. Переборка ограничивает объём, который каждая зависимость способна занять.

---

## Проблема общего пула

Без bulkhead все зависимости конкурируют за одни ресурсы:

```
Сервис: max 200 одновременных goroutines

PaymentService начал отвечать за 5s (вместо 200ms)

1. Запросы к PaymentService занимают goroutines, ждут 5s
2. Через несколько секунд все 200 goroutines заняты PaymentService
3. Запросы к UserService и NotificationService тоже не обрабатываются
4. Весь сервис деградирует из-за одной медленной зависимости
```

С bulkhead каждая зависимость имеет свой изолированный лимит:

```
PaymentService:      max 50 concurrent
UserService:         max 80 concurrent
NotificationService: max 30 concurrent
Прочие:              max 40 concurrent

Если PaymentService тормозит — его 50 goroutines заблокированы,
остальные 150 продолжают работать нормально
```

## Bulkhead через semaphore per dependency

```go
type Bulkheads struct {
    Payment      *semaphore.Weighted
    User         *semaphore.Weighted
    Notification *semaphore.Weighted
}

func NewBulkheads() *Bulkheads {
    return &Bulkheads{
        Payment:      semaphore.NewWeighted(50),
        User:         semaphore.NewWeighted(80),
        Notification: semaphore.NewWeighted(30),
    }
}

// Обёртка клиента с bulkhead
type PaymentClient struct {
    inner     PaymentServiceClient
    bulkhead  *semaphore.Weighted
    timeout   time.Duration
}

func (c *PaymentClient) Charge(ctx context.Context, req *ChargeRequest) (*ChargeResponse, error) {
    // Попытаться занять slot с таймаутом
    acquireCtx, cancel := context.WithTimeout(ctx, c.timeout)
    defer cancel()

    if err := c.bulkhead.Acquire(acquireCtx, 1); err != nil {
        // Все слоты заняты — быстрый отказ
        return nil, fmt.Errorf("payment bulkhead full: %w", ErrServiceOverloaded)
    }
    defer c.bulkhead.Release(1)

    return c.inner.Charge(ctx, req)
}
```

### С метриками

У `semaphore.Weighted` нет метода, возвращающего текущую заполненность, поэтому её считают отдельным счётчиком. Увеличивать его нужно после успешного захвата, а не до: иначе метрика покажет число желающих, а не число работающих.

```go
type PaymentClient struct {
    inner    PaymentServiceClient
    bulkhead *semaphore.Weighted
    inFlight atomic.Int64
    timeout  time.Duration
}

func (c *PaymentClient) Charge(ctx context.Context, req *ChargeRequest) (*ChargeResponse, error) {
    acquireCtx, cancel := context.WithTimeout(ctx, c.timeout)
    defer cancel()

    if err := c.bulkhead.Acquire(acquireCtx, 1); err != nil {
        metrics.BulkheadRejected.WithLabelValues("payment").Inc()
        return nil, fmt.Errorf("payment bulkhead full: %w", ErrServiceOverloaded)
    }
    defer c.bulkhead.Release(1)

    metrics.BulkheadInFlight.WithLabelValues("payment").Set(float64(c.inFlight.Add(1)))
    defer func() {
        metrics.BulkheadInFlight.WithLabelValues("payment").Set(float64(c.inFlight.Add(-1)))
    }()

    start := time.Now()
    resp, err := c.inner.Charge(ctx, req)
    metrics.BulkheadLatency.WithLabelValues("payment").Observe(time.Since(start).Seconds())
    return resp, err
}
```

Метрик нужно именно две. Заполненность отвечает на вопрос «насколько близко к пределу», счётчик отказов — «сколько запросов уже отклонено». Первая позволяет заметить приближение к границе заранее, вторая фиксирует факт срабатывания. По одной заполненности отказы неразличимы: график, упирающийся в потолок, выглядит одинаково и при одном отклонённом запросе, и при тысяче.

## Как выбрать размер отсека

Размер задаётся не наугад, а через ёмкость самой зависимости и закон Литтла: `параллелизм = пропускная способность × время ответа`.

```
Платёжный сервис держит 200 запросов в секунду, отвечает за 250 мс.
Нужный параллелизм = 200 × 0.25 = 50 одновременных вызовов.
```

Пятьдесят и есть разумный размер отсека: он позволяет использовать всю доступную ёмкость и не даёт занять больше. Отсек вдвое больше не увеличит пропускную способность — зависимость всё равно обработает 200 запросов в секунду, — зато удвоит время ожидания и число заблокированных горутин.

Проверяется размер от обратного. Отсек регулярно заполнен, а время ответа зависимости не растёт — предел занижен. Заполнен, и время ответа растёт вместе с ним — предел завышен, очередь образуется уже внутри зависимости.

Отдельно стоит следить за суммой. Отсеки на 50, 80 и 30 вызовов дают 160 одновременных операций, и все они должны помещаться в ресурсы процесса: в пул соединений к базе, в лимит памяти пода, в число доступных сокетов. Сумма отсеков, превышающая ёмкость процесса, возвращает исходную проблему на уровень выше.

## Connection pool как bulkhead

Database connection pool — встроенный bulkhead. `MaxConns` ограничивает параллелизм к БД:

```go
poolConfig, err := pgxpool.ParseConfig(dsn)
if err != nil {
    return nil, fmt.Errorf("parse pool config: %w", err)
}

poolConfig.MaxConns = 20 // не более 20 одновременных запросов к базе
poolConfig.MinConns = 5

pool, err := pgxpool.NewWithConfig(ctx, poolConfig)
```

Отдельного параметра «сколько ждать свободное соединение» в `pgxpool` нет — ожидание ограничивается контекстом вызова:

```go
// Ждать соединение не дольше 500 мс: при заполненном пуле
// запрос получит ошибку вместо неопределённого ожидания.
acquireCtx, cancel := context.WithTimeout(ctx, 500*time.Millisecond)
defer cancel()

rows, err := pool.Query(acquireCtx, "SELECT ...")
```

Ограничение здесь одно и на всё: контекст покрывает и ожидание соединения, и выполнение запроса. Разделить их можно только явным `pool.Acquire(acquireCtx)` с последующей работой на своём контексте.

Разные пулы для разных операций дают ту же изоляцию на уровне базы:

```go
// Пул для чтения — больше соединений, запросы идут на реплику
readPool, err := pgxpool.New(ctx, replicaDSN+"?pool_max_conns=50")

// Пул для записи — меньше соединений, запросы идут на основной узел
writePool, err := pgxpool.New(ctx, masterDSN+"?pool_max_conns=10")
```

Смысл разделения не только в адресах. Общий пул означает, что поток тяжёлых аналитических чтений занимает соединения, нужные для записи заказов, — и запись начинает отказывать из-за отчёта. Разные пулы делают эти операции независимыми.

## Изоляция через отдельный пул горутин

Семафор ограничивает число одновременных операций, но выполняются они на горутинах вызывающего. Для тяжёлых операций — генерации документов, обработки изображений, разбора больших файлов — этого недостаточно: такие задачи нагружают процессор и вытесняют обработку обычных запросов даже при соблюдённом пределе параллелизма. Здесь изолируют не счётчик, а исполнителей.

```go
type BulkheadPool struct {
    jobs chan func()
    wg   sync.WaitGroup
}

func NewBulkheadPool(workers, queueSize int) *BulkheadPool {
    p := &BulkheadPool{
        jobs: make(chan func(), queueSize),
    }
    for i := 0; i < workers; i++ {
        p.wg.Add(1)
        go func() {
            defer p.wg.Done()
            for job := range p.jobs {
                job()
            }
        }()
    }
    return p
}

// Ветка default срабатывает немедленно, поэтому case с контекстом
// в этом select был бы недостижим: ожидания здесь нет по замыслу.
func (p *BulkheadPool) Submit(fn func()) error {
    select {
    case p.jobs <- fn:
        return nil
    default:
        return ErrPoolFull
    }
}

func (p *BulkheadPool) Shutdown() {
    close(p.jobs)
    p.wg.Wait()
}

// Использование — тяжёлые PDF/image операции изолированы от бизнес-логики
var pdfPool = NewBulkheadPool(5, 20)   // max 5 параллельных PDF генераций
var reportPool = NewBulkheadPool(3, 10) // max 3 генерации отчётов

func GeneratePDF(ctx context.Context, data ReportData) error {
    // Буфер обязателен: если вызывающий ушёл по таймауту и никто
    // не читает канал, отправка в него заблокирует работника навсегда.
    resultCh := make(chan error, 1)
    err := pdfPool.Submit(func() {
        resultCh <- doGeneratePDF(data)
    })
    if err != nil {
        return fmt.Errorf("pdf pool full: %w", err)
    }
    select {
    case err := <-resultCh:
        return err
    case <-ctx.Done():
        return ctx.Err()
    }
}
```

## Комбинация с circuit breaker

Bulkhead и circuit breaker дополняют друг друга:

```
Запрос → Circuit Breaker → Bulkhead → Downstream Service
           (open?)          (full?)
```

- **Circuit breaker** отказывает быстро, когда зависимость сломана: она отвечает ошибками.
- **Bulkhead** ограничивает ресурсы, когда зависимость замедлилась, но продолжает отвечать.

Разница существенна: замедление без ошибок предохранитель не увидит вовсе — все вызовы формально успешны, просто долгие. Именно этот случай перехватывает переборка.

```go
type ResilientClient struct {
    inner    ServiceClient
    cb       *gobreaker.CircuitBreaker[*Response]
    bulkhead *semaphore.Weighted
}

func (c *ResilientClient) Call(ctx context.Context, req *Request) (*Response, error) {
    // Переборка снаружи предохранителя: заполненность отсека —
    // проблема вызывающей стороны, а не признак отказа зависимости.
    if !c.bulkhead.TryAcquire(1) {
        metrics.BulkheadRejected.Inc()
        return nil, ErrBulkheadFull
    }
    defer c.bulkhead.Release(1)

    resp, err := c.cb.Execute(func() (*Response, error) {
        return c.inner.Call(ctx, req)
    })
    switch {
    case errors.Is(err, gobreaker.ErrOpenState),
        errors.Is(err, gobreaker.ErrTooManyRequests):
        return nil, ErrCircuitOpen
    case err != nil:
        return nil, err
    }
    return resp, nil
}
```

Порядок здесь выбран не произвольно. Если переборку поместить внутрь предохранителя, её отказы попадут в статистику отказов зависимости — и предохранитель разомкнётся из-за собственной перегрузки вызывающего, при полностью исправном получателе. Дальше он будет отклонять запросы всю выдержку, хотя отсек к тому моменту освободится.

Переборка снаружи даёт правильное разделение ответственности: она отвечает за «у нас нет свободных ресурсов на этот вызов», предохранитель — за «зависимость не отвечает». Это разные события, и в метриках они тоже должны различаться.

## Антипаттерны

**Один общий семафор на все зависимости** — это уже не переборка, а ограничение общего параллелизма. Медленный платёжный сервис по-прежнему вытеснит все остальные вызовы, просто на меньшем числе горутин.

**Предел выше реальной ёмкости зависимости** — отсек на тысячу вызовов при ёмкости в пятьдесят не защищает ни от чего: очередь просто образуется внутри зависимости, где её не видно и нечем ограничить.

**Сумма отсеков больше ресурсов процесса** — изоляция между зависимостями есть, но все вместе они исчерпывают пул соединений или память пода.

**Заполненность не измеряется** — постоянно полный отсек означает либо заниженный предел, либо деградацию зависимости, но без метрики оба случая выглядят как «иногда бывают ошибки».

**Долгое ожидание свободного места** — горутины накапливаются в очереди на захват, и эффект получается тот же, что без переборки. Ожидание должно быть заметно короче времени ответа зависимости:

```go
// Плохо: десять секунд ожидания — очередь на захват растёт
// быстрее, чем освобождаются места
acquireCtx, cancel := context.WithTimeout(ctx, 10*time.Second)

// Хорошо: быстрый отказ, если отсек занят
acquireCtx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
```

**Переборка внутри предохранителя** — её отказы засчитываются как отказы зависимости, и предохранитель размыкается из-за перегрузки вызывающего при исправном получателе.

## Interview-ready answer

**1. Какую проблему решает bulkhead?**

- Исходная ситуация — все зависимости конкурируют за общий ресурс: горутины, соединения, слоты пула.
- Механика отказа — одна замедлившаяся зависимость занимает весь ресурс, и перестают работать вызовы, с ней не связанные.
- Решение — отдельный предел на каждую зависимость: её отказ ограничен её же отсеком.
- Название — из судостроения: пробоина в отсеке не топит судно целиком.

**2. Как выбирается размер отсека?**

- Основа — закон Литтла: параллелизм равен пропускной способности, умноженной на время ответа.
- Пример — 200 запросов в секунду при 250 мс ответа дают 50 одновременных вызовов.
- Больший размер не помогает — пропускная способность задана зависимостью, растут только ожидание и число заблокированных горутин.
- Проверка — отсек полон, а время ответа не растёт: предел занижен; растёт вместе с заполненностью: завышен.
- Ограничение сверху — сумма всех отсеков должна помещаться в ресурсы процесса.

**3. Чем bulkhead отличается от circuit breaker?**

- Предохранитель реагирует на ошибки, переборка — на занятость ресурса.
- Ключевой случай для переборки — зависимость отвечает медленно, но без ошибок: предохранитель этого не увидит вовсе.
- Порядок — переборка снаружи, предохранитель внутри.
- Причина порядка — иначе заполненность отсека попадёт в статистику отказов зависимости и разомкнёт цепь к исправному сервису.

**4. Какие ещё механизмы работают как переборка?**

- Пул соединений к базе — `MaxConns` ограничивает параллелизм по своей природе.
- Разные пулы под чтение и запись — тяжёлые отчёты перестают отбирать соединения у записи заказов.
- Отдельный пул горутин — для тяжёлых операций вроде генерации документов, где нужно изолировать не счётчик, а исполнителей.
- В `pgxpool` отдельного таймаута на ожидание соединения нет — его задаёт контекст вызова.
