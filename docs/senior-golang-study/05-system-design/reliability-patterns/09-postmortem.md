# Постмортемы

Постмортем — формальный документ после инцидента. Его цель не "найти виноватого", а извлечь уроки и предотвратить повторение. В зрелых командах постмортем — это жанр, навык, и часть культуры.

Слово взято из медицины (post mortem — "после смерти"). В медицине цель — понять причину смерти, чтобы лечить других. В инженерии — понять причину сбоя, чтобы не допустить его повторения.

## Простая аналогия

Авиакатастрофа. Расследование смотрит чёрный ящик, опрашивает свидетелей, разбирает обломки. Цель — не "наказать пилота", а понять цепочку событий и **изменить процедуры так, чтобы этот же сценарий больше не привёл к катастрофе**.

Авиация — самая безопасная индустрия именно потому что научилась учиться на инцидентах. Каждое расследование становится учебным материалом, рекомендации внедряются по всей отрасли.

Постмортем в инженерии — то же самое для софта. Не ищем виноватого пилота. Спрашиваем: **почему система допустила, чтобы человек ошибся?**

## Зачем нужен постмортем

**1. Институциональная память.**
Через год после инцидента никто не вспомнит детали. Через 3 года уволятся участники. Постмортем — фиксация для будущего: "в 2024 у нас падал Redis из-за такого-то паттерна, исправили так-то".

**2. Предотвращение повторения.**
Без анализа — инцидент повторится. Один и тот же баг каждые полгода — признак отсутствия культуры постмортемов. Постмортем заставляет копнуть до root cause.

**3. Распространение знаний.**
Один инженер увидел проблему. Постмортем читает 50 человек в компании. Каждый запоминает паттерн и не повторит его в своих сервисах.

**4. Выявление системных проблем.**
"Деплой упал из-за человеческой ошибки" — это симптом. **Почему человек смог так ошибиться?** Нет проверки на CI? Нет review? Нет canary? Системный фикс лучше "будем внимательнее".

**5. Доверие команды.**
Открытое обсуждение провалов без обвинений — признак зрелой инженерной культуры. Привлекает сильных инженеров. В компаниях где "всех уволили после инцидента" — никто не хочет ничего предлагать.

**6. Аргумент для бизнеса.**
"Нам нужно 2 недели на reliability work" — слабо. "У нас был инцидент Х, постмортем выявил 5 action items, бюджет работы 2 недели" — это разговор данных.

## Blameless culture

Самый важный принцип постмортема — **никаких обвинений конкретных людей**.

**Плохо:**
> "Иван деплоил без code review и сломал production. Иван должен быть внимательнее."

**Хорошо:**
> "Деплой содержал untested код. Code review не был обязательным для production-веток. Будем требовать review через GitHub branch protection."

Разница — фокус с человека на процесс. Иван будет внимательнее ровно до следующего раза. А branch protection защищает всех инженеров навсегда.

### Почему важно blameless

**1. Иначе люди скрывают информацию.**
Если за инциденты увольняют — никто не сообщает о near-miss'ах. Атмосфера страха, проблемы накапливаются скрыто. Когда наконец взрывается — масштаб катастрофический.

**2. Виноват не тот, кто нажал кнопку.**
Вы наняли этого человека. Вы дали ему доступ к проду. Вы не построили защиту от его ошибки. Виноват кто-то один или система которая допустила?

**3. Лучшие инженеры тоже ошибаются.**
Google, Facebook, Amazon — там работают элитные инженеры. И всё равно у них регулярные инциденты. Не потому что они "плохие", а потому что системы сложные. Если ругать за ошибки — все будут "не делать ничего", а не "делать осторожно".

### Как формулировать без обвинений

**Антипаттерны** (заменить):

| Так не пишут | Лучше |
|---|---|
| "Команда X не настроила X" | "Не было документированного требования настраивать X" |
| "Инженер Y забыл сделать Z" | "Процесс не имел чек-листа на Z" |
| "Ops должны были заметить" | "Алерт на эту ситуацию отсутствовал" |
| "Это была глупая ошибка" | "Этот класс ошибок легко допустить, нужна защита на уровне типов" |

### Etsy "blameless postmortem" подход

Etsy одни из первых формализовали blameless подход. Их правило: "**не спрашивать "почему ты это сделал?", спрашивать "что заставило тебя думать что это правильное действие в тот момент?"**".

Разница тонкая, но важная. Первое подразумевает обвинение. Второе — это про понимание системы. Часто оказывается что "правильное действие" в том момент **действительно было правильным** при имеющейся информации — просто информация была неполной.

## Когда писать постмортем

Не каждый чих требует формального документа. Но и не каждая компания знает свой порог.

**Триггеры для постмортема:**
- ❗ User-visible incident — пользователи видели ошибки или замедление
- ❗ Data loss или corruption (даже частичный)
- ❗ SLO violation
- ❗ Security incident — утечка, взлом, попытка
- ❗ "Near miss" — почти серьёзный инцидент, который чудом не случился
- ❗ Любой инцидент, потребовавший on-call escalation
- ❗ Любой инцидент, потребовавший работы людей дольше 30 минут

**Не пишут постмортем для:**
- Routine deployments
- Minor bugs without user impact
- Issues caught by CI before production

Если сомневаешься — лучше написать. Постмортем на 1 страницу для маленького инцидента — нормально.

### Когда писать

- **В течение 24-48 часов после инцидента** — пока память свежая
- **Ответственный — incident commander** (тот, кто координировал реагирование)
- **Review — внутри 1 недели** — обсуждение в команде
- **Распространение — через неделю** — после ревью разослать

## Структура постмортема

Стандартная структура (по Google SRE Book):

1. **Title** — короткое описание
2. **Status** — Draft / Review / Final
3. **Authors** — кто пишет, кто ревьюит
4. **Date** — дата инцидента, дата документа
5. **Severity** — масштаб (SEV1/2/3/4)
6. **Summary (TL;DR)** — 2-3 предложения для тех, кто не будет читать дальше
7. **Impact** — кто пострадал, как сильно, в цифрах
8. **Timeline** — хронология событий
9. **Root cause** — что именно сломалось и почему
10. **Detection** — как узнали
11. **Response** — что делали
12. **Resolution** — как починили
13. **What went well** — что сработало хорошо
14. **What went poorly** — что нужно улучшить
15. **Action items** — конкретные таски с owner'ом и сроком
16. **Lessons learned** — общие выводы

### Severity levels (общепринятые)

| Severity | Описание | Примеры |
|---|---|---|
| **SEV1** | Критический, всё лежит | API недоступен, БД упала, безопасность |
| **SEV2** | Major, серьёзная деградация | Часть функционала недоступна, медленные ответы |
| **SEV3** | Minor, ограниченное влияние | Падает редкий endpoint, страдает <5% пользователей |
| **SEV4** | Negligible, internal только | Internal tooling сломан, никто не заметил |

## Шаблон постмортема

```markdown
# Постмортем: [короткое описание инцидента]

**Status:** Final
**Severity:** SEV2
**Authors:** @alice (incident commander), @bob (technical lead)
**Date of incident:** 2026-04-15 14:30 UTC
**Date of postmortem:** 2026-04-17

## Summary (TL;DR)

15 апреля с 14:30 до 16:45 UTC API возвращал 5xx ошибки на 30% запросов
из-за исчерпания пула соединений к Postgres. Причина — медленный запрос
в новом feature flag, попавшем в продакшн без нагрузочного тестирования.

## Impact

- **Длительность:** 2 часа 15 минут (14:30 — 16:45 UTC)
- **Affected users:** ~120k запросов вернули 5xx (30% от трафика)
- **SLO impact:** error budget за месяц израсходован на 60%
- **Revenue:** минус ~$12k по оценке маркетинга
- **Reputation:** 8 жалоб в Twitter, 2 в support

## Timeline (UTC)

- **14:00** — Деплой v2.4.0 содержит новый feature flag для recommendations
- **14:30** — Pageduty alert: error rate > 5%
- **14:32** — On-call (alice) подключается. Начинает investigation.
- **14:38** — Замечен резкий рост connection pool exhaustion в DB
- **14:45** — Объявлен SEV2. Подключён tech lead (bob).
- **14:50** — Принято решение откатить v2.4.0
- **15:05** — Rollback завершён, error rate возвращается к нормальным
- **15:10** — Status page обновлён: "issue mitigated"
- **15:30** — Тестируем что rollback стабилен
- **16:45** — Incident closed, status page green

## Root cause

Новая фича в v2.4.0 добавила endpoint `/api/recommendations`, который при
каждом запросе делал запрос к Postgres:

\`\`\`sql
SELECT user_id, content_id FROM views
WHERE user_id IN (SELECT friend_id FROM friends WHERE user_id = $1)
\`\`\`

В тестах с 100 пользователей запрос выполнялся за 50ms. В production у
популярных пользователей friends содержит до 5000 записей, что превращает
запрос в полный скан таблицы views (200M строк) — 8 секунд на запрос.

При нагрузке 200 RPS на этот endpoint, каждый запрос держал соединение
8 секунд → пул в 100 соединений быстро исчерпался → все остальные
запросы (даже простые SELECT'ы) встали в очередь и таймаутили.

## Detection

- Pageduty сработал через **2 минуты** после начала инцидента
- Триггер: error rate > 5% в окне 1 минуты
- Алерт работал корректно, on-call ответил быстро

## Response

- ✅ On-call быстро подключился (2 мин до acknowledge)
- ✅ Точная диагностика (через 8 минут — нашли pool exhaustion)
- ✅ Быстрое решение откатить (rollback за 15 минут)
- ❌ Не было запасного контакта когда alice потеряла связь на 5 минут

## Resolution

- Откатили на v2.3.5
- Connection pool вернулся к норме за 5 минут
- Recommendations endpoint временно отключён

## What went well

- 🟢 Алерт сработал быстро и точно
- 🟢 On-call процедура отработала
- 🟢 Откат через CI был автоматизирован — не было ручных шагов
- 🟢 Хорошая communication в incident channel — все понимали что происходит

## What went poorly

- 🔴 Фича прошла в продакшн без нагрузочного теста
- 🔴 Не было SLO алерта на DB pool utilization (нашли проблему через
  следствие, а не через метрику corner case)
- 🔴 Запрос с N+1-подобной структурой не отловил code review
- 🔴 Single point of contact в on-call rotation (если alice пропадает,
  никто не подхватывает)

## Lessons learned

1. **Нагрузочное тестирование обязательно для запросов к больно
   читаемым таблицам.** Особенно если запрос параметризован user input
   (количество записей зависит от данных пользователя).
2. **Алерт на pool utilization** ловил бы такие проблемы раньше — пул
   мог быть заполнен на 90% в течение 5 минут до полного отказа.
3. **Production-data should be в шаблонах load test'ов.** Тесты на 100
   пользователях не воспроизводят паттерн топа.
4. **Backup on-call** — если primary не отвечает 5 минут, secondary
   автоматически paged.
```

## Анализ причин: 5 Whys

Техника Toyota — спрашивать "почему?" пять раз, чтобы дойти до истинной причины.

**Пример:**

🔴 Сервис упал.

❓ Почему? — БД исчерпала пул соединений.
❓ Почему? — Новый endpoint держал соединения по 8 секунд.
❓ Почему? — Запрос делал full scan таблицы views.
❓ Почему? — Не было индекса по friend_id.
❓ Почему? — В тестах не было реальной production data, проблема не воспроизводилась.

**Root cause:** отсутствие production-realistic нагрузки в тестах.

Action item — не "добавить индекс" (это симптом), а **"настроить нагрузочные тесты с production-like данными для каждого нового endpoint'а"**.

5 Whys — не догма. Иногда 3 достаточно, иногда нужно 7. Главное — не останавливаться на первом ответе.

### Антипаттерн: "human error" как root cause

Если ответ на "почему?" — "потому что Иван ошибся", это **не root cause**. Спрашивай дальше:

❓ Почему ошибка Ивана попала в продакшн?
- Не было review?
- Не было автоматической проверки на CI?
- Документация была неточной?
- Алерт не сработал?

Любая система, в которой человеческая ошибка приводит к падению production — плохая система. Хорошая система **проектируется с учётом того, что люди ошибаются**.

## Action items: что чинить

Качество постмортема измеряется качеством action items.

**Хороший action item:**
- ✅ **Конкретный** — "добавить алерт на pool utilization > 80%", не "улучшить мониторинг"
- ✅ **С owner'ом** — есть конкретный человек, не "команда"
- ✅ **С deadline** — дата, иначе никогда не сделается
- ✅ **С приоритетом** — P1/P2/P3, иначе всё одновременно "важно"
- ✅ **Tracked** — заведён в jira/линейку, виден на дашборде

**Плохие action items:**
- ❌ "Будем внимательнее" — не действие
- ❌ "Улучшить процесс review" — слишком общо
- ❌ "Команда DevOps добавит мониторинг" — никто конкретно не отвечает
- ❌ "В будущем" — никогда
- ❌ "Добавить документацию" — без конкретики о том, что и где

### Иерархия action items по эффективности

От самых эффективных к слабым:

1. **Eliminate** — устранить класс проблемы целиком
   - "Удалить эту фичу совсем" / "Использовать другую технологию"
2. **Engineering controls** — автоматическая защита
   - "Pre-commit hook блокирует этот паттерн"
   - "CI fail если SQL-запрос делает full scan"
3. **Detection** — заметить проблему раньше
   - "Алерт срабатывает за 30 минут до катастрофы"
4. **Documentation / training** — научить людей
   - "Добавить раздел в onboarding"
5. **Procedural** — изменение процесса
   - "Обязательное review для production deployment"

Слабые AI (документация, тренинги) — последнее, что делать. Если **только** они в результате постмортема — root cause не доделан.

### Tracking action items

Action items без отслеживания — мёртвые. Команды используют:

- **Jira** с тегом `postmortem-AI`
- **Linear** с label `incident`
- Регулярный (например, раз в 2 недели) review статуса AI постмортемов

Если AI висят полгода — это сигнал что они не приоритет, и значит постмортем культура слабая.

## Хорошие примеры из индустрии

Многие компании публикуют публичные постмортемы. Учиться можно прямо на них.

**GitHub** — `https://github.com/blog/category/incident`. Регулярные подробные постмортемы каждого major инцидента. Особенно знаменитый — 24-hour incident в октябре 2018 (split-brain в MySQL replication).

**AWS** — публикуют post-event summaries для major service disruptions. Пример — известный S3 outage 2017 (опечатка в команде дебага → удалена metadata системы → каскад).

**Cloudflare** — публикуют детальные технические разборы с timeline и root cause. Очень читаемо и поучительно.

**Stripe** — публичные incident reports на `https://status.stripe.com/incidents`.

**Gitlab** — публиковали полную хронологию знаменитого database deletion incident в 2017 (инженер удалил production-БД руками, бэкапы не работали).

**Datadog** — серия постмортемов про инциденты с их API.

Запомни паттерн: серьёзные компании **публикуют постмортемы публично** не потому что им не страшно, а потому что:
1. Прозрачность — конкурентное преимущество
2. Доверие пользователей растёт ("они умеют разбирать проблемы")
3. Распространение знаний в индустрии

## Частые ошибки

**1. Blame в постмортеме.**
Прямой или скрытый. Любое упоминание "должны были" про конкретного человека — blame. Замени на "процесс не предусматривал".

**2. Симптом вместо root cause.**
"Сервис упал → перезапустили → починилось" — это resolution, не root cause. Почему упал? Что в коде было не так? Что в системе допустило это?

**3. Пишется через 3 недели после инцидента.**
Память подводит. Хронология теряется. Постмортем — горячий, в 24-48 часов после.

**4. Постмортем без действий.**
"Урок — мы должны быть внимательнее". Окей, и? Без action items — это эссе, не постмортем.

**5. Action items без deadline / owner.**
"Команда улучшит мониторинг" — никогда не случится. Конкретный человек, конкретная дата.

**6. Слишком длинный.**
Постмортем на 30 страниц никто не прочитает. Цель — 2-5 страниц. Tech detail — в supporting data ссылки.

**7. Только техническая часть.**
Хороший постмортем включает и процессы, и коммуникацию, и timeline. "Почему mitigation занял 30 минут — потому что не нашли on-call" — важная часть.

**8. Не делается review с командой.**
Постмортем — collaborative document. Без обсуждения с участниками — упускаются перспективы. Минимум одна встреча review.

**9. Action items не отслеживаются.**
Через 3 месяца никто не помнит про них. Регулярный review — обязателен.

**10. "Same bug different day".**
Если повторяется один и тот же класс инцидентов — постмортемы пишутся, action items не закрываются, или закрываются формально без реального impact'а. Сигнал что культура постмортемов сломана.

## Чек-лист хорошего постмортема

**Содержание:**
- [ ] TL;DR в первых 2-3 предложениях
- [ ] Конкретные числа в impact (длительность, кол-во пользователей, $$$ или error rate)
- [ ] Timeline с реальным timestamps
- [ ] Root cause — добрался до **системной причины**, не остановился на симптоме
- [ ] What went well — даже в плохом инциденте есть что хвалить
- [ ] What went poorly — честно, без замазывания

**Тон:**
- [ ] Никаких имён в негативном контексте
- [ ] Никаких "должны были" про людей
- [ ] Фокус на процессах и системах, не на индивидуальных решениях

**Action items:**
- [ ] Каждый — конкретный
- [ ] Каждый — с owner'ом
- [ ] Каждый — с deadline
- [ ] Каждый — с приоритетом
- [ ] Tracked где-то (Jira/Linear)

**Качество анализа:**
- [ ] Применён 5 Whys или эквивалент
- [ ] Action items нацелены на eliminate/engineering, не только на documentation
- [ ] Учли что-то про detection (как заметить раньше)
- [ ] Учли что-то про response (что улучшить в реагировании)

**Процесс:**
- [ ] Написан в течение 48 часов
- [ ] Review с участниками инцидента
- [ ] Распространён в команде
- [ ] (Опционально) опубликован публично если это уместно
