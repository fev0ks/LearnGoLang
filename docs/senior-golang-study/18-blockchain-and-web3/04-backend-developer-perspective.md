Для Go-разработчика blockchain-проект часто выглядит не как разработка нового протокола, а как интеграция с ещё одной внешней распределённой системой. Backend читает состояние через API узла, отправляет транзакции, отслеживает их результат и преобразует события сети в удобную продуктовую модель.

---

## Где находится обычный backend

Smart contracts плохо подходят для полнотекстового поиска, приватных пользовательских данных, отправки email и вызова внешних API. Эти задачи остаются в обычной инфраструктуре:

```text
Клиенты
   |
   v
Go API -------> PostgreSQL / Redis
   |                    ^
   | чтение и запись    | проекция событий
   v                    |
RPC-провайдер <---- Blockchain ----> Indexer
```

Для продукта blockchain является одним из источников истины, но не обязательно единственным хранилищем. Критичное правило владения может находиться в smart contract, а профиль пользователя и поисковый индекс — в PostgreSQL.

## Какие задачи решает Go-сервис

Backend-разработчик может отвечать за несколько ролей:

- **API для продукта** — объединяет blockchain-данные с обычной базой и внешними сервисами;
- **transaction service** — формирует, отправляет и отслеживает транзакции;
- **indexer** — читает блоки и события контрактов, затем строит удобную модель для запросов;
- **wallet service** — управляет адресами и подписанием, если продукт является custodial-системой;
- **reconciliation worker** — сверяет локальное состояние с принятой историей сети;
- **notification service** — сообщает пользователю о новых статусах операции.

Go подходит для таких сервисов по тем же причинам, что и для другого backend: сетевые клиенты, конкурентная обработка, фоновые worker и предсказуемое развёртывание. Знание Go не заменяет понимание модели конкретной blockchain-сети.

## Чтение данных из сети

Приложение подключается к собственному узлу или внешнему RPC-провайдеру. Через RPC оно может запросить:

- текущий баланс account;
- данные блока или транзакции;
- состояние smart contract;
- журналы событий контракта;
- оценку параметров будущей транзакции.

Чтение из одного RPC-узла не всегда является окончательной истиной. Узел может отставать, быть временно недоступным или показывать верхушку цепочки, которая ещё изменится. Для критичного решения backend учитывает номер блока, свежесть данных и требуемую финальность.

Нельзя бездумно делать RPC-запрос на каждое поле каждой web-страницы. Для быстрых фильтров и списков события обычно индексируют в обычную базу, а критичные данные при необходимости перепроверяют через сеть.

## Отправка транзакций

Есть две основные модели.

**Пользователь подписывает транзакцию.** Wallet находится на стороне пользователя. Backend подготавливает параметры или возвращает данные для вызова, но не получает private key.

**Сервис подписывает транзакцию.** Backend управляет ключом и действует от имени продукта или пользователя. Это custodial-модель: сервис получает больше контроля и одновременно принимает на себя ответственность за защиту ключей, лимиты и аудит операций.

Операцию удобно моделировать как асинхронный процесс:

```text
created -> signed -> submitted -> included -> confirmed
               \          \          \
                cancelled  rejected   reverted
```

Названия состояний зависят от продукта, но принцип остаётся: HTTP-ответ после отправки не равен окончательному результату в blockchain.

Для повторной попытки нельзя просто ещё раз создать и подписать новую транзакцию. Повтор может привести к двум экономическим операциям. Сначала сервис проверяет судьбу предыдущей транзакции и применяет правила идемпотентности конкретной сети и бизнес-процесса.

## Индексирование событий

Smart contract может публиковать события о выполненных действиях. Indexer последовательно читает блоки, извлекает интересующие события и обновляет проекцию в PostgreSQL или другом хранилище.

```text
Blockchain event
    |
    v
Indexer -> deduplication -> PostgreSQL -> Product API
```

Локальная запись является производной от blockchain. Поэтому индексатор должен уметь:

- продолжить работу после перезапуска;
- повторно обработать диапазон блоков без дублей;
- хранить позицию чтения;
- учитывать возможное изменение недавней истории;
- полностью перестроить проекцию из исходных событий.

По модели это похоже на обработку событий из брокера: важны идемпотентность, checkpoint, повторная доставка и восстановление состояния. Отличие в том, что источником служит цепочка блоков, а недавняя принятая последовательность иногда может измениться.

## Основные риски интеграции

- **Reorg.** Недавний блок может быть заменён другой принятой веткой, поэтому его события потребуется отменить или пересчитать.
- **Повторная обработка.** Worker может увидеть один event несколько раз; локальная запись должна быть идемпотентной.
- **Потеря ключа.** Для сервисной подписи компрометация private key означает возможность выполнять операции от имени сервиса.
- **Конкурентные транзакции.** Несколько worker могут конфликтовать при использовании одного account и его последовательности операций.
- **RPC-зависимость.** Один провайдер создаёт точку отказа, ограничивает запросы и может отдавать отстающие данные.
- **Неверная сеть.** Одинаковый адрес в разных сетях не означает одно и то же состояние; запросы и подписи учитывают идентификатор сети.
- **Комиссия.** Стоимость выполнения меняется, поэтому операция может зависнуть или стать экономически невыгодной.
- **Разные статусы.** Доставка транзакции, включение в блок и успешное выполнение smart contract — разные результаты.

Эти риски не требуют сразу изучать внутреннее устройство протокола. Достаточно не переносить на blockchain предположение обычного синхронного API: «получил 200 OK — значит бизнес-операция завершена».

## Что достаточно знать на первом этапе

Для вводного уровня backend-разработчику достаточно уметь объяснить:

1. как wallet подписывает операцию и почему private key нельзя передавать сервисам;
2. как RPC связывает приложение с узлом сети;
3. почему отправка транзакции является началом, а не концом процесса;
4. зачем ждать подтверждение или финальность;
5. зачем события индексируют в обычную базу;
6. почему reorg и повторная обработка требуют идемпотентности;
7. какие части приложения находятся on-chain, а какие остаются обычным backend.

Следующим практическим шагом может быть небольшой read-only сервис: получить по RPC номер блока, найти транзакцию и сохранить выбранные события в PostgreSQL. Подписание реальных финансовых операций лучше изучать после модели ключей, тестовой сети и правил конкретной платформы.

## Interview-ready answer

**1. Что делает backend в Web3-приложении?**

- Интеграция — читает blockchain через RPC и объединяет данные с обычными сервисами.
- Обработка — отправляет и отслеживает транзакции как асинхронные операции.
- Проекции — индексирует события в базу для быстрых запросов, поиска и уведомлений.

**2. Почему нельзя считать транзакцию успешной сразу после отправки?**

- Доставка — RPC-узел мог только принять запрос на распространение.
- Выполнение — транзакция ещё должна попасть в блок и завершиться без отклонения со стороны smart contract.
- Финальность — приложение ждёт гарантию сети, достаточную для риска конкретной операции.

**3. Какие ошибки должен учитывать indexer?**

- Повторы — один event может быть обработан несколько раз, поэтому запись делают идемпотентной.
- Перезапуск — позиция чтения хранится отдельно и позволяет продолжить обработку.
- Reorg — изменения недавней истории требуют отменить или перестроить производные записи.
