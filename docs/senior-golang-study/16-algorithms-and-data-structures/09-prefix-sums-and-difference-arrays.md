Префиксная сумма переносит работу из каждого запроса в однократную
предобработку. Разностный массив делает зеркальную операцию: дешёво записывает
пакет диапазонных обновлений, а итоговые значения восстанавливает одним
проходом. Оба приёма особенно полезны, когда данные обрабатываются снимком, а не
меняются между запросами.

---

## Ментальная модель

Пусть нужно много раз считать сумму элементов на непрерывном отрезке. Повторный
цикл по каждому отрезку стоит O(длина отрезка), хотя большая часть сложений уже
выполнялась для предыдущих запросов.

Префикс хранит сумму всего, что расположено левее границы:

```text
nums:    [ 3, -2,  5,  1 ]
index:      0   1   2   3
prefix:  [ 0,  3,  1,  6,  7 ]
boundary:   0   1   2   3   4
```

`prefix[i]` равен сумме `nums[0:i]`. Поэтому сумма полуинтервала `[left, right)`
получается вычитанием двух уже накопленных частей:

```text
sum(nums[1:3]) = prefix[3] - prefix[1]
               = 6 - 3
               = 3

проверка: -2 + 5 = 3
```

Дополнительный ноль в начале убирает отдельную ветку для `left == 0` и позволяет
одинаково обрабатывать пустой отрезок `[i, i)`.

## Префиксная сумма в одном измерении

```go
// BuildPrefix строит prefix, где prefix[i] = сумма nums[0:i].
func BuildPrefix(nums []int) []int64 {
    prefix := make([]int64, len(nums)+1)
    for i, value := range nums {
        prefix[i+1] = prefix[i] + int64(value)
    }
    return prefix
}

// RangeSum возвращает сумму полуинтервала [left, right).
func RangeSum(prefix []int64, left, right int) (int64, bool) {
    n := len(prefix) - 1
    if n < 0 || left < 0 || left > right || right > n {
        return 0, false
    }
    return prefix[right] - prefix[left], true
}
```

Построение занимает O(n) времени и O(n) памяти. После него один запрос работает
за O(1). Тип `int64` уменьшает риск переполнения по сравнению с `int`, но не
устраняет его для неограниченного входа: допустимый диапазон суммы остаётся
частью контракта.

Префикс эффективен при большом числе запросов. Если сумму нужно получить один
раз, обычный проход O(n) проще и не выделяет дополнительный срез.

## Количество подмассивов с заданной суммой

Префикс помогает не только отвечать на готовые диапазонные запросы. Пусть для
текущей правой границы накоплена сумма `current`. Подмассив имеет сумму `target`,
если раньше встречался префикс `current - target`:

```text
current - previous = target
previous = current - target
```

Хеш-таблица хранит, сколько раз встречалась каждая предыдущая сумма.

```go
// CountSubarraysWithSum считает непрерывные подмассивы с суммой target.
func CountSubarraysWithSum(nums []int, target int64) int64 {
    frequency := map[int64]int64{
        0: 1, // пустой префикс перед первым элементом
    }

    var current int64
    var result int64

    for _, value := range nums {
        current += int64(value)
        result += frequency[current-target]
        frequency[current]++
    }

    return result
}
```

Порядок двух последних операций важен. Сначала считаются только более ранние
префиксы, затем текущий добавляется в таблицу. Если сделать наоборот, при
`target == 0` алгоритм начнёт учитывать пустой подмассив после текущей границы.

Ожидаемое время — O(n), память — O(n). Слово «ожидаемое» относится к операциям
хеш-таблицы: язык Go не гарантирует O(1) в худшем случае для `map`.

В отличие от скользящего окна, решение корректно при отрицательных числах.
Именно отрицательные значения ломают монотонность суммы окна, но не равенство
между двумя префиксами.

## Двумерная префиксная сумма

Для матрицы `prefix[row][col]` хранит сумму прямоугольника от `(0, 0)` до
границы `(row, col)`, не включая саму границу. При добавлении клетки сверху и
слева общая верхняя левая область учитывается дважды, поэтому её нужно вычесть:

```text
prefix[r+1][c+1] = value
                 + prefix[r][c+1]
                 + prefix[r+1][c]
                 - prefix[r][c]
```

```go
// BuildPrefix2D строит префикс для прямоугольной матрицы.
func BuildPrefix2D(matrix [][]int) ([][]int64, bool) {
    rows := len(matrix)
    cols := 0
    if rows > 0 {
        cols = len(matrix[0])
    }

    for _, row := range matrix {
        if len(row) != cols {
            return nil, false
        }
    }

    prefix := make([][]int64, rows+1)
    for r := range prefix {
        prefix[r] = make([]int64, cols+1)
    }

    for r := 0; r < rows; r++ {
        for c := 0; c < cols; c++ {
            prefix[r+1][c+1] = int64(matrix[r][c]) +
                prefix[r][c+1] +
                prefix[r+1][c] -
                prefix[r][c]
        }
    }

    return prefix, true
}

// RectangleSum возвращает сумму [top, bottom) × [left, right).
func RectangleSum(prefix [][]int64, top, left, bottom, right int) (int64, bool) {
    if len(prefix) == 0 || len(prefix[0]) == 0 {
        return 0, false
    }

    rows := len(prefix) - 1
    cols := len(prefix[0]) - 1
    if top < 0 || top > bottom || bottom > rows ||
        left < 0 || left > right || right > cols {
        return 0, false
    }

    for _, row := range prefix {
        if len(row) != cols+1 {
            return 0, false
        }
    }

    sum := prefix[bottom][right]
    sum -= prefix[top][right]
    sum -= prefix[bottom][left]
    sum += prefix[top][left]
    return sum, true
}
```

Построение требует O(rows · cols) времени и памяти, запрос — O(1). Последнее
сложение возвращает область, которую два предыдущих вычитания удалили дважды.

## Разностный массив

Разностный массив нужен для другой формы нагрузки: есть исходный массив и много
операций «прибавить `delta` ко всем индексам `[left, right)`», а прочитать итог
достаточно после всех обновлений.

Одна операция меняет только две границы:

```text
diff[left]  += delta
diff[right] -= delta
```

Префиксная сумма по `diff` включает изменение на `left` и отменяет его на
`right`.

```go
type RangeAdd struct {
    Left  int
    Right int // не включается
    Delta int64
}

func ApplyRangeAdds(n int, updates []RangeAdd) ([]int64, bool) {
    if n < 0 {
        return nil, false
    }
    for _, update := range updates {
        if update.Left < 0 || update.Left > update.Right || update.Right > n {
            return nil, false
        }
    }

    diff := make([]int64, n+1)
    for _, update := range updates {
        diff[update.Left] += update.Delta
        diff[update.Right] -= update.Delta
    }

    result := make([]int64, n)
    var current int64
    for i := 0; i < n; i++ {
        current += diff[i]
        result[i] = current
    }
    return result, true
}
```

Для `n = 5` и обновлений `[1, 4) += 3`, `[2, 5) -= 1` результат равен:

```text
index:   0  1  2  3   4
result: [0, 3, 2, 2, -1]
```

`q` обновлений и восстановление стоят O(q + n), память — O(n). Прямое
изменение каждого диапазона могло бы потребовать O(q · n) в худшем случае.

## Что выбирать

| Нагрузка | Структура | Построение | Запрос | Обновление |
| --- | --- | --- | --- | --- |
| Статический массив, суммы диапазонов | Префиксная сумма | O(n) | O(1) | требуется перестроение |
| Много offline range-add, один финальный снимок | Разностный массив | O(n + q) вместе | чтение снимка O(1) | O(1) на запись границ |
| Динамические суммы и изменения элементов | Fenwick Tree | O(n) | O(log n) | O(log n) |
| Динамические агрегаты общего вида | Segment Tree | O(n) | O(log n) | O(log n) |
| Монотонное окно с движущимися границами | Скользящее окно | нет отдельного | O(n) за проход | состояние окна |

Fenwick Tree и Segment Tree платят логарифмом за возможность чередовать
запросы с обновлениями. Префикс и разностный массив выигрывают, пока фазы
«записать» и «прочитать» разделены.

## Практические ограничения

- **Снимок данных.** Префикс соответствует конкретной версии входного массива.
  Изменение исходных значений не обновляет уже построенный префикс.
- **Память.** Двумерный префикс удваивает порядок хранимых данных. Матрица
  `10 000 × 10 000` из `int64` требует около 800 MB только на значения, без
  заголовков строк.
- **Переполнение.** Для денежных значений сначала фиксируют минимальную единицу
  и максимальную сумму. `int64` не заменяет проверку диапазона.
- **Параллельное чтение.** Полностью построенный и больше не изменяемый префикс
  удобно публиковать как immutable snapshot. Одновременная запись в те же срезы
  без синхронизации остаётся data race.
- **Временные интервалы.** Для метрик по времени сначала определяют, что означает
  индекс: секунду, минуту или bucket. Ошибка в единице измерения не исправляется
  правильной формулой префикса.

## Типичные ошибки

- Создавать `prefix` длиной `n`, а затем добавлять ветку для диапазонов от нуля.
- Смешивать закрытый `[left, right]` и полуоткрытый `[left, right)` интервалы.
- Забывать `frequency[0] = 1` при подсчёте подмассивов.
- Добавлять текущий префикс в `frequency` раньше поиска `current-target`.
- В двумерной формуле дважды вычитать пересечение и не добавить его обратно.
- Использовать статический префикс при чередующихся обновлениях и запросах.
- Хранить сумму в `int`, не проверив максимальный размер входа и значения.

## Interview-ready answer

**1. Зачем нужен дополнительный ноль в начале префиксной суммы?**

- Инвариант — `prefix[i]` хранит сумму полуинтервала `nums[0:i]`.
- Формула — любой диапазон `[left, right)` равен `prefix[right] - prefix[left]`.
- Граница — диапазоны от нулевого индекса и пустые диапазоны не требуют отдельных веток.

**2. Почему префиксная сумма отвечает на запрос диапазона за O(1)?**

- Предобработка — все накопительные сложения выполняются один раз за O(n).
- Запрос — сумма диапазона получается одним вычитанием двух границ.
- Цена — требуется O(n) дополнительной памяти, а изменение входа делает снимок устаревшим.

**3. Как посчитать подмассивы с суммой target при отрицательных числах?**

- Равенство — нужен предыдущий префикс `current-target`.
- Структура — хеш-таблица хранит число появлений каждой предыдущей суммы.
- Порядок — сначала используются предыдущие суммы, затем записывается текущая.
- Сложность — ожидаемое O(n) времени и O(n) памяти.

**4. Чем разностный массив отличается от префиксной суммы?**

- Префикс — ускоряет чтение диапазонов после построения.
- Разность — ускоряет пакетные обновления диапазонов до построения финального снимка.
- Ограничение — оба приёма неудобны, если запросы и обновления произвольно чередуются.

**5. Когда вместо префикса нужен Fenwick Tree или Segment Tree?**

- Сигнал — между запросами меняются отдельные элементы или диапазоны.
- Компромисс — запрос и обновление становятся O(log n) вместо O(1), зато полное перестроение не нужно.
- Выбор — Fenwick Tree проще для обратимых префиксных агрегатов, Segment Tree поддерживает более общие операции.
