Этот документ фиксирует стиль статей в `docs/senior-golang-study`. Его задача — сохранять одинаковую глубину и понятность материалов между разными авторами и рабочими сессиями.

Главный принцип: статья должна быть понятна backend-разработчику, который ещё не знает внутреннее устройство темы, но после чтения должна давать глубину, достаточную для senior-собеседования и практической работы.

## 1. Рефакторинг не означает сокращение

При рефакторинге нужно улучшать порядок и объяснение материала, а не автоматически уменьшать его объём.

- Не удалять полезные подробности только ради короткого текста.
- Не удалять работающие примеры, которые помогают увидеть механику.
- Если раздел перегружает основной flow, его можно перенести под `<details>`, но не выбрасывать.
- Если исходный пример неточен, исправить его и объяснить изменение.
- Перед удалением материала проверить, не отвечает ли он на естественный вопрос читателя: «почему?», «откуда это число?», «что произойдёт на практике?».

Хороший рефакторинг делает путь чтения яснее, сохраняя полезную глубину.

## 2. Порядок объяснения

Сложную тему раскрывать слоями:

1. Задача: какую проблему решаем.
2. Простая ментальная модель без лишних implementation details.
3. Основные сущности и различия между ними.
4. Пошаговая механика на конкретном примере.
5. Почему механизм устроен именно так.
6. Trade-offs и альтернативы.
7. Практические последствия для latency, memory, GC, concurrency и эксплуатации.
8. Типичные ошибки.
9. Короткий нумерованный `Interview-ready answer`.

Не начинать объяснение сразу с internal structs, формул или длинного перечня терминов. Сначала читатель должен понять, какую роль они выполняют.

### Оглавление идёт перед введением

Если в статье есть `## Содержание`, оно всегда идёт сразу после заголовка
первого уровня, до вводного абзаца и любого другого текста:

```md
# Название статьи

## Содержание

- [Первый раздел](#первый-раздел)

Короткое введение в статью.
```

Так оглавление находится в одном ожидаемом месте и не прячет расположенный
перед ним текст. Между `# Заголовком` и `## Содержание` оставлять только пустую
строку.

## 3. Глубина и понятность

### Не пропускать промежуточные шаги

Если в тексте появляется вычисление, последовательность переходов или изменение состояния, нужно показать происхождение каждого шага.

Плохо:

```text
probe sequence: 1 -> 2 -> 0 -> 3
```

Хорошо:

```text
start = 1

следующие смещения: +1, +3, +6

(1 + 1) mod 4 = 2
(1 + 3) mod 4 = 0
(1 + 6) mod 4 = 3

поэтому: 1 -> 2 -> 0 -> 3
```

Читатель не должен угадывать, откуда появляется число, индекс, стрелка или новый объект на схеме.

### Объяснять «почему», а не только «что»

После описания механизма отвечать на вопросы:

- почему выбран такой подход;
- какую проблему он решает;
- чем за это приходится платить;
- в каком workload преимущество исчезает;
- какая альтернатива проще или надёжнее.

Фраза «используется quadratic probing» недостаточна без объяснения, чем она отличается от linear probing и зачем это влияет на clustering.

### Различать похожие сущности

Если рядом встречаются похожие понятия, явно сопоставить их в тексте или таблице. Например:

- slot и bucket;
- group и table;
- container и virtual machine;
- liveness probe и readiness probe;
- safe publication pointer и потокобезопасность объекта за pointer.

Не использовать похожие термины как взаимозаменяемые, если в реализации у них разные роли.

## 4. Терминология и язык

- Основной язык — русский.
- Устоявшиеся индустриальные термины можно оставлять на английском.
- При первом появлении неочевидного термина дать русское объяснение: `overflow chain` — цепочка записей с одинаковым hash.
- Если есть понятный русский вариант, использовать его вместе с английским термином или вместо него.
- Не вводить термин раньше, чем читателю становится понятна его роль.
- Не перегружать каждое предложение смесью русского и английского, если это не повышает точность.

### Русские слова по умолчанию

Если у обычного технического понятия есть ясный и привычный русский вариант, в основном тексте использовать его. Английский язык не должен применяться только потому, что исходная документация написана на нём.

Плохо:

```text
Container запускает host process с shared kernel и отдельным filesystem view.
Application memory при этом остаётся частью workload footprint.
```

Хорошо:

```text
Контейнер запускает процесс хоста и использует общее ядро, но получает
отдельное представление файловой системы.

Память приложения при этом остаётся частью потребления рабочей нагрузки.
```

Обычные слова переводить последовательно:

| Не использовать без причины | Предпочтительный вариант |
| --- | --- |
| `process` | процесс |
| `kernel` | ядро |
| `filesystem` | файловая система |
| `application` | приложение |
| `memory` | память |
| `host` | хост |
| `guest OS` | гостевая ОС |
| `workload` | рабочая нагрузка |
| `boundary` | граница |
| `image` | образ |
| `layer` | слой |
| `storage` | хранилище |
| `permissions` | права |
| `configuration` | конфигурация или настройки |
| `performance` | производительность |

Если английское название нужно для поиска документации, дать его один раз при первом появлении, а дальше использовать русский вариант:

```text
Пространство имён (`namespace`) изолирует представление ресурса.
Дальше процесс работает внутри этого пространства имён.

Копирование при записи (`copy-on-write`, CoW) откладывает копирование файла
до первой попытки его изменить.
```

Оставлять английский без перевода уместно, когда это:

- имя API, команды, флага или поля конфигурации: `docker run`, `LoadOrStore`, `--memory`;
- официальное имя компонента или продукта: Docker Engine, containerd, gVisor;
- устоявшийся термин, русский перевод которого затрудняет поиск или звучит искусственно: `seccomp`, `cgroup`, `runtime`;
- идентификатор из source code или protocol specification.

Даже в этих случаях при первом появлении нужно объяснить роль термина по-русски. Если в одном абзаце английских существительных становится больше, чем русских, абзац нужно переписать.

Писать преимущественно в настоящем времени:

```text
Runtime выбирает следующий slot.
Writer создаёт новую table.
В Go 1.23 sync.Map использует read и dirty.
```

Историческую реализацию также удобнее описывать как модель конкретной версии, а не как длинный рассказ в прошедшем времени.

### Без апелляций к частоте вопроса

Обороты «частый вопрос», «это любят спрашивать», «типичный вопрос», «классика
собеседований» ничего не сообщают о предмете: они лишь обещают, что дальше будет
что-то важное. Абзац начинается с самого утверждения, а не с рамки вокруг него.

Плохо:

```text
Частый вопрос: если часть кадра не доехала, запрашивает ли HTTP/2 её заново.
Нет — механизма «перезапросить кадр» не существует.
```

Хорошо:

```text
Механизма «перезапросить кадр» в HTTP/2 не существует, и знать о потере
протоколу не нужно.
```

Если указание на собеседование действительно несёт информацию — например,
объясняет, какой навык проверяет задача, — оно оформляется как утверждение с
содержанием, а не как вводная фраза:

```text
Плохо:  Классический вопрос про 401 и 403.
Хорошо: Коды 401 и 403 различают не ради чистоты: получив 401, клиент идёт
        обновлять токен, а получив 403 — не идёт.
```

Исключения, где такая формулировка уместна:

- блок `Interview-ready answer` — там вопрос и есть структура материала;
- отдельный раздел, который разбирает, *почему* тему спрашивают и что она
  проверяет (например, «Почему именно это спрашивают» в разборе задач).

### Выделения в тексте

Жирный шрифт — это разметка структуры, а не способ нажать на слово. Допустимы два случая:

- **метка в начале абзаца или пункта**, работающая как мини-заголовок: `**Тик планировщика** (p.schedtick) — не единица времени, а счётчик`;
- **термин при первом появлении**, когда он тут же объясняется.

Выделять слова посреди фразы ради акцента не нужно. Если без выделения смысл теряется, это признак того, что фразу надо переписать: важное ставится в конец предложения или выражается порядком слов, а не начертанием.

Плохо:

```text
Параллелизм кода на Go ограничен **не числом потоков, а числом P**.
Проверка выполняется **до** выделения памяти.
Таблица содержит **типичные вызовы Linux**, а не контракт функций.
```

Хорошо:

```text
Параллелизм кода на Go ограничен числом P, а не числом потоков.
Проверка выполняется раньше выделения памяти.
В таблице приведены типичные вызовы Linux, а не контракт функций.
```

Капс для акцента (`НЕблокирующий`, `СОЗРЕВШИЕ`) не использовать вообще: это то же выделение, только громче. В ячейках таблиц выделения обычно лишние — ячейка короткая и читается целиком.

## 5. Примеры

Примеры являются частью объяснения, а не необязательным украшением.

- Сохранять полезные исходные примеры при рефакторинге.
- Добавлять короткий пример после сложной абстрактной механики.
- Располагать пример рядом с разделом, который он объясняет.
- Показывать состояние до операции, саму операцию и состояние после неё.
- Для concurrency по возможности показывать, где именно могут вмешаться другие goroutines.
- Код должен объяснять одну идею и не притворяться production-ready реализацией.
- Указывать важные ограничения примера.

Длинные дополнительные примеры можно помещать под `<details>`:

```md
<details>
<summary>Практический пример</summary>

Содержимое примера.

</details>
```

При этом центральный пример, без которого непонятен основной механизм, не нужно прятать под `<details>`.

## 6. Схемы и таблицы

Использовать визуальное представление, когда оно действительно сокращает путь к пониманию:

- таблица — для точного сравнения ролей и trade-offs;
- Mermaid — для request flow, lifecycle и связей компонентов;
- ASCII-схема — для layout памяти, hash path, очереди или небольшого пошагового изменения;
- последовательность `до -> операция -> после` — для изменения состояния.

У каждой стрелки и коробки должна быть понятная роль. Не добавлять на схему объект, происхождение которого не объясняется в тексте.

### Разделители между разделами

Перед каждым `## Заголовком`, кроме первого, ставить горизонтальную линию:

```text
Последний абзац предыдущего раздела.

---

## Следующий раздел
```

Перед `###` разделители не ставить: в файлах с частыми подзаголовками они превращают страницу в решето.

Это оформление легко теряется при переписывании файла: новый текст пишется без разделителей, и расхождение замечается не сразу. Поэтому при рефакторинге его нужно проверять отдельно.

## 7. Версии и implementation details

Для runtime, стандартной библиотеки, баз данных, Kubernetes и других изменяющихся технологий:

- сверяться с official documentation или source code;
- явно указывать версию, если устройство зависит от неё;
- отделять public contract от current implementation detail;
- не объяснять современную реализацию через устаревшую архитектуру;
- историческую модель сохранять, если она помогает читать старые статьи или отвечать на interview-вопросы;
- не превращать неподтверждённую деталь реализации в гарантию API.

Полезная формулировка:

```text
Public contract гарантирует ...
В текущей реализации Go 1.26 это достигается через ...
```

## 8. Практический смысл

После внутренней механики связывать её с наблюдаемым поведением:

- где появляется contention;
- какие операции создают allocations;
- что удерживает память;
- как механизм влияет на GC;
- где возможны latency spikes;
- как увидеть проблему через benchmark, trace, metrics или profile;
- когда более простое решение оказывается лучше.

Не утверждать, что одна технология «быстрее» или «лучше», без access pattern и цены выбора.

## 9. Interview-ready answer

Для большой interview-темы в конце добавлять блок:

```md
## Interview-ready answer

**1. Первый вопрос?**

- Первый аспект — короткий ответ.
- Второй аспект — короткий ответ.

**2. Второй вопрос?**

- Первый аспект — короткий ответ.
- Второй аспект — короткий ответ.
```

Правила:

- вопросы обязательно нумеровать;
- сохранять нумерацию при рефакторинге;
- ответ оформлять **списком**, а не сплошным абзацем: один пункт — один аспект;
- в начале пункта давать короткую метку-подлежащее и отделять её тире (`Причина — …`, `Шаг 1 — …`), чтобы ответ сканировался глазами;
- первым пунктом идёт суть — то, что произносится на собеседовании первым, а не подводка к ней;
- не использовать `**жирный**` внутри ответов: в блоке из нескольких вопросов он превращается в шум, выделения достаточно на самом вопросе;
- ответы должны быть короткими, но содержательными;
- сначала проверять понимание основной модели, затем trade-offs и edge cases;
- не добавлять в summary новые факты, которые нигде не объясняются в статье.

Эталон нового формата — [company-algorithmic-tasks.md](12-interview-practice/coding-tasks/company-algorithmic-tasks.md).

> Правило со списками введено позже основной массы статей. Файлы с `Interview-ready answer`
> в старом абзацном формате остаются валидными до планового рефакторинга — приводить их
> к спискам нужно по мере обычной работы над статьёй, а не отдельным сплошным проходом.

## 10. Что особенно нельзя делать

- Сильно сокращать статью без отдельной просьбы пользователя.
- Удалять примеры только ради уменьшения длины файла.
- Заменять объяснение списком терминов.
- Прятать весь основной flow под `<details>`.
- Писать «очевидно», «просто» или «понятно» вместо промежуточного объяснения.
- Оставлять формулу без подстановки конкретных чисел.
- Использовать аббревиатуру до её расшифровки, если она не общеизвестна для backend-разработчика.
- Заменять обычные русские слова английскими без выигрыша в точности: `process`, `kernel`, `filesystem`, `application`, `memory`.
- Смешивать public guarantee и случайную особенность текущего source code.
- Убирать нумерацию у вопросов в `Interview-ready answer`.
- Терять разделители `---` между разделами при переписывании файла.
- Выделять жирным слова посреди фразы ради нажима, а также использовать капс для акцента.
- Начинать абзац с «частый вопрос», «это любят спрашивать» вместо самого утверждения.

## 11. Checklist перед завершением

- Сначала дана простая ментальная модель, затем детали.
- Каждый новый неочевидный термин объяснён при первом появлении.
- Для обычных понятий используются русские слова; нужный английский термин указан один раз в скобках.
- Числа, индексы и переходы на примерах имеют понятное происхождение.
- Похожие сущности явно различены.
- Объяснены причины решения и trade-offs.
- Полезные примеры сохранены или улучшены.
- Основной пример не спрятан под `<details>`.
- Текст написан преимущественно в настоящем времени.
- Жирный стоит только как метка в начале абзаца или маркер термина; акцентов посреди фразы и капса нет.
- Нет апелляций к частоте вопроса вместо содержания.
- Версионные детали проверены по official sources и явно обозначены.
- Добавлены практические последствия и типичные ошибки.
- `Interview-ready answer` содержит нумерованные вопросы.
- Перед каждым `##`, кроме первого, стоит разделитель `---`.
- Если оглавление есть, оно расположено сразу после заголовка статьи, до введения.
- Оглавление соответствует текущим заголовкам.
- Markdown links, code fences и `<details>` проверены.
