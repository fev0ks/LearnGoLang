Начнём с небольшого сценария чтения товара. Его задача — показать связку
«заданный поток → корректный ответ → измерение → критерий результата».
Сценарий предназначен для локального или выделенного тестового окружения;
для запуска против живой системы нужен план из [статьи про production](./05-production-testing.md).

---

## Что проверяет пример

Предположим, на нашем стенде есть `GET /api/products/{id}`. Он возвращает
`200 OK` и JSON с полем `id`, которое совпадает с запрошенным идентификатором.
Тестовые товары заранее созданы. Это контракт учебного примера, а не существующий
endpoint данного репозитория.

Установка инструмента описана в [официальной инструкции k6](https://grafana.com/docs/k6/latest/set-up/install-k6/).
Перед запуском сохранить результат `k6 version`. Скрипт использует публичные
API из документации, сверенной 13 сентября 2026 года; внешний вид итогового
отчёта может отличаться между версиями.

Учебные критерии: p95 меньше 300 мс, p99 меньше 800 мс, доля HTTP-ошибок меньше
1%, не менее 99% ответов проходят проверку статуса и ID, пропущенных итераций нет.
Это иллюстрация настройки, а не универсальные цели качества.

## Сценарий и запуск

Сохранить код в `catalog.js`. Переменная `PRODUCT_IDS` содержит идентификаторы
уже существующих тестовых товаров через запятую. `API_TOKEN` при необходимости
передаётся через окружение из секретов тестового стенда.

```javascript
import http from 'k6/http';
import { check } from 'k6';

const baseURL = (__ENV.BASE_URL || 'http://127.0.0.1:8080').replace(/\/$/, '');
const productIDs = (__ENV.PRODUCT_IDS || '').split(',').map((s) => s.trim());
if (productIDs.some((id) => id.length === 0)) {
    throw new Error('PRODUCT_IDS must contain non-empty existing product IDs');
}
const headers = { 'X-Load-Test': 'catalog-read' };
if (__ENV.API_TOKEN) {
    headers.Authorization = `Bearer ${__ENV.API_TOKEN}`;
}

http.setResponseCallback(http.expectedStatuses(200));

export const options = {
    scenarios: {
        catalog: {
            executor: 'ramping-arrival-rate',
            startRate: 1,
            timeUnit: '1s',
            preAllocatedVUs: 250,
            maxVUs: 250,
            stages: [
                { duration: '30s', target: 1 },
                { duration: '30s', target: 100 },
                { duration: '2m', target: 100 },
                { duration: '30s', target: 0 },
            ],
            gracefulStop: '5s',
        },
    },
    thresholds: {
        http_req_failed: [
            { threshold: 'rate<0.01', abortOnFail: true, delayAbortEval: '10s' },
        ],
        http_req_duration: ['p(95)<300', 'p(99)<800'],
        checks: ['rate>=0.99'],
        dropped_iterations: ['count==0'],
    },
};

export default function () {
    const id = productIDs[Math.floor(Math.random() * productIDs.length)];
    const response = http.get(`${baseURL}/api/products/${encodeURIComponent(id)}`, {
        headers,
        timeout: '2s',
        redirects: 0,
        tags: { name: 'GET /api/products/:id' },
    });
    check(response, {
        'status 200 and matching product id': (r) => {
            if (r.status !== 200) {
                return false;
            }
            try {
                return String(r.json('id')) === id;
            } catch {
                return false;
            }
        },
    });
}
```

Пример команды для стенда на своей машине, где товары `test-1` и `test-2`
предварительно созданы:

```bash
k6 version
BASE_URL=http://127.0.0.1:8080 PRODUCT_IDS=test-1,test-2 k6 run catalog.js
```

Список из двух товаров пригоден для проверки механики. Для измерения ёмкости
нужен представительный набор из [статьи про профиль нагрузки](./02-workload-models.md).
Скрипт выбирает ID равномерно; распределение популярности здесь не реализовано.

`X-Load-Test` — метка, которую приложение может использовать для диагностики.
Она сама по себе не создаёт отдельный tenant, не запрещает запись и не меняет
маршрутизацию. Внешнему клиенту нельзя разрешать включать привилегированный
«тестовый режим» одним произвольным заголовком.

## Как читается профиль нагрузки

`ramping-arrival-rate` задаёт частоту запуска итераций. В этой функции один
HTTP-запрос на итерацию, redirect отключён, явных повторов нет. Поэтому
планируемые итерации/с соответствуют планируемым запросам/с.

| Фаза | Время от старта | Что делает генератор |
| --- | --- | --- |
| Минимальная нагрузка | 0–30 с | Планирует 1 итерацию/с |
| Рост | 30–60 с | Линейно повышает частоту с 1 до 100 итераций/с |
| Плато | 60–180 с | Планирует 100 итераций/с |
| Снижение | 180–210 с | Линейно снижает частоту до нуля |

На плато планируется `100 × 120 = 12 000` итераций. Фактический запуск нужно
подтвердить метриками. Плавная ступень с `target: 100` не означает 100 RPS
с первой секунды этой ступени. Семантика — в
[документации executor](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/ramping-arrival-rate/).

После расписания `gracefulStop` даёт выполняющимся итерациям до пяти секунд на
завершение. Этот параметр не управляет серверными очередями: они могут продолжить
работу после окончания теста.

`sleep()` в конце функции для ограничения RPS не нужен: частоту задаёт executor.
Пауза между действиями внутри пользовательского пути может быть частью модели,
но добавлять её следует осознанно — она занимает VU.

## Проверки и критерии результата

**Check** проверяет ответ конкретной операции. Здесь он один и объединяет статус
и совпадение ID. Ошибка разбора JSON тоже даёт неуспешный check, поэтому HTML
страница с `200 OK` не считается корректным товаром.

Сам по себе неуспешный `check` не делает запуск неуспешным. Порог `checks`
превращает долю успешных проверок в критерий результата. При нескольких checks
на один ответ метрика считает проверки, а не бизнес-операции; это может менять
знаменатель. См. [checks](https://grafana.com/docs/k6/latest/using-k6/checks/).

`setResponseCallback(http.expectedStatuses(200))` отдельно задаёт ожидаемый HTTP
статус для `http_req_failed`. Проверка содержимого не меняет эту метрику:
`200` с неправильным ID остаётся HTTP-успехом, но проваливает наш check.
Семантика описана в [setResponseCallback](https://grafana.com/docs/k6/latest/javascript-api/k6-http/set-response-callback/).

**Threshold** — критерий успеха для метрики. Если итоговый критерий не выполнен,
k6 возвращает ненулевой код выхода. `abortOnFail` дополнительно разрешает раннюю
остановку при нарушении указанного порога. `delayAbortEval: '10s'` откладывает
раннюю проверку, но не удаляет первые десять секунд из статистики.

Порог из примера считает накопленную статистику запуска. Он не означает
«ошибки за последние десять секунд». При большом объёме ранних успешных ответов
свежая деградация может раствориться в общем результате. Для живой системы нужен
отдельный контроль недавних окон и пользовательских метрик. См.
[thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/).

Итоговые процентили тоже смешивают фазы. Для оценки именно 100 RPS выделяют плато
по временным меткам в системе метрик либо выполняют отдельный измеряемый запуск
на постоянной частоте после прогрева. Низкая итоговая latency не доказывает,
что каждое плато прошло требования.

## Длительность, VU и предел генератора

В `http_req_duration` входят отправка, ожидание ответа и чтение тела. Начальные
DNS lookup и установление соединения в эту метрику не входят. Для них смотрят
дополнительные сетевые timings; для полной операции — её длительность с явно
выбранной границей. См. [built-in metrics](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/).

250 VU в примере — запас для иллюстрации. При частоте 100 итераций/с и среднем
полном времени итерации 0,2 с требуется в среднем 20 занятых VU. Если оно растёт
до 2 с, требуется около 200. Таймаут HTTP-запроса не ограничивает весь JavaScript
сценарий: разбор больших тел тоже занимает время.

Здесь число VU заранее выделено и ограничено одинаковым значением. Это позволяет
избежать их динамического добавления во время замера, но может расходовать лишнюю
память генератора. Число исполнителей подбирают по фактической длительности
итераций и запасу ресурсов. См. [VU allocation](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/arrival-rate-vu-allocation/).

Если появляются `dropped_iterations`, нужно выяснить, почему нет свободного VU,
и проверить CPU, память и сеть генератора. Увеличение лимита без диагностики может
лишь отложить обнаружение деградации сервера.

## Как расширять сценарий

- **Несколько endpoint.** Добавить отдельные сценарии с нужными частотами и thresholds по стабильным тегам; общий процентиль может скрыть редкий медленный поиск.
- **Пользовательский путь.** Использовать данные из предыдущего ответа, измерять итог всего пути, отдельно учитывать число HTTP-запросов.
- **Запись.** Подготовить тестовые сущности, сохранять ключ идемпотентности при повторе и сверять итоговые изменения.
- **Авторизация.** Моделировать время жизни токенов и обновление, если они входят в гипотезу; один общий аккаунт может искусственно упереться в пользовательскую квоту.
- **Большие данные.** Подготовить набор отдельно и контролировать стоимость его чтения генератором; малый список ID из примера не даёт репрезентативного кэша.

Тег `name` группирует динамические URL в одну логическую операцию. При экспорте
метрик также проверяют набор экспортируемых тегов: оставленный тег с полным URL
может сохранить высокую cardinality — большое количество уникальных временных
рядов. ID запросов и пользователей лучше держать в логах/traces.

## Типичные ошибки

- **Только статус ответа.** `200` содержит неправильный объект, а тест считает его успехом.
- **Только checks.** Нет threshold, и pipeline не замечает провал проверок.
- **Rate принят за VU.** Целевые старты итераций смешиваются с числом исполнителей.
- **Порог принят за окно.** `delayAbortEval` ошибочно интерпретируется как скользящие десять секунд.
- **Средний график всего запуска.** Участок деградации на плато скрывается за фазами малой нагрузки.

## Interview-ready answer

**1. Как устроить минимальный полезный тест на k6?**

- Сценарий — выполнить реальную операцию над подготовленными данными.
- Поток — выбрать executor под модель нагрузки и проверить фактически достигнутую частоту.
- Качество — проверить содержимое ответа и задать thresholds для latency, ошибок и пропусков.

**2. Чем check отличается от threshold?**

- Check — регистрирует результат проверки конкретного ответа.
- Threshold — определяет успех запуска по метрике и может включать раннюю остановку.
- Ограничение — накопленный порог не заменяет мониторинг недавнего окна в production.

**3. Почему 100 итераций/с могут не дать 100 запросов/с?**

- Сценарий — может содержать несколько запросов, переходы или повторы.
- Генератор — может пропускать старты при нехватке исполнителей.
- Время — на росте частота меняется; целевой уровень относится к концу ступени.
