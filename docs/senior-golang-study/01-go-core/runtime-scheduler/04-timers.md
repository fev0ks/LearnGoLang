Таймер паркует goroutine до нужного момента, не резервируя под неё поток операционной системы. Начиная с Go 1.23 таймеры на каналах получили новые гарантии по сборке мусора и по `Stop`/`Reset`, поэтому старые советы про обязательное вычерпывание канала часто больше не нужны.

Материал ориентирован на Go 1.26. Устройство таймеров внутри runtime — деталь реализации; стабильна семантика пакета `time`.

---

## Ментальная модель

```go
time.Sleep(500 * time.Millisecond)
```

Упрощённо runtime:

1. создаёт таймер с моментом срабатывания;
2. переводит текущую G в состояние ожидания;
3. M продолжает исполнять другие goroutines;
4. после наступления срока runtime делает спящую G готовой;
5. планировщик позже снова запускает её на любом подходящем M.

`Sleep` гарантирует, что пауза будет не меньше указанной длительности, но не точный момент возобновления. После срока goroutine ещё ждёт планировщик и процессорное время от операционной системы.

## Где хранятся таймеры

В текущем runtime таймеры организованы как наборы, привязанные к каждому P, с кучей, упорядоченной по ближайшему сроку. Это уменьшает конкуренцию за блокировку по сравнению с одной глобальной кучей.

Операции в общем случае:

- добавление и изменение таймера поддерживают порядок в куче;
- планировщик проверяет ближайшие таймеры;
- сработавший таймер делает G готовой, отправляет значение в канал или запускает обратный вызов;
- периодический таймер вычисляет следующий срок.

Конкретные поля и имена вспомогательных функций в `runtime/time.go` — детали реализации. Стабильная идея: множество таймеров обслуживается runtime, а не отдельным потоком на каждый таймер.

<details>
<summary>Упрощённые структуры таймеров в Go 1.26</summary>

```go
// Один логический триггер.
type timer struct {
	mu     mutex
	state  uint8
	isChan bool

	when   int64
	period int64
	f      func(arg any, seq uintptr, delay int64)
	arg    any
	seq    uintptr

	ts *timers
}

// Набор таймеров, привязанный к одному P.
type timers struct {
	mu   mutex
	heap []timerWhen
	len  atomic.Uint32

	zombies     atomic.Int32
	minWhenHeap atomic.Int64
}
```

Ключевые поля:

- `when` — абсолютный срок по монотонным часам;
- `period == 0` — одноразовый таймер;
- `period > 0` — периодический таймер или Ticker;
- `f`/`arg` — действие: разбудить G, подготовить отправку в канал или запустить обратный вызов;
- `seq` — защита от срабатывания старой конфигурации после `Reset` или смены срока;
- `heap[0]` — ближайший таймер внутри набора.

Планировщик способен обращаться к таймерам другого P, поэтому привязка к P не означает полного отсутствия синхронизации. Куча защищается блокировкой, а атомарные счётчики дают дешёвую быструю проверку ближайшего срока и количества записей.

</details>

## Связь с планировщиком и netpoller

Когда готовая работа есть, планировщик попутно проверяет сработавшие таймеры. Когда работы нет, runtime может заблокироваться в опросе сети с таймаутом до ближайшего срока.

```text
сетевое событие раньше срока → поллер просыпается из-за дескриптора
срок раньше сетевого события → поллер возвращается по таймауту, планировщик проверяет таймеры
```

Netpoller не исполняет действие таймера. Он лишь помогает runtime эффективно спать до сетевого события или до ближайшего срока: значение `delay` для блокирующего `netpoll` вычисляется именно по ближайшему таймеру. Разбуженная goroutine или обратный вызов затем проходят через планировщик. Подробнее об этом расчёте — в [netpoller](./03-netpoller.md).

## Какой API выбирать

| API | Когда использовать | Можно управлять жизненным циклом |
| --- | --- | --- |
| `time.Sleep` | просто приостановить текущую goroutine | нет |
| `time.After` | одноразовый таймаут в простом `select` | только через канал |
| `time.NewTimer` | таймаут нужно останавливать, перезапускать или переиспользовать | да |
| `time.AfterFunc` | запустить обратный вызов после задержки | `Stop`/`Reset` с особой семантикой |
| `time.NewTicker` | периодическое событие | да, через `Stop` |
| `time.Tick` | короткий вспомогательный случай | только через канал |

## Что изменилось в Go 1.23

Для таймеров на каналах — `NewTimer`, `After`, `NewTicker`, `Tick` — в Go 1.23:

- сборщик мусора может собирать таймеры и тикеры, на которые нет ссылок, даже если код не вызвал `Stop`;
- каналы таймеров работают как синхронные, с ёмкостью 0;
- после возврата из `Stop` или `Reset` канал не получит устаревшее значение от прежней конфигурации.

Поэтому старый универсальный приём больше не нужен для Go 1.23 и новее:

```go
// Старый приём до 1.23; в новом коде механически не копировать.
if !t.Stop() {
    <-t.C
}
t.Reset(d)
```

В модуле с директивой `go` ниже 1.23 может действовать прежнее поведение; им также управляет `GODEBUG=asynctimerchan`.

`Stop` всё ещё полезен, когда таймер больше не нужен: это явный жизненный цикл и предотвращение ненужного пробуждения или обратного вызова. Для Ticker `Stop` прекращает будущие срабатывания.

<details>
<summary>Текущий и прежний Reset рядом</summary>

Для модуля с Go 1.23 и новее таймер на канале можно перезапускать без ручного вычерпывания:

```go
t.Reset(nextDelay)
```

Прежний приём выглядел так:

```go
if !t.Stop() {
	select {
	case <-t.C:
	default:
	}
}
t.Reset(nextDelay)
```

Смешивать эти приёмы механически нельзя. Поведение выбирается директивой `go` модуля и может быть изменено через `GODEBUG=asynctimerchan`; при обновлении полезно иметь тест на то поведение `Stop`/`Reset`, от которого зависит код.

</details>

## Практические паттерны

### Таймаут через context

Если операция принимает `context`, обычно проще позволить API верхнего уровня управлять таймером:

```go
ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()

return call(ctx)
```

### Переиспользуемый Timer в горячем цикле

`time.After` на каждой итерации создаёт новый таймер. В горячем пути можно переиспользовать один:

```go
t := time.NewTimer(time.Second)
defer t.Stop()

for {
    select {
    case v := <-in:
        handle(v)
        t.Reset(time.Second) // семантика Go 1.23+
    case <-t.C:
        onIdleTimeout()
        t.Reset(time.Second)
    }
}
```

Это пример для единственной goroutine-владельца. Одновременные `Stop`, `Reset` и чтение одного таймера из разных goroutines требуют отдельного продуманного протокола синхронизации.

<details>
<summary>Debounce на одном переиспользуемом таймере</summary>

```go
func debounce[T any](
	ctx context.Context,
	in <-chan T,
	delay time.Duration,
	flush func(T),
) {
	timer := time.NewTimer(time.Hour)
	_ = timer.Stop() // пример рассчитан на семантику Go 1.23+
	defer timer.Stop()

	var (
		latest T
		armed  bool
		timerC <-chan time.Time
	)

	for {
		select {
		case value, ok := <-in:
			if !ok {
				return
			}
			latest = value
			armed = true
			timer.Reset(delay) // семантика каналов таймера Go 1.23+
			timerC = timer.C
		case <-timerC:
			if armed {
				flush(latest)
			}
			armed = false
			timerC = nil
		case <-ctx.Done():
			return
		}
	}
}
```

Одна goroutine владеет таймером, поэтому одновременных `Reset` и чтения нет. Присваивание `nil` каналу выключает соответствующую ветку `select` после сброса. В продуктивном коде нужно отдельно решить, следует ли выгружать последнее значение при закрытии входа или при отмене.

</details>

### Жизненный цикл Ticker

```go
ticker := time.NewTicker(time.Second)
defer ticker.Stop()

for {
    select {
    case <-ticker.C:
        refresh()
    case <-ctx.Done():
        return
    }
}
```

## Точность и Ticker

Таймеры — механизм планирования, а не часы реального времени:

- планирование в ядре и нагрузка задерживают исполнение после наступления срока;
- долгая работа сборщика мусора или runtime добавляет задержку;
- Ticker корректирует интервал и может пропускать срабатывания, если получатель не успевает;
- настенные часы могут переводиться, поэтому значения `time.Time` в Go несут монотонную составляющую и сравнение длительностей опирается на неё, когда она доступна.

Если нужно обработать «сколько периодов прошло», нельзя полагаться на количество полученных событий тикера — состояние вычисляют из текущего времени или из данных предметной области.

<details>
<summary>Эксперимент: Ticker не является очередью всех срабатываний</summary>

```go
ticker := time.NewTicker(100 * time.Millisecond)
defer ticker.Stop()

previous := time.Now()
for range 5 {
	tickTime := <-ticker.C
	fmt.Println("tick delta:", tickTime.Sub(previous).Round(10*time.Millisecond))
	previous = tickTime

	// Получатель медленнее периода тикера.
	time.Sleep(350 * time.Millisecond)
}
```

Программа не получает по три события после каждого `Sleep`: Ticker корректирует расписание и может пропускать срабатывания для медленного получателя. Поэтому периодическая сверка состояния обычно вычисляет его заново, а не делает «один шаг на каждое срабатывание».

</details>

`time.AfterFunc` запускает обратный вызов в отдельной goroutine. Он может пересечься с работой приложения и требует обычной синхронизации. Семантика `Reset` различается в зависимости от того, активен ли таймер или обратный вызов уже запущен; её проверяют по документации пакета.

<details>
<summary>AfterFunc: Stop не ждёт уже начавшийся обратный вызов</summary>

```go
done := make(chan struct{})
timer := time.AfterFunc(100*time.Millisecond, func() {
	defer close(done)
	expensiveCleanup()
})

if !timer.Stop() {
	// В этом примере обратный вызов уже мог начаться; ждём его отдельно.
	<-done
}
```

Такое ожидание корректно здесь, потому что таймер новый, `Stop` вызывается один раз, а обратный вызов гарантированно закрывает `done`. В общем случае повторные `Reset` и `Stop` требуют отдельного конечного автомата: API таймера не заменяет `WaitGroup`, мьютекс или протокол владения.

</details>

## Типичные ошибки

- считать `time.Sleep` блокирующим системным вызовом для потока;
- ожидать возобновления точно в момент срока;
- создавать `time.After` в горячем цикле без оценки выделений памяти;
- переносить приём с вычерпыванием канала, написанный до 1.23, в Go 1.23 и новее;
- забывать `Ticker.Stop`, когда периодическая работа должна прекратиться;
- делать тяжёлый обратный вызов в `AfterFunc` без контроля параллелизма;
- считать каждое событие тикера гарантированным;
- одновременно управлять одним таймером из нескольких goroutines без явного владельца.

## Версионная карта таймеров runtime

Этот раздел помогает читать старые статьи, не перенося их устройство на актуальный runtime:

| Версия | Модель |
| --- | --- |
| До Go 1.10 | глобальная куча таймеров и отдельная goroutine `timerproc` |
| Go 1.10–1.13 | кучи таймеров разделены на части, но устройство ещё отличается от современной привязки к P |
| Go 1.14+ | таймеры интегрированы с P и планировщиком, а также с таймаутом ожидания в netpoll |
| Go 1.23+ | таймеры на каналах получают синхронный канал и новые гарантии по сборке мусора и `Stop`/`Reset` |

Поэтому утверждение «в Go есть одна специальная goroutine, которая обслуживает все таймеры» описывает старый runtime, а не Go 1.26. В актуальной модели планировщик проверяет таймеры, привязанные к P, а таймаут блокирующего опроса сети помогает эффективно ждать ближайший срок.

Версионная карта не обещает одинакового внутреннего устройства во всех выпусках после Go 1.14. Проверять нужно стабильную семантику пакета `time`, а поля runtime использовать только для понимания и диагностики.

## Interview-ready answer

**1. Блокирует ли time.Sleep поток операционной системы?**

- Ответ — нет, runtime регистрирует таймер и паркует только G.
- Что делает поток — M вместе с P запускает другую goroutine.
- Возврат — после наступления срока G становится готовой и позже продолжает работу.

**2. Где живут таймеры?**

- Хранение — наборы таймеров с кучей, привязанные к каждому P, что снимает конкуренцию за одну глобальную структуру.
- Проверка — планировщик смотрит сработавшие таймеры попутно с поиском работы.
- Чего нет — отдельного потока или goroutine на каждый таймер.

**3. Зачем netpoller участвует в таймерах?**

- Причина — блокирующий опрос сети уже умеет ждать с таймаутом.
- Как — runtime выбирает таймаут по ближайшему сроку, поэтому одно ожидание просыпается либо по готовности сети, либо по времени.
- Разделение ролей — само действие таймера после пробуждения выполняет планировщик, а не поллер.

**4. Что изменилось в Go 1.23?**

- Каналы — таймеры на каналах стали синхронными, с нулевой ёмкостью.
- Гарантии — после `Stop` или `Reset` устаревшее значение в канал не приходит.
- Сборка мусора — таймеры и тикеры без ссылок собираются даже без `Stop`.
- Следствие — обязательное вычерпывание канала перестало быть правильным умолчанием для нового кода.

**5. Есть ли отдельная goroutine timerproc?**

- Ответ — нет, это описание версий до Go 1.10.
- Сейчас — в Go 1.26 таймеры привязаны к P и интегрированы с планировщиком и ожиданием в netpoll.
- Как отвечать — стоит сразу отделить историческую модель от актуальной, иначе ответ звучит как пересказ старой статьи.
