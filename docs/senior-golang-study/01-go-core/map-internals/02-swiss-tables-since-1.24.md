# Map internals начиная с Go 1.24: Swiss Tables

Go 1.24 (февраль 2025) заменил внутреннюю реализацию `map` на алгоритм **Swiss Tables** — open addressing с metadata-байтами и проверкой 8 слотов за одну операцию. API и семантика не изменились (порядок итерации случаен, nil-map, concurrent → fatal, и т.д.), но реализация другая, а производительность выросла. Прежняя реализация (`hmap` + `bmap` с overflow-цепочками) разобрана в [01-hmap-before-1.24](./01-hmap-before-1.24.md); этот файл — про новую и про то, чем она отличается.

Всё проверено на go1.26 (`internal/runtime/maps`), darwin/arm64.

## Почему заменили hmap

Слабые места старой реализации (`hmap` + `bmap`):

| Проблема | Следствие |
|---|---|
| Overflow-цепочки bucket'ов | pointer chasing → промахи кэша |
| Инкрементальная эвакуация | сложность кода, проверка двух массивов при каждом lookup |
| `tophash` сравнивается по одному слоту | до 8 итераций с ветвлением на bucket |

Swiss Tables (оригинал — Google Abseil, C++, 2017; переосмыслены для Go) бьют по этим точкам:

- **open addressing** вместо chaining — нет overflow-цепочек, всё в непрерывной памяти;
- **ctrl-байты per slot** — проверка сразу 8 слотов одной арифметической (или SIMD) операцией, без цикла и ветвления;
- лучшая cache locality и более высокий допустимый load factor (7/8 против ~6.5/8).

## Идея: группы вместо цепочек

Память таблицы — это непрерывный массив **групп** по 8 слотов. При коллизии новый bucket не создаётся — поиск переходит к следующей группе в том же массиве:

```
Старый hmap (chaining):
bucket → [8 слотов] → overflow → [8 слотов] → overflow → ...   (прыжки по указателям)

Swiss Tables (open addressing, групповое зондирование):
group0   group1   group2   group3   ...                        (один непрерывный массив)
[8 сл.]  [8 сл.]  [8 сл.]  [8 сл.]
   ↑        ↑
 стартовая  если в group0 нет места — пробуем дальше
 группа     (по квадратичной последовательности)
```

Каждой группе соответствует **control word** — 8 байт metadata (по байту на слот). Эти байты и позволяют проверять всю группу разом.

Но массив групп — не самый верхний уровень. Над ним есть **обёртки**: для больших map таблиц несколько, и какую выбрать — решает `directory`. Полная иерархия сверху вниз:

```
Map (заголовок: used, seed, dirPtr, …)
  │
  └─ directory ── массив *table; КАКУЮ table взять — по СТАРШИМ битам хэша
       ├─[0]─▶ table ─┐
       ├─[1]─▶ table  │  каждая table — это уже знакомый
       ├─[2]─▶ table  │  массив ГРУПП (+ счётчики used/capacity)
       └─[3]─▶ table ─┘
                 │
                 └─ groups:  group0  group1  group2  …   ← внутри: квадратичное зондирование
                               │                            (стартовая группа — по H1)
                               └─ group = [8 ctrl-байт] + [8 слотов {key,val}]
                                            ▲ matchH2 сравнивает наклейки разом
```

Три «уровня выбора» — это три применения одного хэша: **directory** берёт `table` по старшим битам, внутри `table` стартовая **группа** выбирается по `H1`, внутри группы слот отсеивается по `H2`.

**Маленькая map** (≤ 8 элементов) обёрток не имеет вовсе: `Map.dirPtr` указывает **прямо на одну группу** — ни directory, ни table. Это частый случай, и его нарочно сделали дешёвым (см. «Small-map оптимизация»).

## Главная идея простыми словами

Дальше будет много терминов — но идея простая, держи её в голове как опору.

**Аналогия.** Представь длинный ряд ячеек, сгруппированных по 8 — как полки по 8 ящиков. Снаружи каждого ящика — маленькая наклейка в 1 байт: короткий «отпечаток» лежащего внутри ключа (или метка «пусто»).

**Чтобы положить или найти ключ — три шага:**

1. Считаем хэш ключа (большое число). Часть его битов говорит, **с какой полки начинать**, а ещё 7 бит — это и есть **наклейка-отпечаток**.
2. Приходим на полку и **одним движением** сравниваем наклейки всех 8 ящиков сразу с нашим отпечатком. Где совпало — кандидат; только у кандидатов открываем ящик и сверяем ключ целиком (наклейка короткая, бывают случайные совпадения).
3. Не нашли, и все 8 ящиков заняты? Переходим к следующей полке (по фиксированному правилу) и повторяем. Поиск **останавливается, как только встретили пустой ящик** — раз пусто, дальше нашего ключа точно нет.

Вот и весь механизм. Всё остальное в файле — детали этих трёх шагов: как именно режется хэш, как «одним движением» сравнить 8 наклеек, как полки растут и что делать с удалёнными ящиками.

**Мини-словарь** (эти слова встретятся дальше):

| Термин | Простыми словами |
|---|---|
| слот | одна ячейка под пару ключ-значение |
| группа (group) | 8 слотов рядом + их 8 «наклеек» (наклейки = control word) |
| ctrl-байт | наклейка слота: «пусто» / «удалён» / отпечаток занятого |
| H1 / H2 | две части хэша: **H1** выбирает стартовую полку (группу), **H2** — это отпечаток (наклейка) |
| зондирование (probing) | переход к следующей группе, если в текущей не нашли |
| tombstone | метка «здесь удалили», чтобы не оборвать поиск (см. Delete) |
| directory | для больших map: несколько таблиц; верхние биты хэша выбирают нужную |

## Запись `m[key] = value`: алгоритм с высоты

А это та же тройка шагов, но уже формально, одним псевдокодом (упрощённый `Map.PutSlot`). Если термины пока пугают — вернись к «простыми словами» выше или к мини-словарю; здесь просто вся карта целиком, детали каждого шага — в разделах ниже.

```
m[key] = value:

    if m.writing != 0: fatal("concurrent map writes")   // детектор гонок
    hash := typ.Hasher(key, m.seed)
    m.writing ^= 1                       // флаг "идёт запись" (toggle, см. concurrent)

    // small-map путь: пока ≤ 8 элементов — одна группа, без directory
    if m.dirLen == 0 && m.used < 8:
        слот := найти в единственной группе (matchH2 → ключ есть? иначе пустой)
        записать, m.used++; m.writing ^= 1; return

    // обычный путь
    table := m.directory[ hash >> globalShift ]   // выбрать table по верхним битам
    seq := probeSeq(H1(hash))                      // стартовая группа = H1 & (numGroups-1)
    for {
        g := table.group(seq.offset)
        if i := g.matchH2(H2(hash)); нашли и key совпал:
            g.slot(i).elem = value         // ключ уже есть → перезапись
            goto done
        if g.matchEmptyOrDeleted() даёт свободный слот:
            занять его (приоритет — переиспользовать tombstone)
            g.ctrl[i] = H2(hash); записать key/value; table.used++
            goto done
        seq = seq.next()                   // группа занята целиком → следующая (квадратично)
    }
    if table.used + tombstones > 7/8 * table.capacity:
        table.rehash()                     // double или split (см. «Рост»)

done:
    m.writing ^= 1                         // снять флаг записи
```

Сразу видно ключевые отличия от `hmap`:

- **Нет цикла «по одному слоту»** — `matchH2` проверяет все 8 слотов группы разом.
- **Нет overflow** — при заполнении группы переходим к следующей группе массива (зондирование), а не аллоцируем bucket.
- **Флаг `writing` ставится через XOR** (toggle), а не просто `=1` — это нарочно, чтобы два конкурентных писателя с большей вероятностью «поймали» друг друга.

## H1 и H2: разрезание хэша

Один 64-битный хэш режется на две независимые части (`internal/runtime/maps`):

```go
func h1(h uintptr) uintptr { return h >> 7 }    // верхние 57 бит
func h2(h uintptr) uintptr { return h & 0x7f }  // нижние 7 бит
```

- **H2** (7 бит) кладётся в `ctrl`-байт занятого слота и служит «быстрым фильтром» внутри группы (аналог `tophash`, но 7 бит, не 8).
- **H1** (57 бит) выбирает **стартовую группу** внутри таблицы: `H1 & (numGroups − 1)`.
- **Верхние биты хэша** (старшие `globalDepth` бит, `hash >> globalShift`) выбирают **таблицу** в directory (для больших map; см. «Рост»).

Worked-пример (`hash = 0xA3F7_2B19_C4D5_E6F9`):

```
H2 = hash & 0x7f          = 0xF9 & 0x7f = 0x79   → пойдёт в ctrl-слота
H1 = hash >> 7            = 0x0147_EE56_38_9A_BD…  → & (numGroups-1) = стартовая группа
directory (globalDepth=2) = hash >> 62 = 0b10 = 2  → table #2
```

Шанс ложного совпадения по H2 — **1/128** (7 бит) против 1/256 у 8-битного `tophash`. Это не проблема: после совпадения H2 всё равно сравнивается полный ключ, а 7 бит выбраны ради 8 слотов в одном 64-битном control word.

## Структуры: Map, table, group

Сама переменная `map` — это указатель на `Map` (`internal/runtime/maps`):

```go
type Map struct {
    used    uint64          // число элементов (len(m)); ДОЛЖНО быть первым — это знает компилятор
    seed    uintptr         // случайный seed хэша, уникальный на каждую map

    dirPtr  unsafe.Pointer  // directory: массив *table … ЛИБО (для малых map) указатель на одну group
    dirLen  int             // длина directory = 1<<globalDepth; для малой map = 0

    globalDepth uint8       // сколько верхних бит хэша идёт на выбор table
    globalShift uint8       // = 64 - globalDepth (на сколько сдвигать хэш для индекса directory)

    writing uint8           // флаг "идёт запись" (toggle XOR 1) — детектор гонок
    tombstonePossible bool  // есть ли где-то tombstone (оптимизация)
    clearSeq uint64         // счётчик clear() — для детекта clear во время итерации
}
```

Таблица — отдельная хэш-таблица фиксированного размера (их может быть много через directory):

```go
type table struct {
    used       uint16   // заполнено слотов
    capacity   uint16   // всего слотов (всегда 2^N) = (lengthMask+1) * 8
    growthLeft uint16   // сколько ещё можно вставить до rehash (учитывает и tombstones)
    localDepth uint8    // сколько бит directory ведёт в эту table (см. extendible hashing)
    index      int      // позиция в directory (-1 если table уже заменена)
    groups     groupsReference   // массив групп по 8 слотов
}
```

### group и раскладка в памяти

Группа = `control word` (8 байт, по байту на слот) + 8 слотов. **Важное отличие от `hmap`:** в Swiss Tables ключ и значение **чередуются по слотам** (`{key,elem}, {key,elem}, …`), а не лежат отдельными блоками, как в `bmap`. В рантайме `key(i) = base + i*SlotSize`, `elem(i) = base + i*SlotSize + ElemOff` — то есть `elem` сразу за `key` внутри слота.

```
group (map[string]int): 8 ctrl + 8 слотов {key, elem}

Offset  Content
────────────────────────────────────────────
  0     ctrl[0..7]    8 × uint8   ← один ctrlGroup (uint64): metadata всех 8 слотов
────────────────────────────────────────────
  8     key[0]  string (16)  ─┐ слот 0  (SlotSize = 24)
 24     elem[0] int    (8)   ─┘
 32     key[1]  string (16)  ─┐ слот 1
 48     elem[1] int    (8)   ─┘
 ...
        key[7], elem[7]                 слот 7
────────────────────────────────────────────
Total: 8 + 8×24 = 200 bytes
```

- **`hmap`** клал все ключи блоком, потом все значения — чтобы срезать padding (например, `map[int8]int64`).
- **Swiss** чередует `{key,elem}` ради locality (ключ и его значение рядом — один cache-line), ценой возможного padding для «неудобных» пар типов (тот самый `map[int8]int64`). Это сознательный размен, отмеченный прямо в комментарии рантайма.

В слоте лежит **сам** ключ/значение, только если он умещается в порог: `> 128` байт (`abi.MapMaxKeyBytes` / `MapMaxElemBytes`) хранятся **по указателю** (`IndirectKey`/`IndirectElem`) — в слоте `*key`, объект отдельной аллокацией. Поэтому огромный ключ не раздувает все 8 слотов группы, но стоит лишней аллокации и разыменования. Порог version-agnostic — такой же в `hmap`; подробнее в [01-hmap-before-1.24](./01-hmap-before-1.24.md), раздел «Что может быть ключом».

### Small-map оптимизация

Если map за всю жизнь не вырастала больше `8` элементов, ей не нужны ни directory, ни `table`: `dirLen == 0`, а `dirPtr` указывает **прямо на одну group**. Поиск/вставка идут по единственной группе одним `matchH2`. Малые map к тому же **никогда не имеют tombstone** (нет probe-цепочки, которую надо беречь) — `delete` сразу ставит слот `empty`.

## ctrl-байт: три состояния

Каждый из 8 `ctrl`-байт группы описывает свой слот (`internal/runtime/maps`):

```
  empty: 1 0 0 0 0 0 0 0   = 0x80   — слот свободен
deleted: 1 1 1 1 1 1 1 0   = 0xFE   — слот удалён (tombstone)
   full: 0 h h h h h h h            — слот занят, hhhhhhh = H2 (нижние 7 бит хэша)
```

**Ключевое свойство:** у занятого слота bit7 = 0 (значение `< 0x80`), у свободного/удалённого bit7 = 1 (`≥ 0x80`). Поэтому «занятые» и «незанятые» слоты различаются одним битом — это и используют `matchEmpty` / `matchEmptyOrDeleted`.

Переходы: `insert` ставит `full(H2)`; `delete` → `empty` (если в группе и так есть пустой) или `deleted`/tombstone (если нет); tombstone превращается в `empty` только при росте таблицы.

## matchH2: 8 слотов одной операцией

Главный трюк Swiss Tables — сравнить H2 со всеми 8 `ctrl`-байтами **без цикла**. Почему это «одно движение», а не 8 проверок: 8 наклеек лежат подряд как **одно 64-битное число**, а процессор обрабатывает целый 64-битный регистр одной инструкцией — неважно, что мы «считаем» его восемью байтами. Сравнение — три арифметических шага над этим словом (это и есть SWAR; на amd64 — одна SIMD-инструкция):

1. **размножить** H2 на все 8 байт: `H2 * 0x0101…01` → слово, где отпечаток повторён 8 раз;
2. **XOR** с control word: байт станет `0x00` там, где наклейка совпала с H2, и ненулевым — где нет;
3. **найти нулевые байты** битовым трюком → `bitset`, где бит выставлен на совпавших слотах.

```
ищем H2 = 0x79, наклейки группы (для краткости 4 байта вместо 8):
control word:      [0x79][0x12][0x80][0x79]
1) размножили H2:  [0x79][0x79][0x79][0x79]
2) XOR:            [0x00][0x6B][0xF9][0x00]   ← 0x00 там, где совпало
3) нули → биты:       1     0     0     1     → bitset: слоты 0 и 3
```

```go
// internal/runtime/maps (портируемая SWAR-версия)
const bitsetLSB = 0x0101010101010101
const bitsetMSB = 0x8080808080808080

func ctrlGroupMatchH2(g ctrlGroup, h2 uintptr) bitset {
    v := uint64(g) ^ (bitsetLSB * uint64(h2))     // шаги 1–2: 0x00 в байтах, где ctrl == h2
    return bitset((v - bitsetLSB) &^ v & bitsetMSB) // шаг 3: старший бит в "нулевых" байтах
}
```

Саму формулу шага 3 вникать необязательно — важно, что цикла и ветвлений нет, всё за пару инструкций. Результат — `bitset`: для каждого слота, где `ctrl[i] == H2`, установлен соответствующий бит. По нему итерируются без ветвления на каждый слот:

```go
match := g.ctrls().matchH2(h2(hash))
for match != 0 {
    i := match.first()                 // индекс следующего совпадения (TrailingZeros)
    if typ.Key.Equal(key, g.key(i)) {  // H2 совпал → полное сравнение ключа
        return g.elem(i), true
    }
    match = match.removeFirst()         // сбросить младший бит, дальше
}
```

«8 шагов зондирования за одну операцию» — формулировка из комментария рантайма. На amd64 это расширяется до SIMD; теоретически с 16-байтным control word можно проверять 16 слотов.

## Квадратичное зондирование

Если в группе нет ни ключа, ни свободного слота — поиск идёт к следующей группе. Но **не линейно** (`+1`), а по **квадратичной** (триангулярной) последовательности:

```go
type probeSeq struct{ mask, offset, index uint64 }

func makeProbeSeq(hash uintptr, mask uint64) probeSeq {
    return probeSeq{mask: mask, offset: uint64(hash) & mask, index: 0}
}
func (s probeSeq) next() probeSeq {
    s.index++
    s.offset = (s.offset + s.index) & s.mask   // +1, +2, +3, … накопительно
    return s
}
```

Стартовая группа = `H1 & mask` (где `mask = numGroups − 1`). Дальше смещения растут на `1, 2, 3, …`, то есть посещаются группы `start, +1, +3, +6, +10, …` (триангулярные числа). Свойства, на которые это опирается:

- число групп — **степень двойки** (поэтому `& mask` корректно «заворачивает»);
- такая последовательность при power-of-two размере обходит **все** группы без повторов;
- цепочка зондирования **всегда заканчивается группой с пустым слотом** (таблица не бывает заполнена на 100% — есть порог 7/8).

Квадратичное зондирование лучше линейного против «кластеризации» (длинных занятых участков подряд), оставаясь cache-дружелюбным (внутри группы — 8 соседних слотов).

## Lookup: пошагово

Чтение — это `matchH2` по цепочке групп. Псевдокод (упрощённый `Map.getWithKey`):

```
v := m[key]:
    if m.used == 0: return zero, false           // пустая map — сразу промах
    if m.writing != 0: fatal("concurrent map read and map write")
    hash := typ.Hasher(key, m.seed)

    if m.dirLen == 0:                             // small-map: одна группа
        g := group(m.dirPtr)
        match := g.matchH2(H2(hash))
        перебрать совпадения, сравнить ключ → нашли/не нашли
        return ...

    table := m.directory[ hash >> globalShift ]  // выбрать table
    for seq := probeSeq(H1(hash)); ; seq = seq.next():
        g := table.group(seq.offset)
        for i := range g.matchH2(H2(hash)):      // кандидаты по H2
            if key == g.key(i): return g.elem(i), true
        if g.matchEmpty() != 0:                  // встретили пустой слот →
            return zero, false                   //   ключа в цепочке нет
        // иначе группа занята целиком (или tombstone) → следующая группа
```

Ключевой инвариант: **поиск останавливается на группе с пустым слотом**. Если бы `delete` ставил `empty` посреди занятой цепочки, lookup оборвался бы рано и не нашёл бы элементы за этой позицией — отсюда tombstone (см. ниже). Tombstone (`deleted`) ведёт себя как «занятый, но никогда не совпадающий» слот: он не матчится по H2, но и не обрывает поиск.

## Insert

Полный путь записи — в разделе «Запись `m[key] = value`: алгоритм с высоты». Ключевые детали именно вставки:

- сначала `matchH2` ищет **существующий** ключ — если найден, значение перезаписывается на месте (как и в `hmap`);
- если ключа нет, `matchEmptyOrDeleted` ищет свободный слот, причём **переиспользование tombstone приоритетнее** занятия пустого слота — так таблица не «забивается» tombstone'ами;
- `growthLeft` считает, сколько ещё можно вставить; когда `used + tombstones` превышает `7/8 * capacity` — `rehash` (double или split);
- слот занимается записью `ctrl[i] = H2`, `key`, `elem`.

`maxAvgGroupLoad = 7` (то есть 7 из 8 слотов на группу в среднем) — это и есть load factor **87.5%**, выше старых ~81%.

## Delete и tombstones

```go
delete(m, "hello")
```

Логика (`Map.Delete`):

```
1. найти слот (как lookup)
2. обнулить key/elem (чтобы GC собрал то, на что они ссылались)
3. если в группе ЕСТЬ пустой слот (matchEmpty != 0):
       ctrl[i] = ctrlEmpty            // probe-цепочка и так обрывается здесь — можно сразу очистить
   иначе:
       ctrl[i] = ctrlDeleted          // tombstone: нельзя обрывать чужие probe-цепочки
       m.tombstonePossible = true
4. m.used--
```

**Зачем tombstone.** Поиск останавливается на пустом слоте. Если удалить элемент из **полностью занятой** группы, поставив `empty`, то ключи, вставленные дальше по цепочке зондирования через эту позицию, станут недостижимы. Поэтому такой слот метится `deleted` (tombstone) — он не матчится, но и не обрывает поиск. Если же в группе уже есть пустой слот, цепочка и так здесь кончается, и можно ставить `empty` сразу.

**Tombstones чистятся только при росте.** In-place очистка усложнила бы итерацию, поэтому tombstone'ы накапливаются и исчезают при `rehash` (копируются только занятые слоты). `delete` всех элементов **не уменьшает** число групп/таблиц — как и в `hmap`, shrink'а нет: память возвращается только пересозданием map. Малые map (`dirLen==0`) tombstone'ов не имеют вовсе (нет probe-цепочки) — там `delete` всегда ставит `empty`.

Параллельное удаление так же небезопасно, как любая запись: `delete` ставит `writing` и роняет `fatal` при гонке (см. «Concurrent access»).

## Рост: double, split и directory

В Swiss Tables рост — это **полная перестройка таблицы** (`rehash`), не инкрементальная эвакуация. Но за счёт разбиения map на несколько таблиц перестраивается за раз только **одна** таблица, а не весь map.

```go
func (t *table) rehash(typ *abi.MapType, m *Map) {
    newCapacity := 2 * t.capacity
    if newCapacity <= maxTableCapacity {   // maxTableCapacity = 1024
        t.grow(typ, m, newCapacity)        // заменить table на вдвое большую
        return
    }
    t.split(typ, m)                        // разбить на две таблицы
}
```

- Пока таблица не достигла `maxTableCapacity` (1024 слота) — она просто **заменяется вдвое большей**: аллоцируется новый массив групп, все занятые слоты копируются с пересчётом позиций (H1 по новому `mask`), tombstone'ы отбрасываются. Старая — мусор для GC.
- Дальше таблица **расщепляется на две** (`split`), и в дело вступает directory.

### Extendible hashing: directory

Простыми словами: вместо одной огромной таблицы держим **несколько таблиц поменьше** и табличку-указатель «какие старшие биты хэша → какая таблица» (это и есть `directory`). Когда одна таблица переполняется, расщепляется **только она** — остальные не трогаем. Так большой `rehash` дробится на много мелких.

Формально: `directory` — массив указателей на `table`, проиндексированный **старшими** битами хэша (`hash >> globalShift`, где `globalShift = 64 − globalDepth`). Число бит `globalDepth` растёт по мере добавления таблиц. Несколько индексов могут указывать на одну таблицу — у каждой таблицы свой `localDepth`:

```
directory (globalDepth = 2)
+----+
| 00 | --\
+----+    +--> table (localDepth = 1)   ← обслуживает оба индекса 00 и 01
| 01 | --/
+----+
| 10 | ------> table (localDepth = 2)
+----+
| 11 | ------> table (localDepth = 2)
+----+
```

Когда переполненную таблицу с `localDepth == globalDepth` нужно расщепить, directory **удваивается** (`globalDepth++`), и таблица делится на две по очередному биту. Если `localDepth < globalDepth`, на таблицу указывает несколько индексов — её можно расщепить без роста directory.

Что это даёт:

- **ограниченный пик памяти и время одного grow** — расщепляется только перегруженная таблица (≤ 1024 слота), остальные не трогаются;
- по сути это и есть аналог «инкрементального» роста `hmap`, но через независимые таблицы, а не через постепенную эвакуацию одного массива.

Маленькие/средние map проще: `dirLen==0` — одна группа (small-map); затем одна таблица; directory с несколькими таблицами появляется только на больших map.

## Итерация

Порядок итерации **намеренно рандомизирован** — как и в `hmap`. Старт выбирается двумя случайными числами (`internal/runtime/maps`, `Iter.Init`):

```go
it.dirOffset   = rand()   // со случайной таблицы в directory
it.entryOffset = rand()   // и со случайного слота внутри
```

Дальше — обход всех таблиц directory и всех групп/слотов каждой таблицы от случайного старта. Семантика та же, что и раньше (из спеки): добавления во время итерации **могут** быть видны или нет; удалённый ключ не выдаётся; элемент не выдаётся дважды; изменённое значение видно актуальным.

Сложность — рост **во время** итерации. Чтобы не выдать ключ дважды, итератор держит ссылку на **исходную** таблицу даже после её замены/расщепления и продолжает идти по ней (сохраняя порядок), но значения каждый раз перепроверяет в актуальной таблице (чтобы увидеть изменения/удаления). Это самая хитрая часть реализации, но снаружи всё это невидимо.

Как и в `hmap`, «порядок случаен» — упрощение: рандомизируется точка входа, а не делается настоящий shuffle. Демонстрация эффекта (одинаковая для обеих реализаций) — в [01-hmap-before-1.24](./01-hmap-before-1.24.md), раздел «Итерация».

## Concurrent access

Map по-прежнему **не потокобезопасна**. Детектор устроен на флаге `Map.writing`:

```go
// при чтении:
if m.writing != 0 { fatal("concurrent map read and map write") }

// при записи флаг ТОГГЛИТСЯ (а не просто ставится):
m.writing ^= 1   // в начале записи
// ... запись ...
if m.writing == 0 { fatal("concurrent map writes") }  // кто-то сбросил → гонка
m.writing ^= 1   // в конце
```

XOR-toggle вместо `=1` выбран нарочно: при двух конкурентных писателях обе стороны с большей вероятностью обнаружат рассинхрон флага и упадут. Флаг ставится **после** вызова `Hasher` (хэш-функция может паниковать — тогда записи фактически не было).

Это `fatal` (`runtime.throw`), а не `panic`: не ловится `recover`, процесс падает с дампом всех горутин. Подробный разбор `throw` vs `panic` — в [05-error-handling](../05-error-handling.md), раздел «Три уровня отказа». Защита та же: `sync.RWMutex` / `sync.Map`, поиск гонок через `go test -race`.

## Что может быть ключом

Это **семантика языка, она не изменилась** с переходом на Swiss Tables: ключ должен быть `comparable` (срезы/map/функции нельзя; интерфейс с не-comparable динамическим типом падает в рантайме; указатель — по адресу; NaN-ключ не достать). Полный разбор с примерами — в [01-hmap-before-1.24](./01-hmap-before-1.24.md), раздел «Что может быть ключом». Под капотом изменились лишь имена: хэш считает `typ.Hasher`, равенство — `typ.Key.Equal`.

## Сравнение: hmap vs Swiss Tables

| Характеристика | hmap (до 1.24) | Swiss Tables (1.24+) |
|---|---|---|
| Разрешение коллизий | chaining (overflow buckets) | open addressing (групповое зондирование) |
| Зондирование | — (цепочка overflow) | **квадратичное** (триангулярное) по группам |
| Слотов в единице | 8 (bucket) | 8 (group) |
| Раскладка слота | ключи блоком, значения блоком | **interleaved** `{key, elem}` по слоту |
| Metadata | `tophash` (8 бит) | `ctrl` (7 бит H2 + 1 бит занятости) |
| Ложное совпадение | 1/256 | 1/128 |
| Проверка слотов | по одному, с ветвлением | все 8 разом (`matchH2`, SWAR/SIMD) |
| Load factor | ~6.5/8 ≈ 81% | 7/8 = 87.5% |
| Рост | инкрементальная эвакуация всего map | `rehash` одной таблицы (double/split) |
| Lookup во время роста | проверять old+new массивы | нет — рост таблицы завершён до возврата |
| «Инкрементальность» | эвакуация 1–2 bucket за операцию | независимые таблицы в directory |
| Удалённый слот | `emptyOne`/`emptyRest` | `empty` / `deleted` (tombstone) |
| Заголовок | `hmap` + `bmap` + overflow pool | `Map` + `table` + directory |

## Что не изменилось

Для пользователя в Go 1.24 **ничего не поменялось**:

```go
m := make(map[string]int)
m["key"] = 1
v := m["key"]
v, ok := m["key"]
delete(m, "key")
for k, v := range m { _ = k; _ = v }
```

Сохранились все наблюдаемые свойства: случайный порядок итерации, безопасное чтение и паника на запись для nil-map, `fatal` при concurrent-доступе, запрет `&m["key"]`, `nil` как zero value, отсутствие shrink после массовых `delete`. **Никаких breaking changes** — поменялись только реализация и производительность.

Бенчмарки из release notes Go 1.24 (порядок величины): lookup ~10–30% быстрее, insert/delete ~10–20%, заметнее всего на `string`-ключах (дорогое сравнение, которое теперь реже доходит до полного сравнения благодаря `matchH2`).

## Interview-ready answer

Практические задачки на поведение map (одинаковое в обеих версиях) — в [03-puzzles-and-gotchas](./03-puzzles-and-gotchas.md). Старая реализация — в [01-hmap-before-1.24](./01-hmap-before-1.24.md).

**1. Что изменилось в map в Go 1.24?**

- Реализацию заменили с `hmap + bmap` (chaining через overflow buckets) на **Swiss Tables** — open addressing с ctrl-байтами и проверкой 8 слотов разом. API и семантика те же, производительность +10–30%.

**2. Что такое ctrl-байт и matchH2?**

- Каждый слот описан одним `ctrl`-байтом: либо 7 бит `H2` у занятого, либо спец-значение (`empty 0x80` / `deleted 0xFE`). `matchH2` сравнивает H2 со всеми 8 ctrl-байтами **одной SWAR/SIMD-операцией**, возвращая bitset совпадений — без цикла и ветвления.

**3. H1 vs H2?**

- Хэш режется: `H1 = hash >> 7` (верхние 57 бит) выбирает стартовую группу, `H2 = hash & 0x7f` (нижние 7 бит) лежит в ctrl для быстрого отсева. Таблицу в directory выбирают старшие `globalDepth` бит хэша. Ложное совпадение 1/128.

**4. Линейное или квадратичное зондирование?**

- **Квадратичное** (триангулярное): смещения растут на 1, 2, 3, … При power-of-two числе групп обходит все группы без повторов и всегда заканчивается на группе с пустым слотом.

**5. Зачем tombstones?**

- Поиск останавливается на пустом слоте. Удаляя из полностью занятой группы, нельзя ставить `empty` — оборвём чужие probe-цепочки. Ставим `deleted` (tombstone): не матчится, но и не обрывает поиск. Чистятся при росте; малые map их не имеют.

**6. Чем рост отличается от старого hmap?**

- Раньше — инкрементальная эвакуация всего map (lookup проверял два массива). Теперь — `rehash` одной таблицы целиком (double до 1024 слотов, дальше split на две), а «инкрементальность» обеспечивает **directory** из независимых таблиц (extendible hashing): растёт только перегруженная таблица.

**7. Раскладка памяти — чем отличается от hmap?**

- `hmap` клал ключи блоком и значения блоком (меньше padding). Swiss **чередует** `{key, elem}` по слотам (locality — ключ и значение в одном cache-line), ценой возможного padding для «неудобных» пар типов.

**8. Что НЕ изменилось?**

- Всё пользовательское: случайный порядок итерации, паника при записи в nil map, `fatal` при concurrent-доступе, запрет `&m["key"]`, `nil` как zero value, отсутствие shrink. Никаких breaking changes.
