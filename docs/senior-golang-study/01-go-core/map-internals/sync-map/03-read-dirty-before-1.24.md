Эта глава описывает конкретно Go 1.23 — последнюю версию `sync.Map` с `read`, `dirty`, `misses` и promotion. Она нужна для чтения старых статей и профилей, анализа сервисов на прежнем toolchain и interview-вопросов с явно указанной версией.

## К какой версии относится глава

Базовая модель `read`/`dirty` использовалась с появления `sync.Map` в Go 1.9 до Go 1.23 включительно. Но набор публичных методов за это время расширялся:

| Версия | Изменение API |
| --- | --- |
| Go 1.9 | Появились `Map`, `Load`, `Store`, `LoadOrStore`, `Delete`, `Range` |
| Go 1.15 | Добавлен `LoadAndDelete` |
| Go 1.20 | Добавлены `Swap`, `CompareAndSwap`, `CompareAndDelete` |
| Go 1.23 | Добавлен `Clear` |
| Go 1.24 | Реализация заменена на concurrent hash-trie |

Поэтому фраза «до Go 1.24» описывает семейство реализации, а код и пошаговые ветви ниже привязаны к исходнику Go 1.23. Нельзя автоматически переносить весь набор методов на Go 1.9.

Между Go 1.23 и Go 1.24 публичный контракт `sync.Map` и гарантии memory model не изменились: поменялось внутреннее хранилище. В Go 1.26 `sync.Map` уже является тонкой обёрткой над `internal/sync.HashTrieMap`.

## Ментальная модель

Главная идея — **два индекса на одни и те же `entry` вместо одного индекса под общей блокировкой**:

```text
read   -> быстрый индекс, читается без mutex
             |
             |  оба указывают на одни и те же *entry
             v
dirty  -> рабочий индекс, доступен только под mu
```

Здесь важно различать две вещи:

| Уровень | Чем представлен | Что означает |
| --- | --- | --- |
| Членство в индексе | Наличие `key -> *entry` в `read.m` или `dirty` | По какому пути можно найти ячейку |
| Логическое присутствие ключа | Состояние `entry.p` | Возвращает ли `Load` пользовательское значение |

`Delete` ключа из `read` меняет логическое состояние `entry.p`, но не удаляет `key -> *entry` из самого индекса. Поэтому такая операция может обойтись без общего `mu`.

Общий `mu` нужен там, где меняются структуры `read`/`dirty`, счётчик `misses` или связь между ними. Состояние уже опубликованной `entry` часто меняется атомарно без общей блокировки.

Отсюда следует главное ограничение модели: она оптимизирует **устоявшийся индекс ключей**. Поток новых ключей постоянно возвращает операции на медленный путь.

## Что хранит структура

Упрощённо структура выглядит так:

```go
type Map struct {
	mu     Mutex
	read   atomic.Pointer[readOnly]
	dirty  map[any]*entry
	misses int
}

type readOnly struct {
	m       map[any]*entry
	amended bool // true: промах по read нужно перепроверить в dirty
}

type entry struct {
	p atomic.Pointer[any]
}

var expunged = new(any)
```

| Поле | Зачем нужно |
| --- | --- |
| `mu` | Общий mutex; защищает изменения структуры `dirty`, счётчик `misses` и публикацию нового `read` |
| `read` | Индекс для преимущественно читаемой нагрузки, доступный через атомарный указатель без блокировки |
| `dirty` | Рабочий индекс под `mu`: новые ключи и все не-`expunged` ячейки из `read` на момент создания |
| `misses` | Число операций чтения, которым пришлось искать ключ через `dirty` |
| `amended` | Консервативный признак того, что промах по `read` нужно перепроверить в `dirty` |
| `expunged` | Специальный указатель-маркер удалённой ячейки, исключённой из `dirty` |

Важно, что оба индекса хранят не значения, а `*entry` — указатели на общие ячейки:

```text
read.m["a"] ──┐
              ├──> entry{ p -> value }
dirty["a"] ───┘
```

Поэтому обновление состояния существующей ячейки видно через любой индекс сразу: меняется `entry.p`, а не сами map. Именно это делает возможными быстрые пути записи и удаления.

`dirty` не является «копией всех ключей из `read`». При создании в него попадают только не-`expunged` ячейки. После удаления ключа, который существует только в `dirty`, запись физически удаляется именно из этого индекса.

## Что означает amended

`amended` («дополненный») отвечает на практический вопрос: **можно ли считать промах по `read` окончательным?**

| Значение | Что гарантировано | Что делает `Load` при промахе по `read` |
| --- | --- | --- |
| `false` | В `dirty` нет ключей сверх `read` | Сразу возвращает miss, `mu` не берётся |
| `true` | В `dirty` могут быть дополнительные ключи | Берёт `mu`, перепроверяет `read`, затем смотрит `dirty` |

Слово «могут» важно. Флаг устанавливается, когда появляется первый новый ключ вне `read`, но не сбрасывается при обычном удалении такого ключа. До следующей promotion `amended` может оставаться консервативным `true`, даже если дополнительных ключей в `dirty` уже не осталось.

Без этого флага каждый промах по `read` требовал бы общей блокировки. `amended == false` даёт доказанный miss без `mu`; `true` требует медленного пути.

Жизненный цикл флага замкнут на promotion — событие, при котором `dirty` целиком становится новым `read` (разобрано ниже):

```text
promotion: read = readOnly{m: dirty}      amended = false (zero value)
    |
    | Store ключа, которого нет ни в read, ни в dirty
    v
read = readOnly{m: прежний map, amended: true}      dirty пересобран из read
    |
    | misses >= len(dirty)
    v
снова promotion -> amended = false
```

Устанавливает флаг только добавление новой индексной записи, которой нет ни в `read`, ни в `dirty`. `Delete` и перезапись существующей `entry` не меняют структуру `read`, поэтому сами по себе флаг не сбрасывают и не устанавливают.

Важная деталь реализации: `readOnly` иммутабелен и публикуется целиком через атомарный указатель. «Взвести `amended`» означает собрать новую структуру и атомарно заменить указатель, а не поменять поле у существующей:

```go
if !read.amended {
	// Первый новый ключ после promotion: собрать dirty и пометить read неполным.
	m.dirtyLocked()
	m.read.Store(&readOnly{m: read.m, amended: true})
}
m.dirty[key] = newEntry(value)
```

Внутренняя map с ключами при этом остаётся той же — меняется только обёртка. Поэтому читающая goroutine никогда не видит `readOnly` в промежуточном состоянии.

## Состояния entry и expunged

Указатель внутри `entry` кодирует три состояния:

| Состояние `entry.p` | Смысл | Как читается через `Load` |
| --- | --- | --- |
| Указатель на value | Ключ присутствует, значение актуально | Возвращает значение |
| `nil` | Ключ логически удалён; `dirty` либо ещё нет, либо он указывает на ту же ячейку | Возвращает «отсутствует» |
| `expunged` | Ключ удалён, `dirty` существует, но этой ячейки в нём нет | Возвращает «отсутствует» |

Для чтения `nil` и `expunged` неразличимы — оба означают «ключа нет». Разница проявляется только при записи: в `nil`-ячейку можно вернуть значение дешёвым CAS, а `expunged` требует общего mutex.

Переход в `expunged` происходит ровно в одном месте — при пересборке `dirty` из `read`. Логически удалённые ячейки в новый `dirty` не копируются:

```text
read:   A -> value      B -> nil          C -> value
                            |
                            | пересборка dirty: nil -> expunged, в dirty не попадает
                            v
read:   A -> value      B -> expunged     C -> value
dirty:  A -> value                        C -> value
```

Отсюда асимметрия: такой ключ как индексная запись присутствует в `read`, но отсутствует в `dirty`. Поэтому `amended` связан только с возможностью дополнительных ключей в `dirty`; он не обещает, что оба индекса содержат одинаковые наборы записей.

Полный жизненный цикл ячейки:

```text
value ──Delete──> nil ──Store через CAS-loop──> value
                  |
                  +──dirtyLocked──> expunged
                                        |
                                        +──под mu: expunged -> nil -> value
```

## Сквозной пример жизненного цикла

Пусть после предыдущей promotion состояние выглядит так:

```text
read:
  "a" -> entry(value=1)
  "b" -> entry(value=2)

dirty   = nil
amended = false
misses  = 0
```

Пример выполняется последовательно, чтобы показать состояния. В реальном коде те же переходы защищены атомарными операциями и `mu`.

### Шаг 1. `Store("c", 3)`

Ключа `"c"` нет ни в `read`, ни в `dirty`, а `amended == false`. Это первый новый ключ после promotion:

1. `dirtyLocked` создаёт `dirty` и поверхностно копирует туда не-`expunged` ячейки из `read`.
2. Публикуется новый `readOnly` с прежней `read.m`, но `amended: true`.
3. Новая `entry("c", 3)` добавляется только в `dirty`.

```text
read:
  "a" -> entry(value=1)
  "b" -> entry(value=2)

dirty:
  "a" -> та же entry(value=1)
  "b" -> та же entry(value=2)
  "c" -> entry(value=3)

amended = true
misses  = 0
```

### Шаг 2. Три раза `Load("c")`

Каждый вызов промахивается по `read`, видит `amended == true`, берёт `mu` и находит `"c"` в `dirty`.

`misses` считает не только отсутствующие ключи. Здесь ключ существует, но каждый поиск всё равно является miss относительно быстрого индекса:

```text
после первого Load: misses = 1
после второго Load: misses = 2
после третьего Load: misses = 3
```

Сейчас `len(dirty) == 3`. Третий вызов выполняет promotion:

```text
read    = прежний dirty
dirty   = nil
amended = false
misses  = 0
```

Теперь `"c"` читается через быстрый `read`.

### Шаг 3. `Delete("b")`

`"b"` находится в `read`, поэтому общий `mu` не нужен. CAS-loop заменяет указатель `entry.p` на `nil`:

```text
read:
  "a" -> entry(value=1)
  "b" -> entry(nil)       // логически отсутствует, но индексная запись жива
  "c" -> entry(value=3)

dirty   = nil
amended = false
```

`Load("b")` уже возвращает miss, хотя `read.m` всё ещё содержит ключ `"b"`.

### Шаг 4. `Store("d", 4)`

Это следующий новый ключ. `dirtyLocked` снова строит `dirty` из `read`:

- `"a"` и `"c"` копируются как общие `*entry`;
- `"b"` атомарно переводится `nil -> expunged` и не попадает в `dirty`;
- `"d"` добавляется новой ячейкой.

```text
read:
  "a" -> entry(value=1)
  "b" -> entry(expunged)
  "c" -> entry(value=3)

dirty:
  "a" -> та же entry(value=1)
  "c" -> та же entry(value=3)
  "d" -> entry(value=4)

amended = true
```

### Шаг 5. `Store("b", 20)`

Быстрый путь находит `"b"` в `read`, но видит `expunged` и отказывается менять ячейку без общей блокировки.

Под `mu` выполняются три действия:

1. `unexpungeLocked` переводит `entry.p` из `expunged` в `nil`.
2. Та же `*entry` возвращается в `dirty["b"]`.
3. В `entry.p` записывается новое значение `20`.

После этого оба индекса снова приводят к одной живой ячейке:

```text
read["b"]  ──┐
             ├──> entry(value=20)
dirty["b"] ──┘
```

Этот пример показывает всю модель: новый ключ создаёт `dirty`, чтения по медленному пути приводят к promotion, `Delete` меняет логическое состояние без удаления индексной записи, а следующая пересборка превращает `nil` в `expunged`.

## Как выполняется Load

```text
Load(key)
  |
  +-- key есть в read -> прочитать entry без общего mutex
  |
  +-- key нет, read.amended=false -> miss
  |
  +-- key нет, read.amended=true
         -> lock mu
         -> повторно проверить read
         -> посмотреть dirty
         -> misses++
```

Повторная проверка после lock обязательна: пока goroutine ждала mutex, другая goroutine могла выполнить promotion, и нужный ключ уже переехал в `read`. Без повторной проверки такое чтение ушло бы в `dirty`, который к этому моменту стал `nil`.

`misses` здесь означает промах по быстрому индексу, а не обязательно отсутствие ключа во всей map. Счётчик увеличивается и когда ключ успешно найден только в `dirty`, и когда его нет нигде.

Та же схема объясняет ramp-up, то есть прогрев: новый ключ сначала доступен только через общий `mu`, пока достаточное число поисков по медленному пути не приведёт к promotion. Поток отсутствующих ключей при `amended == true` тоже конкурирует за этот mutex.

## Как выполняется Store

Здесь ключевая асимметрия с `Load`: изменение уже существующей не-`expunged` ячейки обычно **не берёт mutex вообще**.

```text
Store(key, value)
  |
  +-- key есть в read и не expunged
  |      -> CAS-loop указателя внутри entry, готово   (без mu)
  |
  +-- иначе -> lock mu, перепроверить read, дальше три случая:
         |
         +-- key в read, но expunged
         |      -> вернуть ячейку в dirty, затем записать значение
         |
         +-- key только в dirty
         |      -> записать значение в его entry
         |
         +-- key нигде не найден
                -> если !amended: собрать dirty из read и взвести amended
                -> dirty[key] = новая entry
```

Быстрый путь возможен именно потому, что оба индекса указывают на одни и те же ячейки. Меняется атомарное состояние `entry.p`, а структуры индексных map не трогаются:

```go
func (e *entry) trySwap(i *any) (*any, bool) {
	for {
		p := e.p.Load()
		if p == expunged {
			return nil, false // ячейка выброшена из dirty — нужен медленный путь
		}
		if e.p.CompareAndSwap(p, i) {
			return p, true
		}
	}
}
```

`trySwap` является CAS-loop, а не гарантированно одним CAS: конкурентное обновление может заставить цикл повториться. При этом общий `mu` всё равно не берётся.

Единственное состояние `read`-ячейки, которое обязательно уводит `Store` на медленный путь, — `expunged`. Такая ячейка отсутствует в `dirty`, и вернуть её туда без `mu` нельзя.

Стоимость сильно различается по ветвям:

| Ветвь | Блокировка | Стоимость |
| --- | --- | --- |
| Ключ в `read`, не `expunged` | Нет | CAS-loop над `entry.p` |
| Ключ в `read`, `expunged` | Есть | `expunged -> nil`, вставка в `dirty`, atomic swap |
| Ключ только в `dirty` | Есть | Поиск в map + atomic swap |
| Ключ новый, `amended == true` | Есть | Вставка в `dirty` |
| Ключ новый, `amended == false` | Есть | **`O(N)`**: пересборка всего `dirty` из `read` |

Последняя строка — самая дорогая операция во всей реализации, и платит её та goroutine, которой не повезло записать первый новый ключ после promotion.

`Store` в Go 1.23 — тонкая обёртка над `Swap`. Другие методы используют ту же пару быстрого и медленного путей, но детали различаются. Например, `LoadOrStore` и `CompareAndSwap` засчитывают `miss`, когда нашли ключ только через `dirty`, а `Swap` в своей ветке для `dirty` счётчик не увеличивает.

## Как выполняется Delete

```text
Delete(key)
  |
  +-- key есть в read
  |      -> CAS-loop указателя в nil, готово          (без mu)
  |         запись остаётся в read и, если dirty существует, также в dirty
  |
  +-- key нет в read, amended=false -> ключа нет нигде, делать нечего
  |
  +-- key нет в read, amended=true
         -> lock mu, перепроверить read
         -> delete(dirty, key)        физическое удаление из map
         -> misses++
```

Принципиально это два разных удаления:

| Где живёт ключ | Что делает `Delete` | Судьба ячейки |
| --- | --- | --- |
| В `read` | CAS-loop `entry.p` в `nil` | Индексная запись остаётся в `read`; значение может стать доступно GC, но ключ и `entry` пока удерживаются |
| Только в `dirty` | `delete(m.dirty, key)` под `mu` | Ключ исчезает сразу, дополнительно засчитывается `miss` |

В первом случае нет фиксированного обещания «ещё два шага — и память освобождена». Путь зависит от состояния `dirty` в момент удаления:

- если `dirty == nil`, следующая `dirtyLocked` переводит `nil -> expunged` и не копирует ячейку; последующая promotion убирает её из нового `read`;
- если `dirty` уже содержит эту ячейку, она остаётся там с `p == nil` и может сначала попасть в ближайшую promotion; тогда для полного удаления понадобятся ещё одна пересборка `dirty` и следующая promotion.

До исчезновения из `read` память под ключ и `entry` удерживается, даже если прежнее значение уже доступно GC. Поэтому поток создания и удаления короткоживущих ключей может удерживать служебные объекты заметно дольше логического времени жизни записи.

`Delete` реализован через `LoadAndDelete` и отличается лишь тем, что игнорирует возвращённое прежнее значение.

## Что означает promotion

Если `misses >= len(dirty)`, происходит promotion — `dirty` становится новым `read`:

```text
before:
read  -> старый быстрый индекс
dirty -> рабочий индекс с дополнительными ключами под mu

promotion:
read  = dirty
dirty = nil
misses = 0

after:
read  -> актуальный быстрый индекс
```

Сама promotion выполняется за `O(1)`: реализация не копирует все `entry`, а публикует существующую map `dirty` внутри нового `readOnly`. После этого `dirty` обнуляется.

Цена `O(N)` возникает в другом месте — когда следующий новый ключ вызывает `dirtyLocked` и поверхностно копирует подходящие `*entry` из `read` в новую map.

Порог `misses >= len(dirty)` — эвристика амортизации. Каждый поиск по медленному пути уже платит за общий `mu`; после примерно `N` таких обращений дальнейший ramp-up дороже, чем перейти к быстрому `read` и считать стоимость следующей пересборки `dirty` окупленной этими промахами.

Это не точное равенство наносекунд: стоимость поиска, конкуренции за mutex и копирования указателей на `entry` различается. `len(dirty)` даёт простой размерный порог. Если ключи, находившиеся только в `dirty`, удаляются, `len(dirty)` уменьшается, поэтому promotion может наступить раньше относительно первоначального размера.

Обратная сторона: когда после promotion снова появляется первый новый ключ, `dirty` создаётся заново копированием подходящих `entry` из `read`.

```text
Store нового ключа сразу после promotion:

read (N ключей) ──копирование──> новый dirty (N ключей) + 1 новый ключ
                    O(N) под mu
```

Поэтому повторяющийся цикл «первый новый ключ → `O(N)`-пересборка → чтения по медленному пути → promotion» является неблагоприятным сценарием. Конкретная цена зависит от размера map, распределения ключей и конкуренции за блокировку.

## Как Range влияет на promotion

Публичная семантика `Range` разобрана в [главе про контракт](./01-public-contract.md). Здесь важна историческая деталь реализации: если `read.amended == true`, `Range` немедленно делает `dirty` новым `read`, не ожидая `misses >= len(dirty)`.

Упрощённый путь:

```text
Range
  |
  +-- amended=false -> обходить read
  |
  +-- amended=true
         -> lock mu
         -> перепроверить read.amended
         -> read = dirty
         -> dirty = nil
         -> misses = 0
         -> unlock mu
         -> обходить новый read без общего lock
```

Почему это разумно: полный `Range` и так собирается посетить `O(N)` ячеек. После немедленной promotion будущие `Load` не платят ramp-up за ключи, которые находились только в `dirty`.

Promotion внутри `Range`, как и обычная promotion, не копирует указатели на `entry` по одному. Callback вызывается уже без общего `mu`, поэтому он может обращаться к той же `sync.Map`. При этом публичной гарантии согласованного снимка состояния всё равно нет.

## Как работает Clear

`Clear` появился именно в Go 1.23. В read/dirty реализации он не просто заменяет один корневой указатель, как современный hash-trie:

```text
Clear
  |
  +-- len(read.m) == 0 и amended == false -> return
  |
  +-- иначе
         -> lock mu
         -> опубликовать пустой readOnly
         -> clear(dirty)
         -> misses = 0
         -> unlock mu
```

Условие быстрого выхода проверяет состояние индексов, а не перебирает логически живые значения. Поэтому `Clear` всё равно может зайти под `mu`, если все значения уже удалены, но `read.m` ещё удерживает индексные записи с `nil` или `expunged`.

Если `dirty` не равен `nil`, встроенная функция `clear(m.dirty)` очищает его внутреннее хранилище. Поэтому старый `Clear` не сводится к одной атомарной замене указателя: объём непосредственной работы зависит от размера выделенной map `dirty`. Публичный API не гарантирует конкретную сложность.

Сброс `misses` нужен, чтобы накопленный ramp-up прежнего состояния не влиял на уже пустую map. Если `dirty` существовал, после `clear` он остаётся выделенной пустой map и может быть переиспользован следующей записью; новый ключ устанавливает `amended` и начинает новый жизненный цикл без обязательного повторного выделения памяти.

## Где эта модель работает плохо

| Профиль доступа | Что происходит | Почему |
| --- | --- | --- |
| Write-once, read-many | Хорошо после ramp-up | После promotion ключи находятся в `read`, чтения идут без блокировки |
| Частая перезапись устоявшихся ключей | Обычно хорошо | Для не-`expunged` entry в `read` работает CAS-loop без общего mutex |
| Непересекающиеся ключи у разных goroutines | Помогает частично | Чтения дешёвые, но любой новый ключ идёт через общий `mu` |
| Постоянный поток новых ключей | Плохо | Каждый новый ключ — общий mutex, а `dirty` регулярно пересобирается за `O(N)` |
| Много поисков по медленному пути | Плохо при `amended == true` | И существующий ключ только из `dirty`, и отсутствующий ключ требуют общего mutex |
| Короткоживущие ключи (cache с вытеснением) | Часто плохо | Поток новых ключей и отложенное исчезновение устаревших `entry` из `read` |
| Частый `Range` при `amended == true` | Меняет жизненный цикл | Каждый такой обход может немедленно выполнить promotion |

Общая формулировка: модель оптимизирует **стабильную структуру индекса**, а не частое появление и исчезновение ключей.

## Почему hash-trie заменил эту модель

Release notes Go 1.24 выделяют два результата новой реализации: изменения непересекающихся наборов ключей намного реже конкурируют на больших map, а чтениям больше не нужен ramp-up до низкой конкуренции.

Read/dirty хорошо обслуживает устоявшиеся ключи, особенно в сценарии write-once/read-many. Но поток новых ключей и частые изменения чаще приводят к:

- общему `mu`;
- поиску по медленному пути в `dirty`;
- promotion;
- `O(N)` созданию нового `dirty`.

Ключевая проблема — **глобальность**. Все перечисленные механизмы относятся к map целиком: один mutex, один счётчик `misses`, одно событие promotion, одна пересборка всего `dirty`. Две goroutines, работающие с совершенно разными ключами, всё равно встречаются на этих общих точках.

[Hash-trie](./02-hash-trie-since-1.24.md) убирает этот глобальный жизненный цикл: блокировка находится в отдельном узле дерева, а изменения разных ветвей идут независимо. Промах определяется по `nil` в дочернем указателе и не зависит ни от какого флага.

| | read/dirty до Go 1.24 | hash-trie с Go 1.24 |
| --- | --- | --- |
| Хранилище | Два map на общие `*entry` | Дерево с 16 ветвями на уровень |
| Гранулярность блокировки | Один общий `mu` на всю map | Mutex в каждом indirect node |
| Стоимость промаха | Без блокировки только при `amended == false` | Всегда без mutex узла |
| Реакция на новые ключи | Общий mutex, затем `O(N)` пересборка `dirty` | Локальная публикация новой `entry` или поддерева |
| Периодическая общая работа | Promotion и последующая пересборка `dirty` | Отсутствует |

Поэтому профиль современной `sync.Map` нельзя объяснять через `misses` и promotion: этих сущностей больше не существует.

## Interview-ready answer

**1. К какой версии относится модель read/dirty?**

- Точный код — Go 1.23, последняя версия перед переходом на hash-trie.
- Семейство — основная модель использовалась в Go 1.9–1.23, но публичные методы добавлялись постепенно.
- Структура — атомарный `read`, рабочий `dirty` под общим `mu`, общие `*entry` и счётчик `misses`.

**2. Что означает `amended`?**

- `false` — промах по `read` окончателен: дополнительных ключей в `dirty` нет.
- `true` — ключ может находиться только в `dirty`, поэтому нужен медленный путь под `mu`.
- Консервативность — после удаления ключа, находившегося только в `dirty`, флаг может оставаться `true` до promotion, даже если дополнительных ключей уже нет.

**3. Какие операции обходятся без общего mutex?**

- Чтение ключа, лежащего в `read`, — атомарная загрузка указателя.
- `Store` не-`expunged` ячейки из `read` — CAS-loop над `entry.p`.
- `Delete` ячейки из `read` — CAS-loop, переводящий `entry.p` в `nil`.
- Общее правило — `mu` нужен для структур `read`/`dirty`; состояние существующей `entry` часто меняется атомарно.

**4. Когда `Store` попадает на медленный путь?**

- `expunged` — entry отсутствует в `dirty`, поэтому её нужно вернуть туда под `mu`.
- Ключ только в `dirty` — поиск и атомарная замена выполняются под общим `mu`.
- Новый ключ — добавляется в `dirty`; первый новый ключ при `amended == false` сначала пересобирает `dirty` из `read` за `O(N)`.

**5. Что происходит при `Delete`?**

- Ключ в `read` — указатель ячейки атомарно переводится в `nil`; индексная запись остаётся в `read` и, если `dirty` уже существует, в нём тоже.
- Ключ только в `dirty` — удаляется из map под `mu`, дополнительно засчитывается `miss`.
- Освобождение памяти — отложено и зависит от текущего жизненного цикла; может понадобиться пересборка `dirty` и одна или несколько promotions.

**6. Что такое promotion и когда она происходит?**

- Условие — `misses >= len(dirty)`.
- Действие — существующая map `dirty` публикуется как новый `read`, затем `dirty = nil` и `misses = 0`.
- Стоимость promotion — `O(1)`, без копирования всех `entry`.
- Отложенная цена — первый новый ключ после promotion пересобирает `dirty` из `read` за `O(N)`.

**7. Чем `nil` отличается от `expunged` в entry?**

- Для чтения — ничем, оба означают «ключа нет».
- `nil` — ключ логически удалён; его можно воскресить CAS-loop без общего `mu`.
- `expunged` — ячейка не скопирована в `dirty` при его пересборке, поэтому запись в такой ключ обязана взять `mu`.
- Следствие — `read` может содержать индексные записи, которых нет в `dirty`.

**8. Что особенного делают `Range` и `Clear`?**

- `Range` — при `amended == true` немедленно выполняет promotion, не ожидая порога `misses`.
- Callback — вызывается без общего `mu`; согласованного снимка состояния по-прежнему нет.
- `Clear` — под `mu` публикует пустой `read`, очищает `dirty` и сбрасывает `misses`.
- Версия — `Clear` появился только в Go 1.23.

**9. Почему реализацию заменили?**

- Причина — все узкие места глобальны: один mutex, один `misses`, одна promotion и периодическая `O(N)`-пересборка `dirty`.
- Итог — goroutines с непересекающимися ключами всё равно встречаются в этих общих точках.
- Go 1.24 — release notes отмечают меньшую конкуренцию при изменениях непересекающихся ключей и отсутствие ramp-up для дешёвых чтений.
- Замена — hash-trie с блокировкой на уровне узла и промахом без mutex узла.

**10. Что из этой модели актуально сейчас?**

- Актуально — идея разделять дешёвый путь чтения и дорогой путь изменения структуры индексов.
- Не актуально для Go 1.24–1.26 — `read`, `dirty`, `misses`, `amended`, `expunged` и promotion.
- На собеседовании — уточнить версию, прежде чем описывать внутреннее устройство.
