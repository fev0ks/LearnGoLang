# CRUD над sync.Map с разбором дерева

Запускаемая программа со всеми методами `sync.Map` и построчным разбором того, что при каждом вызове происходит внутри hash-trie. Теория — в [Concurrent hash-trie с Go 1.24](../../02-hash-trie-since-1.24.md) и [публичном контракте](../../01-public-contract.md).

## Запуск

```bash
cd docs/senior-golang-study/01-go-core/map-internals/sync-map/examples/crud
go run .
```

```bash
go run -race .
```

Race detector здесь не формальность: программа в последней секции запускает 100 goroutines и показывает паттерн со счётчиком на ключ. Если переписать его через прямую мутацию загруженного объекта, `-race` сразу это поймает.

## Что показывает программа

| Секция | Методы | Что важно заметить |
| --- | --- | --- |
| CREATE | `Store`, `LoadOrStore` | второй `LoadOrStore` с тем же ключом наш объект не сохраняет, а возвращает существующий |
| READ | `Load` | сохранённый `nil` возвращается с `ok=true`, поэтому отсутствие проверяют по `ok` |
| UPDATE | `Store`, `Swap` | `Swap` отсутствующего ключа работает как вставка и возвращает `loaded=false` |
| UPDATE поля | `CompareAndSwap` | read-modify-write цикл: копия, CAS, повтор при вмешательстве |
| DELETE | `Delete`, `LoadAndDelete`, `CompareAndDelete` | CAS-удаление сравнивает указатель, а не содержимое структуры |
| LIST | `Range` | порядок не определён, `Len` отсутствует, счётчик приходится вести вручную |
| Конкурентный доступ | `LoadOrStore` + счётчик | 100 goroutines, 300 инкрементов, ни одного потерянного |

## Что происходит в дереве

Условные хеши для трёх ключей. Показаны только старшие нибблы, остальные на пример не влияют:

```text
"u1" -> 0x3A9F_...     нибблы: 3, A, 9, ...
"u2" -> 0x321C_...     нибблы: 3, 2, 1, ...
"u3" -> 0xB704_...     нибблы: B, 7, ...
```

Номер ветви на каждом уровне — очередные четыре бита: `(hash >> hashShift) & 0xF`.

### Store("u1") в пустую map

`root.children[3]` пуст, поэтому ячейка публикуется прямо здесь, без создания уровней:

```text
root (16 ветвей)
 └── [3] -> entry{"u1", *User}
```

Дерево не имеет фиксированной глубины: ячейки живут максимально высоко, уровни появляются только там, где нужны.

### Store("u3")

Старший ниббл `B` = 11, ветвь свободна. Два ключа — дерево всё ещё глубиной один уровень:

```text
root
 ├── [3]  -> entry{"u1", ...}
 └── [11] -> entry{"u3", ...}
```

### Store("u2") — здесь появляется уровень

Старший ниббл тоже `3`, но в `root.children[3]` уже лежит `entry{"u1"}`. Ключи разные, одной ячейкой не обойтись. Смотрим следующий ниббл:

```text
"u1": 3 A ...   -> ветвь A (10)
"u2": 3 2 ...   -> ветвь 2
      ^ ^
      | └─ здесь различаются
      └─── здесь совпали
```

Создаётся новый промежуточный узел, обе ячейки раскладываются по второму нибблу, и **только потом** указатель на готовый узел атомарно подставляется в `root.children[3]`:

```text
root
 ├── [3]  -> indirect
 │            ├── [2]  -> entry{"u2", ...}
 │            └── [10] -> entry{"u1", ...}
 └── [11] -> entry{"u3", ...}
```

Порядок принципиален: читатель, идущий по дереву в этот момент, видит либо старый `entry{"u1"}`, либо уже собранный узел. Недостроенного состояния не существует.

Если бы совпал и второй ниббл, шаг повторился бы — ещё уровень, ещё четыре бита. Так до первого различия, а при совпадении всех 64 бит — цепочка `overflow`.

### Load("u2")

```text
hash("u2") = 0x321C...
   |
   | старший ниббл 3
   v
root.children[3]  -> indirect        (atomic load)
   |
   | следующий ниббл 2
   v
children[2]       -> entry           (atomic load)
   |
   v
"u2" == "u2"      -> вернуть значение
```

Ни одного мьютекса, только атомарные чтения указателей.

### Load("u-404")

Пусть старший ниббл `5`. `root.children[5] == nil` — промах на первом шаге, без спуска и без блокировки. Никакого глобального флага вроде `amended` из [прежней реализации](../../03-read-dirty-before-1.24.md) здесь нет: `nil` в ветви сам по себе означает «здесь ничего нет».

### Swap("u2", новое значение)

```text
1. спуститься к слоту без блокировки          -> children[2] узла indirect
2. взять mutex ИМЕННО ЭТОГО indirect          <- не root и не всей map
3. перечитать слот и проверить, что узел жив  -> состояние могло измениться
4. собрать НОВУЮ entry{"u2", новое значение}
5. атомарно заменить указатель в слоте
6. отпустить mutex
```

Шаг 4 — не мелочь: ячейка заменяется целиком, поле внутри неё не мутируется, поэтому читатель видит либо старую ячейку полностью, либо новую полностью.

Шаг 2 — то, ради чего дерево и нужно: запись в `"u1"` и запись в `"u3"` берут разные мьютексы и друг друга не ждут.

Шаг 3 обязателен, потому что между шагами 1 и 2 другая goroutine могла заменить ячейку, углубить ветвь или удалить узел. Если проверка не прошла, блокировка отпускается и поиск начинается заново.

### Delete("u3")

```text
root.children[11] -> entry{"u3"}
   |
   | взять mutex root (он и есть parent этого слота)
   v
записать nil в children[11]
```

Если промежуточный узел стал полностью пустым, он тоже убирается, и очистка может пойти вверх к корню. Удаляемый узел помечается флагом `dead`, чтобы goroutine, успевшая схватить на него указатель, заметила устаревшую ветвь и начала операцию заново.

Контраст с реализацией до Go 1.24: здесь `Delete` освобождает слот сразу, без `nil`-ячеек, `expunged` и ожидания promotion.

## Три правила, из которых выводится остальное

1. **Ячейка лежит на минимальной достаточной глубине.** Уровень добавляется только при коллизии префикса hash, а не заранее.
2. **Публикация всегда атомарна и всегда готовым куском.** Новая ячейка или целое поддерево подставляются одним `Store` указателя, поэтому читателю не нужна блокировка.
3. **Блокируется узел, а не map.** Mutex лежит в каждом промежуточном узле, и записи в разные ветви идут параллельно.

## Главная ошибка

`CompareAndSwap` с `*User` сравнивает **указатели**, а не содержимое. Поэтому «обновить поле» — это не одна операция, а цикл:

```go
for {
	cur, ok := users.Load("u1")
	if !ok {
		break
	}
	old := cur.(*User)

	updated := *old            // копия, общий объект не мутируется
	updated.Email = "new@example.com"

	if users.CompareAndSwap("u1", old, &updated) {
		break // между Load и CAS никто не вмешался
	}
	// вмешались — повторить с актуальным значением
}
```

Если вместо этого написать `old.Email = "..."`, получится гонка: `sync.Map` защищает ячейку с указателем, но не поля объекта за ним. Разбор — в [публичном контракте](../../01-public-contract.md), раздел про memory model.

## Что попробовать

1. Заменить CAS-цикл в `updateField` на прямую мутацию `old.Email = email`, добавить конкурентных читателей и запустить с `-race`.
2. Убрать копию (`updated := *old`) и мутировать `old` перед CAS — CAS пройдёт, но объект успеет измениться до публикации.
3. Сохранить под одним ключом значения разных типов и посмотреть, где именно упадёт type assertion: ошибка появится только в runtime.
4. Вернуть `false` из callback в `Range` и убедиться, что обход прекращается, но стоимость вызова остаётся.
5. Посмотреть, как форма дерева меняется при росте числа ключей: [tree-shape](../tree-shape/).
