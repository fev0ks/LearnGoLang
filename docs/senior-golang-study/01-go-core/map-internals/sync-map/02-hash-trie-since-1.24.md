В Go 1.24 `sync.Map` перешла на concurrent 16-way hash-trie; описанное устройство сверено с исходником Go 1.26. Trie — дерево, в котором путь выбирается не символами ключа, а последовательными частями его hash.

Главная идея реализации:

```text
чтение: hash -> атомарный указатель -> атомарный указатель -> entry

изменение: найти parent -> заблокировать parent -> перепроверить -> заменить указатель
```

Чтение не берёт mutex узлов. Изменение блокирует тот внутренний узел, дочерний указатель которого требуется заменить.

---

## Граница между API и реализацией

Публичный контракт гарантирует:

- безопасные конкурентные вызовы методов;
- атомарность отдельной операции над одним ключом;
- memory-model связь между записью и чтением, которое увидело её результат;
- специальную семантику `Range`.

Публичный контракт не гарантирует:

- что внутри всегда будет hash-trie;
- количество дочерних slots;
- отсутствие allocations;
- конкретный алгоритм `Clear`;
- одинаковую latency каждого вызова.

Дальше описывается реализация Go 1.24–1.26. Старая конструкция `read`/`dirty` разобрана в [следующей исторической главе](./03-read-dirty-before-1.24.md).

## Публичная структура sync.Map

На уровне пакета `sync` структура очень мала:

```go
type Map struct {
	_ noCopy
	m isync.HashTrieMap[any, any]
}
```

`noCopy` помогает статическим анализаторам обнаруживать копирование после первого использования. Все пользовательские данные находятся в `m`.

Публичные методы делегируют работу внутренней map:

```go
func (m *Map) Load(key any) (any, bool) {
	return m.m.Load(key)
}

func (m *Map) Store(key, value any) {
	m.m.Store(key, value)
}
```

Отсюда важное разделение:

```text
sync.Map
├── задаёт публичный нетипизированный API
└── HashTrieMap[any, any]
    └── реализует хранение и конкурентный доступ
```

Параметры типов принадлежат внутренней реализации. Публичная `sync.Map` по-прежнему принимает `any`.

## Основные внутренние структуры

Ниже сохранены все поля, необходимые для понимания устройства. Названия функций вычисления hash и сравнения сокращены, а служебные методы и `unsafe`-преобразования не показаны:

```go
type HashTrieMap[K comparable, V any] struct {
	inited   atomic.Uint32
	initMu   Mutex
	root     atomic.Pointer[indirect[K, V]]
	keyHash  hashFunc
	valEqual equalFunc
	seed     uintptr
}

type node[K comparable, V any] struct {
	isEntry bool
}

type indirect[K comparable, V any] struct {
	node[K, V]
	dead     atomic.Bool
	mu       Mutex
	parent   *indirect[K, V]
	children [16]atomic.Pointer[node[K, V]]
}

type entry[K comparable, V any] struct {
	node[K, V]
	overflow atomic.Pointer[entry[K, V]]
	key      K
	value    V
}
```

Роли полей:

| Сущность или поле | Роль |
| --- | --- |
| `HashTrieMap.root` | Атомарный указатель на корневой `indirect` node |
| `keyHash` | Вычисляет hash ключа |
| `valEqual` | Сравнивает значения для CAS-операций |
| `seed` | Делает hash индивидуальным для экземпляра map |
| `node.isEntry` | Различает лист `entry` и внутренний `indirect` node |
| `indirect.children` | 16 возможных продолжений пути |
| `indirect.mu` | Защищает изменения дочерних slots этого узла |
| `indirect.dead` | Помечает удалённую ветвь, чтобы записывающая goroutine повторила поиск |
| `indirect.parent` | Позволяет удалить опустевшую ветвь снизу вверх |
| `entry.key/value` | Хранит пользовательскую пару |
| `entry.overflow` | Продолжает цепочку при полном совпадении hash |

`inited` и `initMu` нужны для ленивой инициализации. При первом обращении создаётся непустой root node, из type metadata берутся hash/equality functions и генерируется случайный `seed`.

## Как связаны node, indirect и entry

`children` хранит `atomic.Pointer[node]`, а не два разных типа указателей:

```text
atomic.Pointer[node]
        |
        +-- nil
        |
        +-- node{isEntry: true}
        |      └── это начало объекта entry
        |
        +-- node{isEntry: false}
               └── это начало объекта indirect
```

Поле `node` встроено первым и в `entry`, и в `indirect`. Текущая реализация проверяет `isEntry`, а затем через `unsafe.Pointer` интерпретирует адрес как нужный полный тип.

Это похоже на объединение с тегом (`tagged union`):

| `isEntry` | Реальный объект | Что делать при обходе |
| --- | --- | --- |
| `true` | `entry` | Сравнить полный ключ и вернуть значение |
| `false` | `indirect` | Взять следующие четыре bits hash и спуститься глубже |

`isEntry` устанавливается при создании узла и после публикации не меняется. Writer сначала полностью инициализирует объект, затем публикует указатель atomic store; поэтому reader, который получил этот указатель atomic load, видит готовый тег и остальные поля.

Без `node` невозможно объяснить, как один дочерний указатель представляет два вида узлов. Это центральная часть устройства, а не необязательная деталь.

Корень всегда является `indirect` node. Каждая позиция (`slot`) корня и более глубокого `indirect` node содержит:

- `nil`, если ветвь пуста;
- `entry`, если путь уже приводит к листу;
- другой `indirect`, если ключи с общим префиксом hash пришлось разделить глубже.

## Как hash выбирает путь

Каждый `indirect` node содержит 16 slots. Четыре bits кодируют число от `0` до `15`, поэтому один уровень потребляет четыре bits hash:

```text
hash(key): [4 bits][4 bits][4 bits][4 bits]...
               |       |       |
root ----------+       |       |
    indirect ----------+       |
         indirect -------------+
              entry(key, value)
```

Для 64-bit hash возможно не более 16 выборов, для 32-bit — не более 8:

```text
64 bits / 4 bits per level = 16 levels
32 bits / 4 bits per level = 8 levels
```

Текущая реализация начинает со старших bits:

```go
index := (hash >> hashShift) & 0xF
```

`0xF` в binary — `1111`, поэтому маска оставляет четыре нужных bits.

Например:

```text
hash = 0xA37C...
       | ||
       | |+-- третий выбор: slot 7
       | +--- второй выбор: slot 3
       +----- root: slot A, то есть 10
```

Путь:

```text
root.children[10]
    -> children[3]
        -> children[7]
            -> ...
```

Hash использует случайный `seed`. Значения ниже выбраны только для объяснения: реальный hash конкретной строки нельзя считать стабильным между map или запусками процесса.

## Сквозной пример: Store, Load, update и Delete

Пусть учебные hashes имеют вид:

```text
hash("alice") = A3...
hash("bob")   = A7...
```

Первый фрагмент `A` совпадает, второй — различается.

### Шаг 0. Пустая map

После ленивой инициализации root уже существует, но его slots пусты:

```text
root: indirect
└── children[A] = nil
```

### Шаг 1. `Store("alice", 10)`

Операция выбирает root slot `A` и видит `nil`:

1. Берётся `root.mu`.
2. Позиция перепроверяется под блокировкой.
3. Создаётся полностью готовый `entry`.
4. Указатель публикуется через atomic store.

Состояние:

```text
root: indirect
└── children[A] -> entry{
        node.isEntry = true
        key = "alice"
        value = 10
    }
```

Дополнительный уровень пока не нужен: в этой ветви находится только один ключ.

### Шаг 2. `Store("bob", 20)`

Первый фрагмент hash снова выбирает root slot `A`, но там уже лежит `entry("alice")`. Keys не равны, поэтому один slot должен превратиться в subtree:

1. Берётся `root.mu`.
2. Состояние slot перепроверяется.
3. В стороне создаётся новый `indirect` node.
4. Следующие fragments `3` и `7` разводят entries по разным slots.
5. Только готовое subtree публикуется в `root.children[A]`.

До публикации:

```text
new branch: indirect
├── children[3] -> entry("alice", 10)
└── children[7] -> entry("bob", 20)
```

После публикации:

```text
root: indirect
└── children[A] -> node{isEntry: false}
                     └── branch: indirect
                         ├── children[3] -> entry("alice", 10)
                         └── children[7] -> entry("bob", 20)
```

Конкурентное чтение видит либо прежний целый `entry("alice")`, либо уже готовую ветвь с обоими ключами. Частично построенное subtree не публикуется.

### Шаг 3. `Load("bob")`

Reader не берёт mutex:

```text
hash("bob") = A7...

root.children[A]
    -> node.isEntry == false
    -> indirect.children[7]
    -> node.isEntry == true
    -> entry.key == "bob"
    -> value = 20
```

`isEntry` отвечает на вопрос «сравнивать ключ или спускаться глубже».

### Шаг 4. `Store("alice", 11)`

Writer проходит `A -> 3`, находит `entry("alice", 10)` и блокирует `branch.mu`, потому что изменяется `branch.children[3]`.

Поле `value` уже опубликованного `entry` не меняется на месте. Создаётся новый `entry`:

```text
до:    children[3] -> entry("alice", 10)
после: children[3] -> entry("alice", 11)
```

Reader видит старый целый entry либо новый целый entry. Старый объект позже освобождает GC.

### Шаг 5. `Delete("bob")`

Операция проходит `A -> 7`, берёт `branch.mu` и заменяет `children[7]` на `nil`:

```text
root
└── children[A] -> branch
                   ├── children[3] -> entry("alice", 11)
                   └── children[7] -> nil
```

Branch остаётся, потому что она не пуста. Текущая реализация удаляет полностью пустые ветви, но не обязана сжимать любой узел с одним оставшимся child.

## Как выполняется Load

Общий read path:

1. Лениво инициализировать map, если это первый вызов.
2. Вычислить `hash(key)` с seed конкретной map.
3. Атомарно прочитать root.
4. Взять очередные четыре bits и вычислить child index.
5. Атомарно прочитать дочерний указатель.
6. Если указатель равен `nil`, вернуть miss.
7. Если `isEntry == false`, перейти к следующему `indirect`.
8. Если `isEntry == true`, сравнить полный ключ.
9. При полном совпадении hash просмотреть overflow chain.

```text
Load(key)
   |
   v
hash(key, seed)
   |
   v
atomic root load
   |
   v
child by 4 hash bits
   |
   +-- nil ----------------> miss
   |
   +-- indirect -----------> next 4 bits
   |
   +-- entry -> key equal? -> value / miss
```

`Load` не берёт `indirect.mu`. Это не означает отсутствие синхронизации: atomic loads и атомарная публикация указателей формируют безопасный read path.

## Как выполняются изменения

`Store` во внутренней реализации вызывает `Swap`. `LoadOrStore`, `Swap`, успешный `CompareAndSwap` и удаления используют похожую оптимистичную схему:

1. Без блокировки узлов пройти trie и найти предполагаемые `parent`, `slot` и `node`.
2. Взять `parent.mu`.
3. Повторно прочитать slot и проверить `parent.dead`.
4. Если найденное состояние устарело, отпустить блокировку и начать поиск заново.
5. Подготовить новый entry, цепочку или subtree.
6. Атомарно заменить дочерний указатель.
7. Отпустить блокировку.

Перепроверка нужна из-за окна:

```text
goroutine A: нашла parent и slot
goroutine B: изменила или удалила ветвь
goroutine A: получила блокировку
```

Без повторного чтения A могла бы изменить detached node, который больше не доступен из актуального root.

### Почему блокировка локальная

Mutex находится в каждом `indirect` node:

```text
root
├── branch A -- mu A -- keys A...
└── branch B -- mu B -- keys B...
```

Изменения в глубоких независимых ветвях могут выполняться под разными блокировками. Но любые два `Store` не становятся автоматически независимыми:

- новые или неглубокие ключи могут конкурировать за `root.mu`;
- один горячий ключ использует один parent;
- ключи с общим префиксом hash дольше идут по одной ветви;
- CAS одного значения сериализуется с конкурирующими изменениями того же значения.

### Почему entry заменяется

Уже опубликованный `entry` читается без mutex. Изменять его `value` на месте было бы небезопасно для конкурентных читателей.

Вместо этого записывающая goroutine создаёт новый `entry` и меняет указатель:

```text
читатель 1 -> старый entry(value=10)

запись создаёт новый entry(value=11)
запись атомарно заменяет дочерний указатель

читатель 2 -> новый entry(value=11)
```

Цена — дополнительные allocations, pointers и работа GC.

## Как разрешаются коллизии

Нужно различать совпадение префикса и полное совпадение hash.

### Совпал только hash prefix

```text
hash A: A B C 1 ...
hash B: A B C 9 ...
        -----
        общий prefix
```

Реализация добавляет столько `indirect` nodes, сколько нужно до первого различающегося fragment:

```text
slot A
└── slot B
    └── slot C
        ├── slot 1 -> entry A
        └── slot 9 -> entry B
```

Сначала полностью строится новое subtree, затем его верхний указатель публикуется в старой позиции.

### Полностью совпал hash

Если два разных ключа имеют одинаковый hash целиком, углублять trie некуда. Entries связываются через `overflow`:

```text
slot -> entry B -> entry A -> nil
```

Hash приводит к голове цепочки, а точный ключ находится полным сравнением. При обновлении или удалении элемента цепочки соответствующий указатель заменяется атомарно под mutex родительского `indirect` node.

Полные коллизии обычно редки, но корректность от их отсутствия не зависит.

## Как работают Delete и Clear

### Delete

`Delete` делегирует работу `LoadAndDelete`:

1. Находит `entry` и его parent.
2. Берёт `parent.mu` и перепроверяет состояние.
3. Удаляет entry из slot или overflow chain.
4. Если parent стал пустым и не является root, удаляет пустую ветвь снизу вверх.

Перед отсоединением пустого `indirect` node устанавливается `dead`. Записывающая goroutine, которая ранее сохранила указатель на этот node, увидит метку после взятия блокировки и повторит поиск от актуального root.

Удаление не обязано сжимать непустой узел с одним child. Поэтому дерево после churn может сохранять промежуточные nodes до удаления последнего элемента ветви или до `Clear`.

### Clear

Текущая реализация создаёт новый пустой root и атомарно заменяет указатель:

```text
old root -> старое дерево

root.Store(new empty root)

new operations -> новое пустое дерево
old operations -> могут завершить работу со старым деревом
```

Непосредственная работа `Clear` близка к `O(1)` в этой реализации: entries не удаляются по одному. Память старого дерева освобождается GC после исчезновения последних ссылок у уже начавшихся операций.

Это деталь реализации Go 1.24–1.26, а не гарантия сложности публичного API.

## Практические последствия

| Механизм | Выгода | Цена |
| --- | --- | --- |
| Атомарный путь чтения | Читатели не конкурируют за mutex узла | Нужны атомарные указатели и публикация неизменяемых объектов |
| Блокировка `indirect` node | Изменения разных ветвей могут идти параллельно | Root и горячие ветви остаются точками contention |
| Замена entry целиком | Читатель видит согласованный объект | Allocation и последующая работа GC |
| 16 children на node | Меньше глубина дерева | Внутренний узел занимает больше памяти |
| Lazy expansion | Не строится полное дерево заранее | Первый конфликт префиксов создаёт subtree |
| Seed на экземпляр map | Путь не зависит только от ключа | Нельзя рассчитывать на стабильное устройство |
| Atomic root replacement в `Clear` | Быстрое логическое очищение | Физическое освобождение памяти отложено до GC |

Benchmark должен учитывать не только средний throughput, но и:

- p95/p99 latency;
- allocations при нагрузке с частыми обновлениями;
- CPU profile в `Load`, `Swap` и CAS;
- GC time и retained memory;
- распределение ключей и наличие горячего ключа;
- конкуренцию около root на небольшой map.

Практический benchmark вынесен в [отдельную главу](./04-practical-patterns.md).

## Типичные ошибки в объяснении

1. **Показывать `children` без `node`.** Тогда непонятно, как один указатель ведёт и на `entry`, и на `indirect`.
2. **Называть hash-trie публичной гарантией.** Это деталь реализации проверенных версий Go 1.24–1.26.
3. **Говорить «в `sync.Map` нет блокировок».** Блокировки есть у записывающих goroutines; обычный `Load` лишь не берёт их.
4. **Считать все записи независимыми.** Root, общий префикс и горячий ключ создают contention.
5. **Путать prefix collision с полной hash collision.** Первая создаёт дополнительные уровни, вторая — overflow chain.
6. **Говорить, что value меняется на месте.** Текущая реализация публикует новый `entry`.
7. **Считать `Clear` мгновенным освобождением памяти.** Старое дерево остаётся достижимым для уже начавшихся операций и освобождается GC позже.
8. **Объяснять Go 1.24–1.26 через `read`, `dirty` и `misses`.** Это прежняя реализация.

## Interview-ready answer

**1. Как `sync.Map` устроена в Go 1.24–1.26?**

- Оболочка — публичная `sync.Map` хранит `internal/sync.HashTrieMap[any, any]`.
- Основа — root указывает на 16-way hash-trie; четыре bits hash выбирают slot на каждом уровне.
- Child — `atomic.Pointer[node]` содержит `nil`, лист `entry` или внутренний `indirect` node.

**2. Зачем нужен общий тип `node`?**

- Роль — `node.isEntry` различает два реальных устройства: `entry` и `indirect`.
- Хранение — `node` встроен первым в оба типа, поэтому child использует один вид указателя.
- Обход — `entry` завершает поиск, `indirect` переводит его на следующие четыре bits hash.

**3. Как выполняется `Load`?**

- Начало — вычисляется hash ключа с индивидуальным seed map.
- Спуск — child pointers читаются атомарно без `indirect.mu`.
- Финал — на `entry` сравнивается полный ключ, а при полном совпадении hash просматривается overflow chain.

**4. Как выполняется `Store`?**

- Шаг 1 — без блокировки находятся предполагаемые parent и slot.
- Шаг 2 — берётся mutex parent, slot и `dead` перепроверяются.
- Шаг 3 — новый `entry` или готовое subtree публикуется атомарной заменой указателя.
- Конфликт — при устаревшем состоянии операция начинает поиск заново.

**5. Почему изменения могут масштабироваться?**

- Причина — mutex принадлежит отдельному `indirect` node, а не всей map.
- Следствие — изменения в разных глубоких ветвях могут идти под разными блокировками.
- Ограничение — root, общий префикс hash и горячий ключ всё равно создают contention.

**6. Как разрешаются hash collisions?**

- Совпал только prefix — trie добавляет уровни до первого различающегося fragment.
- Совпал hash целиком — entries связываются через `overflow`.
- Корректность — точный ключ всегда проверяется полным сравнением.

**7. Чем современная реализация отличается от Go 1.23 и ниже?**

- Раньше — использовались `read`, `dirty`, общий mutex, `misses` и promotion.
- Сейчас — используется hash-trie с блокировками отдельных внутренних узлов.
- Практика — профиль актуальной `sync.Map` нельзя объяснять через старый read/dirty lifecycle.
