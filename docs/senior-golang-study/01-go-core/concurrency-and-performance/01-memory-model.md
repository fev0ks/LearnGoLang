## Проблема видимости памяти

Интуиция «я написал `x = 42` раньше `ready = true`, значит другая горутина увидит их в том же порядке» — **неверна**. Без синхронизации нет гарантий ни о порядке, ни о самом факте видимости записей между горутинами.

```go
var x int
var ready bool

func main() {
    go func() { // producer
        x = 42       // (1) пишем полезные данные
        ready = true // (2) сигнализируем «данные готовы»
    }()

    for !ready { // (3) consumer активно ждёт сигнала
    }
    fmt.Println(x) // (4) ожидаем 42 — но можем напечатать 0 (или зависнуть на (3))
}
```

Это не теоретическая страшилка. Реальный прогон (go1.26, darwin/arm64, Apple M3 Max):

```text
$ go run .          # обычная сборка
# зависает — 10 запусков из 10 (Ctrl+C)

$ go run -race .    # с детектором гонок
==================
WARNING: DATA RACE
Write at 0x... by goroutine 7:
  main.main.func1()   ready = true   // строка (2)
Previous read at 0x... by main goroutine:
  main.main()         for !ready {}  // строка (3)
==================
WARNING: DATA RACE
Read at 0x... by main goroutine:
  main.main()         fmt.Println(x) // строка (4)
Previous write at 0x... by goroutine 7:
  main.main.func1()   x = 42         // строка (1)
==================
42
Found 2 data race(s)
exit status 66
```

Два независимых наблюдения:
- **Без `-race` программа виснет** (а не печатает `42`): компилятор закэшировал `ready` в регистре, и `for !ready {}` больше не перечитывает память — Причина 1 ниже. На x86 повезёт чаще, но это именно везение.
- **С `-race`** инструментация заставляет перечитывать память (поэтому цикл доходит до `42`), но детектор фиксирует **обе** гонки — на `ready` и на `x`. Под `-race` бинарь корректной программы так ругаться не должен.

Кажется, что цикл `(3)` не завершится, пока `(2)` не выполнится, а раз `(2)` после `(1)` — значит к моменту `(4)` запись `(1)` уже видна. На практике эта программа ломается на **двух** независимых уровнях — компилятор и железо, — и каждого достаточно само по себе.

### Причина 1: переупорядочивание компилятором

Компилятор видит, что внутри producer-горутины `x` и `ready` независимы, и волен поменять записи местами (или вообще держать `x` в регистре до конца функции) — для одной горутины результат неотличим. Тогда `ready` станет `true` **до** того, как `x` получит `42`, и consumer прочитает `x == 0`.

То же касается consumer: компилятор может «закэшировать» `ready` в регистре, прочитав его один раз, и `for !ready {}` превратится в бесконечный цикл, даже когда producer давно выставил флаг. Цикл без синхронизации не обязан перечитывать память.

#### Под капотом: почему busy-wait на обычном `bool` виснет

Это не абстракция — ровно из-за этого пример выше зависает 10/10. В Go **нет `volatile`**.

Действует **as-if-правило** (правило «как если бы»): компилятор волен как угодно переписать код при условии, что наблюдаемое поведение *однопоточной* программы не изменится. Про конкурентный доступ из других горутин компилятор ничего не знает и обязан знать не должен — он оптимизирует каждую горутину так, будто она единственная. Раз *в этой функции* `ready` никто не пишет, чтение можно вынести из цикла в регистр (loop-invariant code motion). Видно прямо в ассемблере (go1.26, arm64):

```text
// for !plain {}   — обычный bool
MOVBU main.plain(SB), R0   // читаем ОДИН раз, ДО цикла
TBZ   $0, R0, loop         // крутимся по регистру — в память больше не лезем
// → значение в R0 навсегда старое → вечный цикл
```

```text
// for !at.Load() {}   — atomic.Bool
loop:
MOVD  $main.at(SB), R0
LDARW (R0), R0             // атомарное чтение из памяти КАЖДУЮ итерацию (+ барьер)
CBZW  R0, loop             // увидит запись из другой горутины → выйдет
```

Разница в одной инструкции внутри цикла: для `bool` загрузки в цикле нет вообще (она поднята наружу), для `atomic.Bool` стоит `LDARW` — load-acquire, который компилятор обязан оставить на месте, не переупорядочивать и читать из памяти. Поэтому «спасает» не магия atomic как такового, а то, что atomic/канал/мьютекс одновременно (а) запрещают такой hoisting и (б) ставят аппаратный барьер. То же — причина, почему «флаг завершения» горутины нельзя делать обычным `bool`.

### Причина 2: переупорядочивание процессором и store buffer

Даже если машинные инструкции идут в порядке `(1)`, `(2)`, ядро CPU не пишет в общую память напрямую. Запись сначала попадает в **store buffer** ядра и публикуется в кэш-иерархию асинхронно. На слабых моделях памяти (ARM, POWER — то есть Apple Silicon, мобильные, серверные ARM) два store могут стать видны другим ядрам **в обратном порядке**. consumer на другом ядре увидит `ready = true`, но ещё старое `x = 0`.

x86 сильнее (TSO — store-store не переупорядочиваются), но и там это не спасает: переупорядочивание из Причины 1 происходит на этапе компиляции и от архитектуры не зависит.

Важно: кэши при этом **когерентны** (MESI) — нет режима, где запись навечно застряла в чужом кэше. Но когерентность гарантирует лишь, что запись станет видна *когда-нибудь* (после слива store buffer в кэш), а не *к моменту* конкретного чтения. «Eventually visible» ≠ «visible к этому чтению» — без барьера окна рассинхрона достаточно, чтобы consumer прочитал старое значение.

> Это лишь интуиция в контексте примера. Store buffer, store-to-load forwarding, модели x86 TSO / ARM weak / RISC-V, memory fences и acquire/release на уровне железа подробно разобраны в [hardware-and-os/04-atomics-and-memory-ordering](../../10-devops-and-observability/hardware-and-os/04-atomics-and-memory-ordering.md) (и cache coherence/MESI — в [03-cache-coherence-and-mesi](../../10-devops-and-observability/hardware-and-os/03-cache-coherence-and-mesi.md)).

### Корень проблемы

Обе причины — следствие одного: **между записями producer и чтениями consumer нет отношения happens-before** (см. ниже). Компилятор и железо оптимизируют каждую горутину так, будто она единственная; «общий порядок» появляется только там, где его явно потребовали примитивом синхронизации.

### Как чинить

Нужна **synchronization edge** — операция, которая одновременно (а) запрещает переупорядочивание через себя и (б) гарантирует, что записи до неё видны после парной операции в другой горутине:

```go
var x int
var ready atomic.Bool // atomic вместо «голого» bool

func main() {
    go func() { // producer
        x = 42
        ready.Store(true) // release: всё, что записано выше, публикуется
    }()

    for !ready.Load() { // acquire: увидев true, видим и x = 42
    }
    fmt.Println(x) // гарантированно 42
}
```

`atomic.Store`/`Load` в Go дают seq-consistent семантику (с Go 1.19) и устанавливают HB между `Store(true)` и читающим его `Load()`. Эквивалентно можно передать готовность через канал или защитить `Mutex` — любой из этих примитивов создаёт нужное ребро. «Голый» `bool` из первого примера такого ребра не создаёт и потому некорректен — и это **гонка данных**, а не просто «иногда неверный результат» (см. [Data race](#data-race-определение-и-последствия)).

## Happens-Before

**Happens-before (HB)** — частичный порядок событий в программе.

> Если A happens-before B, то все эффекты A (записи в память) гарантированно видны при выполнении B.

Свойства:
- В одной горутине: все операции упорядочены по HB в порядке кода;
- Между горутинами: HB устанавливается только через явные **synchronization edges**.

```
Горутина 1:  A → B → C
Горутина 2:  X → Y → Z

Без синхронизации: нет никакого HB между {A,B,C} и {X,Y,Z}
С каналом:   C → [channel send] → X  →  C HB X HB Y HB Z
```

Если между двумя операциями из разных горутин нет HB — поведение **не определено** (для записей).

## Data race: определение и последствия

Имея определение HB, легко дать точное определение гонки. **Data race** возникает когда:
1. Два concurrent доступа к одной переменной;
2. Хотя бы один из них — **запись**;
3. Между ними **нет HB** отношения.

То есть data race — это буквально «отсутствие HB-ребра там, где есть конкурентная запись». Именно поэтому раздел стоит сразу после Happens-Before: гонка определяется *через* него.

Последствия data race в Go: **undefined behavior** на уровне Go specification. Это не «иногда читаем устаревшее значение» — компилятор вправе предполагать, что гонок нет, поэтому при гонке возможны разорванные чтения (torn read), зависший цикл, повреждённый `map` с аварийным `fatal error`, и прочее поведение, которого нет в исходном коде.

```go
// DATA RACE примеры:

// 1. Counter без синхронизации
var counter int
for i := 0; i < 1000; i++ {
    go func() { counter++ }() // READ+WRITE без синхронизации
}

// 2. Map из нескольких горутин
m := map[string]int{}
go func() { m["a"] = 1 }() // WRITE
go func() { _ = m["a"] }() // READ — map не thread-safe!

// 3. Slice append
var s []int
go func() { s = append(s, 1) }() // READ+WRITE slice header
go func() { s = append(s, 2) }() // READ+WRITE slice header
```

**Правильные версии:**
```go
// 1. Counter — atomic или mutex
var counter atomic.Int64
for i := 0; i < 1000; i++ {
    go func() { counter.Add(1) }()
}

// 2. Map — sync.Map или mutex
var mu sync.RWMutex
m := map[string]int{}
go func() {
    mu.Lock()
    m["a"] = 1
    mu.Unlock()
}()

// 3. Slice — через channel или mutex
var mu sync.Mutex
var s []int
go func() {
    mu.Lock()
    s = append(s, 1)
    mu.Unlock()
}()
```

### Data race на одном ядре

Частый вопрос на собесе: «если ядро одно (`GOMAXPROCS=1`), data race ведь невозможен?» — **возможен**. Определение гонки (пункты выше) сформулировано через **отсутствие happens-before**, а не через железо. «Concurrent» здесь означает «не упорядочены отношением HB», а не «физически параллельно на разных ядрах». Из трёх механизмов одноядерности боится только один:

| Механизм | Нужно ≥2 ядра? | На одном ядре |
|---|---|---|
| Кэш / store buffer (Причина 2 выше) | да | **не возникает** — один store buffer, store-to-load forwarding |
| Переупорядочивание/hoisting компилятором (Причина 1) | нет | возникает — это compile-time трансформация |
| Чередование неатомарной операции из-за вытеснения | нет | возникает — `counter++` = load→add→store, планировщик вытесняет между шагами |

Третий — самый наглядный. `counter++` неатомарен; если две горутины успевают вклиниться между чтением и записью, инкременты теряются. Проверка на одном ядре (точка вытеснения вставлена между load и store, чтобы симптом проявился стабильно):

```go
runtime.GOMAXPROCS(1) // одно ядро
// 4 горутины, каждая 1000 раз:
tmp := counter
runtime.Gosched()  // вытеснение МЕЖДУ load и store
counter = tmp + 1  // store по устаревшему tmp
// → counter = 1000 вместо 4000 (go1.26)
```

Главное: `go run -race` помечает гонку **даже при `GOMAXPROCS=1`** — детектор смотрит на happens-before, а не на параллелизм. Сам симптом (потерянный инкремент, разорванное значение) проявляется вероятностно и зависит от планировщика, но **гонка как нарушение модели памяти есть всегда**. Поэтому «у меня же одно ядро / GOMAXPROCS=1» — не оправдание отсутствию синхронизации.

### Data race ≠ race condition

Это разные вещи, и их любят спрашивать на собесе:

- **Data race** — нарушение модели памяти: конкурентный доступ без HB, хотя бы один — запись. Это свойство *кода*, его ловит `go test -race`.
- **Race condition** — логическая ошибка: результат зависит от порядка/тайминга операций. Это свойство *алгоритма*.

Они независимы. Бывает data race без логической ошибки (два потока пишут одно и то же значение — UB по спеке, но «результат» совпадает) и бывает race condition без data race:

```go
var mu sync.Mutex
var balance int // защищён mutex — data race НЕТ

func withdraw(amount int) {
    mu.Lock()
    b := balance // атомарно прочитали
    mu.Unlock()
    if b >= amount { // ...но между Unlock и следующим Lock баланс мог измениться
        mu.Lock()
        balance -= amount // списываем по устаревшему решению → может уйти в минус
        mu.Unlock()
    }
}
```

Каждый доступ к `balance` синхронизирован — `-race` молчит. Но проверка и списание не атомарны как единое целое → два конкурентных `withdraw` могут оба пройти `if` и увести баланс в минус. Лечится расширением критической секции (один `Lock` на «проверить и списать»), а не атомиками. Вывод: `-race` ловит data race, но **не** ловит race condition — за корректность критических секций отвечает дизайн.

## Ключевые HB-правила Go

### 1. Запуск горутины

`go` statement happens-before первой инструкции горутины:

```go
var data int

func main() {
    data = 42
    go func() {
        fmt.Println(data) // гарантированно видит 42
    }()
    // НО: main может завершиться до горутины, нужен WaitGroup
}
```

**Завершение горутины** НЕ устанавливает HB автоматически — нужен `WaitGroup.Wait()`:

```go
var wg sync.WaitGroup
var result int

wg.Add(1)
go func() {
    defer wg.Done()
    result = compute()
}()

wg.Wait()
fmt.Println(result) // OK: wg.Done() HB wg.Wait() → result виден
```

### 2. Каналы

**Unbuffered channel:**
```go
var data int
ch := make(chan struct{})

go func() {
    data = 42
    ch <- struct{}{} // send HB соответствующий receive
}()

<-ch                 // receive возвращает только после send
fmt.Println(data)    // гарантированно 42

// Дополнительно для unbuffered:
// receive happens-before completion of send
// (send в отправителе не завершится, пока получатель не принял)
```

**Buffered channel (capacity C):**
```go
// kth send HB (k + cap)th receive
ch := make(chan int, 3)  // capacity = 3
// 1-й send HB 4-й receive
// 2-й send HB 5-й receive
// и т.д.
```

**Close канала:**
```go
var data int
ch := make(chan struct{})

go func() {
    data = 42
    close(ch) // close HB receive нулевого значения
}()

<-ch                   // получаем нулевое значение из закрытого канала
fmt.Println(data)      // гарантированно 42
```

### 3. sync.Mutex / sync.RWMutex

`n-й Unlock` happens-before `(n+1)-й Lock`:

```go
var mu sync.Mutex
var shared int

// Горутина 1:
mu.Lock()
shared = 42
mu.Unlock() // этот Unlock HB следующий Lock в горутине 2

// Горутина 2:
mu.Lock()
fmt.Println(shared) // гарантированно 42
mu.Unlock()
```

`RWMutex`: `RUnlock` HB `Lock` (write lock блокирует читателей), `Unlock` HB `RLock`.

### 4. sync.Once

Функция f, переданная в `Do`, завершается HB любой последующий вызов `Do`:

```go
var once sync.Once
var config *Config

func getConfig() *Config {
    once.Do(func() {
        config = loadConfig() // загружается ровно один раз
    })
    return config // гарантированно видит результат loadConfig()
}
```

**Без Once — классический race:**
```go
// НЕПРАВИЛЬНО: double-checked locking без правильной синхронизации
var mu sync.Mutex
var config *Config

func getConfig() *Config {
    if config == nil {  // BUG: читаем без lock — гонка с записью под lock
        mu.Lock()
        if config == nil {
            config = loadConfig()
        }
        mu.Unlock()
    }
    return config // может вернуть partially initialized config
}
```

Тонкость: баг — **не** «другая горутина перевычислит конфиг». Перевычисления нет — внутренняя проверка под `mu` его исключает (`Unlock` писателя HB `Lock` читателя → залоченный путь всегда видит готовый `config`). Опасен именно **внешний** `if config == nil` без лока. Присваивание `config = loadConfig()` — это «выделить → инициализировать поля → записать указатель»; для горутины на быстром пути нет HB с инициализацией полей, поэтому она может увидеть **указатель уже не-nil, а поля — ещё нулевыми** (запись указателя «публикуется» раньше записей полей) и вернуть полуинициализированный объект. Это **unsafe publication**: проблема не в «слишком поздно увидел», а в «увидел указатель раньше, чем его содержимое». `sync.Once` корректен потому, что его быстрый путь читает флаг через atomic с acquire-семантикой — то есть участвует в happens-before, и «увидел готовность → увидел и все поля».

### 5. sync/atomic

Начиная с **Go 1.19**: atomic операции на одной переменной имеют **sequentially consistent** семантику — если `Load` наблюдает значение от `Store`, то `Store` HB `Load`:

```go
var flag atomic.Bool
var data int

// Горутина 1:
data = 42
flag.Store(true) // HB

// Горутина 2:
if flag.Load() { // если видим true
    fmt.Println(data) // гарантированно видим 42
}
```

До Go 1.19: только sequentially consistent для отдельных операций, но не было гарантий между разными переменными.

## Паттерны синхронизации

Каждый практический приём синхронизации — это применение конкретного HB-правила выше. Сводка «какой edge зачем»:

| Приём | Какой HB-edge использует | Когда |
|---|---|---|
| Передача владения через канал | send HB receive | отдать данные другой горутине и больше их не трогать |
| Mutex вокруг shared state | `Unlock` HB следующий `Lock` | несколько полей менять согласованно |
| `sync.Once` для ленивой инициализации | завершение `f` HB любой последующий `Do` | один раз построить синглтон/конфиг |
| `atomic.Value` / `atomic.Pointer[T]` snapshot | `Store` HB наблюдающий `Load` (Go 1.19+ seq-consistent) | read-heavy hot-reload без локов |

## Race detector

```bash
# Запуск с race detector (добавить ко всем тестам в CI)
go test -race ./...
go build -race ./...
go run -race main.go
```

Race detector:
- инструментирует **каждый** доступ к памяти (запись и чтение);
- отслеживает HB-граф через vector clocks;
- репортирует при обнаружении concurrent доступа без HB.

```
==================
WARNING: DATA RACE
Write at 0x00c0000b4010 by goroutine 7:
  main.main.func1()
      /app/main.go:12 +0x2c

Previous read at 0x00c0000b4010 by goroutine 8:
  main.main.func2()
      /app/main.go:17 +0x24
==================
```

Ограничения:
- находит только те гонки, которые **реально произошли** во время запуска;
- overhead ~5–20× CPU, ~5–10× memory;
- нет false positives, но есть false negatives (гонка есть, но не сработала).

## Типичные ошибки

Все они — частный случай одного: **общая память без synchronization edge между записью и чтением**.

**Незащищённый результат из горутины** — нет HB между записью в горутине и чтением в main:
```go
// ПЛОХО: запись в горутине и чтение в main без HB → data race
var result []int
go func() { result = []int{1, 2, 3} }()
fmt.Println(result)

// ПРАВИЛЬНО: канал создаёт edge send HB receive
ch := make(chan []int, 1)
go func() { ch <- []int{1, 2, 3} }()
fmt.Println(<-ch)
```

Ещё две классические гонки разобраны как загадки в соседних файлах (тоже «нет HB»):

- **захват переменной цикла горутиной** (до Go 1.22) → [02-goroutines-and-channels, Загадка 1](./02-goroutines-and-channels.md#разбор-примеров-загадок);
- **`WaitGroup.Add` внутри горутины** (гонка с `Wait`) → [03-sync-primitives](./03-sync-primitives.md#syncwaitgroup).

## Interview-ready answer

**1. Что такое happens-before?**
Частичный порядок событий: если A HB B, все записи до и в A гарантированно видны при B. В одной горутине операции упорядочены по коду. Между горутинами HB возникает **только** через synchronization edges: `go`-statement, channel send/receive, `Unlock`/`Lock`, `close`, `sync.Once`, `WaitGroup.Wait`, atomic. Нет edge → порядок и видимость не определены.

**2. Что такое data race и чем он опасен?**
Два конкурентных доступа к одной переменной, хотя бы один — запись, и между ними нет HB. По спецификации Go это **undefined behavior**: можно прочитать старое, несогласованное или рваное (torn) значение, а не «просто иногда неверное». Поэтому гонку нельзя «оставить, если редко».

**3. Какие HB-гарантии у каналов?**
Send HB соответствующий receive; `close` HB receive нулевого значения; у buffered-канала ёмкости C — `k`-й send HB `(k+C)`-й receive. У unbuffered дополнительно: receive HB завершение send. Завершение горутины само по себе HB **не** создаёт — нужен `WaitGroup`/канал.

**4. Что гарантирует sync/atomic по памяти?**
С Go 1.19 атомарные операции **sequentially consistent**: если `Load` увидел значение от `Store`, то `Store` HB этот `Load` (можно публиковать данные через atomic-флаг). Смешивать atomic и обычный доступ к одной переменной нельзя — это гонка.

**5. Как работает race detector и каковы его пределы?**
`-race` инструментирует каждый доступ к памяти и строит HB-граф через vector clocks; репортит доступ без HB. Overhead ~5–20× CPU, ~5–10× память. Нет false positives, но есть **false negatives** — находит лишь гонки, которые реально произошли на этом прогоне. Поэтому `-race` гоняют в CI на представительной нагрузке.

**6. Channel или mutex?**
Channel — передача владения, pipeline-координация, сигналы (done/cancel). Mutex — защита shared mutable state, особенно когда несколько полей меняются согласованно. Hot path с простым состоянием — `atomic`/`atomic.Pointer` (без локов). Сложная multi-field логика → mutex (проще рассуждать о корректности).
