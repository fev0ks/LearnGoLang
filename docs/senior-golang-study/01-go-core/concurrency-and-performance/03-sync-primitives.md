## `sync.Mutex` vs `sync.RWMutex`

### `sync.Mutex` — исключительный доступ

```go
type Counter struct {
    mu    sync.Mutex
    value int
}

func (c *Counter) Increment() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.value++
}

func (c *Counter) Value() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.value
}
```

### `sync.RWMutex` — разделение read/write

```go
type Cache struct {
    mu    sync.RWMutex
    items map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock()         // несколько горутин могут читать одновременно
    defer c.mu.RUnlock()
    v, ok := c.items[key]
    return v, ok
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock()          // исключительный доступ для записи
    defer c.mu.Unlock()
    c.items[key] = value
}
```

### Когда RWMutex выгоден

RWMutex полезен когда:
- Операций чтения **значительно больше**, чем записи (например, 95% reads)
- Критическая секция чтения **не тривиальная** (занимает хоть сколько-то времени)

RWMutex **невыгоден** когда:
- Параллелизма мало (1–2 ядра, низкая конкуренция) — выгоды от параллельных чтений нет, а атомики `readerCount` остаются чистым overhead
- Критическая секция очень короткая **и** конкуренция низкая — Mutex быстрее
- Высокое write-давление: каждый write ждёт всех активных reads → starvation писателя

```
Эмпирическое правило: >80% reads И есть реальная конкуренция на многих ядрах → RWMutex; иначе → Mutex
```

### Бенчмарк: где Mutex обгоняет RWMutex

`b.RunParallel`, состояние под общим локом, запись всегда короткая (`s.val++`), go1.26, Apple M3 Max. В каждой клетке `M / RW`, ns/op, жирным — победитель:

| Сценарий | 1 ядро | 2 ядра | 4 ядра | 8 ядер |
|---|---|---|---|---|
| 50% reads, короткая | **2.43** / 4.32 | **19.5** / 22.0 | 71.8 / **42.7** | 80.9 / **44.7** |
| 50% reads, длинная | **8.96** / 10.4 | **28.6** / 35.4 | 79.9 / **65.3** | 84.3 / **65.5** |
| 99% reads, короткая | **2.33** / 3.60 | 15.7 / **8.57** | 68.4 / **12.9** | 92.6 / **21.6** |
| 99% reads, длинная | 15.7 / 15.7 | 38.4 / **23.1** | 77.8 / **40.2** | 97.1 / **63.5** |

Интересна не «победа RW на 8 ядрах», а **где проходит кроссовер** — и он зависит от доли чтений:

- **1 ядро** — Mutex выигрывает или паритет **всегда**: параллельных читателей нет, атомики `readerCount` у RWMutex — чистый overhead.
- **2 ядра** — точка перелома: при **50% reads `Mutex` ещё впереди** (19.5 vs 22.0 — параллелизма от двух потоков мало, overhead RW не окупился), а при **99% reads RW уже обгоняет** (8.6 vs 15.7).
- **4–8 ядер** — RWMutex впереди везде, и чем больше чтений, тем сильнее: на 99%-короткой — до **4×** (21.6 vs 92.6), на 50%-короткой — лишь ~**1.8×** (44.7 vs 80.9).

То есть кроссовер по числу ядер наступает тем **раньше**, чем выше доля чтений: для 99% хватает 2 ядер, для 50% нужно ≥4. Это и наполняет смыслом правило «>80% reads» — высокая доля чтений опускает порог, при котором RWMutex начинает окупаться.

**Важная оговорка:** запись здесь тривиальная (`s.val++`), эксклюзивный лок держится наносекунды — поэтому при 4+ ядрах RW обгоняет даже на 50%. Если запись долгая/частая, RWMutex теряет: писатель ждёт слива всех читателей (`readerWait`), новые `RLock` встают за ним → **starvation писателя**. Этот микробенч его не показывает. Вывод: решают **доля чтений × длина секции × число ядер × стоимость записи** вместе; одно ядро / короткие секции / дорогие записи → `Mutex`.

### Под капотом: Mutex — это `state int32` + `sema`

`sync.Mutex` — это **всего два поля**, никакой ОС-блокировки в неконтенционном случае:

```go
type Mutex struct {
    state int32  // битовое поле: флаги + счётчик ждущих
    sema  uint32 // семафор рантайма для парковки/пробуждения
}
// биты state (младшие):
//   bit 0  mutexLocked   — залочен
//   bit 1  mutexWoken    — есть разбуженный, но ещё не схвативший
//   bit 2  mutexStarving — режим голодания
//   биты 3.. — число ждущих горутин (waiterShift)
```

Раскладка одного `int32`: `[ waiters … | S | W | L ]`, где L/W/S — три младших бита, а всё выше — счётчик ждущих. Примеры значений:

| `state` (bin) | `=dec` | Что значит |
|---|---|---|
| `…0000 0000` | 0 | свободен, ждущих нет |
| `…0000 0001` | 1 | залочен (L=1), без очереди — типичный неконтенционный случай |
| `…0000 1001` | 9 | залочен + **1** ждущий (`1<<3 \| L`) |
| `…0001 0001` | 17 | залочен + **2** ждущих (`2<<3 \| L`) |
| `…0000 1011` | 11 | залочен + 1 ждущий + **W** (кого-то разбудили, ещё не схватил) |
| `…0001 1101` | 29 | залочен + 3 ждущих + **S** (режим голодания, `3<<3 \| S \| L`) |

`Lock` на свободном делает `CAS(0 → 1)`; `Add`/`CAS` в slow path меняют сразу нужные биты и счётчик одним словом. Например, поставить флаг «голодание» — `state |= mutexStarving` (бит 2), добавить ждущего — `+= 1<<mutexWaiterShift`.

**Fast path (неконтенция).** `Lock()` начинается с одного `CAS(&state, 0, mutexLocked)`: если лок свободен — захватили за одну атомарную инструкцию, **без сисколов и без парковки**. Это главная причина, почему незанятый `Mutex` почти бесплатный.

**Slow path (`lockSlow`).** Если CAS не прошёл — лок занят. Горутина не сразу паркуется:
1. **Спин.** Несколько итераций активного ожидания (`runtime_canSpin` + `PAUSE`-инструкция) — на multicore лок часто отпускают за наносекунды, и спин дешевле, чем парковка+пробуждение (~1 мкс). Спин разрешён только если есть смысл: GOMAXPROCS>1, не одно ядро, спинов было немного.
2. **Парковка.** Не дождались — `runtime_SemacquireMutex(&sema)` усыпляет горутину (это уже `gopark`, не syscall). `Unlock` потом разбудит через `runtime_Semrelease`.

**Normal mode vs starvation mode** — два режима работы лока:
- **Normal:** ждущие лежат в FIFO-очереди, но разбуженный конкурирует за лок с **новоприбывшими** горутинами, которые уже крутятся на CPU. Новички часто выигрывают (они «горячие») → разбуженный встаёт обратно в голову очереди. Это даёт throughput, но рискует **голоданием**.
- **Starvation:** если горутина не может взять лок дольше **1 мс**, `Mutex` переключается в режим голодания. Выход из режима — когда ждущий забрал лок и он либо последний, либо ждал <1 мс.

Что конкретно меняет выставленный бит `mutexStarving` — три эффекта в коде:
1. **Новички перестают спинить.** Условие спина `state&(locked|starving) == locked` становится ложным → горутины не крутятся вхолостую (перехватить лок спином всё равно нельзя — его вручают голове очереди).
2. **Новички перестают пытаться захватить лок.** Ветка `if state&starving == 0 { new |= locked }` отключается → новоприбывшая горутина только встаёт **в хвост** очереди, не конкурируя за лок.
3. **`Unlock` передаёт лок напрямую.** В `unlockSlow` вместо «снять бит + разбудить одного, пусть конкурирует» вызывается `Semrelease(&sema, handoff=true)` — проснувшаяся горутина из **головы** FIFO-очереди сразу владеет локом.

Итог: голодание жертвует немного throughput (разбуженную горутину надо дошедулить на ядро) ради **строгого FIFO** — гарантии, что дольше всех ждущий получит лок следующим, сколько бы горячих новичков ни пришло. Без этого режима запаркованная горутина под высокой конкуренцией почти всегда проигрывала бы новичку, уже крутящемуся на CPU, и могла бы ждать бесконечно.

**`Unlock`** симметричен: fast path — `AtomicAdd(&state, -mutexLocked)`; если выставлены другие биты (есть ждущие) — `unlockSlow` будит одного или передаёт лок напрямую в starvation-режиме.

**Суть `lockSlow` без рантайм-шелухи.** Это просто **retry-цикл** «попробуй взять → не вышло, поспини → всё ещё нет, запишись в ждущие и усни»:

```
for {
    // 1. Лок занят, НЕ голодание, спинить ещё можно?
    if занят && !голодание && canSpin:
        поспинить (несколько PAUSE); снова в начало цикла

    // 2. Готовим новое состояние одним словом:
    new := old
    if !голодание:        new |= locked          // пробуем захватить
    if занят || голодание: new += 1<<waiterShift  // иначе встаём в очередь
    if ждём уже >1мс:     new |= starving         // объявляем голодание

    // 3. Пытаемся применить через CAS:
    if CAS(old → new):
        if лок был свободен:
            return                  // ✅ взяли через CAS, ушли
        Semacquire(&sema)           // 💤 лок был занят → усыпили
        // ...проснулись:
        if режим голодания:
            // лок передан НАМ напрямую (Unlock отдал первому в очереди)
            поправить счётчики; return   // ✅
        // иначе — обычный режим: просыпаемся и КОНКУРИРУЕМ заново
    else:
        old = m.state               // кто-то опередил → перечитать и по новой
}
```

Три ветки выхода: (1) захватил CAS-ом без сна; (2) проснулся в режиме голодания — лок уже мой; (3) проснулся в обычном режиме — снова в драку с новоприбывшими. Вся «замудрённость» исходника ниже — это аккуратная работа с битами `state` и race-инструменты вокруг этих трёх веток.

<details>
<summary>Исходник: <code>Lock</code> / <code>lockSlow</code> / <code>Unlock</code> (sync/mutex.go, упрощённо — убраны race-инструменты)</summary>

```go
func (m *Mutex) Lock() {
    // Fast path: захватить свободный mutex одним CAS.
    if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
        return
    }
    // Slow path вынесен отдельно, чтобы fast path инлайнился.
    m.lockSlow()
}

func (m *Mutex) lockSlow() {
    var waitStartTime int64
    starving := false
    awoke := false
    iter := 0
    old := m.state
    for {
        // Спинить можно, только если лок занят и НЕ в режиме голодания.
        if old&(mutexLocked|mutexStarving) == mutexLocked && runtime_canSpin(iter) {
            // Выставить mutexWoken, чтобы Unlock не будил лишних.
            if !awoke && old&mutexWoken == 0 && old>>mutexWaiterShift != 0 &&
                atomic.CompareAndSwapInt32(&m.state, old, old|mutexWoken) {
                awoke = true
            }
            runtime_doSpin() // несколько PAUSE-инструкций
            iter++
            old = m.state
            continue
        }
        new := old
        if old&mutexStarving == 0 {
            new |= mutexLocked // в normal-режиме пытаемся взять лок
        }
        if old&(mutexLocked|mutexStarving) != 0 {
            new += 1 << mutexWaiterShift // встаём в очередь (+1 к счётчику ждущих)
        }
        if starving && old&mutexLocked != 0 {
            new |= mutexStarving // мы ждали >1мс → переключаем в голодание
        }
        if awoke {
            new &^= mutexWoken // сбросить «разбуженного»
        }
        if atomic.CompareAndSwapInt32(&m.state, old, new) {
            if old&(mutexLocked|mutexStarving) == 0 {
                break // взяли лок через CAS
            }
            // Уже ждали? тогда в голову очереди (LIFO).
            queueLifo := waitStartTime != 0
            if waitStartTime == 0 {
                waitStartTime = runtime_nanotime()
            }
            runtime_SemacquireMutex(&m.sema, queueLifo, 1) // ПАРКОВКА
            // Проснулись: проверяем, не пора ли в голодание.
            starving = starving || runtime_nanotime()-waitStartTime > starvationThresholdNs // 1мс
            old = m.state
            if old&mutexStarving != 0 {
                // В голодании лок передан НАМ напрямую — поправляем счётчики.
                delta := int32(mutexLocked - 1<<mutexWaiterShift)
                if !starving || old>>mutexWaiterShift == 1 {
                    delta -= mutexStarving // выходим из режима голодания
                }
                atomic.AddInt32(&m.state, delta)
                break
            }
            awoke = true
            iter = 0
        } else {
            old = m.state
        }
    }
}

func (m *Mutex) Unlock() {
    // Fast path: снять бит locked.
    new := atomic.AddInt32(&m.state, -mutexLocked)
    if new != 0 {
        m.unlockSlow(new) // есть ждущие/флаги → разбудить или передать лок
    }
}
```

Видно ровно то, что описано выше: fast path — один `CAS`/`Add`; в `lockSlow` сначала спин (`runtime_doSpin`), потом парковка (`runtime_SemacquireMutex`); порог `starvationThresholdNs` (1 мс) переключает режим, а в голодании лок «вручается» проснувшейся горутине через коррекцию `delta`.
</details>

### `sync.Mutex` vs `runtime.mutex` — два разных лока

Дальше встретится `runtime.mutex` (поле `lock` в `semaRoot`, `hchan` и др.) — это **не** `sync.Mutex`, а отдельный, более низкоуровневый примитив. Разница в **уровне блокировки**:

| | `sync.Mutex` | `runtime.mutex` |
|---|---|---|
| Уровень | **горутина** | **OS-поток (M)** |
| При contention | парк горутины (`gopark`), а её M крутит другие горутины | спин → блокировка **самого потока** через `futex` (Linux) / OS-семафор (Darwin/Windows) — поток спит в ядре |
| Где | пользовательский код | внутренности рантайма: планировщик, `hchan`, аллокатор (`mheap`), `semtable`, GC |
| Справедливость | normal / starvation (порог 1 мс) | нет, нарочно простой |
| Цена блокировки | дёшево (M свободен) | дорого (простаивает целый поток) → держат **очень короткими** секциями |

**Почему рантайму нужен свой лок, а не `sync.Mutex`.** Slow-path `sync.Mutex` сам построен поверх рантайма: паркует горутину через `semtable`, а `semtable` защищён… `runtime.mutex`. То есть `sync.Mutex` нельзя использовать для реализации **самого планировщика и парковки** — циклическая зависимость (нельзя «запарковать горутину» в коде, который и реализует парковку горутин). `runtime.mutex` — фундамент: блокирует на уровне потока напрямую через ОС, поэтому работает и там, где планировщик недоступен (на `g0`, внутри scheduler, когда преемпция запрещена). Отсюда же ограничение: под `runtime.mutex` нельзя делать то, что рекурсивно дёрнет рантайм (аллокацию и т.п.), — секции держат крошечными.

### Рантайм-семафор: поле `sema` и `semtable`

Понятие общее для `Mutex`, `RWMutex`, `WaitGroup` — у всех есть поле `sema uint32` (или `writerSem`/`readerSem`). Сам `uint32` — **не очередь**: в нём только **счётчик токенов** (число доступных «разрешений»). А очередь припаркованных горутин лежит в **глобальной для рантайма** хеш-таблице `semtable`, ключ — **адрес** этого `uint32`.

```go
// runtime/sema.go
var semtable semTable
const semTabSize = 251 // простое число — чтобы адреса не коррелировали с бакетами

type semTable [semTabSize]struct {
    root semaRoot
    pad  [cpu.CacheLinePadSize - unsafe.Sizeof(semaRoot{})]byte // добить до кэш-линии
}

// бакет: какой semaRoot отвечает за данный адрес
func (t *semTable) rootFor(addr *uint32) *semaRoot {
    return &t[(uintptr(unsafe.Pointer(addr))>>3)%semTabSize].root
}

// semaRoot — балансированное дерево (treap) горутин, ждущих на РАЗНЫХ адресах
type semaRoot struct {
    lock  mutex         // runtime.mutex, защищает это дерево
    treap *sudog        // корень treap: по узлу на каждый УНИКАЛЬНЫЙ адрес
    nwait atomic.Uint32 // число ждущих — читается БЕЗ lock (быстрый путь)
}

// узлы дерева — это sudog'и; здесь важно, ГДЕ в нём лежит адрес
type sudog struct {
    g        *g
    elem     unsafe.Pointer // ← АДРЕС семафора (&sema). ключ, по которому ищут в treap
    next     *sudog         // в treap — ПРАВЫЙ потомок (в каналах — сосед по очереди!)
    prev     *sudog         // в treap — ЛЕВЫЙ потомок
    waitlink *sudog         // список sudog с ТЕМ ЖЕ elem (горутины на одном адресе)
    ticket   uint32         // приоритет для балансировки treap
    // ... (isSelect, success и др.)
}
```

Ключевой момент: адрес семафора — это `sudog.elem`. При парковке рантайм делает `s.elem = unsafe.Pointer(&sema)` и вставляет `s` в treap, сравнивая адреса (`addr < t.elem` → налево, иначе направо). При `Semrelease(&sema)` идут по дереву, сравнивая `t.elem` с `&sema`, находят узел и будят горутину из его списка. Обрати внимание: `next/prev` у `sudog` **многоразовые** — в дереве семафора это потомки treap, а в очереди канала (тот же тип `sudog`) это соседи по двусвязному `waitq`. Какую роль играют — зависит от того, где сейчас живёт `sudog`.

Три уровня, от грубого к точному:

```
1) semtable — массив из 251 бакета. Бакет = (адрес_семафора >> 3) % 251
   ┌──────┬──────┬─────┬──────┬─────┬───────┐
   │ [0]  │ [1]  │ ... │ [k]  │ ... │ [250] │
   └──────┴──────┴─────┴──┬───┴─────┴───────┘
                          │
2) в бакете — semaRoot.treap: BST, упорядоченный ПО АДРЕСУ (O(log n) найти адрес)
                       &mu200            ← узлы упорядочены: &mu100 < &mu200 < &mu500
                      /       \
                  &mu100      &mu500
                    │           │
3) в каждом узле — waitlink-список горутин, ждущих именно на ЭТОМ адресе (O(1)):
                    │           │
              g7 → g3        g1 → g4 → g2
```

`&mu100/200/500` — это адреса разных мьютексов (числа намекают на порядок адресов в памяти). Спуск по дереву ведёт к нужному адресу, а список в узле — очередь горутин на нём.

- **`semTable`** — фиксированный массив из **251** бакета (простое число; `pad` разносит соседние `semaRoot` по разным кэш-линиям, чтобы не было [false sharing](../../10-devops-and-observability/hardware-and-os/03-cache-coherence-and-mesi.md) — когда запись в один бакет инвалидировала бы линию с соседним). Бакет выбирается как `(addr >> 3) % 251`.
- **`semaRoot`** — внутри бакета **treap** (балансированное дерево): по узлу на каждый **уникальный адрес** семафора. Найти адрес — `O(log n)`. Горутины, ждущие на **одном и том же** адресе, связаны в список через `sudog.waitlink` под этим узлом — операции с ним `O(1)`. Плюс свой `lock` (рантайм-мьютекс на это дерево) и `nwait` — счётчик ждущих, который читают **без** лока, чтобы `Semrelease` мог быстро выйти, если ждать некому.

Две операции:
- **`runtime_Semacquire(&sema)`** («занять»): счётчик > 0 — уменьшить и идти дальше; 0 — **запарковать** горутину: завести `sudog`, найти `rootFor(&sema)`, вставить в treap (или в список по своему адресу) и `gopark`. Это и есть «спим на `sema`» — горутина снята с ядра, CPU не жжёт.
- **`runtime_Semrelease(&sema)`** («освободить»): если `nwait == 0` — просто инкремент счётчика и выход; иначе под `root.lock` найти в treap узел по адресу `&sema`, снять оттуда одну горутину и разбудить (`goready`).

Поэтому «писатель спит на `writerSem`» = горутина-писатель лежит как `sudog` в `semtable`, в дереве бакета `rootFor(&rw.writerSem)`; последний читатель делает `Semrelease(&rw.writerSem)` → рантайм по тому же адресу находит её и будит.

**Почему очередь вынесена в общую таблицу, а не в саму структуру.** В голом `uint32` негде хранить голову списка ждущих. Адрес переменной — бесплатный уникальный ключ, поэтому waiter-очередь держат отдельно и общую на весь рантайм. Это позволяет `Mutex`/`RWMutex`/`WaitGroup` оставаться крошечными (поле `sema` — те же 4 байта), а машинерию парковки/пробуждения — переиспользовать на всех. `runtime_SemacquireMutex` — тот же семафор с небольшими отличиями (учёт спинов, опция handoff для starvation-режима).

### Под капотом: RWMutex — поверх Mutex + счётчик читателей

```go
type RWMutex struct {
    w           Mutex        // лочится писателями (исключает других писателей)
    writerSem   uint32       // писатель спит здесь, ждя завершения читателей
    readerSem   uint32       // читатели спят здесь, ждя завершения писателя
    readerCount atomic.Int32 // число активных читателей (может стать отрицательным!)
    readerWait  atomic.Int32 // сколько читателей писатель ещё ждёт
}
const rwmutexMaxReaders = 1 << 30
```

Главная идея: `readerCount` в обычное время — это просто **число активных читателей** (0, 1, 2, …). А `rwmutexMaxReaders = 2³⁰` — это «заведомо больше, чем реально бывает читателей» сдвиг, которым писатель **меняет знак** счётчика, не теряя при этом его младшую часть (реальное число читателей). Знак и работает сигналом «пришёл писатель».

**`RLock`** — `readerCount.Add(1)`:
- результат **≥ 0** → писателя нет, читаем сразу (одна атомарка, без локов, без очереди);
- результат **< 0** → писатель уже объявился (вычел 2³⁰) → читатель спит на `readerSem`.

**`RUnlock`** — `readerCount.Add(-1)`:
- результат **≥ 0** → писателя нет, просто ушли;
- результат **< 0** → писатель ждёт нас; идём в `rUnlockSlow`: уменьшаем `readerWait`, и **последний** уходящий читатель (`readerWait == 0`) будит писателя.

**`Lock`** (писатель):
1. `rw.w.Lock()` — внутренний `Mutex`, отсекает **других писателей** (писатели между собой эксклюзивны);
2. `readerCount.Add(-rwmutexMaxReaders)` — вычитает 2³⁰, делая счётчик отрицательным. Это разом: (а) новые `RLock` увидят `<0` и заснут, (б) `r = (результат) + 2³⁰` = сколько читателей было **активно** в этот момент;
3. если `r != 0` — записывает `readerWait = r` и спит на `writerSem`, пока эти `r` читателей не доработают.

**`Unlock`** (писатель):
1. `readerCount.Add(+rwmutexMaxReaders)` — возвращает знак (снова ≥ 0); результат = число читателей, **накопившихся в очереди**, пока держался лок;
2. будит их всех (`Semrelease` на `readerSem` в цикле);
3. `rw.w.Unlock()` — пускает следующего писателя.

Трассировка «3 читателя активны, приходит писатель»:

```
readerCount = 3                       // 3 читателя читают
Lock:  w.Lock() ✓
       readerCount += -2³⁰  → -(2³⁰-3)   // знак < 0: новые RLock теперь спят
       r = -(2³⁰-3) + 2³⁰ = 3            // писатель должен дождаться 3 читателей
       readerWait = 3 → спим на writerSem

(приходит новый RLock: +1 → всё ещё < 0 → спит на readerSem)

3 читателя делают RUnlock: readerWait 3→2→1→0
       последний (0) → Semrelease(writerSem) → писатель проснулся, пишет

Unlock: readerCount += +2³⁰ → 1          // 1 читатель накопился в очереди
        Semrelease(readerSem) ×1 → будим его
        w.Unlock() → пускаем следующего писателя
```

**Почему RWMutex дороже Mutex на чтении** — теперь видно из кода: даже самый дешёвый `RLock` — это атомарный инкремент **общего** `readerCount`. На многих ядрах эта кэш-линия «пинг-понгует» между ними (coherence traffic), и при коротких секциях такой overhead съедает весь выигрыш от параллельных чтений (см. бенчмарк выше: на 1–2 ядрах Mutex впереди). **Starvation писателя** тоже отсюда: шаг 2 в `Lock` сразу глушит **новые** `RLock` (они видят `<0`) — иначе бесконечный поток читателей не давал бы писателю ни единого окна. Цена — пришедший читатель ждёт, пока писатель отработает.

**Писатель ↔ пачка читателей: как именно чередуются.** Если в очереди несколько писателей — ждут ли читатели, пока запишут все? **Нет.** Гарантия из доки Go — *«a blocked Lock call excludes new readers»*: пока писатель объявлен (взял или ждёт `Lock`), блокируются только **новые** `RLock`. Но писатели не «осушаются» подряд: на выходе писатель **сначала будит накопившихся читателей и лишь потом** отпускает внутренний `rw.w` (порядок в `Unlock` выше — цикл `Semrelease` идёт до `w.Unlock`). Поэтому между двумя писателями всегда вклинивается **пачка ждавших читателей**:

```
A пишет; пришёл читатель R → блокируется (readerCount < 0)
B, C ждут на rw.w (ещё даже не объявились как писатели)
A.Unlock: будит R  →  отпускает rw.w
   R читает; B берёт rw.w, видит активного R → ждёт его (readerWait)
R.RUnlock → будит B → B пишет → на B.Unlock проснётся пачка читателей, пришедших при B
…
```

Итог: писатели **сериализуются** между собой (по одному через внутренний `Mutex`), но это чередование «писатель → пачка читателей → писатель», а не «все писатели, потом читатели». Новый читатель ждёт только **текущего** объявленного писателя, а не всю очередь записи.

<details>
<summary>Исходник: <code>RLock</code> / <code>RUnlock</code> / <code>Lock</code> / <code>Unlock</code> (sync/rwmutex.go, упрощённо)</summary>

```go
func (rw *RWMutex) RLock() {
    if rw.readerCount.Add(1) < 0 {
        // писатель ждёт — встаём спать
        runtime_SemacquireRWMutexR(&rw.readerSem, false, 0)
    }
}

func (rw *RWMutex) RUnlock() {
    if r := rw.readerCount.Add(-1); r < 0 {
        rw.rUnlockSlow(r) // писатель ждёт нас
    }
}
func (rw *RWMutex) rUnlockSlow(r int32) {
    // последний уходящий читатель будит писателя
    if rw.readerWait.Add(-1) == 0 {
        runtime_Semrelease(&rw.writerSem, false, 1)
    }
}

func (rw *RWMutex) Lock() {
    rw.w.Lock() // 1. отсечь других писателей
    // 2. объявить писателя; r = число активных читателей
    r := rw.readerCount.Add(-rwmutexMaxReaders) + rwmutexMaxReaders
    // 3. дождаться этих читателей
    if r != 0 && rw.readerWait.Add(r) != 0 {
        runtime_SemacquireRWMutex(&rw.writerSem, false, 0)
    }
}

func (rw *RWMutex) Unlock() {
    // 1. вернуть знак; r = читатели, накопившиеся в очереди
    r := rw.readerCount.Add(rwmutexMaxReaders)
    // 2. разбудить их всех
    for i := 0; i < int(r); i++ {
        runtime_Semrelease(&rw.readerSem, false, 0)
    }
    rw.w.Unlock() // 3. пустить следующего писателя
}
```
</details>

## Типичные ошибки с Mutex

### 1. Копирование Mutex (go vet ловит)

```go
type Safe struct {
    mu sync.Mutex
    v  int
}

// Плохо — копируем структуру вместе с mutex
s1 := Safe{}
s2 := s1 // mu скопирован в неопределённом состоянии!

// Хорошо — передавай указатель
s := &Safe{}
process(s)
```

**Что физически происходит.** `Mutex` — это `state int32` + `sema uint32` (см. «Под капотом» выше). Копирование структуры тупо копирует **байты этих полей** — снимок состояния на момент копии. Возникают два сценария, оба плохие:

- **Скопировали залоченным** (`state` с битом `mutexLocked`): копия рождается «уже залоченной», но `Unlock` сделают на **оригинале** — копию никто никогда не разблокирует. Любой `Lock()` на ней виснет навсегда → дедлок. А если на оригинале кто-то припаркован, ждёт он на семафоре по **адресу оригинала** (очередь в `semtable` ключуется адресом — см. выше); у копии другой адрес → это **другой, ничего не знающий о тех ждущих** семафор.
- **Скопировали разлоченным:** теперь у тебя **два независимых мьютекса** вместо одного. Код думает, что защищает `v` одним локом, а на деле горутина A берёт `s1.mu`, горутина B берёт `s2.mu` — оба проходят **одновременно**, взаимное исключение сломано → гонка по данным, которые мьютекс якобы защищал.

Суть: **состояние лока неотделимо от его адреса**. Скопировав, ты разрываешь связь «лок ↔ его очередь ждущих ↔ защищаемые данные». То же касается `RWMutex`, `WaitGroup`, `Once`, `Cond` — все содержат внутреннее состояние и **не копируемы** после первого использования.

**Где это случается незаметно** (не только явное `s2 := s1`):
- получатель по значению: `func (s Safe) Method()` — `s` копируется на каждом вызове;
- передача структуры в функцию/возврат по значению, а не по указателю;
- `append(slice, s)` / элемент `map[k]Safe` — копирование при росте/присваивании;
- `range` по слайсу структур: `for _, s := range items` — `s` это копия.

`go vet` (анализатор `copylocks`) ловит это статически: `assignment copies lock value` / `passes lock by value`. Правило простое — **типы с мьютексом всегда передавай указателем** (`*Safe`), а методы вешай на `*Safe`.

### 2. Lock без Unlock (deadlock)

```go
func bad(mu *sync.Mutex) {
    mu.Lock()
    if someCondition {
        return // УТЕЧКА: mutex остался locked
    }
    mu.Unlock()
}

// Хорошо — defer гарантирует unlock при любом выходе
func good(mu *sync.Mutex) {
    mu.Lock()
    defer mu.Unlock()
    if someCondition {
        return // OK: defer выполнится
    }
}
```

### 3. Разблокировка без блокировки

```go
var mu sync.Mutex
mu.Unlock() // panic: sync: unlock of unlocked mutex
```

### 4. Рекурсивный Lock (deadlock)

```go
func (s *Safe) A() {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.B() // DEADLOCK: B попытается взять уже захваченный mutex
}

func (s *Safe) B() {
    s.mu.Lock()
    defer s.mu.Unlock()
    // ...
}

// Решение: unexported helper без lock
func (s *Safe) b() { /* логика без lock */ }
func (s *Safe) B() {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.b()
}
```

## `sync.WaitGroup`

Ждёт завершения группы горутин.

```go
var wg sync.WaitGroup

for i, task := range tasks {
    wg.Add(1)               // Add ПЕРЕД запуском горутины
    go func(t Task) {
        defer wg.Done()     // Done при выходе
        process(t)
    }(task)
}

wg.Wait()                   // блокируется пока счётчик не стал 0
```

**Почему `Add` перед `go`?**

```go
// Плохо: race condition
for _, task := range tasks {
    go func(t Task) {
        wg.Add(1)   // если main достигнет Wait() до этой строки — не дождётся горутины
        defer wg.Done()
        process(t)
    }(task)
}

// Правильно: Add в calling goroutine, перед запуском
for _, task := range tasks {
    wg.Add(1)
    go func(t Task) {
        defer wg.Done()
        process(t)
    }(task)
}
```

### WaitGroup + closer goroutine

```go
out := make(chan Result)
var wg sync.WaitGroup

for _, id := range ids {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        out <- fetch(id)
    }(id)
}

// Закрываем out когда все workers завершились
go func() {
    wg.Wait()
    close(out)
}()

for r := range out {
    process(r)
}
```

### Под капотом: одно атомарное слово

```go
type WaitGroup struct {
    noCopy noCopy
    state  atomic.Uint64 // СТАРШИЕ 32 бита — счётчик; МЛАДШИЕ 32 — число ждущих на Wait
    sema   uint32
}
```

**Что такое `noCopy noCopy`.** Это zero-size маркер «меня нельзя копировать после первого использования» — чисто для `go vet`, не для рантайма:

```go
type noCopy struct{}              // 0 байт, на размер WaitGroup не влияет
func (*noCopy) Lock()   {}        // пустые методы — нужны только чтобы
func (*noCopy) Unlock() {}        // реализовать интерфейс sync.Locker
```

Анализатор `copylocks` в `go vet` помечает копию любой структуры, которая содержит `sync.Locker` (тип с методами `Lock/Unlock`). У `Mutex`/`RWMutex` такие методы есть свои → их копии vet ловит автоматически. А у `WaitGroup` собственных `Lock/Unlock` нет, поэтому в неё **встраивают** `noCopy` — чтобы появился Locker и vet так же ругался на копию (`passes lock by value`). Копировать использованную `WaitGroup` нельзя по той же причине, что и `Mutex` (см. «Копирование Mutex» ниже): `sema`-очередь ключуется адресом, а `state` — снимок счётчика; у копии всё рассинхронизируется. Важно: `noCopy` **не запрещает** копирование на уровне компилятора — он лишь даёт `go vet` зацепку для предупреждения.

Счётчик и число «ждунов» упакованы в **одно 64-битное слово**, чтобы менять их одной атомарной операцией:
- **`Add(delta)`** — `state.Add(uint64(delta) << 32)` (сдвиг, т.к. счётчик в старшей половине). Достаёт из результата counter и waiters. `counter < 0` → `panic: negative WaitGroup counter`. Если `counter > 0` или ждущих нет — просто возврат. Если `counter == 0` **и** есть ждущие — будит их всех через `sema`.
- **`Done()`** — это `Add(-1)`.
- **`Wait()`** — в цикле читает `state`: если `counter == 0` — сразу выходит (ничего ждать). Иначе CAS-ом инкрементит счётчик ждущих и паркуется на `sema` до пробуждения из `Add`.

Отсюда понятны правила: `Add` до `go` (иначе `Wait` может увидеть `counter==0` и уйти раньше времени — гонка по тому же слову); число `Done` ровно равно числу `Add` (иначе counter уходит в минус → паника). Раньше (до Go 1.20) тут был хитрый `state1 [3]uint32` с ручным выравниванием под 64 бита на 32-битных платформах — сейчас просто `atomic.Uint64`.

> **`errgroup` вместо «голого» `WaitGroup`.** Если горутины могут вернуть ошибку и нужно «дождаться всех + первая ошибка отменяет остальных», берут `golang.org/x/sync/errgroup`: это `WaitGroup` + распространение ошибки + производный `ctx`, который отменяется при первом фейле, + `SetLimit(n)` (встроенный семафор). Разбор с примером — в [05-error-handling](../05-error-handling.md).

## `sync.Once`

Выполняет функцию ровно один раз, независимо от количества вызывающих горутин.

```go
var (
    instance *Config
    once     sync.Once
)

func GetConfig() *Config {
    once.Do(func() {
        instance = loadConfig() // вызовется только один раз
    })
    return instance
}
```

### Паника внутри Once

Если переданная функция паникует, `once.Do` считается **выполненным**. Повторный вызов `Do` не будет вызван.

```go
var once sync.Once
var initialized bool

once.Do(func() {
    panic("init failed") // паника!
})

once.Do(func() {
    initialized = true // НИКОГДА не выполнится
})
// initialized остаётся false
```

Следствие: если инициализация может провалиться, используй другой паттерн:

```go
var (
    instance *DB
    initErr  error
    once     sync.Once
)

func getDB() (*DB, error) {
    once.Do(func() {
        instance, initErr = connectDB()
    })
    return instance, initErr
}
```

### Под капотом: atomic-флаг + mutex (и почему не просто CAS)

```go
type Once struct {
    done atomic.Uint32 // 0 — ещё не выполняли, 1 — выполнено
    m    Mutex
}

func (o *Once) Do(f func()) {
    if o.done.Load() == 0 { // FAST PATH: одна атомарная загрузка, без лока
        o.doSlow(f)
    }
}

func (o *Once) doSlow(f func()) {
    o.m.Lock()
    defer o.m.Unlock()
    if o.done.Load() == 0 {       // двойная проверка под локом
        defer o.done.Store(1)     // ← Store в DEFER: флаг ставится даже если f паникует
        f()
    }
}
```

Два разбора, ради которых это стоит читать:

- **Почему `done` ставится через `defer`** — это и есть механика Загадки 3: даже если `f()` паникует, `defer o.done.Store(1)` срабатывает при размотке, Once помечается выполненным, и следующий `Do` уже не запустит `f`. Отсюда правило «в падающем инициализаторе возвращай ошибку, а не паникуй».

- **Почему нельзя «просто `CAS(done, 0, 1)` в начале»** — казалось бы, первый, кто сделал CAS, выполняет `f`, остальные видят `done==1` и выходят. Но тогда остальные вышли бы **до** того, как `f` завершилась — и получили бы недоинициализированный объект. Контракт `Once` сильнее: к моменту возврата **любого** `Do` функция `f` гарантированно **завершена и её записи видны**. Это обеспечивает `Mutex` (его `Unlock`→`Lock` даёт happens-before), а `defer done.Store(1)` под локом фиксирует флаг до `Unlock`. То есть это ровно правильное решение той проблемы unsafe publication, что разобрана в [01-memory-model](./01-memory-model.md): быстрый путь читает `done` атомарно (acquire), а медленный — устанавливает порядок через лок.

#### Зачем slow-path вынесен в отдельную функцию

Разделение на `Do` и `doSlow` — не стиль, а трюк под **инлайнинг**. У компилятора есть бюджет инлайна (~80 «стоимости»): функцию встраивают в вызывающего, только если она маленькая. `Do` — это `Load` + сравнение + вызов, она крошечная → **инлайнабельна**. `doSlow` — `Lock`/`defer`/`f()` — большая и с `defer`, → не инлайнится. Если бы slow-path лежал прямо в `Do`, та раздулась бы и **перестала** встраиваться.

Что это даёт: тело `Do` встраивается в **каждое** место вызова `once.Do(...)`. На горячем пути остаётся буквально `if once.done.Load() == 0 { … }` — **один атомарный Load + предсказанный branch, без `CALL`/`RET`**. Реальный вызов (`doSlow`) — только на самый первый раз. Проверяется через `go build -gcflags=-m` (выдаёт `inlining call to sync.(*Once).Do` в вызывающего; `doSlow` не инлайнится).

Это типовой приём всего пакета `sync`: «вынеси холодный путь в отдельную функцию, чтобы горячий инлайнился». Так же сделаны `Mutex.Lock`→`lockSlow`, `RWMutex.RUnlock`→`rUnlockSlow`. Подробнее про инлайнинг (бюджет, что он экономит) — в [03-interfaces-method-sets-and-nil](../03-interfaces-method-sets-and-nil.md), раздел про инлайнинг.

## `sync.Cond`

Условная переменная: горутина ждёт пока **условие** не станет истинным.

```go
type Queue struct {
    mu    sync.Mutex
    cond  *sync.Cond
    items []int
}

func NewQueue() *Queue {
    q := &Queue{}
    q.cond = sync.NewCond(&q.mu)
    return q
}

func (q *Queue) Push(v int) {
    q.mu.Lock()
    q.items = append(q.items, v)
    q.mu.Unlock()
    q.cond.Signal() // разбудить одну ожидающую горутину
}

func (q *Queue) Pop() int {
    q.mu.Lock()
    defer q.mu.Unlock()
    for len(q.items) == 0 {
        q.cond.Wait() // атомарно: unlock mu + ждёт сигнала + lock mu
    }
    v := q.items[0]
    q.items = q.items[1:]
    return v
}
```

### `Signal` vs `Broadcast`

- `Signal()` — будит **одну** горутину (если несколько ждут — случайную)
- `Broadcast()` — будит **все** ожидающие горутины

### Когда `sync.Cond`, когда channel

| | `sync.Cond` | Channel |
|---|---|---|
| Broadcast ("все проснитесь") | ✅ `Broadcast()` | ✅ `close(done)` |
| Передача данных | ❌ (только сигнал) | ✅ |
| Сложное условие ожидания | ✅ for-loop с проверкой | ⚠️ сложнее |
| Производительность | быстрее при высокой конкуренции | overhead на channel ops |

**Практически** — `sync.Cond` используется редко. В большинстве случаев channel понятнее. `Cond` нужен когда нужно Broadcast + состояние защищено тем же mutex.

## `sync.Pool`

Пул объектов для переиспользования, снижает аллокации.

```go
var bufPool = sync.Pool{
    New: func() any {
        return make([]byte, 0, 4096) // создаётся только при пустом pool
    },
}

func encode(data []byte) string {
    buf := bufPool.Get().([]byte)
    defer func() {
        buf = buf[:0]       // сбросить длину, сохранить capacity
        bufPool.Put(buf)    // вернуть в pool
    }()
    
    buf = append(buf, data...)
    // ... encode
    return string(buf)
}
```

### Поведение при GC

`sync.Pool` — **не постоянное хранилище**. Объекты могут быть удалены GC в любой момент (обычно на каждом GC цикле). Не используй Pool для хранения state между запросами.

### Когда Pool полезен

- Шорт-лайфовые объекты с высокой аллокацией (буферы, временные структуры)
- HTTP/RPC handlers: пул буферов для encode/decode
- `fmt.Fprintf` в stdlib использует `sync.Pool` для буферов

### Когда Pool вреден

- Объект требует инициализации состояния (риск "dirty" объектов)
- Объект хранит ресурсы (connections, file handles) — используй явный pool с close
- Редкие аллокации — overhead Pool выше чем прямая аллокация

### Под капотом: per-P шардинг + victim cache

`sync.Pool` масштабируется почти без контеншена, потому что **шардирован по P** (процессорам планировщика): у каждого P свой кусок пула, и горутина почти всегда работает со **своим**, не трогая чужие ядра.

```go
type poolLocalInternal struct {
    private any       // ОДИН слот только для своего P — доступ без синхронизации
    shared  poolChain // lock-free дек: свой P — с головы, чужие P — воруют с хвоста
}
// Pool.local — массив [GOMAXPROCS]poolLocal, по одному элементу на P
```

Картинка (GOMAXPROCS=3):

```
            P0                  P1                  P2
      ┌───────────┐       ┌───────────┐       ┌───────────┐
      │ private:x │       │ private:y │       │ private:_ │
      │ shared:   │       │ shared:   │       │ shared:   │
      │ [a b c]   │◀─────╴│ [d e]     │       │ [f]       │
      └───────────┘ steal └───────────┘       └───────────┘
       свой P берёт          свой P            ↑ P2 пусто — крадёт
       с головы (c)          с головы          с ХВОСТА у P0 (a)
```

Свой P работает с **головой** своего дека (LIFO, без атомиков на `private`); чужие P, если у них пусто, **воруют с хвоста** — пока элементов много, голова и хвост далеко друг от друга, owner и вор не пересекаются.

**А если элемент один — owner и вор метят в один слот?** Тут спасает то, что `head` и `tail` упакованы в **одно** 64-битное слово, и обе операции завершаются **атомарным CAS** по нему:

```go
type poolDequeue struct {
    headTail atomic.Uint64 // [ head(32) | tail(32) ] — оба индекса в ОДНОМ слове
    vals     []eface
}
// popHead (owner):  CAS(headTail, old, pack(head-1, tail))
// popTail (вор):    CAS(headTail, old, pack(head,   tail+1))
```

- **`head == tail` — дек пуст** (ноль элементов). Оба, и `popHead`, и `popTail`, первым делом это проверяют → «брать нечего». Конфликта нет.
- **Ровно один элемент** (head и tail зажимают один слот): owner и вор делают CAS по **одному и тому же** `headTail`. Атомарный CAS пропустит только одного; проигравший перечитает слово, увидит `head == tail` (пусто) и уйдёт. Последний элемент достаётся **ровно одному** — ни двойной выдачи, ни рваного состояния.

Это та же механика CAS-loop, что у `Mutex.state` и `Once.done`: корректность держится на «поменяй, только если не изменилось», а упаковка обоих индексов в одно CAS-абельное слово делает безопасной границу «пусто / один элемент».

**`Get` — по возрастанию цены, первый успех выигрывает:**

```
1. procPin()              привязать горутину к своему P (запрет преемпции)
2. private своего P?      → есть → вернуть (САМЫЙ дешёвый путь, без атомиков)
3. голова своего shared?  → есть → вернуть
4. хвост shared чужих P?  → украсть у соседа
5. victim cache?          → взять оттуда (см. ниже)
6. New()                  → создать новый
```

**`Put` (тоже под `procPin`):** положить в `private` своего P, если он пуст; иначе — в голову своего `shared`.

Закрепление за P (`procPin`) — почему «почти без контеншена»: в типичном горячем цикле `Get`/`Put` бьют в шаги 2 и `private`, то есть **в локальный слот своего P**, без атомиков и без обращения к чужим ядрам. Кража (шаг 4) — редкий fallback.

#### Victim cache (Go 1.13+): почему объект переживает один GC, но не два

На каждом GC зарегистрированный `poolCleanup` сдвигает уровни:

```
            local (живой)        victim (жертвенный)
старт:      [объекты A]          [пусто]

── GC #1 ──►  victim ← local,  local ← nil
            [пусто]              [объекты A]      ← A ещё достижимы через Get (шаг 5)

(между GC: Get может достать A из victim; Put кладёт новое в local)

── GC #2 ──►  victim ← local,  local ← nil
            [пусто]              [новое из local] ← A, если не забрали, ТЕПЕРЬ собраны GC
```

То есть объект не выбрасывается сразу: один GC он живёт в `victim` (его ещё можно достать), и только если за следующий цикл не понадобился — на **втором** GC окончательно собирается.

**Зачем так:** без victim cache пул обнулялся бы целиком на каждом GC, и сразу после сборки горячий путь ловил бы шквал `New()` (всплеск аллокаций ровно тогда, когда GC и так нагрузил систему). Victim размазывает это: половина объектов переживает один цикл.

**Практический вывод не меняется:** Pool — **не хранилище**. Рассчитывать, что объект доживёт, нельзя (максимум — два GC), но и обнуление мягче, чем «всё на каждом GC».

## `sync.Map`

Потокобезопасный map, оптимизированный для двух конкретных use case.

```go
var m sync.Map

// Store
m.Store("key", "value")

// Load
v, ok := m.Load("key")
if ok {
    fmt.Println(v.(string))
}

// LoadOrStore — atomic get-or-set
actual, loaded := m.LoadOrStore("key", "default")

// Delete
m.Delete("key")

// Range — итерация (не safe для concurrent modification)
m.Range(func(k, v any) bool {
    fmt.Println(k, v)
    return true // false = stop iteration
})
```

### Когда `sync.Map`, когда `map + mutex`

`sync.Map` оптимален **только** для:
1. Ключ пишется один раз, потом только читается (append-only)
2. Разные горутины читают/пишут **непересекающиеся** наборы ключей

Во всех остальных случаях — `map + sync.RWMutex` быстрее:

```go
// Типичная read-heavy cache — RWMutex быстрее
type Cache struct {
    mu sync.RWMutex
    m  map[string]Entry
}
```

**Почему** (кратко): путь чтения `sync.Map` lock-free, а `RWMutex` даже на `RLock` пишет в общий счётчик → на многих ядрах его кэш-линия «пинг-понгует» и читатели тормозят друг друга. На 1 ядре и при записи в один горячий ключ `RWMutex` обычно быстрее. Детальный разбор устройства (две реализации: read/dirty до Go 1.24 и hash-trie с 1.24), CPU-уровень и бенчмарки — в [map-internals/04-sync-map](../map-internals/04-sync-map.md).

## `atomic` — операции без mutex

Атомарные операции на примитивных типах без lock overhead. Реализованы аппаратными инструкциями CPU (`LOCK XADD`, `CMPXCHG` на x86), а не блокировкой.

### Как это работает между ядрами (вкратце)

«Атомарно» = операция read-modify-write (прочитать → изменить → записать) выполняется как **неделимое целое**: другое ядро не может вклиниться и увидеть промежуточное состояние. На железе это обеспечивается так:

- **Эксклюзивный захват кэш-линии.** По протоколу когерентности (MESI) ядро на время операции переводит нужную cache line в состояние **Exclusive/Modified** — другие ядра не могут одновременно её менять. На x86 это и делает префикс **`LOCK`** (`LOCK XADD`, `LOCK CMPXCHG`): на время инструкции линия «заперта» за этим ядром. Раньше при невыровненных данных был дорогой bus lock на всю шину; сейчас — обычно лок на уровне одной кэш-линии.
- **CAS как одна инструкция.** `CompareAndSwap` — это аппаратный `CMPXCHG` (x86) / `LDREX`+`STREX`-петля (ARM): сравнение и запись неделимы. Весь lock-free Go стоит на нём.
- **Барьер памяти.** Atomic — это ещё и **memory fence**: запрещает компилятору и CPU переупорядочивать обращения через него и делает запись видимой другим ядрам. Поэтому atomic решает не только «не рваться», но и **видимость** (с Go 1.19 atomic'и seq-consistent).

Цена: атомарная инструкция дороже обычной (десятки нс при контеншене — линия «пинг-понгует» между ядрами), но **на порядок дешевле** мьютекса с парковкой. Полный разбор (store buffer, MESI, `LOCK`-префикс, fences, x86 TSO vs ARM weak) — в [hardware-and-os/04-atomics-and-memory-ordering](../../10-devops-and-observability/hardware-and-os/04-atomics-and-memory-ordering.md) и [03-cache-coherence-and-mesi](../../10-devops-and-observability/hardware-and-os/03-cache-coherence-and-mesi.md).

### Пять механик (плюс And/Or в 1.23)

Все атомарные операции сводятся к нескольким примитивам:

| Операция | Что делает атомарно | Возвращает |
|---|---|---|
| `Load` | прочитать значение | значение |
| `Store(new)` | записать значение | — |
| `Swap(new)` | записать new | **старое** значение |
| `Add(delta)` | прибавить delta (можно отрицательный) | **новое** значение |
| `CompareAndSwap(old, new)` | если текущее == old → записать new | `bool` (удалось ли) |
| `And(mask)` / `Or(mask)` ¹ | побитовые `&` / `\|` | старое значение |

¹ — `And`/`Or` добавлены в Go 1.23 (`atomic.AndInt64`, метод `.And()` и т.п.).

**CAS** (Compare-And-Swap) — фундамент всех lock-free алгоритмов: «поменяй, только если значение не изменилось с тех пор, как я его прочитал».

### Типизированный API (Go 1.19+) — предпочтительный

```go
var counter atomic.Int64
counter.Add(1)
val := counter.Load()
counter.CompareAndSwap(val, val+1)
```

Почему именно типизированные обёртки:
- нельзя случайно обратиться к переменной **не**атомарно — внутреннее поле приватное, доступ только через методы;
- не нужно следить за 8-байтным выравниванием на 32-bit платформах — обёртка гарантирует его сама (та же проблема, что у `WaitGroup`, см. выше).

Существует и старый функциональный API на `*T` (`atomic.AddInt64(&x, 1)`, `atomic.LoadInt64`, `atomic.CompareAndSwapInt64`) — он остаётся в stdlib и им пользуются внутренности рантайма (где нельзя завести поле-обёртку). Для своего кода бери типизированный.

### Типизированные типы (Go 1.19+)

| Тип | Для чего | `Add` | `CAS` | `And/Or` (1.23) |
|---|---|:---:|:---:|:---:|
| `atomic.Int32` / `Int64` | знаковые счётчики | ✅ | ✅ | ✅ |
| `atomic.Uint32` / `Uint64` / `Uintptr` | беззнаковые, битмаски | ✅ | ✅ | ✅ |
| `atomic.Bool` | флаги | ❌ | ✅ | ❌ |
| `atomic.Pointer[T]` | указатели, **типобезопасно** | ❌ | ✅ | ❌ |

### CAS-loop: оптимистичные обновления

Когда нужной операции нет (нет `atomic.Mul`, атомарного max и т.п.) — делают через **CAS в цикле**: прочитать, посчитать, попытаться записать; если кто-то опередил — повторить.

```go
var n atomic.Int64

// атомарно: n = max(n, x)
func atomicMax(n *atomic.Int64, x int64) {
    for {
        old := n.Load()
        if x <= old {
            return // уже не меньше
        }
        if n.CompareAndSwap(old, x) {
            return // успех
        }
        // кто-то изменил n между Load и CAS → повторяем с новым old
    }
}
```

Это и есть **lock-free**: без блокировок, прогресс гарантирован (хотя отдельная горутина может «крутиться» при высокой конкуренции).

### `atomic.Pointer[T]`

Для атомарной подмены целого объекта (hot-reload конфига, lock-free снапшот) — типобезопасно, без приведений и паник (Go 1.19+):

```go
var cfg atomic.Pointer[Config]
cfg.Store(&Config{MaxConn: 100})
c := cfg.Load() // *Config, без .(...)
```

Паттерн чтения-без-локов: писатель готовит новый `*Config` и `Store`-ит его одним атомарным действием; читатели делают `Load()` без блокировки. Компилятор не даст положить в `Pointer[Config]` другой тип.

### Когда atomic, когда mutex

| | `atomic` | `mutex` |
|---|---|---|
| Простые счётчики, флаги | ✅ | ❌ overhead |
| Произвольные структуры | ❌ | ✅ |
| CAS-loop (оптимистичные обновления) | ✅ | ❌ |
| Несколько полей **согласованно** | ❌ | ✅ |
| Атомарная подмена одного указателя | ✅ `Pointer[T]` | ⚠️ можно, но дороже |
| Lock-free алгоритмы | ✅ | ❌ |

**Правило:** atomic — для одиночных счётчиков/флагов/указателей. Как только нужно поменять **несколько полей согласованно** — это уже инвариант, его держит mutex.

```go
// ОДНО значение — atomic к месту: feature flag (часто читается, редко пишется)
var featureEnabled atomic.Bool
if featureEnabled.Load() { // hot path, миллионы раз/сек
    doNewBehavior()
}
featureEnabled.Store(true) // редко
```

**Как НЕ надо — два atomic на связанные поля.** Каждое поле атомарно, но **пара — нет**: между двумя `Store` есть окно, и читатель видит рассогласованный снимок.

```go
type Rect struct {
    w, h atomic.Int64
}
func (r *Rect) Set(w, h int64) {
    r.w.Store(w) // ← между этими двумя Store'ами читатель
    r.h.Store(h) //   может увидеть НОВЫЙ w и СТАРЫЙ h
}
func (r *Rect) Area() int64 {
    return r.w.Load() * r.h.Load() // площадь от несогласованной пары w/h
}
```

`-race` тут промолчит (все доступы атомарны!) — но логика битая: `w` и `h` обязаны меняться **вместе**, это инвариант, а atomic его не держит.

**Как надо — mutex на всю операцию** (критическая секция = «поменять/прочитать обе как одно целое»):

```go
type Rect struct {
    mu   sync.Mutex
    w, h int64
}
func (r *Rect) Set(w, h int64) {
    r.mu.Lock()
    defer r.mu.Unlock()
    r.w, r.h = w, h // оба поля под одним локом — атомарно как пара
}
func (r *Rect) Area() int64 {
    r.mu.Lock()
    defer r.mu.Unlock()
    return r.w * r.h // согласованный снимок
}
```

**Lock-free альтернатива** — если объект менять целиком и редко: держать **неизменяемый** снимок и атомарно подменять указатель (`atomic.Pointer`). Инвариант сохраняется, потому что подмена указателя атомарна:

```go
var rect atomic.Pointer[Rect] // Rect здесь immutable: создали — не меняем поля
rect.Store(&Rect{W: 10, H: 20})  // подменили весь объект одним Store
r := rect.Load()                  // согласованный снимок целиком
_ = r.W * r.H
```

## `singleflight` — дедупликация одинаковых запросов

`golang.org/x/sync/singleflight` — не из stdlib, но де-факто стандарт. Решает **cache stampede / thundering herd**: когда N горутин одновременно промахиваются по кэшу и идут за **одним и тем же** ключом, реально выполняется **один** вызов, остальные ждут и получают тот же результат.

### Методы

| Метод | Поведение |
|---|---|
| `Do(key, fn)` | блокирующий; дедуплицирует по key; возвращает `(v, err, shared)` |
| `DoChan(key, fn)` | возвращает `<-chan Result` — для `select` с `ctx.Done()` |
| `Forget(key)` | убрать in-flight ключ (например, чтобы не «залипла» ошибка) |

### Основа: `Group`, `call`, `Result`

```go
type Group struct {
    mu sync.Mutex
    m  map[string]*call   // in-flight вызовы по ключу
}

type call struct {
    wg    sync.WaitGroup   // Do-waiter'ы ждут на нём
    val   any
    err   error
    dups  int              // сколько вызовов присоединилось (→ shared)
    chans []chan<- Result  // DoChan: по каналу на каждого вызывающего
}

type Result struct {
    Val    any
    Err    error
    Shared bool
}
```

На **один** `call` (один ключ in-flight) подвешены и waiter'ы `Do` (через `wg`), и каналы `DoChan` (через `chans`). `fn` выполняется **один раз**, результат раздаётся всем — собственно `doCall`:

```go
func (g *Group) doCall(c *call, key string, fn func() (any, error)) {
    c.val, c.err = fn()           // (+ обработка panic/Goexit, см. ниже)
    g.mu.Lock()
    c.wg.Done()                   // будим Do-followers
    if g.m[key] == c {
        delete(g.m, key)          // снимаем in-flight запись
    }
    for _, ch := range c.chans {  // раздаём DoChan-waiter'ам — ПОД ЛОКОМ
        ch <- Result{c.val, c.err, c.dups > 0}
    }
    g.mu.Unlock()
}
```

### `Do` — leader + followers

```go
func (g *Group) Do(key string, fn func() (any, error)) (v any, err error, shared bool) {
    g.mu.Lock()
    if g.m == nil {
        g.m = make(map[string]*call)
    }
    if c, ok := g.m[key]; ok {     // FOLLOWER: вызов по ключу уже летит
        c.dups++
        g.mu.Unlock()
        c.wg.Wait()                // ждём, пока leader доделает
        return c.val, c.err, true  // читаем ОБЩИЙ результат
    }
    c := new(call)                 // LEADER: первый по этому ключу
    c.wg.Add(1)
    g.m[key] = c
    g.mu.Unlock()

    g.doCall(c, key, fn)           // выполнить fn синхронно и разбудить всех
    return c.val, c.err, c.dups > 0
}
```

Первый по ключу — *leader*: регистрирует `call`, синхронно гоняет `fn`. Остальные — *followers*: видят существующий `call`, делают `c.dups++` (отсюда `shared=true`) и блокируются на `c.wg.Wait()`, после чего читают `c.val/c.err`.

Использование (защита от cache stampede):

```go
type Service struct {
    sf    singleflight.Group
    cache *Cache
}

func (s *Service) GetUser(ctx context.Context, id string) (*User, error) {
    if u, ok := s.cache.Get(id); ok {
        return u, nil
    }
    // Do: для одного id реально выполнится ЛИШЬ у первой горутины,
    // остальные с тем же id заблокируются и получат тот же (v, err)
    v, err, shared := s.sf.Do(id, func() (any, error) {
        u, err := loadUserFromDB(ctx, id) // дорогой запрос — один на всех
        if err == nil {
            s.cache.Set(id, u)
        }
        return u, err
    })
    _ = shared // true, если результат разделён с другими вызовами
    if err != nil {
        return nil, err
    }
    return v.(*User), nil
}
```

### `DoChan` — уйти по своему `ctx`

Проблема `Do`: он блокирующий, и `ctx` замыкается внутри `fn` от **первого** вызывающего — остальные не могут уйти по своему дедлайну. `DoChan` вместо ожидания на `wg` отдаёт **канал**:

```go
func (g *Group) DoChan(key string, fn func() (any, error)) <-chan Result {
    ch := make(chan Result, 1)        // ← БУФЕР 1 (критично, см. «Под капотом»)
    g.mu.Lock()
    if g.m == nil {
        g.m = make(map[string]*call)
    }
    if c, ok := g.m[key]; ok {
        c.dups++
        c.chans = append(c.chans, ch) // присоединяем НАШ канал к летящему call
        g.mu.Unlock()
        return ch
    }
    c := &call{chans: []chan<- Result{ch}}
    c.wg.Add(1)
    g.m[key] = c
    g.mu.Unlock()

    go g.doCall(c, key, fn)           // для DoChan fn крутится в ОТДЕЛЬНОЙ горутине
    return ch
}
```

Каждый ждущий делает `select` на **свой** `ctx.Done()`:

```go
func (s *Service) GetUser(ctx context.Context, id string) (*User, error) {
    if u, ok := s.cache.Get(id); ok {
        return u, nil
    }

    ch := s.sf.DoChan(id, func() (any, error) {
        // ВАЖНО: НЕ берём ctx вызывающего — он у каждого свой.
        // Запрос живёт по своему таймауту, не привязанному к одному клиенту.
        reqCtx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
        defer cancel()
        u, err := loadUserFromDB(reqCtx, id)
        if err == nil {
            s.cache.Set(id, u)
        }
        return u, err
    })

    select {
    case res := <-ch:
        if res.Err != nil {
            return nil, res.Err
        }
        // res.Shared — был ли результат разделён с другими вызовами
        return res.Val.(*User), nil
    case <-ctx.Done():
        // ЭТОТ вызывающий ушёл по своему дедлайну. fn продолжает крутиться
        // для остальных ждущих — мы лишь перестали ждать.
        return nil, ctx.Err()
    }
}
```

Две тонкости:
- **Уход по `ctx.Done()` НЕ отменяет `fn`.** Дорогой запрос доработает для остальных ждущих этот ключ — отменилось лишь *наше ожидание*. Поэтому `fn` нельзя завязывать на ctx конкретного клиента (иначе его отмена убила бы общий запрос для всех — это и есть баг `Do`).
- **Утечки горутины нет:** канал от `DoChan` буферизован (cap 1) — почему именно так, ниже.

### Под капотом: почему `cap 1`, `Forget`, паника

**Почему канал `cap 1` — условие корректности, а не оптимизация.** Видно по `doCall`: рассылка идёт в цикле **под `g.mu`**. Если вызывающий ушёл по своему `ctx.Done()` и не читает канал, то будь он **unbuffered**, `ch <- Result{...}` заблокировался бы навсегда — **держа мьютекс всей `Group`** → залип бы весь singleflight. Буфер 1 (канал одноразовый, в него шлют ровно один `Result`) гарантирует: send кладёт в буфер и возвращается немедленно, а заброшенный канал собирается GC. Тот же принцип «send под локом обязан не блокировать», что в рантайме.

**`Forget(key)`** — просто `delete(g.m, key)` под локом: снимает in-flight запись досрочно, следующий `Do` станет новым leader'ом и запустит свежий `fn`.

**Паника в `fn`** не глушится: `doCall` ловит её в `*panicError`. `Do`-followers после `wg.Wait()` сами делают `panic(e)` (а на `runtime.Goexit()` — `Goexit()`); для `DoChan` панику в канал не доставить, поэтому `doCall` делает `go panic(e)` — **роняет процесс** с оригинальным стеком (паника в `fn` = баг, терять нельзя).

### Подводные камни

- **Общий результат на всех.** Все ждущие получают **один и тот же** `v` и `err`. Если `fn` вернула ошибку — её получат все. Если `v` — мутабельный объект, его нельзя менять у получателей (это общий указатель).
- **Отмена контекста.** `ctx` замыкается внутри `fn` от **первого** вызывающего. Если он отменится, упадут все ждущие. Когда у каждого свой дедлайн — используй `DoChan` + `select { case r := <-ch: case <-ctx.Done(): }`, чтобы конкретный вызывающий мог уйти по своему ctx.
- **Head-of-line blocking.** Зависший `fn` держит всех ждущих этого ключа. `DoChan` + таймаут на стороне вызывающего спасает.
- **Кэширование ошибок.** `Do` не кэширует результат сам — он лишь дедуплицирует *одновременные* вызовы. Между «волнами» кэшировать надо самому. `Forget(key)` помогает сбросить, если первый вызов завершился ошибкой и не нужно её «расшаривать» следующей волне.

Задача и практика (формулировка, базовое решение, тесты) — в [coding-tasks/concurrency/06-singleflight](../../12-interview-practice/coding-tasks/concurrency/06-singleflight.md).

## Шпаргалка: выбор примитива

```
Нужно передать данные между goroutines?
  → channel

Нужно защитить shared state?
  Reads >> Writes (>80% reads)?
    → sync.RWMutex
  Иначе?
    → sync.Mutex

Нужна ленивая инициализация?
  → sync.Once

Дождаться группы горутин?
  Могут вернуть ошибку / нужна отмена остальных при первой?
    → errgroup
  Просто дождаться завершения?
    → sync.WaitGroup

Нужен pool временных объектов?
  → sync.Pool

Нужны счётчики/флаги без lock?
  → sync/atomic

Нужна атомарная подмена целого объекта (hot-reload)?
  → atomic.Pointer[T]

N горутин запрашивают один ключ (cache stampede)?
  → singleflight

Нужен thread-safe map (read-heavy, разные ключи)?
  → sync.Map
  Иначе:
  → map + sync.RWMutex
```

## Разбор примеров-загадок

### Загадка 1: RLock → Lock в одной горутине

```go
var mu sync.RWMutex
mu.RLock()
mu.Lock()   // ?
```

<details>
<summary>Ответ</summary>

```
deadlock — fatal error: all goroutines are asleep
```

`Lock()` ждёт освобождения **всех** read-локов, но `RUnlock()` в этой же горутине так и не наступит — она застряла на `Lock()`. RWMutex **не поддерживает upgrade** RLock→Lock.

Коварнее: даже рекурсивный `RLock()` может зависнуть. Если между двумя `RLock()` одной горутины другой поток вызвал `Lock()`, второй `RLock()` встанет в очередь **за** ожидающим писателем (чтобы не морить его голодом) → взаимная блокировка. Вывод: не бери RWMutex повторно/рекурсивно.
</details>

---

### Загадка 2: лишний Done → паника

```go
var wg sync.WaitGroup
wg.Add(1)
go func() {
    wg.Done()
    wg.Done()  // ?
}()
wg.Wait()
```

<details>
<summary>Ответ</summary>

```
panic: sync: negative WaitGroup counter
```

Счётчик ушёл ниже нуля → паника. Частые причины: лишний `Done()`, `Add` внутри горутины (гонка с `Wait`), повторное использование `wg` до полного `Wait`. Правило: число `Add` строго равно числу `Done`, `Add` — в вызывающей горутине **до** `go`.
</details>

### Загадка 3: sync.Once + паника «съедает» инициализацию

```go
var once sync.Once
func tryInit() {
    defer func() { recover() }()
    once.Do(func() { panic("boom") })
}

func main() {
    tryInit()
    once.Do(func() { fmt.Println("init") })  // ?
    fmt.Println("end")
}
```

<details>
<summary>Ответ</summary>

```
end
```

`"init"` **не печатается**. Первый `Do` запаниковал, но Once уже пометил себя выполненным — любой следующий `Do` игнорируется навсегда. Поэтому в инициализаторе, который может упасть, нельзя паниковать «вникуда»: возвращай ошибку через замыкание (`instance, err = ...`) и решай повторять или нет на уровне выше.
</details>

### Загадка 4: atomic + обычный доступ к одной переменной

```go
var counter int64
go func() { atomic.AddInt64(&counter, 1) }()
go func() { counter++ }()   // ?
```

<details>
<summary>Ответ</summary>

`go test -race` репортит **data race**, даже что один из доступов «атомарный». Атомарность работает, только если **все** обращения к переменной идут через `atomic`. Смешивание `atomic.AddInt64` и обычного `counter++` = гонка (компилятор/CPU может переупорядочить, прочитать рваное значение).

Правило: переменную под `atomic` трогают **исключительно** через `atomic.*` (или новый типизированный `atomic.Int64` — он не даёт случайно обратиться напрямую).
</details>

### Загадка 5: defer Unlock и долгая работа под локом

```go
func (c *Cache) GetOrLoad(key string) Value {
    c.mu.Lock()
    defer c.mu.Unlock()
    if v, ok := c.m[key]; ok {
        return v
    }
    v := slowLoadFromDB(key)  // ?  держим Lock всё это время
    c.m[key] = v
    return v
}
```

<details>
<summary>Ответ</summary>

Баг производительности: `defer c.mu.Unlock()` держит **эксклюзивный** лок на всё время `slowLoadFromDB` — остальные горутины (даже читатели) стоят. Под глобальным локом нельзя делать I/O / медленные вызовы.

Фиксы: загружать вне лока (double-checked), либо `singleflight` чтобы не грузить один ключ N раз. `defer` удобен, но «растягивает» критическую секцию до конца функции — иногда нужен ручной `Unlock()` раньше.
</details>

## Interview-ready answer

**1. Когда RWMutex лучше Mutex?**

- Когда чтений ≫ записей (ориентир >80%) и критическая секция не однострочная. При частых записях RWMutex хуже: писатель ждёт всех читателей, плюс свой overhead. Короткая секция → обычный Mutex быстрее.

**2. RWMutex реентерабельный?**

- Нет. RLock→Lock в одной горутине — дедлок (нет upgrade). Рекурсивный RLock тоже опасен: второй RLock может встать за ожидающим писателем. Не бери лок повторно.

**3. Как работает sync.Once и что при панике?**

- `Do` выполняет функцию ровно раз (быстрый atomic-флаг + lock на медленном пути). Паника внутри всё равно помечает Once выполненным — следующий `Do` не запустится. Для падающей инициализации возвращай ошибку, не паникуй.

**4. atomic или mutex?**

- atomic — для одиночных счётчиков/флагов (lock-free, дёшево). Mutex — для нескольких полей «атомарно» или произвольных структур. Нельзя смешивать atomic и прямой доступ к одной переменной — это гонка. С Go 1.19 — типизированные `atomic.Int64/Bool/Pointer`.

**5. sync.Map vs map + RWMutex?**

- `sync.Map` выигрывает в двух сценариях: append-only (ключ пишется раз, дальше читается) или непересекающиеся наборы ключей у горутин. Иначе `map + RWMutex` быстрее — `sync.Map` держит два внутренних map и при частых записях постоянно их промотирует.

**6. Почему нельзя копировать sync-типы?**

- `Mutex`, `WaitGroup`, `Once`, `Cond` содержат внутреннее состояние; копия = рассинхрон (lock на копии не блокирует оригинал). `go vet -copylocks` ловит «passes lock by value» — всегда передавай указателем.

**7. Что такое CAS и зачем CAS-loop?**

- CAS (`CompareAndSwap`) — «запиши new, только если значение всё ещё == old». Это база lock-free алгоритмов. Когда нужной атомарной операции нет (max, умножение, обновление структуры по указателю), её делают через CAS в цикле: Load → посчитать → CompareAndSwap → при неудаче повторить. Прогресс гарантирован без блокировок.

**8. Как атомарно подменить целый объект (hot-reload конфига)?**

- `atomic.Pointer[T]` (Go 1.19+): писатель готовит новый `*Config` и `Store`-ит его одним атомарным действием, читатели делают `Load()` без блокировки (lock-free снапшот). Типобезопасно — компилятор не даст положить другой тип. Для нескольких полей согласованно — это уже инвариант, нужен mutex.

**9. Что такое singleflight и зачем?**

- `golang.org/x/sync/singleflight` дедуплицирует одновременные запросы по ключу: при cache stampede (N горутин промахнулись по одному ключу) реально выполняется один вызов, остальные ждут и получают тот же результат. Подводные камни: общий `err` на всех, отмена ctx первого вызывающего валит всех (нужен `DoChan` + свой `select`), head-of-line blocking.

**10. Как устроен Mutex и что такое starvation mode?**

- Внутри — `state int32` (биты: locked/woken/starving + счётчик ждущих) и `sema`. Незанятый лок берётся одним `CAS` без сисколов. Если занят — сначала **спин** (несколько активных итераций, дешевле парковки на multicore), потом парковка через семафор рантайма. Два режима: **normal** — разбуженный конкурирует с новоприбывшими (throughput, но риск голодания); **starvation** — если горутина ждёт >1 мс, лок передаётся напрямую первому в очереди, а новички сразу встают в хвост (гарантия против вечного ожидания). Переключение туда-обратно по порогу 1 мс.

**11. Почему sync.Pool масштабируется и при чём тут GC?**

- Пул шардирован по P: у каждого P свой `private`-слот (без синхронизации) + lock-free дек `shared`, из которого другие P могут «воровать» с хвоста. Поэтому горутины обычно бьют в свой локальный слот, не трогая чужие кэш-линии. При GC объекты не выбрасываются сразу: срабатывает **victim cache** — `victim ← local`, `local ← nil`; забрать ещё можно, но на следующем GC, если не пригодились, окончательно собираются. Поэтому объект переживает один GC, но не два, и Pool нельзя использовать как хранилище.
