Cassandra — распределённая **wide-column** база данных: строка живёт внутри партиции, набор колонок у разных строк может отличаться, а сама партиция целиком лежит на фиксированном наборе узлов. Система собрана из двух источников: способ раскладывать данные по узлам и сходиться после сбоя взят из Amazon Dynamo, а модель данных (партиция, строки внутри неё, колонки) — из Google BigTable.

Главное архитектурное решение Cassandra: в кластере нет ведущего узла. Любой узел принимает любой запрос, а согласованность настраивается не на уровне кластера, а на уровне отдельного запроса. Отсюда и её ниша, и её цена: запись масштабируется почти линейно, но нет join'ов, ad-hoc запросов и привычных транзакционных инвариантов — схема проектируется от запросов, а не от сущностей.

Описание defaults ориентировано на Cassandra 5.0 (последняя стабильная ветка). Где поведение заметно менялось между версиями, это отмечено отдельно.

> **ScyllaDB** — совместимая реализация той же модели, переписанная на C++ без JVM. Протокол CQL, модель данных и все решения из этой статьи применимы к ней без изменений; отличается только движок и, как следствие, число узлов на ту же нагрузку. Пример миграции — история Discord в [highload-design-patterns.md](../../05-system-design/highload-design-patterns.md).

## Где используется

- потоки событий с очень высокой скоростью записи: телеметрия, клики, показы;
- данные, похожие на временной ряд, где запись идёт в конец, а чтение — по недавнему окну;
- ленты активности и истории сообщений, читаемые по одному владельцу;
- журналы аудита, которые пишутся всегда и почти не изменяются;
- хранилище, размазанное по нескольким дата-центрам с локальным чтением в каждом;
- системы, где доступность на запись важнее строгой согласованности.

Общий признак: заранее известный и стабильный набор запросов, каждый из которых достаёт данные по конкретному ключу. Если запросы придумываются на ходу, Cassandra будет мешать, а не помогать. Разбор конкретного дизайна с Cassandra под ленту сообщений — в [04-chat-messaging.md](../../05-system-design/interview-cases/04-chat-messaging.md).

## Кольцо токенов: кластер без координатора

Все узлы Cassandra равноправны: нет primary и нет replica в том смысле, в каком они есть у PostgreSQL или MongoDB. Клиент может обратиться к любому узлу, и этот узел становится **координатором** (`coordinator`) конкретного запроса — он сам находит нужные реплики, рассылает им запрос и собирает ответы.

Чтобы координатор мог вычислить владельцев данных без обращения к какому-либо реестру, используется **согласованное хеширование** (`consistent hashing`). Partition key прогоняется через хеш-функцию (по умолчанию `Murmur3Partitioner`), результат — **токен**, число из диапазона от `-2^63` до `2^63 - 1`. Узлы разбирают этот диапазон между собой, и владелец ключа определяется одной арифметической операцией.

```text
Кольцо токенов (упрощение: диапазон 0..99 вместо -2^63..2^63-1)

              A (токен 0)
       E (80)         B (20)
              D (60)
                  C (40)

Узел отвечает за диапазон (предыдущий токен .. свой токен]:

  B -> (0..20]
  C -> (20..40]
  D -> (40..60]
  E -> (60..80]
  A -> (80..99] и (99..0]   — кольцо замыкается на нуле
```

Пусть `token("device-17") = 57`. Число попадает в диапазон `(40..60]`, значит первичный владелец — узел D. Дальше вступает **replication factor (RF)** — сколько копий партиции хранится в кластере. При `RF = 3` копии кладутся на D и на два следующих узла по часовой стрелке: E и A. Никакого выбора «кто главный» между D, E и A не происходит — все три равноценны.

### Virtual nodes

Если бы у каждого узла был ровно один токен, добавление узла в кластер разрезало бы ровно один диапазон: новый узел забирал бы данные у одного соседа, и весь поток передачи данных шёл бы между двумя машинами. **Virtual nodes** (`vnodes`) решают это тем, что каждый физический узел получает несколько токенов и владеет множеством мелких диапазонов, разбросанных по кольцу. Добавление узла тогда забирает понемногу у многих соседей, и передача данных распараллеливается.

Значение по умолчанию менялось: в 3.x было `num_tokens: 256`, начиная с 4.0 — `num_tokens: 16`. Уменьшение выглядит контринтуитивно, но объясняется доступностью. Чем больше у узла токенов, тем с большим числом других узлов он делит хотя бы один диапазон. При 256 токенах в кластере из десятков машин практически любая тройка узлов оказывается совладельцами какого-нибудь диапазона — то есть одновременный отказ почти любых трёх узлов при `RF = 3` теряет кворум хотя бы для части данных. При 16 токенах пересечений меньше, и вероятность потерять кворум при том же числе отказов заметно ниже. Компенсация за меньшее число токенов — алгоритм распределения `allocate_tokens_for_local_replication_factor`, который выбирает токены осознанно, а не случайно, и сохраняет ровный баланс.

### Как узлы узнают друг о друге

- **Gossip** — узлы периодически обмениваются информацией о состоянии соседей: кто жив, какие у кого токены, какая версия схемы. Реестра нет, состояние сходится обменом.
- **Snitch** — компонент, сообщающий, в каком дата-центре и стойке находится узел. От него зависит выбор реплик и маршрутизация. `GossipingPropertyFileSnitch` — обычный выбор для собственного железа, для облаков есть свои варианты.
- **Replication strategy** — правило раскладки копий. `SimpleStrategy` просто идёт по часовой стрелке и годится только для одного дата-центра; `NetworkTopologyStrategy` задаёт RF отдельно для каждого дата-центра и старается разложить копии по разным стойкам, чтобы отказ стойки не уносил все реплики сразу. В производственных кластерах используется вторая, даже если дата-центр один.

## Путь записи: LSM-дерево

Cassandra не изменяет данные на месте. Любая запись — это добавление новой версии ячейки с меткой времени, и никакого чтения перед записью не происходит. Эта структура называется **LSM-дерево** (`Log-Structured Merge tree`) и объясняет почти всё поведение базы: и высокую скорость записи, и дорогое чтение, и существование compaction, и надгробия.

```text
INSERT / UPDATE / DELETE — для движка это одна и та же операция
      |
      v
[CommitLog]   дозапись в конец файла на диске: журнал упреждающей записи.
      |       Только последовательный ввод-вывод, ничего не ищется и не перезаписывается.
      v
[Memtable]    отсортированная структура в памяти: partition key -> строки -> ячейки.
      |       Здесь новая версия ячейки просто ложится поверх старой.
      |  переполнение порога памяти
      v
[SSTable]     неизменяемый отсортированный файл на диске.
              После создания не меняется никогда.
```

Подтверждение клиенту отправляется после записи в CommitLog и Memtable — до попадания на диск в виде SSTable. Durability обеспечивает именно CommitLog: при перезапуске узел проигрывает журнал в память. По умолчанию `commitlog_sync: periodic` с периодом `commitlog_sync_period: 10000ms`, то есть подтверждённая запись может потеряться при внезапном отключении питания в пределах этого окна; режим `batch` синхронизирует журнал до подтверждения, платя за это латентностью.

Почему запись такая дешёвая:

- **нет поиска существующей строки.** `UPDATE` не читает старое значение — он пишет новую версию ячейки. `UPDATE` и `INSERT` в CQL вообще делают одно и то же, `upsert` здесь режим по умолчанию;
- **нет случайного доступа к диску.** И CommitLog, и сброс Memtable — последовательная запись;
- **нет блокировок между строками.** Разные записи не конфликтуют, потому что конфликт разрешается позже, при чтении.

Разрешение конфликтов — **last write wins** по метке времени ячейки. Если две реплики получили разные значения одной ячейки, при слиянии победит то, у которого больше timestamp. Отсюда два практических следствия. Во-первых, расхождение часов между узлами напрямую превращается в потерю данных: запись с «убежавшими вперёд» часами навсегда перекроет более позднюю. Во-вторых, операция «прочитать, изменить, записать» на уровне приложения небезопасна без [lightweight transaction](#lightweight-transactions-counters-и-batch) — две одновременные попытки просто перезапишут друг друга без признаков конфликта.

### Из чего состоит SSTable

Одна SSTable — это набор файлов с общим префиксом. Полезно знать, что где лежит, потому что путь чтения ходит именно по ним:

| Файл | Роль |
| --- | --- |
| `Data.db` | сами данные: партиции и строки в отсортированном порядке |
| `Filter.db` | фильтр Блума по ключам партиций |
| `Index.db`, `Summary.db` | индекс партиций и его разреженная выборка (формат `big`) |
| `Partitions.db`, `Rows.db` | индекс на префиксных деревьях (формат `bti`, появился в 5.0) |
| `CompressionInfo.db` | смещения блоков сжатия |
| `Statistics.db` | метаданные: диапазоны меток времени, доля надгробий, TTL |

Формат `bti` (`Big Trie-Indexed`) из Cassandra 5.0 заменяет пару `Index.db` + `Summary.db` на индекс, построенный на префиксных деревьях (`trie`). Он занимает меньше памяти и ищет ключ за меньшее число обращений, но включается явно и не меняет модель данных.

## Путь чтения: слияние SSTable

Чтение дороже записи ровно потому, что запись дешёвая. Одна логическая строка может быть размазана по нескольким SSTable: колонку `status` записали вчера, `updated_at` — сегодня, а вчерашний сброс Memtable уже лежит отдельным файлом. Чтобы вернуть строку, координируемая реплика обязана собрать её из всех источников, где она может встречаться.

```text
SELECT по полному partition key
      |
      v
Memtable            свежие данные, ещё не сброшенные на диск
      |
      v
для каждой SSTable, попадающей в диапазон ключа:

  Filter.db (фильтр Блума)
      |  "точно нет"        -> SSTable пропускается целиком, диск не трогается
      |  "возможно есть"
      v
  key cache               готовое смещение ключа в Data.db
      |  промах
      v
  индекс партиций         Index.db + Summary.db, либо Partitions.db + Rows.db
      v
  Data.db                 чтение нужного фрагмента строки
      |
      v
слияние фрагментов: для каждой ячейки побеждает версия с максимальной меткой
времени; надгробие перекрывает все значения старше себя
```

**Фильтр Блума** — вероятностная структура, отвечающая на вопрос «есть ли такой ключ в этом файле». Она может ошибиться в сторону «возможно есть» (ложное срабатывание стоит одного лишнего обращения к диску), но никогда не ошибается в сторону «точно нет». Именно поэтому чтение по несуществующему ключу обычно почти бесплатно. Разбор самой структуры — в [03-bloom-filter.md](../../12-interview-practice/coding-tasks/data-structures/03-bloom-filter.md).

**Read amplification** — сколько файлов приходится потрогать ради одной строки. Это главная метрика чтения в LSM, и именно её уменьшает compaction. Строка, которую переписывали сотню раз мелкими обновлениями, окажется в десятке SSTable, и каждое чтение будет собирать её заново.

Кэши стоит различать: они решают разные задачи и по-разному опасны.

| Кэш | Что хранит | Когда помогает | Чем опасен |
| --- | --- | --- | --- |
| `key cache` | смещение ключа партиции в `Data.db` | почти всегда, включён по умолчанию | практически ничем, дёшев по памяти |
| `row cache` | голову партиции целиком | узкие партиции, читаемые многократно и почти не меняющиеся | любая запись в партицию сбрасывает её из кэша; на широких партициях съедает память впустую |
| `chunk cache` | распакованные блоки файлов | горячий рабочий набор больше страничного кэша | конкурирует за память с кучей JVM |

`row cache` по умолчанию выключен, и включать его без замеров не нужно: на записываемых данных он чаще вредит, чем помогает.

## Consistency levels

**Consistency level (CL)** задаётся отдельно для каждого запроса и определяет, скольких реплик координатор дожидается перед ответом клиенту. Это не настройка кластера и не свойство таблицы — критичная запись и фоновая аналитика в одном приложении спокойно ходят с разными уровнями.

Механика запроса на чтение при `RF = 3`, `CL = QUORUM`:

1. координатор вычисляет владельцев по токену: реплики A, B, C;
2. отправляет полное чтение самой быстрой реплике (по измеренной латентности) и **digest-запрос** — контрольную сумму данных — остальным. Так по сети идёт один набор данных, а не три;
3. дожидается двух ответов (`QUORUM` при RF=3 — это `3/2 + 1 = 2`);
4. если контрольные суммы совпали, ответ уходит клиенту;
5. если не совпали, координатор запрашивает полные данные, сливает их по меткам времени и **перед ответом клиенту** дописывает актуальную версию на отставшие реплики — это blocking read repair.

| Уровень | Сколько реплик должны ответить | Замечание |
| --- | --- | --- |
| `ANY` | ноль реплик, достаточно принятой подсказки | только для записи, самый слабый; данные могут ещё не существовать ни на одной реплике |
| `ONE` | одна | минимальная латентность, чтение может вернуть старое значение |
| `LOCAL_ONE` | одна в локальном дата-центре | как `ONE`, но без похода в другой дата-центр |
| `TWO`, `THREE` | две, три | фиксированное число вместо доли от RF |
| `QUORUM` | `RF/2 + 1` по всему кластеру | при нескольких дата-центрах требует походов между ними |
| `LOCAL_QUORUM` | `RF_local/2 + 1` в локальном дата-центре | рабочая настройка по умолчанию для multi-DC |
| `EACH_QUORUM` | кворум в каждом дата-центре | только для записи, дорого |
| `ALL` | все реплики | недоступность одной реплики роняет запрос |

### Почему W + R > RF даёт актуальное чтение

Формула читается как «множества ответивших реплик обязаны пересечься». Разберём при `RF = 3` и репликах A, B, C.

Запись прошла с `CL = QUORUM`, то есть подтверждена двумя репликами — пусть это A и B. Чтение с `CL = QUORUM` ждёт ответа тоже от двух, но заранее неизвестно, от каких:

```text
прочитали {A, B} -> пересечение с {A, B} = {A, B}
прочитали {A, C} -> пересечение с {A, B} = {A}
прочитали {B, C} -> пересечение с {A, B} = {B}
```

Пустого пересечения не бывает: 2 + 2 = 4 > 3, и хотя бы одна из прочитанных реплик точно видела запись. Победит она, потому что её метка времени больше.

Теперь `CL = ONE` на обеих операциях: запись подтверждена одной репликой A, чтение уходит на одну реплику C. 1 + 1 = 2, что не больше 3 — пересечение может быть пустым, и клиент получит значение, которое было до записи. Данные при этом не потеряны: они доедут до C через hinted handoff или repair, просто позже.

Что уровни согласованности **не** дают ни при каком значении:

- изоляцию: другой читатель может увидеть частично применённую запись — часть реплик уже обновилась, часть нет;
- атомарность между строками и партициями: `BATCH` не транзакция;
- защиту от одновременного обновления одной ячейки: два `UPDATE` с `QUORUM` перезапишут друг друга по last write wins.

Классификация Cassandra по CAP и PACELC — в [02-cap-and-base.md](../database-fundamentals/02-cap-and-base.md).

## Как реплики расходятся и сходятся обратно

Реплики расходятся постоянно: узел перезагружается, сеть моргает, запись с `CL = ONE` доезжает не до всех. Cassandra не пытается это предотвратить — вместо этого у неё три независимых механизма схождения, работающих на разных горизонтах времени.

**Hinted handoff (подсказки).** Если во время записи реплика недоступна, координатор сохраняет у себя «подсказку» — запись, предназначенную этому узлу, — и доставляет её, когда узел вернётся. Окно ограничено: `max_hint_window: 3h` по умолчанию. Узел, отсутствовавший дольше трёх часов, подсказок не получит, и его придётся чинить repair'ом. Подсказки не считаются за consistency level, кроме `CL = ANY`.

**Read repair (починка при чтении).** Работает так, как описано выше: расхождение, найденное при сравнении контрольных сумм, чинится синхронно, до ответа клиенту. Важная деталь для тех, кто читал старую документацию: в Cassandra 4.0 фоновый вероятностный read repair удалён вместе с настройками `read_repair_chance` и `dclocal_read_repair_chance`. Остался только блокирующий вариант, а он по определению не срабатывает при `CL = ONE` — там нечего сравнивать. Кластер, который всё читает с `ONE`, чинится исключительно repair'ом.

**Anti-entropy repair (плановая сверка).** `nodetool repair` сравнивает данные между репликами и переносит недостающее. Чтобы не гонять по сети всё содержимое, реплики обмениваются **деревьями Меркла** (`Merkle tree`) — деревьями хешей, где каждый узел дерева суммирует хеши потомков. Совпал корень — диапазон идентичен, сверка окончена. Не совпал — спуск по дереву быстро локализует конкретный расходящийся поддиапазон, и по сети идёт только он.

Repair — не факультативная гигиена, а обязательная операция, и вот почему. Надгробие удаляется физически через `gc_grace_seconds` (по умолчанию `864000`, то есть 10 суток). Если реплика, пропустившая удаление, не получит его через repair до истечения этого срока, надгробие исчезнет с остальных реплик — и при следующей сверке отставшая реплика будет выглядеть как та, у которой есть «недостающие данные». Удалённая строка вернётся. Отсюда правило эксплуатации: **каждый узел должен проходить repair чаще, чем раз в `gc_grace_seconds`**.

## Модель данных: primary key

`PRIMARY KEY` в Cassandra — это две разные вещи в одной конструкции, и их смешивание порождает большинство ошибок проектирования.

- **partition key** — первая часть ключа. Определяет, на каких узлах лежит строка. Внутри одной партиции данные физически лежат рядом и читаются одним обращением.
- **clustering columns** — остальные части. Задают порядок сортировки строк внутри партиции и позволяют брать диапазоны.

```text
CREATE TABLE messages (
    chat_id  uuid,        -- partition key
    sent_at  timestamp,   -- clustering column
    msg_id   uuid,        -- clustering column
    body     text,
    PRIMARY KEY (chat_id, sent_at, msg_id)
) WITH CLUSTERING ORDER BY (sent_at DESC, msg_id ASC);

физически на диске:

партиция chat_id = 7f3a...        <- целиком на RF узлах, определённых токеном
    (sent_at=10:05, msg_id=c) -> body = "ok"
    (sent_at=10:01, msg_id=b) -> body = "hello"
    (sent_at=10:00, msg_id=a) -> body = "hi"
    ^ строки отсортированы по clustering-колонкам, сверху свежие
```

Составной partition key оформляется дополнительными скобками: `PRIMARY KEY ((chat_id, bucket), sent_at)` означает, что раскладку по узлам определяет пара `(chat_id, bucket)`, а `sent_at` сортирует строки внутри.

Из такой физики следуют жёсткие правила, что можно спросить:

| Запрос | Работает | Почему |
| --- | --- | --- |
| `WHERE chat_id = ?` | да | известен полный partition key — координатор знает узлы |
| `WHERE chat_id = ? AND sent_at > ?` | да | диапазон по первой clustering-колонке внутри партиции |
| `WHERE chat_id = ? AND msg_id = ?` | нет | пропущена `sent_at` — нельзя взять вторую clustering-колонку без первой |
| `WHERE sent_at > ?` | нет | без partition key неизвестно, к каким узлам обращаться |
| `WHERE chat_id IN (?, ?, ?)` | да, но осторожно | координатор опрашивает несколько партиций и ждёт самую медленную |

Ограничение выглядит суровым, пока не увидеть его причину: любой запрос без полного partition key превращается в обход всего кластера. Cassandra не запрещает его из вредности — она отказывается делать вид, что такой запрос дёшев.

Отсюда главный принцип моделирования: **таблица проектируется под запрос, а не под сущность**. Если сообщения нужно читать и по чату, и по автору — это две таблицы с одними и теми же данными, разложенными по разным ключам, и приложение пишет в обе. Дублирование здесь не признак плохой нормализации, а способ платить за чтение один раз при записи. Дисковое место в этой модели — самый дешёвый ресурс.

## Проектирование partition key

Partition key — решение, которое почти невозможно изменить потом: смена ключа означает переливку таблицы целиком. У него две независимые задачи, и провалить можно каждую.

### Задача первая: равномерность

**Hot partition** — партиция, на которую приходится непропорционально большая доля трафика. Разберём на числах, почему это не лечится масштабированием.

Кластер из 30 узлов, `RF = 3`, равномерная нагрузка 60 000 записей в секунду:

```text
каждая запись уходит на 3 реплики: 60 000 × 3 = 180 000 операций/с по кластеру
на узел:                           180 000 / 30 = 6 000 операций/с
```

Теперь один ключ — активный магазин на маркетплейсе или сервисный аккаунт — даёт ещё 20 000 записей в секунду. Его партиция принадлежит ровно трём узлам:

```text
на этих трёх узлах:  6 000 + 20 000 = 26 000 операций/с
на остальных 27:                       6 000 операций/с
```

Добавление узлов не помогает вообще: партиция неделима, её нельзя разложить между машинами. Лечение — только на уровне ключа: добавить в partition key ещё одну колонку, которая размажет нагрузку. Для счётчиков это обычно искусственный `shard_id` от 0 до N (запись в случайный, чтение суммой по всем N), для потоков событий — временное окно.

### Задача вторая: ограниченный размер

**Unbounded partition** — партиция, у которой в ключе нет ничего, что останавливало бы её рост. Датчик, пишущий в `PRIMARY KEY (device_id, ts)`, будет складывать в одну партицию всё, что произвёл за годы.

```text
замер раз в 10 секунд:      6 в минуту × 60 × 24 = 8 640 строк в сутки
строка ~200 байт:           8 640 × 200 ≈ 1,7 МБ в сутки
за год:                     8 640 × 365 ≈ 3,2 млн строк ≈ 630 МБ
```

Практические ориентиры — не больше ~100 МБ и не больше ~100 000 строк на партицию. Годовая партиция превышает оба порога в несколько раз. Последствия накапливаются медленно и проявляются все сразу: растёт латентность чтения, compaction такой партиции требует всё больше памяти и времени, repair начинает передавать по сети гигантские диапазоны, а восстановление узла упирается в отдельные тяжёлые партиции.

Лечение — **bucketing**, добавление временного окна в partition key. Размер окна считается от тех же цифр:

```text
bucket = сутки:  8 640 строк, 1,7 МБ    -> обе границы с большим запасом
bucket = месяц:  259 200 строк, 52 МБ   -> по объёму проходит, по числу строк нет
```

Значит для этого профиля нагрузки корзина — сутки:

```sql
-- растёт бесконечно
PRIMARY KEY (device_id, ts)

-- размер партиции ограничен сутками
PRIMARY KEY ((device_id, day), ts)
-- day = '2026-08-03'
```

Цена решения: чтение за произвольный интервал теперь задевает несколько партиций, и приложение обязано само перечислить корзины. Это осознанный обмен — предсказуемая стоимость чтения нескольких партиций вместо непредсказуемой стоимости одной растущей.

В Cassandra 4.1 появились **guardrails** — пороги, при превышении которых кластер пишет предупреждение или отклоняет операцию (размер партиции, число надгробий, число колонок). Их стоит включить до того, как проблема станет заметна по латентности.

Как выбор ключа влияет на дизайн целиком, на сквозном примере — в [12-sharding.md](./postgresql/12-sharding.md) разбираются те же компромиссы для PostgreSQL.

## Tombstones

**Tombstone (надгробие)** — маркер удаления: специальная запись с меткой времени, означающая «всё, что старше этой отметки, считается удалённым». `DELETE` не стирает данные, а создаёт такой маркер.

### Почему нельзя просто удалить

Разберём сценарий при `RF = 3` и репликах A, B, C. Строка есть на всех трёх. Приходит `DELETE` с `CL = QUORUM`, узел C в этот момент недоступен:

```text
A: строка удалена     B: строка удалена     C: строка на месте (узел был недоступен)
```

C возвращается. Запускается repair и сравнивает содержимое реплик. Если бы удаление просто стирало данные, картина для repair выглядела бы так: у C есть строка, у A и B её нет — значит, A и B отстали, надо им долить. Удалённая строка воскресает.

Надгробие превращает удаление в факт с меткой времени, который участвует в слиянии наравне с данными и побеждает всё, что старше. Repair теперь видит не «отсутствие данных», а «явное более позднее удаление» и распространяет именно его. Обратная сторона — надгробия обязаны храниться какое-то время, и это время должно быть больше, чем окно, за которое отставшая реплика гарантированно чинится. Отсюда `gc_grace_seconds: 864000` (10 суток) и требование запускать repair чаще этого срока.

Надгробия бывают разного охвата, и от этого зависит их стоимость:

| Тип | Что закрывает | Как появляется |
| --- | --- | --- |
| cell tombstone | одну ячейку | `UPDATE ... SET col = null` |
| row tombstone | одну строку | `DELETE FROM ... WHERE` с полным ключом строки |
| range tombstone | диапазон строк внутри партиции | `DELETE ... WHERE pk = ? AND ts < ?` |
| partition tombstone | всю партицию | `DELETE FROM ... WHERE pk = ?` |

Одно надгробие на партицию дешевле миллиона надгробий на ячейки — при чтении оно отсекает всё разом.

### Чем они опасны при чтении

Надгробия читаются как обычные данные: чтобы вернуть живые строки, движок обязан перебрать удалённые и убедиться, что они удалены. Партиция на 10 000 строк, где 9 900 удалены, при запросе `LIMIT 10` может заставить прочитать почти всю партицию, прежде чем наберётся десяток живых строк. Отсюда пороги:

- `tombstone_warn_threshold: 1000` — запрос выполняется, но в лог уходит предупреждение;
- `tombstone_failure_threshold: 100000` — запрос отклоняется с `TombstoneOverwhelmingException`.

Порог отказа существует не чтобы мешать, а чтобы один запрос не собрал в память столько надгробий, что уронит узел по памяти.

Паттерны, которые производят надгробия тоннами:

- **очередь на Cassandra.** Классический антипаттерн: писать задачи в партицию, читать с начала и удалять обработанные. Голова партиции превращается в сплошную полосу надгробий, через которую приходится продираться каждому чтению. Для очередей есть [Kafka и брокеры сообщений](../../07-message-brokers-and-streaming/README.md);
- **запись `null`.** `UPDATE ... SET col = null` — это не «не трогать колонку», а надгробие на ячейку. Особенно легко получить случайно, когда приложение пишет структуру целиком, а часть полей пустая;
- **массовый TTL.** Каждая истёкшая ячейка становится надгробием. Само по себе это нормально — но только если compaction умеет выбрасывать такие данные целиком (см. TWCS);
- **коллекции целиком.** Присваивание всего списка или множества (`SET tags = {...}`) сначала ставит range tombstone на прежнее содержимое, а потом пишет новое. Добавление элемента (`tags = tags + {...}`) надгробия не создаёт.

## Compaction

**Compaction (уплотнение)** — фоновое слияние SSTable: несколько неизменяемых файлов читаются, их содержимое сливается по меткам времени, надгробия старше `gc_grace_seconds` выбрасываются, и получается новый файл. Это единственный способ, которым LSM-дерево вообще избавляется от старых версий и удалённых данных.

Compaction — компромисс между тремя видами накладных расходов, и стратегии различаются именно тем, какой из них они приносят в жертву:

- **read amplification** — сколько файлов трогает одно чтение;
- **write amplification** — сколько раз одни и те же данные переписываются на диск за свою жизнь;
- **space amplification** — сколько лишнего места занимают ещё не слитые версии.

| Стратегия | Read | Write | Space | Профиль нагрузки |
| --- | --- | --- | --- | --- |
| `STCS` (SizeTiered) | высокая | низкая | высокая: слияние крупных файлов требует свободного места сопоставимо с их размером | запись преобладает, чтения в основном по свежим данным. Значение по умолчанию |
| `LCS` (Leveled) | низкая: строка обычно лежит в одном файле на уровень | высокая: данные переписываются многократно | низкая | много чтений и много перезаписей одних и тех же строк |
| `TWCS` (TimeWindow) | низкая для запросов по времени | низкая | низкая | временные ряды с TTL |
| `UCS` (Unified, 5.0) | настраивается | настраивается | настраивается | один параметр масштабирования вместо выбора между STCS и LCS |

`STCS` группирует файлы по размеру и сливает похожие. Проблема в том, что для слияния нескольких больших файлов нужно место под результат до удаления исходников — поэтому на диске держат заметный запас. Кроме того, старые и новые версии строки могут годами лежать в разных «ярусах» и не встречаться при слиянии.

`TWCS` заслуживает отдельного объяснения, потому что для временных рядов даёт не постепенное улучшение, а качественно другое поведение. Стратегия складывает данные в SSTable по временным окнам и не сливает файлы из разных окон. Когда весь TTL внутри окна истёк, файл удаляется **целиком, без чтения и слияния**. Данные за прошлый месяц исчезают одной операцией с файловой системой вместо перебора миллионов надгробий. Условие работы — записи должны приходить примерно в порядке времени; поток с большим опозданием (запись «задним числом») размазывает данные по окнам и ломает эффект.

`UCS` из Cassandra 5.0 параметризует поведение так, что одна и та же стратегия настройкой сдвигается от tiered-поведения к leveled. Она доступна, но по умолчанию новые таблицы по-прежнему создаются с `SizeTieredCompactionStrategy`.

## Индексы и обходные пути

Регулярный вопрос при переходе с SQL: «а если нужно искать по колонке, которой нет в ключе?» У Cassandra есть несколько ответов, и правильный почти всегда — последний.

**Secondary index (`2i`)** — локальный индекс: каждый узел индексирует только свои данные. Запрос по такому индексу не знает, на каком узле лежит нужное значение, поэтому координатор опрашивает весь кластер и собирает ответы (`scatter-gather`). Стоимость растёт с числом узлов, а не с числом найденных строк, и на большом кластере это худший вид запроса. Отдельно плохо на колонках с низкой кардинальностью: индекс по `status`, у которого три значения, указывает на треть таблицы.

**SASI** — расширенный индекс с поиском по префиксу и диапазонам, помечен как экспериментальный и в новых проектах не используется.

**Storage-Attached Index (`SAI`)**, Cassandra 5.0 — переработанный индекс, хранящийся рядом с данными в тех же SSTable. Он существенно дешевле по записи и по месту, чем `2i`, поддерживает несколько индексированных колонок в одном запросе, а также векторный поиск по типу `vector` через индекс ANN. Ограничение остаётся тем же: запрос без partition key всё равно опрашивает узлы, поэтому SAI хорош как уточняющий фильтр внутри известной партиции, а не как замена ключу.

**Materialized view** — представление, которое Cassandra поддерживает сама, перекладывая данные под другой ключ. Помечено экспериментальным с версии 3.0 и таким остаётся: при расхождении представление не чинится repair'ом вместе с базовой таблицей и может тихо разойтись с ней. Ту же задачу решают ручной второй таблицей.

**`ALLOW FILTERING`** — не оптимизация, а разрешение выполнить заведомо дорогой запрос. Cassandra читает строки и отбрасывает не подошедшие, то есть делает полный проход. На тестовой таблице в тысячу строк это работает мгновенно и создаёт иллюзию, что всё в порядке; на проде тот же запрос кладёт кластер. Единственное безопасное применение — фильтр внутри одной известной партиции, где объём чтения ограничен ею.

Основной ответ на «нужен другой запрос» в Cassandra — **вторая таблица с другим partition key**, наполняемая приложением. Дублирование данных здесь дизайн, а не компромисс.

## Lightweight transactions, counters и batch

Три механизма, которые выглядят как знакомые вещи из SQL, но работают иначе. Ошибка в ожиданиях от них — источник трудноуловимых дефектов.

### Lightweight transactions

**LWT** — условная запись, выполняющаяся через консенсус Paxos. Она даёт линеаризуемость для одной партиции: «вставить, только если ключа ещё нет», «сменить статус, только если он был прежним».

```sql
-- регистрация без гонки: два одновременных запроса не создадут двух пользователей
INSERT INTO users (login, user_id) VALUES ('anna', ...) IF NOT EXISTS;

-- смена состояния только из ожидаемого
UPDATE orders SET status = 'processing'
WHERE order_id = ? IF status = 'pending';
```

Ответ возвращает колонку `[applied]`: `true` — условие выполнилось, `false` — нет, и вместе с ним приходит текущее значение, из-за которого условие не сработало.

Цена высока и её надо назвать явно. Классический путь Paxos в Cassandra — четыре сетевых обмена между координатором и репликами (подготовка, чтение, предложение, фиксация) против одного у обычной записи. Латентность отличается кратно, а конкуренция за один и тот же ключ вызывает борьбу предложений и повторы. В Cassandra 4.1 появился переработанный вариант протокола (`paxos_variant: v2`), сокращающий число обменов, но порядок стоимости остаётся прежним. LWT — точечный инструмент для уникальности и переходов состояний, а не режим работы приложения.

Отдельная тонкость: чтобы прочитать значение с той же линеаризуемостью, чтение должно идти с `CL = SERIAL` или `LOCAL_SERIAL`. Обычное чтение с `QUORUM` может застать Paxos в промежуточном состоянии.

Общий консенсусный протокол для многопартиционных транзакций (`Accord`) в проекте разрабатывается, но в стабильные релизы 5.0 не входит — рассчитывать на него в дизайне пока нельзя.

### Counters

Счётчик — специальный тип колонки, поддерживающий атомарный инкремент. Ограничения делают его нишевым инструментом:

- таблица со счётчиками не может содержать обычных не-ключевых колонок;
- операция инкремента **не идемпотентна**: повтор после таймаута может увеличить значение дважды, а таймаут не сообщает, применилась ли запись;
- счётчик нельзя восстановить из резервной копии вместе с остальными данными согласованно.

Если счётчик участвует в деньгах или квотах, надёжнее хранить события и агрегировать их отдельно, а не полагаться на counter-колонку.

### Batch

`BATCH` в CQL — не транзакция, и это главное о нём.

- **logged batch** даёт атомарность: координатор сначала записывает батч в служебный `batchlog` на других узлах, и если он умрёт посередине, оставшиеся операции будут доиграны. Изоляции нет — другой читатель увидит частично применённый батч. Цена: дополнительная запись батчлога и её репликация;
- **unlogged batch** просто отправляет несколько операций одним пакетом без всяких гарантий.

Батч не ускоряет запись. Если операции идут в разные партиции, координатор становится узким местом: он один рассылает всё и ждёт всех, тогда как параллельные независимые запросы разложились бы по узлам. Пороги по умолчанию — `batch_size_warn_threshold: 5KiB` и `batch_size_fail_threshold: 50KiB` — существуют именно потому, что большие батчи регулярно роняют координаторов.

Уместное применение батча — **атомарная запись одного факта в несколько денормализованных таблиц**: одно и то же сообщение в `messages_by_chat` и `messages_by_author`. Именно ради этого случая он и нужен.

## Несколько дата-центров

Репликация между дата-центрами в Cassandra — не отдельный продукт и не надстройка, а параметр keyspace:

```sql
CREATE KEYSPACE events WITH replication = {
    'class': 'NetworkTopologyStrategy',
    'dc_eu':  3,
    'dc_us':  3
};
```

Каждый дата-центр получает собственный RF, и записи расходятся между ними асинхронно. Отсюда рабочий уровень согласованности для такой топологии — `LOCAL_QUORUM`: запрос дожидается кворума только в своём дата-центре и не платит межконтинентальным round trip, а второй дата-центр догоняет фоном. При RF=3 в каждом из двух дата-центров `QUORUM` потребовал бы 4 ответа из 6 — то есть неизбежного похода через океан на каждом запросе.

Зачем это делают:

- **географическая близость.** Читатели в каждом регионе работают с локальными репликами;
- **отказоустойчивость уровня региона.** Потеря дата-центра не теряет данные;
- **изоляция нагрузок.** Отдельный дата-центр под аналитику или Spark принимает тяжёлые сканирования, не мешая рабочему трафику. Это обычный приём: логический дата-центр не обязан быть физически отдельным.

Плата — межрегиональный трафик, более долгое схождение реплик и repair, который теперь ходит по глобальной сети.

## Работа из Go

Драйвер — **gocql**. С 2024 года он передан в Apache Software Foundation и развивается как официальный драйвер проекта: `github.com/apache/cassandra-gocql-driver/v2` (имя пакета осталось `gocql`). Старый путь `github.com/gocql/gocql` продолжает работать для существующего кода, но новые проекты стоит начинать с версии под ASF.

```go
import (
    "context"
    "time"

    "github.com/apache/cassandra-gocql-driver/v2"
)

func newSession(ctx context.Context) (*gocql.Session, error) {
    cluster := gocql.NewCluster("10.0.0.1", "10.0.0.2", "10.0.0.3")
    cluster.Keyspace = "events"

    // уровень по умолчанию для всех запросов сессии
    cluster.Consistency = gocql.LocalQuorum

    // ключевая настройка: отправлять запрос сразу на реплику-владельца ключа
    // и только в своём дата-центре — иначе координатором станет случайный узел
    cluster.PoolConfig.HostSelectionPolicy = gocql.TokenAwareHostPolicy(
        gocql.DCAwareRoundRobinPolicy("dc_eu"),
    )

    cluster.ConnectTimeout = 2 * time.Second
    cluster.Timeout = 2 * time.Second
    cluster.NumConns = 2

    return cluster.CreateSession()
}
```

**Token-aware маршрутизация** — не микрооптимизация. Без неё драйвер выбирает координатора по кругу, и в среднем этот координатор не владеет ключом: он вынужден переслать запрос настоящим репликам и подождать. Получается лишний сетевой обмен на каждом запросе. С token-aware политикой драйвер сам считает токен от partition key и идёт прямо к владельцу.

Чтение с постраничной выборкой. Драйвер запрашивает данные страницами, а не целиком, и итератор подгружает следующую прозрачно:

```go
iter := session.Query(`
        SELECT sent_at, msg_id, body
        FROM messages_by_chat
        WHERE chat_id = ? AND day = ?`,
        chatID, day).
    WithContext(ctx).
    Idempotent(true). // разрешает драйверу повторить запрос при таймауте
    PageSize(500).
    Iter()

var (
    sentAt time.Time
    msgID  gocql.UUID
    body   string
)
for iter.Scan(&sentAt, &msgID, &body) {
    // обработка строки
}
if err := iter.Close(); err != nil {
    return err
}
```

Для постраничной выдачи наружу (курсор в API) используется состояние страницы: `iter.PageState()` возвращает непрозрачный срез байт, который передаётся клиенту и возвращается обратно в `query.PageState(state)`. Считать его смещением нельзя — это внутреннее состояние драйвера и сервера.

Что важно учитывать в Go-коде поверх Cassandra:

- **`Idempotent(true)` ставится осознанно.** Драйвер повторяет только помеченные так запросы. Обычные `INSERT` и `UPDATE` в Cassandra идемпотентны по своей природе (та же запись с той же меткой времени даёт тот же результат), а вот инкремент счётчика, добавление элемента в список и LWT — нет, и помечать их идемпотентными нельзя;
- **prepared statements обязательны для горячих запросов.** `session.Query` кэширует подготовленный вариант, но `gocql.Session` должна жить всё время работы приложения — пересоздание сессии на запрос обнуляет кэш и метаданные кольца;
- **таймаут запроса дублируется контекстом.** `cluster.Timeout` ограничивает ожидание ответа драйвером, `ctx` — время жизни операции в приложении. Нужны оба;
- **ошибка `gocql.ErrTimeoutNoResponse` не означает «не записалось».** Запись могла примениться на части реплик. Дизайн приложения должен переживать повтор — то есть операции проектируются идемпотентными по бизнес-смыслу, с явным идентификатором вместо автоинкремента;
- **`Unlogged batch` в цикле — типичная причина деградации.** Параллельные одиночные запросы почти всегда быстрее.

## Эксплуатация

Cassandra — база, где значительная часть работы приходится не на схему, а на регламент обслуживания.

- **`nodetool status`** — состояние кольца: какие узлы живы, сколько данных на каждом, насколько равномерно распределены токены. Первая команда при любом разбирательстве.
- **`nodetool repair`** — обязательная плановая операция чаще, чем `gc_grace_seconds`. Обычно её ставят на регламент через отдельный оркестратор (например, Reaper), который режет диапазоны на части и растягивает нагрузку во времени: repair всего узла разом заметно бьёт по латентности.
- **`nodetool tablestats` / `tablehistograms`** — размеры партиций, число SSTable на чтение, доля надгробий. Именно здесь видно, что модель данных поехала: максимальный размер партиции и число надгробий на срез растут раньше, чем это заметит мониторинг латентности.
- **`nodetool compactionstats`** — не отстаёт ли уплотнение. Растущая очередь compaction означает, что чтение будет деградировать.
- **JVM и паузы сборщика мусора** — специфическая для Cassandra статья расходов. Крупные кучи и неудачные настройки сборщика дают всплески латентности, которые снаружи выглядят как проблемы сети. Это же основной аргумент в пользу ScyllaDB, где JVM нет.
- **Добавление и вывод узлов** — операции с передачей данных (`streaming`), которые занимают часы и нагружают сеть. Планировать их надо заранее, а не в момент, когда кластер уже не справляется.

Отдельно стоит помнить про синхронизацию часов. Поскольку конфликты разрешаются по меткам времени, разъехавшийся NTP на одном узле приводит к тому, что его записи либо навсегда перекрывают более поздние чужие, либо проигрывают собственным более старым. Симптом — «данные записались и пропали» без каких-либо ошибок.

---

## Сильные стороны

- горизонтальное масштабирование записи почти линейно по числу узлов;
- нет единой точки отказа: любой узел принимает любой запрос;
- согласованность настраивается на каждый запрос, а не на кластер целиком;
- репликация между дата-центрами встроена и настраивается параметром keyspace;
- предсказуемая стоимость чтения по известному ключу независимо от объёма таблицы;
- продуманная работа с временными рядами: `TWCS` плюс TTL удаляет старые данные без нагрузки на чтение.

---

## Слабые стороны

- нет join'ов, подзапросов и ad-hoc фильтрации: доступен только заранее спроектированный набор запросов;
- нет транзакций между партициями; LWT решают узкую задачу и стоят дорого;
- надгробия и compaction требуют понимания, иначе деградация приходит через месяцы после запуска;
- ошибка в partition key почти неисправима без переливки таблицы;
- эксплуатация сложнее одиночной SQL-базы: repair по регламенту, наблюдение за compaction, настройка JVM;
- last write wins делает систему чувствительной к рассинхронизации часов;
- денормализация переносит ответственность за согласованность таблиц в код приложения.

---

## Когда выбирать

Cassandra подходит, если:

- скорость записи измеряется сотнями тысяч операций в секунду и продолжает расти;
- данные естественно разбиваются на партиции по ключу, который известен в каждом запросе;
- набор запросов заранее известен и меняется редко;
- допустима согласованность в конечном счёте либо достаточно `LOCAL_QUORUM` в рамках дата-центра;
- нужна работа из нескольких дата-центров с локальным чтением;
- в команде есть готовность вести регламент обслуживания распределённой базы.

---

## Когда не выбирать

Лучше посмотреть в другую сторону, если:

- запросы заранее неизвестны или нужны произвольные срезы — это [PostgreSQL](./postgresql/README.md);
- нужны аналитические агрегации по большим объёмам — это [ClickHouse](./06-clickhouse.md);
- бизнес-инварианты требуют транзакций между сущностями;
- объёмы не оправдывают сложность: PostgreSQL с партиционированием закрывает очень многое, а стоит несравнимо дешевле в сопровождении;
- нужна очередь задач — для этого есть [брокеры сообщений](../../07-message-brokers-and-streaming/README.md);
- команда не готова к эксплуатации распределённой базы, и это не изменится.

Сравнение с другими системами в одной таблице — в [01-comparison-table.md](./01-comparison-table.md). Ближайший управляемый аналог с похожей моделью — [DynamoDB](./10-dynamodb.md).

---

## Типичные ошибки

- проектировать схему как реляционную: нормализовать сущности и потом искать, чем заменить join;
- выбрать partition key, который даёт горячую или неограниченно растущую партицию;
- строить очередь задач на Cassandra и получить партицию из сплошных надгробий;
- писать `null` в колонку, считая, что это «оставить как есть», и накапливать надгробия на ячейки;
- пропускать плановый `nodetool repair` и получить воскресшие удалённые строки;
- добавить `ALLOW FILTERING`, потому что «на тестовых данных быстро»;
- ожидать актуального чтения при записи и чтении с `CL = ONE`;
- рассчитывать на `BATCH` как на транзакцию или как на способ ускорить запись;
- использовать LWT в горячем пути вместо точечной защиты уникальности;
- работать без token-aware политики в драйвере и платить лишний сетевой обмен на каждом запросе;
- не следить за расхождением часов между узлами.

## Query examples

Таблица под чтение истории чата, с корзиной по суткам и `TWCS`:

```sql
CREATE TABLE messages_by_chat (
    chat_id  uuid,
    day      date,          -- корзина, ограничивающая размер партиции
    sent_at  timestamp,
    msg_id   uuid,
    author   uuid,
    body     text,
    PRIMARY KEY ((chat_id, day), sent_at, msg_id)
) WITH CLUSTERING ORDER BY (sent_at DESC, msg_id ASC)
  AND compaction = {
        'class': 'TimeWindowCompactionStrategy',
        'compaction_window_unit': 'DAYS',
        'compaction_window_size': 3
      }
  AND default_time_to_live = 7776000;   -- 90 суток
```

Окно `TWCS` и корзина `day` в ключе — разные вещи: первое режет SSTable по времени, второе режет партицию. Размер окна выбирается от TTL: за 90 суток при окне в 3 дня накапливается 30 окон, то есть 30 групп файлов, которые движок держит на диске и по одной удаляет по истечении TTL. Окно в сутки дало бы 90 групп — слишком много открытых файлов и записей в метаданных ради того же результата.

Запись. Полный partition key указывается всегда:

```sql
INSERT INTO messages_by_chat (chat_id, day, sent_at, msg_id, author, body)
VALUES (7f3a0000-0000-0000-0000-000000000001, '2026-08-03',
        toTimestamp(now()), now(),
        65f00000-0000-0000-0000-000000000002, 'привет');
```

Чтение последних сообщений — одна партиция, диапазон по clustering-колонке:

```sql
SELECT sent_at, msg_id, author, body
FROM messages_by_chat
WHERE chat_id = 7f3a0000-0000-0000-0000-000000000001
  AND day = '2026-08-03'
LIMIT 20;
```

Та же запись во вторую таблицу, разложенную под другой запрос. Атомарность обеспечивает logged batch:

```sql
BEGIN BATCH
  INSERT INTO messages_by_chat   (chat_id, day, sent_at, msg_id, body) VALUES (...);
  INSERT INTO messages_by_author (author, day, sent_at, msg_id, body) VALUES (...);
APPLY BATCH;
```

Уникальность логина через lightweight transaction:

```sql
INSERT INTO users_by_login (login, user_id)
VALUES ('anna', 65f00000-0000-0000-0000-000000000002)
IF NOT EXISTS;
-- ответ содержит [applied] = true|false; при false вернётся занявший логин user_id
```

TTL на конкретную запись, поверх табличного значения по умолчанию:

```sql
INSERT INTO sessions (session_id, user_id)
VALUES (..., ...) USING TTL 3600;

-- сколько осталось жить конкретной ячейке
SELECT TTL(user_id), WRITETIME(user_id) FROM sessions WHERE session_id = ...;
```

Полный проход по таблице (миграция, выгрузка) — по диапазонам токенов, а не `ALLOW FILTERING`:

```sql
SELECT chat_id, day FROM messages_by_chat
WHERE token(chat_id, day) > -9223372036854775808
  AND token(chat_id, day) <= -8000000000000000000;
```

Что делать не нужно:

```sql
-- полный проход по всему кластеру ради нескольких строк
SELECT * FROM messages_by_chat WHERE author = ? ALLOW FILTERING;

-- правильный ответ: вторая таблица messages_by_author с этим ключом
```

Диагностика конкретного запроса — трассировка показывает, какие узлы и SSTable были задеты:

```sql
TRACING ON;
SELECT ... ;
```

## Interview-ready answer

**1. Что такое Cassandra и на какой модели она построена?**

- Суть — распределённая wide-column база без ведущего узла: любой узел принимает запрос и становится координатором.
- Раскладка данных — согласованное хеширование: partition key превращается в токен, узлы владеют диапазонами токенов, replication factor задаёт число копий.
- Происхождение — распределённая часть от Amazon Dynamo, модель данных от Google BigTable.
- Ниша — очень высокая скорость записи и доступность при заранее известном наборе запросов; join'ов, ad-hoc фильтрации и межпартиционных транзакций нет.

**2. Почему запись быстрая, а чтение дороже?**

- Запись — LSM-дерево: дозапись в CommitLog плюс отсортированная структура в памяти, без чтения старого значения и без изменения данных на месте.
- Чтение — сборка строки из нескольких неизменяемых SSTable плюс Memtable, со слиянием версий по меткам времени.
- Экономия на чтении — фильтр Блума на каждой SSTable отсекает файлы, где ключа точно нет.
- Плата — read amplification: чем больше мелких обновлений одной строки, тем больше файлов трогает чтение; уменьшает её compaction.

**3. Как получить актуальное чтение и что означает формула W + R > RF?**

- Механизм — кворумы: множества ответивших реплик обязаны пересекаться, тогда читающий гарантированно застанет хотя бы одну реплику, видевшую запись.
- Пример — при RF=3 запись с `QUORUM` (2 реплики) и чтение с `QUORUM` (2 реплики) дают 2+2 > 3; любая пара из трёх пересекается с любой другой.
- Обратный случай — `ONE` на запись и `ONE` на чтение: 1+1 не больше 3, пересечение может быть пустым, вернётся старое значение.
- Для нескольких дата-центров — `LOCAL_QUORUM`, чтобы не платить межрегиональный round trip на каждом запросе.
- Чего кворум не даёт — изоляции и атомарности между строками; одновременные обновления одной ячейки просто перезаписывают друг друга по метке времени.

**4. Как реплики сходятся после сбоя?**

- Hinted handoff — координатор придерживает записи для недоступной реплики и досылает их, окно по умолчанию 3 часа.
- Read repair — расхождение, найденное при сравнении контрольных сумм на чтении, чинится до ответа клиенту; в 4.0 фоновый вероятностный вариант удалён, поэтому при `CL = ONE` починки на чтении нет вообще.
- Anti-entropy repair — плановый `nodetool repair` с деревьями Меркла: сравнение хешей быстро локализует расходящийся диапазон.
- Почему repair обязателен — надгробия живут `gc_grace_seconds` (10 суток по умолчанию); не успевший получить удаление узел воскресит строку.

**5. Почему partition key — главное решение?**

- Он определяет и раскладку по узлам, и что вообще можно спросить: без полного partition key запрос обходит весь кластер.
- Ошибка первого рода — горячая партиция: партиция неделима, её обслуживают ровно RF узлов, и расширение кластера нагрузку не размажет.
- Ошибка второго рода — неограниченный рост: ориентиры порядка 100 МБ и 100 000 строк, дальше страдают чтение, compaction, repair и восстановление узла.
- Лечение — bucketing: добавить в ключ временное окно, размер которого посчитан от реального потока записей.
- Цена ошибки — смена partition key означает переливку таблицы целиком.

**6. Что такое tombstone и чем он опасен?**

- Назначение — сделать удаление явным фактом с меткой времени: иначе repair увидел бы у отставшей реплики «недостающие данные» и воскресил удалённую строку.
- Стоимость чтения — надгробия перебираются как обычные строки; пороги 1000 (предупреждение) и 100 000 (отказ запроса) защищают узел от переполнения памяти.
- Источники — очередь на Cassandra, запись `null` в колонку, массовый TTL, присваивание коллекции целиком.
- Правильный ответ для временных рядов — `TWCS`: истёкшая SSTable удаляется целиком, без перебора надгробий.

**7. Когда Cassandra не нужна?**

- Когда запросы заранее неизвестны или требуются произвольные срезы — там уместен PostgreSQL.
- Когда нужны аналитические агрегации по большим объёмам — там уместен ClickHouse.
- Когда бизнес-инварианты пересекают сущности и требуют транзакций.
- Когда объёмы не оправдывают стоимость эксплуатации: repair по регламенту, наблюдение за compaction, настройка JVM.
- Когда нужна очередь задач — Cassandra здесь худший из доступных вариантов.
