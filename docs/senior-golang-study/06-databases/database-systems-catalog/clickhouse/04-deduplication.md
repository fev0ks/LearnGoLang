## Почему база не мешает вставить дубликат

Уникальных ключей в ClickHouse нет. `PRIMARY KEY` не проверяет уникальность и вообще ничего не проверяет при вставке — это разреженный индекс для поиска, а не ограничение целостности. Ни `UNIQUE`, ни `ON CONFLICT`, ни проверки перед записью здесь не существует.

Причина не в недоделанности, а в устройстве записи. Проверка уникальности означала бы чтение перед записью: движок обязан был бы найти все куски, где может лежать такой ключ, и заглянуть в каждый. Именно от этого ClickHouse и отказался ради дешёвой вставки — кусок пишется, ничего не читая ([00-storage-model.md](./00-storage-model.md)). Проверка вернула бы стоимость обратно и упёрлась бы в распределённый случай, где куски лежат на разных шардах.

Поэтому дедупликация здесь — не настройка, а решение схемы и запросов.

## Три уровня дедупликации

Вопрос «как не вставить дубликаты» на самом деле объединяет три разные задачи. Они решаются разными механизмами, и путаница между ними — источник большинства проблем.

```text
Уровень 1. Один и тот же INSERT ушёл дважды (retry после таймаута)
           -> block_id или insert_deduplication_token

Уровень 2. Разные INSERT содержат разные версии одной сущности (upsert)
           -> ReplacingMergeTree: ключ ORDER BY + колонка версии

Уровень 3. Merge ещё не прошёл, дубликаты физически лежат в таблице
           -> FINAL, argMax или LIMIT 1 BY в запросе
```

| Уровень | Что предотвращает | Механизм | Когда срабатывает |
| --- | --- | --- | --- |
| вставка | повторную запись одного и того же блока | хеш блока или явный токен | сразу, в пределах окна дедупликации |
| хранение | накопление версий одной сущности | движок `ReplacingMergeTree` | при фоновом merge, время не гарантировано |
| чтение | видимость ещё не слитых дубликатов | `FINAL`, `argMax`, `LIMIT 1 BY` | в каждом запросе, ценой скорости |

Первый уровень нужен всегда, где есть повторы запросов. Второй — там, где сущность обновляется. Третий обязателен вместе со вторым: без него результат запроса зависит от того, успел ли пройти merge, то есть недетерминирован.

## Уровень 1: дедупликация блока при повторе

Сценарий: приложение отправило `INSERT`, соединение оборвалось по таймауту, ответ не получен. Данные могли записаться, а могли и нет. Повтор без защиты удваивает батч.

**Как это решает ClickHouse.** Для каждого вставленного блока считается `block_id` — хеш его содержимого. Идентификаторы недавно вставленных блоков хранятся: у `Replicated`-таблиц в Keeper, у обычных — в локальном файле. Приходит блок с уже известным идентификатором — он молча отбрасывается, а клиент получает успешный ответ.

```text
попытка 1:  INSERT (1000 строк) -> block_id = ab12cd -> part создан -> таймаут у клиента
попытка 2:  INSERT (те же 1000) -> block_id = ab12cd -> уже известен -> данные отброшены
результат:  1000 строк, а не 2000
```

Журнал дедупликации ограничен:

| Настройка таблицы | Значение по умолчанию | Смысл |
| --- | --- | --- |
| `replicated_deduplication_window` | 10 000 | сколько последних блоков помнить |
| `replicated_deduplication_window_seconds` | 3600 (1 час) | как долго помнить |
| `non_replicated_deduplication_window` | 0 | то же для нереплицированной таблицы |

Отсюда две ловушки, которые видно только в проде:

- **час — не TTL каждого идентификатора в изоляции.** Временное окно считается относительно новых записей журнала; при постоянном потоке старый `block_id` обычно вытесняется примерно через час, но единственная запись может храниться дольше. Гарантию задаёт конечное окно, а не обещание «любой retry до часа безопасен»;
- **у обычного `MergeTree` дедупликации нет вовсе.** `non_replicated_deduplication_window = 0` выключает её по умолчанию. Одиночный сервер, стенд разработчика и тесты ведут себя иначе, чем реплицированный кластер, и защита, работающая в проде, в тестах не проверяется.

**Явный токен вместо хеша.** `insert_deduplication_token` задаёт идентичность вставки самим приложением и имеет приоритет над хешем содержимого:

```sql
INSERT INTO events SETTINGS insert_deduplication_token = 'orders-2026-04-01-batch-42'
VALUES (...);
```

Токен решает случаи, где хеш содержимого не работает:

- **недетерминированные данные.** Колонка с `DEFAULT now()` или `rand()` делает каждый повтор уникальным по содержимому, и хеш никогда не совпадёт;
- **другое разбиение на блоки при повторе.** Хеш считается по блоку целиком; если повтор нарезал те же строки иначе (другой размер батча, другой `max_insert_block_size`), совпадения не будет;
- **`INSERT ... SELECT`.** Источник должен вернуть те же строки в том же порядке; для стабильного результата обычно нужен `ORDER BY ALL` в части `SELECT` либо явный token.

Поскольку токен важнее содержимого, его коллизия опаснее обычного дубликата: другая порция данных с тем же token может быть принята как уже записанная. Токен обязан однозначно описывать **всю порцию**, а не только её начало. Для Kafka это, например, `topic + partition + first_offset + last_offset`; для файла — стабильный идентификатор файла и номер chunk. Такой token воспроизводится при retry, но меняется для другой порции.

**Взаимодействие с materialized view.** Вставка в таблицу с incremental materialized view порождает вставки в target tables. Модель настроек зависит от версии:

- **25.8 LTS:** обычная, асинхронная и dependent-view дедупликация управляются прежними раздельными настройками; для полного пути нужны `insert_deduplicate = 1` и `deduplicate_blocks_in_dependent_materialized_views = 1`;
- **26.1:** исправлен end-to-end путь для async insert и dependent views;
- **26.2+:** `deduplicate_insert` унифицирует обычные и асинхронные вставки и имеет приоритет над прежними настройками;
- **26.7:** для `INSERT ... SELECT` действует отдельный `deduplicate_insert_select = 'enable_when_possible'`: дедупликация включается, только если ClickHouse может доказать стабильность результата. Режим `force_enable` отклонит нестабильный запрос вместо тихого выполнения без защиты;
- **26.3 LTS+:** async insert включён по умолчанию, унифицированная дедупликация — основной режим.

Если исходная вставка выполнена с дедупликацией, выключенной на уровне запроса, ClickHouse не записывает `block_id`; включить настройку только на retry уже недостаточно. Версию и весь набор настроек нужно фиксировать в тесте pipeline, а не проверять один флаг отдельно.

**Чего этот уровень не делает.** Он не знает ничего о бизнес-смысле строк. Две разные вставки, содержащие одну и ту же сущность в разных состояниях, — не дубликат для этого механизма, и обе останутся в таблице. Это задача следующего уровня.

## Уровень 2: ReplacingMergeTree

`ReplacingMergeTree` оставляет одну строку на каждый уникальный ключ `ORDER BY`. Ключ сортировки здесь работает как ключ дедупликации — единственная роль, в которой он хоть как-то похож на первичный ключ реляционной базы.

```sql
CREATE TABLE orders (
    order_id    UInt64,
    status      LowCardinality(String),
    amount      Decimal(18, 2),
    version     UInt64,
    updated_at  DateTime64(3),
    is_deleted  UInt8 DEFAULT 0
)
ENGINE = ReplacingMergeTree(version, is_deleted)
ORDER BY order_id;
```

Параметры движка:

- **первый параметр — колонка версии** (`ver`). При слиянии выживает строка с максимальным значением; типы `UInt*`, `Date`, `DateTime`, `DateTime64`. Без версии выигрывает последняя вставленная — правило, на которое нельзя опираться, когда данные приходят из нескольких источников или переигрываются из очереди;
- **второй параметр — колонка удаления** (`is_deleted`, `UInt8`). Строка со значением `1` означает «сущность удалена». Задать её можно только вместе с версией.

**Что происходит при слиянии.**

```text
до merge (три parts, ORDER BY order_id, ver = version):

  part 1:  order_id=17  status='new'      version=100
  part 2:  order_id=17  status='paid'     version=105
  part 3:  order_id=17  status='shipped'  version=109

merge объединил part 1 и part 2:

  part 1+2: order_id=17  status='paid'     version=105   <- победила бо́льшая версия
  part 3:   order_id=17  status='shipped'  version=109   <- в слиянии не участвовал

SELECT * FROM orders WHERE order_id = 17          -> ДВЕ строки
SELECT * FROM orders FINAL WHERE order_id = 17    -> одна строка, status='shipped'
```

**Три правила, без которых движок не работает так, как ожидается.**

- **Дедупликация не происходит в момент вставки.** Между вставкой и слиянием таблица содержит все версии. Гарантий по времени нет: merge выбирается фоновым планировщиком по размеру и возрасту parts. Запрос без `FINAL` возвращает разное число строк в зависимости от того, когда его выполнили.
- **Слияние не пересекает границу партиции.** Все версии одной сущности обязаны попадать в одну партицию, иначе они не схлопнутся никогда. Отсюда практическое правило: колонки, входящие в `PARTITION BY`, не должны меняться при обновлении сущности. Партиционирование таблицы заказов по `toYYYYMM(updated_at)` — типичная ошибка: заказ, обновлённый в конце апреля и в начале мая, навсегда останется двумя строками в двух партициях.
- **На insert-time схлопывание полагаться нельзя.** Даже если несколько версий пришли одним запросом, модель корректности остаётся той же: физическое удаление старых версий происходит при merge, а запрос до этого обязан использовать `FINAL` или явную агрегацию.

**Удаление через `is_deleted`.** Строка-надгробие со значением `1` побеждает предыдущие версии при слиянии, но сама остаётся в таблице и продолжает возвращаться запросом. Для ручного удаления нужен `OPTIMIZE TABLE ... FINAL CLEANUP` при включённом `allow_experimental_replacing_merge_with_cleanup`. Автоматический cleanup требует согласованного набора `enable_replacing_merge_with_cleanup_for_min_age_to_force_merge`, `min_age_to_force_merge_on_partition_only` и `min_age_to_force_merge_seconds`; одного таймера недостаточно. В обычных запросах сначала выбирают последнюю версию сущности и лишь затем отбрасывают `is_deleted = 1`.

**Про `OPTIMIZE TABLE ... FINAL`.** Команда принудительно сливает партицию в один part и действительно убирает дубликаты. Она же переписывает всю партицию целиком. Для 200 ГБ при измеренной эффективной скорости rewrite 200 МБ/с нижняя оценка — `200 000 / 200 = 1000 секунд`, то есть около 17 минут; при 50 МБ/с — уже около 67 минут. Репликация, чтение, запись нового part и конкурирующая нагрузка увеличивают время и write amplification. Как разовая операция после переливки данных — уместна; как регулярная процедура по расписанию — способ загрузить диски бесполезной работой.

## Уровень 3: дедупликация на чтении

Пока merge не прошёл, дубликаты лежат в таблице, и запрос обязан справляться с ними сам. Есть три способа, и выбор между ними — это выбор между удобством и скоростью.

**`FINAL`** — движок выполняет слияние на лету, в момент чтения:

```sql
SELECT order_id, status, amount
FROM orders FINAL
WHERE order_id = 17;
```

Цена: вместо независимого чтения parts запрос вынужден читать пересекающиеся диапазоны согласованно, сливая их по ключу сортировки. Что смягчает эту цену:

- `max_final_threads` (по умолчанию 0 — авто) задаёт степень параллельности слияния при чтении;
- `do_not_merge_across_partitions_select_final` (по умолчанию 0) обрабатывает партиции независимо. Включать вручную его нужно осознанно: результат изменится, если один ключ встречается в разных партициях;
- `enable_automatic_decision_for_merging_across_partitions_for_final` (по умолчанию 1) включает предыдущую оптимизацию автоматически, когда выражение партиционирования детерминировано и все его колонки входят в первичный ключ. В этом случае движок сам доказал, что одинаковые ключи не могут оказаться в разных партициях.

Здесь же видна асимметрия, о которой легко забыть: фоновый merge никогда не сливает партиции, а `FINAL` по умолчанию сливает. Схема, где версии одной сущности расползлись по партициям, даёт корректный ответ с `FINAL` и не сходится физически никогда.

**`argMax`** — явная агрегация вместо слияния. Часто быстрее `FINAL` на широких сканах, потому что это обычный `GROUP BY` без требований к порядку чтения:

```sql
SELECT
    order_id,
    tupleElement(current, 1) AS status,
    tupleElement(current, 2) AS amount,
    tupleElement(current, 3) AS updated_at
FROM
(
    SELECT
        order_id,
        argMax(tuple(status, amount, updated_at, is_deleted), version) AS current
    FROM orders
    WHERE order_id BETWEEN 1000 AND 2000
    GROUP BY order_id
)
WHERE tupleElement(current, 4) = 0;
```

Один `argMax` над `tuple` гарантирует, что `status`, `amount`, время и tombstone взяты из одной версии строки. Несколько независимых `argMax(column, version)` при равной максимальной версии могут выбрать значения недетерминированно и собрать несуществующую комбинацию. Поэтому `version` должна быть уникальной и монотонной в пределах `order_id`; если источник допускает равенство, в max-аргумент включают стабильный tie-breaker: `tuple(version, source_offset)`.

Фильтровать `is_deleted` во внутреннем `WHERE` нельзя: это отбросило бы tombstone и вернуло предыдущую, «живую» версию. Сначала выбирается победитель, затем внешний запрос проверяет его признак удаления.

**`LIMIT 1 BY`** — оставить одну строку на ключ после сортировки:

```sql
SELECT order_id, status, amount, updated_at
FROM
(
    SELECT order_id, status, amount, updated_at, is_deleted, version
    FROM orders
    WHERE order_id BETWEEN 1000 AND 2000
    ORDER BY order_id, version DESC
    LIMIT 1 BY order_id
)
WHERE is_deleted = 0;
```

Читается ближе всего к исходному намерению, но требует сортировки выбранных строк — на больших выборках это дороже `argMax`.

| Способ | Что делает | Сильная сторона | Слабая сторона |
| --- | --- | --- | --- |
| `FINAL` | слияние parts при чтении | не меняет текст запроса | замедление тем сильнее, чем больше parts |
| `argMax` | агрегация по ключу | обычно быстрее на широких выборках | нужен стабильный version/tie-breaker |
| `LIMIT 1 BY` | одна строка на ключ после сортировки | явно показывает выбор победителя | требует сортировки и внешней проверки tombstone |

Практичный компромисс — прятать выбранный способ за обычным `VIEW`, чтобы приложение не повторяло его в каждом запросе:

```sql
CREATE VIEW orders_current AS
SELECT
    order_id,
    tupleElement(current, 1) AS status,
    tupleElement(current, 2) AS amount
FROM
(
    SELECT
        order_id,
        argMax(tuple(status, amount, is_deleted), version) AS current
    FROM orders
    GROUP BY order_id
)
WHERE tupleElement(current, 3) = 0;
```

## Collapsing и VersionedCollapsing

`CollapsingMergeTree` решает ту же задачу иначе: вместо «оставить последнюю версию» он взаимно уничтожает пары строк. Колонка `sign` принимает значение `1` (состояние) или `-1` (отмена состояния). Изменение сущности пишется двумя строками: отмена старого состояния и запись нового.

```text
INSERT: (user_id=5, views=10, sign=1)                     -- первое состояние

обновление до views=15 пишется парой строк:
INSERT: (user_id=5, views=10, sign=-1)                    -- отмена прежнего
INSERT: (user_id=5, views=15, sign=1)                     -- новое состояние

merge уничтожает первую и вторую строки, остаётся:
        (user_id=5, views=15, sign=1)
```

Запрос считает не строки, а суммы со знаком:

```sql
SELECT user_id, sum(views * sign) AS views
FROM user_stats
GROUP BY user_id
HAVING sum(sign) > 0;
```

Условие `sum(sign) > 0` отбрасывает сущности, у которых отмены и состояния сошлись в ноль, то есть удалённые.

Слабое место движка — зависимость от порядка: отмена, пришедшая раньше состояния (а это возможно при нескольких producers или переигрывании очереди), схлопывается неправильно. `VersionedCollapsingMergeTree` добавляет колонку версии и снимает требование к физическому порядку поступления пары.

На практике `ReplacingMergeTree` покрывает большинство случаев проще: он требует одну строку на обновление, а не две, и не требует знать предыдущее состояние сущности. Collapsing уместен там, где источник — поток изменений из OLTP-базы (`CDC`), который и так содержит образы «до» и «после».

## Какой способ дедупликации выбрать

| Ситуация | Решение | Что помнить |
| --- | --- | --- |
| Повтор запроса после таймаута | стабильный token + включённая дедупликация | окно конечно; token описывает весь batch |
| События append-only, повторов нет | `MergeTree`, ничего дополнительно | самый дешёвый вариант, не усложнять |
| Сущность обновляется, нужно «текущее состояние» | `ReplacingMergeTree(ver, is_deleted)` + `argMax` в запросах | все версии обязаны попадать в одну партицию |
| Поток изменений из OLTP-базы с образами «до/после» | `VersionedCollapsingMergeTree` | запросы через `sum(x * sign)` |
| Счётчики и агрегаты | `SummingMergeTree` или `AggregatingMergeTree` + materialized view | дедупликация вставки становится критичной: повтор задвоит сумму |
| Нужна строгая уникальность в момент записи | не ClickHouse | проверка уникальности — задача OLTP-базы перед вставкой |

Последняя строка — главный ответ на вопрос «как гарантировать отсутствие дубликатов». Гарантию в момент записи ClickHouse не даёт ни одним из механизмов: первый уровень закрывает окно повторов, второй сходится когда-нибудь, третий маскирует расхождение при чтении. Если инвариант уникальности нужен как бизнес-правило, его держат в PostgreSQL, а в ClickHouse льют поток событий.

## Interview-ready answer

**1. Почему в ClickHouse нельзя просто объявить уникальный ключ?**

- Проверка уникальности требует чтения перед записью, а вставка устроена как дозапись куска без чтения — на этом держится её стоимость.
- В распределённой таблице проверка упёрлась бы ещё и в другие шарды.
- Следствие — дедупликация решается схемой и запросами, а не ограничением.

**2. Как защититься от повтора одного и того же INSERT?**

- Механизм — по каждому блоку считается `block_id`, повтор с тем же идентификатором отбрасывается, клиент получает успех.
- Границы — конечный журнал: до 10 000 блоков и временное вытеснение старых записей относительно новых вставок.
- Ловушка — у нереплицированного `MergeTree` окно равно нулю, защиты нет вовсе.
- Надёжный вариант — `insert_deduplication_token`, выведенный из источника данных, а не сгенерированный заново.

**3. Что ломает дедупликацию вставки?**

- Недетерминированные данные: `now()` или `rand()` делают каждый повтор уникальным по содержимому.
- Другое разбиение на блоки при повторе: хеш считается по блоку целиком.
- `INSERT ... SELECT` с недетерминированным порядком строк; в 26.7 его отдельно контролирует `deduplicate_insert_select`.
- Коллизия явного token или retry с другим token.
- Несогласованные настройки по версиям: на 25.8 действуют старые раздельные флаги, в 26.2+ основной переключатель — `deduplicate_insert`.

**4. Как хранить сущность, у которой меняется состояние?**

- `ReplacingMergeTree(ver, is_deleted)`: ключ `ORDER BY` работает как ключ дедупликации, побеждает максимальная версия.
- Схлопывание происходит при слиянии, момент не гарантирован; до него в таблице лежат все версии.
- Все версии сущности обязаны попадать в одну партицию: слияние не пересекает границу партиции.
- Читать нужно через `FINAL`, `argMax` или `LIMIT 1 BY`, иначе результат зависит от того, прошло ли слияние.

**5. Чем argMax лучше FINAL?**

- `FINAL` выполняет слияние на лету и дорожает вместе с числом кусков.
- `argMax` — обычный `GROUP BY` без требований к порядку чтения, на широких выборках обычно быстрее.
- Цена `argMax` — запрос переписывается; `tuple` нужен, чтобы поля пришли из одной версии строки.
- Удобный компромисс — спрятать выбранный способ за обычным `VIEW`.

**6. Когда дедупликация не решается в ClickHouse вообще?**

- Когда уникальность нужна как бизнес-инвариант в момент записи: ни один из трёх уровней такой гарантии не даёт.
- Правильный ответ — держать инвариант в OLTP-базе, а в ClickHouse лить поток событий.
