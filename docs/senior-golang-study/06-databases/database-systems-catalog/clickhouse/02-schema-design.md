Схема в ClickHouse решает больше, чем в реляционной базе. Там неудачный индекс добавляется на живой таблице одной командой, здесь неудачный ключ сортировки означает перезаливку. Эта статья — про три решения, принимаемые до первой загрузки данных: как делить данные на партиции, в каком порядке их сортировать и какими типами описывать колонки.

---

## Схема проектируется от запросов

Нормализованная OLTP-схема редко переносится в ClickHouse один к одному: runtime `JOIN` имеет цену, а повторяющиеся значения широкого события хорошо сжимаются. Это не запрет на `JOIN`, а причина проектировать таблицу от access patterns и измерять стоимость соединения под целевой concurrency, а не копировать доменную модель автоматически.

Практические следствия:

- **широкая денормализованная таблица — норма.** Название категории, имя города и тип устройства кладутся в саму таблицу событий, а не подтягиваются соединением;
- **частые lookup по небольшим справочникам выносятся в dictionaries:** `dictGet` подставляет значение по ключу без построения hash table в каждом запросе; для исследовательских связей обычный `JOIN` может быть уместнее;
- **одни и те же данные могут лежать дважды** с разным `ORDER BY`, если запросы принципиально разные — это дешевле, чем заставлять один ключ обслуживать оба сценария.

## PARTITION BY, ORDER BY и PRIMARY KEY

Три разных механизма, которые легко перепутать.

| Механизм | Что задаёт | Что даёт запросу | Цена ошибки |
| --- | --- | --- | --- |
| `PARTITION BY` | деление данных на независимые группы каталогов | пропуск целых партиций, мгновенный `DROP PARTITION` | мелкие партиции → лавина parts |
| `ORDER BY` | физический порядок строк внутри part | быстрые диапазонные чтения, ключ дедупликации | смена ключа = перезаливка таблицы |
| `PRIMARY KEY` | по каким колонкам строится `primary.idx` | отсечение гранул по разреженному индексу | длинный ключ увеличивает индекс в памяти |

`PRIMARY KEY` по умолчанию равен `ORDER BY` и обязан быть его префиксом. Задавать его отдельно имеет смысл, когда сортировка нужна по большему числу колонок, чем индекс: например `ORDER BY (tenant_id, user_id, event_time)` с `PRIMARY KEY (tenant_id, user_id)` даст порядок по времени внутри пользователя, но не будет держать в памяти третью колонку индекса.

```sql
CREATE TABLE events (
    event_date  Date,
    event_time  DateTime,
    user_id     UInt64,
    event_type  LowCardinality(String),
    value       Float64
)
ENGINE = MergeTree
PARTITION BY event_date
ORDER BY (event_type, user_id, event_time);
```

Здесь:

- `PARTITION BY event_date` — запрос с фильтром по дате не открывает каталоги других дней;
- `ORDER BY (event_type, user_id, event_time)` — эффективны условия по `event_type`, по паре `(event_type, user_id)` и по их префиксам; условие только по `user_id` индексом не поддерживается, потому что это не префикс ключа.

Партиция по дню при удержании данных за год даёт 365 активных временных партиций — часто разумный порядок величины. Партиция по часу дала бы 8760 партиций: это не автоматический отказ, но parts распределяются по гораздо большему числу независимых очередей слияния, а операции с метаданными дорожают. Официальный грубый ориентир — держать кардинальность partition key ниже диапазона примерно 1000–10 000; точный предел зависит от объёма на партицию, частоты вставок и хранения.

`LowCardinality(String)` заменяет строку на числовой код в словаре. Для колонки с десятком различных значений это уменьшает и объём на диске, и стоимость `GROUP BY`. Для колонки с миллионами уникальных значений словарь становится дороже самих данных, и тип вредит.

## Как выбрать ORDER BY

Ключ сортировки решает три задачи сразу: задаёт физический порядок строк, определяет разреженный индекс и служит ключом дедупликации для движков семейства Replacing и Collapsing. Правила выбора вытекают из первых двух.

- **Первой ставится колонка, по которой фильтруют почти всегда.** Индекс работает по префиксу ключа: при `ORDER BY (a, b, c)` условие по `a` отсекает гранулы, условие только по `c` — нет.
- **Дальше учитываются селективность, кардинальность и корреляция.** Колонка с небольшим числом значений в начале ключа создаёт длинные однородные диапазоны и улучшает сжатие. Уникальный идентификатор не превращает разреженный индекс в построчный — засечка всё равно одна на гранулу, — но часто ухудшает локальность для аналитических фильтров. Если основной запрос действительно ищет по этому идентификатору, он может быть первым: выбор проверяют по реальным access patterns, а не по кардинальности в отрыве от запросов.
- **Время обычно идёт последним.** Оно почти уникально, зато внутри уже отобранной группы даёт нужный порядок и хорошо сжимается кодеком `Delta`.
- **Ключ не должен быть длинным.** Каждая колонка ключа занимает место в `primary.idx`, который держится в памяти; три-четыре колонки — обычный размер.

Разница между `ORDER BY` и `PRIMARY KEY` нужна редко, но в одном случае решает: когда сортировка требуется по большему числу колонок, чем есть смысл держать в индексе. Тогда `PRIMARY KEY` объявляется префиксом ключа сортировки, и последняя колонка участвует в порядке, но не раздувает индекс.

Если один ключ не обслуживает два разных класса запросов, ответ — не компромиссный ключ, а вторая структура: проекция или отдельная таблица с другим `ORDER BY`, заполняемая materialized view. Проекции разобраны в [06-query-execution.md](./06-query-execution.md), materialized view — в [08-materialized-views.md](./08-materialized-views.md).

## Как выбрать PARTITION BY

Партиционирование в ClickHouse — не инструмент ускорения запросов в первую очередь, а инструмент управления жизненным циклом данных. Отсечение партиций даёт первый и самый грубый фильтр, но главное — целую партицию можно мгновенно удалить или перенести на другой диск.

- **По времени и почти всегда по месяцу или дню.** `toYYYYMM(event_time)` для долгого хранения, `event_date` для потока в десятки миллионов строк в день.
- **Предпочтительный порядок — сотни или первые тысячи активных партиций.** Каждая партиция — независимый набор parts со своим слиянием; диапазон около 1000–10 000 уже требует измерений и веской причины.
- **Ключ партиционирования не должен меняться у существующей строки.** Иначе новая версия попадёт в другую партицию, а слияние границу партиции не пересекает — [04-deduplication.md](./04-deduplication.md).
- **Колонка с высокой кардинальностью в ключе партиционирования — ошибка.** Вставка, задевшая больше `max_partitions_per_insert_block = 100` партиций, будет отклонена.

Иногда к времени добавляют вторую колонку: `PARTITION BY (toYYYYMM(event_time), tenant_id)` позволяет удалять данные конкретного арендатора одной командой. Цена — умножение числа партиций на число арендаторов, поэтому приём годится для десятков крупных арендаторов, но не для тысяч мелких.

## Типы колонок

| Тип | Когда применять | Чем платят |
| --- | --- | --- |
| `LowCardinality(String)` | повторяющиеся строки, грубый ориентир — меньше 10 тысяч значений | на высокой кардинальности словарь и lookup могут не окупиться |
| `Enum8` / `Enum16` | фиксированный список значений, известный заранее | новое значение требует `ALTER` |
| `DateTime` | момент времени с точностью до секунды | часовой пояс задаётся типом или сервером |
| `DateTime64(3)` | нужна миллисекундная точность | больше объём, медленнее сравнения |
| `Decimal(18, 2)` | деньги | арифметика медленнее, чем у `Float` |
| `UInt*` вместо `Int*` | счётчики и идентификаторы с доказанно неотрицательным диапазоном | отрицательное значение не представимо; преобразования и арифметику нужно проверять |
| `Nullable(T)` | значение действительно бывает неизвестным | отдельный null-map substream, хуже сжатие и медленнее чтение |

Отдельно про `Nullable`: в ClickHouse это не бесплатный модификатор, как в PostgreSQL, а дополнительный поток null mask рядом с данными. В Wide part он обычно представлен отдельным физическим substream; Compact part упакован иначе, но логическая цена остаётся. Если «неизвестно» и «ноль» бизнес-логика не различает, дешевле объявить колонку `DEFAULT 0`, чем `Nullable`.

Сжатие настраивается кодеками поверх типа: `Delta` перед общим кодеком для монотонно растущих значений вроде меток времени, `DoubleDelta` для равномерных рядов, `Gorilla` для медленно меняющихся чисел с плавающей точкой, `T64` для целых в узком диапазоне.

```sql
CREATE TABLE metrics (
    ts     DateTime CODEC(Delta, ZSTD(1)),
    device LowCardinality(String),
    value  Float64  CODEC(Gorilla, ZSTD(1))
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (device, ts);
```

## TTL: срок жизни данных

`TTL` задаёт правило, по которому движок сам избавляется от старых данных или переносит их на другой диск.

```sql
ALTER TABLE events MODIFY TTL
    event_date + INTERVAL 30 DAY TO VOLUME 'cold',
    event_date + INTERVAL 90 DAY DELETE;
```

Данные старше 30 дней уезжают на медленный том, старше 90 — удаляются. Это дешевле любого `DELETE`, а при настройке таблицы `ttl_only_drop_parts = 1` истёкший кусок удаляется целиком, без перезаписи. Подробнее про стоимость удаления — [05-update-and-delete.md](./05-update-and-delete.md).

## Что менять на живой таблице можно, а что нет

| Изменение | Возможно | Цена |
| --- | --- | --- |
| Добавить колонку | да | метаданные, данные не переписываются |
| Удалить колонку | да | удаление файлов колонки и метаданных; обычно быстро, но освобождение места зависит от формата parts и реплик |
| Сменить тип колонки | да, если приведение допустимо | мутация с перезаписью колонки |
| Добавить колонку в конец `ORDER BY` | да, `MODIFY ORDER BY` | только если колонка добавлена и не входит в `PRIMARY KEY` |
| Изменить порядок или начало `ORDER BY` | нет | новая таблица и переливка данных |
| Сменить `PARTITION BY` | нет | новая таблица и переливка данных |
| Сменить движок | нет | новая таблица и переливка данных |

Три нижние строки и делают проектирование схемы решением, которое дороже всего исправлять. Практический вывод: до первой загрузки полезно прогнать на реальном срезе данных те запросы, ради которых таблица создаётся, и посмотреть на объём и на число прочитанных строк.

## Interview-ready answer

**1. Чем PARTITION BY отличается от ORDER BY?**

- `PARTITION BY` делит данные на независимые группы каталогов: даёт отсечение партиций и мгновенное удаление старых данных.
- `ORDER BY` задаёт физический порядок строк внутри куска, определяет разреженный индекс и служит ключом дедупликации.
- Не путать с реляционной моделью — ни то, ни другое не проверяет уникальность.

**2. Как выбрать ORDER BY?**

- Первой — колонка, по которой фильтруют почти всегда: индекс работает только по префиксу ключа.
- Дальше — по селективности, кардинальности и корреляции; время часто оказывается ближе к концу.
- Длину держать в три-четыре колонки: индекс лежит в памяти.
- Уникальный идентификатор в начале обычно ухудшает локальность аналитических запросов, но оправдан, если точечный lookup — основной access pattern.

**3. Сколько партиций считается нормой?**

- Часто сотни или первые тысячи; 8760 часовых партиций — уже повод доказать выбор измерениями, но не универсальная граница отказа.
- Ограничение сверху на вставку — `max_partitions_per_insert_block = 100` затронутых партиций в одном блоке.

**4. Когда LowCardinality вредит?**

- Когда различных значений много: словарь становится дороже самих данных.
- Грубый ориентир — меньше 10 тысяч различных значений, но решение проверяется по размеру и скорости на реальных данных.

**5. Что нельзя изменить на живой таблице?**

- Ключ сортировки в начале, ключ партиционирования и движок — только новая таблица и переливка через `INSERT ... SELECT`.
- Добавить колонку в конец `ORDER BY` можно, если она новая и не входит в первичный ключ.
