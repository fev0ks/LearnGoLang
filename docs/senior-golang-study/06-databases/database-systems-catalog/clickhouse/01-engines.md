Движок таблицы в ClickHouse определяет, где и как хранятся данные, какие операции поддерживает таблица и что происходит при фоновом слиянии частей. Для семейства MergeTree особенно важно последнее: выбранный движок задаёт семантику схлопывания версий, суммирования или удаления строк. Механика хранения и слияния разобрана в [00-storage-model.md](./00-storage-model.md).

## Семейство MergeTree

Движок определяет, что merge делает со строками, у которых совпал ключ `ORDER BY`.

| Движок | Что делает при merge | Типичное применение |
| --- | --- | --- |
| `MergeTree` | ничего, все строки остаются | события append-only |
| `ReplacingMergeTree` | оставляет одну строку на ключ | таблица состояний, upsert |
| `CoalescingMergeTree` | берёт последнее не-`NULL` значение каждой колонки | разреженные частичные обновления состояния |
| `SummingMergeTree` | складывает числовые колонки | предагрегация счётчиков |
| `AggregatingMergeTree` | сливает состояния агрегатных функций | целевые таблицы materialized view |
| `CollapsingMergeTree` | взаимно уничтожает строки со `sign = 1` и `sign = -1` | поток изменений из OLTP-базы |
| `VersionedCollapsingMergeTree` | то же, но с учётом версии | тот же поток при нарушенном порядке |

Префикс `Replicated` (`ReplicatedMergeTree`, `ReplicatedReplacingMergeTree`) добавляет репликацию через ClickHouse Keeper или ZooKeeper. У реплицированных движков журнал дедупликации включён по умолчанию и согласован между репликами. У обычного `MergeTree` локальная дедупликация тоже существует, но `non_replicated_deduplication_window` по умолчанию равен нулю, поэтому её нужно включать осознанно.

Общее свойство всех перечисленных движков: преобразование происходит при merge, то есть неизвестно когда. Пока merge не прошёл, таблица содержит и старые, и новые строки, а запрос без специальных мер видит их все. Отсюда правило, действующее для всей семьи: движок отвечает за то, к чему данные сойдутся со временем, а не за то, что вернёт следующий запрос. Как получить корректный ответ до слияния — [04-deduplication.md](./04-deduplication.md).

`CoalescingMergeTree` появился в 25.6 и полезен, когда разные события заполняют разные поля одной сущности: например, батарею, координаты и версию прошивки устройства. Все обновляемые поля делают `Nullable`, а при merge движок сохраняет последнее не-`NULL` значение каждой колонки по ключу `ORDER BY`. «Последнее» определяется порядком вставки, а не timestamp из строки; до merge корректное состояние читают через `FINAL` либо собирают явной агрегацией со стабильной версией. Для CDC с полной строкой и явной монотонной версией `ReplacingMergeTree` обычно проще.

`GraphiteMergeTree` в таблице не приведён: это специализированный движок для прореживания метрик Graphite по правилам хранения, за пределами этой ниши он не используется.

## Префикс Replicated

Репликация в ClickHouse задаётся на уровне таблицы, а не кластера: `ReplicatedMergeTree` реплицируется, соседняя `MergeTree` в той же базе — нет. Реплики равноправны, запись принимает любая из них, а остальные подтягивают куски через журнал в Keeper.

Практическое следствие для разработки: стенд на одиночном сервере с обычным `MergeTree` ведёт себя иначе, чем производственный кластер. На нём нет кворумной записи и очереди репликации, а локальная дедупликация обычно выключена. Поэтому сценарии retry и отказов нужно отдельно проверять на конфигурации, близкой к производственной, — разбор в [04-deduplication.md](./04-deduplication.md).

Устройство репликации, шардирование и движок `Distributed` разобраны в [10-sharding-and-replication.md](./10-sharding-and-replication.md).

## Служебные движки

Кроме семейства MergeTree есть движки, которые ничего не хранят сами или хранят данные особым образом. Их роль — соединять ClickHouse с внешним миром и с самим собой.

| Движок | Что это | Зачем нужен |
| --- | --- | --- |
| `Distributed` | таблица-прокси поверх шардов | запрос ко всем шардам как к одной таблице |
| `Buffer` | буфер в памяти перед целевой таблицей | сгладить мелкие вставки; данные могут потеряться при аварийном завершении |
| `Kafka` | подписка на топик как таблица | загрузка потока без внешнего консьюмера |
| `Dictionary` | доступ к словарю как к таблице | подстановка справочных значений вместо `JOIN` |
| `MySQL`, `PostgreSQL`, `S3`, `URL` | чтение внешнего источника | разовая переливка и федеративные запросы |
| `Merge` | чтение нескольких таблиц как одной | объединение таблиц с одинаковой схемой |
| `Null` | принимает и выбрасывает данные | цель для materialized view, когда сырые данные не нужны |
| `Memory` | таблица целиком в памяти | временные данные и тесты |

Связка `Null` + materialized view встречается чаще, чем кажется: сырой поток пишется в таблицу-пустышку, а на выходе materialized view оседают только агрегаты. Данные не хранятся дважды, а вход в конвейер выглядит как обычный `INSERT`.

## Как выбрать движок

| Что за данные | Движок | Почему |
| --- | --- | --- |
| События, которые не меняются | `MergeTree` | ничего лишнего, самый дешёвый вариант |
| Сущность с состоянием, нужен upsert | `ReplacingMergeTree` | последняя версия по ключу и колонке версии |
| Частичные обновления разных полей | `CoalescingMergeTree` | объединяет последние не-`NULL` значения по ключу |
| Счётчики по ключу | `SummingMergeTree` | суммирование при слиянии вместо пересчёта |
| Целевая таблица materialized view | `AggregatingMergeTree` | хранит состояния агрегатов, а не готовые числа |
| Поток изменений с образами «до» и «после» | `VersionedCollapsingMergeTree` | взаимное уничтожение пар без зависимости от порядка |
| Производственный кластер | тот же движок с префиксом `Replicated` | репликация и защита вставки от повторов |

Ошибка выбора обходится дорого: сменить движок таблицы на месте нельзя, потребуется создать новую таблицу и перелить данные через `INSERT ... SELECT`. Поэтому движок выбирается вместе с ключом сортировки, до первой загрузки — [02-schema-design.md](./02-schema-design.md).

## Interview-ready answer

**1. За что отвечает движок таблицы в ClickHouse?**

- За способ хранения и поведение таблицы; для семейства MergeTree — в том числе за преобразование строк при фоновом слиянии.
- Например, строки остаются как есть, схлопываются по ключу, суммируются или взаимно уничтожаются.

**2. Чем отличаются ReplacingMergeTree, CoalescingMergeTree и CollapsingMergeTree?**

- `ReplacingMergeTree` — одна строка на ключ `ORDER BY`, побеждает максимальная версия; обновление это одна вставка.
- `CoalescingMergeTree` — последнее не-`NULL` значение выбирается отдельно для каждой колонки; подходит для разреженных частичных обновлений.
- `CollapsingMergeTree` — пары строк со `sign = 1` и `sign = -1` уничтожают друг друга; обновление это две вставки и знание прежнего состояния.
- Выбор — Replacing проще и покрывает большинство случаев, Coalescing экономит повтор неизменившихся полей, Collapsing уместен для потока с образами «до/после».

**3. Что даёт префикс Replicated?**

- Репликацию на уровне таблицы через ClickHouse Keeper, с равноправными репликами.
- Общий журнал дедупликации повторных вставок в Keeper. У нереплицированной таблицы возможен локальный журнал, но по умолчанию его окно равно нулю.

**4. Зачем нужны Distributed, Buffer и Null?**

- `Distributed` — прокси поверх шардов, чтобы запрос к кластеру выглядел как запрос к одной таблице.
- `Buffer` — сглаживание мелких вставок в памяти, ценой риска потери данных при аварийном завершении.
- `Null` — приёмник для materialized view, когда нужны только агрегаты, а сырые данные хранить незачем.
