Всё поведение ClickHouse — от требования батчить вставку до дорогого `UPDATE` и отсутствия уникальных ключей — выводится из устройства хранения. Эта статья разбирает его снизу вверх: как данные лежат на диске, какими порциями читаются и что с ними делает фоновое слияние.

---

## Столбцовое хранение

В строчной базе данных значения одной строки лежат на диске рядом: чтобы прочитать одно поле, приходится поднять всю строку. В столбцовой рядом лежат значения одной колонки.

```text
Строчное хранение (PostgreSQL):
  [id=1, type='view', value=10][id=2, type='cart', value=20][id=3, ...]
  запрос sum(value) поднимает с диска и id, и type

Столбцовое хранение (ClickHouse):
  id:     [1, 2, 3, ...]
  type:   ['view', 'cart', ...]
  value:  [10, 20, ...]
  запрос sum(value) читает только один файл
```

Отсюда два выигрыша сразу. Первый очевиден: запрос `SELECT event_type, count() FROM events GROUP BY event_type` по таблице из пятидесяти колонок читает данные только колонки `event_type`; `count()` не является отдельной колонкой на диске. Второй важнее для объёма: соседние значения одной колонки однородны — идут подряд одинаковые коды типа события, близкие метки времени, повторяющиеся идентификаторы. Такие данные сжимаются в разы лучше, чем чересполосица разнотипных полей одной строки, а меньший объём на диске означает меньше чтения.

Цена решения — обратная сторона того же свойства: собрать одну строку целиком дорого, потому что её поля разбросаны по разным файлам. Поэтому профиль «прочитать и обновить конкретную запись по идентификатору» здесь проигрывает реляционной базе, а профиль «просканировать миллиард строк по трём колонкам» — выигрывает.

## Part: единица хранения

**Part (кусок данных)** — каталог на диске с данными одной партиции, отсортированными по ключу `ORDER BY`. Part неизменяем: после создания в него не дописывают и не правят строки.

Ниже показан распространённый формат `Wide`, где у каждой колонки свои файлы данных и засечек. Небольшие parts ClickHouse может записывать в формате `Compact`: значения всех колонок лежат в одном файле, чтобы не создавать десятки маленьких файлов. Порог выбора задают `min_bytes_for_wide_part` и `min_rows_for_wide_part`. Логическая модель — сортировка, гранулы и разреженный индекс — от формата part не меняется.

```text
Каталог одного part: 20260401_1_1_0/

  primary.idx        значения ORDER BY для первой строки каждой гранулы
  event_time.bin     сжатые данные колонки event_time
  event_time.mrk3    засечки: где в .bin начинается каждая гранула
  user_id.bin
  user_id.mrk3
  ...
  count.txt          число строк в part
  checksums.txt      контрольные суммы файлов

Имя part: <партиция>_<мин.блок>_<макс.блок>_<уровень слияния>

  20260401_1_1_0   вставка №1, ещё не сливалась (уровень 0)
  20260401_2_2_0   вставка №2
  20260401_1_2_1   результат слияния двух предыдущих (уровень 1)
```

## Гранула: единица чтения

**Гранула** — минимальный диапазон строк, который разреженный индекс умеет отбирать как единое целое. `index_granularity = 8192` задаёт верхний ориентир по числу строк, но при адаптивной гранулярности размер дополнительно ограничен `index_granularity_bytes` — по умолчанию примерно 10 МиБ несжатых данных. Поэтому у широких строк в грануле может быть заметно меньше 8192 строк.

Следствие остаётся тем же: точечный запрос читает и распаковывает не одну строку, а содержащую её гранулу. Точное число строк зависит от ширины записи и настроек таблицы.

```text
Упрощённый пример для узких строк,
index_granularity = 8192 и не сработавшего ограничения по байтам:

  строки 0..8191       -> гранула 0    primary.idx[0] = ключ строки 0
  строки 8192..16383   -> гранула 1    primary.idx[1] = ключ строки 8192
  строки 16384..24575  -> гранула 2    primary.idx[2] = ключ строки 16384
```

## Разреженный индекс

**Разреженный индекс** (`sparse index`) — `primary.idx` хранит значение ключа не для каждой строки, а для начала каждой гранулы. Если для оценки предположить фиксированные гранулы по 8192 строки, part на 100 млн строк даёт `ceil(100 000 000 / 8192) = 12 208` засечек. При ключе из трёх восьмибайтовых колонок полезная нагрузка ключей составит `12 208 × 24 = 292 992 байта`, то есть примерно 286 КиБ. Реальный файл включает служебные данные, а при адаптивной гранулярности число засечек может быть больше.

Плата за разреженность: индекс не отвечает на вопрос «есть ли такая строка», он отвечает «в каких гранулах она может быть». Точечный поиск по ключу читает минимум одну гранулу, поэтому «достать одну строку по id» обычно стоит здесь дороже, чем в PostgreSQL, даже при подходящем ключе.

## Merge: слияние кусков

**Merge (слияние)** — фоновый процесс, который берёт несколько parts одной партиции и пишет из них один новый, сохраняя порядок сортировки. Старые куски после этого помечаются неактивными и удаляются.

```text
до слияния:                          после слияния:

  20260401_1_1_0   (уровень 0)   ->   20260401_1_3_1   (уровень 1)
  20260401_2_2_0   (уровень 0)         неактивные куски удаляются
  20260401_3_3_0   (уровень 0)
```

Слияние решает сразу две задачи. Первая — не дать числу кусков расти бесконечно: каждый кусок это отдельные файлы, и запрос вынужден заглянуть в каждый из них. Вторая — именно при слиянии движки семейства MergeTree применяют своё преобразование: схлопывают версии строк, складывают счётчики, вычищают удалённые строки. Разбор движков — в [01-engines.md](./01-engines.md).

Ключевое ограничение: слияние никогда не пересекает границу партиции. Куски из разных партиций не сливаются ни при каких условиях, и на этом правиле держится весь разбор дедупликации в [04-deduplication.md](./04-deduplication.md).

## Что из этого следует

Из трёх свойств — неизменяемость кусков, чтение гранулами и слияние в фоне — выводятся практические правила, которые дальше разбираются в отдельных статьях:

- **вставка обязана быть батчевой**, потому что каждая создаёт кусок, а стоимость куска почти не зависит от числа строк в нём — [03-insert-path.md](./03-insert-path.md);
- **изменение и удаление строк не бесплатны**, потому что кусок нельзя поправить на месте, его можно только переписать целиком или прикрыть патчем — [05-update-and-delete.md](./05-update-and-delete.md);
- **уникальность не проверяется при записи**: сортировка внутри куска ничего не говорит о содержимом соседних кусков, поэтому дубликаты — вопрос схемы и запросов — [04-deduplication.md](./04-deduplication.md);
- **порядок сортировки решает всё для чтения**: индекс работает только по префиксу `ORDER BY` — [02-schema-design.md](./02-schema-design.md) и [06-query-execution.md](./06-query-execution.md).

## Interview-ready answer

**1. Что такое part и почему он неизменяем?**

- Part — каталог с данными одной партиции, отсортированными по `ORDER BY`; внутри лежат файлы колонок, засечки и индекс.
- Неизменяемость даёт дешёвую запись: вставка не ищет и не правит существующие данные, а только дозаписывает новый каталог.
- Плата — фоновое слияние обязано постоянно объединять куски, иначе их число растёт и чтение дорожает.

**2. Что такое гранула и index_granularity?**

- Гранула — минимальный диапазон, который индекс отбирает как единое целое: до 8192 строк по умолчанию, но также с ограничением по объёму через `index_granularity_bytes`.
- Следствие — точечный запрос всё равно читает гранулу, поэтому чтение одной строки по ключу обычно дороже, чем в OLTP-базе.

**3. Почему индекс называется разреженным?**

- В `primary.idx` хранится ключ только первой строки каждой гранулы, а не каждой строки.
- При допущении о фиксированных гранулах 100 млн строк дают около 12 тысяч засечек, то есть порядок сотен килобайт для короткого ключа.
- Смысл ответа — индекс отвечает не «есть ли строка», а «в каких гранулах она может быть».

**4. Что делает merge и чего он не делает?**

- Делает — объединяет куски одной партиции в один, сохраняя порядок, и применяет преобразование движка: схлопывание версий, суммирование, вычистку удалённых строк.
- Не делает — не пересекает границу партиции: куски разных партиций не сливаются никогда.
- Практический вывод — если версии одной сущности попали в разные партиции, они не схлопнутся ни при каком слиянии.
