# Пагинация

Пагинация кажется простой, пока таблица маленькая. На больших таблицах наивный `OFFSET` деградирует, а при живом потоке данных ещё и теряет/дублирует строки. Здесь — какие бывают подходы, их компромиссы и нюансы под PostgreSQL.

## Offset-пагинация

Классика: `LIMIT N OFFSET M`.

```sql
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 50 OFFSET 10000;
```

**Почему глубокий OFFSET дорогой.** БД не умеет «перепрыгнуть» 10000 строк — она **читает и отбрасывает** их, чтобы добраться до нужного окна. `OFFSET 10000 LIMIT 50` обрабатывает 10050 строк ради 50. В `EXPLAIN ANALYZE` это видно по `Rows Removed`/большому `actual rows` под узлом сортировки. Стоимость растёт линейно с глубиной страницы: 1000-я страница в ~1000 раз дороже первой.

**Вторая беда — дрейф данных.** Между запросами страниц данные меняются. Вставили строку в начало (при `ORDER BY created_at DESC`) — и «страница 2» сдвинулась: пользователь увидит уже показанную строку (дубль) или пропустит одну. Offset нумерует по позиции, а позиция нестабильна.

Плюсы: тривиально реализовать, легко «прыгнуть на страницу N», удобно для UI «1 2 3 … 100».
Минусы: деградация на глубоких страницах, дубли/пропуски при живом потоке.

Вывод: offset ок для **маленьких** или **редко меняющихся** наборов и когда реально нужен произвольный доступ к странице. Для лент/бесконечного скролла по большим таблицам — keyset.

## Keyset-пагинация (cursor / seek)

Идея: вместо «пропусти M строк» — «дай строки **после** вот этого значения». Курсор — это значение сортировочного ключа последней показанной строки.

```sql
-- следующая страница: строки со временем меньше, чем у последней показанной
SELECT * FROM orders
WHERE created_at < $1            -- $1 = created_at последней строки прошлой страницы
ORDER BY created_at DESC
LIMIT 50;
```

Здесь БД по индексу **сразу спускается** к нужному месту и читает ровно 50 строк — стоимость **не зависит** от глубины страницы. И дрейфа нет: курсор привязан к значению, а не к позиции.

### Tie-breaker и сравнение кортежей

Если ключ сортировки **не уникален** (два заказа с одинаковым `created_at`), простой `<` теряет или дублирует строки на границе страницы. Решение — добавить в сортировку уникальный tie-breaker (обычно PK) и сравнивать **кортежи целиком**:

```sql
SELECT * FROM orders
WHERE (created_at, id) < ($1, $2)      -- row-comparison: строгий лексикографический порядок
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

`(created_at, id) < ($1, $2)` — это встроенное сравнение кортежей: сначала по `created_at`, при равенстве по `id`. Ровно то, что нужно для стабильной границы. Разворачивать его вручную в `created_at < $1 OR (created_at = $1 AND id < $2)` не нужно — но если разворачиваешь, то именно так (частая ошибка — забыть вторую ветку).

Порядок `ORDER BY` и знак сравнения обязаны совпадать: оба `DESC` → `<`; оба `ASC` → `>`.

### Индекс под keyset

Запрос эффективен, только если есть индекс, чей порядок **точно совпадает** с `ORDER BY`:

```sql
CREATE INDEX idx_orders_created_id ON orders (created_at DESC, id DESC);
```

Тогда план — `Index Scan` по индексу без отдельной сортировки: спуск к курсору + чтение 50 строк. Если направления в индексе и в `ORDER BY` расходятся — PostgreSQL может читать индекс в обратную сторону (`Index Scan Backward`), но составной ключ с разными направлениями (`created_at DESC, id ASC`) требует и индекса с такими же направлениями.

### Курсор в API

Наружу отдавать сырые `created_at`/`id` не обязательно — курсор делают **непрозрачным** (opaque): кодируют ключ в base64-токен `next_cursor`. Клиент его не парсит, просто возвращает в следующем запросе. Это позволяет менять состав ключа, не ломая контракт.

```text
GET /orders?limit=50
→ { items: [...], next_cursor: "eyJjcmVhdGVkX2F0IjoiMjAyNC0wMS0..." }

GET /orders?limit=50&cursor=eyJjcmVhdGVkX2F0...
```

Признак «есть ещё страница»: запросить `LIMIT 51`, вернуть 50, а по наличию 51-й выставить `has_more`.

### Пагинация назад

Для «предыдущей страницы» — перевернуть знак и порядок, потом развернуть результат в приложении:

```sql
-- назад от курсора: берём в обратную сторону, затем reverse в коде
SELECT * FROM orders
WHERE (created_at, id) > ($1, $2)
ORDER BY created_at ASC, id ASC
LIMIT 50;
```

## Offset vs Keyset: сравнение

| | Offset (`LIMIT/OFFSET`) | Keyset (cursor) |
|---|---|---|
| Стоимость глубокой страницы | растёт линейно (читает и отбрасывает) | константная (спуск по индексу) |
| Стабильность при живых данных | дубли/пропуски (позиция плывёт) | стабильна (привязка к значению) |
| Прыжок на «страницу N» | легко | нельзя (только вперёд/назад) |
| Сложность API | простой (номер страницы) | нужен курсор/токен |
| Требование к индексу | желателен | **обязателен** под `ORDER BY` |
| Когда | малые/статичные наборы, нужен random-access | ленты, бесконечный скролл, большие/живые таблицы |

Компромисс: можно комбинировать — offset внутри узкого, уже отфильтрованного окна (когда OFFSET заведомо мал), keyset для основной ленты.

## Проблема общего количества (COUNT)

UI часто хочет «страница 5 из 340» — то есть общее число строк. Но `SELECT count(*) FROM orders WHERE …` на большой таблице — это **полный проход** (Seq Scan или Index Only Scan по всем подходящим строкам), часто дороже самой страницы. Варианты:

- **Не показывать точное число** — «бесконечный скролл» или «Далее», где total не нужен вовсе (лучший вариант для больших лент).
- **Приблизительная оценка** без фильтров — из статистики планировщика, мгновенно:
  ```sql
  SELECT reltuples::bigint AS approx FROM pg_class WHERE relname = 'orders';
  -- или из EXPLAIN: оценка rows у плана запроса
  ```
- **Показывать «10 000+»** — считать `count(*)` с `LIMIT`-ограничением (например до 10 000) и показывать «>10k».
- **Кэшировать/материализовать** счётчики, если точное число действительно нужно часто.

## Динамическая сортировка и фильтры

Опасная комбинация — много опциональных фильтров + сортировка «по любому столбцу от UI». Проблемы:

- keyset требует **детерминированного** `ORDER BY`, совпадающего с индексом; произвольная сортировка от клиента ломает и keyset, и производительность;
- индекс на каждый вариант сортировки/фильтра плодит индексы (overhead на запись, см. [02-indexes.md](./02-indexes.md)).

Практика:
- **ограничить** список сортируемых/фильтруемых полей белым списком (не «любой столбец»);
- под реальные комбинации завести **композитные** индексы под keyset;
- каждый поддерживаемый вариант проверить через [EXPLAIN](./03-query-planning.md) — что идёт `Index Scan`, а не `Seq Scan` + `Sort`;
- никогда не подставлять имя столбца сортировки в SQL строкой из запроса пользователя (SQL-инъекция) — только через белый список.

## N+1 при загрузке связанных данных

Классический антипаттерн уровня приложения: загрузили 100 заказов, потом **для каждого** отдельным запросом тянем пользователя → 1 + 100 запросов.

Лечения:
- **JOIN** — одним запросом (когда нужны колонки связанной таблицы);
- **batch-запрос** по собранным id: `WHERE user_id = ANY($1)` — один запрос вместо N;
- **preload/dataloader** на уровне репозитория — собрать id страницы, догрузить связанные одним `ANY(...)`, разложить по map.

```sql
-- вместо 100 запросов по одному user_id
SELECT * FROM users WHERE id = ANY($1);   -- $1 = массив собранных user_id
```

## Поиск по тексту

Если пагинация идёт поверх поиска:
- `LIKE '%text%'` по большой таблице не масштабируется (Seq Scan) — ускоряется триграммным GIN (`gin_trgm_ops`, см. [02-indexes.md](./02-indexes.md));
- для настоящего полнотекстового поиска — `tsvector`/`tsquery` + GIN ([07-jsonb-and-arrays.md](./07-jsonb-and-arrays.md));
- при больших объёмах и сложном ранжировании — внешний движок (Elasticsearch/OpenSearch).

Нюанс: пагинация по релевантности (`ORDER BY rank`) плохо ложится на keyset (ранг не уникален и пересчитывается) — там чаще offset в пределах небольшого top-K.

## Interview-ready answer

**1. Чем плох `OFFSET` на глубоких страницах?**

- БД читает и отбрасывает все `OFFSET` строк, чтобы дойти до окна → стоимость растёт линейно с глубиной. Плюс при живом потоке страницы «плывут» — дубли и пропуски, потому что offset нумерует по позиции.

**2. Как работает keyset-пагинация и почему она стабильнее?**

- Вместо «пропусти M» — «дай строки после курсора» (`WHERE (created_at, id) < ($1,$2) ORDER BY created_at DESC, id DESC LIMIT N`). По индексу БД сразу спускается к месту — стоимость не зависит от глубины, а привязка к значению (а не позиции) убирает дрейф. Нужен tie-breaker (PK) и индекс под тот же `ORDER BY`.

**3. Минусы keyset?**

- Нельзя прыгнуть на произвольную страницу (только вперёд/назад), нужен курсор в API, обязателен подходящий индекс, произвольная пользовательская сортировка усложняет.

**4. Почему `COUNT(*)` для «страница X из Y» — проблема?**

- Это полный проход по подходящим строкам, часто дороже самой страницы. Решения: не показывать total (бесконечный скролл), приблизительная оценка из `pg_class.reltuples`, или «10k+» через `count` с `LIMIT`.

**5. Что такое N+1 и как лечить?**

- 1 запрос списка + по запросу на каждый элемент за связанными данными. Лечится JOIN или batch-запросом `WHERE id = ANY($1)` / dataloader.
