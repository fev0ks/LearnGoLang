# Атомарные операции и порядок работы с памятью

Когда несколько goroutines работают с общей памятью, порядка строк в исходном коде недостаточно, чтобы понять, какие значения увидит каждое ядро. На результат одновременно влияют контракт языка Go, преобразования компилятора и модель памяти процессора.

Атомарные операции решают две разные задачи: неделимо изменяют отдельное значение и создают правила порядка и видимости памяти. Эти свойства связаны, но не являются одним и тем же.

## Ментальная модель

Представим, что одна goroutine подготовила новые настройки приложения, а другая должна начать ими пользоваться:

```text
Goroutine A                         Goroutine B

config = newConfig
ready = true            ----->     if ready {
                                       use(config)
                                   }
```

Нам нужны две гарантии:

1. Goroutine B действительно замечает изменение `ready`.
2. Если B увидела `ready == true`, она видит полностью записанный `config`, а не старое или частично обновлённое состояние.

Обычная запись в `ready` не создаёт этих гарантий. Нужна **синхронизация**, которая связывает публикацию данных с их чтением.

Короткая ментальная модель:

> Атомарность отвечает на вопрос «может ли операция быть замечена частично?», а порядок памяти — «какие другие записи гарантированно видны вместе с ней?».

Например, атомарный счётчик решает проблему потерянных инкрементов. А атомарный флаг готовности дополнительно может безопасно опубликовать данные, записанные перед ним.

## Три уровня, которые нельзя смешивать

Между Go-кодом и физической памятью находятся несколько слоёв:

```text
исходный Go-код
       |
       | правила Go Memory Model
       v
компилятор и созданные им инструкции
       |
       | правила модели памяти архитектуры
       v
CPU, буферы записей, кэши и их согласование
       |
       v
значения, наблюдаемые goroutines
```

| Уровень | Что он определяет |
| --- | --- |
| Go Memory Model | Какие результаты разрешены Go-программе и где возникает `happens-before` |
| Компилятор | Какие преобразования допустимы без нарушения контракта Go |
| Модель памяти CPU | В каком порядке ядра могут наблюдать инструкции чтения и записи |
| Микроархитектура | Как конкретный процессор реализует модель через буферы, кэши и протокол их согласования |

Из этого следуют два важных вывода:

- факт о `store buffer` не делает Go-программу с гонкой данных корректной;
- факт, что пример «работает на x86», не создаёт гарантии языка и не запрещает компилятору преобразовать код.

Сначала нужно рассуждать через Go Memory Model. Детали CPU объясняют стоимость и реализацию уже корректных примитивов синхронизации.

## Мотивирующий пример: результат `(0, 0)`

Рассмотрим классический тест порядка записей и чтений:

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var x, y int64
    var r1, r2 int64

    var wg sync.WaitGroup
    wg.Add(2)

    go func() {
        defer wg.Done()
        x = 1
        r1 = y
    }()

    go func() {
        defer wg.Done()
        y = 1
        r2 = x
    }()

    wg.Wait()
    fmt.Println(r1, r2)
}
```

Если представить, что операции двух goroutines входят в один последовательный порядок, легко объяснить три результата:

| Результат | Возможная последовательность |
| --- | --- |
| `(0, 1)` | первая goroutine читает `y` до записи второй |
| `(1, 0)` | вторая goroutine читает `x` до записи первой |
| `(1, 1)` | обе записи становятся наблюдаемыми до обоих чтений |

Для `(0, 0)` требуется, чтобы каждое чтение произошло раньше чужой записи:

```text
read y < write y
read x < write x
```

Но порядок программы требует:

```text
write x < read y
write y < read x
```

Если объединить условия, получается цикл:

```text
write x < read y < write y < read x < write x
```

В едином последовательном порядке такой цикл невозможен.

### Почему этот Go-код всё равно некорректен

В примере есть гонки данных:

- одна goroutine записывает `x`, пока другая читает `x`;
- одна goroutine записывает `y`, пока другая читает `y`;
- эти доступы не связаны синхронизацией.

`WaitGroup` безопасно публикует итоговые `r1` и `r2` для `main`, но не упорядочивает конкурентные обращения к `x` и `y` между двумя рабочими goroutines.

Поэтому возможный `(0, 0)` нельзя объявить только «физикой процессора». На результат могут влиять и компилятор, и CPU. Главное практическое заключение проще: **эта программа нарушает Go Memory Model**.

```go
package main

import (
    "fmt"
    "sync"

func main() {
    const iterations = 100_000
    results := make(map[[2]int64]int)

    for range iterations {

        var r1, r2 int64

        }()

        go func() {
            defer wg.Done()
            y = 1

        }()

        fmt.Printf("%v: %d\n", result, count)
    }

```

Конкретные частоты зависят от процессора, версии Go, компилятора и нагрузки. `(0, 0)` может не встретиться вообще, но отсутствие симптома не означает отсутствие гонки:

```bash
go run -race main.go
```

Детектор гонок должен использоваться для обнаружения нарушения, а не конкретный набор напечатанных результатов.

### Что изменится с `sync/atomic`

Заменим обычные обращения к `x` и `y` атомарными:

```go
var x, y atomic.Int64
var r1, r2 int64

var wg sync.WaitGroup
wg.Add(2)

go func() {
    defer wg.Done()
    x.Store(1)
    r1 = y.Load()
}()

go func() {
    defer wg.Done()
    y.Store(1)
    r2 = x.Load()
}()

wg.Wait()
```

Публичные атомарные операции Go ведут себя так, будто входят в единый последовательно согласованный порядок (`sequentially consistent`, SC). Поэтому `(0, 0)` становится невозможным: тот же цикл порядка нельзя построить в допустимой истории выполнения.

## Буфер записей и `(0, 0)` на уровне CPU

Теперь временно отвлечёмся от некорректной Go-программы и рассмотрим аппаратный litmus test: предполагается, что процессор получил именно две записи и два чтения в указанном порядке.

Современное ядро обычно не ждёт полного завершения coherence protocol после каждой записи. Оно помещает ожидающую запись в **буфер записей** (`store buffer`) и продолжает исполнять инструкции.

```text
Core 0

Store x = 1 ---> store buffer ---> L1 cache/coherence ---> видно Core 1
```

Буфер нужен, потому что получение строки кэша в состоянии, допускающем запись, и инвалидирование чужих копий занимают время. Без буфера конвейер CPU часто простаивал бы в ожидании памяти.

Свою запись ядро может прочитать из буфера до завершения публикации другим ядрам. Это называется **перенаправлением записи в чтение** (`store-to-load forwarding`). Другое ядро ожидающую запись пока не наблюдает.

### Пошаговый сценарий

Начальное состояние:

```text
x = 0
y = 0
```

Далее возможна такая аппаратная история:

```text
1. Core 0 выполняет Store x = 1
   x = 1 остаётся в буфере записей Core 0

2. Core 1 выполняет Store y = 1
   y = 1 остаётся в буфере записей Core 1

3. Core 0 выполняет Load y
   запись y = 1 ещё ожидает в другом ядре, поэтому результат равен 0

4. Core 1 выполняет Load x
   запись x = 1 ещё ожидает в другом ядре, поэтому результат равен 0

5. Обе записи позднее становятся наблюдаемыми через coherence protocol
```

Получается `(0, 0)`. В терминах наблюдаемого порядка более позднее чтение обгоняет более раннюю запись по другому адресу. Это называют **StoreLoad reordering**.

Cache coherence при этом не нарушается. Для каждого отдельного адреса ядра согласуют порядок значений `0 -> 1`, но coherence не обязана создавать единый порядок операций сразу над `x` и `y`.

Подробнее взаимодействие строк кэша разобрано в [Cache coherence и MESI](./03-cache-coherence-and-mesi.md).

## Виды переупорядочивания

Для двух операций над разными адресами обычно рассматривают четыре сочетания:

| Название | Порядок программы | Что может наблюдаться |
| --- | --- | --- |
| `LoadLoad` | `Load A`, затем `Load B` | чтение `B` наблюдается раньше чтения `A` |
| `LoadStore` | `Load A`, затем `Store B` | запись `B` наблюдается раньше чтения `A` |
| `StoreLoad` | `Store A`, затем `Load B` | чтение `B` наблюдается раньше записи `A` |
| `StoreStore` | `Store A`, затем `Store B` | запись `B` наблюдается раньше записи `A` |

Эта таблица описывает наблюдаемый порядок операций с памятью, а не обязательную физическую перестановку инструкций внутри процессора. Один и тот же эффект может возникать из-за буферов, спекулятивного исполнения или других деталей микроархитектуры.

Также это не полный список правил: зависимости по данным, обращения к одному адресу, атомарные инструкции, device memory и специальные типы записей имеют дополнительные ограничения.

## Модели памяти x86, ARM и RISC-V

### x86-64 и TSO

Для обычной кэшируемой памяти x86-64 предоставляет относительно строгую модель **Total Store Order** (`TSO`):

- чтения не меняют наблюдаемый порядок с другими чтениями;
- записи не меняют наблюдаемый порядок с другими записями;
- основное ослабление — более позднее чтение другого адреса может наблюдаться раньше предыдущей записи из-за буфера записей.

Поэтому store-buffering test с `(0, 0)` является классическим примером допустимого `StoreLoad reordering` на x86.

Это упрощённая модель для обычной write-back памяти. Non-temporal instructions, device memory и другие специальные случаи требуют отдельных правил.

### ARM

ARM использует более слабую модель памяти и сохраняет меньше вариантов порядка автоматически. Между независимыми чтениями и записями могут потребоваться acquire/release instructions или явные barriers.

Это не означает, что ARM «хаотично переставляет всё». Архитектура задаёт точные правила для зависимостей, атомарных инструкций и барьеров. Но полагаться на случайные свойства x86 при переносе низкоуровневого кода на ARM нельзя.

Для корректной Go-программы различие скрывают компилятор и стандартные примитивы синхронизации. Программа с гонкой данных остаётся некорректной и на x86, и на ARM.

### RISC-V

Базовая модель RISC-V называется **RISC-V Weak Memory Ordering** (`RVWMO`). Она допускает слабое упорядочивание и предоставляет инструкцию `FENCE`, а расширение `A` — атомарные операции «прочитать — изменить — записать» (`read-modify-write`, RMW).

Отдельное расширение `Ztso` добавляет более строгую TSO-подобную семантику. Поэтому нельзя просто сказать, что RISC-V «строже ARM»: нужно знать, используется базовый RVWMO или дополнительное расширение.

### Сравнение

| Архитектура | Базовая модель | Как задаётся дополнительный порядок |
| --- | --- | --- |
| x86-64 | относительно строгая TSO | `LFENCE`, `SFENCE`, `MFENCE`, инструкции с `LOCK` prefix |
| ARM | weakly ordered | acquire/release instructions, `DMB`, `DSB`, `ISB` по назначению |
| RISC-V | RVWMO | `FENCE`, atomic extension `A`; опционально `Ztso` |

Практическое правило для Go-разработчика не зависит от архитектуры: доступ к общему изменяемому состоянию должен быть связан через `sync`, `sync/atomic`, каналы или другой документированный механизм синхронизации.

## Барьеры памяти

**Барьер памяти** (`memory fence` или `memory barrier`) задаёт порядок между обращениями к памяти до и после него.

Важно различать утверждения:

- барьер **упорядочивает** определённые операции;
- барьер не обязан буквально очищать все кэши;
- барьер сам по себе не превращает составную операцию вроде `counter++` в атомарную.

### x86

Упрощённо роли инструкций выглядят так:

| Инструкция | Основная роль для памяти |
| --- | --- |
| `LFENCE` | упорядочить предыдущие чтения относительно последующих чтений |
| `SFENCE` | упорядочить предыдущие записи относительно последующих записей |
| `MFENCE` | упорядочить предыдущие чтения и записи относительно последующих чтений и записей |

Обычные записи в write-back память x86 и без `SFENCE` сохраняют порядок StoreStore. `SFENCE` особенно важен для специальных weakly ordered stores, например non-temporal writes. Это хороший пример того, почему таблицу барьеров нельзя читать в отрыве от типа памяти и инструкций.

Если на аппаратном уровне поставить `MFENCE` между записью и чтением в обеих последовательностях:

```text
Core 0: Store x = 1; MFENCE; Load y
Core 1: Store y = 1; MFENCE; Load x
```

то `(0, 0)` становится невозможным: каждое чтение должно идти после предыдущей записи в глобально наблюдаемом порядке x86.

Это иллюстрация уровня CPU, а не рекомендация вставлять assembly fences в прикладной Go-код. Компилятор Go выбирает нужные инструкции для `sync/atomic` и примитивов `sync`.

### ARM

На ARM три похожих по названию инструкции решают разные задачи:

| Инструкция | Роль |
| --- | --- |
| `DMB` | упорядочивает указанные обращения к данным |
| `DSB` | дополнительно ожидает завершения указанных операций перед продолжением |
| `ISB` | синхронизирует поток инструкций после изменения состояния, влияющего на их исполнение |

`ISB` не является просто «ещё более сильным барьером данных». Например, он нужен после изменений системных регистров или кода, влияющих на последующее декодирование инструкций.

### RISC-V

Инструкция RISC-V `FENCE` отдельно задаёт набор предыдущих и последующих операций: какие чтения, записи или I/O operations должны наблюдаться до каких других операций.

Именно поэтому фраза «поставить fence» без архитектуры и типа операций недостаточна. Нужно знать, какой порядок требуется и какой контракт предоставляет конкретная инструкция.

## Атомарные операции на уровне CPU

Атомарная операция наблюдается участвующими потоками как неделимая: они не видят промежуточное состояние RMW-операции.

Обычный `counter++` концептуально состоит из трёх шагов:

```assembly
MOV RAX, [counter]    ; прочитать старое значение
ADD RAX, 1            ; вычислить новое значение
MOV [counter], RAX    ; записать результат
```

Два ядра могут одновременно прочитать `10`, оба вычислить `11` и оба записать `11`. Один инкремент потеряется.

Атомарная версия объединяет чтение, изменение и запись в одну неделимую RMW-операцию.

### Атомарность и порядок — разные свойства

| Свойство | Что гарантирует |
| --- | --- |
| Атомарность | операция не наблюдается частично; конкурентные RMW-операции не теряют изменения из-за разрыва операции |
| Порядок памяти | определяет, какие другие чтения и записи можно наблюдать до или после операции |

В языках с relaxed atomics операция может быть атомарной, но не публиковать соседние данные. В Go публичные атомарные операции дают более сильную sequentially consistent семантику.

### `LOCK` prefix на x86

x86 предоставляет RMW-инструкции с `LOCK` prefix:

```assembly
LOCK ADD [counter], 1
LOCK XADD [counter], RAX
LOCK CMPXCHG [value], RBX
```

Операция `XCHG` с операндом в памяти атомарна на x86 и без явно написанного `LOCK` prefix.

На современных процессорах инструкция с `LOCK` prefix над обычной выровненной памятью обычно получает строку кэша в эксклюзивное состояние через протокол согласования кэшей (`cache coherence`). Другие ядра не могут одновременно изменить эту строку.

Из этого возникает цена конкуренции:

```text
Core 0 владеет строкой кэша
        |
        v
Core 1 запрашивает владение
        |
        v
Core 0 инвалидирует копию, Core 1 получает строку
        |
        v
Core 0 снова запрашивает строку ...
```

Чем больше ядер изменяют одно значение, тем чаще строка кэша перемещается между ядрами. Поэтому atomic counter без mutex всё равно может стать узким местом.

Точное время операции нельзя задавать одной универсальной цифрой. Оно зависит от архитектуры, расположения строки кэша, NUMA, конкуренции и соседних данных.

### Ложное совместное использование (false sharing)

Даже разные атомарные переменные могут мешать друг другу, если находятся в одной строке кэша:

```go
type Counters struct {
    requests atomic.Int64
    errors   atomic.Int64
}
```

Если разные ядра часто изменяют `requests` и `errors`, вся общая строка кэша может перемещаться между ними. Логически значения независимы, но аппаратная единица согласования — строка кэша, а не отдельное поле.

Не стоит автоматически добавлять выравнивающие поля (`padding`): сначала проблему подтверждают бенчмарком или аппаратными счётчиками. Выравнивание увеличивает расход памяти и может ухудшить локальность данных.

## Compare-and-Swap

**Compare-and-Swap** (`CAS`) атомарно сравнивает текущее значение с ожидаемым и записывает новое только при совпадении:

```text
CAS(address, expected, new):
    atomically:
        if *address != expected:
            return false

        *address = new
        return true
```

CAS подходит для оптимистичного обновления: сначала вычисляем результат без блокировки, затем проверяем, что состояние никто не изменил.

```go
func atomicMax(dst *atomic.Int64, candidate int64) {
    for {
        current := dst.Load()
        if candidate <= current {
            return
        }

        if dst.CompareAndSwap(current, candidate) {
            return
        }

        // Кто-то изменил dst после Load. Читаем новое состояние и повторяем.
    }
}
```

CAS — важный строительный блок алгоритмов без блокировок (`lock-free`), но не превращает произвольный код в lock-free автоматически.

### Что происходит при конкуренции

```text
G1: Load 10 -> хочет записать 15
G2: Load 10 -> хочет записать 12

G1: CAS(10, 15) -> success
G2: CAS(10, 12) -> fail, потому что текущее значение уже 15
```

Неуспешный CAS требует повторения. При высокой конкуренции goroutine может много раз проигрывать, расходовать CPU и заставлять строку кэша постоянно перемещаться между ядрами.

Lock-free обычно означает прогресс системы в целом: хотя бы одна операция завершится. Это не гарантирует, что каждая конкретная goroutine завершится за ограниченное число шагов — такая более сильная гарантия называется wait-free.

### Проблема ABA

CAS сравнивает значения, а не историю изменений:

```text
G1 читает A

G2 меняет A -> B
G2 меняет B -> A

G1 выполняет CAS(A, C) -> success
```

Для G1 значение выглядит неизменившимся, хотя состояние успело пройти через `B`.

Типичные способы защиты:

- хранить рядом со значением счётчик версии;
- не переиспользовать объект, пока другие потоки могут хранить ссылку;
- применять epoch-based reclamation или hazard pointers в системах с ручным управлением памятью;
- проектировать состояние так, чтобы возвращение к тому же значению было безопасно.

GC Go уменьшает риск классического ABA из-за освобождения и повторного использования объекта, если ссылки хранятся как обычные Go-указатели или `atomic.Pointer`. Но логический ABA значений остаётся возможным, а `unsafe.Pointer`/`uintptr` требуют отдельной осторожности.

## Уровни упорядочивания памяти

В C++, Rust, процессорных ISA и литературе встречаются разные memory orders. Они полезны для понимания реализации, хотя публичный `sync/atomic` Go не позволяет выбирать order для каждой операции.

| Уровень | Основная гарантия |
| --- | --- |
| `relaxed` | атомарность конкретного значения без публикации соседних данных |
| `acquire` | последующие операции не переходят до acquire; наблюдающий load получает опубликованные ранее данные |
| `release` | предыдущие операции не переходят после release; store публикует сделанные до него записи |
| `acq_rel` | сочетание acquire и release для RMW-операции |
| `seq_cst` | все sequentially consistent atomics входят в единый глобальный порядок |

### Acquire и release на примере публикации

В псевдокоде API с явным выбором memory order выглядит так:

```text
Producer:                         Consumer:

data = 42                         if LoadAcquire(ready) {
StoreRelease(ready, true)             use(data)
                                  }
```

Если acquire-load увидел значение от release-store, образуется связь:

```text
data = 42
    sequenced-before
release store ready = true
    synchronized-before
acquire load ready == true
    sequenced-before
use(data)
```

Поэтому consumer гарантированно видит `data == 42`.

Одна acquire-операция без соответствующей публикации не делает произвольные старые записи видимыми. Важно именно то, что acquire-load наблюдает release-store или связанную с ним release sequence.

### Последовательная согласованность (sequential consistency)

Sequential consistency (`SC`) добавляет единый порядок всех SC atomic operations, согласованный с порядком операций каждой goroutine.

Это контракт уровня языка, а не название одной CPU-инструкции. На одной архитектуре SC store может компилироваться в `XCHG`, на другой — в store-release вместе с barrier или другую допустимую последовательность.

Фраза «`MFENCE` и есть seq_cst» поэтому неверна: `MFENCE` — инструмент x86, а SC — свойство всей истории атомарных операций программы.

## `sync/atomic` в Go

Публичный пакет `sync/atomic` предоставляет sequentially consistent atomic operations. Если эффект атомарной операции A наблюдается операцией B, A находится `synchronized-before` B.

### Типизированный API

Начиная с Go 1.19 доступны типизированные обёртки:

```go
var requests atomic.Uint64
var enabled atomic.Bool

requests.Add(1)
enabled.Store(true)

count := requests.Load()
isEnabled := enabled.Load()
```

Основные типы:

| Тип | Типичная задача |
| --- | --- |
| `atomic.Bool` | флаг готовности или включения функции |
| `atomic.Int32`, `atomic.Int64` | счётчик или числовое состояние |
| `atomic.Uint32`, `atomic.Uint64`, `atomic.Uintptr` | счётчики и битовые маски |
| `atomic.Pointer[T]` | безопасная публикация указателя на неизменяемый снимок данных |
| `atomic.Value` | публикация значения, когда удобен динамический тип |

Старый функциональный API (`atomic.AddInt64`, `atomic.LoadInt64`) остаётся рабочим. Типизированные значения удобнее и самостоятельно обеспечивают необходимое выравнивание своих полей.

### Безопасная публикация конфигурации

```go
type Config struct {
    Timeout time.Duration
    Region  string
}

var current atomic.Pointer[Config]

func UpdateConfig(timeout time.Duration, region string) {
    next := &Config{
        Timeout: timeout,
        Region:  region,
    }

    current.Store(next)
}

func LoadConfig() *Config {
    return current.Load()
}
```

После `Store` читатели получают целиком опубликованный снимок. Но безопасность указателя не делает объект автоматически потокобезопасным: после публикации `Config` лучше не изменять. Для обновления создаётся новый снимок и атомарно заменяется указатель.

### Что atomic не решает

Отдельные атомарные поля не создают одну транзакцию:

```go
type Balance struct {
    available atomic.Int64
    reserved  atomic.Int64
}
```

Читатель может увидеть новый `available` и старый `reserved`. Если между полями есть инвариант, обычно нужен `Mutex` или неизменяемый снимок, опубликованный одним `atomic.Pointer`.

Также нельзя смешивать атомарный и обычный доступ к одной переменной:

```go
var counter atomic.Int64

counter.Add(1) // atomic

// Нельзя обходить atomic API и читать его внутреннее значение обычной загрузкой.
```

Все конкурентные обращения к одному атомарному состоянию должны проходить через его atomic API.

<details>
<summary>Как операции Go 1.26 выглядят на amd64</summary>

В текущей реализации Go 1.26 для amd64 типичные соответствия выглядят примерно так:

| Операция Go | Одна из используемых инструкций amd64 |
| --- | --- |
| `Load` | обычный `MOV` |
| `Store` | `XCHG` с операндом в памяти |
| `Add` | `LOCK XADD` |
| `CompareAndSwap` | `LOCK CMPXCHG` |

Это деталь реализации, а не публичный контракт `sync/atomic`. Компилятор и runtime могут изменить соответствие в другой версии, а ARM64 и RISC-V используют другие инструкции. Обычный `MOV` для `Load` на amd64 не ослабляет контракт Go: нужная семантика получается из всей последовательности выбранных инструкций и правил компилятора.

Проверять текущую реализацию нужно в [`internal/runtime/atomic`](https://go.dev/src/internal/runtime/atomic/), а гарантии программы — в [Go Memory Model](https://go.dev/ref/mem).

## Как `sync.Mutex` использует атомарные операции

`sync.Mutex` не является альтернативой atomics на уровне реализации: его быстрый путь сам использует атомарные операции.

Упрощённая схема текущей реализации:

```go
type Mutex struct {
    state int32
    sema  uint32
}

func (m *Mutex) Lock() {
    if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
        return
    }

    m.lockSlow()
}

func (m *Mutex) Unlock() {
    newState := atomic.AddInt32(&m.state, -mutexLocked)
    if newState != 0 {
        m.unlockSlow(newState)
    }
}
```

Это учебное сокращение, а не код для собственной реализации mutex.

### Быстрый путь

Если mutex свободен, `Lock` захватывает его одним CAS. Этот путь обычно:

- не создаёт allocation;
- не паркует goroutine;
- не делает отдельный системный вызов.

### Медленный путь

При конкуренции реализация учитывает ожидающие goroutines и режим предотвращения голодания (`starvation`), может недолго активно повторять проверку (`spinning`), а затем припарковать goroutine через семафор runtime.

Цена определяется не названием примитива, а характером нагрузки:

- короткая критическая секция и редкая конкуренция обычно дёшевы;
- горячий общий mutex сериализует goroutines;
- замена mutex на CAS-loop может лишь перенести ожидание в активные повторы CAS и усилить перемещение строки кэша между ядрами.

В Go 1.26 основная реализация пользовательского `sync.Mutex` находится в [`internal/sync/mutex.go`](https://go.dev/src/internal/sync/mutex.go). Детальный разбор примитивов находится в [Sync primitives](../../01-go-core/concurrency-and-performance/03-sync-primitives.md).

## Go Memory Model

Go Memory Model определяет, когда чтение в одной goroutine гарантированно наблюдает запись из другой.

Главное практическое правило:

> Если несколько goroutines обращаются к одной памяти и хотя бы одна пишет, доступы нужно связать документированным механизмом синхронизации.

### Программа без гонок и DRF-SC

Для программы без гонок данных Go гарантирует **DRF-SC** (`data-race-free sequential consistency`): результат можно объяснить некоторым последовательным чередованием операций goroutines.

Именно поэтому сначала устраняют гонки, а затем рассуждают о допустимом порядке.

### Что такое гонка данных

Гонка данных возникает, когда:

1. две goroutines обращаются к одной области памяти конкурентно;
2. хотя бы один доступ является записью;
3. доступы не являются оба атомарными и не упорядочены через `happens-before`.

Программа с гонкой ошибочна и теряет гарантию DRF-SC. Но формулировка «полностью undefined behavior как в C++» для Go неточна: спецификация Go накладывает некоторые ограничения даже на исполнения с гонкой. Полагаться на эти ограничения для корректности нельзя, особенно для многословных значений вроде interface, string или slice header.

### `Happens-before`

`Happens-before` строится из двух видов порядка:

- **sequenced-before** — порядок операций внутри одной goroutine;
- **synchronized-before** — связь между goroutines, созданная примитивом синхронизации.

Транзитивное объединение этих связей даёт `happens-before`.

Основные примеры:

| Событие A | Событие B | Есть связь |
| --- | --- | --- |
| выполнение `go f()` | начало `f` | запуск synchronized-before начала goroutine |
| завершение goroutine | произвольное чтение в другой goroutine | само по себе связи нет |
| отправка в канал | завершение соответствующего чтения | send synchronized-before receive |
| `close(ch)` | чтение, увидевшее закрытый канал | close synchronized-before receive |
| `Mutex.Unlock` | более поздний успешный `Mutex.Lock` | `Unlock` synchronized-before `Lock` |
| `WaitGroup.Done` | `Wait`, который он разблокировал | done synchronized-before return from wait |
| atomic A | atomic B, наблюдающая эффект A | A synchronized-before B |

### Безопасная публикация через atomic flag

```go
var data int
var ready atomic.Bool

// Publisher
data = 42
ready.Store(true)

// Reader
if ready.Load() {
    fmt.Println(data) // гарантированно 42, если Load увидел true от Store
}
```

Цепочка порядка:

```text
data = 42
    sequenced-before
ready.Store(true)
    synchronized-before
ready.Load() == true
    sequenced-before
read data
```

Если publisher продолжает изменять `data` после публикации без новой синхронизации, atomic flag уже не защищает эти последующие записи.

### Детектор гонок

Race detector (детектор гонок) инструментирует обращения к памяти и отслеживает отсутствие необходимого порядка во время конкретного запуска:

```bash
go test -race ./...
go run -race ./cmd/service
```

Он является динамическим инструментом:

- находит гонку только на выполненном пути;
- не доказывает отсутствие всех гонок после одного зелёного запуска;
- замедляет программу и увеличивает потребление памяти;
- не обнаруживает логические race conditions, если все обращения к памяти формально синхронизированы.

Поэтому `-race` запускают на модульных и интеграционных тестах с реалистичными конкурентными сценариями, а не используют как замену анализу `happens-before`.

## Что выбрать: atomic, mutex или канал

| Задача | Обычно подходящий инструмент | Почему |
| --- | --- | --- |
| один независимый счётчик | `atomic.Int64` | операция естественно выражается одним `Add` |
| флаг или неизменяемый снимок | `atomic.Bool`, `atomic.Pointer[T]` | одна точка публикации, частые чтения |
| несколько связанных полей | `sync.Mutex` | инвариант защищается одной критической секцией |
| «проверить, затем изменить» (`check-then-act`) над сложным состоянием | `sync.Mutex` | проверка и изменение остаются одной операцией уровня приложения |
| передача владения или результата | канал | явно моделирует поток передачи данных |
| ожидание события с блокировкой | канал, `sync.Cond`, `WaitGroup` | goroutine можно припарковать вместо активного опроса |

Atomic стоит выбирать не потому, что «mutex медленный», а когда состояние действительно выражается одной атомарной переменной и инвариант легко доказать.

Пример, где mutex понятнее CAS-loop:

```go
type Account struct {
    mu      sync.Mutex
    balance int64
}

func (a *Account) Withdraw(amount int64) bool {
    a.mu.Lock()
    defer a.mu.Unlock()

    if a.balance < amount {
        return false
    }

    a.balance -= amount
    return true
}
```

Здесь нужно атомарно на уровне бизнес-операции проверить баланс и изменить его. Отдельный atomic load плюс atomic add не предотвращает вмешательство другой goroutine между шагами.

## Типичные ошибки

### 1. Флаг готовности через обычный `bool`

```go
var ready bool

go func() {
    prepare()
    ready = true
}()

for !ready {
}
```

Это гонка данных. Цикл может не увидеть запись, а кроме того он бесполезно занимает CPU.

Для простого сигнала обычно лучше канал. `atomic.Bool` подходит, если действительно нужен часто читаемый lock-free флаг и активные повторы ограничены внешним протоколом.

### 2. Атомарный указатель на изменяемый объект

```go
cfg := current.Load()
cfg.Timeout = time.Second // небезопасно при конкурентных чтениях и записях
```

Atomic гарантирует публикацию указателя, но не сериализует последующие изменения объекта. Используют неизменяемые снимки или отдельный mutex внутри объекта.

### 3. Независимые atomics для общего инварианта

```go
available.Store(100)
reserved.Store(20)
```

Другой поток может прочитать значения между двумя stores. Если пара должна изменяться согласованно, используют mutex или публикуют неизменяемую структуру одним атомарным указателем.

### 4. Побочный эффект внутри CAS-loop

```go
for {
    old := state.Load()
    chargeCard() // ошибка: CAS может не пройти, цикл повторится
    if state.CompareAndSwap(old, old+1) {
        break
    }
}
```

CAS-loop может повторяться, поэтому вычисление до успешного CAS должно быть безопасно для повторного выполнения. Внешний побочный эффект выполняют после успешного изменения либо защищают другим протоколом.

### 5. Busy-wait без необходимости

```go
for !ready.Load() {
}
```

Даже корректное atomic чтение может постоянно занимать CPU и заставлять строку кэша перемещаться между ядрами. Если ожидание может быть долгим, канал, `WaitGroup` или `sync.Cond` обычно лучше.

### 6. Предположение «работает на x86 — значит корректно»

Модель x86 не заменяет Go Memory Model. Компилятор участвует в преобразовании кода, а программа с гонкой ошибочна на любой архитектуре.

### 7. Сравнение производительности без модели нагрузки

Бенчмарк без конкуренции не отвечает на вопрос о горячей строке кэша, а бенчмарк только с максимальной конкуренцией может не соответствовать реальной структуре обращений.

Сравнивают как минимум:

- разное число goroutines;
- соотношение чтений и записей;
- размер критической секции;
- отсутствие и наличие конкуренции;
- поведение на целевой архитектуре.

## Практическая диагностика

### Поиск гонок

```bash
go test -race ./...
go test -race -count=10 ./path/to/package
```

Повторение повышает шанс выполнить редкий конкурентный путь, но само по себе не является доказательством отсутствия гонок.

### Бенчмарк атомарных операций и mutex

```bash
go test -bench=. -benchmem -cpu=1,2,4,8,16 ./path/to/package
```

Параметр `-cpu` помогает увидеть, как решение ведёт себя при росте параллелизма. Результат нужно интерпретировать вместе с характером нагрузки: один локальный счётчик и один общий горячий счётчик — разные задачи.

### Профиль конкуренции за mutex

```bash
go test \
  -run='^$' \
  -bench=BenchmarkWorkload \
  -mutexprofile=mutex.out \
  ./path/to/package

go tool pprof mutex.out
```

Профиль mutex показывает места конкуренции за блокировки. Он не говорит автоматически, что mutex нужно заменить на atomic: сначала проверяют длительность критической секции, гранулярность блокировки и структуру доступа.

### Проверка скомпилированных инструкций

Для изучения деталей реализации можно посмотреть ассемблерный код:

```bash
go build -gcflags='-S' ./path/to/package
go tool objdump -s 'package\.Function' ./binary
```

Ассемблерный код объясняет соответствие для конкретной версии Go, `GOARCH` и флагов компилятора. Гарантии программы всё равно берутся из Go Memory Model, а не из одной получившейся инструкции.

## Interview-ready answer

**1. Чем атомарность отличается от порядка работы с памятью?**

Атомарность не позволяет наблюдать промежуточное состояние операции. Порядок работы с памятью определяет, какие другие чтения и записи гарантированно наблюдаются до или после неё. Операция может быть атомарной, но иметь relaxed ordering; публичные атомарные операции Go дают SC ordering.

**2. Почему в тесте с буферами записей возможен результат `(0, 0)`?**

Каждое ядро может оставить свою запись в store buffer и выполнить последующее чтение другого адреса до того, как чужая запись стала наблюдаемой. На x86 это классическое переупорядочивание StoreLoad. Но Go-пример с обычными переменными содержит гонку данных и не должен объясняться только железом.

**3. Чем x86 отличается от ARM с точки зрения порядка памяти?**

x86 TSO сохраняет больше порядка автоматически и для обычной памяти в основном допускает StoreLoad relaxation. ARM использует более слабую модель и чаще требует acquire/release instructions или барьеры. Корректный Go-код с `sync`/`sync/atomic` остаётся переносимым между ними.

**4. Что гарантируют acquire и release?**

Release-store публикует операции, выполненные до него. Если acquire-load наблюдает эту запись, следующие операции читателя видят опубликованные данные. Важна связанная пара публикации и наблюдения, а не acquire или release по отдельности.

**5. Что гарантирует `sync/atomic` в Go?**

Публичные атомарные операции Go ведут себя так, будто входят в единый SC order. Если операция B наблюдает эффект A, A находится synchronized-before B. Это позволяет, например, безопасно публиковать неизменяемый снимок через `atomic.Pointer`.

**6. Когда atomic лучше mutex?**

Когда состояние естественно помещается в одно независимое значение: счётчик, флаг, битовая маска или указатель на неизменяемый снимок. Если нужно согласованно менять несколько полей или выполнять «проверить, затем изменить», mutex обычно проще и надёжнее.

**7. Что такое CAS-loop и чем он опасен?**

CAS-loop читает состояние, вычисляет новое значение и пытается записать его, только если состояние не изменилось. При неудаче цикл повторяется. При высокой конкуренции возможны многочисленные повторы и голодание отдельной goroutine; побочные эффекты внутри повторяемой части опасны.

**8. Что такое проблема ABA?**

Значение меняется `A -> B -> A`, и CAS по одному значению не замечает историю. Используют метки версии, безопасное управление временем жизни объекта или проектируют состояние так, чтобы возврат к `A` не нарушал инвариант.

**9. Доказывает ли зелёный запуск `go test -race` отсутствие гонок?**

Нет. Детектор гонок анализирует только выполненные пути. Он очень полезен, но требует хорошего покрытия конкурентных сценариев и не заменяет анализ `happens-before`.
