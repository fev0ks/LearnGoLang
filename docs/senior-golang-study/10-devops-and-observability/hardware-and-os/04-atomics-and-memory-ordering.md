Этот файл объясняет аппаратную сторону атомарных операций: как ядро процессора
получает исключительное право на строку кэша, почему операция «прочитать,
изменить, записать» (`read-modify-write`, RMW) остаётся неделимой и откуда
берётся её цена. Прикладной API Go вынесен в
[Sync primitives](../../01-go-core/concurrency-and-performance/03-sync-primitives.md),
а формальные гарантии языка — в [Go Memory Model](../../01-go-core/concurrency-and-performance/01-memory-model.md).

Здесь и далее **ядро** означает ядро процессора (`core`), а не ядро операционной
системы.

## Что здесь нужно для собеседования

Статья объясняет механизмы, а не набор мнемоник. Названия конкретных инструкций
запоминать не нужно — важны пять идей:

1. `counter++` теряет обновления, потому что состоит из трёх шагов, а атомарная
   RMW-операция делает их одним.
2. Неделимость обеспечивает не блокировка шины памяти, а исключительное владение
   строкой кэша плюс контракт атомарной инструкции.
3. Атомарность, согласованность кэшей и порядок памяти — три разных свойства,
   и ни одно не заменяет остальные.
4. Из-за буфера записей даже на x86 в тесте с двумя переменными наблюдается
   результат `(0, 0)` — отсюда и нужда в барьерах и acquire/release.
5. Цена атомарной операции определяется не самой инструкцией, а тем, где сейчас
   находится строка кэша и сколько ядер за неё борются.

Разбор отдельных машинных инструкций x86, ARM64 и RISC-V вынесен в
[справочник по инструкциям](./04a-atomics-hardware-reference.md). Он нужен, когда
приходится читать ассемблер, и не требуется для понимания механизмов.

Короткие ответы на частые вопросы собраны в разделе
[Interview-ready answer](#interview-ready-answer).

## Ментальная модель

Пусть два ядра одновременно увеличивают один счётчик. Обычная запись в память требует от ядра получить право изменять соответствующую строку кэша, но сама последовательность «прочитать — вычислить — записать» не становится от этого одной операцией.

Атомарная read-modify-write операция (`RMW`) добавляет важную гарантию:

> Между чтением старого значения и публикацией нового другое ядро не может успешно изменить тот же атомарный объект.

Упрощённая аппаратная картина выглядит так:

```text
Core 0: хочет атомарно увеличить counter
        |
        | 1. запрашивает строку кэша для записи
        v
coherence protocol:
инвалидирует копии этой строки у других ядер
        |
        | 2. Core 0 получает исключительное владение
        v
Core 0: неделимо читает counter, прибавляет 1 и записывает результат
        |
        | 3. строка остаётся в кэше Core 0 в изменённом состоянии
        v
Core 1: при следующем доступе получает уже новое значение
```

Здесь нет программного mutex и обычно нет блокировки всей шины памяти. Неделимость обеспечивается совместной работой:

- инструкции процессора с атомарным контрактом;
- протокола согласования кэшей (`cache coherence`);
- механизма, который не разрешает другой конфликтующей операции вклиниться в RMW;
- правил порядка памяти конкретной архитектуры.

Ядро получает исключительное право изменять строку через coherence-протокол. Затем механизм атомарной инструкции удерживает конфликтующие RMW в согласованном порядке, пока текущее чтение старого значения и запись нового не завершатся как одна операция.

## Атомарность, согласованность кэшей и порядок памяти

Эти три свойства отвечают на разные вопросы.

| Свойство | Вопрос | Пример гарантии |
| --- | --- | --- |
| Атомарность | Можно ли увидеть операцию частично или вклиниться внутрь RMW? | два атомарных инкремента не превращаются в один |
| Согласованность кэшей | Согласны ли ядра с порядком значений одного адреса? | если для `x` наблюдается `0 -> 1`, ядро не должно позднее вернуться к старому `0` без новой записи |
| Порядок памяти | Как соотносятся операции над разными адресами? | увидев флаг, видит ли читатель данные, записанные до флага |

Согласованность кэшей обычно работает на уровне **строки кэша**, например 64 байт на многих современных CPU. Атомарный объект может занимать 8 байт, но право на запись и сообщения между ядрами относятся ко всей строке.

Отсюда следуют два вывода:

1. Атомарность одного `counter` не создаёт транзакцию над соседними переменными.
2. Даже разные переменные могут мешать друг другу, если находятся в одной строке кэша.

## Почему обычный `counter++` теряет обновления

На уровне исходного кода `counter++` выглядит одной операцией. На уровне инструкций это логически три шага:

```assembly
MOV RAX, [counter]    ; прочитать
ADD RAX, 1            ; вычислить
MOV [counter], RAX    ; записать
```

Начальное значение равно `10`:

```text
Core 0                              Core 1

read counter -> 10
                                    read counter -> 10
compute 10 + 1 -> 11
                                    compute 10 + 1 -> 11
write counter = 11
                                    write counter = 11
```

Оба обычных store по отдельности могут быть физически неделимыми, но вся последовательность из трёх шагов неделимой не является. Итог равен `11`, хотя выполнено два инкремента.

Атомарный `fetch-add` должен допустить один из двух порядков:

```text
вариант A: Core 0 меняет 10 -> 11, затем Core 1 меняет 11 -> 12
вариант B: Core 1 меняет 10 -> 11, затем Core 0 меняет 11 -> 12
```

Итог в обоих случаях равен `12`.

## Как CPU выполняет атомарную RMW-операцию

Рассмотрим выровненный атомарный `fetch-add` над обычной кэшируемой памятью. Конкретные названия состояний и сообщений зависят от протокола, но причинно-следственная последовательность примерно одинакова.

### Шаг 1. Ядро декодирует атомарную инструкцию

Процессор видит не просто обычные load и store, а инструкцию с атомарной семантикой:

```text
atomic fetch-add [counter], 1
```

Архитектура обещает, что другие агенты памяти наблюдают эту операцию как одну RMW, а не как независимые чтение и запись.

### Шаг 2. Адрес переводится в физический и проверяется

Перед доступом участвуют обычные механизмы памяти:

- TLB переводит виртуальный адрес в физический;
- процессор определяет тип памяти: обычная кэшируемая, некэшируемая или device memory;
- проверяются размер и выравнивание операнда;
- определяется строка кэша, содержащая адрес.

Выравнивание важно. Если атомарный объект пересекает границу строки кэша или страницы, одна строка уже не может быть единицей владения для всей операции. На одних архитектурах такой доступ запрещён, на других поддерживается дорогим специальным механизмом.

### Шаг 3. Ядро запрашивает строку для записи

Если строка отсутствует в локальном кэше или находится в разделяемом состоянии, ядру нужно право записи. Оно отправляет запрос наподобие `Read For Ownership` (`RFO`):

```text
Core 0                    Coherence fabric                   Core 1

RFO line(counter)  -----> directory / snoop  -------------> есть копия?
                                                         да, инвалидировать
                    <----- подтверждения invalidation -----
```

Другие ядра:

- инвалидируют свои разделяемые копии;
- если у кого-то есть изменённая версия, передают актуальные данные;
- подтверждают, что больше не могут записывать через старую копию.

Пока подтверждения не собраны, Core 0 ещё не получил исключительное право на изменение строки.

### Шаг 4. Ядро получает исключительное владение

После согласования у Core 0 появляется единственная копия строки, через которую разрешена запись. В терминах MESI-подобной модели это состояние `Modified` или переход к нему.

Важно: такое владение нужно и обычному store. Само по себе оно ещё не превращает последовательность load + add + store в атомарную. Дополнительная гарантия атомарной инструкции состоит в том, что её чтение и запись образуют одну архитектурную RMW-операцию.

### Шаг 5. RMW выполняется без конфликтующего вклинивания

Ядро:

1. получает текущее значение `counter`;
2. вычисляет новое;
3. фиксирует новую версию в строке кэша;
4. возвращает требуемый результат инструкции, например старое значение для `fetch-add`.

Пока атомарная операция не достигла точки, определённой архитектурой как её выполнение, другое ядро не может успешно завершить конфликтующую RMW над тем же объектом.

Это не обязательно означает, что арифметический блок физически удерживает «замок» много тактов. Реализация может использовать внутренние повторы, очереди запросов или специальный блок в подсистеме кэша. Публичная гарантия ISA одна: операция наблюдается атомарно.

### Шаг 6. Новое значение становится доступно другим ядрам

Изменённая строка может остаться в L1-кэше Core 0 и не записываться немедленно в оперативную память. Это не нарушает видимость:

- coherence-протокол знает владельца актуальной версии;
- запрос Core 1 будет обслужен владельцем или через общий уровень кэша;
- запись в DRAM может произойти существенно позже.

Поэтому «сделать значение видимым» не означает «сбросить L1 в RAM». Для согласованной памяти достаточно, что система может доставить читателю актуальную версию по правилам coherence.

### Что происходит, если два ядра начинают одновременно

```text
Core 0: RFO line(counter) ----\
                               > coherence выбирает порядок владения
Core 1: RFO line(counter) ----/
```

Один запрос побеждает первым. Допустим, это Core 0:

```text
1. Core 0 получает строку и меняет 10 -> 11.
2. Запрос Core 1 ждёт или повторяется.
3. Core 1 получает уже обновлённую строку.
4. Core 1 меняет 11 -> 12.
```

Coherence сериализует конфликтующие права на запись, а атомарная инструкция не даёт разделить одну RMW на независимо наблюдаемые части.

## Два способа сделать RMW неделимой

Архитектуры приходят к одному результату двумя разными путями. Понимать стоит
именно эту развилку, а не конкретные мнемоники инструкций.

**1. Одна инструкция с атомарным контрактом.** Процессор получает команду вида
«прибавь к значению по этому адресу единицу неделимо» и сам обеспечивает, что
конфликтующая операция не вклинится внутрь. Так работают locked-инструкции x86,
расширение LSE на ARM64 и семейство AMO на RISC-V.

**2. Резервирующее чтение плюс условная запись.** Ядро читает значение и
одновременно ставит на его область **резервирование** (`reservation`). Дальше
новое значение вычисляется обычными инструкциями. Затем выполняется условная
запись: она проходит, только если резервирование не нарушено.

```text
прочитать значение и поставить резервирование
        |
        v
вычислить новое значение обычными инструкциями
        |
        v
условная запись
        |
        +-- резервирование цело     -> запись прошла, RMW завершилась
        |
        +-- резервирование нарушено -> запись НЕ прошла, повторить цикл
```

Так устроены `LDXR`/`STXR` на ARM64 и `LR`/`SC` на RISC-V.

Ключевой момент второго способа: между чтением и записью другое ядро физически
**может** изменить память. Неделимость достигается не запретом, а тем, что в
этом случае условная запись просто не выполняется — наружу видна только
успешная RMW.

Резервирование может сорваться и по другим разрешённым архитектурой причинам, а
не только из-за конкурента. Поэтому цикл обязан обрабатывать неуспешную запись
повтором в любом случае, даже если конкурента в логике программы не видно.

Один и тот же контракт языка компилируется в разные последовательности на разных
архитектурах. Отсюда практическое правило: корректность доказывают через модель
памяти языка, а не через ассемблер одной платформы.

Конкретные инструкции всех трёх архитектур, включая случаи, когда x86 вынужден
блокировать шину памяти вместо обычного пути через кэш, — в
[справочнике по инструкциям](./04a-atomics-hardware-reference.md).

## Обычные атомарные load и store

Не каждая атомарная операция является RMW.

| Операция | Читает старое | Пишет новое | Нужна неделимая связка read + write |
| --- | ---: | ---: | ---: |
| atomic load | да | нет | нет |
| atomic store | нет | да | нет |
| exchange | да | да | да |
| fetch-add | да | да | да |
| compare-and-swap | да | иногда | да |

Выровненный load или store поддерживаемого машинного размера часто выполняется обычной инструкцией загрузки или записи. Атомарность означает, что читатель не увидит смесь частей старого и нового значения.

Но из этого нельзя заключать, что:

- любой обычный доступ в исходном языке разрешено смешивать с atomic API;
- load или store автоматически имеет нужный memory order;
- доступ любого размера атомарен;
- невыровненный или пересекающий cache line доступ имеет те же свойства.

Язык и ISA отдельно задают:

1. какие размеры и выравнивания поддерживаются;
2. является ли доступ атомарным;
3. какой порядок памяти он создаёт;
4. что происходит при неподдерживаемом адресе.

## Store buffer и наблюдаемый порядок

Атомарность одной операции не устраняет необходимость в модели памяти. Чтобы увидеть проблему, рассмотрим аппаратный litmus test над двумя разными адресами:

```text
Начально: x = 0, y = 0

Core 0: Store x = 1        Core 1: Store y = 1
        Load y -> r1                Load x -> r2
```

Современное ядро обычно не ждёт полного завершения coherence protocol после каждого store. Оно помещает ожидающую запись в **буфер записей** (`store buffer`) и продолжает исполнение:

```text
Core 0

Store x = 1 -> store buffer -> L1/coherence -> доступно Core 1
```

Буфер скрывает задержку получения строки для записи и инвалидирования чужих копий.

### Как получается `(0, 0)`

```text
1. Core 0 помещает x = 1 в свой store buffer.
2. Core 1 помещает y = 1 в свой store buffer.
3. Core 0 читает y, пока запись Core 1 ещё не стала доступна ему: r1 = 0.
4. Core 1 читает x, пока запись Core 0 ещё не стала доступна ему: r2 = 0.
5. Позднее обе записи распространяются через coherence protocol.
```

Результат:

```text
r1 = 0
r2 = 0
```

Cache coherence не нарушается. Для каждого отдельного адреса ядра согласуют переход `0 -> 1`. Но coherence одного адреса не обязана создавать общий последовательный порядок операций сразу над `x` и `y`.

В наблюдаемом порядке более поздний load обогнал более ранний store по другому адресу. Это называют `StoreLoad reordering`.

### Своя запись и store-to-load forwarding

Если то же ядро читает адрес, для которого у него уже есть запись в store buffer, оно может получить собственное новое значение напрямую из буфера:

```text
Store x = 1
Load x -> 1  // forwarding из своего store buffer
```

Другое ядро в тот же момент ещё может видеть старое `x = 0`. Это не означает, что одновременно существуют два допустимых глобальных значения без правил: coherence и модель памяти определяют, как версии становятся наблюдаемыми.

## Модели памяти архитектур

Модель памяти архитектуры задаёт не расположение операций в исходном коде, а разрешённые наблюдения других ядер.

### Четыре категории переупорядочивания

Для операций над разными адресами используют такую классификацию:

| Название | Порядок программы | Какой эффект может наблюдаться |
| --- | --- | --- |
| `LoadLoad` | `Load A`, затем `Load B` | результат чтения `B` доступен раньше результата `A` |
| `LoadStore` | `Load A`, затем `Store B` | запись `B` наблюдается раньше завершения чтения `A` |
| `StoreLoad` | `Store A`, затем `Load B` | чтение `B` наблюдается раньше записи `A` |
| `StoreStore` | `Store A`, затем `Store B` | запись `B` наблюдается раньше записи `A` |

Это наблюдаемый порядок, а не обязательная физическая перестановка инструкций. Эффект могут создавать store buffer, очереди загрузок, спекулятивное исполнение и другие детали.

### Насколько разные архитектуры переупорядочивают

| Архитектура | Насколько строгая модель | Что из этого следует |
| --- | --- | --- |
| x86-64 | относительно строгая `Total Store Order` (`TSO`): load не переставляются с другими load, store с другими store | единственное заметное ослабление — более поздний load другого адреса может наблюдаться раньше предыдущего store. Отсюда и `(0, 0)` в тесте выше |
| ARM | заметно слабее: для независимых обращений сохраняется меньше порядка | алгоритм, случайно работающий за счёт x86 TSO, может сломаться, и переносить его без анализа нельзя |
| RISC-V | базовая модель `RVWMO` тоже слабая, порядок добавляется явно | поведение зависит от используемых расширений; есть опциональное `Ztso` с более строгими правилами |

Ни ARM, ни RISC-V не «переставляют всё случайно»: обе архитектуры точно
определяют зависимости, типы памяти и семантику атомарных инструкций. Но
практический вывод от этого не меняется: **проверка «работает на моём x86» не
является доказательством корректности**. Корректность доказывают через модель
памяти языка.

Точные правила каждой архитектуры — в
[справочнике по инструкциям](./04a-atomics-hardware-reference.md).

## Барьеры памяти

Барьер памяти (`memory barrier`, `memory fence`) ограничивает наблюдаемый порядок операций до и после него.

Барьер:

- не обязан очищать все кэши;
- не обязан немедленно записывать данные в DRAM;
- не делает составной `counter++` атомарным;
- имеет смысл только вместе с определением, какие операции и какую область он упорядочивает.

### Как это выглядит на конкретных архитектурах

У каждой архитектуры свой набор барьеров: на x86 это `LFENCE`, `SFENCE` и
`MFENCE`, на ARM — `DMB`, `DSB` и `ISB`, на RISC-V — `FENCE` с явным указанием
упорядочиваемых классов операций. Они не взаимозаменяемы и решают разные задачи;
таблицы с ролью каждой инструкции собраны в
[справочнике по инструкциям](./04a-atomics-hardware-reference.md).

Для понимания достаточно результата на примере store-buffering test:

```text
Core 0: Store x = 1; барьер; Load y
Core 1: Store y = 1; барьер; Load x
```

Барьер между store и последующим load не позволяет этому load обогнать запись.
Поэтому результат `(0, 0)` здесь становится невозможным.

---

## Публикация через release/acquire

Барьеры расставляют не вручную. В языках их прячут за парой операций:
**release-store публикует** сделанные до него записи, а **acquire-load,
увидевший это значение, наблюдает** их все. Это и есть основной способ передать
данные между потоками.

Псевдокод языка с явным порядком памяти:

```text
Producer:                         Consumer:

data = 42                         if LoadAcquire(ready) {
StoreRelease(ready, true)             use(data)
                                  }
```

Если acquire-load увидел значение от release-store:

```text
data = 42
    before
release store ready = true
    synchronizes with
acquire load ready == true
    before
use(data)
```

Читатель видит опубликованное `data == 42`.

Acquire сам по себе не «подтягивает всю память». Нужна соответствующая release-публикация, эффект которой наблюдает acquire.

### Для Go этих уровней нет

В C++ и Rust порядок памяти выбирают явно: `relaxed`, `acquire`, `release`,
`acq_rel`, `seq_cst`. В Go такого выбора нет — все публичные операции
`sync/atomic` ведут себя так, будто входят в единый последовательный порядок.

Поэтому знать надо не таблицу уровней, а саму идею публикации: данные становятся
видны читателю не «сами по себе», а через пару связанных операций. В Go эту роль
играют канал, mutex или атомарная запись с последующим атомарным чтением.

Полная таблица уровней и правила, по которым компилятор отображает их на
инструкции конкретных архитектур, — в
[справочнике по инструкциям](./04a-atomics-hardware-reference.md).

## CAS на аппаратном уровне

Compare-and-Swap (`CAS`) получает три значения:

```text
address  — адрес атомарного объекта
expected — значение, которое вызывающий ожидает увидеть
desired  — значение, которое нужно записать при совпадении
```

Внутри одной атомарной операции процессор читает текущее значение, сравнивает его с `expected` и при совпадении записывает `desired`:

```text
current = atomic_load(address)

if current == expected:
    atomic_store(address, desired)
    return success, current

return failure, current
```

Возвращённый `current` нужен вызывающему, чтобы понять, с каким значением произошло сравнение. API языка может вернуть только `bool` или одновременно статус и фактическое значение — это уже контракт конкретного языка.

### Один CAS на примере двух ядер

```text
Начально: value = 10

Core 0: CAS(value, expected=10, desired=11)
Core 1: CAS(value, expected=10, desired=20)
```

Оба ядра могут начать операцию почти одновременно, но coherence-протокол и атомарный механизм выбирают порядок конфликтующих RMW. Допустим, первым становится Core 0:

```text
1. Core 0 атомарно читает value == 10.
2. 10 совпадает с expected Core 0.
3. Core 0 записывает 11 и завершает CAS с success.

4. Core 1 получает актуальную строку и атомарно читает value == 11.
5. 11 не совпадает с expected Core 1, равным 10.
6. Core 1 ничего не меняет и завершает CAS с failure.

Итог: value = 11
```

Если первым получит право Core 1, результат будет `20`, а CAS Core 0 завершится неуспешно. Не существует допустимого результата, в котором оба CAS с одинаковым `expected=10` успешно запишут разные значения: первый успешный CAS изменяет объект, поэтому сравнение второго уже не проходит.

Момент атомарного чтения и возможной записи является **точкой линеаризации** (`linearization point`) CAS. Вся операция ведёт себя так, будто произошла в одной точке между вызовом и возвратом, даже если внутри процессор выполнил несколько шагов или повторов.

### Что возвращает CAS на уровне инструкции

Конкретные кодировки различаются, но интерфейс у всех архитектур один:
инструкция сообщает, прошла ли замена, и отдаёт фактически прочитанное значение,
чтобы вызывающий мог решить, повторять ли попытку. На x86 это `LOCK CMPXCHG` с
флагом `ZF`, на ARM64 — инструкция `CAS` из расширения LSE либо пара
`LDXR`/`STXR`, на RISC-V — `LR`/`SC` либо `AMOCAS`. Разбор каждой из них — в
[справочнике по инструкциям](./04a-atomics-hardware-reference.md).

Для понимания стоимости важнее другое: **неуспешный CAS не является дешёвым
чтением**. Инструкция всё равно участвует в согласовании кэшей и обычно требует
строку в состоянии, допускающем запись. Поэтому множество проигрывающих CAS
создаёт трафик согласованности, даже если значение в итоге меняет только один
участник.

### Логический failure и аппаратный retry

Итоговое различие:

| Событие | Видит вызывающий CAS | Требуется новая прикладная попытка |
| --- | --- | --- |
| `current != expected` | `failure` и, в некоторых API, `current` | да, если алгоритм хочет пересчитать `desired` |
| ARM `STXR` или RISC-V `SC` потерял reservation | ничего: реализация CAS повторяет внутренний loop | нет |
| `current == expected`, условная запись успешна | `success` | нет |

Go `CompareAndSwap` возвращает `false`, когда сравнение не прошло. Неуспех внутреннего `STXR`/`SC` компилятор или runtime не выдаёт за результат Go-CAS: машинная последовательность повторяется до успешной условной записи либо до обнаружения нового несовпадающего значения.

### Что CAS гарантирует, а что остаётся алгоритму

| CAS гарантирует | CAS не гарантирует |
| --- | --- |
| атомарное сравнение и условную замену одного поддерживаемого объекта | согласованное изменение нескольких независимых адресов |
| единственный успешный переход от конкретного `expected` | справедливость между конкурентами |
| возврат успеха только для выполненной замены | ограниченное число повторов CAS-loop |
| сравнение текущих битов с `expected` | обнаружение истории `A -> B -> A` |

Последний случай — проблема ABA: аппаратный CAS сравнивает текущее битовое представление, а не журнал предыдущих состояний.

Высокоуровневый CAS-loop, его повторяемые побочные эффекты, `lock-free`/`wait-free` и защита от ABA разобраны в [Sync primitives](../../01-go-core/concurrency-and-performance/03-sync-primitives.md).

## Откуда берётся стоимость атомарных операций

Атомарная инструкция не обязательно дорога сама по себе. Главная цена часто возникает из-за положения строки и конкуренции.

### Строка уже принадлежит ядру

Если строка находится в локальном L1 в состоянии, разрешающем запись, атомарная операция не требует передачи владения от другого ядра. Она всё равно сильнее ограничивает исполнение, чем обычная арифметика в регистре, но coherence traffic минимален.

### Строка находится у другого ядра

Нужно:

1. отправить запрос владения;
2. найти текущего владельца;
3. передать актуальную строку;
4. инвалидировать чужую копию;
5. дождаться необходимых подтверждений;
6. только затем завершить конфликтующую запись.

На многоядерной или NUMA-системе путь может пересекать межъядерную и межсокетную фабрику.

### Несколько писателей: cache-line ping-pong

```text
Core 0 owns line
    -> Core 1 requests line
    -> Core 1 owns line
    -> Core 2 requests line
    -> Core 2 owns line
    -> Core 0 requests line
    -> ...
```

Каждый инкремент сериализуется на одной coherence unit. Отсутствие mutex не устраняет общий последовательный участок.

Поэтому один глобальный atomic counter может масштабироваться хуже, чем:

- per-core или sharded counters;
- локальное накопление с редким объединением;
- пакетная обработка нескольких событий;
- mutex, если вокруг значения всё равно есть составной инвариант.

### Ложное разделение данных

Две независимые переменные могут находиться в одной строке:

```text
cache line 64 bytes

| requests | errors | свободное место ... |
```

Core 0 часто меняет `requests`, Core 1 — `errors`. Поля логически независимы, но любое изменение требует владения всей строкой. Она начинает перемещаться между ядрами. Это ложное разделение данных (`false sharing`), подробно разобранное в [03-cache-coherence-and-mesi.md](./03-cache-coherence-and-mesi.md).

Разносить поля padding-ом следует после измерения:

- padding увеличивает размер структуры;
- больше данных хуже помещается в кэш;
- проблема может быть не в false sharing, а в реальной конкуренции за один объект.

### Почему нет универсальной цены «atomic = N ns»

Задержка зависит от:

- наличия строки в L1/L2/LLC;
- текущего владельца строки;
- числа конкурирующих ядер;
- расположения ядер и NUMA-узлов;
- модели CPU и coherence fabric;
- размера, выравнивания и типа памяти;
- memory ordering;
- окружающего кода и пропускной способности.

Бенчмарк без конкуренции отвечает только на вопрос о локальном hot path. Бенчмарк с одним общим значением и максимальным числом ядер измеряет крайний cache-line ping-pong. Для практического выбора нужны оба режима и реальный access pattern.

## Граница с Go

В этом hardware-файле достаточно трёх правил о Go:

1. Сначала корректность доказывают через Go Memory Model.
2. Все публичные atomic-операции Go ведут себя так, будто входят в единый sequentially consistent order.
3. Компилятор выбирает инструкции и барьеры для конкретного `GOARCH`; исходный код не должен зависеть от случайной реализации amd64.

Например, результат `(0, 0)` из аппаратного store-buffering test полезен для понимания CPU. Но похожая Go-программа с обычными конкурентными чтениями и записями содержит data race. Её поведение нельзя корректно доказывать только через store buffer или x86 TSO.

API `atomic.Int64`, `atomic.Pointer[T]`, `atomic.Value`, CAS-loop, выбор между atomic и mutex, ABA и типичные ошибки находятся в [Sync primitives](../../01-go-core/concurrency-and-performance/03-sync-primitives.md).

## Типичные ошибки в рассуждениях

### 1. «Atomic блокирует всю память»

Для обычной выровненной кэшируемой памяти современный процессор обычно использует coherence на уровне строки кэша. Глобальный bus lock — специальный дорогой случай, а не основная модель.

### 2. «Эксклюзивная строка сама делает `counter++` атомарным»

Обычному store тоже нужно право записи. Но другое ядро может вмешаться между отдельными load и store исходного `counter++`. Нужна именно atomic RMW instruction или корректный синхронизирующий алгоритм.

### 3. «Значение видно, когда оно записано в RAM»

Актуальная версия может оставаться в кэше владельца. Coherence доставляет её другому ядру без обязательного предварительного write-back в DRAM.

### 4. «Atomic очищает кэши»

Atomic меняет права владения и порядок наблюдения согласно ISA. Инвалидирование конфликтующих копий строки не равно очистке всех кэшей.

### 5. «Cache coherence задаёт порядок всех переменных»

Coherence в первую очередь согласует значения одного адреса или одной coherence unit. Порядок независимых адресов определяет memory model и barriers.

### 6. «Acquire или release достаточно в одиночку»

Для публикации нужна связанная пара: release публикует предыдущие записи, а acquire должен наблюдать эффект этой публикации.

### 7. «Работает на x86 — значит корректно»

x86 TSO сильнее многих weakly ordered архитектур, но не заменяет контракт языка и не запрещает компилятору допустимые преобразования.

### 8. «Lock-free означает, что никто не ждёт»

Поток может многократно проигрывать CAS или conditional store. `Lock-free` гарантирует прогресс системы в целом, а не равномерную задержку каждой операции.

## Interview-ready answer

**1. Как процессор делает read-modify-write операцию атомарной?**

Ядро получает исключительное право изменять содержащую адрес строку кэша через coherence-протокол. Затем архитектурный atomic-механизм не позволяет конфликтующей RMW вклиниться между чтением старого значения и фиксацией нового. На x86 это locked instruction; на ARM и RISC-V возможен exclusive/reservation loop, где конфликт заставляет conditional store завершиться неуспешно и повториться.

**2. Значит ли `LOCK` на x86 блокировку всей шины?**

Обычно нет. Для выровненной кэшируемой памяти современные x86 используют согласование кэшей. Bus lock остаётся специальным дорогим путём, например для некоторых split-line или некэшируемых доступов.

**3. Чем атомарность отличается от cache coherence?**

Атомарность не даёт наблюдать RMW частично. Coherence согласует версии одного адреса между кэшами. Ни одно из свойств само по себе не задаёт полный порядок операций над разными адресами.

**4. Почему обычный `counter++` теряет обновления, хотя отдельный store атомарен?**

Инкремент состоит из load, вычисления и store. Два ядра могут прочитать одно старое значение и записать одинаковый результат. Atomic fetch-add делает всю тройку одной RMW.

**5. Как достигается атомарность на ARM и RISC-V, где нет locked-инструкции x86?**

Через резервирующее чтение и условную запись. Чтение ставит резервирование на область памяти, вычисление идёт обычными инструкциями, а запись проходит только при целом резервировании. Конкурирующая запись срывает его, условная запись не выполняется, и цикл повторяется. Наружу видна только успешная RMW.

**6. Зачем нужен store buffer?**

Он позволяет ядру продолжать исполнение, пока запись получает строку и распространяется через coherence. Из-за него последующий load другого адреса может наблюдаться раньше предыдущего store, что на x86 проявляется как StoreLoad relaxation.

**7. Fence сбрасывает кэши в RAM?**

Нет. Fence задаёт порядок наблюдения определённых операций. Актуальные данные могут оставаться в кэшах и передаваться через coherence без немедленной записи в DRAM.

**8. Почему горячий atomic counter плохо масштабируется?**

Все писатели сериализуются на одной строке кэша. При переходе между ядрами строка постоянно меняет владельца, создавая coherence traffic и рост задержки.

**9. Чем atomicity отличается от memory ordering?**

Atomicity защищает одну операцию от частичного наблюдения и конфликтующего вмешательства. Memory ordering определяет, какие соседние операции над другими адресами видны до или после неё.

**10. Как эти детали применять в Go?**

Корректность доказывают через Go Memory Model и публичный контракт `sync/atomic`. Аппаратная модель нужна для понимания стоимости, false sharing и различий архитектур, но не заменяет `happens-before`.
