# Виртуальная память и paging

Когда Go-программа делает `make([]byte, 1<<20)` — куда именно эти байты попадают в физическом RAM? Ответ — **ни в какой**, пока ты их не прочтёшь или не запишешь. Между "адресом в твоей программе" и "физическим адресом в RAM" работает целая система — **виртуальная память**.

Без понимания virtual memory непонятно: почему `RSS` не равен `VIRT` в `top`, почему два процесса видят разные данные по адресу `0x1000`, почему `mmap` не сразу занимает RAM, почему swap убивает latency.

См. также: [linux/01-virtual-memory.md](../linux/01-virtual-memory.md) — Linux-specific детали (OOM killer, swap tuning). Этот файл — про hardware и kernel-уровень.

## Простая аналогия

Представь библиотеку с миллионом книг. У каждой книги — **номер по каталогу** (виртуальный адрес). Но физически книги хранятся не по порядку — где есть свободное место, туда и кладут. Есть **каталожный шкаф** (page table), который переводит "номер по каталогу" в "физическое место на полке".

Что это даёт:
- Можно перестраивать стеллажи, не меняя номера в каталоге
- Можно "пометить" книгу как "хранится в подвале" (swap) — каталог скажет "пойди достань"
- Две библиотеки в одном здании могут использовать **одинаковые номера** для разных книг — каталоги у них разные

Virtual memory — это **тот самый каталог**. Программа работает с "номерами по каталогу", а железо + kernel автоматически переводят их в физические адреса.

## Зачем нужна виртуальная память

Когда-то компьютеры работали с физической памятью напрямую: программа знает что её данные лежат по адресу `0x4000`. Это создавало проблемы:

**1. Изоляция процессов.**
Если процесс A пишет по адресу `0x1000`, не должен ли он повредить процесс B, который тоже использует `0x1000`? Без виртуальной памяти — повредит.

**2. Защита kernel.**
Программа может случайно (или специально) записать в область памяти ядра. Это даёт root.

**3. Фрагментация.**
Программа просит 100 MB подряд. В RAM есть 100 MB свободно, но кусочками — нигде нет 100 MB подряд. Без виртуальной памяти — отказ. С виртуальной — кусочки маппятся в один непрерывный диапазон виртуальных адресов.

**4. Больше памяти чем RAM.**
Через swap программа может работать с "памятью" больше чем RAM физически — неиспользуемые страницы вытесняются на диск.

**5. Совместное использование.**
Системные библиотеки (libc) могут быть в RAM один раз, но видны во многих процессах через одинаковые виртуальные адреса.

Виртуальная память решает всё это одной абстракцией.

## Виртуальный и физический адрес

**Виртуальный адрес (VA)** — то что видит программа. На 64-bit системе адресное пространство — 2^64 = 16 экзабайт (но реально используется 48 бит = 256 TB на современных x86).

**Физический адрес (PA)** — реальный байт в чипах DRAM.

Программа никогда не работает напрямую с PA. Между ними — **MMU** (Memory Management Unit), часть CPU, которая на каждый доступ к памяти переводит VA → PA.

```
Программа: load address 0x7ffe1234
                ↓
              MMU
                ↓
         Page table lookup
                ↓
Physical RAM: address 0xa1c000
                ↓
         Возврат байта
```

Каждый процесс имеет **своё** отображение VA → PA. Адрес `0x1000` в процессе A может указывать на физический адрес `0x40000`, а в процессе B — на `0x80000`. Они изолированы.

### Layout процесса

Типичная карта виртуального адресного пространства процесса в Linux:

```
0xFFFFFFFFFFFFFFFF ┌────────────────────────┐
                   │     Kernel space       │  (только в kernel mode)
0xFFFF800000000000 ├────────────────────────┤
                   │      (canonical hole)  │  ─ "запрещённая" зона
0x00007FFFFFFFFFFF ├────────────────────────┤
                   │         Stack          │  ↓ растёт вниз
                   │           ↓            │
                   ├────────────────────────┤
                   │     mmap region        │  библиотеки, mmap'd файлы
                   │           ↑            │
                   ├────────────────────────┤
                   │         Heap           │  ↑ растёт вверх
                   ├────────────────────────┤
                   │      BSS (uninit)      │  глобальные переменные = 0
                   ├────────────────────────┤
                   │     Data (init)        │  инициализированные глобалы
                   ├────────────────────────┤
                   │      Text (code)       │  машинный код
0x0000000000400000 └────────────────────────┘
0x0000000000000000   (нижние страницы недоступны — null pointer deref ловится)
```

Адреса >= `0xFFFF800000000000` — kernel space, доступен только когда CPU в kernel mode (см. [06-processes-and-threads.md](./06-processes-and-threads.md)).

ASLR (Address Space Layout Randomization) рандомизирует расположение секций при запуске — защита от exploit'ов, использующих знание адресов.

## Page и page table

VA → PA маппинг — не побайтово (слишком много метаданных), а **страницами** (pages).

**Стандартный размер страницы:** 4 KiB (4096 байт) на x86 и большинстве ARM.

```
Virtual address (48 bit на x86_64):
┌──────────────────────────────────┬─────────────────┐
│  Page number (36 бит)            │ Offset (12 бит) │
└──────────────────────────────────┴─────────────────┘
         ↓                                 ↓
  Page table lookup                  В пределах страницы — не нужен перевод
         ↓
  Frame number (физический номер страницы)
         ↓
  ┌──────────────────────────────────┬─────────────────┐
  │  Frame number                    │ Offset          │
  └──────────────────────────────────┴─────────────────┘
                  Physical address
```

Для 4 KB страницы младшие 12 бит — offset внутри страницы (не меняются при переводе). Верхние биты — номер страницы, который ищется в page table.

### Page table — большая таблица

С 36-битным page number таблица содержала бы 2^36 = 68 миллиардов записей. По 8 байт = 512 GB просто на таблицу — это бред.

Решение — **multi-level page table**. На x86_64 обычно 4 уровня (или 5 на новейших):

```
VA: [ PML4 idx | PDPT idx | PD idx | PT idx | Offset ]
       9 бит     9 бит     9 бит    9 бит    12 бит

CR3 register (per-process) → PML4 → PDPT → PD → PT → frame
```

Каждый уровень — таблица на 512 записей (2^9). Большинство записей в верхних уровнях NULL — не аллоцируем то, что не используется. Реальный размер page table для среднего процесса — десятки KB вместо TB.

### Что хранится в page table entry (PTE)

Каждая запись PTE содержит:
- Frame number (где в физической памяти)
- Present bit (загружена ли в RAM)
- Read/Write bits
- User/Kernel bit
- Accessed bit (CPU помечает при доступе)
- Dirty bit (CPU помечает при записи)
- NX (No-Execute) bit — защита от выполнения кода в data области

Это даёт хорошую защиту: память может быть read-only (защита от записи), no-execute (защита от выполнения), kernel-only (защита от чтения user'ом).

## MMU и TLB

**MMU (Memory Management Unit)** — аппаратный модуль внутри CPU, делающий перевод VA → PA. Программно настраивается kernel'ом, но работает прозрачно для программ.

**Проблема:** 4-уровневая page table = 4 чтения памяти для перевода **одного** адреса. Каждое чтение — десятки наносекунд. Полный walk — 100+ нс на доступ. Это убьёт производительность.

**Решение:** TLB (Translation Lookaside Buffer) — маленький кэш переводов внутри CPU.

```
CPU: load 0x7ffe1234
         ↓
       TLB lookup
       ├─ HIT  → PA найден, доступ за 1 цикл
       └─ MISS → walk page table (~100 нс), записать в TLB
```

TLB — 64-2048 записей в зависимости от CPU. При TLB miss CPU "ходит" по page table, и это дорого.

### TLB shootdown

Когда kernel меняет mapping (например, освободил страницу) — нужно **инвалидировать TLB** на всех ядрах, которые могли закэшировать этот перевод. Это inter-processor interrupt — медленная операция.

Поэтому массовые манипуляции памятью (например, freeing larger regions) могут вызвать latency spikes из-за TLB shootdown'ов. Контейнеры на одной ноде с сильно меняющейся памятью — иногда заметно тормозят друг друга через этот эффект.

## Page fault

**Page fault** — исключение CPU, возникающее когда программа обращается к адресу, который не маппится на физический фрейм (или маппится, но с неподходящими правами).

CPU поднимает прерывание, kernel разбирается:

### Типы page faults

**1. Minor page fault.**
Страница не в RAM, но не на диске тоже — нужно её **создать**. Например, программа впервые читает страницу из anonymous mapping (heap) — kernel выделяет физическую страницу из свободного пула, обнуляет, маппит.

**Latency:** ~1-10 мкс. Дёшево.

**2. Major page fault.**
Страница вытеснена в swap или соответствует mmap'd файлу, не загруженному в RAM. Нужно **прочитать с диска**.

**Latency:** 100 мкс — 10 мс. Очень дорого.

**3. Invalid page fault (segmentation fault).**
Адрес вообще не маппится (null pointer deref, write to read-only). Kernel посылает процессу SIGSEGV — обычно процесс падает.

### Как смотреть

```bash
# Minor + major page faults для процесса
ps -o min_flt,maj_flt PID

# В реальном времени
pidstat -r -p PID 1

# Системные метрики
vmstat 1
# columns: si (swap in), so (swap out), bi (block in), bo (block out)
```

**Major faults в production** — почти всегда плохо. Это либо memory pressure (swap), либо холодный mmap'd файл (если так задумано — нормально).

## Demand paging и lazy allocation

Когда программа делает `malloc(1<<30)` (1 GB) — kernel **не выделяет** 1 GB физической памяти. Он только:
1. Помечает в page table — "этот диапазон зарезервирован"
2. Возвращает указатель
3. Все страницы — **not present** (флаг в PTE)

Когда программа реально прочитает или запишет в страницу — page fault → kernel выделит физическую страницу → продолжение работы.

Это называется **lazy allocation** или **demand paging**.

### Демо

```go
package main

import (
    "fmt"
    "os"
    "runtime"
)

func main() {
    // Аллоцировать 1 GB, но не трогать
    huge := make([]byte, 1<<30)

    runtime.GC()
    fmt.Printf("Allocated 1 GB but untouched\n")
    printMemUsage()

    // Записать в каждую страницу
    for i := 0; i < len(huge); i += 4096 {
        huge[i] = 1
    }

    fmt.Println("\nAfter touching every page:")
    printMemUsage()
    _ = os.Stdout  // keep huge alive
}

func printMemUsage() {
    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    fmt.Printf("Heap alloc: %d MB\n", m.HeapAlloc/1024/1024)
    fmt.Printf("Sys (total OS memory): %d MB\n", m.Sys/1024/1024)

    // RSS (то что реально занято в RAM) можно прочитать из /proc/self/status
    if data, err := os.ReadFile("/proc/self/status"); err == nil {
        for _, line := range []string{"VmRSS:", "VmSize:"} {
            for _, l := range splitLines(string(data)) {
                if hasPrefix(l, line) {
                    fmt.Println(l)
                }
            }
        }
    }
}
```

Запустишь на Linux — увидишь:
- После аллокации: VmSize большой (виртуальная), VmRSS маленький
- После записи: VmRSS вырос до 1 GB

**VmSize** растёт сразу — это виртуальное резервирование. **VmRSS** растёт только когда трогаешь страницы.

## Copy-on-write (COW)

Когда процесс делает `fork()` — теоретически нужно скопировать всю его память (стек, heap, mmap regions) в новый процесс. Это могло бы быть гигабайты, и заняло бы много времени.

**Хитрость:** kernel не копирует ничего. Он маппит **те же физические страницы** в новый процесс, помечая их read-only.

Когда один из процессов **пишет** в страницу:
1. Page fault (write на read-only)
2. Kernel замечает что это COW-страница
3. Создаёт **копию** страницы в новом физическом фрейме
4. Маппит её процессу, который писал, с правами на запись
5. Продолжение работы

То есть копируются **только страницы, в которые реально записали** после fork. Это делает fork невероятно дешёвой операцией: clone процесса = доли миллисекунды.

**Применения:**
- `fork()` + `exec()` — типичный паттерн запуска процессов в Unix
- `redis-cli BGSAVE` — Redis форкается и сохраняет snapshot, родитель продолжает работать
- Postgres использует fork для каждого нового соединения

В Go fork напрямую не используется (только `os/exec`, который под капотом fork+exec). Но runtime'у это важно потому что любая запись после fork — это page fault.

## mmap vs brk: как программа просит память

Когда программе нужна память, есть два основных syscall'а:

### brk / sbrk

Старый способ. Просто увеличивает "конец" data segment. Похоже на push в стек, но для heap.

```
До brk(0x800000):
[ text ][ data ][ heap до 0x600000 ]

После brk(0x800000):
[ text ][ data ][ heap до 0x800000 ]
                      ↑ выросло
```

**Минус:** последовательное. Нельзя освободить середину — только сжать с конца.

### mmap

Гибкий способ. Создаёт mapping для любого диапазона виртуальных адресов.

```go
// Создать 1 GB anonymous mapping
addr, err := syscall.Mmap(
    -1,                           // fd: -1 для anonymous
    0,                            // offset
    1<<30,                        // length
    syscall.PROT_READ|syscall.PROT_WRITE,
    syscall.MAP_ANON|syscall.MAP_PRIVATE,
)
```

**Виды mmap:**
- **Anonymous** — просто RAM (для heap, стека, mmap'd аллокаторов)
- **File-backed** — маппинг файла в адресное пространство; чтение из адреса = чтение из файла (kernel page cache в деле)
- **Shared** — несколько процессов имеют доступ к одной физической странице
- **Private** — изменения видны только этому процессу (COW для file mappings)

**Применения:**
- Загрузка библиотек (`*.so` файлы маппятся file-backed shared)
- Heap у современных allocator'ов (Go runtime, jemalloc)
- Shared memory между процессами
- Чтение больших файлов без `read()` syscall'ов (просто `mmap` + читай через указатель)

## Swap

Когда RAM кончается, kernel может **вытеснить** редко используемые страницы на disk — в swap-раздел или swap-файл.

```
Process accesses page X:
  → Page fault
  → Kernel: "X в swap, читаю с диска"
  → Disk I/O: 50 мкс - 10 мс
  → Page загружена, продолжение работы
```

Это очень медленно. Если процесс активно работает с большим набором данных, превышающим RAM — он будет постоянно **thrashing** (свопить туда-сюда), всё замедлится в 100-1000 раз.

### swappiness — насколько агрессивно свопить

```bash
cat /proc/sys/vm/swappiness    # обычно 60
# 0 — не свопить пока совсем не прижмёт
# 100 — свопить активно даже при наличии RAM
```

Для серверов с БД часто ставят `vm.swappiness=1` или `0` — лучше OOM-kill, чем медленный swap.

### swap в контейнерах

Kubernetes обычно отключает swap (`--fail-swap-on=true` по умолчанию). Это потому что memory limits и QoS работают предсказуемо только без swap: процесс либо в лимите, либо OOMKilled, без "медленной зоны".

### Когда swap полезен

- Долгоживущие процессы со страницами которые **реально** не используются — kernel их свопит, освобождая RAM для cache
- Защита от случайных всплесков использования (буфер от OOM)

Для большинства production-серверов swap либо маленький, либо отсутствует.

## Huge pages

4 KB страница — мелкая. Для процесса с GB памяти page table содержит **миллионы записей**. TLB не успевает кэшировать — много TLB miss'ов.

**Решение:** **huge pages** — страницы по 2 MB (или 1 GB) вместо 4 KB.

- Меньше PTE → page table компактнее
- Меньше TLB miss'ов → быстрее доступ к памяти
- Один TLB entry покрывает 2 MB вместо 4 KB → много меньше "холодных" переходов

**Минусы:**
- Меньше гранулярность (2 MB или ничего)
- Сложнее аллокация (нужны 2 MB подряд в физической RAM)
- Не для всех workload'ов выгодно

### Transparent Huge Pages (THP)

Linux может автоматически объединять 4 KB страницы в 2 MB huge pages, когда видит большие непрерывные регионы. Иногда это даёт +10-30% производительности (БД), иногда — латентность из-за фоновой работы khugepaged.

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never
```

Для production-БД часто рекомендуют `madvise` (включать только когда программа явно попросит) или `never`.

## Как Go runtime запрашивает память

Go runtime — собственный allocator (на базе tcmalloc). Он минимизирует syscall'ы:

1. **При старте** runtime mmap'ит большой регион (arena), но **не трогает** его — это виртуальное резервирование без потребления RAM (`MAP_NORESERVE`).
2. По мере роста heap — трогает страницы по мере необходимости (demand paging).
3. Когда GC освобождает память — runtime может вернуть страницы kernel'у через `madvise(MADV_DONTNEED)` или `MADV_FREE`. Это говорит kernel'у "эту страницу можно отдать, я её не использую".

### Почему RSS Go процесса не падает после GC

После GC virtual address space занят теми же страницами (Go не освобождает мгновенно), но **физически** kernel может их забрать. С `MADV_FREE` — забирает только когда RAM нужна другим. Поэтому в `top` Go-процесс может показывать высокий RSS долго после освобождения данных — это normal.

С Go 1.16+ runtime по умолчанию использует `MADV_DONTNEED` на Linux — RSS возвращается агрессивнее.

### GOMEMLIMIT (Go 1.19+)

```go
// Soft limit на heap
debug.SetMemoryLimit(2 << 30)  // 2 GB
// или env: GOMEMLIMIT=2GiB
```

Runtime теперь учитывает memory pressure и более агрессивно GC'ит, не превышая лимит. Связь с виртуальной памятью — runtime лучше понимает сколько у него реально есть RAM (особенно важно в контейнерах с cgroup limits).

## VIRT, RSS, USS, PSS — что это такое

`top`, `ps`, `htop` показывают несколько столбцов памяти, и они означают разное:

| Метрика | Что |
|---|---|
| **VIRT / VSZ** | Виртуальное адресное пространство — все mmap'ы, включая нетронутые. Может быть огромным и не значит ничего страшного. |
| **RSS** | Resident Set Size — реально занятая физическая память. То что мешает другим процессам. |
| **USS** | Unique Set Size — память, занятая **только этим процессом** (не shared). При убийстве процесса именно USS освободится. |
| **PSS** | Proportional Set Size — RSS, но shared страницы делятся пропорционально между процессами, которые их используют. |
| **Swap** | Сколько страниц процесса в swap. |

**Пример:**
- VIRT = 10 GB (mmap'ом запросили арена для heap)
- RSS = 500 MB (реально используем)
- VIRT-RSS = 9.5 GB виртуально зарезервировано, но физически не занято

VIRT — обычно бесполезный показатель, не пугайся высоких значений. RSS — реальная нагрузка. USS — нагрузка "только меня".

```bash
# Detailed память процесса
cat /proc/PID/smaps
# или summary
cat /proc/PID/status | grep -E "Vm|Rss"
```

---

## Практические выводы

**1. Большой VIRT — не повод для паники.**
Go-сервис с VIRT = 100 GB и RSS = 200 MB — нормально. Runtime запросил много виртуально, реально использует мало.

**2. Page fault rate — важная метрика.**
Минорные — норма. Мажорные (`pgmajfault` в `/proc/vmstat`) — сигнал что что-то лежит на диске и читается. Либо swap (плохо), либо холодный mmap (зависит от паттерна).

**3. Swap в production-сервере обычно зло.**
Если включён — мониторь `vm.swap_used`. Свопящийся БД-сервер = death по латенси. Disable или max 1-2 GB как буфер от OOM.

**4. Huge pages — для серверов с большой памятью.**
PostgreSQL, Redis, JVM-сервисы с десятками GB heap выигрывают 10-30% от huge pages. Маленьким Go-сервисам — мало пользы.

**5. mmap для больших файлов.**
Вместо `os.ReadFile()` для гигабайтного файла — `mmap`. Не загружаешь весь файл в RAM, kernel'еет page cache подгружает по мере доступа.

**6. Понимать что fork — это COW.**
Если форкаешься для тяжёлой задачи (BGSAVE в Redis) — память не дублируется. Но **запись** в parent после fork — это page faults.

**7. cgroup memory limits и swap.**
В контейнерах cgroup лимит на память считает RSS+swap (если включён). С отключённым swap (k8s default) — поведение чище: либо в лимит, либо OOMKilled.

**8. GOMEMLIMIT для Go-сервисов в контейнерах.**
По умолчанию Go runtime не знает про cgroup лимит → может уйти выше → OOMKilled. С `GOMEMLIMIT` runtime будет GC'ить агрессивнее, избегая OOM. См. [01-go-core/memory-internals/04-garbage-collector.md](../../01-go-core/memory-internals/04-garbage-collector.md).
