## Как архитектуры выполняют атомарную RMW

Архитектуры дают похожий результат разными интерфейсами.

### x86: locked instruction

x86 предоставляет атомарные RMW-инструкции с префиксом `LOCK`:

```assembly
LOCK XADD [counter], RAX
LOCK CMPXCHG [value], RBX
```

`XCHG` с операндом в памяти имеет атомарную семантику и без явно записанного `LOCK`.

Для выровненного операнда в обычной кэшируемой памяти современные x86-процессоры обычно используют cache-coherence mechanism:

1. получают строку в состояние, разрешающее запись;
2. не позволяют другому ядру изменить конфликтующую область во время locked operation;
3. выполняют RMW;
4. сохраняют атомарный и упорядочивающий контракт инструкции.

На время locked operation процессор удерживает внутренний контроль над строкой, необходимый для неделимого RMW. После завершения инструкции строка остаётся обычной частью кэша в состоянии, разрешающем запись.

### Когда x86 использует bus lock

Исторические процессоры могли блокировать внешнюю шину памяти сигналом `LOCK#`. Современный CPU для кэшируемой строки обычно обходится coherence-протоколом, но bus lock или другой очень дорогой путь всё ещё возможен, например когда:

- операнд атомарной операции пересекает границу строки кэша;
- память не кэшируется подходящим образом;
- тип памяти не позволяет обычный cache-coherent путь.

Поэтому невыровненная атомарная операция — не просто «немного медленнее». Она может вызвать исключение, специальную обработку или системный скачок задержки в зависимости от CPU и настроек ОС.

### ARM64: exclusive pair

Один способ ARM64 — пара load-exclusive/store-exclusive:

```assembly
retry:
    LDXR  X0, [counter]      // прочитать и создать exclusive reservation
    ADD   X1, X0, #1
    STXR  W2, X1, [counter]  // записать, только если reservation сохранилась
    CBNZ  W2, retry          // иначе повторить
```

Пошагово:

1. `LDXR` читает значение и регистрирует его область во внутреннем exclusive monitor.
2. Ядро вычисляет новое значение обычной инструкцией.
3. Если другое ядро выполнило конфликтующую запись, reservation теряется.
4. `STXR` сообщает failure и ничего не записывает.
5. Код повторяет цикл с новым значением.

Здесь между `LDXR` и `STXR` другое ядро физически может изменить память. Атомарность достигается иначе: условная запись в таком случае **не пройдёт**, поэтому наружу виден только успешный RMW.

Кроме конфликтующей записи, reservation могут разрушить и другие разрешённые архитектурой события. Поэтому код обязан обрабатывать неуспешный `STXR` повтором, даже если на уровне исходной логики не удалось заметить конкурента.

Exclusive reservation не запрещает другим ядрам обращаться к памяти. Их конфликтующая запись аннулирует reservation, после чего условный store завершается неуспешно.

### ARM64: LSE atomics

ARMv8.1-A Large System Extensions (`LSE`) добавляют инструкции вроде `CAS`, `LDADD`, `SWP`. Для программы это одна ISA-инструкция:

```assembly
LDADD Xdelta, Xold, [counter]
```

Она всё равно должна взаимодействовать с coherence-протоколом, но избавляет программу от явного exclusive-loop. На системах с высокой конкуренцией такие инструкции могут масштабироваться лучше, потому что повторы и арбитраж выполняются ближе к подсистеме памяти.

### RISC-V: LR/SC и AMO

RISC-V предоставляет два семейства:

- `LR`/`SC` — load-reserved/store-conditional, похожие по идее на ARM exclusive pair;
- `AMO` — готовые atomic memory operations, например `AMOADD`.

Упрощённый LR/SC-loop:

```assembly
retry:
    LR.D   t0, (a0)
    ADDI   t1, t0, 1
    SC.D   t2, t1, (a0)
    BNEZ   t2, retry
```

`SC.D` записывает только при действующей reservation и тоже может потребовать повторения без видимой прикладному коду записи конкурента. `AMOADD.D` выражает read-modify-write одной инструкцией ISA:

```assembly
AMOADD.D t0, t1, (a0)
```

Биты `aq` и `rl` добавляют acquire/release ordering. Без них атомарность RMW не обязана упорядочивать все соседние обращения к памяти.

### Сравнение механизмов

| Архитектура | Механизм | Что происходит при конфликте |
| --- | --- | --- |
| x86 | locked RMW, например `LOCK CMPXCHG` | инструкция получает требуемое владение и архитектурно выполняется как одна atomic RMW |
| ARM64 | `LDXR`/`STXR` | `STXR` завершается неуспешно, код повторяет цикл |
| ARM64 с LSE | `CAS`, `LDADD`, `SWP` | одна ISA-инструкция, конфликт разрешает аппаратная реализация |
| RISC-V | `LR`/`SC` | `SC` завершается неуспешно, код повторяет цикл |
| RISC-V | `AMOADD`, `AMOSWAP` и другие AMO | одна ISA-инструкция, RMW атомарна по правилам ISA |

Одинаковый контракт языка может компилироваться в разные последовательности. Поэтому исходный код должен опираться на memory model языка, а не проверять только ассемблер одной архитектуры.

## Модели памяти по архитектурам

### x86-64 и TSO

Для обычной write-back памяти x86-64 предоставляет относительно строгую модель `Total Store Order` (`TSO`):

- load не меняет наблюдаемый порядок с другими load;
- store не меняет наблюдаемый порядок с другими store;
- основное ослабление — более поздний load другого адреса может наблюдаться раньше предыдущего store из-за store buffer.

Поэтому результат `(0, 0)` в store-buffering test допустим на x86.

Специальные типы памяти, non-temporal stores и операции с устройствами имеют дополнительные правила. TSO нельзя без оговорок переносить на любой доступ, который синтаксически похож на чтение или запись.

### ARM

ARM использует более слабую модель памяти. Для независимых обращений сохраняется меньше порядка, поэтому применяются:

- инструкции load-acquire и store-release;
- `DMB` для порядка обращений к данным;
- более сильные механизмы, когда требуется не только порядок, но и завершение операции.

ARM не «случайно переставляет всё». ISA точно определяет зависимости, типы памяти, области действия барьеров и семантику атомарных инструкций. Но низкоуровневый алгоритм, случайно работающий благодаря x86 TSO, нельзя переносить на ARM без анализа.

### RISC-V

Базовая модель RISC-V называется `RVWMO` — RISC-V Weak Memory Ordering. Она предоставляет:

- `FENCE` для порядка выбранных классов операций;
- биты `aq` и `rl` у атомарных инструкций;
- опциональное расширение `Ztso` с более строгой TSO-подобной моделью.

Поэтому недостаточно сказать «RISC-V слабее или сильнее ARM». Нужно учитывать используемые расширения и конкретные mapping rules компилятора.

### Краткое сравнение

| Архитектура | Базовая модель | Чем добавляется порядок |
| --- | --- | --- |
| x86-64 | относительно строгая TSO | locked operations, `LFENCE`, `SFENCE`, `MFENCE` по назначению |
| ARM | weakly ordered | acquire/release instructions, `DMB`, `DSB`, `ISB` по назначению |
| RISC-V | RVWMO | `FENCE`, биты `aq`/`rl`; опционально `Ztso` |

## Барьеры памяти по архитектурам

Что такое барьер и чего он **не** делает — в [основной статье](./04-atomics-and-memory-ordering.md). Здесь только конкретные инструкции.

### x86

Упрощённо:

| Инструкция | Роль |
| --- | --- |
| `LFENCE` | ограничивает порядок load относительно последующих load и имеет дополнительные execution-ordering применения |
| `SFENCE` | упорядочивает предыдущие store относительно последующих store, особенно важно для weakly ordered stores |
| `MFENCE` | упорядочивает предыдущие load/store относительно последующих load/store |

Для store-buffering test:

```text
Core 0: Store x = 1; MFENCE; Load y
Core 1: Store y = 1; MFENCE; Load x
```

`MFENCE` не позволяет обоим последующим load обогнать предыдущие store, поэтому `(0, 0)` исключается на аппаратном уровне x86.

### ARM

| Инструкция | Роль |
| --- | --- |
| `DMB` | задаёт порядок указанных обращений к данным |
| `DSB` | дополнительно требует завершения указанных операций перед продолжением |
| `ISB` | синхронизирует последующий поток инструкций после изменений, влияющих на их выбор или выполнение |

`ISB` не является «самым сильным DMB». Он решает другую задачу, например после изменения системного состояния, влияющего на последующие инструкции.

### RISC-V

`FENCE` содержит predecessor-set и successor-set: какие предыдущие чтения, записи или I/O operations должны наблюдаться до каких последующих операций.

Биты `aq` и `rl` атомарной инструкции задают локальный acquire/release ordering:

- `aq` не позволяет нужным последующим операциям наблюдаться до atomic;
- `rl` не позволяет нужным предыдущим операциям наблюдаться после atomic.

Фраза «atomic всегда является full fence» для RISC-V неверна: семантика зависит от битов и требуемого порядка.

## Уровни упорядочивания памяти

Идея публикации через release/acquire разобрана в
[основной статье](./04-atomics-and-memory-ordering.md). Здесь — полный набор
уровней и то, как они ложатся на инструкции.

В C++, Rust, ISA и технической литературе встречаются такие memory orders:

| Уровень | Основная гарантия |
| --- | --- |
| `relaxed` | атомарность конкретного объекта без общего порядка соседних данных |
| `acquire` | последующие операции не переходят до acquire; наблюдающий load получает опубликованные данные |
| `release` | предыдущие операции не переходят после release; store публикует сделанные до него записи |
| `acq_rel` | acquire и release для одной RMW |
| `seq_cst` | SC-операции входят в единый порядок, согласованный с правилами языка |

Go такого выбора не даёт: все публичные операции `sync/atomic` ведут себя как
`seq_cst`. Уровни встречаются при чтении кода на C++ и Rust, исходников runtime
и ядра Linux.

### Почему memory order не равен одной инструкции

`Sequential consistency` — свойство допустимой истории операций программы, а `MFENCE` — конкретная инструкция x86.

Один и тот же языковой `seq_cst`:

- на x86 может использовать свойства TSO и locked instruction;
- на ARM — acquire/release instruction, barrier или LSE-вариант;
- на RISC-V — `aq`/`rl`, `FENCE` и правила выбранной atomic instruction.

Компилятор обязан получить требуемый контракт из возможностей целевой ISA. Поэтому нельзя доказывать семантику языка фразой «здесь же есть fence» без анализа всей mapping sequence.

## CAS по архитектурам

Что такое CAS, точка линеаризации и чем логический failure отличается от аппаратного повтора — в [основной статье](./04-atomics-and-memory-ordering.md).

### x86: `LOCK CMPXCHG`

Для 64-битного варианта x86 операнды можно представить так:

```text
RAX       = expected
RBX       = desired
[address] = current
```

Инструкция:

```assembly
LOCK CMPXCHG [address], RBX
```

выполняет два пути.

Совпадение:

```text
если [address] == RAX:
    [address] = RBX
    ZF = 1
```

Несовпадение:

```text
если [address] != RAX:
    RAX = [address]   // вернуть фактически прочитанное значение
    ZF = 0
```

Флаг `ZF` (`Zero Flag`) сообщает, прошла ли замена. На успешном пути память получает `desired`; на неуспешном — вызывающий получает в `RAX` актуальное значение и может решить, повторять ли попытку.

Путь инструкции над обычной кэшируемой памятью выглядит так:

```text
1. Ядро запрашивает содержащую address строку для locked RMW.
2. Coherence-протокол упорядочивает запрос относительно RMW других ядер.
3. CMPXCHG читает current и сравнивает его с RAX.
4. При совпадении новое значение фиксируется в строке.
5. Инструкция возвращает результат через ZF и при несовпадении через RAX.
```

Неуспешный `LOCK CMPXCHG` не является дешёвым обычным чтением. Locked instruction всё равно участвует в согласовании кэшей и обычно требует строку в состоянии, допускающем RMW. Поэтому множество проигрывающих CAS создаёт coherence traffic, даже если только один участник меняет значение.

У x86 архитектурный `CMPXCHG` не сообщает ложный (`spurious`) failure: `ZF=0` означает, что прочитанные биты не совпали с `expected`. Внутренние аппаратные повторы, если они нужны реализации CPU, не видны программе.

### ARM64: одна LSE-инструкция

С расширением Large System Extensions (`LSE`) ARM64 предоставляет инструкцию `CAS`. Упрощённо:

```assembly
// X0 сначала содержит expected, X1 — desired, X2 — address
CAS X0, X1, [X2]
```

Аппаратная семантика:

```text
current = [X2]

if current == X0:
    [X2] = X1

X0 = current
```

После инструкции `X0` содержит фактически прочитанное значение. Код сохраняет исходный `expected` в другом регистре и сравнивает его с новым `X0`, чтобы определить успех.

Варианты инструкции задают порядок памяти:

| Инструкция | Порядок |
| --- | --- |
| `CAS` | без дополнительного acquire/release ordering |
| `CASA` | acquire |
| `CASL` | release |
| `CASAL` | acquire + release |

Одна ISA-инструкция не означает один внутренний такт. Процессор всё равно получает нужные права на строку и разрешает конфликт через coherence subsystem, но эти шаги скрыты за одной архитектурной командой.

### ARM64: CAS через `LDXR`/`STXR`

Без LSE та же логика собирается из exclusive load и conditional store:

```assembly
retry:
    LDXR  Xcurrent, [Xaddress]
    CMP   Xcurrent, Xexpected
    B.NE  mismatch

    STXR  Wstatus, Xdesired, [Xaddress]
    CBNZ  Wstatus, retry

    // Логический CAS успешен.
    B     success

mismatch:
    // Текущее значение не равно expected.
```

Здесь есть два разных уровня повторения:

```text
LDXR прочитал current
        |
        +-- current != expected
        |      -> логический failure возвращается вызывающему
        |
        +-- current == expected
               |
               +-- STXR success -> логический success
               |
               +-- STXR failure -> аппаратная попытка повторяется
```

`STXR` может завершиться неуспешно из-за потери exclusive reservation. Причиной бывает конфликтующая запись, а архитектура допускает потерю reservation и по другим причинам. Такой результат ещё не означает, что `current != expected`: реализация CAS повторяет `LDXR` и заново проверяет значение.

Граница reservation может быть шире самого атомарного объекта. Поэтому запись в соседнюю область той же reservation granule способна сорвать `STXR`, хотя прикладное значение CAS не изменилось. Это один из источников дополнительных повторов и чувствительности к размещению данных.

Для acquire/release используются соответствующие варианты exclusive-инструкций, например `LDAXR` и `STLXR`, либо дополнительные барьеры согласно требуемому контракту.

### RISC-V: `LR`/`SC`

В стандартном atomic extension RISC-V CAS можно построить через load-reserved/store-conditional:

```assembly
retry:
    LR.D   t0, (a0)         // t0 = current
    BNE    t0, a1, mismatch // a1 = expected

    SC.D   t1, a2, (a0)     // a2 = desired
    BNEZ   t1, retry         // reservation потеряна

    // success
```

Логика совпадает с ARM exclusive-loop:

1. `LR.D` читает значение и создаёт reservation set.
2. Несовпадение с `expected` даёт логический failure.
3. `SC.D` пытается записать `desired`.
4. Потеря reservation заставляет повторить внутреннюю попытку.
5. Только успешный `SC.D` означает успешный CAS.

Биты `.aq` и `.rl` добавляют acquire/release ordering к атомарной последовательности. Они отвечают за порядок соседних обращений, а reservation — за условие успешной записи.

### RISC-V: `AMOCAS` из расширения `Zacas`

Расширение `Zacas` предоставляет нативные инструкции:

```assembly
AMOCAS.W   // 32 бита
AMOCAS.D   // 64 бита
AMOCAS.Q   // 128 бит на RV64
```

Для `AMOCAS.D`:

```text
rd  = expected до инструкции
rs2 = desired
rs1 = address

current = memory[rs1]

if current == rd:
    memory[rs1] = rs2

rd = current
```

Как и ARM LSE CAS, инструкция возвращает прочитанное значение в регистре с `expected`. Совпадение исходного `expected` с возвращённым `current` означает успех. Варианты `.aq`, `.rl` и `.aqrl` задают порядок памяти.

`AMOCAS.W/D/Q` требует естественного выравнивания адреса по размеру операнда. `Zacas` является отдельным расширением, поэтому конкретный RISC-V CPU может поддерживать `LR`/`SC`, но не иметь `AMOCAS`.
