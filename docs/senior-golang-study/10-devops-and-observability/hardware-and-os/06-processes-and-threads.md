## Главное различие

Когда мы запускаем программу, ОС создаёт для неё **процесс**. Процесс объединяет ресурсы приложения: виртуальную память, открытые файлы, права доступа и другие настройки.

Сам код исполняют **потоки**. В одном процессе может быть несколько потоков: у каждого свой стек и состояние выполнения, но память и большинство ресурсов процесса они разделяют.

Поэтому процесс отвечает на вопрос **«какие ресурсы принадлежат приложению?»**, а поток — **«кто исполняет его код?»**.

В Go появляется ещё один уровень — **goroutine**. Goroutine не является потоком ОС: Go runtime размещает множество goroutines на меньшем количестве системных потоков. Сначала разберём процессы и потоки, а затем вернёмся к тому, как с ними соотносится модель Go.

## Простая аналогия

Подойдёт жилой дом с несколькими **квартирами** — это процессы. У каждой квартиры свой адрес, своя мебель, свои ключи. Жильцы одной квартиры не могут зайти в другую без отдельного разрешения.

Внутри квартиры живут несколько **людей** — это потоки. Они пользуются общей гостиной, кухней и ванной (память процесса), но у каждого своя кровать и свои личные вещи (стек и регистры). Работают они независимо, но в общем пространстве, и если один разобьёт общую посуду, это коснётся всех в квартире.

Сравнение:
- **Изоляция:** между процессами — стены и замки. Внутри процесса между потоками — только договорённости.
- **Связь:** процессы общаются "почтой" (IPC, sockets). Потоки — просто пишут друг другу в общую тетрадь (shared memory).
- **Стоимость:** построить квартиру дорого (создание процесса). Завести нового жильца — относительно дёшево (создание потока).

## Что такое процесс

С точки зрения OS, процесс — это **контейнер ресурсов**:

**1. Виртуальное адресное пространство.**
Своя карта виртуальных адресов со стеком, кучей, кодом и сегментами данных (см. [Виртуальная память и страничная организация](./05-virtual-memory-and-paging.md)). Адрес `0x1000` в процессе A может отображаться на совершенно другой физический адрес, чем `0x1000` в процессе B.

**2. PID (Process ID).**
Уникальный идентификатор. В Linux допустимый диапазон задаёт настройка ядра
`/proc/sys/kernel/pid_max`, поэтому конкретный предел зависит от версии и
конфигурации. PID 1 в данном пространстве имён процессов занимает `init`,
`systemd` или само приложение в контейнере.

**3. Таблица file descriptors.**
Список открытых файлов, сокетов, pipe'ов. По умолчанию: 0 = stdin, 1 = stdout, 2 = stderr. Все открытые `os.Open` и `net.Dial` добавляются сюда.

**4. Working directory.**
Текущая директория (`pwd`). Все относительные пути считаются от неё.

**5. Environment variables.**
`$PATH`, `$HOME`, и т.д.

**6. UID/GID.**
От чьего имени работает процесс. Определяет права доступа к файлам и системным операциям.

**7. Signal handlers.**
Что делать при SIGINT, SIGTERM, SIGSEGV. См. [linux/04-signals-and-processes.md](../linux/04-signals-and-processes.md).

**8. Состояние выполнения.**
Running, sleeping, zombie, stopped. Видно в `ps`.

### Когда процесс создаётся

Только через `fork()` (или производные — `vfork`, `clone`). Каждый процесс имеет **родителя** (parent process). Образуется дерево.

```bash
$ pstree -p
systemd(1)
├─sshd(842)
│   └─sshd(2103)
│       └─bash(2105)
│           └─go(2200)
│               └─myapp(2201)
└─dockerd(950)
    └─containerd-shim(1234)
        └─myapp-in-container(1)  ← PID 1 внутри namespace
```

## Что такое поток

Поток — это **независимый путь выполнения** внутри одного процесса.

Несколько потоков в процессе **разделяют:**
- Виртуальное адресное пространство (тот же heap, тот же code)
- File descriptors
- Working directory, environment
- UID/GID
- Signal handlers (но каждый thread может маскировать сигналы по-своему)

Каждый поток имеет **своё:**
- TID (Thread ID)
- Стек (обычно 8 MB на Linux по умолчанию, см. `ulimit -s`)
- Контекст регистров (`RAX`, `RSP`, `RIP` и другие)
- Состояние выполнения

**Главная разница:** потоки одного процесса видят одну и ту же память. Если thread A пишет `var = 42`, thread B сразу же может это прочитать. Это — основа multi-threaded программирования (и источник race conditions).

### Что значит «у потока свои регистры»

Регистры — это очень маленькие и быстрые ячейки внутри CPU. Процессор использует их прямо во время выполнения инструкций: хранит операнды вычислений, адрес вершины стека, адрес следующей инструкции и служебные флаги.

На уровне архитектуры каждый логический CPU предоставляет выполняемому коду свой набор регистров. Например, ядро с двумя hardware threads через SMT представляется ОС как два логических CPU, и у каждого есть независимое архитектурное состояние регистров.

У потока ОС есть **собственный контекст регистров** — набор значений, с которыми его выполнение должно продолжиться:

| Регистр x86-64 | Что хранит в контексте потока |
| --- | --- |
| `RIP` | адрес следующей инструкции |
| `RSP` | адрес вершины стека этого потока |
| `RAX`, `RBX`, `RCX` и другие general-purpose registers | промежуточные значения, аргументы и результаты согласно выполняемому коду и calling convention |
| `RBP` | может указывать на начало текущего stack frame; оптимизирующий компилятор также может использовать его как обычный регистр |
| `RFLAGS` | флаги результата операций и управляющее состояние |
| `XMM`/`YMM` и другие vector registers | SIMD-вычисления и значения с плавающей точкой |

Физически значения находятся в регистрах CPU только пока поток выполняется на конкретном логическом CPU. Когда поток ожидает своей очереди, ОС хранит его сохранённый регистровый контекст в памяти ядра.

```text
Thread A выполняется на CPU 0

регистры CPU 0:
RIP = адрес следующей инструкции A
RSP = вершина стека A
RAX = текущее значение A
```

Планировщик решает запустить на CPU 0 поток B:

```text
1. Сохранить значения регистров CPU 0 в контекст Thread A.

2. Загрузить сохранённый контекст Thread B в регистры CPU 0:
   RIP = адрес следующей инструкции B
   RSP = вершина стека B
   RAX = текущее значение B

3. Продолжить выполнение с адреса в RIP.
```

После этого тот же физический CPU выполняет B так, будто B не прерывался. Позже планировщик может восстановить регистры A, и A продолжит со своего `RIP` и своего стека.

```text
                 context switch

Thread A context ---------------------> память ядра
                                              |
регистры CPU <------------------------ Thread B context
                                              |
                                              v
                                    выполнение Thread B
```

Поэтому два потока могут выполнять одну и ту же функцию, но находиться в разных её местах:

```text
Thread A:
RIP = инструкция внутри первой итерации
RSP = стек A

Thread B:
RIP = инструкция внутри десятой итерации
RSP = стек B
```

Код функции и heap у них общие, а текущая позиция выполнения, цепочка вызовов и промежуточные значения различаются благодаря разным `RIP`, `RSP` и остальному регистровому контексту.

Поток не закреплён навсегда за одним CPU. Планировщик может сохранить его контекст на CPU 0, а затем восстановить на CPU 3. Для программы это остаётся тем же потоком с тем же TID, стеком и продолжением выполнения.

У goroutine похожая идея, но её контекст сохраняет Go runtime. Когда goroutine получает время выполнения, runtime восстанавливает необходимые значения и запускает её на одном из системных потоков. Поэтому goroutine также не владеет постоянным физическим набором регистров.

### Multithreading vs multiprocess

- **Multithreaded:** один процесс, несколько потоков → общая память, дешёвые "коммуникации" (просто переменные), но **catastrophic crash** одного потока валит весь процесс.
- **Multiprocess:** несколько процессов → изоляция, crash одного не валит других, но "общаются" через IPC (медленнее).

Web-серверы исторически делятся:
- **Apache prefork** — multiprocess. Стабильно, но дорого по памяти.
- **Apache worker / nginx** — multithreaded внутри. Эффективнее.
- **Postgres** — multiprocess (forks per connection). Изоляция от crash.
- **Go** — multithreaded внутри процесса, но **goroutines** мультиплексируются (см. ниже).

## Процесс и поток: сравнение

| Свойство | Процесс | Поток |
| --- | --- | --- |
| Виртуальное адресное пространство | Отдельное от других процессов | Общее с другими потоками того же процесса |
| Открытые файловые дескрипторы | Таблица дескрипторов принадлежит процессу | Использует общую таблицу процесса |
| Идентификатор | Собственный PID | Собственный TID; при этом поток относится к PID процесса |
| Стоимость создания | Обычно выше: нужно создать отдельный набор ресурсов | Обычно ниже: большая часть ресурсов уже существует в процессе |
| Переключение контекста | Обычно дороже: может потребоваться смена адресного пространства | Обычно дешевле: адресное пространство остаётся тем же |
| Последствия ошибки | Обычно ограничены процессом | Ошибка может завершить весь процесс |
| Обмен данными | Требует IPC: каналов, сокетов или явно настроенной общей памяти | Происходит через общую память и требует синхронизации |
| Владение ресурсами | Объединяет память, дескрипторы и другие ресурсы приложения | Использует ресурсы процесса, но имеет собственные стек и регистры |
| Расход памяти | Обычно выше из-за отдельного адресного пространства и структур ОС | Обычно ниже, но каждому потоку всё равно нужны стек и служебные структуры |

## Создание процесса: fork() и exec()

В Unix-like системах есть только **один** способ создать процесс — `fork()`. Он создаёт **копию** существующего процесса:

```c
pid_t pid = fork();
if (pid == 0) {
    // Внутри child процесса
    // Всё то же что у parent, но pid = 0 здесь
} else if (pid > 0) {
    // Внутри parent процесса
    // pid = PID нового child
} else {
    // Ошибка
}
```

После fork:
- Child наследует **копию** всей памяти parent'а (благодаря COW — копируется лениво, см. [05-virtual-memory-and-paging.md](./05-virtual-memory-and-paging.md))
- Child наследует копии open file descriptors
- Child имеет свой PID, parent — свой
- Оба продолжают выполняться **с следующей инструкции после fork()** (но в разных PID)

### exec()

Чтобы запустить **другую** программу, после fork делается `exec()` — он **заменяет** содержимое процесса новой программой:

```c
pid_t pid = fork();
if (pid == 0) {
    // Заменить себя на /usr/bin/ls
    execvp("/usr/bin/ls", argv);
    // Если execvp удался — этот код уже НЕ выполнится
}
// Parent ждёт child
waitpid(pid, &status, 0);
```

Это паттерн "fork+exec" — стандартный способ запустить новую программу. Shell делает именно это для каждой команды.

В Go:
```go
cmd := exec.Command("/usr/bin/ls", "-la")
cmd.Run()  // под капотом — fork+exec
```

### Если бы не было fork

В Windows нет fork — используется `CreateProcess()`, который сразу создаёт процесс с другой программой. Это проще архитектурно. Но **fork+exec гибче**: между ними можно настроить пайпы, поменять environment, установить limits, и т.д.

### Тонкости fork

- **Только текущий thread "переходит" в child.** Если в parent было 10 threads, в child останется только тот, который сделал fork(). Остальные просто исчезают вместе с их данными — что часто приводит к проблемам (locked mutex'ы в never-running threads, и т.д.).
- **Для этого fork+exec обычно делают сразу.** Если планируется работать после fork **без** exec — лучше избегать многопоточного fork.
- **Async-safe functions only between fork and exec.** Большинство стандартных функций НЕ безопасно вызывать в child до exec.

## Создание потока: clone() в Linux

В Linux нет специального syscall для потоков. Есть **`clone()`** — обобщение fork, позволяющее точно контролировать что разделять с родителем.

```c
clone(flags, stack, ...)
```

Через flags указывается что разделить:
- `CLONE_VM` — общая память
- `CLONE_FILES` — общие file descriptors
- `CLONE_FS` — общая working directory
- `CLONE_SIGHAND` — общие signal handlers
- `CLONE_THREAD` — это thread того же процесса (TID, не PID)
- `CLONE_NEWNS`, `CLONE_NEWPID`, etc. — namespaces для контейнеров

**Fork** = clone без всех CLONE_* флагов (всё дублируется).

**Thread** = clone со всеми CLONE_* флагами (всё разделено).

**Контейнер** = clone с CLONE_NEW* флагами (новые namespaces).

То есть в Linux fork, threads, и контейнеры — варианты одного и того же syscall'а. Очень элегантно.

В библиотеках:
- `pthread_create()` (C) — высокоуровневая обёртка над clone() для threads
- `clone()` напрямую — для специфических задач (контейнеры через runc используют clone)

В Go:
- `go func() { ... }()` — создаёт **goroutine**, не OS thread (см. ниже)
- Runtime сам управляет OS threads под капотом

## Режим ядра и пользовательский режим

CPU имеет два (на x86 фактически 4 кольца, но обычно используются 2) режима выполнения:

**User mode (ring 3):**
- Программы пользователя
- НЕ имеет прямого доступа к hardware
- НЕ может выполнять привилегированные инструкции (`HLT`, `CLI`, изменение page tables, etc.)
- Доступ к памяти — только к виртуальному пространству **своего процесса**
- Если попытается сделать что-то запрещённое → CPU exception → kernel убивает процесс

**Kernel mode (ring 0):**
- Ядро OS, драйверы
- Полный доступ ко всему hardware
- Может выполнять любые инструкции
- Доступ ко всей памяти, включая других процессов

```
┌─── Kernel space (ring 0) ────────┐
│   Scheduler, FS, network stack,   │
│   drivers, page tables, etc.       │
├──────────────────────────────────┤
│         Syscall boundary           │  ← переход через специальный механизм
├──────────────────────────────────┤
│   User space (ring 3)              │
│   ┌─────────┐  ┌─────────┐         │
│   │Process A│  │Process B│ ...     │
│   └─────────┘  └─────────┘         │
└──────────────────────────────────┘
```

### Зачем нужны два режима

Защита. Без них любая программа могла бы:
- Прочитать память других процессов (включая пароли)
- Сбить page tables (положить весь компьютер)
- Прямо общаться с hardware (диск, сеть) — обходя security

Kernel — единственный "доверенный" слой, через который всё проходит. Все взаимодействия user-space программ с hardware и с другими процессами — через kernel.

## Системные вызовы: переход между режимами

Программа хочет открыть файл, послать сетевой пакет, выделить память — это всё операции, требующие kernel. Способ запросить услугу у ядра — **syscall** (system call).

```
User program:
   read(fd, buf, 4096)
            ↓
   Setup arguments in registers
            ↓
   SYSCALL instruction (x86_64) или INT 0x80 (старый x86)
            ↓
   CPU mode: User → Kernel
            ↓
   Kernel: dispatch к функции sys_read
            ↓
   Read data from file (actual I/O if needed)
            ↓
   Set return value in register
            ↓
   SYSRET instruction
            ↓
   CPU mode: Kernel → User
            ↓
User program: continue
```

### Стоимость syscall

Базовая стоимость на современных Intel/AMD: ~100-500 нс. После Spectre/Meltdown mitigations (KPTI) — увеличилась в 1.5-3 раза.

Для backend это значит: **сотни тысяч syscall'ов в секунду — нормально, миллионы — потолок**. Поэтому:
- Buffered I/O > unbuffered (один большой syscall vs много мелких)
- `bufio.Reader` в Go буферизует чтение из net.Conn
- HTTP keep-alive — много запросов через один TCP connection

### Какие операции — syscall

В Go:
- `os.Open`, `os.Read`, `os.Write` — syscalls
- `net.Dial`, `Read`/`Write` на сокет — syscalls
- `time.Now()` — syscall на старых системах, но в Linux обычно через `vDSO` (без перехода в kernel)
- `make([]byte, ...)` — может вызвать syscall (mmap для большой памяти), но мелкие — нет
- `mutex.Lock()` — обычно НЕ syscall (atomic CAS в user space), только при contention — syscall (futex для sleep)
- `runtime.Gosched()` — не syscall, передача управления внутри Go runtime

### vDSO — syscall без перехода в kernel

Некоторые syscall'ы (time, getpid) Linux экспонирует через специальный shared object `vDSO`, mapped в каждый процесс. Программа "делает syscall", но фактически выполняется код в user-space, который читает данные kernel'а через shared memory.

Это даёт **`time.Now()` за ~25 нс** в Go вместо ~500 нс честного syscall.

## task_struct в Linux

В ядре Linux каждый process/thread представлен структурой `task_struct`. Это огромная struct с сотнями полей:

```c
struct task_struct {
    pid_t pid;
    pid_t tgid;          // Thread Group ID — это PID процесса для thread'ов
    struct task_struct *parent;
    struct mm_struct *mm;        // Memory management (page tables)
    struct files_struct *files;  // File descriptors
    struct fs_struct *fs;        // Filesystem info (cwd, etc.)
    struct signal_struct *signal;
    int state;                    // RUNNING, INTERRUPTIBLE, ZOMBIE, etc.
    // ... сотни полей
};
```

**Ключевые поля:**
- `pid` — TID (yes, в kernel это всегда называется PID, но для thread'ов — это TID)
- `tgid` — Thread Group ID — это и есть PID процесса с user point of view
- `mm` — указатель на структуру памяти. **Threads** одного процесса имеют **тот же** `mm`.

### State машина процесса

```
            ┌─ TASK_RUNNING (executing or runnable)
            │
new ────────┼─ TASK_INTERRUPTIBLE (sleeping, can be woken by signal)
            │
            ├─ TASK_UNINTERRUPTIBLE (sleeping in kernel, e.g., disk I/O)
            │
            ├─ TASK_STOPPED (SIGSTOP)
            │
            └─ TASK_ZOMBIE (process exited, waiting for parent to read exit code)
```

В `ps` и `top` эти состояния видны в столбце `STAT`:
- `R` — running
- `S` — interruptible sleep
- `D` — uninterruptible sleep (часто signals to disk I/O issue)
- `Z` — zombie
- `T` — stopped

### Zombie процессы

Когда процесс завершается (`exit()`), его `task_struct` остаётся в kernel до тех пор пока parent не прочитает exit code через `wait()`. Если parent не делает wait — child становится "zombie".

Zombies не потребляют CPU/memory, но занимают place в process table. Если zombie много (например, бесконечно spawn'ишь процессы и не делаешь wait) — таблица процессов забивается, и новый fork() будет fail'ить.

В Go-сервисах в Docker процесс становится PID 1, и если он не reap'ит детей правильно, накапливаются zombie. Решение — использовать `tini` как init в контейнере, или Go-библиотеку для reaping.

## Goroutine, потоки и процессы

```
┌──────────── Process ────────────┐
│                                  │
│  ┌──── OS Thread 1 ─────┐        │
│  │   ┌─ Goroutine A    │        │
│  │   ├─ Goroutine B    │        │
│  │   └─ Goroutine C    │ ← мультиплекс
│  └──────────────────────┘        │
│                                  │
│  ┌──── OS Thread 2 ─────┐        │
│  │   ┌─ Goroutine D    │        │
│  │   └─ Goroutine E    │        │
│  └──────────────────────┘        │
│                                  │
└──────────────────────────────────┘
```

**Goroutine** — это **user-level thread**, управляемый Go runtime. Не OS thread.

| Свойство | Process | OS Thread | Goroutine |
|---|---|---|---|
| Создание | дороже: отдельное адресное пространство и ресурсы | легче: ресурсы процесса уже есть | обычно самое дешёвое: объект создаёт runtime |
| Память | отдельное адресное пространство и таблицы страниц | отдельный стек и контекст, остальное общее | небольшой растущий стек и метаданные runtime |
| Количество на машине | ограничено `pid_max`, памятью и лимитами ОС | ограничено памятью, стеками и лимитами ОС | ограничено памятью, нагрузкой и возможностями runtime |
| Управление | OS scheduler | OS scheduler | Go runtime scheduler |
| Переключение контекста | выполняет ядро; стоимость зависит от ОС и адресных пространств | выполняет ядро; стоимость зависит от CPU и нагрузки | выполняет runtime; обычно дешевле, но измеряется на конкретной версии Go |

### Как Go runtime использует OS threads

Go runtime использует модель **M:N scheduling**:

- **G** (goroutines) — пользовательские задачи, тысячи или миллионы
- **M** (machines) — OS threads, обычно сколько-то
- **P** (processors) — логические «слоты» исполнения; их число равно
  `GOMAXPROCS`. До Go 1.25 стандартное значение было числом доступных логических
  CPU; в Go 1.25+ на Linux оно также учитывает CPU limit cgroup, если
  `GOMAXPROCS` не задан явно.

Goroutines выполняются на P. Каждый P привязан к одному M. Если goroutine блокируется (syscall, channel), runtime может **переместить** другие goroutines с этого P на другой M, чтобы продолжить работу.

Подробнее: [01-go-core/runtime-scheduler/01-scheduler-and-preemption.md](../../01-go-core/runtime-scheduler/01-scheduler-and-preemption.md) и [07-context-switching-and-scheduling.md](./07-context-switching-and-scheduling.md).

### Почему goroutines дешевле

- **Стек растёт по необходимости**, начиная примерно с 2 КиБ. Потоку ОС адресное пространство под стек резервируется сразу, обычно 8 МиБ.
- **Переключение не требует ядра ОС.** Go runtime меняет goroutine сам, без системного вызова: достаточно сохранить и восстановить нужные регистры. Это заметно дешевле переключения контекста ядром, но конкретное число зависит от версии Go и нагрузки и измеряется бенчмарком.
- **Потоки создаются по мере надобности**, а не заранее под каждую goroutine.

### Когда Go использует OS threads

- Runtime создаёт и переиспользует системные потоки по потребности; их число не
  обязано в точности совпасть с `GOMAXPROCS` в момент запуска.
- При блокирующем syscall — Go может запустить **новый thread** чтобы продолжить работу остальных goroutines
- При вызове CGO — Go pinning'ует goroutine к thread'у (LockOSThread под капотом)

В `runtime/debug.SetMaxThreads()` можно увидеть лимит — по умолчанию 10000. Если Go-программа создаёт больше — это знак что что-то не так (например, много блокирующих CGO вызовов).

## Когда Go создаёт системный поток

Понимание помогает диагностировать "почему мой Go-сервис вдруг использует 100+ OS threads".

**1. Число системных потоков не равно `GOMAXPROCS`.**
`GOMAXPROCS` ограничивает число P, то есть параллельное выполнение Go-кода. На
8 логических CPU runtime может использовать до восьми P, но реальное число
системных потоков зависит от блокировок, сборщика мусора, сетевого poller и
другой работы runtime.

**2. Когда goroutine делает блокирующий syscall.**
Например, `os.File.Read()` на медленный диск — syscall блокируется. Go runtime отвязывает thread (M) от P, оставляя его в syscall'е, и берёт другой thread (или создаёт новый) чтобы взять P и продолжить работу остальных goroutines.

Когда syscall завершается, thread может снова получить P, или остаться в "свободном пуле".

**3. CGO calls.**
Каждый вызов CGO блокирует thread (Go runtime не может управлять C-кодом). При 100 параллельных CGO calls получается 100 OS threads.

**4. `runtime.LockOSThread()`.**
Если goroutine "залочила" thread (см. ниже) — этот thread не может быть использован для других goroutines.

**5. Network polling.**
Go использует один (или несколько) thread'ов для `epoll`/`kqueue` (net poller). На Linux обычно один.

### Сколько threads "норма"

Для типичного Go-сервиса:
- Stateless API сервис: ~`GOMAXPROCS + 1-3 threads` (CPU + epoll + GC)
- С блокирующими syscalls (тяжёлый I/O): `GOMAXPROCS + N`, где N — peak параллельных блокирующих операций
- С CGO: `GOMAXPROCS + параллельных CGO calls`
- С `runtime.LockOSThread`: + locked goroutines

Сотни или тысячи системных потоков в Go-приложении — аномалия, которая требует объяснения. Частая причина — синхронные вызовы CGO.

## LockOSThread и привязка к потоку

Иногда нужно чтобы goroutine **всегда** выполнялась на **одном и том же** OS thread'е:

```go
import "runtime"

go func() {
    runtime.LockOSThread()
    defer runtime.UnlockOSThread()

    // Этот код всегда выполняется на одном thread'е
    // ...
}()
```

### Зачем нужно

**1. Thread-local state в C-библиотеках.**
Многие C-библиотеки хранят данные в thread-local storage (TLS), привязанные к pthread. Если Go-goroutine "прыгает" между threads — TLS будет разный.

**2. OpenGL и GUI frameworks.**
Большинство GUI требуют чтобы все calls шли с "main thread". Goroutine должна быть locked к OS main thread.

**3. Signal handlers.**
Если goroutine хочет обрабатывать signal сама — нужно lock'нуть, иначе signal придёт неизвестному thread'у.

**4. Process-level ops.**
Например, `setuid()` в Linux работает per-thread на новых kernel'ах. Чтобы изменить UID для всего процесса — нужно lock thread (или сделать в каждом thread).

### Стоимость

- Locked thread не может быть использован для других goroutines — это "потерянный" М для Go scheduler
- При большом числе locked goroutines Go runtime создаст много OS threads
- При `Lock` thread "становится постоянным" — не возвращается в пул

### main goroutine

Goroutine, выполняющая `func main()`, по умолчанию **не** привязана к главному потоку ОС. Если привязка нужна, например для GUI, `runtime.LockOSThread()` вызывают в `init()` пакета, который импортируется первым.

## Практические выводы

**1. Goroutine — это не поток ОС.**
Различать их важно и в обсуждении, и в диагностике. Десятки тысяч goroutine могут быть нормой, если они в
основном ждут I/O. То же число системных потоков не автоматически ошибка, но
требует объяснения: стоит проверить CGO, блокирующие системные вызовы, `LockOSThread`,
лимиты ОС и потребление памяти стека.

**2. Goroutine можно создавать свободно, но не бесконтрольно.**
Goroutine обычно заметно дешевле системного потока, но не бесплатна. Если
структура задачи естественно конкурентна, ограничивай параллелизм внешних
вызовов и измеряй память, задержки и число ожидающих задач, а не выбирай число
goroutine по условной цене создания.

**3. Аварийное завершение одной goroutine завершает весь процесс.**
В отличие от процессов, потоки одного процесса не изолированы. `panic` в goroutine без `recover` валит приложение целиком. Если часть работы должна падать изолированно, её выносят в отдельный процесс через `exec.Command`.

**4. Контейнер — это процесс.**
Контейнер — это один или несколько процессов с изоляцией через namespaces и
лимитами cgroup; это не отдельный тип процесса. Если Go-сервис в контейнере
запущен как PID 1, он должен корректно обрабатывать сигналы и забирать
завершившихся потомков, например после `exec.Command`.

**5. `ulimit -u` и max processes.**
Лимит числа процессов и потоков задаётся политикой ОС, PAM, systemd или
контейнерным окружением; универсального значения по умолчанию нет. Для
Go-сервиса с большим объёмом CGO или внешних команд сначала измерь текущие
лимиты и причину роста, а не повышай их вслепую.

**6. Понимай разницу process model и thread model.**
PostgreSQL forks процесс на каждое соединение — изоляция и стабильность. Nginx использует workers + threads — эффективность. Go — горутины + thread pool — оба плюса.

**7. `/proc` заменяет отладчик во многих ситуациях.**
`/proc/PID/status`, `/proc/PID/maps` и `/proc/PID/task/` показывают состояние процесса, карту памяти, список потоков и открытые дескрипторы без остановки приложения.

**8. Число системных вызовов имеет значение, но не фиксированную цену.**
Переход в ядро стоит времени, однако задержка сильно зависит от операции: `read` может завершиться мгновенно из страничного кэша или ждать устройство. Приписывать каждому вызову фиксированные 100–500 нс и обязательную очистку кэшей неверно. Практический приём прежний: буферизовать ввод-вывод, использовать keep-alive для TCP и объединять операции там, где это уменьшает реальное число обращений.

## Типичные заблуждения

- **«Goroutine — это лёгкий поток ОС».** Ядро о goroutine ничего не знает. Оно планирует только потоки ОС, а goroutine распределяет по ним Go runtime.
- **«Число системных потоков равно `GOMAXPROCS`».** `GOMAXPROCS` ограничивает параллельное выполнение Go-кода. Реальное число потоков зависит от блокирующих системных вызовов, CGO, сборщика мусора и сетевого poller.
- **«`fork` копирует память, поэтому он дорогой».** Копирование при записи откладывает копирование до первого изменения страницы, поэтому сам форк дёшев.
- **«После `fork` в потомке остаются все потоки».** Остаётся только тот поток, который вызвал `fork`. Именно поэтому за форком в многопоточной программе почти всегда сразу следует `exec`.
- **«Потоки и процессы в Linux — разные механизмы».** И то и другое создаётся системным вызовом `clone`; разница только в том, какие ресурсы указано разделять с родителем.
- **«Контейнер — это лёгкая виртуальная машина».** Контейнер — обычный процесс с изоляцией через пространства имён и ограничениями через cgroup. Отдельного ядра ОС у него нет.
- **«`mutex.Lock()` — это системный вызов».** Быстрый путь выполняется в пространстве пользователя через атомарную операцию. К ядру обращаются только при конкуренции, чтобы усыпить поток.

## Interview-ready answer

**1. Чем процесс отличается от потока?**

Процесс — контейнер ресурсов: виртуальное адресное пространство, таблица дескрипторов, права, переменные окружения. Поток — исполнитель кода внутри процесса: у него свои стек, регистры и состояние выполнения, а память и дескрипторы он разделяет с другими потоками того же процесса.

**2. Как создаются процессы и потоки в Linux?**

Оба создаются системным вызовом `clone`. Если ничего не разделяется — получается процесс, как при `fork`. Если разделяются адресное пространство, дескрипторы и обработчики сигналов — получается поток. Отдельные флаги `CLONE_NEW*` создают пространства имён, на которых построены контейнеры.

**3. Что делает `fork` и почему он дёшев?**

Он создаёт копию текущего процесса. Память при этом физически не копируется: страницы отображаются в оба процесса только для чтения, а настоящая копия создаётся при первой записи. Это копирование при записи.

**4. Где здесь goroutine?**

Это третий уровень. Go runtime мультиплексирует множество goroutine на меньшем числе потоков ОС: goroutine планирует runtime, потоки планирует ядро. Ядро отдельные goroutine не видит.

**5. Почему goroutine дешевле потока ОС?**

Её стек начинается примерно с 2 КиБ и растёт по необходимости, тогда как потоку резервируется около 8 МиБ. Переключение между goroutine делает runtime в пространстве пользователя, без перехода в ядро.

**6. Когда Go создаёт дополнительные системные потоки?**

При блокирующем системном вызове, при вызовах CGO, при `runtime.LockOSThread` и для внутренних задач runtime. Поэтому число потоков не совпадает с `GOMAXPROCS`, а его резкий рост обычно указывает на блокирующий CGO или синхронный ввод-вывод.

**7. Зачем нужен `runtime.LockOSThread`?**

Чтобы goroutine всегда выполнялась на одном потоке ОС. Это нужно, когда состояние живёт в потоке: thread-local storage в C-библиотеках, GUI-фреймворки, обработка сигналов, операции уровня потока вроде `setuid`. Цена — этот поток больше не обслуживает другие goroutine.

**8. Что происходит с Go-сервисом как PID 1 в контейнере?**

Он получает обязанности init-процесса: корректно обрабатывать сигналы завершения и забирать завершившихся потомков. Иначе после `exec.Command` в таблице процессов накапливаются зомби, а `SIGTERM` может не привести к аккуратной остановке.
