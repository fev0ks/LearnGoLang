# Иерархия памяти: от регистра до диска

Компьютер не имеет "одной памяти". Внутри — пирамида из разных видов хранения, у каждого свой компромисс между **скоростью** и **объёмом/стоимостью**. Чем ближе к CPU — тем быстрее, дороже и меньше. Эта пирамида определяет почему один код работает 1 наносекунду, а другой — 10 миллисекунд за то же логическое действие.

Senior backend должен видеть эту иерархию: знать порядки величин, понимать почему `var x int` иногда быстрее `*x`, почему `[]byte` иногда быстрее `[]string`, почему БД на NVMe в 100 раз быстрее БД на HDD.

## Простая аналогия

Представь повара в ресторане.

- **Регистры** — нож в руке. Доступ мгновенный, но в руке умещается одна вещь.
- **L1 cache** — разделочная доска. Несколько ингредиентов сразу, поворот головы.
- **L2/L3 cache** — стол рабочего места. Десятки штук, два шага.
- **RAM** — холодильник. Сотни штук, надо встать и подойти.
- **SSD** — склад в подвале. Тысячи штук, надо спуститься.
- **HDD** — соседнее здание. Десятки тысяч, нужна машина.
- **Сеть** — поставка из другого города.

Хороший повар не ходит в подвал за каждой щепоткой соли — он держит часто нужное под рукой. **Кэширование** на CPU — это автоматическая версия того же поведения.

## Пирамида памяти

```
              Скорость              Объём             Стоимость
                ↑                     ↑                   ↑
 ┌────────────┐ │ < 1 ns              │ < 1 KB            │
 │ Registers  │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~1 ns               │ 32-64 KB / ядро   │
 │   L1 cache │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~3-5 ns             │ 256 KB-1 MB/ядро  │
 │   L2 cache │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~10-20 ns           │ 4-32 MB / чип     │
 │   L3 cache │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~80-100 ns          │ 16-256 GB         │
 │   DRAM     │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~50-100 μs (NVMe)   │ 1-10 TB           │
 │    SSD     │ │ ~100-200 μs (SATA)  │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~5-10 ms            │ 1-20 TB           │
 │    HDD     │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ 0.5 ms (same DC)    │ практически       │
 │  Network   │ │ 100+ ms (cross-     │  безграничный     │
 │            │ │  continent)         │                   │
 └────────────┘ ↓                     ↓                   ↓
              Медленнее         Больше              Дешевле
```

Каждый уровень примерно в 10-100 раз медленнее предыдущего. CPU не хочет ждать. Поэтому он держит "горячие" данные ближе и подгружает следующие уровни upfront.

## Latency numbers, которые нужно помнить

Знаменитый список Jeff Dean (Google) "Latency Numbers Every Programmer Should Know" — must-know для senior:

| Операция | Время | В единицах L1 |
|---|---|---|
| L1 cache reference | **0.5 ns** | 1 |
| Branch mispredict | 5 ns | 10 |
| L2 cache reference | 7 ns | 14 |
| Mutex lock/unlock | 25 ns | 50 |
| Main memory reference | **100 ns** | 200 |
| Compress 1KB with Zstd | 2 μs | 4 000 |
| Send 1KB over 1 Gbps network | 10 μs | 20 000 |
| Read 4KB from SSD | **150 μs** | 300 000 |
| Read 1 MB from memory | 250 μs | 500 000 |
| Round trip in same datacenter | 500 μs | 1 000 000 |
| Read 1 MB from SSD | 1 ms | 2 000 000 |
| Disk seek (HDD) | **10 ms** | 20 000 000 |
| Read 1 MB from disk (HDD) | 20 ms | 40 000 000 |
| Send packet CA → NL → CA | **150 ms** | 300 000 000 |

**Что нужно вынести в голову:**
- L1 — 0.5 нс
- RAM — 100 нс (в 200 раз медленнее L1)
- SSD — 100 мкс (в 1000 раз медленнее RAM)
- HDD seek — 10 мс (в 100 раз медленнее SSD)
- Cross-DC — 500 мкс (в 5000 раз медленнее RAM)
- Cross-continent — 150 мс (просто очень долго)

Чтобы было нагляднее — масштабируем так, чтобы L1 = 1 секунде:

```
L1 cache:          1 секунда
L2 cache:          14 секунд
RAM:               3 минуты 20 секунд
SSD seek:          3.5 дня
Round trip DC:     11.5 дней
HDD seek:          7.5 месяцев
Cross-continent:   9 лет
```

То есть когда программа делает SQL-запрос в БД через сеть — это с точки зрения CPU **поход за чем-то в другой город**. Поэтому **меньше походов** > "оптимизация цикла внутри" в 99% backend случаев.

## Регистры CPU

Самая быстрая память — внутри ядра, прямо рядом с ALU (arithmetic logic unit).

**На x86_64:** 16 general-purpose 64-bit регистров (RAX, RBX, ..., R15) + ~32 SIMD регистра (XMM/YMM/ZMM) для векторных операций + регистры FPU.

**Размер:** буквально несколько байт. Очень мало.

**Доступ:** 0 циклов — операнды берутся прямо в ALU. Невозможно "обратиться" к регистру явно из Go — компилятор сам решает что в регистрах, что в стеке.

Программист не видит регистры напрямую — но видит их **эффект**: если переменная "горячая" и компилятор смог удержать её в регистре, цикл работает в 10-100 раз быстрее, чем если та же переменная — в памяти.

```go
// Компилятор обычно держит i в регистре
for i := 0; i < n; i++ {
    sum += data[i]
}

// А если *p — указатель, который компилятор не может оптимизировать?
// Каждое обращение — потенциальное чтение из memory.
for i := 0; i < n; i++ {
    *p += data[i]  // *p может уйти в L1, не в регистр
}
```

**Escape analysis** в Go частично определяет — попадёт ли переменная в регистр или нет. См. [01-go-core/memory-internals/03-escape-analysis.md](../../01-go-core/memory-internals/03-escape-analysis.md).

## Кэши CPU: L1, L2, L3

Если регистр — 1 байт под рукой, а RAM — 100 нс (вечность), то нужны промежуточные уровни. Это и есть CPU cache: маленькая быстрая память **внутри** чипа.

### Иерархия cache на типичном x86 сервере

```
┌─ CPU package ─────────────────────────────────┐
│                                                │
│  ┌─ Core 0 ───┐  ┌─ Core 1 ───┐    ...        │
│  │ Registers  │  │ Registers  │                │
│  │  L1d  L1i  │  │  L1d  L1i  │  (per-core)   │
│  │     L2     │  │     L2     │  (per-core)   │
│  └────────────┘  └────────────┘                │
│                                                │
│            ┌─────  L3  ─────┐                  │
│            │  shared across │                  │
│            │   all cores    │                  │
│            └────────────────┘                  │
└────────────────────────────────────────────────┘
                       ↓
                   Memory bus
                       ↓
                ┌──────────────┐
                │     DRAM     │
                └──────────────┘
```

**L1** — самый близкий. Разделён на L1d (data) и L1i (instructions). 32-64 KB на ядро. ~1 нс.

**L2** — побольше, чуть медленнее. 256 KB — 1 MB на ядро. ~3-10 нс.

**L3** — большой, общий для всех ядер чипа. 4-32 MB на чип. ~10-20 нс.

Деление data/instructions на L1 — потому что CPU одновременно читает и инструкции (что выполнять) и данные (с чем работать). Раздельные кэши = меньше конфликтов.

### Cache line — единица работы кэша

CPU не загружает один байт — он работает блоками по **64 байта** (на x86 и большинстве ARM). Эти блоки называются **cache lines**.

Если код читает байт по адресу X, CPU вытащит всю линию [X-padding, X+padding] в кэш. Соседние 63 байта окажутся "бесплатно" в L1.

Это и есть основа **пространственной локальности** (см. ниже).

Подробнее о cache line и связанных эффектах (false sharing, MESI) — в [03-cache-coherence-and-mesi.md](./03-cache-coherence-and-mesi.md).

### Простой mental model

```go
// "Sum 1 MB array"
//
// Если массив не в кэше: ~16384 cache misses
//   16384 * 100 нс = ~1.6 мс
//
// Если массив помещается в L2 после первого прохода: следующие проходы
//   16384 * 3 нс = ~50 мкс — в 30 раз быстрее
//
// Поэтому повторное использование данных в горячем цикле = фундаментальная оптимизация
```

## DRAM — оперативная память

DRAM (Dynamic RAM) — то что в slot'ах материнки. "Память" в обыденном смысле.

**Латенси:** ~80-100 нс. В 200 раз медленнее L1.

**Throughput:** на современных DDR4/DDR5 — десятки GB/s на канал, несколько каналов = 50-200 GB/s суммарно.

**Размер:** 16 GB на ноутбуке, 64-256 GB на сервере, до терабайт на больших машинах.

### Почему DRAM так медленный

Технически DRAM — это **миллиарды конденсаторов**. Каждый бит — заряд на конденсаторе, который **разряжается** со временем (отсюда "dynamic"). Чтобы не потерять данные, контроллер периодически перезаряжает (refresh) — это занимает время.

Чтение байта:
1. Активировать строку матрицы (row activation) — несколько наносекунд
2. Считать колонку из этой строки
3. Усилить сигнал (он маленький)
4. Передать через шину к CPU

Поэтому 100 нс — это не "медленная электроника", это физика конденсаторов и сигналов.

### DRAM устройство (кратко)

```
DIMM (планка памяти)
  └── Ranks (логические наборы чипов)
       └── Banks (параллельно доступные)
            └── Rows × Columns (матрица)
```

Контроллер памяти держит несколько banks "открытыми" одновременно — это позволяет читать из одного банка пока другой ещё активируется. Так получается параллелизм.

**Memory channels:** современные CPU имеют 2-12 каналов памяти, работающих параллельно. 4-канальная DDR5-5600 = теоретически 180 GB/s.

### Practical: NUMA

На многосокетных серверах (2+ CPU чипа) каждый CPU имеет свою "локальную" RAM. Доступ к "чужой" RAM — через межсокетный link, медленнее. Это **NUMA** (Non-Uniform Memory Access).

Для большинства Go-сервисов это прозрачно. Для высокопроизводительных систем — приходится pinning процесса к узлу и аллоцировать память на нём.

## SSD vs HDD

После RAM — постоянное хранилище. Сюда улетает то, что не помещается в RAM, и здесь живут БД (хотя горячие страницы они кэшируют в RAM).

### HDD (Hard Disk Drive)

Магнитный диск, вращается 5400-15000 RPM. Головка физически двигается.

- **Sequential read/write:** 100-200 MB/s
- **Random IOPS:** ~100-200 операций в секунду (!!!)
- **Latency:** 5-10 мс (физический seek + rotational latency)

HDD катастрофически медленный для **случайных** обращений (типичный паттерн БД). Sequential — относительно неплохо.

**Когда ещё актуально:** холодные архивы, S3 Glacier, дешёвый backup. На горячих БД — почти везде заменён SSD.

### SSD (Solid State Drive)

Flash-память, без движущихся частей.

**SATA SSD** (старый стандарт):
- ~500 MB/s
- ~100k IOPS
- ~100-200 мкс latency

**NVMe SSD** (PCIe):
- 3-7 GB/s (PCIe 4.0)
- 500k-1M IOPS
- 50-100 мкс latency

NVMe — на порядок быстрее SATA SSD. Современные production-БД обычно на NVMe.

### Особенности flash

SSD не "пишет в место" — она пишет в **свободный блок** и помечает старый как stale. Периодически garbage collector чистит. Это создаёт:

- **Write amplification:** одна логическая запись = несколько физических
- **Износ:** каждая ячейка выдерживает ограниченное число записей (10k-100k для consumer, 1M+ для enterprise)
- **Latency spikes:** во время фоновой GC SSD может тормозить

В backend это видно как "p99 latency на запись внезапно подскакивает" — это GC на SSD сработал.

## Сеть как часть иерархии

Сетевые задержки доминируют над всем остальным в распределённых системах.

| Дистанция | RTT (round-trip time) |
|---|---|
| Within rack | ~0.1 мс |
| Within datacenter | ~0.5 мс |
| Within region (e.g. eu-west-1 ↔ eu-west-2) | ~5-20 мс |
| Cross-continent | 100-200 мс |
| Satellite | 500+ мс |

**Что это значит для backend:**
- Один лишний межсервисный вызов = +0.5 мс
- БД-запрос в RDS в той же AZ = ~1 мс
- БД-запрос в другую region = 30-50 мс
- Запрос к Stripe API из Европы = 100+ мс

Поэтому в архитектуре **count of round trips** > "оптимизация байтов". 10 параллельных запросов = 1 RTT. 10 последовательных = 10 RTT. В 10 раз медленнее.

## Почему кэш работает: локальность

Кэширование работает не магически, а потому что **реальные программы имеют два свойства**:

### Temporal locality (временная)

Если обратился к данным сейчас — скорее всего обратишься снова в ближайшее время.

```go
// counter обновляется в каждой итерации
for _, item := range items {
    counter += item.value  // обращение к counter каждый раз
}
// → counter живёт в регистре или L1, всё быстро
```

### Spatial locality (пространственная)

Если обратился к адресу X — скорее всего обратишься к X+1, X+2, ... в ближайшее время.

```go
// Линейный обход массива — идеальная spatial locality
for i := 0; i < len(arr); i++ {
    sum += arr[i]
}
// → каждая cache line (64 байта = 8 int64) подгружается один раз и используется 8 раз
```

Это работает потому что cache загружает **линиями**, не байтами. Один miss → 64 байта в L1 → 7 hit'ов подряд "бесплатно".

### Anti-pattern: cache-unfriendly доступ

```go
// Linked list — катастрофа для cache
type Node struct {
    value int
    next  *Node
}

for n := head; n != nil; n = n.next {
    sum += n.value  // каждый узел может быть где угодно в памяти
}
// → каждый доступ — потенциальный cache miss
// → может быть в 10-50 раз медленнее массива той же длины
```

Поэтому Go-сообщество предпочитает **slice'ы** linked list'ам: данные лежат подряд, идеально для cache.

### Random vs sequential доступ

```go
// Sequential: ~1 нс на элемент после прогрева кэша
for i := 0; i < N; i++ {
    sum += arr[i]
}

// Random: каждый доступ = cache miss = ~100 нс
indices := randomPermutation(N)
for _, i := range indices {
    sum += arr[i]
}
// Тот же массив, та же сумма, в 50-100 раз медленнее
```

Этот эффект — фундамент для дизайна структур данных:
- BTree, B+Tree в БД оптимизированы под чтение страницами с диска/SSD
- Slice вместо linked list когда нужен обход
- Struct of Arrays (SoA) вместо Array of Structs (AoS) для горячих циклов

## Где живут переменные Go в этой иерархии

```go
func process(req *Request) Response {
    var sum int64       // ← регистр (если компилятор смог) или стек
    items := req.Items  // ← slice header в регистре, backing array в куче или стеке

    for i, item := range items {  // i — регистр, item — копия
        sum += item.Price          // item.Price в регистре или L1
    }

    return Response{Total: sum}    // составляется в регистрах/стеке
}
```

**Иерархия в Go runtime:**

| Где | Что |
|---|---|
| **Registers** | "Горячие" локальные переменные (счётчики циклов, частые операнды) |
| **Stack** | Локальные переменные, не сбежавшие в heap. Очень быстро. |
| **L1/L2 cache** | Недавно использованные данные (автоматически, без участия программиста) |
| **Heap (in DRAM)** | Объекты, escape'нувшие в кучу. GC их освобождает. |
| **Mmap'd memory** | Файлы, замапленные в адресное пространство процесса |
| **Swap (disk)** | Если RAM не хватает — kernel вытесняет страницы. Очень плохо для latency. |

Подробнее про stack vs heap, escape analysis, GC — в [01-go-core/memory-internals/](../../01-go-core/memory-internals/).

**Связка с эскейпами:**

```go
// x не escape — стек. Быстро.
func foo() {
    var x int
    x = compute()
    use(x)
}

// x escape (вернули указатель) — heap. Медленнее: GC, плюс возможно cache miss.
func bar() *int {
    var x int
    x = compute()
    return &x  // ← заставляет аллоцировать в куче
}
```

## Практические выводы для backend

**1. Думай порядками величин, не процентами.**
Оптимизация tight loop'а на 10% — мелочь. Уменьшение количества DB-запросов с 100 до 1 — × 100. Кэш в Redis вместо DB — × 100. Локальный кэш в памяти вместо Redis — ещё × 100.

**2. Минимизируй network round trips.**
Один JOIN вместо 10 SELECT'ов. Bulk INSERT вместо ста отдельных. gRPC streaming вместо ста unary calls.

**3. Используй cache-friendly структуры.**
Slice > linked list для большинства случаев. Struct'ы с горячими полями в начале (cache line). Не разбрасывай горячий код по куче через указатели если не нужно.

**4. Готовь данные к доступу.**
Если знаешь паттерн доступа — отсортируй заранее, денормализуй, прогрей кэш. Один проход по подготовленным данным — на порядок быстрее блуждания по графу указателей.

**5. Знай численные пороги.**
- RAM lookup → 100 нс — можно делать миллионы в секунду
- SSD → 100 мкс — можно делать 10 тысяч в секунду
- HTTP → 1-100 мс — десятки в секунду
- Не путай эти масштабы при capacity planning

**6. Storage matters.**
БД на HDD — приговор к p99=секунды. БД на NVMe — millisecond. Выбор storage для основной БД — одно из самых важных решений в инфраструктуре.

**7. Read amplification важна.**
Один SELECT иногда читает мегабайты с диска внутри (full table scan, неоптимальный JOIN). Запрос-секунду + EXPLAIN — часто = "читается 100x от того, что нужно".

**8. Сначала измерить, потом оптимизировать.**
pprof покажет где CPU. perf-event и `runtime.MemStats` покажет cache misses (на linux через `perf stat`). Без замеров — гадание на кофейной гуще.
