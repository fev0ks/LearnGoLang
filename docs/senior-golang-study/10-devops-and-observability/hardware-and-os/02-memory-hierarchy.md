Компьютер не имеет "одной памяти". Внутри — пирамида из разных видов хранения, у каждого свой компромисс между **скоростью** и **объёмом/стоимостью**. Чем ближе к CPU — тем быстрее, дороже и меньше. Эта пирамида определяет почему один код работает 1 наносекунду, а другой — 10 миллисекунд за то же логическое действие.

Senior backend должен видеть эту иерархию: знать порядки величин, понимать почему `var x int` иногда быстрее `*x`, почему `[]byte` иногда быстрее `[]string`, почему БД на NVMe в 100 раз быстрее БД на HDD.

## Простая аналогия

Иерархию удобно представить через работу повара в ресторане.

- **Регистры** — нож в руке. Доступ мгновенный, но в руке умещается одна вещь.
- **L1 cache** — разделочная доска. Несколько ингредиентов сразу, поворот головы.
- **L2/L3 cache** — стол рабочего места. Десятки штук, два шага.
- **RAM** — холодильник. Сотни штук, надо встать и подойти.
- **SSD** — склад в подвале. Тысячи штук, надо спуститься.
- **HDD** — соседнее здание. Десятки тысяч, нужна машина.
- **Сеть** — поставка из другого города.

Хороший повар не ходит в подвал за каждой щепоткой соли — он держит часто нужное под рукой. **Кэширование** на CPU — это автоматическая версия того же поведения.

## Пирамида памяти

```
              Скорость              Объём             Стоимость
                ↑                     ↑                   ↑
 ┌────────────┐ │ < 1 ns              │ сотни байт —      │
 │ Registers  │ │                     │ единицы KB\*      │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~1 ns               │ 32-64 KB / ядро   │
 │   L1 cache │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~4-10 ns            │ 256 KB-1 MB/ядро  │
 │   L2 cache │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~10-20 ns           │ 4-32 MB / чип     │
 │   L3 cache │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~80-100 ns          │ 16-256 GB         │
 │   DRAM     │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~50-100 μs (NVMe)   │ 1-10 TB           │
 │    SSD     │ │ ~100-200 μs (SATA)  │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ ~5-10 ms            │ 1-20 TB           │
 │    HDD     │ │                     │                   │
 └────────────┘ │                     │                   │
 ┌────────────┐ │ 0.5 ms (same DC)    │ практически       │
 │  Network   │ │ 100+ ms (cross-     │  безграничный     │
 │            │ │  continent)         │                   │
 └────────────┘ ↓                     ↓                   ↓
              Медленнее         Больше              Дешевле
```

\* Это не фиксированный размер, как у L1: он зависит от ISA и модели CPU.
Размер одного регистра, набора регистров, видимого программе, и внутреннего
physical register file процессора — разные величины; подробности ниже.

Каждый уровень примерно в 10-100 раз медленнее предыдущего. CPU не хочет ждать. Поэтому он держит "горячие" данные ближе и подгружает следующие уровни upfront.

## Ориентиры по задержкам

Ниже — классический список «Latency Numbers Every Programmer Should Know».
Он нужен **не как набор точных констант, а как шкала порядков величин**: важно
помнить, что между соседними строками разница в разы или на порядки, а не
конкретные цифры.

Числа в списке зафиксированы около 2012 года и с тех пор частично устарели —
особенно пропускная способность памяти, SSD и сети. Реальные задержки зависят
от модели CPU, NUMA-топологии, очереди устройства, размера операции и текущей
нагрузки, поэтому перед capacity planning или выводом о регрессии их нужно
измерить на своей системе.

| Операция | Время | В единицах L1 | Примечание |
|---|---|---|---|
| L1 cache reference | **0.5-1 ns** | 1 | |
| Branch mispredict | 5 ns | 10 | зависит от глубины конвейера и частоты |
| L2 cache reference | 4-10 ns | ~10 | |
| Mutex lock/unlock | 25 ns | 50 | без конкуренции |
| Main memory reference | **100 ns** | 200 | |
| Compress 1KB with Zstd | 2 μs | 4 000 | |
| Send 1KB over 1 Gbps network | 10 μs | 20 000 | на 10-25 Gbps соответственно меньше |
| Read 4KB from SSD | **50-150 μs** | ~200 000 | NVMe ближе к нижней границе |
| Read 1 MB from memory | 250 μs | 500 000 | сильно устарело: на DDR4/DDR5 это единицы-десятки мкс |
| Round trip in same datacenter | 500 μs | 1 000 000 | |
| Read 1 MB from SSD | 1 ms | 2 000 000 | на NVMe заметно быстрее |
| Disk seek (HDD) | **10 ms** | 20 000 000 | |
| Read 1 MB from disk (HDD) | 20 ms | 40 000 000 | |
| Send packet CA → NL → CA | **150 ms** | 300 000 000 | ограничено скоростью света в волокне |

Строки с пометкой «устарело» оставлены специально: этот список часто цитируют
на собеседованиях, и полезно знать и его, и то, чем он расходится с современным
железом.

**Что важно запомнить как порядок величин:**
- L1 — около 1 нс
- RAM — около 100 нс (примерно в 100 раз медленнее L1)
- SSD — около 100 мкс (примерно в 1000 раз медленнее RAM)
- HDD seek — около 10 мс (примерно в 100 раз медленнее SSD)
- Round trip внутри дата-центра — около 500 мкс
- Между континентами — около 150 мс (просто очень долго)

Чтобы было нагляднее — масштабируем так, чтобы L1 равнялся 1 секунде:

```
L1 cache:          1 секунда
L2 cache:          около 5 секунд
RAM:               около 1.5 минут
SSD:               около 1 дня
Round trip DC:     около 6 дней
HDD seek:          около 4 месяцев
Cross-continent:   около 5 лет
```

То есть сетевой SQL-запрос для CPU несоизмеримо дороже нескольких инструкций
внутри процесса. Поэтому в типичной backend-нагрузке уменьшение числа сетевых
round trip обычно важнее микрооптимизации цикла. Это не отменяет профилирование:
локальный CPU-bound путь — отдельный случай.

## Регистры CPU

Самая быстрая память — внутри ядра, прямо рядом с ALU (arithmetic logic unit).

Когда говорят о «размере регистров», легко смешать три разных ответа:

| Что измеряем | Типичный размер на x86-64 | Что это означает |
| --- | --- | --- |
| Один general-purpose register, например `RAX` | 64 бита = **8 байт** | В нём помещается `int64`, указатель или часть машинной инструкции. |
| 16 именованных general-purpose registers: `RAX` ... `R15` | `16 × 8 =` **128 байт** | Это минимальный понятный объём «обычных» регистров, доступных коду x86-64. `EAX`, `AX` и `AL` — не новые регистры, а 32-, 16- и 8-битные части `RAX`. |
| SIMD-регистры для векторных вычислений | от **256 байт** (`16 × 128-bit XMM`) до **2 КиБ** (`32 × 512-bit ZMM` с AVX-512) | Они нужны, например, чтобы одной инструкцией обработать несколько чисел. `XMM` и `YMM` — младшие части `ZMM`, поэтому складывать объёмы `XMM + YMM + ZMM` нельзя. |

Для грубой оценки на x86-64 достаточно сложить неперекрывающиеся части:
`16 × 8 = 128` байт GPR и SIMD-набор. Получается 384 байта с XMM,
640 байт с AVX2 и 2 176 байт с AVX-512. Регистры флагов, управления и x87
добавляют ещё немного, но не меняют порядок величины: сотни байт или несколько
КиБ, а не десятки КиБ, как у L1.

Есть ещё внутренний **physical register file**: современный out-of-order CPU
держит дополнительные физические регистры для register renaming, чтобы
несколько инструкций могли выполняться параллельно. Его точный объём — деталь
конкретной микроархитектуры, не контракт x86-64, поэтому в общей таблице
памяти не стоит называть одно универсальное число.

**Доступ:** отдельного чтения из памяти нет — операнд уже находится у блока
исполнения. Но сама инструкция не обязательно занимает 0 циклов: простое
сложение обычно имеет latency порядка одного такта, умножение и
деление — больше. Невозможно "обратиться" к регистру явно из Go — компилятор
сам решает, что держать в регистрах, а что в стеке.

Программист не видит регистры напрямую — но видит их **эффект**: если переменная "горячая" и компилятор смог удержать её в регистре, цикл работает в 10-100 раз быстрее, чем если та же переменная — в памяти.

```go
// Компилятор обычно держит i в регистре
for i := 0; i < n; i++ {
    sum += data[i]
}

// А если *p — указатель, который компилятор не может оптимизировать?
// Каждое обращение — потенциальное чтение из memory.
for i := 0; i < n; i++ {
    *p += data[i]  // *p может уйти в L1, не в регистр
}
```

**Escape analysis** в Go частично определяет — попадёт ли переменная в регистр или нет. См. [01-go-core/memory-internals/03-escape-analysis.md](../../01-go-core/memory-internals/03-escape-analysis.md).

Для конкретной ISA набор и ширина регистров задаются документацией процессора:
[Intel 64 and IA-32 Software Developer's Manual](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html),
[обзор Intel AVX-512](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-avx-512-instructions.html).

## Кэши CPU: L1, L2, L3

Если один обычный регистр — 8 байт данных под рукой, а RAM — 100 нс (вечность), то нужны промежуточные уровни. Это и есть CPU cache: маленькая быстрая память **внутри** чипа.

### Иерархия cache на типичном x86 сервере

```
┌─ CPU package ─────────────────────────────────┐
│                                                │
│  ┌─ Core 0 ───┐  ┌─ Core 1 ───┐    ...        │
│  │ Registers  │  │ Registers  │                │
│  │  L1d  L1i  │  │  L1d  L1i  │  (per-core)   │
│  │     L2     │  │     L2     │  (per-core)   │
│  └────────────┘  └────────────┘                │
│                                                │
│            ┌─────  L3  ─────┐                  │
│            │  shared across │                  │
│            │   all cores    │                  │
│            └────────────────┘                  │
└────────────────────────────────────────────────┘
                       ↓
                   Memory bus
                       ↓
                ┌──────────────┐
                │     DRAM     │
                └──────────────┘
```

**L1** — самый близкий. Разделён на L1d (data) и L1i (instructions). 32-64 KB на ядро. ~1 нс.

**L2** — побольше, чуть медленнее. 256 KB — 1 MB на ядро. ~4-10 нс.

**L3** — большой, общий для всех ядер чипа. 4-32 MB на чип. ~10-20 нс.

Деление data/instructions на L1 — потому что CPU одновременно читает и инструкции (что выполнять) и данные (с чем работать). Раздельные кэши = меньше конфликтов.

### Cache line — единица работы кэша

CPU не загружает один байт — он работает блоками по **64 байта** (на x86 и большинстве ARM). Эти блоки называются **cache lines**.

Если код читает байт по адресу X, CPU вытащит всю линию [X-padding, X+padding] в кэш. Соседние 63 байта окажутся "бесплатно" в L1.

Это и есть основа **пространственной локальности** (см. ниже).

Подробнее о cache line и связанных эффектах (false sharing, MESI) — в [03-cache-coherence-and-mesi.md](./03-cache-coherence-and-mesi.md).

### Простая оценка эффекта

```go
// Суммирование массива на 1 МБ.
//
// 1 МБ / 64 байта на строку кэша = 16384 строки.
//
// Первый проход, данных в кэше нет: 16384 промаха
//   16384 * 100 нс = около 1.6 мс
//
// Следующие проходы, если массив помещается в L2:
//   16384 * 4 нс = около 65 мкс, то есть примерно в 25 раз быстрее
//
// Поэтому повторное использование уже загруженных данных в горячем цикле —
// одна из самых результативных оптимизаций.
```

## DRAM — оперативная память

DRAM (Dynamic RAM) — то что в slot'ах материнки. "Память" в обыденном смысле.

**Латенси:** ~80-100 нс. В 200 раз медленнее L1.

**Throughput:** на современных DDR4/DDR5 — десятки GB/s на канал, несколько каналов = 50-200 GB/s суммарно.

**Размер:** 16 GB на ноутбуке, 64-256 GB на сервере, до терабайт на больших машинах.

### Почему DRAM так медленный

Технически DRAM — это **миллиарды конденсаторов**. Каждый бит — заряд на конденсаторе, который **разряжается** со временем (отсюда "dynamic"). Чтобы не потерять данные, контроллер периодически перезаряжает (refresh) — это занимает время.

Чтение байта:
1. Активировать строку матрицы (row activation) — несколько наносекунд
2. Считать колонку из этой строки
3. Усилить сигнал (он маленький)
4. Передать через шину к CPU

Поэтому 100 нс — это не "медленная электроника", это физика конденсаторов и сигналов.

### DRAM устройство (кратко)

```
DIMM (планка памяти)
  └── Ranks (логические наборы чипов)
       └── Banks (параллельно доступные)
            └── Rows × Columns (матрица)
```

Контроллер памяти держит несколько banks "открытыми" одновременно — это позволяет читать из одного банка пока другой ещё активируется. Так получается параллелизм.

**Memory channels:** современные CPU имеют 2-12 каналов памяти, работающих параллельно. 4-канальная DDR5-5600 = теоретически 180 GB/s.

### Practical: NUMA

На многосокетных серверах (2+ CPU чипа) каждый CPU имеет свою "локальную" RAM. Доступ к "чужой" RAM — через межсокетный link, медленнее. Это **NUMA** (Non-Uniform Memory Access).

Для большинства Go-сервисов это прозрачно. Для высокопроизводительных систем — приходится pinning процесса к узлу и аллоцировать память на нём.

## SSD vs HDD

После RAM — постоянное хранилище. Сюда улетает то, что не помещается в RAM, и здесь живут БД (хотя горячие страницы они кэшируют в RAM).

### HDD (Hard Disk Drive)

Магнитный диск, вращается 5400-15000 RPM. Головка физически двигается.

- **Последовательное чтение и запись:** 100-200 MB/s
- **Случайные операции:** ~100-200 IOPS (`input/output operations per second` — число независимых операций ввода-вывода в секунду)
- **Задержка:** 5-10 мс (физическое перемещение головки плюс ожидание поворота диска)

HDD катастрофически медленный для **случайных** обращений (типичный паттерн БД). Sequential — относительно неплохо.

**Когда ещё актуально:** холодные архивы, S3 Glacier, дешёвый backup. На горячих БД — почти везде заменён SSD.

### SSD (Solid State Drive)

Flash-память, без движущихся частей.

**SATA SSD** (старый стандарт):
- ~500 MB/s
- ~100k IOPS
- ~100-200 мкс latency

**NVMe SSD** (PCIe):
- 3-7 GB/s (PCIe 4.0)
- 500k-1M IOPS
- 50-100 мкс latency

NVMe — на порядок быстрее SATA SSD. Современные production-БД обычно на NVMe.

### Особенности flash

SSD не "пишет в место" — она пишет в **свободный блок** и помечает старый как stale. Периодически garbage collector чистит. Это создаёт:

- **Write amplification:** одна логическая запись = несколько физических
- **Износ:** каждая ячейка выдерживает ограниченное число записей (10k-100k для consumer, 1M+ для enterprise)
- **Latency spikes:** во время фоновой GC SSD может тормозить

В backend это видно как "p99 latency на запись внезапно подскакивает" — это GC на SSD сработал.

## Сеть как часть иерархии

Сетевые задержки доминируют над всем остальным в распределённых системах.

| Дистанция | RTT (round-trip time) |
|---|---|
| Within rack | ~0.1 мс |
| Within datacenter | ~0.5 мс |
| Within region (e.g. eu-west-1 ↔ eu-west-2) | ~5-20 мс |
| Cross-continent | 100-200 мс |
| Satellite | 500+ мс |

**Что это значит для backend:**
- Один лишний межсервисный вызов = +0.5 мс
- БД-запрос в RDS в той же AZ = ~1 мс
- БД-запрос в другую region = 30-50 мс
- Запрос к Stripe API из Европы = 100+ мс

Поэтому в архитектуре **count of round trips** > "оптимизация байтов". 10 параллельных запросов = 1 RTT. 10 последовательных = 10 RTT. В 10 раз медленнее.

## Почему кэш работает: локальность

Кэширование работает не магически, а потому что **реальные программы имеют два свойства**:

### Temporal locality (временная)

Если обратился к данным сейчас — скорее всего обратишься снова в ближайшее время.

```go
// counter обновляется в каждой итерации
for _, item := range items {
    counter += item.value  // обращение к counter каждый раз
}
// → counter живёт в регистре или L1, всё быстро
```

### Spatial locality (пространственная)

Если обратился к адресу X — скорее всего обратишься к X+1, X+2, ... в ближайшее время.

```go
// Линейный обход массива — идеальная spatial locality
for i := 0; i < len(arr); i++ {
    sum += arr[i]
}
// → каждая cache line (64 байта = 8 int64) подгружается один раз и используется 8 раз
```

Это работает потому что cache загружает **линиями**, не байтами. Один miss → 64 байта в L1 → 7 hit'ов подряд "бесплатно".

### Anti-pattern: cache-unfriendly доступ

```go
// Linked list — катастрофа для cache
type Node struct {
    value int
    next  *Node
}

for n := head; n != nil; n = n.next {
    sum += n.value  // каждый узел может быть где угодно в памяти
}
// → каждый доступ — потенциальный cache miss
// → может быть в 10-50 раз медленнее массива той же длины
```

Поэтому Go-сообщество предпочитает **slice'ы** linked list'ам: данные лежат подряд, идеально для cache.

### Random vs sequential доступ

```go
// Sequential: ~1 нс на элемент после прогрева кэша
for i := 0; i < N; i++ {
    sum += arr[i]
}

// Random: каждый доступ = cache miss = ~100 нс
indices := randomPermutation(N)
for _, i := range indices {
    sum += arr[i]
}
// Тот же массив, та же сумма, в 50-100 раз медленнее
```

Этот эффект — фундамент для дизайна структур данных:
- BTree, B+Tree в БД оптимизированы под чтение страницами с диска/SSD
- Slice вместо linked list когда нужен обход
- Struct of Arrays (SoA) вместо Array of Structs (AoS) для горячих циклов

## Где живут переменные Go в этой иерархии

```go
func process(req *Request) Response {
    var sum int64       // ← регистр (если компилятор смог) или стек
    items := req.Items  // ← slice header в регистре, backing array в куче или стеке

    for i, item := range items {  // i — регистр, item — копия
        sum += item.Price          // item.Price в регистре или L1
    }

    return Response{Total: sum}    // составляется в регистрах/стеке
}
```

**Иерархия в Go runtime:**

| Где | Что |
|---|---|
| **Registers** | "Горячие" локальные переменные (счётчики циклов, частые операнды) |
| **Stack** | Локальные переменные, не сбежавшие в heap. Очень быстро. |
| **L1/L2 cache** | Недавно использованные данные (автоматически, без участия программиста) |
| **Heap (in DRAM)** | Объекты, escape'нувшие в кучу. GC их освобождает. |
| **Mmap'd memory** | Файлы, замапленные в адресное пространство процесса |
| **Swap (disk)** | Если RAM не хватает — kernel вытесняет страницы. Очень плохо для latency. |

Подробнее про stack vs heap, escape analysis, GC — в [01-go-core/memory-internals/](../../01-go-core/memory-internals/).

**Связка с эскейпами:**

```go
// x не escape — стек. Быстро.
func foo() {
    var x int
    x = compute()
    use(x)
}

// x escape (вернули указатель) — heap. Медленнее: GC, плюс возможно cache miss.
func bar() *int {
    var x int
    x = compute()
    return &x  // ← заставляет аллоцировать в куче
}
```

## Практические выводы для backend

**1. Мыслить порядками величин, а не процентами.**
Ускорение горячего цикла на 10% почти ничего не меняет. Уменьшение числа запросов к БД со ста до одного меняет всё. Кэш в Redis вместо БД и локальный кэш в памяти вместо Redis дают следующие порядки.

**2. Минимизировать сетевые round trips.**
Один JOIN вместо десяти SELECT. Пакетная вставка вместо ста отдельных. Потоковый вызов gRPC вместо ста одиночных.

**3. Выбирать структуры данных, дружелюбные к кэшу.**
Слайс лучше связного списка в большинстве случаев: данные лежат подряд. Горячие поля структуры полезно держать рядом, чтобы они попадали в одну строку кэша. Лишний уровень указателей на горячем пути — это лишний потенциальный промах.

**4. Готовить данные к доступу заранее.**
Если известен паттерн доступа, помогает предварительная сортировка, денормализация или прогрев кэша. Один проход по подготовленным данным на порядок быстрее блуждания по графу указателей.

**5. Помнить численные пороги.**
- обращение к RAM — около 100 нс, значит миллионы операций в секунду;
- чтение с SSD — около 100 мкс, значит десятки тысяч в секунду;
- HTTP-запрос — от миллисекунды до сотен, значит десятки в секунду.

Эти масштабы нельзя смешивать при планировании ёмкости.

**6. Тип хранилища определяет хвостовые задержки.**
БД на HDD со случайным доступом даёт p99 в секундах. БД на NVMe — в миллисекундах. Выбор хранилища для основной БД — одно из самых значимых инфраструктурных решений.

**7. Учитывать усиление чтения (`read amplification`).**
Один SELECT внутри может прочитать мегабайты: полное сканирование таблицы, неудачный JOIN, отсутствующий индекс. `EXPLAIN` часто показывает, что читается в сотни раз больше, чем нужно результату.

**8. Сначала измерение, потом оптимизация.**
`pprof` показывает, где тратится CPU. Промахи кэша видны через `perf stat` на Linux. Без замеров любая оптимизация этого уровня — угадывание.

## Типичные заблуждения

- **«Память — это одна сущность».** Между регистром и диском лежит несколько уровней, и разница между соседними — от разов до порядков. Одно и то же логическое действие может стоить наносекунду или миллисекунду в зависимости от того, где лежат данные.
- **«Числа из списка задержек — константы».** Это шкала порядков, зафиксированная около 2012 года. Часть значений с тех пор изменилась в разы; перед выводом о регрессии их измеряют на своей машине.
- **«Кэш ускоряет любой код».** Кэш помогает только при локальности доступа. Случайный обход большого массива или обход связного списка сводит его пользу почти к нулю.
- **«Процессор читает нужный байт».** Читается целая строка кэша, обычно 64 байта. Отсюда и польза последовательного доступа, и проблема ложного разделения данных (см. [03](./03-cache-coherence-and-mesi.md)).
- **«SSD не имеет всплесков задержки».** Внутренняя сборка мусора флеш-памяти периодически замедляет операции, и это видно как рост p99 на записи.
- **«Большой объём RAM решает проблему».** Если рабочий набор не помещается в кэши процессора, задержка определяется доступом к DRAM, а не размером RAM.

## Interview-ready answer

**1. Зачем нужна иерархия памяти?**

Быстрая память дорогая и маленькая, дешёвая — большая и медленная. Иерархия даёт компромисс: часто используемые данные лежат близко к процессору, редкие — далеко. Работает это потому, что у реальных программ есть временная и пространственная локальность.

**2. Какие порядки задержек нужно помнить?**

L1 — около 1 нс, RAM — около 100 нс, SSD — около 100 мкс, round trip внутри дата-центра — около 500 мкс, между континентами — около 150 мс. Важны не цифры, а расстояние между ними: каждый следующий уровень медленнее в разы или на порядки.

**3. Что такое строка кэша и почему это важно?**

Минимальная единица обмена с кэшем, обычно 64 байта. Процессор загружает её целиком, поэтому соседние данные попадают в кэш бесплатно — отсюда выигрыш последовательного доступа. Обратная сторона — две независимые переменные в одной строке начинают мешать друг другу между ядрами.

**4. Почему слайс обычно быстрее связного списка?**

Элементы слайса лежат подряд, поэтому один промах кэша подтягивает сразу несколько элементов. Узлы связного списка размещены произвольно, и почти каждый переход по указателю — отдельный промах.

**5. Что такое временная и пространственная локальность?**

Временная — недавно использованные данные скорее всего понадобятся снова. Пространственная — вместе с одним адресом скорее всего понадобятся соседние. На этих двух свойствах реальных программ и держится эффективность кэша.

**6. Что важнее оптимизировать в типичном backend-сервисе?**

Число сетевых round trips и обращений к БД. Один лишний запрос к соседнему сервису стоит дороже, чем сотни тысяч инструкций внутри процесса. Микрооптимизация цикла оправдана только там, где профиль показал локальную CPU-bound нагрузку.
