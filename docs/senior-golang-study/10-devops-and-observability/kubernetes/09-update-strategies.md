# Стратегии обновления и безопасный rollout

Обновление — единственный вид исчезновения Pod, который инициирует само приложение: шаблон изменился, и контроллер заменяет старые экземпляры новыми. Стратегия задаёт способ и темп этой замены.

Исчезновение Pod по другим причинам — отказ узла, обслуживание, выселение — разобрано в [материале про прерывания](./08-node-failure-and-disruptions.md). Там же `PodDisruptionBudget`, который на темп rollout не влияет: это частая путаница.

## Стратегии обновления Kubernetes

Стратегия обновления отвечает на вопрос: **как контроллер заменяет старые Pod
новыми после изменения шаблона?**

Она не определяет:

- как распределять пользовательский трафик между версиями;
- как откатывать миграцию базы данных;
- как проверить бизнес-метрики новой версии;
- как обеспечить совместимость протоколов;
- как восстановиться после отказа всего кластера.

Слово `strategy` встречается у разных контроллеров, но поля и допустимые
значения отличаются.

### Сначала различим поля

| Объект | Поле | Встроенные типы | Значение по умолчанию |
| --- | --- | --- | --- |
| `Deployment` | `spec.strategy.type` | `RollingUpdate`, `Recreate` | `RollingUpdate` |
| `StatefulSet` | `spec.updateStrategy.type` | `RollingUpdate`, `OnDelete` | `RollingUpdate` |
| `DaemonSet` | `spec.updateStrategy.type` | `RollingUpdate`, `OnDelete` | `RollingUpdate` |

`Recreate` нельзя указать у `StatefulSet`, а `OnDelete` — у `Deployment`.
Kubernetes API проверяет тип стратегии в контексте конкретного объекта.

`Job` и `CronJob` в таблицу не входят: они управляют задачами, которые должны
завершиться, а не постепенной заменой постоянно работающих реплик.

### Deployment: RollingUpdate

`RollingUpdate` постепенно уменьшает старый `ReplicaSet` и увеличивает новый:

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
```

Два параметра задают границы:

- `maxSurge` — сколько дополнительных Pod можно создать сверх
  `spec.replicas`;
- `maxUnavailable` — сколько желаемых реплик может быть недоступно во время
  обновления.

Для четырёх реплик из примера:

```text
desired replicas = 4
maxSurge = 1
maxUnavailable = 0

максимум Pod во время обновления:
4 + 1 = 5

минимум доступных Pod:
4 - 0 = 4
```

Поэтому упрощённая последовательность выглядит так:

```text
до:
old=4, new=0, available=4

1. создать один новый Pod:
old=4, new=1, всего=5

2. дождаться его readiness:
old available=4, new available=1

3. удалить один старый Pod:
old=3, new=1, available=4

4. повторять, пока old=0, new=4
```

Если в кластере нет ресурсов для дополнительного Pod, он остаётся `Pending`.
Старые четыре Pod продолжают работать, но rollout не продвигается: при
`maxUnavailable: 0` контроллер не может сначала удалить один из них и
освободить место.

Значения можно задавать числом или процентом:

```yaml
rollingUpdate:
  maxSurge: 25%
  maxUnavailable: 25%
```

Для процентов Kubernetes округляет `maxSurge` вверх, а `maxUnavailable` вниз.
Значения по умолчанию для обоих полей — `25%`. Одновременно сделать оба
значения равными нулю нельзя: тогда контроллер не смог бы ни создать
дополнительный Pod, ни удалить старый.

### Deployment: Recreate

`Recreate` сначала завершает старые Pod текущего `Deployment`, а затем создаёт
новые:

```yaml
spec:
  strategy:
    type: Recreate
```

```text
old=3, new=0
       │
       ▼
old=0, new=0    ← окно недоступности
       │
       ▼
old=0, new=3
```

Эта стратегия почти всегда создаёт перерыв в обслуживании. Она может быть
осознанным выбором, если:

- старая и новая версии не могут работать одновременно;
- приложение использует ресурс с единственным активным владельцем;
- временная недоступность допустима;
- более безопасная совместимая миграция пока невозможна.

`Recreate` не делает несовместимое обновление безопасным автоматически. Новый
Pod всё равно может не запуститься, а изменение схемы данных — оказаться
необратимым.

При `type: Recreate` блок `strategy.rollingUpdate` не используется и не должен
оставаться в манифесте:

```yaml
# неверная смесь двух стратегий
strategy:
  type: Recreate
  rollingUpdate:
    maxSurge: 1
```

### StatefulSet: RollingUpdate

У `StatefulSet` поле называется `updateStrategy`, потому что механизм
отличается от обновления взаимозаменяемых реплик `Deployment`:

```yaml
spec:
  updateStrategy:
    type: RollingUpdate
```

По умолчанию контроллер обновляет Pod **в обратном порядке номеров**. Для
`postgres-0`, `postgres-1`, `postgres-2`:

```text
1. удалить и пересоздать postgres-2
2. дождаться, пока postgres-2 станет Running и Ready
3. удалить и пересоздать postgres-1
4. дождаться готовности postgres-1
5. удалить и пересоздать postgres-0
```

Контроллер не создаёт `postgres-2-new` рядом со старым `postgres-2`, потому
что обе копии претендовали бы на одну идентичность и обычно на один PVC.

Для поэтапного обновления можно задать `partition`:

```yaml
spec:
  replicas: 4
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 2
```

Обновляются только Pod с номером не меньше `2`:

```text
postgres-3 → новая версия
postgres-2 → новая версия
postgres-1 → старая версия
postgres-0 → старая версия
```

Это позволяет остановить обновление на части реплик, но не настраивает долю
пользовательского трафика. Клиенты системы с состоянием могут обращаться к
репликам неравномерно или учитывать их роли.

### StatefulSet: OnDelete

```yaml
spec:
  updateStrategy:
    type: OnDelete
```

После изменения `spec.template` контроллер не трогает существующие Pod. Новая
версия появляется только после ручного удаления конкретного Pod:

```bash
kubectl delete pod postgres-2
```

`StatefulSet` создаёт новый `postgres-2` уже из обновлённого шаблона. Такой
режим полезен, когда порядок обновления контролирует оператор или отдельная
процедура, но требует дисциплины:

- легко надолго оставить разные версии;
- автоматический rollout status не заменяет внешний процесс обновления;
- ручное удаление неправильной реплики может нарушить кворум приложения.

### DaemonSet: RollingUpdate и OnDelete

`DaemonSet` запускает Pod на каждом подходящем узле, поэтому его обновление
считается по узлам, а не по числу обычных реплик.

- `RollingUpdate` автоматически заменяет Pod на узлах с учётом
  `maxUnavailable` и, если настроен, `maxSurge`;
- `OnDelete` оставляет старый Pod на узле, пока его не удалят вручную.

Такие стратегии используют для сетевых плагинов, драйверов хранилищ,
сборщиков логов и других узловых агентов. Ошибка в их обновлении может затронуть
не один сервис, а весь `worker node`, поэтому темп выбирают особенно осторожно.

### Blue-green и canary — другой уровень

`Blue-green` и `canary` часто называют стратегиями развёртывания, но они **не
являются допустимыми значениями** `Deployment.spec.strategy.type`.

| Подход | Как устроен | Чем реализуется |
| --- | --- | --- |
| blue-green | старая и новая версии запущены параллельно, затем точка входа переключается целиком | два `Deployment`, переключение selector `Service`, Ingress или Gateway |
| canary | сначала небольшая часть трафика получает новую версию | два набора Pod и взвешенная маршрутизация через Ingress, Gateway API, сервисную сетку (`service mesh`) или контроллер постепенной доставки |
| A/B | версия выбирается по пользователю, заголовку или другому признаку | L7-маршрутизация, а не обычный `Deployment` |

Упрощённый blue-green:

```text
до переключения:
Service selector: version=blue
                       │
                       ▼
                 Deployment blue

после проверки green:
Service selector: version=green
                       │
                       ▼
                 Deployment green
```

Упрощённый canary:

```text
90% трафика → стабильная версия
10% трафика → новая версия
```

Обычный `RollingUpdate` управляет количеством старых и новых Pod, но не
гарантирует точный процент запросов на каждую версию. Pod могут обрабатывать
разное число долгих соединений или запросов, поэтому для управляемого canary
нужна маршрутизация трафика и анализ метрик.

### Как выбрать

| Ситуация | Подход |
| --- | --- |
| приложение без локального состояния, версии совместимы | `Deployment` с `RollingUpdate` |
| версии не могут сосуществовать, простой допустим | `Deployment` с `Recreate` |
| реплики с состоянием обновляются по порядку | `StatefulSet` с `RollingUpdate` |
| удалением каждой реплики с состоянием управляет внешняя процедура | `StatefulSet` с `OnDelete` |
| нужен постепенный процент трафика и автоматический анализ метрик | canary через отдельный контроллер или L7-маршрутизацию |
| нужно быстро переключать две полностью развернутые версии | blue-green |

## Что нужно для безопасного rollout

Даже правильно выбранная стратегия определяет только механизм и допустимый темп замены. Для безопасного `RollingUpdate` нужны дополнительные условия:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
minReadySeconds: 10
progressDeadlineSeconds: 600
```

| Условие | Почему важно |
| --- | --- |
| корректная readiness | новый Pod считается доступным только когда действительно готов принимать запросы |
| свободные ресурсы под `maxSurge` | планировщику нужно где-то разместить дополнительный Pod |
| `minReadySeconds` при необходимости | кратковременный успех проверки не принимается за устойчивую готовность |
| корректное завершение | старый Pod успевает доработать уже принятые запросы |
| совместимость соседних версий | старые и новые реплики некоторое время работают одновременно |
| совместимая схема данных | откат на прежний образ не должен ломаться о новую схему |
| наблюдение за обновлением | успех вызова API не равен работоспособности приложения |

`maxUnavailable: 0` не гарантирует работу без простоя: узел может отказать прямо во время обновления, readiness probe может оказаться слишком поверхностной, а версии протокола — несовместимыми.

## Наблюдение и откат

Успешный `kubectl apply` означает, что API принял новый шаблон, а не что обновление завершилось. Состояние проверяют отдельно:

```bash
kubectl -n payments rollout status deployment/api --timeout=5m
```

Команда ждёт, пока все реплики новой ревизии станут доступными, и при истечении времени возвращает ненулевой код завершения. Именно это делает её пригодной для использования в пайплайне доставки.

Если обновление не двигается, смотрят не на `Deployment`, а на новый `ReplicaSet` и его Pod — причина почти всегда там:

```bash
kubectl -n payments get replicaset -l app=api
kubectl -n payments get pods -l app=api -o wide
kubectl -n payments describe deployment api
kubectl -n payments get events --sort-by='.metadata.creationTimestamp'
```

Типичные причины остановки:

| Что видно | Причина |
| --- | --- |
| новый Pod в `Pending` | не хватает ресурсов под `maxSurge` или мешают правила размещения |
| новый Pod в `ImagePullBackOff` | неверная ссылка на образ или нет доступа к реестру |
| новый Pod `Running`, но `0/1 Ready` | не проходит readiness probe |
| счётчик реплик не меняется долгое время | истёк `progressDeadlineSeconds`, условие `Progressing` перешло в `False` |

Откат возвращает предыдущий шаблон Pod:

```bash
kubectl -n payments rollout undo deployment/api
kubectl -n payments rollout undo deployment/api --to-revision=3
```

История ревизий хранится в старых `ReplicaSet` в пределах `revisionHistoryLimit`, поэтому откатиться можно только на сохранённые ревизии.

Ключевое ограничение: откат возвращает **шаблон Pod и ничего больше**. Он не отменяет выполненную миграцию базы данных, не забирает обратно опубликованное в брокер сообщение и не восстанавливает изменённое внешнее состояние. Поэтому в системах с миграциями обычно надёжнее движение вперёд с исправлением, чем откат образа на несовместимую схему.

## Interview-ready answer

**1. Какие стратегии обновления есть у Deployment?**

`RollingUpdate` постепенно заменяет старый `ReplicaSet` новым в границах `maxSurge` и `maxUnavailable`. `Recreate` сначала завершает все старые Pod, а затем создаёт новые, поэтому обычно даёт окно недоступности.

**2. Гарантирует ли RollingUpdate работу без простоя?**

Нет. `maxSurge` и `maxUnavailable` управляют только количеством Pod. Ещё нужны корректная readiness, свободные ресурсы, аккуратный вывод старых Pod из-под трафика, совместимость соседних версий и наблюдение за целевыми показателями сервиса.

**3. Что произойдёт при `maxUnavailable: 0`, если в кластере нет свободных ресурсов?**

Дополнительный Pod останется в `Pending`, а обновление остановится. Удалить один из старых Pod, чтобы освободить место, контроллер не может: это нарушило бы заданное условие доступности. Старая версия при этом продолжает работать.

**4. Какие стратегии обновления есть у StatefulSet?**

`RollingUpdate` пересоздаёт Pod в обратном порядке их номеров и ждёт готовности каждой реплики. `OnDelete` применяет новый шаблон только после ручного удаления Pod. Поле называется `updateStrategy`, а значение `Recreate` для `StatefulSet` недопустимо.

**5. Являются ли canary и blue-green значениями `strategy.type`?**

Нет. Это стратегии распределения трафика между версиями. Они требуют двух наборов Pod и переключения или взвешивания трафика через `Service`, Ingress, Gateway API, сервисную сетку либо отдельный контроллер постепенной доставки.

**6. Почему обычный RollingUpdate не даёт настоящий canary?**

Он управляет соотношением числа старых и новых Pod, но не долей запросов. Pod могут обслуживать разное число долгих соединений, поэтому «10% новых Pod» не означает «10% трафика». Нужна маршрутизация уровня 7 и анализ метрик.

**7. Что реально откатывает `rollout undo`?**

Только предыдущий шаблон Pod. Миграции, опубликованные сообщения и изменённое внешнее состояние остаются, поэтому откат должен быть частью совместимой стратегии выпуска.
