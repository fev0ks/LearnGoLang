Kubernetes-компоненты не существуют в вакууме: они запускаются на физических или виртуальных машинах и вместе образуют кластер. Этот файл объясняет, где проходит граница кластера, как плоскость управления и рабочие узлы размещаются по машинам и какие отказы выдерживает такая система.

Кластеризация Kubernetes не равна автоматической кластеризации приложения или базы данных. Kubernetes помогает размещать и восстанавливать Pod, но не объединяет память машин и не создаёт репликацию бизнес-данных.

Роли `kube-apiserver`, `etcd`, `kube-scheduler`, контроллеров и `kubelet` сначала разобраны в [материале про архитектуру Kubernetes](./01-kubernetes-architecture.md).

## Что такое Kubernetes-кластер

**Kubernetes-кластер** — это плоскость управления и один или несколько узлов, которыми она управляет как общей платформой для запуска приложений.

У кластера есть:

- единый Kubernetes API;
- общее состояние объектов API;
- набор машин с процессором, памятью, сетью и дисками;
- общая сетевая модель для Pod и `Service`;
- системные компоненты, которые размещают приложения и согласуют желаемое состояние.

Упрощённая формула:

```text
Kubernetes-кластер =
    плоскость управления и состояние API
    + один или несколько узлов
    + сеть Pod и Service
    + интеграции с хранилищами и инфраструктурой
```

Слово «общий» здесь означает **общее управление**, а не общую оперативную память или файловую систему.

## Зачем объединять машины в кластер

Представим три виртуальные машины. Без оркестратора команде нужно самостоятельно решать:

- на какой машине запустить каждую копию Go-сервиса;
- как узнать адреса всех копий;
- что делать, если процесс или машина перестали отвечать;
- как обновить версию без одновременной остановки всех копий;
- как добавить копии при росте нагрузки;
- как применять одинаковые правила доступа и размещения.

В Kubernetes пользователь описывает цель:

```yaml
kind: Deployment
spec:
  replicas: 3
```

После этого компоненты Kubernetes:

1. Создают три объекта Pod.
2. Выбирают подходящий узел для каждого Pod.
3. Запускают контейнеры на выбранных узлах.
4. Наблюдают получившееся состояние.
5. Создают замену, если наблюдаемое число Pod стало меньше желаемого.

| Задача | Что даёт кластер |
| --- | --- |
| единая точка управления | изменения проходят через Kubernetes API |
| управление группой машин | планировщик выбирает подходящий узел для каждого Pod |
| восстановление | контроллеры создают замену, когда наблюдаемое состояние расходится с желаемым |
| обнаружение приложения | `Service` и DNS скрывают изменяющиеся адреса Pod |
| обновление и масштабирование | `Deployment` меняет версию, HPA может менять число реплик |
| единые правила | права доступа (`RBAC`), квоты, сетевые политики и проверки приёма применяются на уровне платформы |

Подробный путь от `Deployment` до Pod разобран в [материале про основные объекты](./03-core-objects-and-deployment-flow.md).

## Кластер не превращает машины в один большой сервер

Допустим, в кластере три рабочих узла:

```text
worker-1: 4 CPU, 8 GiB памяти
worker-2: 4 CPU, 8 GiB памяти
worker-3: 4 CPU, 8 GiB памяти
```

Во всём кластере действительно есть двенадцать ядер процессора и 24 GiB памяти. Но один Pod должен целиком поместиться на **одном** узле.

```text
Pod запрашивает 2 CPU и 4 GiB  → можно разместить на любом узле
Pod запрашивает 8 CPU и 4 GiB  → нельзя разместить ни на одном узле
```

Планировщик не может выдать одному процессу по части оперативной памяти с трёх машин. Во втором случае Pod остаётся `Pending`, пока:

- не появится более крупный узел;
- не уменьшатся запросы ресурсов Pod;
- другой Pod не освободит достаточно ресурсов;
- автомасштабирование узлов не добавит подходящую машину.

Расчёт запросов ресурсов и диагностика `Pending` подробно разобраны в [статье про Pod](./04-pod-vs-container.md).

## Где проходит граница кластера

| Понятие | Что означает |
| --- | --- |
| `Node` | одна физическая или виртуальная машина, зарегистрированная в Kubernetes API |
| `Namespace` | логическое разделение объектов внутри одного кластера: область имён, квот и прав доступа |
| Kubernetes-кластер | собственные API, состояние `etcd`, плоскость управления и набор узлов |
| несколько кластеров | независимые границы управления и отказа |

`Namespace` не является маленьким кластером. Объекты разных пространств имён всё равно зависят от одной плоскости управления, одних узлов и обычно одной сетевой инфраструктуры.

Граница кластера важна при отказах:

- отказ одного Pod находится внутри кластера и обычно обрабатывается контроллерами;
- отказ одного узла может быть обработан оставшимися узлами;
- потеря всей плоскости управления замораживает управление;
- потеря всех машин кластера не может быть исправлена компонентами внутри этого же кластера.

## Масштабирование, высокая доступность и кластеризация

Эти понятия связаны, но отвечают на разные вопросы:

| Понятие | Вопрос | Пример |
| --- | --- | --- |
| масштабирование | как обработать больше нагрузки? | увеличить число Pod с 3 до 10 |
| высокая доступность (`high availability`, HA) | как продолжить работу при отказе части системы? | разместить реплики на разных узлах и зонах |
| кластер Kubernetes | где работает общая платформа управления? | одна плоскость управления и набор рабочих узлов |
| кластеризация приложения | как несколько экземпляров согласуют бизнес-состояние? | кластер PostgreSQL, Kafka или Redis |

Наличие Kubernetes-кластера само по себе не гарантирует высокую доступность приложения:

- одна реплика Go-сервиса всё ещё является единой точкой отказа;
- три реплики могут случайно оказаться на одном узле;
- база данных может находиться на одной машине;
- неверная проверка готовности может исключить все здоровые Pod;
- приложение может не поддерживать одновременную работу нескольких экземпляров.

И наоборот, один сервис может выдерживать высокую нагрузку вне Kubernetes, если более простая платформа уже предоставляет нужное масштабирование.

## Основные варианты физического размещения

Логические роли Kubernetes одинаковы, но по машинам они могут размещаться по-разному.

### Одноузловой кластер

В учебном или локальном окружении всё может работать на одной машине:

```text
Одна виртуальная машина
├── kube-apiserver
├── kube-scheduler
├── kube-controller-manager
├── etcd
├── kubelet и среда выполнения контейнеров
└── Pod приложения
```

Это настоящий кластер с точки зрения Kubernetes API, но без отказоустойчивости. Отказ машины одновременно останавливает управление и приложения.

### Одна машина управления и несколько рабочих узлов

```text
Узел плоскости управления
├── kube-apiserver
├── kube-scheduler
├── kube-controller-manager
└── etcd

Рабочий узел 1                 Рабочий узел 2
├── kubelet                    ├── kubelet
├── среда выполнения           ├── среда выполнения
└── Pod A, Pod B               └── Pod C
```

Теперь отказ рабочего узла не уничтожает состояние кластера: контроллеры могут создать замену Pod на другом узле. Но машина плоскости управления остаётся единой точкой отказа **управления**.

Если она выключится, уже работающие Pod могут продолжить обслуживать запросы, однако нельзя:

- применить новый манифест;
- назначить новый Pod;
- обновить число реплик;
- согласовать изменения `Service` и `EndpointSlice`;
- автоматически восстановить приложение после следующего отказа.

### Отказоустойчивая плоскость управления

В рабочем окружении плоскость управления обычно запускают на нескольких машинах:

```text
общий адрес Kubernetes API
          │
          ▼
   балансировщик
     │    │    │
     ▼    ▼    ▼
    CP1  CP2  CP3

рабочие узлы: worker-1, worker-2, worker-3, ...
```

`CP1`, `CP2` и `CP3` — не «три независимых Kubernetes». Это три машины одной плоскости управления с общим состоянием.

### Управляемый Kubernetes

В управляемом сервисе плоскость управления запускает облачный провайдер. Пользователь получает адрес Kubernetes API и управляет рабочими нагрузками, но может не видеть:

- машины плоскости управления;
- процессы `kube-apiserver`;
- участники `etcd`;
- способ выбора лидера и резервного копирования.

Это переносит часть операционной ответственности провайдеру, но не делает автоматически отказоустойчивыми Pod, базы данных и внешние зависимости пользователя.

## Как строится отказоустойчивая плоскость управления

Недостаточно просто создать три машины. После отказа одной машины должна сохраниться каждая необходимая роль:

| Часть | Как устраняется единая точка отказа |
| --- | --- |
| адрес API | клиенты используют общий DNS-адрес или виртуальный IP |
| `kube-apiserver` | несколько экземпляров одновременно принимают запросы |
| балансировка | балансировщик направляет соединение только доступному API-серверу |
| `kube-scheduler` | несколько экземпляров используют выбор лидера; решения принимает один активный лидер |
| `kube-controller-manager` | несколько экземпляров используют выбор лидера |
| `etcd` | несколько участников подтверждают записи большинством голосов |

Путь одного API-запроса:

```text
kubectl / kubelet
        │
        ▼
общий адрес Kubernetes API
        │
        ▼
балансировщик
        │
        ├── kube-apiserver на CP1
        ├── kube-apiserver на CP2
        └── kube-apiserver на CP3
                     │
                     ▼
          etcd: 3 участника, кворум 2
```

Допустим, `CP1` полностью выключается:

1. Балансировщик перестаёт отправлять новые соединения на `kube-apiserver` этой машины.
2. Запросы продолжают принимать API-серверы на `CP2` и `CP3`.
3. Если на `CP1` работал лидер планировщика или контроллеров, оставшиеся экземпляры выбирают нового лидера.
4. Если два оставшихся участника `etcd` доступны друг другу, они образуют большинство из трёх.
5. Рабочие узлы продолжают обращаться к общему адресу и не должны знать, какой API-сервер сейчас отвечает.

Схема считается отказоустойчивой не из-за количества коробок, а потому, что после потери одной коробки остаются:

- доступный API;
- активный планировщик;
- активные контроллеры;
- кворум хранилища состояния.

## Зачем etcd нужен кворум

`etcd` хранит состояние Kubernetes API и использует согласование участников, чтобы не принять противоречащие друг другу записи при сетевом разделении.

Для подтверждения записи нужно большинство участников:

```text
N — общее число участников etcd
quorum = floor(N / 2) + 1
```

Примеры:

```text
1 участник → quorum = 1 → нельзя потерять ни одного
2 участника → quorum = 2 → нельзя потерять ни одного
3 участника → quorum = 2 → можно потерять 1
4 участника → quorum = 3 → можно потерять 1
5 участников → quorum = 3 → можно потерять 2
```

Поэтому нечётное число участников использует машины эффективнее:

- три и четыре участника выдерживают одинаковый один отказ;
- пять участников выдерживают два отказа;
- добавление четвёртого участника к трём увеличивает стоимость, но не число допустимых отказов.

Если кластер `etcd` разделился сетью на группы из двух и одного участника:

```text
сторона A: 2 участника → есть большинство → может продолжать работу
сторона B: 1 участник  → большинства нет → не принимает новые записи
```

Это защищает Kubernetes от появления двух независимых версий состояния.

Резервная копия `etcd` всё равно нужна. Репликация помогает пережить часть отказов во время работы, но не защищает от ошибочного удаления данных, повреждения всех реплик или потери всего региона.

## Совмещённый и отдельный etcd

В кластерах, созданных через `kubeadm`, встречаются две основные топологии:

| Топология | Где работает `etcd` | Преимущество | Цена |
| --- | --- | --- | --- |
| совмещённая (`stacked`) | по одному участнику `etcd` на каждом узле плоскости управления | требуется меньше машин | отказ узла одновременно уменьшает число API-компонентов и участников `etcd` |
| отдельная (`external etcd`) | участники `etcd` работают на отдельных машинах | границы отказа плоскости управления и хранилища разделены | требуется больше инфраструктуры и сложнее эксплуатация |

Для совмещённой топологии с тремя узлами:

```text
CP1: kube-apiserver + scheduler + controllers + etcd-1
CP2: kube-apiserver + scheduler + controllers + etcd-2
CP3: kube-apiserver + scheduler + controllers + etcd-3
```

Отказ `CP1` одновременно убирает один API-сервер и одного участника `etcd`, но оставшихся двух достаточно для работы.

Для отдельной топологии роли разделены:

```text
плоскость управления: CP1, CP2, CP3
хранилище состояния: etcd-1, etcd-2, etcd-3
```

Теперь отказ одного узла плоскости управления не уменьшает число участников `etcd`. Цена — шесть машин вместо трёх, дополнительные сетевые зависимости и более сложное обслуживание.

Это конкретные топологии `kubeadm`, а не требование Kubernetes API. Управляемый провайдер может реализовать отказоустойчивость иначе и скрыть её детали.

## Что означает «кластер упал»

Фраза «кластер упал» неточна: приложение, рабочие узлы, API и хранилище состояния могут отказывать независимо.

| Что отказало | Наблюдаемое последствие |
| --- | --- |
| процесс приложения | `kubelet` может перезапустить контейнер внутри существующего Pod |
| один Pod | контроллер рабочей нагрузки может создать новый Pod |
| один рабочий узел | его Pod становятся недоступны; после обнаружения отказа замены могут быть созданы на здоровых узлах |
| единственный узел плоскости управления | работающие Pod могут продолжить работу, но изменения и восстановление желаемого состояния останавливаются |
| один узел отказоустойчивой плоскости управления | запросы идут другим API-серверам, выбирается новый лидер, кворум `etcd` сохраняется |
| потерян кворум `etcd` | приложения могут продолжать работу, но плоскость управления не может надёжно записывать новое состояние |
| уничтожены все машины кластера | восстановление изнутри невозможно |

Плоскость управления обычно не участвует в обработке каждого запроса к Go-сервису:

```text
клиент
  → внешний балансировщик / Gateway
  → плоскость данных Service
  → Pod
```

Поэтому недоступный Kubernetes API и недоступное приложение — разные состояния. Но без API и контроллеров кластер не может реагировать на новые изменения и следующие отказы.

Подробные задержки обнаружения отказа узла, выселение Pod и риск двух активных экземпляров при сетевом разделении разобраны в [материале про отказ узла](./08-node-failure-and-disruptions.md).

## Как пережить потерю всего кластера

Если уничтожены все машины или весь регион, компонентам внутри кластера уже негде работать. Для восстановления нужны механизмы **за его границей**:

1. Terraform, Cluster API или облачная платформа создают новый кластер.
2. GitOps или CI/CD повторно применяет манифесты.
3. Резервные копии и межрегиональная репликация восстанавливают базы данных и постоянные тома.
4. Внешний DNS или глобальный балансировщик переводит трафик.

Важно различать данные:

| Резервная копия | Что восстанавливает |
| --- | --- |
| снимок `etcd` | объекты Kubernetes API и состояние плоскости управления |
| backup PostgreSQL | бизнес-данные PostgreSQL |
| backup постоянных томов | файлы и данные на соответствующем хранилище |
| Git-репозиторий с манифестами | декларативное описание приложений, но не их изменяемые данные |

Снимок `etcd` не заменяет резервные копии бизнес-данных. И наоборот, backup PostgreSQL не восстанавливает определения `Deployment`, RBAC и `Service`.

## Один кластер или несколько

Несколько кластеров создают более сильную границу отказа, чем несколько `Namespace`, но увеличивают операционную сложность.

| Один кластер | Несколько кластеров |
| --- | --- |
| проще общие сеть, наблюдаемость и доставка приложений | сильнее изоляция окружений и аварий |
| выше утилизация общего набора узлов | можно независимо обновлять платформы |
| один отказ плоскости управления затрагивает все пространства имён | отказ одного кластера не обязан затрагивать другой |
| проще поддерживать единые политики | нужно синхронизировать политики и конфигурацию |
| меньше инфраструктуры | больше стоимость и сложнее межкластерная сеть |

Типичные причины создать отдельный кластер:

- отделить рабочее окружение от экспериментов;
- получить независимую границу соответствия требованиям безопасности;
- разместиться в другом регионе;
- независимо обновлять версию платформы;
- подготовить аварийное переключение.

Создавать отдельный кластер для каждой команды или каждого сервиса необязательно. Выбор зависит от требуемой изоляции, масштаба и готовности команды поддерживать дополнительную инфраструктуру.

## Как посмотреть топологию живого кластера

```bash
# Общий адрес Kubernetes API
kubectl cluster-info

# Узлы, роли, версии и внутренние адреса
kubectl get nodes -o wide

# Метки зон и регионов
kubectl get nodes -L topology.kubernetes.io/region,topology.kubernetes.io/zone

# Системные Pod и узлы, на которых они работают
kubectl -n kube-system get pods -o wide

# Состояние и доступные ресурсы конкретного узла
kubectl describe node <node-name>

# Готовность API-сервера
kubectl get --raw='/readyz?verbose'
```

В управляемом Kubernetes процессы плоскости управления могут не отображаться в `kube-system`. Тогда их топология и гарантии доступности описываются документацией и соглашением об уровне сервиса провайдера.

## Interview-ready answer

**1. Что такое Kubernetes-кластер?**

Это плоскость управления и один или несколько узлов, которыми она управляет через единый API и общее состояние. Кластер объединяет машины на уровне управления приложениями, но не объединяет их оперативную память в один сервер.

**2. Чем Namespace отличается от отдельного кластера?**

`Namespace` логически разделяет объекты внутри одного Kubernetes API. Пространства имён всё равно зависят от общей плоскости управления и узлов. Отдельный кластер имеет собственные API, состояние и границу отказа.

**3. Гарантирует ли Kubernetes-кластер высокую доступность приложения?**

Нет. Нужны несколько реплик, распределение по независимым узлам или зонам, корректные проверки состояния, доступная база данных и совместимая архитектура приложения. Кластер предоставляет механизмы, но их нужно настроить.

**4. Почему один большой Pod не может использовать сумму ресурсов всех узлов?**

Планировщик назначает Pod целиком одному узлу. Кластер управляет группой отдельных машин, а не создаёт общую память. Если Pod не помещается ни на один узел, он остаётся `Pending`.

**5. Как строится отказоустойчивая плоскость управления?**

Клиенты используют общий адрес API перед несколькими `kube-apiserver`. Планировщик и контроллеры запускаются в нескольких экземплярах с выбором лидера, а `etcd` — несколькими участниками с кворумом.

**6. Почему обычно используют три участника etcd?**

Для записи нужно большинство. Три участника имеют кворум два и выдерживают отказ одного. Два участника тоже требуют два голоса и не выдерживают ни одного отказа, поэтому третий участник добавляет реальную отказоустойчивость.

**7. Что происходит при потере всей плоскости управления?**

Уже работающие Pod и настроенная сетевая плоскость могут продолжить обслуживать трафик, но новые изменения, размещение Pod и согласование желаемого состояния останавливаются.

**8. Может ли Kubernetes сам восстановиться после потери всего кластера?**

Нет. Нужен внешний процесс: создание нового кластера, повторное применение манифестов, восстановление бизнес-данных и переключение внешнего трафика.
