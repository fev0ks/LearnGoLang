Контейнер — это изолированное окружение для запуска процесса. Pod — объект Kubernetes, который объединяет один или несколько тесно связанных контейнеров и задаёт для них общую единицу размещения, сети и жизненного цикла.

---

## Что такое Pod и зачем он нужен

Kubernetes не запускает контейнеры как самостоятельные объекты нагрузки. Поле `containers` всегда находится внутри `PodSpec`, а `kube-scheduler` выбирает рабочий узел для Pod целиком.

Простая ментальная модель:

```text
Pod — логический хост приложения
│
├── общий IP и пространство сетевых портов
├── набор доступных томов
├── правила запуска и завершения
│
├── контейнер приложения
└── необязательный вспомогательный контейнер
```

Pod нужен Kubernetes как **атомарная единица размещения**. Все его контейнеры назначаются на один `Node`, создаются в общем контексте и удаляются вместе.

При этом разные компоненты Kubernetes используют разные части описания Pod:

- `kube-scheduler` учитывает эффективные requests, ограничения и политики размещения;
- `kubelet` создаёт контейнеры, подключает тома и выполняет probes;
- сетевая реализация предоставляет IP и связность;
- API хранит настройки безопасности, правила жизненного цикла и `ServiceAccount` — идентичность, от имени которой Pod обращается к Kubernetes API.

В наиболее частом случае Pod содержит один контейнер:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: api
  labels:
    app: api
spec:
  containers:
    - name: api
      image: registry.example/api:v1.2.3
      ports:
        - name: http
          containerPort: 8080
```

Обычно такой Pod не создают вручную. `Deployment`, `StatefulSet` или `Job` хранит шаблон Pod и создаёт нужные экземпляры через контроллеры. Если Pod потерян, контроллер создаёт **новый** объект с другим UID, а не переносит старый Pod на другую машину.

Один Pod представляет один экземпляр приложения. Если `Deployment` масштабируется с одной до трёх реплик, Kubernetes создаёт три отдельных Pod:

```text
Deployment replicas=3
├── Pod A → Node 1
├── Pod B → Node 2
└── Pod C → Node 3
```

Каждый Pod получает собственный IP и может независимо заменяться. Более подробная цепочка `Deployment → ReplicaSet → Pod` разобрана в [карте объектов Kubernetes](./03-core-objects-and-deployment-flow.md).

## Контейнер и Pod: короткое сравнение

| Вопрос | Контейнер | Pod |
| --- | --- | --- |
| Что это | изолированное окружение для процесса или группы процессов | объект Kubernetes, содержащий один или несколько контейнеров |
| Кто непосредственно запускает | среда выполнения контейнеров, например containerd | `kubelet` просит среду выполнения создать окружение Pod и его контейнеры |
| Единица размещения (`scheduling`) | нет | да, `kube-scheduler` назначает целый Pod одному `Node` |
| Сетевой адрес в Kubernetes | использует сеть Pod | Pod получает IP, общий для его контейнеров |
| Файловая система | собственные слои образа | может объявить тома и подключить их выбранным контейнерам |
| Ресурсы | requests и limits задаются каждому контейнеру | `kube-scheduler` учитывает эффективный запрос всего Pod |
| Масштабирование | отдельно внутри Pod не масштабируется | контроллер создаёт дополнительные Pod по одному шаблону |
| Замена после потери Node | сам контейнер не переносится | контроллер создаёт новый Pod на доступном узле |

Pod не является маленькой виртуальной машиной. У него нет отдельного гостевого ядра: контейнеры используют ядро операционной системы `Node` и изолируются механизмами контейнерной среды.

## Что разделяют контейнеры внутри Pod

Контейнеры одного Pod всегда находятся на одном рабочем узле, но разделяют не всё:

| Ресурс | Что происходит внутри Pod |
| --- | --- |
| сеть | контейнеры используют одно сетевое пространство имён (`network namespace`), общий IP и общее пространство портов |
| `localhost` | процесс в одном контейнере может обратиться к процессу в другом через `127.0.0.1` |
| тома | том объявляется в Pod, но каждый контейнер явно выбирает, какие тома и куда подключить |
| слои образа | не разделяются: у каждого контейнера своя корневая файловая система |
| переменные окружения | задаются отдельно для каждого контейнера |
| процессы | пространство имён процессов (`process namespace`) по умолчанию раздельное; общий режим включается через `shareProcessNamespace: true` |
| ресурсы | requests и limits задаются контейнерам отдельно, но при размещении учитывается Pod целиком |
| безопасность | часть настроек задаётся на уровне Pod, часть — отдельно для каждого контейнера |

Общий IP означает и общее пространство портов. Если основной контейнер уже слушает `0.0.0.0:8080`, второй контейнер того же Pod не сможет занять этот же порт.

Зато локальное взаимодействие не требует `Service`:

```text
контейнер-прокси: :8443
          │
          └── http://127.0.0.1:8080
                         │
                  контейнер api: :8080
```

Том также не подключается всем контейнерам автоматически. Сначала он объявляется в `spec.volumes`, затем каждый потребитель добавляет собственный `volumeMount`.

`Service` направляет трафик на IP и порт Pod, а не на абстрактный «контейнер по имени». Какой процесс получит соединение, определяется портом, который он слушает.

## Зачем запускать несколько контейнеров в одном Pod

Один контейнер на Pod — нормальный вариант по умолчанию. Дополнительный контейнер оправдан, когда два процесса образуют **один экземпляр приложения** и должны:

1. всегда размещаться на одной машине;
2. общаться через `localhost` или общий том;
3. масштабироваться в соотношении один к одному;
4. создаваться и удаляться вместе;
5. не иметь самостоятельного смысла друг без друга.

### Почему не запустить оба процесса в одном контейнере

Технически один контейнер может содержать несколько процессов. Но отдельные контейнеры дают Kubernetes и разработчику более точные границы управления:

| Два процесса в одном контейнере | Два контейнера в одном Pod |
| --- | --- |
| нужен собственный process supervisor | `kubelet` отдельно наблюдает состояние каждого контейнера |
| общий образ со всеми зависимостями | приложение и помощник используют разные образы |
| общий resource limit | requests и limits задаются каждому контейнеру |
| общий security context процесса контейнера | контейнерам можно дать разные права и файловые системы |
| сложнее понять, какой процесс упал | у каждого контейнера своё состояние, счётчик перезапусков и логи |
| обновление помощника требует пересборки общего образа | образ помощника можно собирать и версионировать отдельно |

При этом оба контейнера всё ещё остаются в одном Pod, если им действительно нужны общие `localhost`, том и судьба реплики. Получается промежуточная модель: процессы изолированы и наблюдаются отдельно, но Kubernetes всегда размещает и масштабирует их вместе.

Типичные роли:

| Роль | Пример | Зачем тот же Pod |
| --- | --- | --- |
| вспомогательный контейнер (`sidecar`) | агент отправки файловых логов | должен видеть локальный файл конкретной реплики |
| прокси / ambassador | mTLS-прокси или адаптер к внешнему API | перехватывает или проксирует соединения конкретного приложения через `localhost` |
| adapter | преобразует локальный формат метрик в формат системы мониторинга | читает данные конкретной реплики и публикует их рядом с ней |
| локальный служебный процесс | обновляет сертификат или конфигурационный файл | пишет данные в общий том, который читает приложение |

Названия `adapter` и `ambassador` описывают архитектурную роль, а не отдельные виды объектов Kubernetes. На уровне API это обычные контейнеры внутри одного Pod либо встроенные sidecars.

### Пример: приложение и обработчик файлового лога

Представим старое приложение, которое умеет писать access log только в файл. Вспомогательный контейнер читает этот файл и передаёт строки дальше:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: api-with-log-reader
spec:
  containers:
    - name: api
      image: registry.example/legacy-api:v1.2.3
      args:
        - --access-log=/var/log/app/access.log
      ports:
        - name: http
          containerPort: 8080
      volumeMounts:
        - name: logs
          mountPath: /var/log/app

    - name: log-reader
      image: busybox:1.36.1
      command:
        - sh
        - -c
        - touch /logs/access.log && tail -n +1 -f /logs/access.log
      volumeMounts:
        - name: logs
          mountPath: /logs

  volumes:
    - name: logs
      emptyDir: {}
```

Это учебный пример: `busybox` только печатает прочитанные строки в `stdout`. В реальной системе его место занимает Fluent Bit, Vector или другой агент доставки.

Оба контейнера находятся в `spec.containers`, поэтому Kubernetes не гарантирует, какой из них стартует первым. Команда `touch` заранее создаёт файл и позволяет `log-reader` безопасно начать работу даже раньше приложения. Если требуется строгий порядок запуска, используют встроенный sidecar, разобранный ниже.

Механика:

1. `kube-scheduler` размещает **весь Pod** на одном `Node`.
2. `kubelet` создаёт том `emptyDir`.
3. Оба контейнера подключают один том по разным путям.
4. Приложение пишет в `/var/log/app/access.log`.
5. `log-reader` видит тот же файл как `/logs/access.log`.
6. При масштабировании до трёх Pod появляются три пары `api + log-reader`.

Если вынести `log-reader` в случайный отдельный Pod, у него не будет доступа к `emptyDir` приложения и потеряется связь «один обработчик на одну реплику». Именно эта тесная связь оправдывает общий Pod.

Но если приложение умеет писать логи в `stdout`, отдельный sidecar часто не нужен: узловой агент логов может собирать вывод всех контейнеров. Sidecar добавляет потребление памяти и CPU, ещё один образ, конфигурацию и отдельный источник отказов.

`emptyDir` живёт столько же, сколько Pod. Перезапуск отдельного контейнера не удаляет том, но удаление Pod удаляет и его содержимое. Поэтому этот том подходит для обмена и временных данных, а не для единственной копии важного состояния.

### Пример: локальный прокси

Второй распространённый сценарий — прокси рядом с приложением:

```text
обычный трафик
      │
      ▼
Pod IP:8443
контейнер-прокси
      │  localhost:8080
      ▼
контейнер Go API
```

Прокси может завершать mTLS, добавлять телеметрию или применять сетевые правила, не меняя код Go-приложения. При масштабировании каждая реплика API получает собственный прокси, поэтому сохраняется связь один к одному.

Цена решения:

- прокси потребляет ресурсы в каждом Pod;
- ошибка его конфигурации может сделать недоступными все реплики;
- rollout приложения теперь также доставляет конфигурацию прокси;
- задержка запроса увеличивается хотя бы на локальную обработку прокси.

### Когда контейнеры нужно разделить

Не следует помещать в один Pod два обычных сервиса только потому, что они взаимодействуют.

| Вопрос | Если ответ «да» |
| --- | --- |
| компоненты нужно масштабировать независимо? | разные Pod |
| у компонентов разные циклы выпуска и владельцы? | разные Pod |
| один компонент должен пережить замену другого? | разные Pod |
| компоненты могут работать на разных узлах? | разные Pod |
| между ними достаточно сетевого API? | разные Pod и `Service` |
| процесс нужен только конкретной реплике и требует её локальные файлы или `localhost`? | один многоконтейнерный Pod может быть оправдан |

Плохие кандидаты для одного Pod:

- фронтенд и бэкенд;
- API и асинхронный обработчик;
- приложение и PostgreSQL;
- два микросервиса с разной нагрузкой.

Если Pod содержит `api` и `worker`, увеличение числа API с 3 до 10 автоматически создаст и 10 worker, даже если очередь этого не требует. Такая связка лишает компоненты независимого масштабирования.

## Init containers и sidecars

В Pod могут быть разные типы контейнеров. Встроенный sidecar (`native sidecar`) — это специальный вариант инициализационного контейнера, который не завершается после подготовки:

| Тип | Где описывается | Когда работает | Основная роль |
| --- | --- | --- | --- |
| контейнер приложения | `spec.containers` | во время основной работы Pod | выполняет бизнес-функцию или постоянную вспомогательную работу |
| обычный init container | `spec.initContainers` | выполняется до основных контейнеров и завершается | подготавливает файлы или проверяет предпосылки запуска |
| native sidecar | `spec.initContainers` с `restartPolicy: Always` | запускается в порядке init containers и продолжает работать рядом с приложением | постоянный помощник с управляемым порядком запуска и завершения |
| отладочный контейнер (`ephemeral container`) | добавляется в уже существующий Pod | временно во время диагностики | предоставляет отсутствующие в образе отладочные утилиты |

### Обычный init container

Обычные init containers выполняются строго по порядку. Каждый должен успешно завершиться до запуска следующего init container и основных контейнеров:

```yaml
spec:
  initContainers:
    - name: prepare-config
      image: registry.example/config-renderer:v2
      command:
        - /app/render
        - --output=/work/config.yaml
      volumeMounts:
        - name: work
          mountPath: /work

  containers:
    - name: api
      image: registry.example/api:v1.2.3
      args:
        - --config=/etc/app/config.yaml
      volumeMounts:
        - name: work
          mountPath: /etc/app

  volumes:
    - name: work
      emptyDir: {}
```

Порядок:

```text
prepare-config запускается
        │
        ├── ошибка → kubelet повторяет попытку согласно restart policy Pod
        │
        └── exit code 0
                 │
                 ▼
             запускается api
```

Подходящие задачи:

- сгенерировать конфигурационный файл;
- дождаться локально проверяемой предпосылки;
- скачать небольшой файл начальной загрузки;
- подготовить права или структуру временного тома.

Миграцию общей базы опасно запускать в init container каждой реплики: несколько Pod могут выполнять её одновременно, а rollout блокируется до завершения. Миграцию обычно оформляют отдельным `Job` и проектируют совместимость схемы со старой и новой версиями приложения.

### Native sidecar

В Kubernetes 1.33 native sidecars имеют стабильный статус (`stable`). Такой контейнер описывается среди `initContainers`, но получает `restartPolicy: Always`:

```yaml
spec:
  initContainers:
    - name: log-shipper
      image: registry.example/log-shipper:v3
      restartPolicy: Always
      volumeMounts:
        - name: logs
          mountPath: /logs

  containers:
    - name: api
      image: registry.example/api:v1.2.3
      volumeMounts:
        - name: logs
          mountPath: /logs
```

Несмотря на расположение в `initContainers`, `log-shipper` не завершается перед запуском `api`. После его успешного старта `kubelet` переходит к следующим init containers, а затем запускает основные контейнеры.

Преимущества native sidecar:

- можно гарантировать запуск помощника до основного контейнера;
- при завершении Pod основные контейнеры останавливаются раньше sidecars;
- завершившийся основной контейнер `Job` не ждёт бесконечного sidecar;
- sidecar независимо перезапускается при падении.

Обычный sidecar в `spec.containers` остаётся допустимым, если строгий порядок не нужен. Но Kubernetes не гарантирует порядок старта обычных контейнеров, а в `Job` бесконечно работающий обычный контейнер может не дать Pod завершиться.

Проверка готовности (`readiness probe`) native sidecar участвует в общей готовности Pod. Это полезно, если без прокси приложение нельзя обслуживать, но ошибочная probe помощника способна исключить из трафика здоровый основной процесс.

## Размещение и ресурсы Pod

`kube-scheduler` размещает Pod целиком на одном `Node`. Для одновременно работающих контейнеров их requests складываются.

Например:

```text
api:
  cpu request = 2000m
  memory request = 512Mi

proxy:
  cpu request = 500m
  memory request = 128Mi

итого для одновременной работы:
  cpu = 2000m + 500m = 2500m = 2.5 CPU
  memory = 512Mi + 128Mi = 640Mi
```

`1000m` CPU равно одному CPU. `kube-scheduler` ищет один узел, на котором одновременно помещаются 2.5 CPU, 640 MiB памяти и остальные требования Pod.

Для обычных init containers расчёт отличается, потому что они выполняются последовательно. Упрощённо `kube-scheduler` сравнивает:

1. сумму requests постоянно работающих контейнеров приложения и sidecars;
2. наибольший request обычного init container.

Эффективный request Pod должен покрывать большее из этих значений. Поэтому тяжёлый init container может потребовать крупный узел, даже если после запуска приложение использует мало ресурсов.

### Что происходит, если Pod не помещается

Предположим, в кластере есть только три узла по четыре CPU:

```text
Node A: 4 CPU
Node B: 4 CPU
Node C: 4 CPU
```

Создаётся Pod, которому нужно восемь CPU:

```yaml
spec:
  containers:
    - name: api
      image: registry.example/api:v1.2.3
      resources:
        requests:
          cpu: "8"
```

Свободные ресурсы трёх узлов нельзя сложить. Ни один Node не подходит, поэтому Kubernetes принимает объект, но контейнер не запускается. Pod остаётся `Pending`, а `spec.nodeName` не заполняется.

`kube-scheduler` возвращает Pod в очередь и повторяет попытки размещения. В событиях появляется `FailedScheduling`:

```text
Pod: api-7b9c8d6f5-k4m2p
Status: Pending
Node: <none>

Events:
  Warning  FailedScheduling
  0/3 nodes are available: 3 Insufficient cpu.
```

Причина видна через:

```bash
kubectl describe pod api-7b9c8d6f5-k4m2p
```

`kube-scheduler` сравнивает requests не с суммой ресурсов кластера и не с текущей загрузкой CPU, а со свободной частью `Allocatable` каждого узла после requests уже назначенных Pod. Даже Node с восемью CPU может не принять `requests.cpu: "8"`: часть ресурса зарезервирована для системы, а часть запрошена системными `DaemonSet`.

Возможные выходы:

| Изменение | Результат |
| --- | --- |
| на одном подходящем узле освободились ресурсы | `kube-scheduler` назначает ожидающий Pod при следующей попытке |
| добавлен более крупный Node | Pod запускается, если выполнены также правила размещения (`affinity`), отметки отторжения узла (`taint`), требования хранилища и другие ограничения |
| настроено автоматическое масштабирование узлов | autoscaler может создать Node, подходящий под requests ожидающего Pod |
| исправлен завышенный request | новый Pod из обновлённого шаблона может поместиться на существующий узел |
| Pod имеет более высокий приоритет (`Priority`) | `kube-scheduler` может вытеснить менее приоритетные Pod, если это освободит достаточно места на одном узле |
| задача допускает горизонтальное разделение | вместо одного большого Pod запускается несколько меньших |

Автомасштабирование не складывает маленькие машины. Если разрешённые типы Node имеют только четыре CPU, добавление ещё десяти таких узлов не поможет Pod с запросом восемь CPU.

Вытеснение (`preemption`) тоже помогает только тогда, когда после удаления менее приоритетных Pod требуемые ресурсы освобождаются **на одном узле**. Если Pod не помещается даже на полностью пустой Node, он останется `Pending` до изменения requests или конфигурации узлов.

Если ожидающий Pod принадлежит `Deployment`, `ReplicaSet` уже считает его существующей репликой и не создаёт бесконечные замены. Но нужное число готовых реплик не достигается, поэтому rollout может остановиться в ожидании.

## Кто и что перезапускает

Нужно разделять жизненный цикл контейнера и жизненный цикл Pod:

| Событие | Кто реагирует | Результат |
| --- | --- | --- |
| процесс контейнера завершился | `kubelet` | может перезапустить этот контейнер внутри того же Pod |
| обычный init container завершился с ошибкой | `kubelet` | повторяет init container либо завершает Pod при `restartPolicy: Never` |
| native sidecar завершился | `kubelet` | перезапускает sidecar из-за его `restartPolicy: Always` |
| Pod удалён | контроллер нагрузки | создаёт новый Pod, если наблюдаемое число реплик стало меньше желаемого |
| рабочий узел потерян | control plane и контроллер нагрузки | после обнаружения отказа создаётся заменяющий Pod на доступном узле |

Поле Pod `restartPolicy` принимает:

| Значение | Поведение |
| --- | --- |
| `Always` | `kubelet` перезапускает контейнер после любого завершения |
| `OnFailure` | перезапускает при ненулевом exit code |
| `Never` | не перезапускает завершившийся контейнер |

У `Deployment` допустим только `restartPolicy: Always`. `Job` обычно использует `OnFailure` или `Never`.

Падение одного контейнера не означает автоматический перезапуск остальных контейнеров Pod. Например, `api` может продолжать работать, пока его `log-reader` находится в `CrashLoopBackOff`. В этот момент контейнер помощника не готов, поэтому весь Pod также не считается Ready. Если процесс помощника работает, но не может выполнять свою функцию, это дополнительно отражают через readiness probe.

`CrashLoopBackOff` обычно означает, что `kubelet` уже несколько раз запускал контейнер, процесс снова завершался, и теперь между попытками действует увеличивающаяся задержка. UID и IP Pod при перезапуске отдельного контейнера не меняются.

Если заменяется весь Pod, новый объект получает другой UID и обычно другой IP. Kubernetes не переносит существующий Pod между узлами.

Проверки состояния и корректное завершение Go-процесса подробно разобраны в [материале про probes и graceful shutdown](./07-probes-and-graceful-shutdown.md).

## Pod phase и состояние контейнера

Pod phase — грубое итоговое состояние всего Pod:

| Phase | Смысл |
| --- | --- |
| `Pending` | Pod принят API, но один или несколько контейнеров ещё не готовы к запуску |
| `Running` | Pod назначен узлу, контейнеры созданы, хотя бы один основной контейнер работает или запускается повторно |
| `Succeeded` | все контейнеры завершились успешно и не будут перезапущены |
| `Failed` | все контейнеры завершились, и хотя бы один завершился неуспешно либо Pod завершён системой как failed |
| `Unknown` | состояние Pod не удалось получить, обычно из-за потери связи с рабочим узлом |

У каждого контейнера есть отдельное состояние:

| Container state | Смысл |
| --- | --- |
| `Waiting` | контейнер ещё не запущен, например загружается образ или действует restart backoff |
| `Running` | процесс контейнера работает |
| `Terminated` | процесс завершился; status содержит reason, exit code и время завершения |

`CrashLoopBackOff`, `ImagePullBackOff` и `Terminating` — не значения Pod phase. Колонка `STATUS` в `kubectl get pods` формирует удобное человекочитаемое описание из нескольких полей.

Поэтому возможна ситуация:

```text
Pod phase: Running

api container:
  state: Running

log-reader container:
  state: Waiting
  reason: CrashLoopBackOff
```

Одной общей фразы «Pod работает» недостаточно: для многоконтейнерного Pod нужно проверять состояние каждого контейнера и общую готовность.

## Практическая диагностика

```bash
# На каком Node находится Pod и какой у него IP
kubectl get pod api-abc -o wide

# События размещения, проверки, тома и состояния всех контейнеров
kubectl describe pod api-abc

# Логи конкретного контейнера
kubectl logs api-abc -c api
kubectl logs api-abc -c log-reader

# Логи предыдущего запуска упавшего контейнера
kubectl logs api-abc -c log-reader --previous

# Потребление ресурсов по контейнерам, если доступен Metrics API
kubectl top pod api-abc --containers
```

Если в Pod несколько контейнеров, для `logs` и `exec` лучше явно указывать `-c`: это делает диагностику воспроизводимой. `port-forward` не выбирает контейнер — он направляет соединение в общую сеть Pod, поэтому важно понимать, какой процесс слушает указанный порт.

Минимальный маршрут:

```text
Pod Pending
  → describe
  → FailedScheduling / события тома / события образа

Pod Running, но не Ready
  → describe
  → readiness каждого контейнера

Контейнер перезапускается
  → logs --previous
  → last state, reason и exit code
```

## Interview-ready answer

**1. Зачем Kubernetes нужен Pod, если уже есть контейнер?**

Pod задаёт атомарную единицу размещения и жизненного цикла. Kubernetes назначает Pod одному Node, выдаёт ему сетевую идентичность, подключает тома и управляет всеми его контейнерами как одним экземпляром приложения.

**2. Чем Pod отличается от контейнера?**

Контейнер содержит процесс и его изолированное окружение. Pod — объект Kubernetes, который содержит один или несколько контейнеров, общий IP, доступные тома и правила запуска. Контейнер отдельно не является единицей размещения Kubernetes.

**3. Когда несколько контейнеров стоит поместить в один Pod?**

Когда они тесно связаны, должны всегда находиться на одном Node, общаться через `localhost` или общий том и масштабироваться один к одному. Например, приложение и локальный mTLS-прокси. Независимо масштабируемые сервисы размещают в разных Pod.

**4. Что контейнеры одного Pod разделяют, а что нет?**

Они разделяют IP и пространство портов, могут подключать общие тома и всегда размещаются вместе. Корневые файловые системы, переменные окружения и пространство имён процессов по умолчанию раздельные.

**5. Что произойдёт, если Pod не помещается ни на один Node?**

Он останется `Pending`, а в событиях появится `FailedScheduling`. `kube-scheduler` повторяет попытки, но не складывает ресурсы разных узлов. Нужен достаточно крупный Node, освобождение ресурсов, корректировка requests или разделение задачи.

**6. Падение одного контейнера пересоздаёт весь Pod?**

Нет. `kubelet` может перезапустить только упавший контейнер внутри того же Pod. Новый Pod создаётся контроллером при удалении или потере старого; он получает новый UID и обычно новый IP.

**7. Чем init container отличается от sidecar?**

Обычный init container должен успешно завершиться до запуска основных контейнеров. Native sidecar описывается в `initContainers` с `restartPolicy: Always`: он запускается в упорядоченной init-последовательности, но продолжает работать рядом с приложением.

**8. Является ли `CrashLoopBackOff` фазой Pod?**

Нет. Это причина ожидания конкретного контейнера между повторными запусками. Pod phase при этом может оставаться `Running` или `Pending`; точную причину смотрят в состоянии контейнера, событиях и предыдущих логах.
