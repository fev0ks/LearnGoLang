REST — не протокол и не формат, а набор архитектурных ограничений, описанный Роем Филдингом в диссертации 2000 года. На практике словом «REST API» называют почти любой HTTP API с JSON, и расхождение между этим бытовым значением и исходным определением — самая частая тема вопросов на собеседовании.

## Что такое REST на самом деле

Обычный ответ «REST это когда `GET /users/42` и JSON» описывает частный случай, а не стиль. Стиль задаётся ограничениями, из которых следуют полезные свойства системы:

| Ограничение | Что требует | Что даёт взамен |
| --- | --- | --- |
| Клиент-сервер | разделение хранения данных и интерфейса | стороны развиваются независимо |
| Отсутствие состояния | каждый запрос самодостаточен | любой узел может обслужить любой запрос |
| Кэшируемость | ответ помечен как кэшируемый или нет | часть запросов вообще не доходит до сервера |
| Единообразный интерфейс | ресурсы, представления, самоописываемые сообщения | клиент не знает внутреннего устройства сервера |
| Слоистая система | клиент не знает, отвечает ли ему сервер или посредник | появляются CDN, прокси, балансировщики |
| Код по требованию (необязательно) | сервер может прислать исполняемый код | редко используется, единственное необязательное ограничение |

Практическая ценность здесь не в терминах, а в следствиях. Отсутствие состояния — причина, по которой сервисы масштабируются добавлением реплик. Кэшируемость и слоистость — причина, по которой перед приложением можно поставить CDN, и оно об этом не узнает. Единообразный интерфейс — причина, по которой сторонний разработчик понимает API без чтения кода сервера.

## Шесть ограничений Филдинга

Разберём те, которые нарушают чаще всего.

**Отсутствие состояния** означает не «нет базы данных», а «сервер не хранит контекст между запросами клиента». Сессия в памяти процесса нарушает ограничение: запрос обязан попасть на тот же инстанс, появляются липкие сессии и боль при выкатке. Токен, который клиент присылает с каждым запросом, ограничение соблюдает.

**Кэшируемость** требует, чтобы ответ явно сообщал о своей пригодности к кэшированию. На практике это `Cache-Control` в каждом ответе, а не «мы решили, что это можно кэшировать» на стороне клиента. Разбор директив — [04-realtime/02-sse.md](../04-realtime/02-sse.md) и [request-lifecycle](../../request-lifecycle/06-response-return-caching-and-browser-rendering.md).

**Единообразный интерфейс** — самое содержательное и самое размытое ограничение. Оно распадается на четыре части:

- идентификация ресурсов — у сущности есть устойчивый адрес;
- манипуляция через представления — клиент получает представление (JSON, XML), а не внутренний объект, и меняет ресурс, отправляя новое представление;
- самоописываемые сообщения — в сообщении достаточно информации, чтобы его обработать: метод, тип содержимого, директивы кэширования;
- гипермедиа как двигатель состояния приложения — переходы клиент берёт из ссылок в ответе, а не зашивает в код.

Последний пункт и есть HATEOAS, и именно он в реальных API почти отсутствует.

**Слоистая система** объясняет, почему нельзя полагаться на прямое соединение с клиентом: между вами и им стоят CDN, балансировщик, сервисная сетка. Отсюда требование не привязывать логику к IP-адресу источника и читать реальный адрес из заголовков, которые ставит край сети.

## Уровни зрелости Ричардсона

Модель Леонарда Ричардсона описывает, насколько API использует возможности HTTP. Она полезна именно как язык для разговора: «у нас уровень 2» короче, чем перечислять свойства.

```text
Уровень 0 — один адрес, один метод
    POST /api  { "action": "getUser", "id": 42 }
    HTTP используется как транспорт для своего RPC; так работает SOAP

Уровень 1 — ресурсы
    POST /users/42  { "action": "get" }
    появились адреса сущностей, но метод по-прежнему один

Уровень 2 — HTTP-методы и коды ответов
    GET /users/42        → 200
    DELETE /users/42     → 204
    POST /users          → 201 + Location
    методы несут семантику, коды отражают результат; здесь находится ~99% API

Уровень 3 — гипермедиа
    GET /users/42 → { "id": 42, "_links": { "orders": "/users/42/orders" } }
    клиент узнаёт доступные переходы из ответа
```

Практический вывод: уровень 2 — это норма индустрии и разумная цель. Уровень 3 окупается редко, и честный ответ на собеседовании звучит так: «наш API соответствует второму уровню, третий не внедряли осознанно, потому что цена выше выгоды».

## HATEOAS: почему его почти никто не делает

Идея: сервер в каждом ответе перечисляет возможные следующие действия, а клиент не хранит знание о структуре адресов. Тогда сервер может менять адреса, не ломая клиентов.

```json
{
  "id": 42,
  "status": "pending",
  "_links": {
    "self":   { "href": "/orders/42" },
    "pay":    { "href": "/orders/42/payment", "method": "POST" },
    "cancel": { "href": "/orders/42", "method": "DELETE" }
  }
}
```

Здесь есть и второе, менее очевидное свойство: набор ссылок зависит от состояния. У оплаченного заказа не будет ссылки `pay`, и клиенту не нужно дублировать у себя правила перехода состояний.

Почему на практике не приживается:

- клиенты всё равно пишутся под конкретную версию API, и разработчик зашивает адреса, даже когда ссылки есть;
- генераторы клиентов из OpenAPI работают с фиксированными адресами, а не с гипермедиа;
- растёт размер ответа и число решений в клиенте, а выигрыш от «свободы менять адреса» на практике съедается версионированием;
- нет единого формата: HAL, JSON:API, Siren, собственный `_links` — договариваться приходится каждый раз.

Где гипермедиа действительно работает: платёжные и банковские API с длинными сценариями, где следующий шаг зависит от состояния операции, и публичные API с очень долгой жизнью и неизвестными клиентами.

## Коды ответов: карта по классам

Код ответа — часть единообразного интерфейса: он сообщает результат так, чтобы посредники (кэши, прокси, клиентские библиотеки) могли принять решение, не разбирая тело. Отсюда практическое требование: код обязан отражать результат честно. Ответ `200 OK` с телом `{"error": "not found"}` ломает и кэширование, и повторные попытки, и мониторинг — это самый частый антипаттерн, потому что «клиенту так удобнее парсить».

| Класс | Смысл | Что делает клиент по умолчанию |
| --- | --- | --- |
| 1xx | промежуточный ответ, обработка продолжается | ждёт окончательный ответ |
| 2xx | запрос принят и обработан | считает операцию успешной |
| 3xx | нужно обратиться в другое место или использовать кэш | следует за перенаправлением или берёт локальную копию |
| 4xx | ошибка на стороне клиента, повтор без изменений не поможет | не повторяет запрос, показывает ошибку |
| 5xx | ошибка на стороне сервера, запрос сам по себе корректен | может повторить с выдержкой, если операция идемпотентна |

Граница 4xx и 5xx — это не «где сломалось», а «кому чинить»: 4xx говорит «поправь запрос», 5xx — «попробуй позже, чиним мы». Поэтому невалидные данные от клиента никогда не 5xx, а исчерпание пула соединений к базе никогда не 4xx.

### 1xx — промежуточные

- `100 Continue` — ответ на заголовок `Expect: 100-continue`: клиент спрашивает разрешение прислать большое тело, сервер отвечает «шли» или сразу отказывает, экономя трафик.
- `103 Early Hints` — ранняя подсказка браузеру о ресурсах, которые стоит начать загружать, пока сервер готовит ответ. Практическая замена мёртвого server push из HTTP/2 ([02-http/01-http-versions.md](../02-http/01-http-versions.md)).

### 2xx — успех

| Код | Когда | Тонкость |
| --- | --- | --- |
| 200 OK | успешная операция с телом ответа | для создания ресурса лучше 201 |
| 201 Created | ресурс создан | обязателен заголовок `Location` с адресом созданного ресурса |
| 202 Accepted | запрос принят, но ещё не выполнен | асинхронная обработка: в теле или `Location` — адрес для проверки статуса |
| 204 No Content | успех без тела | тело обязано быть пустым, иначе клиенты ломаются |
| 206 Partial Content | отдана часть ресурса | ответ на `Range`, см. раздел про частичные ответы ниже |

Три развилки внутри класса, на которых чаще всего выбирают неправильно:

- **200 против 201** — `201` отдают, когда запрос создал ресурс, и обязательно с заголовком `Location`, указывающим на него. Возврат `200` без `Location` заставляет клиента гадать, где теперь лежит созданное, и вытаскивать адрес из тела ответа.
- **201 против 202** — это выбор контракта, а не стиля: `202` честно говорит «работа поставлена в очередь», и клиент обязан опрашивать статус. Если операция на самом деле выполнена синхронно, `202` вводит в заблуждение и порождает лишний опрос. Обратная ошибка тяжелее: `201` на поставленную в очередь задачу означает обещание, что ресурс уже существует, а его ещё нет.
- **202 и его завершение** — у асинхронной операции должен быть понятный конец: ресурс статуса отвечает `303 See Other` с адресом готового результата, и клиент перестаёт опрашивать один и тот же адрес вечно.
- **204 против 200 с пустым телом** — `204` означает «тела нет и не будет», и клиенты вправе даже не пытаться его читать. `200` с нулевой длиной формально корректен, но ломает библиотеки, которые ожидают разбираемое тело при `200`.

### 3xx — перенаправления и кэш

| Код | Когда | Тонкость |
| --- | --- | --- |
| 300 Multiple Choices | у ресурса несколько представлений, выбор за клиентом | почти не используется, согласование делают через `Accept` |
| 301 Moved Permanently | адрес изменился навсегда | браузеры исторически меняют метод на `GET`; кэшируется агрессивно и надолго |
| 302 Found | временное перенаправление | тоже меняет метод на `GET`; в новом коде вместо него берут 307 или 303 |
| 303 See Other | «результат смотри по другому адресу», метод всегда меняется на `GET` | штатный ответ после `POST`, чтобы обновление страницы не повторило операцию; в API — указатель на ресурс статуса асинхронной задачи |
| 304 Not Modified | представление не изменилось | не перенаправление: ответ на условный запрос, тело пустое, клиент использует свою копию |
| 307 Temporary Redirect | временное перенаправление с сохранением метода и тела | единственный безопасный временный вариант для `POST` |
| 308 Permanent Redirect | постоянное перенаправление с сохранением метода и тела | постоянный аналог 307 |

Развилки внутри класса:

- **301 против 302** — постоянный переезд против временного. Разница не в семантике ответа, а в поведении клиента дальше: `301` кэшируется агрессивно и надолго, поэтому ошибочный постоянный редирект живёт у пользователей месяцами и правится только сменой адреса.
- **302 против 307** — оба временные, но `307` гарантирует сохранение метода и тела, а `302` исторически превращает `POST` в `GET`. Для API это значит, что редирект `POST` через `302` тихо теряет тело запроса.
- **303 против 307** — решают противоположные задачи. `303` меняет метод на `GET` намеренно: после `POST` уводит клиента к результату, и обновление страницы уже не повторит операцию. `307` наоборот обещает повторить запрос как есть по другому адресу.
- **304 в этом классе особняком** — это не перенаправление, а ответ на условный запрос: тело пустое, клиент использует свою копию. Разбор — в разделе про условные запросы ниже.
- **305 и 306** объявлены устаревшими и в живых системах не встречаются.

Развёрнутое сравнение постоянных и временных вариантов с историей смены метода — в разделе про редиректы ниже.

### 4xx — ошибка клиента

| Код | Когда | С чем путают |
| --- | --- | --- |
| 400 Bad Request | запрос не разобрать: сломанный JSON, неверный тип | с 422, где разобрать удалось |
| 401 Unauthorized | нет удостоверения личности или оно невалидно | с 403; сопровождается `WWW-Authenticate` |
| 403 Forbidden | личность известна, прав нет | с 401 и с 404 |
| 404 Not Found | ресурса нет | с 403 при скрытии существования |
| 405 Method Not Allowed | адрес есть, метод не поддерживается | обязателен заголовок `Allow` со списком методов |
| 406 Not Acceptable | не можем отдать в запрошенном представлении | с 415: 406 про `Accept`, 415 про `Content-Type` |
| 409 Conflict | конфликт с текущим состоянием ресурса | с 412: 409 без условного заголовка |
| 410 Gone | ресурс существовал и удалён навсегда | с 404: 410 сообщает, что возвращаться не за чем |
| 412 Precondition Failed | не выполнено условие из `If-Match` или `If-Unmodified-Since` | с 409 |
| 413 Content Too Large | тело больше допустимого | часто отдаёт прокси, а не приложение |
| 415 Unsupported Media Type | не принимаем такой `Content-Type` | с 406 |
| 422 Unprocessable Content | синтаксис верный, смысл — нет | с 400 |
| 428 Precondition Required | сервер требует условный запрос | защита от слепой перезаписи |
| 429 Too Many Requests | превышен лимит | обязателен `Retry-After`, см. [05-integration-patterns/03-rate-limiting.md](../05-integration-patterns/03-rate-limiting.md) |

Четыре пары внутри этого класса вызывают больше всего споров на ревью, и именно их разбирают на собеседовании:

- **400 против 422** — `400` означает «не смог разобрать»: сломанный JSON, поле не того типа, нет обязательного поля. `422` означает «разобрал, но принять не могу»: отрицательная сумма, дата в прошлом, недопустимый переход статуса. Граница проходит по линии «синтаксис против смысла». На практике многие API отдают `400` на всё, и это допустимо, если в теле есть машинно-читаемый код ошибки; недопустимо другое — смешивать их с `401`, `403` и `404`.
- **401 против 403** — `401` значит «не знаю, кто ты»: токена нет, он истёк или невалиден, и ответ должен содержать `WWW-Authenticate`. `403` значит «знаю, кто ты, и тебе нельзя». Практическое следствие важнее формулировки: получив `401`, клиент идёт обновлять токен, а получив `403` — не идёт, потому что новый токен ничего не изменит. Перепутанные коды дают бесконечный цикл обновления токена.
- **404 против 403** — вопрос не семантики, а модели безопасности: `403` подтверждает, что ресурс существует. Для платежей, чужих документов и всего, где сам факт существования является информацией, отвечают `404`. Для явно своих коллекций пользователя `403` понятнее и не мешает отладке. Правило: скрывать существование нужно там, где перебор адресов даёт злоумышленнику полезное знание.
- **409 против 412** — `412` это ответ на несоблюдённое предусловие из заголовка (`If-Match`), то есть механика оптимистичной блокировки. `409` — конфликт с текущим состоянием без всяких условных заголовков: попытка создать дубликат, перевести заказ из «отменён» в «оплачен». Если клиент прислал предусловие и оно не выполнено — `412`; если предусловия не было, а операция противоречит состоянию — `409`.

### 5xx — ошибка сервера

| Код | Когда | Практическая деталь |
| --- | --- | --- |
| 500 Internal Server Error | необработанная ошибка внутри приложения | наружу не должно утекать содержимое исключения |
| 501 Not Implemented | метод не поддерживается сервером в принципе | редкий, не путать с 405 |
| 502 Bad Gateway | посредник получил невалидный ответ от источника | обычно отдаёт прокси, а не приложение |
| 503 Service Unavailable | сервис временно не готов | сопровождается `Retry-After`; правильный ответ при перегрузке и на время обслуживания |
| 504 Gateway Timeout | источник не ответил вовремя | приходит от прокси, чей таймаут короче времени обработки |

Развилки внутри класса:

- **500 против 503** — разница в том, что делать клиенту. `503` означает «повтори позже», и клиент с автоматическими повторами поступит правильно; `500` означает «повтор не поможет», и настойчивые попытки только усилят нагрузку. Перегруженный сервис обязан отвечать `503` с `Retry-After`, а не «пятисоткой» из-за исчерпанного пула соединений.
- **502 против 504** — оба приходят от посредника и говорят о разном. `502` значит «источник ответил чем-то невалидным или разорвал соединение», `504` — «источник не ответил вовремя». Первое обычно означает упавший процесс или несовместимый протокол, второе — что таймаут прокси короче реального времени обработки.
- **500 против 4xx** — граница не «где произошло исключение», а «кому чинить». Необработанная паника при валидных данных это `500`, а невалидные данные от клиента остаются `4xx`, даже если внутри они тоже вызвали исключение.
- **Что отдавать в теле** — наружу идёт обезличенное сообщение и идентификатор запроса, подробности только в логах. Утечка текста исключения и стека это одновременно и подсказка атакующему, и бесполезная для клиента информация.
- **501 против 405** — `501` значит «сервер вообще не умеет такой метод», `405` — «умеет, но не для этого ресурса», и во втором случае обязателен заголовок `Allow` со списком допустимых методов.

## Согласование представлений

Один ресурс может иметь несколько представлений, и выбор происходит по заголовкам запроса. Это часть единообразного интерфейса, про которую вспоминают редко.

```http
GET /reports/42 HTTP/1.1
Accept: application/json, application/xml;q=0.8
Accept-Language: ru-RU, en;q=0.5
Accept-Encoding: gzip, br
```

Сервер выбирает представление и обязан сообщить, по какому заголовку оно менялось:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Language: ru-RU
Vary: Accept, Accept-Language, Accept-Encoding
```

Заголовок `Vary` здесь не формальность: без него общий кэш отдаст русскую версию англоязычному клиенту, а сжатый ответ — клиенту, который сжатие не поддерживает. Обратная крайность тоже вредна — `Vary: Cookie` практически отключает кэширование, потому что каждое значение cookie порождает отдельную запись.

Отдельное применение согласования — версионирование через тип содержимого: `Accept: application/vnd.example.v2+json` вместо `/v2/` в адресе. Формально чище, на практике неудобнее: версию не видно в логах и в адресной строке, её сложнее задать в curl, и большинство команд остаётся на версии в пути ([09-versioning-and-evolution.md](../../api-design/09-versioning-and-evolution.md)).

## Условные запросы: кэш и оптимистичная блокировка

`ETag` обычно объясняют через экономию трафика, но у него есть вторая роль — защита от потери обновлений при конкурентной записи, и на собеседовании чаще спрашивают именно её.

**Для чтения** клиент присылает последний известный отпечаток и получает пустой ответ, если ничего не изменилось:

```http
GET /orders/42
If-None-Match: "v7"

HTTP/1.1 304 Not Modified
```

**Для записи** тот же отпечаток превращается в условие «изменяй, только если версия не поменялась»:

```text
Клиент A: GET /orders/42 → ETag: "v7", status=pending
Клиент B: GET /orders/42 → ETag: "v7", status=pending

Клиент A: PATCH /orders/42, If-Match: "v7"  → 200, теперь ETag: "v8"
Клиент B: PATCH /orders/42, If-Match: "v7"  → 412 Precondition Failed
          B перечитывает ресурс и решает, что делать с чужим изменением
```

Без `If-Match` второй клиент молча затёр бы изменение первого — классическая потеря обновления. Код `412 Precondition Failed` означает «условие не выполнено», в отличие от `409 Conflict`, который говорит о конфликте состояния без привязки к условному заголовку.

Практические детали:

- отпечаток бывает сильным (`"v7"`) и слабым (`W/"v7"`): слабый допускает семантически эквивалентные, но байтово разные представления, и для `If-Match` не годится;
- источником отпечатка удобно делать версию строки в базе или её `xmin`, а не хеш тела — тогда сравнение дешёвое и точное;
- `If-Unmodified-Since` решает ту же задачу через время, но точность в одну секунду делает его ненадёжным при частых изменениях;
- требование `If-Match` можно сделать обязательным: ответ `428 Precondition Required` заставляет клиента работать по правилам.

## Редиректы: 301, 302, 307, 308

Четыре кода различаются по двум признакам: постоянный ли переезд и сохраняется ли метод запроса.

| Код | Переезд | Метод при повторе | Когда применять |
| --- | --- | --- | --- |
| 301 Moved Permanently | постоянный | исторически меняется на GET | адрес изменился навсегда, тело не важно |
| 302 Found | временный | исторически меняется на GET | временное перенаправление, в новом коде лучше избегать |
| 303 See Other | не переезд, а указание на результат | всегда меняется на GET, и это намеренно | после `POST`, чтобы обновление страницы не повторило операцию |
| 307 Temporary Redirect | временный | сохраняется | временное перенаправление с сохранением POST |
| 308 Permanent Redirect | постоянный | сохраняется | постоянный переезд с сохранением POST |

Историческая путаница здесь настоящая: спецификация для 301 и 302 требовала сохранять метод, но браузеры повсеместно превращали `POST` в `GET`, и это поведение закрепилось. Коды 307 и 308 ввели именно для того, чтобы явно обещать сохранение метода.

Практические следствия:

- для API редирект на `POST` без 307 или 308 приводит к тихой потере тела запроса;
- постоянные редиректы кэшируются браузером агрессивно и надолго, поэтому ошибочный 301 живёт у пользователей месяцами — временный переезд оформляют 302 или 307;
- клиент в Go по умолчанию следует за редиректами до десяти раз, и при этом заголовок `Authorization` не переносится на другой хост; поведение настраивается через `CheckRedirect` ([02-http/03-client-in-go.md](../02-http/03-client-in-go.md)).

## Частичные ответы: Range и 206

Механизм, о котором вспоминают, только когда нужно докачивать файлы или перематывать видео.

```http
GET /files/report.pdf
Range: bytes=1000000-1999999

HTTP/1.1 206 Partial Content
Content-Range: bytes 1000000-1999999/5242880
Accept-Ranges: bytes
Content-Length: 1000000
```

Сервер объявляет поддержку заголовком `Accept-Ranges: bytes`, клиент запрашивает диапазон, получает `206` и указание, какой именно кусок пришёл. Если диапазон невалиден, ответ — `416 Range Not Satisfiable`.

Зачем это нужно на практике: докачка после обрыва без повторной передачи мегабайтов, перемотка медиа без загрузки целого файла, параллельная загрузка кусками. В Go `http.ServeContent` и `http.ServeFile` обрабатывают `Range` самостоятельно, поэтому чаще всего достаточно отдавать файл через них, а не писать байты вручную.

Тонкость про кэш и условные запросы: докачка должна проверять, что файл не изменился между попытками, — для этого вместе с `Range` присылают `If-Range` с отпечатком. Если ресурс изменился, сервер отдаст полный ответ `200` вместо куска, и клиент начнёт заново.

## CORS: почему браузер не пускает запрос

Строго говоря, это не про REST, но именно здесь чаще всего ломается работа фронтенда с API, а причина непонятна из сообщения об ошибке.

Правило источника запрещает странице читать ответ с другого источника (схема, хост или порт отличаются). CORS — механизм, которым сервер разрешает такое чтение. Ключевые факты, которые снимают большую часть путаницы:

- ограничение работает в браузере, а не на сервере: curl и запрос с другого сервера идут без всякого CORS;
- при простом запросе браузер отправляет его на сервер и лишь потом решает, отдавать ли ответ странице; то есть запрос уже выполнился, даже если код увидел ошибку;
- при непростом запросе (метод кроме GET, HEAD, POST, нестандартные заголовки, тип содержимого кроме трёх разрешённых) сначала отправляется предварительный запрос `OPTIONS`.

```http
OPTIONS /orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PATCH
Access-Control-Request-Headers: content-type, authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 600
```

Типичные ошибки в продакшене:

- `Access-Control-Allow-Origin: *` вместе с `Access-Control-Allow-Credentials: true` не работает: при отправке учётных данных источник обязан быть указан явно;
- забытый `Access-Control-Max-Age` означает предварительный запрос перед каждым обращением, то есть удвоение числа запросов;
- обработчик `OPTIONS` не должен требовать аутентификации: предварительный запрос идёт без токена;
- при ответе с динамическим источником нужен `Vary: Origin`, иначе общий кэш отдаст чужому источнику разрешение, выданное первому.

## Что в REST переоценено

Несколько утверждений, которые стоит уметь оспорить.

**«REST требует JSON».** Формат не оговорён вообще: REST совместим с XML, protobuf, HTML. JSON — индустриальная привычка, а не требование стиля.

**«Если есть `GET /users/42`, это REST».** Это уровень 2 модели Ричардсона и соблюдение части ограничений. Полное соответствие требует гипермедиа, а его почти никто не делает — и это нормально, если названо своим именем.

**«REST медленнее gRPC, поэтому хуже».** Разница в сериализации и мультиплексировании имеет значение на внутреннем трафике с большими объёмами; для публичного API преимущество совместимости, кэширования и отладки обычно перевешивает. Сравнение — [00-protocol-comparison.md](../00-protocol-comparison.md).

**«REST не умеет стриминг».** Сам стиль этому не мешает: поток от сервера к клиенту делается через [SSE](../04-realtime/02-sse.md), двусторонний обмен — через [WebSocket](../04-realtime/01-websocket.md). Ограничение не в REST, а в модели «запрос-ответ».

## Interview-ready answer

**1. Что такое REST и чем он отличается от «HTTP API с JSON»?**

- REST — набор архитектурных ограничений (клиент-сервер, отсутствие состояния, кэшируемость, единообразный интерфейс, слоистость, необязательный код по требованию), а не протокол и не формат данных.
- Из ограничений следуют практические свойства: масштабирование репликами, возможность поставить CDN и прокси, понятность API стороннему разработчику.
- Бытовое «REST API» обычно означает второй уровень зрелости Ричардсона: ресурсы в адресах, осмысленные методы и коды ответов.
- Честная формулировка на собеседовании — назвать свой уровень и объяснить, какие ограничения соблюдаются, а какие нет и почему.

**2. Что такое уровни зрелости Ричардсона?**

- Нулевой — один адрес и один метод, HTTP как транспорт для своего RPC.
- Первый — появились ресурсы с адресами, но метод по-прежнему один.
- Второй — методы несут семантику, коды ответов отражают результат; здесь находится подавляющее большинство реальных API.
- Третий — гипермедиа: доступные переходы приходят в ответе, а не зашиты в клиенте.
- Практический вывод — второй уровень это разумная цель, третий внедряют осознанно и редко.

**3. Что такое HATEOAS и почему он редко используется?**

- Идея — сервер перечисляет в ответе возможные следующие действия, набор ссылок зависит от состояния ресурса.
- Обещание — сервер может менять адреса, не ломая клиентов, а правила перехода состояний не дублируются в клиенте.
- Почему не приживается — клиенты всё равно пишутся под версию API и зашивают адреса, генераторы из OpenAPI работают с фиксированными путями, единого формата ссылок нет.
- Где оправдан — длинные сценарии с состоянием (платежи, банковские операции) и публичные API с неизвестными долгоживущими клиентами.

**4. Как решить проблему потери обновления при конкурентной записи?**

- Механизм — условные запросы: сервер отдаёт `ETag`, клиент присылает его обратно в `If-Match` при изменении.
- Поведение — если версия изменилась, сервер отвечает `412 Precondition Failed`, и клиент перечитывает ресурс вместо затирания чужой записи.
- Отличие от `409 Conflict` — `412` говорит именно о невыполненном условии из заголовка, а `409` о конфликте состояния в общем смысле.
- Источник версии — номер версии строки или системная версия записи в базе; слабые отпечатки (`W/"..."`) для этой задачи не подходят.

**5. Чем 302 отличается от 307?**

- Оба означают временное перенаправление, но 307 гарантирует сохранение метода и тела запроса.
- Исторически браузеры при 301 и 302 превращали `POST` в `GET`, и это поведение закрепилось вопреки спецификации.
- Для API это означает тихую потерю тела при редиректе `POST` без 307 или 308.
- Постоянные коды (301 и 308) агрессивно кэшируются, поэтому ошибочный постоянный редирект живёт у пользователей месяцами.

**6. Почему запрос из браузера падает с ошибкой CORS, а из curl работает?**

- Проверка выполняется браузером, а не сервером: curl и серверные клиенты правило источника не применяют.
- При простом запросе браузер уже отправил его на сервер и лишь потом отказался отдать ответ странице — побочные эффекты на сервере при этом произошли.
- Непростой запрос (метод кроме GET, HEAD, POST, свои заголовки, иной тип содержимого) предваряется запросом `OPTIONS`, который должен обрабатываться без аутентификации.
- Частые ошибки — `*` вместе с передачей учётных данных, отсутствие `Access-Control-Max-Age` (предварительный запрос на каждое обращение) и отсутствие `Vary: Origin` при динамическом источнике.
