CDN (`Content Delivery Network`) — распределённая сеть узлов, которая принимает запрос
рядом с пользователем и по возможности отвечает сохранённой копией. Она уменьшает
задержку и исходящий трафик origin, но добавляет распределённое состояние: разные узлы
могут временно хранить разные версии объекта.

Слово «кэш» здесь не означает один Redis перед приложением. CDN состоит из множества
общих HTTP-кэшей, маршрутизации, управляющей плоскости для настроек и инвалидаций, а
также каналов получения данных из origin.

---

## Какую проблему решает CDN

Пусть изображения товара хранятся только в одном регионе. Пользователь на другом
континенте платит за каждый запрос межконтинентальным временем передачи, а origin
обрабатывает один и тот же неизменный файл миллионы раз.

CDN решает три задачи:

1. **Задержка.** Копия находится на ближайшем узле присутствия (`Point of Presence`,
   PoP), поэтому большая часть пути заканчивается рядом с пользователем.
2. **Разгрузка origin.** Повторные запросы не доходят до исходного хранилища и
   приложения.
3. **Устойчивость.** При разрешённой политике узел может временно отдать устаревшую
   копию, когда origin недоступен.

CDN не делает любые данные кэшируемыми. Персональная корзина, банковский баланс и
одноразовый токен требуют другой политики, чем изображение с хешем содержимого в URL.
Сначала определяется контракт свежести и доступа, затем настраивается кэш.

## Простая ментальная модель

Для каждого запроса CDN отвечает на четыре вопроса:

```text
1. Можно ли этому запросу использовать общий кэш?
2. Какой cache key соответствует запросу?
3. Есть ли по ключу достаточно свежий объект?
4. Если объекта нет или он устарел, можно ли получить либо перепроверить его у origin?
```

Результат запроса попадает в один из основных классов:

| Результат | Что произошло | Нагрузка на origin |
| --- | --- | --- |
| `HIT` | Свежий объект найден на edge | Нет |
| `MISS` | Объекта нет, CDN получает его из следующего слоя | Да, если промахнулись все слои |
| `REVALIDATED` | Кэш подтвердил версию условным запросом и получил `304` | Есть запрос, почти нет тела ответа |
| `STALE` | По политике отдана устаревшая копия | Может не быть либо обновление идёт параллельно |
| `BYPASS` | Запрос сознательно не использует кэш | Да |

Названия диагностических статусов зависят от реализации. Стандартизированный заголовок
`Cache-Status` описан в RFC 9211, но конкретный провайдер может использовать свой
заголовок. Поэтому приложение не должно строить бизнес-гарантию на случайном имени
`HIT` или `MISS`.

## Топология CDN

Полезная логическая схема выглядит так:

```text
Клиент
  |
  v
Edge PoP
  |
  v
Региональный кэш / mid-tier
  |
  v
Origin shield
  |
  v
Origin router
  |------------------|
  v                  v
Origin Region A    Origin Region B
```

Не каждая система содержит все уровни. Региональный кэш и origin shield являются
опциональными ролями, а не обязательными продуктами.

### Edge PoP

Edge — ближайший к пользователю узел. Он завершает клиентское соединение, применяет
правила доступа и ограничения скорости, ищет объект в локальном кэше и пересылает
промах дальше.

Клиент обычно попадает в подходящий PoP через Anycast, DNS-маршрутизацию или их
комбинацию. Точный механизм зависит от сети CDN и не меняет контракт кэша.

### Региональный кэш

Региональный слой объединяет промахи нескольких edge-узлов. Объект, вытесненный из
маленького edge-кэша, ещё может находиться в более крупном региональном кэше. Это
повышает offload origin без полного копирования каталога в каждый PoP.

### Origin shield

Origin shield — выбранный слой кэша непосредственно перед origin. Его основная роль —
свести одновременные промахи многих регионов к меньшему числу запросов и создать одну
точку применения request coalescing.

Shield не должен становиться безусловной единственной точкой отказа. Нужен второй
экземпляр, региональный выбор или контролируемый обход при недоступности. Конкретная
топология зависит от допустимой задержки между shield и origin.

### Origin

Origin — источник истины для объекта: object storage, медиасервис или приложение.
Кэширование чтений не переносит туда операции записи. Изменение объекта, управление
правами и выпуск версии остаются отдельным управляющим потоком.

## Pull CDN и предварительное размещение

### Pull CDN

В модели pull CDN загружает объект по первому промаху:

```text
первый запрос  -> MISS -> origin -> сохранить копию -> ответить
следующие      -> HIT  -> ответить с edge
```

Pull подходит, когда каталог велик, а будущую популярность трудно предсказать. В кэши
попадает рабочее множество, а не весь каталог.

Цена pull:

- первый пользователь платит задержкой заполнения;
- внезапно популярный объект создаёт одновременные промахи;
- редкий объект может постоянно вытесняться и загружаться заново;
- после глобальной инвалидации origin видит волну заполнений.

### Push или pre-position

В модели предварительного размещения система заранее отправляет объект в выбранные
регионы или прогревает его запросами до прихода пользовательского трафика.

Подход полезен для предсказуемого запуска:

- нового релиза мобильного приложения;
- премьеры популярного видео;
- ограниченного набора игровых ресурсов;
- аварийного обновления, которое должно быть готово во многих регионах к точному
  времени.

Цена предварительного размещения:

- часть переданных объектов никто не запросит;
- нужно выбрать регионы и момент прогрева;
- обновление версии создаёт дополнительный управляющий процесс;
- полный каталог может не вместиться на edge.

Поддержка настоящей загрузки на edge зависит от провайдера. Универсальный вариант —
версионированный URL и контролируемые запросы прогрева через обычный pull-путь.

### Гибрид

На практике небольшое предсказуемо горячее множество прогревают, а длинный хвост
оставляют pull-кэшу. Решение принимают по данным о популярности, размеру объектов,
стоимости первого промаха и доступной ёмкости edge.

## Путь запроса при попадании и промахе

### Свежий объект на edge

```text
1. Edge проверяет доступ и ограничение скорости.
2. Строит cache key.
3. Находит свежую запись.
4. Возвращает тело, не обращаясь к origin.
```

Большое тело передаётся из edge пользователю, поэтому клиентский egress остаётся. CDN
снижает трафик между origin и edge, а не количество байтов, получаемых клиентом.

### Полный промах

```text
1. Edge не находит запись и обращается к региональному кэшу.
2. Региональный кэш промахивается и обращается к shield.
3. Shield получает объект у origin.
4. Ответ идёт обратно и сохраняется на разрешённых уровнях.
5. Edge возвращает объект клиенту.
```

Во время заполнения реализация может одновременно передавать байты клиенту и сохранять
их, но это не универсальная гарантия HTTP-кэша. Для больших объектов нужно отдельно
проверять потоковое заполнение, поддержку `Range` и поведение при разрыве origin.

### Устаревший объект

Дальнейшее поведение задаёт политика:

- синхронно перепроверить версию у origin;
- отдать устаревшую копию и обновить её в фоне;
- отдать устаревшую копию только при ошибке origin;
- считать запись непригодной и вернуть ошибку.

Именно контракт продукта определяет выбор. Для хешированного JS допустимо только точное
содержимое по URL, для публичной ленты может быть приемлема версия на минуту старше, а
для отозванного документа устаревшая копия опасна.

## Cache key: какой ответ считается тем же объектом

**Cache key** — идентификатор варианта ответа. Базово он строится из метода и целевого
URI, а CDN часто позволяет явно включать, исключать и нормализовать части запроса.

Практическая модель:

```text
cache_key = scheme
          + host
          + normalized_path
          + selected_query_parameters
          + selected_request_headers
```

Точный состав зависит от настроек. `POST` с телом, `Authorization`, `Cookie` и правила
конкретного CDN нельзя считать безопасно кэшируемыми по умолчанию: для них задают явный
контракт либо используют `BYPASS`.

### Query parameters

Если параметры меняют содержимое, они входят в ключ:

```text
/catalog?category=books&page=1
/catalog?category=books&page=2
```

Технические параметры можно исключить после нормализации:

```text
/logo.png?utm_source=a
/logo.png?utm_source=b
```

Но исключать параметр можно только после доказательства, что origin также не меняет по
нему тело, язык, права или формат. Иначе разные ответы попадут в одну запись.

Порядок параметров полезно нормализовать:

```text
?a=1&b=2
?b=2&a=1
```

Однако CDN и origin обязаны одинаково трактовать повторные параметры, percent-encoding,
регистр и разделители. Разная каноникализация создаёт cache poisoning: edge видит один
ключ, а origin — два разных запроса.

### Заголовок Vary

`Vary` сообщает общему кэшу, какие заголовки запроса влияют на вариант ответа:

```http
Vary: Accept-Encoding, Accept-Language
```

`Accept-Encoding` обычно создаёт ограниченное число вариантов. `Vary: Cookie` может
создать вариант почти для каждого пользователя и уничтожить hit ratio. Ещё хуже, если
персональный ответ по ошибке сохраняется без разделения по пользователю.

Список допустимых вариантов лучше нормализовать на edge:

```text
Accept-Language: ru-RU,ru;q=0.9,en;q=0.8 -> language=ru
Accept-Language: ru                       -> language=ru
```

Так множество произвольных строк превращается в небольшой набор бизнес-вариантов.

### Персонализация

Общий каркас страницы можно кэшировать публично, а персональные данные загружать
отдельным запросом с `private` или `no-store`. Это сохраняет высокий hit ratio и снижает
риск утечки между пользователями.

## Свежесть, перепроверка и устаревший ответ

Политика HTTP-кэширования описывается заголовками ответа. Основные директивы:

| Директива | Смысл для общего кэша |
| --- | --- |
| `max-age=N` | Ответ свежий N секунд, если более специальная директива не переопределила срок |
| `s-maxage=N` | Срок свежести только для общих кэшей; имеет приоритет над `max-age` |
| `public` | Явно разрешает хранение в общем кэше в случаях, где оно иначе ограничено |
| `private` | Ответ предназначен одному пользователю и не сохраняется общим кэшем |
| `no-cache` | Хранить можно, но перед повторным использованием нужна перепроверка у origin |
| `no-store` | Не сохранять ответ в кэше |
| `must-revalidate` | После истечения свежести не использовать ответ без успешной перепроверки |
| `stale-while-revalidate=N` | В течение N секунд можно отдать stale и обновить копию в фоне |
| `stale-if-error=N` | В течение N секунд можно отдать stale при ошибке получения свежей версии |
| `immutable` | Пока ответ свежий, клиенту не нужно перепроверять, изменился ли он |

### Freshness и Age

TTL — разговорное название срока свежести. Кэш вычисляет возраст ответа с учётом
`Date`, времени хранения и переданного `Age`. Заголовок `Age` помогает увидеть, сколько
секунд ответ находился в цепочке общих кэшей, но промежуточные реализации и диагностические
заголовки всё равно нужно проверять в конкретной системе.

### Условная перепроверка

Origin может выдать валидатор:

```http
ETag: "catalog-v42"
Cache-Control: public, s-maxage=60
```

После истечения свежести кэш отправляет:

```http
If-None-Match: "catalog-v42"
```

Если содержимое не изменилось, origin отвечает `304 Not Modified` без полного тела.
Запрос и работа origin остаются, но исходящий трафик резко уменьшается.

### Stale-while-revalidate

```http
Cache-Control: public, s-maxage=60, stale-while-revalidate=300
```

Модель:

```text
0..60 с:     ответ свежий
60..360 с:   можно отдать stale и параллельно перепроверить
после 360 с: обычный stale, нужна синхронная политика получения свежей версии
```

Это хороший выбор для публичной витрины, где небольшое отставание приемлемо. Для точного
остатка товара на checkout такой контракт может быть неверным: витрина кэшируется, а
резерв выполняется отдельным точным запросом к Stock Service.

### Stale-if-error

```http
Cache-Control: public, s-maxage=60, stale-if-error=600
```

При ошибке или недоступности origin кэш может использовать копию до 10 минут после
истечения обычной свежести. В интерфейсе стоит явно показывать время данных, если
устаревание влияет на решение пользователя.

`stale-if-error` не подходит для отзыва доступа, изменившегося денежного баланса или
другого состояния, где устаревший ответ опаснее ошибки.

## Инвалидация и выпуск новой версии

У распределённого кэша нет бесплатной мгновенной инвалидации всех узлов. Выбор зависит
от того, меняется ли объект по тому же URL.

### Версионированный URL

Для неизменяемой статики имя включает хеш содержимого:

```text
/assets/app.7f3a2c.js
/images/product-42.19bd8a.webp
```

Новая версия получает новый URL, поэтому старая запись не может ответить на новый
запрос. Политика может быть долгой:

```http
Cache-Control: public, max-age=31536000, immutable
```

HTML или manifest, который ссылается на новую версию, хранится заметно меньше. Старые
объекты удаляются после окна, достаточного для клиентов со старым HTML и незавершённых
загрузок.

### Purge

Purge — команда управляющей плоскости удалить либо пометить устаревшими записи по URL,
префиксу или тегу. Возможности и скорость распространения зависят от CDN.

Инвалидацию нужно считать асинхронным процессом:

```text
запрос purge принят -> команда распространяется -> отдельные PoP применяют её
```

Изолированный или временно недоступный PoP способен применить команду позже. Поэтому
purge удобен для исправления контента, но не должен быть единственной защитой при
мгновенном отзыве секрета или прав доступа.

### Короткий TTL

Короткий TTL ограничивает максимальный срок обычного устаревания, но увеличивает число
перепроверок и промахов. Для конфигурации, меняющейся несколько раз в день, разумнее
совместить умеренный TTL, валидатор и purge, чем обращаться к origin каждую секунду.

### Порядок публикации

Безопасная выкладка статики идёт от зависимостей к ссылкам:

```text
1. Загрузить новые versioned assets в origin.
2. Проверить их доступность через CDN.
3. Опубликовать HTML или manifest со ссылками на новые URL.
4. Не удалять старые assets до истечения окна совместимости.
```

Если сначала опубликовать HTML, часть пользователей получит ссылки на файлы, которые
ещё не дошли до origin или реплик.

## Cache stampede и защита origin

**Cache stampede** — множество одновременных промахов по одному ключу. Он возникает
при истечении TTL, purge, запуске горячего объекта или восстановлении пустого кэша.

### Request coalescing

Схлопывание запросов (`request coalescing`, `single flight`) назначает один запрос
владельцем заполнения:

```text
первый MISS       -> fetch origin
следующие MISS    -> ждут тот же fetch
успешный ответ    -> одна запись в кэш, ответ всем ожидающим
```

Ошибку тоже нельзя бесконтрольно размножать. После неудачного заполнения нужны короткая
отрицательная запись, backoff или stale-ответ, иначе каждая новая группа снова атакует
origin.

### Shield против глобальной волны

Предположим:

```text
edge PoP:                         200
один горячий объект истёк везде:  одновременно
```

Даже при локальном coalescing каждый PoP способен создать один запрос заполнения:

```text
без общего слоя: до 200 запросов к origin на один объект
```

Если все PoP сходятся на одном доступном shield и на нём тоже работает coalescing, то в
идеальном случае до origin дойдёт один запрос. При нескольких shield будет примерно по
одному заполнению на shield. Это расчёт модели, а не универсальная гарантия продукта.

### Разнесение TTL

Случайный разброс (`jitter`) предотвращает одновременное истечение большого набора
объектов:

```text
base TTL = 300 с
jitter   = от -30 до +30 с
итоговый TTL распределён в диапазоне 270..330 с
```

Jitter помогает для множества ключей, но не решает истечение одного сверхгорячего
ключа. Для него нужны coalescing, shield, `stale-while-revalidate` или предварительный
прогрев.

### Отрицательное кэширование

Короткое кэширование подтверждённого `404` защищает origin от повторов по
несуществующему URL. Ошибки `5xx` нельзя кэшировать общей долгой политикой: временный
сбой превратится в устойчивую ошибку на edge. Для них лучше ограниченный
`stale-if-error`, backoff и защита origin.

## Закрытый контент: signed URL и signed cookie

Обычный публичный URL можно переслать кому угодно. Для платного видео, приватного файла
или временной загрузки edge проверяет подписанное разрешение.

### Signed URL

Подписанный URL обычно содержит:

```text
resource path
expires_at
policy or tenant
key_id
signature
```

Подпись позволяет edge проверить, что доверенный сервис выдал доступ к этому пути до
указанного срока, а клиент не изменил параметры.

Signed URL удобен для одного объекта или ограниченного набора URL. Его недостатки:

- адрес попадает в историю, журналы и аналитику;
- ссылку можно повторно использовать до истечения срока, если политика не связывает её
  с дополнительным контекстом;
- уникальные параметры подписи дробят кэш, если входят в cache key.

### Signed cookie

Подписанная cookie передаёт разрешение отдельно от URL. Она удобна, когда клиенту нужен
доступ ко множеству сегментов одного видео или ко всему префиксу каталога: URL остаются
стабильными и хорошо кэшируются.

Cookie должна иметь подходящие `Secure`, `HttpOnly` и `SameSite` в зависимости от
клиента и потока авторизации. Эти атрибуты не заменяют проверку области пути, срока и
подписи на edge.

### Проверка раньше lookup

Безопасный порядок:

```text
1. Проверить подпись, срок, область и key_id.
2. Сопоставить запрос с каноническим объектом.
3. Выполнить cache lookup по ключу, который не смешивает разные варианты содержимого.
4. Вернуть объект.
```

Если убрать токен из cache key до проверки подписи, неавторизованный запрос может
получить публичный `HIT`. Если оставить уникальную подпись в ключе без нормализации,
каждый пользователь создаст отдельную копию. Поэтому авторизация отделяется от
идентичности уже разрешённого объекта.

### Ограничения подписи

- короткий срок уменьшает окно повторного использования, но чаще требует обновления;
- ротация ключей требует периода, когда edge принимает текущий и предыдущий ключ;
- часы выдающего сервиса и edge должны иметь контролируемое расхождение;
- HTTPS защищает токен в пути;
- подпись управляет доставкой, но не является DRM: получивший расшифрованные байты
  клиент способен их копировать.

## Несколько регионов origin

CDN снижает число запросов к origin, но промахи всё равно требуют доступного источника.
Для нескольких регионов есть две основные модели.

### Active-passive

Основной origin обслуживает заполнения, резервный принимает их после проверки здоровья
и переключения.

Преимущества:

- один источник упрощает порядок обновлений;
- легче контролировать, какая версия считается текущей.

Недостатки:

- переключение занимает время;
- резервный регион нужно регулярно проверять под реальной нагрузкой;
- холодные соединения и кэши создают всплеск после failover.

### Active-active

Маршрутизатор выбирает доступный или ближайший origin-регион.

Преимущества:

- меньше межрегиональная задержка заполнения;
- трафик распределяется в штатном режиме;
- отказ одного региона не переводит всю нагрузку на никогда не прогревавшийся путь.

Недостатки:

- версии объектов и метаданные должны быть согласованы;
- два региона могут временно выдавать разный контент по одному URL;
- запись и инвалидация требуют отдельной модели согласованности.

Для неизменяемых объектов проблему упрощает versioned URL: одинаковый URL обязан
обозначать одинаковые байты во всех регионах. Для изменяемого API нужно решить, допустим
ли replica lag, какой регион является лидером и можно ли отдавать stale.

### Failover и stale

Порядок деградации может быть таким:

```text
edge HIT
-> regional HIT
-> primary origin
-> secondary origin
-> stale-if-error, если разрешено контрактом
-> явная ошибка
```

Нельзя бесконечно переключаться между origin на каждый таймаут: нужны ограничение
повторов, общий deadline и circuit breaker. Иначе один пользовательский запрос умножает
нагрузку во время аварии.

## Расчёт нагрузки и hit ratio

Для ёмкости нужны как минимум две метрики:

- **Request hit ratio** — доля запросов, обслуженных из кэша.
- **Byte hit ratio** — доля байтов, которые не пришлось получать от origin.

Высокий request hit ratio не гарантирует низкий origin egress, если промахиваются самые
крупные объекты.

### Допущения примера

Все размеры ниже десятичные: `1 MB = 1 000 000 bytes`.

```text
общий пик:                             1 000 000 запросов/с

изображения:
доля запросов:                         90% = 900 000/с
средний размер:                        50 kB
hit ratio:                             99%

видеосегменты:
доля запросов:                         10% = 100 000/с
средний размер:                        2 MB
hit ratio:                             95%
```

### Трафик от edge к клиентам

```text
изображения:   900 000 × 50 kB = 45 000 000 kB/с = 45 GB/с
видео:         100 000 ×  2 MB =    200 000 MB/с = 200 GB/с

всего:                                  245 GB/с
в битах:                245 × 8 =      1 960 Gbit/с = 1,96 Tbit/с
```

CDN-флот должен отдать пользователям весь этот трафик независимо от hit ratio.

### Запросы и трафик к origin

```text
промахи изображений: 900 000 × (1 - 0,99) = 9 000 запросов/с
их трафик:             9 000 × 50 kB       = 0,45 GB/с

промахи видео:       100 000 × (1 - 0,95) = 5 000 запросов/с
их трафик:             5 000 × 2 MB        = 10 GB/с

origin total:                                  10,45 GB/с
origin в битах:       10,45 × 8              = 83,6 Gbit/с
```

Request hit ratio:

```text
HIT изображений: 900 000 - 9 000 = 891 000/с
HIT видео:       100 000 - 5 000 =  95 000/с

(891 000 + 95 000) / 1 000 000 = 98,6%
```

Byte hit ratio:

```text
1 - origin bytes / client bytes
= 1 - 10,45 / 245
= 95,73%
```

Несмотря на `98,6%` попаданий по запросам, origin всё ещё отдаёт `83,6 Gbit/с`, потому
что сравнительно редкие промахи видео велики.

Если пик держался бы сутки, исходящий объём origin составил бы:

```text
10,45 GB/с × 86 400 с = 902 880 GB = 902,88 TB/сутки
```

Для накопления за обычные сутки нужно подставлять среднюю, а не пиковую нагрузку. Здесь
суточное число показывает верхний сценарий непрерывного пика, а не прогноз.

### Эффект улучшения video hit ratio

Если поднять hit ratio видеосегментов с `95%` до `98%`:

```text
новые промахи видео: 100 000 × 0,02 = 2 000 запросов/с
новый трафик видео:    2 000 × 2 MB  = 4 GB/с

экономия origin: 10 GB/с - 4 GB/с = 6 GB/с = 48 Gbit/с
```

Поэтому byte hit ratio и egress по типам объектов важнее одного общего процента `HIT`.

## Отказы и деградация

| Сбой | Что видит система | Безопасная реакция |
| --- | --- | --- |
| Недоступен один edge PoP | Новые или переподключившиеся клиенты идут другим путём; текущие соединения могут оборваться | Перемаршрутизация, ограниченные повторы клиента |
| Недоступен региональный кэш | Промахи идут в другой mid-tier или к shield | Контролируемый bypass, защита следующего слоя |
| Недоступен shield | Все регионы рискуют одновременно обратиться к origin | Резервный shield, rate limit заполнений, stale |
| Недоступен основной origin | Полные промахи и перепроверки не завершаются | Резервный origin, `stale-if-error` только для разрешённых данных |
| Purge распространился частично | Разные PoP отдают разные версии | Versioned URL, наблюдение propagation lag, короткий TTL для изменяемого объекта |
| Origin отвечает медленно | Очереди заполнения растут, coalesced-запросы ждут | Deadline, stale-ответ, circuit breaker, admission control |
| Повреждён большой cache fill | Часть клиентов получает ошибку или незавершённое тело | Не публиковать неполную запись как готовую, повторить с ограничением |

### Graceful degradation

Деградация задаётся по классам контента, а не одним глобальным переключателем:

- изображения и публичные статьи можно отдавать stale дольше;
- результаты поиска можно временно кэшировать короче и показать время обновления;
- приватный документ после отзыва доступа не отдаётся stale;
- точный checkout обходит CDN-проекцию и обращается к authoritative service;
- при перегрузке новые cache fills ограничиваются, а существующие `HIT` продолжают
  обслуживаться.

Так авария origin не обязана превращаться в полную недоступность уже сохранённого
публичного контента.

## Безопасность кэша

### Cache poisoning

Злоумышленник добивается, чтобы CDN сохранил ответ, сформированный по данным, которых
нет в cache key. Затем этот ответ получают другие пользователи.

Источники расхождения:

- edge и origin по-разному нормализуют путь или query string;
- origin доверяет непроверенному `Host` или `X-Forwarded-Host`;
- заголовок меняет ответ, но не указан в `Vary` и не включён в ключ;
- нестандартный метод или тело запроса ошибочно считаются тем же объектом;
- ответ с ошибкой или редиректом получает слишком долгий TTL.

Защита строится на единой каноникализации, allowlist заголовков, проверке `Host`, явных
правилах кэширования и тестах, которые отправляют семантически разные запросы к одному
кандидату ключа.

### Утечка персонального ответа

Самая опасная ошибка — сохранить приватный ответ под общим ключом. Защита:

- персональные ответы получают `Cache-Control: private` или `no-store`;
- edge не переписывает эту политику широким правилом «cache everything»;
- авторизация проверяется раньше cache lookup;
- публичная и персональная части используют разные URL и обработчики;
- в тестах два пользователя последовательно запрашивают один URL через тот же PoP.

### Cache deception

При cache deception динамический приватный обработчик принимает URL, похожий на
статический, а edge кэширует его по расширению. Например, приложение трактует
`/account/profile.css` как профиль, а CDN — как публичный CSS.

Кэшируемость должна следовать из доверенной политики маршрута и заголовков origin, а не
только из суффикса пользовательского пути.

### Отзыв доступа

Purge и короткий TTL сокращают окно, но мгновенный отзыв требует проверки разрешения на
каждом запросе у edge или origin. При высокой цене утечки система предпочитает явную
ошибку устаревшему ответу.

## Наблюдаемость

Метрики собираются по типу контента, региону, статусу кэша и origin, иначе среднее
скрывает горячий объект или один проблемный PoP.

### Основные метрики

- request hit ratio и byte hit ratio;
- запросы и исходящий трафик origin;
- задержка `HIT`, регионального попадания, shield-попадания и полного `MISS`;
- число одновременных заполнений и доля схлопнутых запросов;
- возраст ответа и доля `STALE`;
- ошибки origin отдельно от ошибок edge;
- доля bypass по причине авторизации, метода или политики;
- использование диска и частота вытеснений по PoP;
- время распространения purge;
- top-N ключей по miss traffic, а не только по числу запросов.

### Диагностические данные

Для одного запроса полезны:

- `Age` и `Cache-Status`, если они поддерживаются;
- идентификатор PoP и цепочка внутренних кэшей;
- нормализованный класс cache key без секретных значений;
- причина `BYPASS` или `MISS`;
- версия объекта и `ETag`;
- выбранный origin-регион;
- trace только для выборки промахов, чтобы не создавать телеметрию на каждый байт.

Подписи URL, cookie и исходные query parameters нельзя бездумно писать в журналы: они
могут давать доступ к закрытому контенту.

## Trade-offs и выбор политики

| Контент | Cache key | Свежесть | Инвалидация | Поведение при сбое |
| --- | --- | --- | --- | --- |
| JS/CSS с хешем | Полный versioned URL + encoding | Год, `immutable` | Новый URL | Старая версия корректна только по старому URL |
| Публичное изображение | Путь версии + вариант размера/формата | Часы или дни | Новый URL или purge | Stale обычно допустим |
| HTML shell | Host + path + язык | Секунды или минуты | Purge + короткий TTL | Короткий stale по контракту |
| Каталог товаров | Нормализованные фильтры + регион/язык | Короткий TTL + SWR | Событие изменения + purge | Показать время проекции; checkout проверяет точно |
| Приватный файл | Канонический объект после проверки подписи | По сроку политики | Отзыв доступа не полагается только на purge | Ошибка безопаснее stale |
| Баланс или одноразовый токен | Не использовать общий кэш | `private, no-store` | Не требуется | Только authoritative service |

Чем дольше TTL, тем выше hit ratio и устойчивость к origin, но дольше обычное окно
устаревания. Чем больше измерений cache key, тем точнее варианты, но ниже повторное
использование и выше расход места. Эти параметры нельзя оптимизировать независимо.

## Типичные ошибки

### Кэшировать всё одним правилом

Одинаковая политика для статики, HTML и приватного API либо перегружает origin, либо
утекает пользовательскими данными. Политика задаётся по классу маршрута и контракту
свежести.

### Считать purge мгновенной транзакцией

Инвалидация распространяется по распределённой управляющей плоскости. Для статики
версионированный URL надёжнее изменения байтов по старому имени.

### Смотреть только request hit ratio

Небольшая доля промахов крупных объектов способна создавать большую часть origin
egress. Нужны byte hit ratio и разбивка по типу контента.

### Включить весь query string в ключ

Технические параметры и уникальные подписи создают миллионы одноразовых вариантов.
Параметры нормализуются по allowlist, но только после проверки доступа и соответствия
семантике origin.

### Исключить слишком много из ключа

Удаление языка, tenant или параметра размера смешивает разные ответы. Ошибка опаснее
низкого hit ratio, потому что другой пользователь получает корректный `HIT` с чужим
содержимым.

### Не ограничить fill concurrency

Пустой кэш после аварии посылает весь поток в origin. Нужны coalescing, shield, rate
limit, jitter и приоритетное прогревание горячего множества.

### Использовать stale без бизнес-контракта

Устаревшая статья и устаревшее право доступа имеют разную цену. `stale-if-error`
включается для конкретного класса данных, а не как глобальный способ повысить
доступность.

### Хранить подписанные ссылки в журналах

URL может быть временным bearer credential. Журналы редактируют или хешируют
чувствительные параметры, ограничивают доступ к ним и учитывают срок хранения.

## Interview-ready answer

**1. Из каких уровней состоит CDN?**

- Edge — принимает клиентский запрос рядом с пользователем и ищет объект в локальном кэше.
- Региональный кэш — объединяет промахи нескольких edge-узлов и хранит более широкое рабочее множество.
- Origin shield — схлопывает промахи регионов перед исходным хранилищем.
- Origin — остаётся источником истины и обслуживает полный промах.

**2. Чем pull CDN отличается от предварительного размещения?**

- Pull — загружает объект по первому запросу и хорошо работает с большим непредсказуемым каталогом.
- Предварительное размещение — прогревает известные горячие объекты до пользовательского пика.
- Цена pull — задержка первого промаха и риск stampede.
- Цена прогрева — лишние передача, хранение и управляющая логика для невостребованных объектов.

**3. Из чего строится cache key?**

- Основа — схема, host, нормализованный путь и выбранные query parameters.
- Варианты — заголовки, реально меняющие ответ, включаются настройкой или через `Vary`.
- Персонализация — приватные данные отделяются от общей страницы и не попадают в публичный ключ.
- Безопасность — edge и origin обязаны одинаково канонизировать запрос, иначе возможны poisoning и утечки.

**4. Как обновлять контент в CDN?**

- Неизменяемая статика — получает новый URL с хешем и долгий TTL.
- Изменяемый объект — использует TTL, валидатор и при необходимости асинхронный purge.
- Мягкая свежесть — `stale-while-revalidate` отдаёт старую копию и обновляет её в фоне.
- Авария origin — `stale-if-error` применяется только там, где устаревание безопаснее ошибки.

**5. Как защитить origin от cache stampede?**

- Coalescing — один запрос заполняет ключ, остальные ждут тот же результат.
- Shield — объединяет заполнения многих PoP перед origin.
- Разнесение — jitter не даёт множеству ключей истечь одновременно.
- Деградация — stale, backoff и rate limit ограничивают волну во время ошибки.

**6. Чем signed URL отличается от signed cookie?**

- Signed URL — выдаёт временный доступ к конкретному URL и удобен для одного объекта.
- Signed cookie — даёт доступ к набору стабильных URL, например сегментам видео.
- Порядок — подпись проверяется раньше cache lookup, затем запрос сопоставляется с каноническим объектом.
- Ограничение — подпись можно повторно использовать до истечения срока и она не заменяет DRM.

**7. Почему request hit ratio недостаточно?**

- Причина — промахи крупных объектов могут создавать большую часть исходящего трафика origin.
- Метрика — byte hit ratio показывает долю байтов, обслуженных без origin.
- Разрез — обе метрики нужны по типу контента, региону и размеру объекта.
- Ёмкость — origin планируется по miss RPS, miss bandwidth и пиковому заполнению после сбоя.

**8. Как CDN работает с несколькими origin-регионами?**

- Active-passive — сохраняет один обычный источник и переключает заполнения при отказе.
- Active-active — уменьшает задержку и постоянно использует несколько регионов, но требует согласованных версий.
- Неизменяемость — versioned URL упрощает репликацию: один URL означает одинаковые байты.
- Деградация — повторы ограничиваются общим deadline, после чего разрешённый контент может быть отдан stale.
