HTTP-метод сообщает не только название операции, но и её стандартную семантику.
На неё опираются клиенты, прокси, кэши, политики повторов и средства
наблюдаемости. Если `POST` используется для обычного чтения или `GET` запускает
изменение, инфраструктура уже не может сделать правильные выводы только по
протоколу.

## Таблица свойств методов

| Метод | Безопасный по HTTP | Идемпотентный по HTTP | Содержимое запроса | Кэширование ответа |
| --- | --- | --- | --- | --- |
| GET | да | да | общей семантики нет; обычно не отправляют | да |
| HEAD | да | да | обычно не отправляют | да |
| OPTIONS | да | да | обычно не отправляют | нет |
| POST | нет | нет | да | возможно при явной свежести, но поддерживается редко |
| PUT | нет | да | да | нет |
| PATCH | нет | не гарантируется | да | возможно при специальных условиях, но поддерживается редко |
| DELETE | нет | да | общей семантики нет; обычно не отправляют | нет |

Определения, которые важно не путать между собой:

- **Безопасный метод** имеет семантику только для чтения: клиент не просит
  изменить состояние ресурса. Сервер всё равно может записать журнал доступа,
  увеличить метрику или начислить стоимость запроса — такие побочные эффекты не
  делают `GET` небезопасным. Именно стандартная семантика позволяет браузеру
  предварительно загружать ссылки, а роботу — переходить по ним без подтверждения.
- **Идемпотентный метод** имеет один и тот же предполагаемый эффект после одного
  и нескольких одинаковых запросов. Второй `DELETE` может вернуть `404` вместо
  `204`, а в логах появится ещё одна запись, но целевой ресурс останется удалённым.
- **Кэшируемость** — отдельное свойство. Например, `OPTIONS` безопасен, но его
  ответы не кэшируются; ответ на небезопасный `POST` спецификация разрешает
  кэшировать при явной информации о свежести.
- **Возможность повтора** тоже не равна идемпотентности. Идемпотентность разрешает
  клиенту повторить запрос после сетевого сбоя, но конкретная библиотека может
  применять более узкую политику и должна уметь заново отправить тело.

Содержимое запроса у `GET` и `DELETE` не запрещено форматом сообщения, но RFC
9110 не задаёт ему общей семантики. API не должен на него рассчитывать без
прямого соглашения с клиентом и всеми промежуточными компонентами.

Например, в Go 1.26 `http.Transport` автоматически повторяет только некоторые
сетевые ошибки на ранее использованном соединении. Запрос должен быть
воспроизводимым, а транспорт считает подходящими `GET`, `HEAD`, `OPTIONS`,
`TRACE` либо запросы с `Idempotency-Key`/`X-Idempotency-Key`. Поэтому из
семантической идемпотентности `PUT` ещё не следует, что любой Go-клиент свободно
повторит его автоматически. И наоборот, одно только наличие заголовка не делает
серверную операцию идемпотентной: сервер обязан реализовать соответствующий
контракт.

## Когда какой метод

- `GET` — чтение, в котором клиент не запрашивает изменение ресурса.
- `POST /collection` — создание ресурса с идентификатором, выбранным сервером.
- `POST /resource/{id}:verb` — действие, которое не выражается стандартными
  CRUD-методами; например, `:confirm` или сложный `:search`.
- `PUT /collection/{id}` — создание или полная замена ресурса по известному URI.
- `PATCH /collection/{id}` — частичное обновление, тело — дельта или `FieldMask`.
- `DELETE /collection/{id}` — удаление ресурса.

Дальше — почему именно так, и где обычно ошибаются.

## POST для чтения: когда это оправдано

`POST` для чтения не нарушает синтаксис HTTP, но лишает инфраструктуру
стандартного сигнала «это безопасное чтение». Для обычного получения ресурса
это обычно неоправданно:

```text
POST /v1/bundles                     # «поиск рекомендаций»
POST /v1/bundles/{id}/acc-details    # явное чтение деталей
POST /v1/quiz-sessions/{id}/page-info # чтение шага квиза
```

Практические последствия:

1. **Кэширование.** Ответ на `POST` можно кэшировать при явной информации о
   свежести, но распространённые кэши ориентированы прежде всего на `GET` и
   часто требуют специальной настройки. Если ответ `200 OK` содержит
   `Content-Location`, совпадающий с URI запроса, его можно представить как
   текущее состояние ресурса и переиспользовать для последующего `GET` или
   `HEAD`.
2. **Повторы.** Стандартная семантика `POST` не гарантирует идемпотентность,
   поэтому универсальный клиент не может без дополнительного контракта решить,
   безопасен ли повтор. Операция только для чтения может быть повторяемой на уровне
   приложения, но клиенту или прокси это нужно явно настроить.
3. **Наблюдаемость и доступ.** Политики, которые делят трафик по методу на
   чтение и запись, классифицируют такой запрос как запись. Это искажает метрики
   и может потребовать исключений в правилах доступа.
4. **Условное чтение.** Экосистема валидации кэша через `ETag`, `If-None-Match`
   и `304 Not Modified` рассчитана прежде всего на `GET` и `HEAD`. Заголовки
   предусловий не ограничены только этими методами, но для изменяющих запросов
   выполняют другую роль и обычно приводят к `412 Precondition Failed`.

### Когда чтение реально не помещается в URL

Есть три основных подхода.

#### Подход A. Подходит GET с query

Начинать стоит с `GET`: фильтры можно выразить query-параметрами или ссылкой на
заранее сохранённые критерии.

```text
GET /v1/bundles?searchCriteriaId={id}
GET /v1/bundles?searchCriteriaId={id}&refresh=true
GET /v1/bundles/{bundleId}/acc?accId={accId}
```

Особенно если уже есть концепция `searchCriteriaId` — она и есть
сохранённый фильтр.

Секреты и персональные данные не стоит помещать в query: URI часто попадает в
историю браузера, журналы доступа и метрики прокси. Кодирование значения не
делает его секретным. Для чувствительного сложного фильтра тело запроса уменьшает
риск случайной утечки, хотя само по себе не заменяет TLS и настройку логирования.

#### Подход B. `POST /resource:search` с телом

Допустимый компромисс, когда фильтр слишком велик для практических ограничений
URI, содержит чувствительные данные или имеет сложную вложенную структуру:

```text
POST /v1/bundles:search       # тело — SearchCriteria
```

Нотация `:search` явно отделяет поиск от `POST /collection`, который обычно
означает создание. Операция остаётся только чтением на уровне приложения, но
HTTP не начинает считать `POST` безопасным методом. Этот контракт и политику
повторов нужно документировать отдельно.

#### Подход C. Через ресурс «search»

Когда поиск дорогой, асинхронный или результаты живут:

```text
POST /v1/searches             # создать запрос, вернуть {searchId}
GET  /v1/searches/{searchId}/bundles?page=...
```

Это подходит, когда поиск долгий, выполняется асинхронно, пагинируется или его
результат нужно получить повторно по стабильному идентификатору.

## POST для создания ресурса

Обычная семантика ресурсного API:

- `POST /collection` создаёт ресурс, URI которого выбирает сервер;
- `201 Created` возвращается с `Location: /collection/{id}` и, при
  необходимости, с представлением созданного ресурса;
- `202 Accepted` подходит, если создание только поставлено в асинхронную
  обработку и ещё не завершено.

```text
POST /v1/orders
Body: {...}
Response: 201
Location: /v1/orders/abc-123
Body: { "id": "abc-123", "status": "new", ... }
```

### Идемпотентность POST

HTTP не гарантирует идемпотентность `POST`: повтор может создать второй ресурс
или ещё раз выполнить действие. Если клиент должен безопасно повторять такую
операцию после сетевого сбоя, нужен отдельный механизм идемпотентности.

Один из распространённых вариантов — заголовок `Idempotency-Key`. Клиент
генерирует ключ на логическую операцию, а сервер атомарно резервирует ключ и
координирует статус обработки с бизнес-транзакцией. Повтор с тем же ключом и
тем же содержимым возвращает сохранённый результат без повторного
бизнес-эффекта; тот же ключ с другим содержимым должен быть отклонён.

```text
POST /v1/payments
Idempotency-Key: 9e3b... (UUID v4 от клиента)
```

Подробно — в [05-integration-patterns/02-idempotency.md](../protocols/05-integration-patterns/02-idempotency.md).

Особенно критично для платежей:

```text
POST /v1/payments
POST /v1/payments/{id}:confirm
POST /v1/payments/{id}:capture
POST /v1/payment-intents
```

Для операций, где повтор создаёт дорогостоящий или необратимый эффект, контракт
безопасных повторов обязателен. Это может быть `Idempotency-Key`, уникальный
идентификатор операции или другой атомарный механизм дедупликации. Сам HTTP не
требует конкретного заголовка, но без такого контракта клиент после сетевого
обрыва не может отличить «запрос не дошёл» от «операция завершилась, ответ
потерялся».

## PUT vs PATCH

`PUT` создаёт или полностью заменяет ресурс по URI, который уже известен
клиенту. Если ресурса не было, сервер обычно возвращает `201 Created`; если
представление заменено — `200 OK` с телом или `204 No Content`.

`PATCH` обычно частично изменяет существующий ресурс. В теле передаётся не
полное представление, а набор изменений в заранее выбранном формате. Создание
ресурса через `PATCH` возможно только тогда, когда это явно допускают контракт
сервера и используемый формат изменений.

Антипример (имя метода противоречит реальному действию):

```text
PATCH /v1/admin/quiz/block/link    # rpc называется ReplaceQuizBlockLinks — это PUT
```

Если URI идентифицирует набор связей как отдельный ресурс и операция заменяет
его целиком, семантика соответствует `PUT`. Если меняется только часть
представления, подходит `PATCH`.

### Установка состояния через PUT

`PUT /collection/{id}` — идемпотентный способ «положить состояние = X»:

```protobuf
rpc SaveBundle(SaveBundleRequest) returns (EmptyResponse) {
  option (google.api.http) = {
    put: "/v1/saved-bundles/{bundleId}"
    body: "*"
  };
}
```

«Сохрани bundleId в список сохранённых». Повтор задаёт то же целевое состояние:
ресурс `/saved-bundles/{bundleId}` существует. Сервер всё равно должен обеспечить
уникальность, но контракт `PUT` прямо сообщает клиенту об идемпотентности.

Альтернатива через POST:

```text
POST /v1/saved-bundles            # body: { bundleId: "abc" }
```

Тоже валидно, но идемпотентность конкретной операции нужно описать отдельно и
обеспечить на сервере, например уникальным ограничением на `(user_id, bundle_id)`.

### PATCH + FieldMask

Для частичных обновлений в protobuf API часто используют `FieldMask`, например
по рекомендациям Google AIP-134:

```protobuf
import "google/protobuf/field_mask.proto";

message UpdatePromoCodeRequest {
  PromoCode promo_code = 1;
  google.protobuf.FieldMask update_mask = 2;
}
```

`update_mask = "description,currency_code"` — обновятся только эти поля. Это
точнее, чем PATCH с произвольным телом, и не требует отдельного типа запроса для
каждой комбинации изменяемых полей. Подробно — в
[05-payloads-and-types.md](./05-payloads-and-types.md).

### PATCH без FieldMask

Альтернатива — JSON Merge Patch с типом
`application/merge-patch+json` или JSON Patch с типом
`application/json-patch+json`. Первый формат описывает желаемые значения полей,
второй — последовательность операций `add`, `remove`, `replace` и других. Для
protobuf API эти форматы менее естественны, но подходят для HTTP API без
protobuf.

Сервер может перечислить поддерживаемые форматы в заголовке `Accept-Patch`
ответа на `OPTIONS`. Ответ на `PATCH` кэшируется только при явной информации о
свежести и `Content-Location`, совпадающем с URI запроса; на практике такая
поддержка встречается редко. Сохранённый ответ можно использовать для
последующего `GET` или `HEAD`, но не как ответ на следующий `PATCH`.

### Почему PATCH не гарантирует идемпотентность

Свойство конкретного `PATCH` зависит от формата и содержимого запроса.
Присвоение `{"status": "cancelled"}` можно повторить без дополнительного
изменения состояния. Операция «уменьшить баланс на 100» или добавление в конец
массива при каждом повторе применяет дельту ещё раз:

```json
[
  {
    "op": "add",
    "path": "/items/-",
    "value": { "sku": "ABC-42", "quantity": 1 }
  }
]
```

Поэтому HTTP не объявляет `PATCH` идемпотентным в общем случае. Для
неидемпотентной дельты используют ключ идемпотентности или другой механизм
дедупликации. `If-Match` решает соседнюю задачу: не даёт применить изменение к
версии ресурса, которая успела устареть. Механика серверной дедупликации разобрана
в [06-idempotency.md](../../05-system-design/reliability-patterns/06-idempotency.md).

## Условные запросы и потерянное обновление

Без проверки версии два клиента могут прочитать одно состояние, изменить его и
последней записью затереть результат друг друга. Это потерянное обновление
(`lost update`). `ETag` и `If-Match` реализуют оптимистическую блокировку на
уровне HTTP:

```text
GET /v1/orders/42
Response: 200 OK
ETag: "v7"

PATCH /v1/orders/42
If-Match: "v7"
Body: { "status": "cancelled" }
```

Сервер применяет `PATCH`, только если текущий `ETag` всё ещё равен `"v7"`.
После конкурентного изменения версия уже другая, поэтому сервер возвращает
`412 Precondition Failed`. Если API требует условие для изменения, но клиент
его не прислал, сервер может вернуть `428 Precondition Required`.

Заголовки предусловий не привязаны только к `GET`, `PUT` или `DELETE`:

- `If-Match` можно использовать с изменяющим методом, включая `PATCH`;
- `If-None-Match: *` позволяет создать ресурс, только если он ещё не существует;
- ложный `If-None-Match` приводит к `304 Not Modified` для `GET`/`HEAD` и к
  `412 Precondition Failed` для остальных методов;
- ложный `If-Match` приводит к `412 Precondition Failed` независимо от метода.

`If-Match` и `Idempotency-Key` не взаимозаменяемы. Первый защищает от записи по
устаревшей версии, второй узнаёт повтор одной логической операции. Для
неидемпотентной операции с конкурентным обновлением могут понадобиться оба.

## DELETE

`DELETE /collection/{id}` просит удалить связь между URI и текущим ресурсом.
Типичные ответы:

- `204 No Content` — удаление завершено, тело не требуется;
- `200 OK` — сервер возвращает представление результата;
- `202 Accepted` — удаление принято в асинхронную обработку.

Неудачные или неоднозначные варианты:

```text
DELETE /v1/rec/bundles/pr-transfer        # без id — что удаляем?
DELETE /v1/admin/quiz?quizId=X            # допустимо, но ресурс хуже читается
DELETE /v1/orders        body: {...}      # у тела нет общей семантики
```

Правильно:

```text
DELETE /v1/bundles/{bundleId}/pr-transfers/{leg}
DELETE /v1/admin/quizzes/{quizId}
DELETE /v1/orders/{orderId}
```

### Тело в DELETE

RFC 9110 не запрещает содержимое запроса синтаксически, но не задаёт для него
общей семантики. Клиенту не следует отправлять такое содержимое без заранее
оговорённой поддержки конкретного сервера-источника; часть реализаций может
отклонить запрос, в том числе из-за риска рассинхронизации разбора запроса
(`request smuggling`).

Для публичного API надёжнее выразить цель через URI или отдельное действие.
Если тело всё же используется во внутреннем API, его семантика и поддержка
каждым промежуточным компонентом должны быть частью контракта.

### Идемпотентность DELETE

DELETE идемпотентен по семантике: «привести состояние к "ресурса нет"».
Повторный DELETE на уже удалённый ресурс — ок, обычно возвращает `404` или
`204`. На клиенте это легко обработать.

Для пакетного удаления часто используют явное действие:

```text
POST /v1/orders:batchDelete    body: { orderIds: [...] }
```

Это конвенция дизайна API, а не требование HTTP. Она делает тело, частичный
успех и результат каждой операции явной частью контракта.

## OPTIONS и HEAD

`HEAD` имеет ту же семантику, что и `GET`, но сервер не отправляет содержимое
ответа. Метод подходит, чтобы получить метаданные, проверить доступность ресурса
или валидатор `ETag`, не скачивая представление целиком. Ответ на `HEAD` также
может обновить метаданные уже сохранённого ответа на `GET` в кэше.

`OPTIONS` сообщает доступные способы взаимодействия с ресурсом или сервером:

- `OPTIONS /v1/orders/42` относится к конкретному ресурсу;
- `OPTIONS *` относится к серверу в целом;
- заголовок `Allow` перечисляет поддерживаемые методы;
- браузер использует `OPTIONS` для CORS preflight, но этим назначение метода не
  ограничивается.

Поддержку нельзя всегда делегировать gateway: приложение должно проверить,
какие `HEAD` и `OPTIONS` действительно обслуживает его HTTP-стек.

### `405 Method Not Allowed` и `501 Not Implemented`

`405` означает: сервер знает метод, но не разрешает его для этого ресурса. В
ответе должен быть `Allow`. `501` означает: сервер не распознаёт метод или не
поддерживает необходимую для него функциональность.

## Резюме: правило выбора метода

1. Чтение, которое клиент не воспринимает как изменение ресурса, → `GET`.
2. Сложный, большой или чувствительный фильтр может оправдать
   `POST /resource:search`; операция при этом остаётся только чтением на уровне
   приложения, но HTTP не считает метод `POST` безопасным.
3. Создание с URI, выбранным сервером, → `POST /collection` и обычно
   `201 Created + Location`.
4. Создание или полная замена по известному URI → `PUT /collection/{id}`.
5. Частичное изменение → `PATCH /collection/{id}` с `FieldMask`, JSON Merge
   Patch или JSON Patch.
6. Идемпотентное «установить состояние» → ресурсный `PUT`.
7. Удаление → `DELETE /collection/{id}`; тело не использовать без явно
   согласованной семантики.
8. Действие, которое не выражается стандартными методами, → явный custom method
   вида `POST /collection/{id}:verb`.
9. Защита от потерянного обновления → `ETag` + `If-Match`.
10. Защита от повторного бизнес-эффекта → ключ идемпотентности или другой
    атомарный механизм дедупликации.

Это стартовые правила, а не замена проектированию. Окончательный выбор зависит
от модели ресурса, требований к повторам, кэшированию, конкурентным изменениям
и ограничений клиентов или gateway.

## Interview-ready answer

**1. Чем безопасный метод отличается от идемпотентного?**

- Безопасность — клиент не запрашивает изменение состояния ресурса; служебные
  эффекты вроде логирования допустимы.
- Идемпотентность — один и несколько одинаковых запросов имеют один
  предполагаемый эффект на ресурс.
- Связь — безопасные методы идемпотентны, но `PUT` и `DELETE` идемпотентны и при
  этом небезопасны.
- Ответ — повтор может вернуть другой статус: второй `DELETE` способен вернуть
  `404`, хотя ресурс остаётся удалённым.
- Кэширование — отдельное свойство, которое нельзя вывести только из
  безопасности или идемпотентности.

**2. Почему для чтения предпочитают GET и когда допустим POST?**

- Причина — `GET` сообщает кэшам, клиентам и средствам наблюдаемости стандартную
  семантику безопасного чтения.
- Кэш — `POST` можно кэшировать при явной свежести, но это поддерживается хуже и
  часто требует специальной настройки.
- Компромисс — `POST /orders:search` оправдан для большого, вложенного или
  чувствительного фильтра.
- Ограничение — на уровне приложения такой поиск только читает данные, но HTTP
  не считает метод `POST` безопасным; политику повторов нужно документировать
  отдельно.

**3. `PUT` или `PATCH`?**

- `PUT` — создаёт или полностью заменяет представление по известному URI и
  идемпотентен по стандартной семантике.
- `PATCH` — передаёт частичное изменение и не гарантирует идемпотентность для
  произвольного формата дельты.
- Формат — различие «поле не прислали» и «поле нужно обнулить» выражают через
  `FieldMask`, JSON Merge Patch или другой явный контракт.
- Конкуренция — `If-Match` защищает оба метода от записи поверх более новой
  версии ресурса.

**4. Как сделать `POST` повторяемым без второго бизнес-эффекта?**

- Контракт — клиент присылает ключ идемпотентности, а сервер сохраняет результат
  первой обработки и возвращает его на повтор.
- Область ключа — один ключ соответствует одной логической операции, а не одной
  сетевой попытке.
- Атомарность — проверка и фиксация ключа выполняются как одна защищённая
  операция, иначе два параллельных запроса оба начнут обработку.
- Срок жизни — сервер хранит ключ достаточно долго, чтобы перекрыть окно
  возможных повторов.

**5. Чем `If-Match` отличается от `Idempotency-Key`?**

- `If-Match` — проверяет версию ресурса и предотвращает потерянное обновление.
- `Idempotency-Key` — распознаёт повтор одной логической операции и предотвращает
  второй бизнес-эффект.
- Совместное применение — неидемпотентная операция над конкурентно изменяемым
  ресурсом может требовать обоих механизмов.
