Go 1.24.0 выпущен 11 февраля 2025 года. Релиз почти не требует переписывать прикладной код, но меняет три важных слоя: организацию инструментов проекта, внутреннюю реализацию `map` и несколько API для безопасной работы с файлами, benchmarks и очисткой ресурсов.

---

## Ментальная модель

Go 1.24 — релиз инфраструктуры вокруг программы. Generic type aliases расширяют язык, но основная практическая ценность находится в toolchain, runtime и стандартной библиотеке:

- инструменты вроде генераторов можно фиксировать прямо в `go.mod`;
- runtime меняет внутреннее устройство `map`, не меняя контракт встроенного типа;
- стандартная библиотека добавляет узкие API для проблем, которые раньше решались самописными обходными путями.

Совместимость исходного кода не означает идентичность поведения. Новый `vet` находит дополнительные ошибки, crypto-пакеты отвергают часть устаревших данных, а профили CPU и памяти могут измениться из-за новой реализации runtime.

## Краткий обзор

| Категория | Изменение | Практический эффект |
| --- | --- | --- |
| Язык | Generic type aliases | Параметризованный псевдоним сохраняет идентичность исходного типа |
| Инструменты | Директива `tool` в `go.mod` | Больше не нужен файл `tools.go` с пустыми imports |
| Инструменты | `go build -json`, JSON-события в `go test -json` | CI не обязан разбирать неструктурированный текст |
| Инструменты | `GOCACHEPROG` вышел из эксперимента | Внешний процесс может обслуживать кэш сборки и тестов |
| Runtime | Встроенный `map` перешёл на Swiss Tables | Лучше locality; внутреннее устройство старого `hmap` больше не описывает текущий runtime |
| Стандартная библиотека | `os.Root` | Операции с файлами ограничиваются выбранным каталогом |
| Стандартная библиотека | `testing.B.Loop` | Меньше ошибок в benchmarks и меньше риска удалить полезную работу оптимизацией |

| Crypto | ML-KEM, FIPS-механизмы, более строгие RSA/X.509 defaults | Новые возможности и возможные отказы на устаревших ключах или сертификатах |

## Что изменилось

### Язык: generic type aliases

**Type alias** — другое имя того же типа. В Go 1.24 alias может иметь собственные type parameters:

```go
type Set[T comparable] = map[T]struct{}

var ready Set[string] = map[string]struct{}{
    "worker-1": {},
}
```

Alias нужно отличать от определения нового типа:

```go
type IDs[T ~int64] = []T  // тот же тип, что и []T
type UserIDs []int64      // новый defined type
```

У alias нет новой идентичности типа и собственного набора методов. Он удобен при переименовании или реэкспорте generic-типа без дополнительной конвертации. Если нужны отдельные инварианты, методы или защита от случайного смешивания значений, требуется defined type, а не alias.

---

### Инструменты проекта в `go.mod`

До Go 1.24 зависимости генераторов и анализаторов часто удерживали через файл `tools.go`:

```go
//go:build tools

package tools

import _ "golang.org/x/tools/cmd/stringer"
```

Теперь `go get -tool` добавляет executable package как инструмент модуля, а `go tool` запускает зафиксированную версию:

```bash
go get -tool golang.org/x/tools/cmd/stringer@v0.30.0
go tool stringer -type=Status
```

В `go.mod` появляется директива `tool`, а версия модуля остаётся в `require`. Команды `go get tool` и `go install tool` работают со всеми инструментами текущего модуля.

Trade-off не исчезает: инструменты участвуют в графе модулей и могут влиять на выбор версий общих зависимостей. После миграции нужно проверить `go mod tidy`, генерацию и воспроизводимость CI.

---

### Структурированный вывод сборки

`go build` и `go install` принимают `-json`. `go test -json` также включает события сборки и отличает их от событий тестов по полю `Action`. Это полезно для CI-интерфейсов, собственных панелей сборки и агрегации ошибок.

`GOCACHEPROG` позволяет обслуживать кэш дочерним процессом по JSON-протоколу. Это низкоуровневая точка расширения для больших систем сборки, а не готовый сетевой кэш: протокол хранения, безопасность, вытеснение и наблюдаемость всё равно остаются задачами выбранной реализации.

### Swiss Tables для встроенных map

Public contract `map` не меняется: порядок обхода не гарантирован, конкурентная запись без синхронизации остаётся ошибкой, а адрес элемента получить нельзя. Меняется реализация runtime — вместо исторического `hmap` используется дизайн на основе Swiss Tables.

По release notes совокупность нескольких runtime-оптимизаций уменьшает CPU overhead на 2–3% в среднем по набору репрезентативных benchmarks. Это не означает, что любая операция с `map` ускоряется на 2–3%: результат зависит от размера ключей и значений, доли lookup/insert/delete, локальности кэша и архитектуры CPU.

Подробная механика разобрана отдельно: [Swiss Tables в Go 1.24+](../01-go-core/map-internals/01-swiss-tables-since-1.24.md).

Код, который через `unsafe` полагался на layout старого `hmap`, изначально нарушал контракт и после обновления может сломаться. Обычный код с `map` не должен знать о группах, control bytes или внутреннем каталоге таблиц.

### Ограниченный каталог через os.Root

`os.OpenRoot` возвращает `os.Root`; его методы не разрешают выйти за выбранный каталог, в том числе по символической ссылке наружу:

```go
func readUserFile(baseDir, name string) ([]byte, error) {
    root, err := os.OpenRoot(baseDir)
    if err != nil {
        return nil, err
    }
    defer root.Close()

    file, err := root.Open(name)
    if err != nil {
        return nil, err
    }
    defer file.Close()

    return io.ReadAll(file)
}
```

Обычный `filepath.Join(baseDir, name)` только строит путь и сам по себе не создаёт границу доступа. `os.Root` проверяет операции относительно открытого корня.

Это не полный sandbox процесса. Код по-прежнему может вызвать обычный `os.Open`, обратиться к сети или выполнить системный вызов. `os.Root` ограничивает конкретные файловые операции, выполненные через его методы.

### Benchmarks через testing.B.Loop

Новый цикл заменяет ручную работу с `b.N`:

```go
func BenchmarkEncode(b *testing.B) {
    input := Payload{ID: 42, Name: "worker"}

    for b.Loop() {
        encode(input)
    }
}
```

Benchmark-функция выполняется один раз на каждый `-count`, поэтому setup и cleanup вне цикла не повторяются при подборе числа итераций. Аргументы и результаты вызовов внутри цикла сохраняются живыми, что мешает компилятору полностью удалить измеряемую работу.

`B.Loop` не делает benchmark корректным автоматически. Внутри всё ещё нельзя незаметно измерять логирование, случайный ввод-вывод или конкурирующую подготовку вместо целевой операции.

### runtime.AddCleanup

`runtime.AddCleanup` регистрирует функцию, которая может выполниться после того, как объект становится недостижимым:

```go
type Resource struct {
    handle int
}

func NewResource() *Resource {
    resource := &Resource{handle: openHandle()}
    runtime.AddCleanup(resource, closeHandle, resource.handle)
    return resource
}
```

В отличие от `SetFinalizer`, к одному объекту можно привязать несколько cleanups, аргумент cleanup не обязан быть самим объектом, а циклы ссылок обычно не приводят к тем же проблемам удержания памяти.

Cleanup не гарантирован до завершения процесса и может сработать заметно позже потери последней ссылки. Поэтому `Close` и `defer resource.Close()` остаются основным контрактом для файлов, соединений и транзакций; `AddCleanup` подходит как страховка или для низкоуровневых структур, где детерминированное освобождение невозможно.

### Crypto и совместимость данных

Go 1.24 добавляет `crypto/mlkem` с ML-KEM-768 и ML-KEM-1024, новые стандартные пакеты `crypto/hkdf`, `crypto/pbkdf2` и `crypto/sha3`, а также механизмы сборки и запуска Go Cryptographic Module в FIPS 140-3 mode.

Наличие этих механизмов не делает произвольное приложение автоматически сертифицированным: важны версия модуля, режим запуска, разрешённые алгоритмы и требования конкретной среды.

Есть и более строгие defaults:

- `crypto/rsa` отвергает ключи короче 1024 бит;
- `crypto/x509.Certificate.Verify` больше не поддерживает подписи SHA-1;
- `crypto/tls` по умолчанию включает гибридный post-quantum key exchange `X25519MLKEM768`;
- некоторые старые или некорректные RSA-ключи и сертификаты теперь отвергаются.

Именно эти изменения чаще затрагивают legacy-интеграции, чем новый синтаксис языка.

## Практические последствия

- **Tooling.** Генераторы и CLI-инструменты можно версионировать без фиктивных imports, но их граф зависимостей нужно проверять так же, как граф приложения.
- **Производительность.** Новая реализация `map` и распределителя памяти меняет профили CPU; выигрыш подтверждается только benchmark или production-профилем конкретного сервиса.
- **Безопасность файлов.** `os.Root` уменьшает риск path traversal в распаковщиках архивов, файловых API и плагинах, если все чувствительные операции проходят через root.
- **Управление ресурсами.** `AddCleanup` уменьшает ущерб от забытого освобождения, но не заменяет явный lifecycle.
- **Криптография.** Старые ключи, сертификаты и несовместимые TLS peers могут перестать работать, хотя прикладной код успешно компилируется.

## Что проверить перед апгрейдом

1. Запустить `go test ./...` и `go vet ./...`: новые анализаторы находят некорректно объявленные тесты и небезопасные вызовы `fmt.Printf(variable)`.
2. Найти `tools.go` и решить, выгодна ли миграция на директиву `tool`; это не обязательное условие обновления.
3. Проверить код с `unsafe`, который касается `map`, runtime structs или бинарного layout.
4. Прогнать TLS- и X.509-интеграционные тесты на реальных legacy certificates и peers.
5. Сравнить CPU, аллокации и tail latency на репрезентативной нагрузке.
6. Для файловых API проверить не только `..`, но и символические ссылки, переименования и platform-specific пути.

---

## Типичные ошибки

- Приписывать новой реализации `map` все заявленные 2–3% экономии CPU, хотя число относится к совокупности runtime-оптимизаций.
- Считать `os.Root` sandbox всего процесса и продолжать выполнять часть чувствительных операций через обычный пакет `os`.
- Использовать `AddCleanup` для обязательного освобождения дефицитного ресурса вместо явного `Close`.
- Заменять defined type на alias там, где требуются собственные методы и несовместимость типов.
- Обновить компилятор, но не прогнать интеграции со старыми RSA-ключами, SHA-1 certificates или нестандартными TLS peers.

## Interview-ready answer

**1. Что в Go 1.24 меняет встроенный map?**

- Суть — runtime переходит на реализацию на основе Swiss Tables, сохраняя публичный контракт `map`.
- Производительность — лучше locality может снизить CPU, но итог зависит от access pattern и измеряется на конкретной нагрузке.
- Совместимость — обычный Go-код продолжает работать; ломается только код с недопустимыми `unsafe`-допущениями о старом `hmap`.

**2. Зачем нужна директива tool в go.mod?**

- Задача — фиксировать версии генераторов и анализаторов как часть модуля без файла `tools.go`.
- Запуск — `go get -tool` добавляет инструмент, а `go tool` запускает зафиксированную версию.
- Trade-off — зависимости инструментов остаются частью module graph и требуют контроля.

**3. Чем os.Root отличается от filepath.Join?**

- Граница — методы `os.Root` не позволяют файловой операции выйти из открытого каталога, включая выход через symlink.
- Join — `filepath.Join` только нормализует и соединяет строки пути, но не ограничивает доступ.
- Ограничение — `os.Root` не изолирует сеть, процессы или обычные вызовы пакета `os`.

**4. Заменяет ли runtime.AddCleanup явный Close?**

- Ответ — нет, cleanup выполняется недетерминированно и не гарантирован до завершения процесса.
- Применение — это страховка для низкоуровневого ресурса, если владелец забыл явное освобождение.
- Основной контракт — дефицитные ресурсы закрываются явно, обычно через `defer`.
