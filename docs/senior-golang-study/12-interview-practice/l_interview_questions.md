## Скрининг

### Сети, инфраструктура, git

**Какие протоколы поверх HTTP знаешь?**

- Протоколы в строгом смысле — задают собственный формат сообщений и правила обмена:
  - gRPC — RPC поверх HTTP/2: бинарный protobuf, мультиплексирование, стриминг в обе стороны;
  - SOAP — XML-конверт со своей семантикой (заголовки, faults), HTTP тут только транспорт;
  - JSON-RPC — минималистичный конверт запрос/ответ в JSON, тоже транспорт-агностичный: по HTTP обычно один POST-эндпоинт;
  - WebSocket — начинается с HTTP-запроса `Upgrade`, но после хендшейка это уже не HTTP, а свой полнодуплексный кадровый протокол на том же TCP-соединении;
  - WebDAV — расширение самого HTTP новыми методами (`PROPFIND`, `MKCOL`, `LOCK`).
- Не протоколы, хотя перечисляют в одном ряду:
  - REST — архитектурный стиль поверх обычного HTTP: ресурсы в URL, семантика методов, коды статусов;
  - GraphQL — язык запросов и система типов; транспорт не оговаривает, по HTTP обычно ездит одним `POST /graphql`;
  - OData — соглашение о синтаксисе запросов и метаданных поверх REST (`$filter`, `$expand`).
- Пограничный случай — SSE: не отдельный протокол, а формат тела ответа `text/event-stream`. Соединение остаётся обычным HTTP-ответом, который сервер просто не закрывает и дописывает события.
- Сам HTTP идёт поверх — TCP для HTTP/1.1 и HTTP/2, плюс TLS для https; HTTP/3 — поверх QUIC, то есть уже UDP.
- См. [protocols/00-protocol-comparison.md](../08-networking-and-api/protocols/00-protocol-comparison.md).

**Какие виды хранилищ знаешь?**

- Реляционные (PostgreSQL, MySQL) — строгая схема, ACID, JOIN.
- Документные (MongoDB) — гибкая JSON-схема.
- Key-value (Redis, DynamoDB) — быстрый доступ по ключу.
- Колоночные и wide-column (ClickHouse, Cassandra) — аналитика и большой объём записи.
- Графовые (Neo4j) — связи и обходы.
- Поисковые (Elasticsearch) — полнотекст.
- Блоб-хранилища и объектные (S3) — файлы.
- Как выбирать — по модели данных, паттерну доступа и требованиям к консистентности.
- См. [database-systems-catalog/01-comparison-table.md](../06-databases/database-systems-catalog/01-comparison-table.md).

**Для чего нужны линтеры?**

- Что делают — статический анализ кода без его запуска.
- Что ловят — баги (непроверенные ошибки, гонки, разыменование nil), нарушения единого стиля, запахи и уязвимости.
- Зачем команде — снимают с ревью споры о стиле и типовые придирки, оставляя людям обсуждение логики.
- Стандарт де-факто в Go — `golangci-lint`: агрегатор, прогоняющий `govet`, `staticcheck`, `errcheck`, `gosec` и десятки других за один проход.
- Где включать — в CI как блокирующий шаг и в pre-commit локально.

**Зачем нужны моки?**

- Что делают — подменяют зависимости (БД, внешние API) на управляемые заглушки.
- Что это даёт:
  - Изоляцию — тестируется своя логика, а не чужой сервис.
  - Скорость и детерминированность — нет сети и реальных данных.
  - Возможность проверить взаимодействие — с какими аргументами и сколько раз вызвали зависимость.
  - Моделирование сбоев — ошибки, таймауты, пустые ответы, которые в реальности не воспроизвести по требованию.
- Чего не заменяют — интеграционных тестов: мок проверяет ваши предположения о зависимости, а не саму зависимость.
- См. [09-testing-and-quality/03-test-doubles-and-test-design.md](../09-testing-and-quality/03-test-doubles-and-test-design.md).

**Чем образ отличается от контейнера?**

- Образ — неизменяемый шаблон из слоёв только для чтения: код, зависимости и метаданные о том, что запускать.
- Контейнер — запущенный экземпляр образа: к слоям образа добавляется writable-слой поверх, и стартует процесс в своих namespace и cgroups.
- Аналогия — образ это класс, контейнер это объект; из одного образа поднимают сколько угодно контейнеров.
- Практическое следствие — данные, записанные в writable-слой, умирают вместе с контейнером, поэтому состояние выносят в тома.
- См. [docker/02-containers.md](../10-devops-and-observability/docker/02-containers.md).

**Какие есть способы прокинуть исходный код в контейнер?**

- `COPY` в Dockerfile — зашить код в образ на этапе сборки; это основной способ.
- `ADD` — то же самое плюс распаковка архивов и загрузка по URL, но из-за неявности его берут только когда нужна распаковка.
- Bind-mount (`-v $PWD:/app`) — примонтировать каталог с хоста, чтобы работал hot-reload при разработке.
- Именованный том — когда нужна не выдача исходников, а сохранение данных между перезапусками.
- Как выбирать — для прода `COPY` вместе с multi-stage build, чтобы в финальный образ попал только бинарь; для локальной разработки bind-mount.
- См. [dockerfiles-for-go/02-dockerfile-anatomy.md](../10-devops-and-observability/dockerfiles-for-go/02-dockerfile-anatomy.md).

**Чем отличается merge от rebase?**

- `merge` — объединяет ветки merge-коммитом, сохраняя историю как есть: нелинейная, но правдивая.
- `rebase` — переносит коммиты ветки поверх целевой, переписывая их: линейная чистая история, но новые хеши.
- Главное правило — не ребейзить опубликованные и общие ветки.
- Когда что — merge для интеграции в общие ветки, rebase для причёсывания своей локальной ветки перед PR.

### Очереди и Kafka

**Для чего нужны очереди?**

- Развязка — продюсер и консьюмер не знают друг о друге и не обязаны быть живыми одновременно.
- Сглаживание пиков — очередь работает буфером, а её длина становится видимым сигналом перегрузки.
- Асинхронная обработка — долгие операции уходят из запроса пользователя в фон.
- Надёжность — сообщение переживает падение консьюмера, ретраи и dead letter queue встроены в модель.
- Фан-аут — одно событие получают несколько независимых потребителей.
- Масштабирование — консьюмеров добавляют горизонтально, не трогая продюсера.
- См. [07-message-brokers-and-streaming/README.md](../07-message-brokers-and-streaming/README.md).

**Гарантирована ли доставка сообщений в Kafka?**

- Короткий ответ — да, но это результат настройки, а не свойство «из коробки».
- Что обеспечивает сохранность — репликация партиций вместе с `acks=all` и `min.insync.replicas`: запись подтверждается, только когда её приняли все синхронные реплики.
- Базовая семантика — at-least-once, то есть дубликаты возможны и обработчик должен быть идемпотентным.
- Exactly-once — достижим внутри Kafka через идемпотентного продюсера и транзакции, но не распространяется на внешние побочные эффекты.
- Как потерять сообщения — выставить `acks=0` или `acks=1`: во втором случае подтверждение приходит от лидера до репликации, и его падение уносит хвост.
- Детали — в секции [техничка про Kafka](#техничка--теория).

### Go — основы

**Чем отличается массив от слайса?**

- Массив `[N]T` — длина фиксирована и входит в тип, значение копируется целиком.
- Слайс — заголовок `{указатель, len, cap}` поверх backing-массива; копируется только заголовок, сам массив остаётся общим.
- Что из этого следует — изменение элемента через копию слайса видно снаружи, а через копию массива нет.
- См. [04-slices.md](../01-go-core/04-slices.md).

**Как объединить два слайса?**

- Коротко — `c := append(a, b...)` через variadic-распаковку.
- Безопаснее — собрать в новый слайс, чтобы не затронуть backing-массив `a`: `c := make([]T, 0, len(a)+len(b)); c = append(c, a...); c = append(c, b...)`.
- Из стандартной библиотеки — `slices.Concat(a, b)`, добавлен в Go 1.22.

**Как получить первые N элементов слайса?**

- Слайсинг: `s[:n]` (первые n, разделяет backing-массив с исходным). Если нужна независимая копия — `append([]T(nil), s[:n]...)` или `slices.Clone(s[:n])`.

**Что такое map?**

- Встроенная хеш-таблица «ключ → значение», доступ в среднем O(1) (худший случай O(n) при вырожденном распределении хешей). С Go 1.24 — на Swiss Tables. См. [map-internals](../01-go-core/map-internals/README.md).

**Какой порядок обхода map?**

- Не определён и намеренно рандомизирован: рантайм стартует итерацию со случайного бакета, чтобы код не закладывался на порядок. Нужен порядок — собрать ключи в слайс и отсортировать.

**Какие ключи можно использовать для map?**

- Можно — любые сравнимые (`==`) типы: bool, числа, string, указатели, каналы, интерфейсы, а также структуры и массивы из сравнимых типов.
- Нельзя — slice, map, функции. Это ошибка компиляции, а не рантайма: `map[[]int]string` просто не соберётся («invalid map key type»).
- Отдельный случай — `map[any]T`: статический тип ключа сравним, а динамический может и не быть. Запись слайса в такую map компилируется и падает уже в рантайме: `runtime error: hash of unhashable type []int`.

### Go — конкурентность

**Что такое горутина? Кто ей управляет?**

- Что это — лёгкий поток исполнения со стартовым стеком около 2 КБ, который растёт и сжимается по мере надобности.
- Кто управляет — планировщик рантайма Go, а не ядро ОС.
- Модель — G-M-P: G это горутина, M это поток ОС, P это логический процессор с локальной очередью.
- Почему дёшево — горутины мультиплексируются на небольшое число потоков, а переключение между ними идёт в пространстве пользователя, без системного вызова.
- См. [runtime-scheduler/01-scheduler-and-preemption.md](../01-go-core/runtime-scheduler/01-scheduler-and-preemption.md).

**Что такое каналы? Зачем нужны? Какие бывают?**

- Что это — типизированная труба для передачи данных между горутинами; она же точка синхронизации.
- Зачем — реализует принцип «share memory by communicating»: владение значением передаётся, а не разделяется под блокировкой.
- По буферизации — небуферизированные (рандеву: отправитель ждёт получателя) и буферизированные (`make(chan T, n)`).
- По направлению — двунаправленный `chan T`, только на приём `<-chan T`, только на отправку `chan<- T`; направление в сигнатуре функции документирует роль и проверяется компилятором.
- См. [concurrency-and-performance/02-goroutines-and-channels.md](../01-go-core/concurrency-and-performance/02-goroutines-and-channels.md).

**Аксиомы каналов?**

- Nil-канал — и отправка, и чтение блокируются навсегда; этим пользуются, чтобы выключить ветку в `select`.
- Чтение из закрытого — не блокирует: сначала отдаётся остаток буфера, потом бесконечно нулевое значение; проверка через `v, ok := <-ch`.
- Отправка в закрытый канал — паника. Повторный `close` и `close(nil)` — тоже паника.
- Кто закрывает — всегда отправитель и ровно один раз; получатель закрывать не должен.
- Закрытие как сигнал — это broadcast: его увидят сразу все читатели, поэтому закрытый канал удобен как «стоп» для группы горутин.

**Select каналов?**

- `select` ждёт готовности одного из нескольких каналов; если готовы несколько — выбирает случайный; `default` делает неблокирующим; `case <-ctx.Done()` — типовой выход по отмене. Пустой `select{}` блокируется навсегда.

**Race condition?**

- Race condition — логическая ошибка: результат зависит от порядка/тайминга операций. Свойство алгоритма, а не отдельной переменной; `-race` его не ловит.
- Data race — нарушение модели памяти: два конкурентных доступа к одной ячейке памяти, хотя бы один из них запись, и между ними нет happens-before. Свойство кода, ловится `go test -race`/`go run -race`; по спецификации Go это undefined behavior.
- Одно без другого бывает — race condition без data race: `Lock` → прочитали баланс → `Unlock` → `if b >= amount` → `Lock` → списали → `Unlock`. Каждый доступ синхронизирован, `-race` молчит, но «проверить и списать» не атомарно как целое, и две горутины уводят баланс в минус.
- Обратное тоже бывает — две горутины пишут в переменную одно и то же значение: результат «правильный», а data race по спеке есть.
- Лечится по-разному — data race закрывается мьютексом/атомиком/каналом, race condition — расширением критической секции и дизайном инварианта.
- См. [concurrency-and-performance/01-memory-model.md](../01-go-core/concurrency-and-performance/01-memory-model.md).

**Примитивы синхронизации?**

- Из пакета `sync` — `Mutex` и `RWMutex`, `WaitGroup`, `Once`, `Cond`, `Map`.
- Атомарные операции — пакет `sync/atomic` для счётчиков, флагов и указателей.
- Языковые средства — каналы и `context` для отмены.
- Из `golang.org/x/sync` — `errgroup`, `semaphore`, `singleflight`.
- Как усилить ответ — назвать к каждому сценарий, а не только имя.
- См. [concurrency-and-performance/03-sync-primitives.md](../01-go-core/concurrency-and-performance/03-sync-primitives.md).

### Go — язык и инструменты

**Есть ли наследование в Go?**

- Нет. Вместо наследования — композиция (встраивание структур, embedding) и интерфейсы (неявная реализация). Переиспользование через «has-a», полиморфизм через интерфейсы.

**Использовал type switch?**

- Да: `switch v := x.(type) { case int: …; case string: … }` — ветвление по динамическому типу значения в интерфейсе; типобезопасная альтернатива цепочке type assertion. Применяют для разбора `any`, ошибок, AST.

**Для чего нужен пакет errors?**

- Работа с ошибками-значениями: оборачивание (`fmt.Errorf("...: %w", err)`), `errors.Is` (сравнение с sentinel), `errors.As` (извлечение типа), `errors.Unwrap`, `errors.Join` (1.20). Даёт цепочку контекста без потери исходной ошибки. См. [05-error-handling.md](../01-go-core/05-error-handling.md).

**Использовал pprof? Инструменты для отладки?**

- pprof — профили CPU, heap, goroutine, mutex и block; `net/http/pprof` для снятия прямо с прода, разбор через `go tool pprof`.
- Race-детектор — `go test -race`, обязателен в CI.
- Бенчмарки — `go test -bench -benchmem`, чтобы видеть не только время, но и аллокации.
- `runtime/trace` — поведение планировщика, задержки, блокировки во времени.
- `GODEBUG` — быстрые переключатели без перекомпиляции: `gctrace=1` по сборщику, `schedtrace` по планировщику.
- Статический анализ и отладчик — `go vet` и `delve`.
- См. [profiling/01-pprof-tools-and-workflow.md](../01-go-core/profiling/01-pprof-tools-and-workflow.md).

### Базы данных

**Индексы в БД? Плюсы и минусы?**

- Что это — отдельная структура данных поверх таблицы, чтобы находить строки по условию, сортировать и джойнить без полного скана.
- Виды в PostgreSQL:
  - B-tree — дефолт: равенство, диапазоны, сортировка, leftmost-prefix у составных;
  - Hash — только равенство, зато компактнее B-tree на длинных ключах;
  - GIN — «много значений в одном поле»: jsonb, массивы, полнотекстовый поиск;
  - GiST — геоданные и пересечения диапазонов, а также ограничения `EXCLUDE`;
  - BRIN — очень большие таблицы, где физический порядок строк коррелирует со значением (логи, append-only по времени): крошечный размер ценой точности.
- Плюсы:
  - чтение по условию из O(n) превращается в O(log n) вместо seqscan;
  - убирают сортировку на `ORDER BY` и ускоряют джойны (merge join, index nested loop);
  - index-only scan отдаёт данные, вообще не заглядывая в таблицу;
  - уникальный индекс заодно обеспечивает ограничение целостности.
- Минусы:
  - каждая запись дороже: `INSERT`/`UPDATE`/`DELETE` обновляют ещё и все индексы таблицы;
  - занимают место на диске и в памяти, конкурируя за кеш с самой таблицей;
  - неиспользуемые и дублирующие индексы дают только накладные расходы;
  - планировщик тратит время на их перебор, а неактуальная статистика приводит к выбору не того индекса.
- Когда не поможет — низкая селективность (условие выбирает большую долю таблицы), функция над столбцом без функционального индекса, `LIKE '%…'` с ведущим шаблоном.
- См. [postgresql/02-indexes.md](../06-databases/database-systems-catalog/postgresql/02-indexes.md).

**Зачем транзакции? Уровни изоляции?**

- Зачем — атомарная единица работы с гарантиями ACID: набор операций применяется целиком либо не применяется вовсе.
- Уровни изоляции — по возрастанию строгости, каждый следующий отсекает всё, что предыдущий, плюс своё:
  - `READ UNCOMMITTED` — в PostgreSQL совпадает с `READ COMMITTED`: dirty read невозможен в принципе, его не даёт MVCC;
  - `READ COMMITTED` (дефолт PG) — снимок берётся на каждый запрос, отсекает dirty read; non-repeatable и phantom read остаются;
  - `REPEATABLE READ` — снимок фиксируется на всю транзакцию, отсекает non-repeatable read и в PostgreSQL ещё и phantom read (в стандарте ANSI на этом уровне фантомы допустимы); write skew остаётся;
  - `SERIALIZABLE` — SSI поверх снимка, отсекает и write skew: результат эквивалентен какому-то последовательному выполнению транзакций.
- Цена — на RR и Serializable конкурентная транзакция может отвалиться с `40001 serialization_failure`, поэтому обязателен retry всей транзакции.
- См. [postgresql/04-transactions-and-locking.md](../06-databases/database-systems-catalog/postgresql/04-transactions-and-locking.md).

**Расскажи про JOIN.**

- Что это — соединение строк таблиц по условию.
- Виды по логике:
  - `INNER` — только строки, где совпадение нашлось в обеих таблицах.
  - `LEFT` и `RIGHT` — все строки из левой (правой) таблицы плюс совпадения, где их нет подставляется NULL.
  - `FULL` — все строки из обеих таблиц.
  - `CROSS` — декартово произведение, без условия.
- Не путать с алгоритмами — какой из nested loop, hash join или merge join применить, решает планировщик; это уровень исполнения, а не язык запроса.
- См. [postgresql/00-sql-basics-and-syntax.md](../06-databases/database-systems-catalog/postgresql/00-sql-basics-and-syntax.md).

**Deadlock в базе данных?**

- Что происходит — две транзакции взаимно ждут друг друга: T1 держит A и ждёт B, T2 держит B и ждёт A. Сами они не разойдутся.
- Что делает СУБД — находит цикл в графе ожиданий и откатывает одну транзакцию-жертву с ошибкой.
- Профилактика:
  - Захватывать строки в едином порядке, например всегда по возрастанию id.
  - Держать транзакции короткими, без внешних вызовов внутри.
  - Не расширять область блокировок без необходимости.
  - Предусмотреть ретрай: жертву откатили, повтор обычно проходит.
- См. [postgresql/04-transactions-and-locking.md](../06-databases/database-systems-catalog/postgresql/04-transactions-and-locking.md).

**Денормализация — плюсы и минусы?**

- Что это — намеренное дублирование или предрасчёт данных вопреки нормальным формам, чтобы читать быстрее: денормализованный столбец-копия, счётчик-агрегат, материализованное представление.
- Плюсы:
  - меньше JOIN на горячем пути — данные лежат рядом и читаются одним обращением;
  - агрегаты считаются заранее, а не на каждый запрос;
  - меньше нагрузка на планировщик и предсказуемее план запроса;
  - в распределённой системе избавляет от похода в соседний сервис за теми же полями.
- Минусы:
  - избыточность и рост объёма — данные лежат в нескольких местах, индексов тоже больше;
  - риск рассинхрона копий — источником правды остаётся одно место, остальное нужно обновлять;
  - запись дорожает и усложняется: обновлять надо всюду, желательно в одной транзакции или через Outbox;
  - схему тяжелее менять, а копии нужно уметь пересобирать (бэкфилл).
- Как применяют — точечно, под конкретный доказанный read-паттерн, а не «на всякий случай». Сначала нормальная схема и индексы, денормализация — когда план запроса упёрся.

## Техничка — теория

### Kafka и доставка сообщений

**За счёт чего обеспечивается отказоустойчивость Kafka?**

- Основа — репликация партиций: у каждой партиции есть leader и follower-реплики, их число задаёт `replication.factor`.
- ISR — набор реплик, догнавших лидера; запись считается надёжной после попадания в них.
- Отказоустойчивость — при падении брокера-лидера новым лидером становится одна из реплик ISR.
- Что даёт гарантию — связка `acks=all` и `min.insync.replicas`: подтверждённое сообщение заведомо лежит более чем на одном узле.
- Хранение — данные лежат на диске в виде лога и живут по политике retention, а не удаляются после чтения.
- См. [07-message-brokers-and-streaming/01-kafka.md](../07-message-brokers-and-streaming/01-kafka.md).

**Какие гарантии доставки предоставляет Kafka?**

- Три семантики: at-most-once, at-least-once (дефолт на практике) и exactly-once (идемпотентный продюсер + транзакции). Выбор регулируется `acks`, ретраями продюсера и моментом коммита offset у консьюмера.

**Что такое at-most-once?**

- «Не более одного раза»: сообщение может быть потеряно, но никогда не дублируется. Достигается, когда offset коммитят до обработки (или `acks=0`): упали после коммита — сообщение потеряно. Подходит, где потеря терпима, а дубль — нет (метрики, логи).

**Что такое at-least-once?**

- «Не менее одного раза»: сообщение не теряется, но возможны дубли. Offset коммитят после успешной обработки: упали до коммита — сообщение прочитают повторно. Самый частый выбор; требует идемпотентной обработки.

**at-least-once, но бизнес-логика чувствительна к дубликатам — что делать?**

- Общая идея — не бороться с дублями, а сделать так, чтобы повтор не менял результат.
- Дедупликация по ключу — таблица обработанных id сообщения или `idempotency-key`, вставка через `INSERT ... ON CONFLICT DO NOTHING`.
- Upsert вместо insert — операция становится безопасной при повторе сама по себе.
- Проверка состояния перед эффектом — если заказ уже оплачен, второй платёж не проводится.
- Транзакции Kafka — дают exactly-once внутри конвейера consume-process-produce, но не покрывают внешние побочные эффекты.
- См. [reliability-patterns/06-idempotency.md](../05-system-design/reliability-patterns/06-idempotency.md).

### Микросервисы и распределённость

**Плюсы и минусы микросервисной архитектуры?**

- Плюсы:
  - независимый деплой — релиз одного сервиса не тянет за собой остальные и не требует общего окна;
  - независимое масштабирование — реплики добавляют там, где нагрузка, а не всему монолиту целиком;
  - изоляция отказов — падение некритичного сервиса не роняет систему, если есть таймауты, ретраи и circuit breaker;
  - технологическая свобода — свой язык и своё хранилище под задачу сервиса;
  - автономные команды — граница сервиса совпадает с зоной ответственности, меньше конфликтов в общей кодовой базе.
- Минусы:
  - распределённая сложность — вместо вызова функции сеть: латентность, таймауты, ретраи, частичные отказы;
  - нет ACID между сервисами — согласованность собирают на Saga и Outbox, живут с eventual consistency;
  - сложнее отладка — нужен distributed tracing, централизованные логи и корреляция по request-id;
  - дороже эксплуатация — CI/CD, оркестрация, service discovery, observability на каждый сервис;
  - цена ошибки в границах — неверно нарезанные сервисы дают распределённый монолит, который хуже обычного.
- Когда оправдано — когда нагрузка и число команд окупают эту цену; иначе начинают с модульного монолита и выносят сервисы по мере надобности.
- См. [service-topologies/01-monolith-vs-modular-monolith-vs-microservices.md](../04-architecture-and-patterns/service-topologies/01-monolith-vs-modular-monolith-vs-microservices.md).

**Что знаете про распределённые транзакции?**

- Постановка проблемы — когда транзакция охватывает несколько сервисов или БД, классический ACID не работает.
- 2PC (two-phase commit) — надёжно, но блокирующе и медленно, плохо масштабируется.
- Saga — цепочка локальных транзакций с компенсирующими действиями при ошибке; бывает оркестрация и хореография.
- Что берут на практике — Saga плюс Outbox для надёжной публикации событий, с eventual consistency.
- См. [patterns/09-saga-and-outbox.md](../04-architecture-and-patterns/patterns/09-saga-and-outbox.md).

**Как решается проблема дубликатов входящих запросов?**

- Механизм — клиент шлёт заголовок `Idempotency-Key`, уникальный для логической операции.
- Что делает сервер — атомарно фиксирует ключ, выполняет операцию и сохраняет результат рядом с ключом.
- При повторе с тем же ключом — возвращает сохранённый ответ, не выполняя эффект второй раз.
- Подстраховка на уровне БД — уникальный индекс по ключу: даже при гонке двух параллельных повторов пройдёт только один.
- Что учесть — у ключей нужен срок жизни, иначе таблица растёт бесконечно.
- См. [05-integration-patterns/02-idempotency.md](../08-networking-and-api/protocols/05-integration-patterns/02-idempotency.md).

### Планировщик, горутины, netpoller

**Расскажите про планировщик.**

- Модель G-M-P — G это горутины, M это OS-потоки, P это логические процессоры. `GOMAXPROCS` по умолчанию равен числу логических CPU, а с Go 1.25 в контейнере дополнительно ограничен CPU-квотой cgroup (см. [go1.25.md](../15-go-version-differences/go1.25.md)).
- Очереди — у каждого P своя локальная (LRQ), плюс есть общая глобальная (GRQ).
- Work-stealing — при опустошении локальной очереди P крадёт работу у других.
- Тип планировщика — кооперативно-вытесняющий: переключение в точках безопасности плюс асинхронная вытесняющая преемпция по сигналу (с Go 1.14, ~10 мс).
- См. [runtime-scheduler/01-scheduler-and-preemption.md](../01-go-core/runtime-scheduler/01-scheduler-and-preemption.md).

**В какой момент происходит переключение горутин?**

- На вызовах функций (проверка стека/преемпции), операциях с каналами, блокирующих вызовах, syscall, аллокации/GC, `runtime.Gosched()`, и принудительно по async-преемпции (сигнал) для долгих CPU-циклов без вызовов.

**Что такое netpoller?**

- Что это — встроенный в рантайм асинхронный поллер сетевого ввода-вывода поверх epoll, kqueue или IOCP.
- Что происходит при операции на неготовом сокете — горутина паркуется, дескриптор регистрируется в поллере, а поток ОС освобождается под другие горутины.
- Пробуждение — когда сокет готов, поллер возвращает горутину в очередь планировщика.
- Зачем это нужно — благодаря нему тысячи соединений обслуживаются несколькими потоками, и блокирующий по виду код остаётся неблокирующим по сути.
- Важное исключение — обычные файлы так не поллятся, их чтение блокирует поток.
- См. [runtime-scheduler/03-netpoller.md](../01-go-core/runtime-scheduler/03-netpoller.md).

**Что происходит с горутиной при блокировке на чтении файла? Отличие от сетевого запроса?**

- Файл не поллится — чтение обычного файла не обслуживается netpoller: на Linux epoll не работает с regular files, поэтому это обычный блокирующий syscall, блокирующий сам M.
- Что делает рантайм — отвязывает P от заблокированного M (handoff) и отдаёт P другому или новому M, чтобы остальные горутины продолжали работать.
- Судьба горутины — она «висит» вместе со своим M до возврата syscall.
- Сетевой запрос — паркует горутину без блокировки M, через netpoller.
- Итог — file read блокирует поток, network read нет.
- См. [runtime-scheduler/02-syscall.md](../01-go-core/runtime-scheduler/02-syscall.md) и [03-netpoller.md](../01-go-core/runtime-scheduler/03-netpoller.md).

### Context

**Что такое context? Какие контексты бывают?**

- Что это — сквозной механизм отмены, дедлайнов и request-scoped значений по дереву вызовов.
- Корневые контексты — `context.Background()` в проде и `context.TODO()` как заглушка на время рефакторинга.
- Производные — `WithCancel`, `WithTimeout`, `WithDeadline`, `WithValue`, а с Go 1.20 ещё и `WithCancelCause`, позволяющий узнать причину отмены.
- Методы интерфейса — `Done()`, `Err()`, `Deadline()`, `Value()`.
- Обязательная гигиена — вызывать `cancel()` через `defer` даже при успешном завершении, иначе течёт таймер и связанные ресурсы.
- См. [concurrency-and-performance/04-context-patterns.md](../01-go-core/concurrency-and-performance/04-context-patterns.md).

**Для чего используется context.WithValue?**

- Прокинуть request-scoped данные сквозь стек вызовов: request-id, trace-id, авторизация, локаль. Не для опциональных параметров функции и не для бизнес-данных. Ключ — неэкспортируемый собственный тип (чтобы не было коллизий), значения иммутабельны.

### Гонки и синхронизация

**Как обнаружить гонку?**

- Инструмент — race-детектор: `go test -race`, `go run -race`, `go build -race`. Инструментирует каждый доступ к памяти, строит happens-before через vector clocks и репортит конфликтующие чтение/запись со стеками обеих горутин.
- Главное ограничение — детектор динамический: находит только те гонки, которые реально произошли на конкретном прогоне. False positives нет, false negatives есть, поэтому «прогнали с `-race`, значит гонок нет» — неверный вывод.
- Цена — примерно 5–20× по CPU и 5–10× по памяти, в прод такой бинарь не катят.
- Как пользоваться — гонять в CI на представительной нагрузке и на тестах с реальной конкурентностью (`t.Parallel`, несколько горутин), а не на однопоточных.
- Что не поймает — только data race. Логическая гонка (проверка и действие под разными `Lock`) детектору не видна, за неё отвечает дизайн критических секций.

**Что будет, если в map читать по ключу «a», а писать по ключу «b» (конкурентно)?**

- Это всё равно гонка — разные ключи не спасают.
- Почему — общая структура map (рост, эвакуация бакетов) меняется целиком, и запись по одному ключу может переехать данные другого.
- Как проявляется — рантайм валит процесс фатальной ошибкой `concurrent map read and map write`, либо гонку ловит `-race`.
- Важная деталь — это не паника, а фатальная ошибка: `recover` её не перехватит.
- Что делать — синхронизировать доступ через `RWMutex`, шардировать по ключу или взять `sync.Map` в подходящем сценарии.
- См. [map-internals/03-puzzles-and-gotchas.md](../01-go-core/map-internals/03-puzzles-and-gotchas.md).

**Чем отличаются Mutex и RWMutex?**

- `Mutex` — эксклюзивный доступ: один владелец и на чтение, и на запись.
- `RWMutex` — различает `RLock` (много читателей одновременно) и `Lock` (один писатель, блокирует всех).
- Когда RWMutex выгоден — при сильном перекосе в сторону чтения и нетривиальной критической секции.
- Когда он хуже — при частой записи или очень коротких секциях медленнее обычного `Mutex` из-за большего оверхеда, прежде всего contention на счётчике читателей между ядрами.
- Starvation писателя не грозит — `RWMutex` в Go writer-preferring: пока писатель ждёт `Lock`, новые `RLock` блокируются.
- См. [concurrency-and-performance/03-sync-primitives.md](../01-go-core/concurrency-and-performance/03-sync-primitives.md).

**Почему предпочесть map+RWMutex, а не sync.Map?**

- Ниша `sync.Map` — узкие сценарии: ключи пишутся один раз и много читаются, либо у горутин непересекающиеся наборы ключей.
- Для общего случая с частыми апдейтами — `map` + `RWMutex` быстрее, типобезопасна (без боксинга в `any`), даёт `len` и просто понятнее.
- Минусы `sync.Map` — нет дженериков, аллокации на интерфейсах.
- Оговорка про версии — в Go 1.24 `sync.Map` переписали на HashTrieMap, она стала заметно быстрее; вывод «для общего случая берут map + RWMutex» это не отменяет, но старые бенчмарки уже не показательны.
- См. [map-internals/sync-map](../01-go-core/map-internals/sync-map/README.md).

### Архитектура

**Для чего интерфейсы? Что про dependency injection?**

- Роль интерфейсов — задают контракт и развязывают модули: код зависит от абстракции, а не от конкретной реализации.
- Идиома Go — интерфейс объявляет потребитель, а не поставщик, и делает его узким.
- Что такое DI — передача зависимостей снаружи, через конструктор или параметры, вместо создания их внутри.
- Как делают в Go — чаще всего вручную конструкторами; для больших графов есть `wire` (кодогенерация) и `fx` (рантайм-контейнер).
- Что это даёт — тестируемость через подмену моками и слабую связанность модулей.
- См. [patterns/06-solid-in-go.md](../04-architecture-and-patterns/patterns/06-solid-in-go.md).

**Чистая/гексагональная и многослойная архитектура?**

- Многослойная — handler, затем service, затем repository; зависимости идут сверху вниз.
- Гексагональная (ports and adapters) и чистая — домен в центре, зависимости направлены внутрь через интерфейсы-порты, а инфраструктура (БД, HTTP, брокер) подключается внешними адаптерами.
- Общая цель — изолировать бизнес-логику от деталей инфраструктуры, чтобы смена БД или транспорта не переписывала домен.
- Практический признак, что всё сделано верно — доменный пакет не импортирует ни драйвер БД, ни веб-фреймворк.
- См. [patterns/02-architecture-patterns.md](../04-architecture-and-patterns/patterns/02-architecture-patterns.md).

**Что такое интерфейс any? Как с ним работать?**

- `any` = `interface{}` (псевдоним с 1.18) — «любой тип». Достать конкретный тип: type assertion `v, ok := x.(T)` или `type switch`. С дженериками `any` — частый констрейнт. Минусы: теряется типобезопасность, боксинг/аллокации.

**Составные индексы?**

- Индекс по нескольким столбцам `(a, b, c)`. Работает по leftmost-prefix: применим к условиям на `a`, `(a,b)`, `(a,b,c)`, но не на `b`/`c` без `a`. Порядок столбцов критичен.
- Оговорка про версии — PostgreSQL 18 умеет skip scan и может задействовать индекс без условия на `a`, если у `a` мало различных значений. Правило «ведущим ставят столбец, по которому фильтруют чаще» это не отменяет.
- Разбор — в [задаче 2 ниже](#задача-2--sql-запросы-и-составной-индекс).

## Лайвкодинг и задачи

### Задача-разминка: SQL `SET enable_seqscan TO off;`

```sql
SET enable_seqscan TO off;
```

- Что делает — PostgreSQL-параметр сессии, который отключает sequential scan в планировщике; точнее, делает его стоимость заведомо огромной, чтобы планировщик предпочитал индексные сканы там, где это возможно.
- Зачем применяют — для отладки: проверить, есть ли подходящий индекс, какой план выйдет с ним, и сравнить cost.
- Чем это не является — не оптимизация прода: на маленьких таблицах seqscan часто быстрее.
- Область действия — только текущая сессия, до `RESET` или реконнекта.
- См. [postgresql/03-query-planning.md](../06-databases/database-systems-catalog/postgresql/03-query-planning.md).

### Задача 1 — что выведет Go-программа?

<details>
<summary>Код задачи</summary>

```go
package main

import (
    "fmt"
    "sync"
)

type listSKU []string

func (l listSKU) getLastSKU() string {
    return l[len(l)] // ← индекс len(l) выходит за границу
}

func main() {
    items := listSKU{
        "MP990099991",
        "MP900000002",
        "MP000000003",
        "MP000000004",
        "MP000000005",
    }

    wg := sync.WaitGroup{}
    wg.Add(1)

    go func() {
        lastItem := items.getLastSKU()
        fmt.Printf("Last SKU: %s\n", lastItem)
        wg.Done()
    }()

    wg.Wait()
    fmt.Println("Program completed.")
}
```

</details>

- Программа упадёт с паникой `runtime error: index out of range [5] with length 5`.
- Почему — у слайса из 5 элементов валидные индексы `0..4`, а `l[len(l)]` обращается к `l[5]`.
- Что с `wg.Done()` — паника происходит внутри горутины до него, поэтому `Done` не вызовется; но это и неважно: неперехваченная паника в любой горутине аварийно завершает всю программу (stack trace, exit code 2).
- Что не напечатается — ни `Last SKU:`, ни `Program completed.`.
- Фикс: `return l[len(l)-1]`. Дополнительно стоит защититься от пустого слайса (`if len(l) == 0 { return "" }`), а в горутине — `defer wg.Done()`, чтобы Done вызывался даже при panic/recover.

### Задача 2 — SQL-запросы и составной индекс

Схема:

```sql
CREATE TABLE customer (
    id INTEGER PRIMARY KEY,
    email VARCHAR(100) NOT NULL,
    country CHAR(2) NOT NULL
);

CREATE TABLE cart_item (
    id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    title VARCHAR(20) NOT NULL,
    amount INTEGER NOT NULL,
    price INTEGER NOT NULL
);
```

**Задача — все клиенты и элементы их корзины** (LEFT JOIN, чтобы показать и клиентов с пустой корзиной):

```sql
SELECT c.id, c.email, ci.title, ci.amount
FROM customer c
LEFT JOIN cart_item ci ON ci.customer_id = c.id;
```

**Задача — топ-10 клиентов из России по сумме корзины ≥ 1000:**

```sql
SELECT c.id, c.email, SUM(ci.price * ci.amount) AS total
FROM customer c
JOIN cart_item ci ON ci.customer_id = c.id
WHERE c.country = 'RU'
GROUP BY c.id, c.email
HAVING SUM(ci.price * ci.amount) >= 1000
ORDER BY total DESC
LIMIT 10;
```

- Фильтр по стране (`WHERE`) — до группировки; фильтр по агрегату суммы (`HAVING`) — после; стоимость = `price * amount`.

**Задача — будет ли применяться индекс?** `CREATE INDEX myIdx ON carts (sku, country, customer_id);` (отдельная таблица `carts`, со схемой выше не связана):

```sql
-- Запрос А:
SELECT * FROM carts WHERE sku = 192 AND country = 'ru';
```
- Да, индекс применится. Условия покрывают левый префикс индекса `(sku, country)` — равенство по двум первым столбцам, ровно под B-tree.

```sql
-- Запрос Б:
SELECT * FROM carts WHERE country = 'ru' AND customer_id = 10;
```
- Ожидаемый на собесе ответ — нет: нарушен leftmost-prefix, отсутствует ведущий столбец `sku`, а по `country` и `customer_id` без него B-tree навигировать не может.
- Что сделает планировщик — уйдёт в seqscan; возможен и full index scan, если индекс заметно уже таблицы, но это не то ускорение, ради которого строят индекс.
- Оговорка про версии — с PostgreSQL 18 у B-tree появился skip scan: планировщик перебирает различные значения пропущенного `sku` и внутри каждого ищет по `country`. Выигрывает только при низкой кардинальности `sku`, иначе вырождается в тот же полный проход.
- Как починить надёжно — индекс с `country` впереди, например `(country, customer_id)`.
- Разбор leftmost-prefix — раздел «Составные индексы» выше и [postgresql/02-indexes.md](../06-databases/database-systems-catalog/postgresql/02-indexes.md).

### Лайвкодинг-вопросы по слайсам

**Как устроен слайс? Как работает append?**

- Что такое слайс — заголовок `{ptr, len, cap}` над backing-массивом.
- Если `len < cap` — `append` пишет прямо в существующий массив, и запись видна всем слайсам поверх него.
- Если места нет — аллоцируется новый массив, данные копируются, возвращается новый заголовок; рост примерно вдвое на малых слайсах и плавнее на больших.
- Отсюда правило — результат `append` всегда присваивают обратно: `s = append(s, …)`.
- См. [04-slices.md](../01-go-core/04-slices.md).

**Сложность доступа к элементу слайса?** — O(1) (адрес = база + индекс × размер элемента).

**Сложность добавления в конец?** — амортизированная O(1) (редкие реаллокации с копированием дают худший O(n), но усреднённо константа).

**Как исправить, чтобы foo() не влияла на arr?**

- Симптом классический: `foo` получает слайс, делит общий backing-массив и портит `arr` (через запись по индексу или `append` в пределах `cap`). Способы:
  - передавать копию: `cp := slices.Clone(arr)` (или `append([]T(nil), arr...)`) и работать с ней;
  - ограничить ёмкость full-slice-выражением `arr[i:j:j]` — тогда первый же `append` в `foo` реаллоцирует и оригинал не тронет; от записи по индексу в пределах `len` это не защищает, там спасает только копия;
  - не мутировать вход, а возвращать новый слайс.

**Можно ли предвыделить память через make()?** (с подвохом)

- Да — `make([]T, 0, n)` даёт длину 0 и ёмкость n, поэтому последующие `append` не вызывают реаллокаций.
- Где подвох — в путанице длины и ёмкости: `make([]T, n)` создаёт слайс из n нулевых элементов, и первый же `append` добавит n+1-й.
- Как это выглядит в баге — на выходе получают слайс, где первая половина пустые нули, а данные идут следом.
- Правило — для предвыделения под будущий `append` всегда `make([]T, 0, n)`.

### Лайвкодинг-вопросы по конкурентности

**Почему `wg.Add(1)` нельзя делать внутри запускаемой горутины?**

- Гонка на старте — `wg.Wait()` может выполниться раньше, чем запущенная горутина успеет сделать `Add(1)`.
- Что тогда произойдёт — `Wait` увидит счётчик 0, сразу вернётся, и программа завершится, не дождавшись работы.
- Худший вариант — если `Add` попадёт уже внутрь работающего `Wait`, рантайм выдаст панику `sync: WaitGroup misuse: Add called concurrently with Wait`.
- Как правильно — вызывать `Add` в той же горутине, что запускает воркеров, до `go`, а внутри горутины оставлять только `defer wg.Done()`.
- Правило — `Add` всегда вызывают до `go func()`, в родительской горутине.
- С Go 1.25 проще — `wg.Go(func(){ … })` сам делает `Add(1)` и `defer Done()`, ошибиться негде. См. [concurrency-and-performance/02-goroutines-and-channels.md](../01-go-core/concurrency-and-performance/02-goroutines-and-channels.md).

**В какой последовательности отработают запущенные горутины?**

- Порядок не определён — зависит от планировщика; гарантий очерёдности запуска/завершения нет. Если нужен порядок — синхронизировать явно (каналы, цепочка сигналов).

**Проблемы при 100k URL (по горутине на URL) и как обойти?**

- Проблемы: 100k одновременных горутин и соединений → всплеск памяти, исчерпание файловых дескрипторов/портов, перегрузка цели (DoS по себе и по ним), отсутствие лимита и backpressure, неконтролируемые ошибки.
- Решения: ограничить конкурентность — worker pool или семафор (`golang.org/x/sync/semaphore`, буферизованный канал-семафор), `errgroup` с `SetLimit(N)`; переиспользовать `http.Client` с настроенным `Transport` (`MaxConnsPerHost`), таймауты и `context`, ретраи с backoff, батчинг.

**Исправить программу: завершиться, как только любая горутина вернёт ошибку.**

- Канонично — `errgroup.WithContext`: первая вернувшаяся ошибка отменяет общий `context`, остальные горутины видят `ctx.Done()` и сворачиваются, а `g.Wait()` возвращает эту ошибку.

```go
g, ctx := errgroup.WithContext(ctx)
for _, u := range urls {
    g.Go(func() error {
        return fetch(ctx, u) // вернёт err → ctx отменится для всех
    })
}
if err := g.Wait(); err != nil { /* первая ошибка */ }
```

- Про `u := u` — до Go 1.22 внутри цикла была обязательна эта строка (все замыкания делили одну переменную); с 1.22 переменная цикла своя на каждой итерации, и копия больше не нужна.
- Вручную то же делается через `context.WithCancel` + `cancel()` при первой ошибке и `sync.Once` или канал для её фиксации. См. [concurrency-and-performance/04-context-patterns.md](../01-go-core/concurrency-and-performance/04-context-patterns.md).
