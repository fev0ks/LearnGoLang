## Скрининг

### Сети, инфраструктура, git

**Какие протоколы поверх HTTP знаешь?**

- Поверх HTTP строят: REST, gRPC (поверх HTTP/2), GraphQL, SOAP, WebSocket (апгрейд с HTTP), SSE, OData. Сам HTTP идёт поверх TCP/TLS. См. [protocols/11-protocol-comparison.md](../08-networking-and-api/protocols/11-protocol-comparison.md).

**Какие виды хранилищ знаешь?**

- Реляционные (PostgreSQL, MySQL) — строгая схема, ACID, JOIN. Документные (MongoDB) — гибкая JSON-схема. Key-value (Redis, DynamoDB) — быстрый доступ по ключу. Колоночные/wide-column (ClickHouse, Cassandra) — аналитика и большой объём записи. Графовые (Neo4j) — связи и обходы. Поисковые (Elasticsearch) — полнотекст. Блоб/объектные (S3) — файлы. Выбор — по модели данных, паттерну доступа и требованиям к консистентности. См. [database-systems-catalog/01-comparison-table.md](../06-databases/database-systems-catalog/01-comparison-table.md).

**Для чего нужны линтеры?**

- Статический анализ кода без запуска: ловят баги (непроверенные ошибки, гонки, nil), навязывают единый стиль, находят запахи и уязвимости, экономят ревью. Стандарт де-факто — `golangci-lint` (агрегатор: govet, staticcheck, errcheck, gosec и десятки других одним проходом), встраивается в CI и pre-commit.

**Зачем нужны моки?**

- Подменяют зависимости (БД, внешние API) в тестах: изолируют тестируемый код, делают тесты быстрыми и детерминированными, позволяют проверить взаимодействие и смоделировать ошибки/таймауты. См. [09-testing-and-quality/03-test-doubles-and-test-design.md](../09-testing-and-quality/03-test-doubles-and-test-design.md).

**Чем образ отличается от контейнера?**

- Образ (image) — неизменяемый шаблон из слоёв (read-only): код + зависимости + метаданные. Контейнер — запущенный экземпляр образа с добавленным writable-слоем и своим процессом/namespace. Аналогия: образ — класс, контейнер — объект. См. [docker/01-container-vs-virtual-machine.md](../10-devops-and-observability/docker/01-container-vs-virtual-machine.md).

**Какие есть способы прокинуть исходный код в контейнер?**

- `COPY`/`ADD` в Dockerfile (зашить в образ на сборке); bind-mount тома (`-v $PWD:/app`) для разработки с hot-reload; volume; build-context. Для прода — `COPY` + multi-stage build; для локалки — bind-mount. См. [dockerfiles-for-go/02-dockerfile-anatomy.md](../10-devops-and-observability/dockerfiles-for-go/02-dockerfile-anatomy.md).

**Чем отличается merge от rebase?**

- `merge` объединяет ветки merge-коммитом, сохраняя историю как есть (нелинейная, но правдивая). `rebase` переносит коммиты ветки поверх целевой, переписывая их (линейная чистая история, но новые хеши). Правило: не ребейзить опубликованные/общие ветки. Merge — для интеграции в общие ветки, rebase — для причёсывания своей локальной ветки перед PR.

### Очереди и Kafka

**Для чего нужны очереди?**

- Развязка producer/consumer, сглаживание пиков (буфер/backpressure), асинхронная обработка, ретраи и надёжность, фан-аут событий, масштабирование консьюмеров. См. [07-message-brokers-and-streaming/README.md](../07-message-brokers-and-streaming/README.md).

**Гарантирована ли доставка сообщений в Kafka?**

- Да, настраиваемо: durability за счёт репликации партиций и `acks=all` + `min.insync.replicas`. Базовая семантика — at-least-once; exactly-once достижим через идемпотентного продюсера и транзакции. Без правильных настроек (`acks=0/1`) сообщения можно потерять. Детали — в секции [техничка про Kafka](#техничка--теория).

### Go — основы

**Чем отличается массив от слайса?**

- Массив `[N]T` — фиксированная длина в типе, копируется целиком по значению. Слайс — заголовок `{указатель, len, cap}` поверх общего backing-массива, копируется как заголовок. См. [04-slices.md](../01-go-core/04-slices.md).

**Как объединить два слайса?**

- `c := append(a, b...)` (variadic-распаковка). Безопаснее — в новый слайс: `c := make([]T, 0, len(a)+len(b)); c = append(c, a...); c = append(c, b...)`, чтобы не затронуть backing-массив `a`. С Go 1.21 есть `slices.Concat(a, b)`.

**Как получить первые N элементов слайса?**

- Слайсинг: `s[:n]` (первые n, разделяет backing-массив с исходным). Если нужна независимая копия — `append([]T(nil), s[:n]...)` или `slices.Clone(s[:n])`.

**Что такое map?**

- Встроенная хеш-таблица «ключ → значение», доступ амортизированно O(1). С Go 1.24 — на Swiss Tables. См. [map-internals](../01-go-core/map-internals/README.md).

**Какой порядок обхода map?**

- Не определён и намеренно рандомизирован: рантайм стартует итерацию со случайного бакета, чтобы код не закладывался на порядок. Нужен порядок — собрать ключи в слайс и отсортировать.

**Какие ключи можно использовать для map?**

- Любые **сравнимые** (`==`) типы: bool, числа, string, указатели, каналы, интерфейсы, а также структуры/массивы из сравнимых типов. Нельзя: slice, map, функции (несравнимы → паника/ошибка компиляции). Осторожно с интерфейсами, прячущими несравнимый тип (паника в рантайме).

### Go — конкурентность

**Что такое горутина? Кто ей управляет?**

- Лёгкий поток исполнения (стартовый стек ~2 КБ, растёт по мере надобности), мультиплексируемый рантаймом Go на OS-потоки. Управляет планировщик Go по модели **G-M-P** (G — горутина, M — OS-поток, P — процессор-контекст). См. [runtime-scheduler/01-scheduler-and-preemption.md](../01-go-core/runtime-scheduler/01-scheduler-and-preemption.md).

**Что такое каналы? Зачем нужны? Какие бывают?**

- Типизированная труба для обмена данными и синхронизации между горутинами («share memory by communicating»). Бывают небуферизированные (rendezvous) и буферизированные; по направлению — `chan T`, `<-chan T`, `chan<- T`. См. [concurrency-and-performance/02-goroutines-and-channels.md](../01-go-core/concurrency-and-performance/02-goroutines-and-channels.md).

**Аксиомы каналов?**

- Отправка/чтение из **nil**-канала блокируются навсегда. Чтение из **закрытого** канала не блокирует: отдаёт остаток буфера, потом нулевое значение (`v, ok` → `ok=false`). Отправка в закрытый канал и повторный `close` — **паника**. Закрывает всегда отправитель. Закрытие — broadcast всем читателям.

**Select каналов?**

- `select` ждёт готовности одного из нескольких каналов; если готовы несколько — выбирает случайный; `default` делает неблокирующим; `case <-ctx.Done()` — типовой выход по отмене. Пустой `select{}` блокируется навсегда.

**Race condition?**

- Состояние гонки — одновременный доступ к общим данным минимум с одной записью без синхронизации; результат зависит от тайминга. Детектируется `go test -race`/`go run -race`. См. [concurrency-and-performance/01-memory-model.md](../01-go-core/concurrency-and-performance/01-memory-model.md).

**Примитивы синхронизации?**

- `sync.Mutex`/`RWMutex`, `sync.WaitGroup`, `sync.Once`, `sync.Cond`, `sync.Map`, пакет `sync/atomic`, каналы, `context` для отмены, `golang.org/x/sync` (`errgroup`, `semaphore`, `singleflight`). См. [concurrency-and-performance/03-sync-primitives.md](../01-go-core/concurrency-and-performance/03-sync-primitives.md).

### Go — язык и инструменты

**Есть ли наследование в Go?**

- Нет. Вместо наследования — **композиция** (встраивание структур, embedding) и интерфейсы (неявная реализация). Переиспользование через «has-a», полиморфизм через интерфейсы.

**Использовал type switch?**

- Да: `switch v := x.(type) { case int: …; case string: … }` — ветвление по динамическому типу значения в интерфейсе; типобезопасная альтернатива цепочке type assertion. Применяют для разбора `any`, ошибок, AST.

**Для чего нужен пакет errors?**

- Работа с ошибками-значениями: оборачивание (`fmt.Errorf("...: %w", err)`), `errors.Is` (сравнение с sentinel), `errors.As` (извлечение типа), `errors.Unwrap`, `errors.Join` (1.20). Даёт цепочку контекста без потери исходной ошибки. См. [05-error-handling.md](../01-go-core/05-error-handling.md).

**Использовал pprof? Инструменты для отладки?**

- pprof — профили CPU/heap/goroutine/mutex/block (`net/http/pprof` в проде, `go tool pprof`). Ещё: `go test -race`, `delve` (дебаггер), `go test -bench -benchmem`, `runtime/trace`, `GODEBUG` (gctrace, schedtrace), `go vet`. См. [profiling/01-pprof-tools-and-workflow.md](../01-go-core/profiling/01-pprof-tools-and-workflow.md).

### Базы данных

**Индексы в БД? Плюсы и минусы?**

- Структуры (обычно B-tree) для быстрого поиска/сортировки/джойнов вместо полного скана. Виды: B-tree (диапазоны, сортировка, дефолт), Hash (равенство), GIN (jsonb, полнотекст), GiST/BRIN (геоданные, диапазоны). «+» ускоряют чтение; «−» замедляют запись (надо обновлять индекс), занимают место, лишние индексы вредят. См. [relational-databases-and-sql/03-indexes-and-query-plans.md](../06-databases/relational-databases-and-sql/03-indexes-and-query-plans.md).

**Зачем транзакции? Уровни изоляции?**

- Атомарная единица работы с ACID. Уровни: Read Uncommitted, Read Committed (дефолт PG), Repeatable Read, Serializable — отсекают dirty/non-repeatable/phantom read. См. [relational-databases-and-sql/02-transactions-isolation-and-locks.md](../06-databases/relational-databases-and-sql/02-transactions-isolation-and-locks.md).

**Расскажи про JOIN.**

- Соединение строк таблиц по условию. `INNER` — только совпавшие; `LEFT/RIGHT` — все из левой/правой + совпадения (или NULL); `FULL` — все из обеих; `CROSS` — декартово произведение. Алгоритмы планировщика: nested loop, hash join, merge join. См. [relational-databases-and-sql/01-relational-model-and-sql-basics.md](../06-databases/relational-databases-and-sql/01-relational-model-and-sql-basics.md).

**Deadlock в базе данных?**

- Две транзакции взаимно ждут блокировки друг друга (T1 держит A, ждёт B; T2 держит B, ждёт A). СУБД детектирует цикл и откатывает одну из транзакций (жертву). Профилактика: единый порядок захвата строк, короткие транзакции, меньше escalation блокировок. См. [relational-databases-and-sql/02-transactions-isolation-and-locks.md](../06-databases/relational-databases-and-sql/02-transactions-isolation-and-locks.md).

**Денормализация — плюсы и минусы?**

- Денормализация — намеренное дублирование/предрасчёт данных ради ускорения чтения. «+» меньше JOIN и агрегаций на горячем пути, быстрее чтение; «−» избыточность и рост объёма, риск рассинхрона копий, усложнение записи (обновлять в нескольких местах). Применяют точечно под конкретный read-паттерн.

## Техничка — теория

### Kafka и доставка сообщений

**За счёт чего обеспечивается отказоустойчивость Kafka?**

- Репликация партиций: у каждой партиции есть leader и follower-реплики (`replication.factor`), запись подтверждается после попадания в ISR (in-sync replicas). При падении брокера-лидера один из ISR становится новым лидером. `min.insync.replicas` + `acks=all` гарантируют, что подтверждённое сообщение лежит на нескольких узлах. Данные durable на диске (лог + retention). См. [07-message-brokers-and-streaming/01-kafka.md](../07-message-brokers-and-streaming/01-kafka.md).

**Какие гарантии доставки предоставляет Kafka?**

- Три семантики: **at-most-once**, **at-least-once** (дефолт на практике) и **exactly-once** (идемпотентный продюсер + транзакции). Выбор регулируется `acks`, ретраями продюсера и моментом коммита offset у консьюмера.

**Что такое at-most-once?**

- «Не более одного раза»: сообщение может быть потеряно, но никогда не дублируется. Достигается, когда offset коммитят **до** обработки (или `acks=0`): упали после коммита — сообщение потеряно. Подходит, где потеря терпима, а дубль — нет (метрики, логи).

**Что такое at-least-once?**

- «Не менее одного раза»: сообщение не теряется, но возможны дубли. Offset коммитят **после** успешной обработки: упали до коммита — сообщение прочитают повторно. Самый частый выбор; требует идемпотентной обработки.

**at-least-once, но бизнес-логика чувствительна к дубликатам — что делать?**

- Сделать обработку **идемпотентной**: дедупликация по ключу сообщения/`idempotency-key` (таблица обработанных id, `INSERT ... ON CONFLICT DO NOTHING`), upsert вместо insert, проверка состояния перед эффектом, exactly-once через транзакции Kafka. Идея — повтор не меняет результат. См. [reliability-patterns/06-idempotency.md](../05-system-design/reliability-patterns/06-idempotency.md).

### Микросервисы и распределённость

**Плюсы и минусы микросервисной архитектуры?**

- «+» независимый деплой и масштабирование, изоляция отказов, разные стеки, автономные команды. «−» распределённая сложность (сеть, латентность, частичные отказы), нет ACID между сервисами, сложнее отладка/трейсинг, эксплуатация (DevOps, observability), консистентность данных. См. [service-topologies/01-monolith-vs-modular-monolith-vs-microservices.md](../04-architecture-and-patterns/service-topologies/01-monolith-vs-modular-monolith-vs-microservices.md).

**Что знаете про распределённые транзакции?**

- Когда транзакция охватывает несколько сервисов/БД, классический ACID не работает. Подходы: **2PC** (two-phase commit — надёжно, но блокирующе и медленно, плохо масштабируется) и **Saga** (цепочка локальных транзакций с компенсирующими действиями при ошибке; оркестрация или хореография). На практике в микросервисах — Saga + Outbox для надёжной публикации событий, eventual consistency. См. [patterns/09-saga-and-outbox.md](../04-architecture-and-patterns/patterns/09-saga-and-outbox.md).

**Как решается проблема дубликатов входящих запросов?**

- Идемпотентность: клиент шлёт `Idempotency-Key`, сервер хранит ключ+результат и при повторе возвращает сохранённый ответ, не выполняя эффект дважды. Плюс дедупликация на уровне БД (уникальные ключи). См. [protocols/07-idempotency.md](../08-networking-and-api/protocols/07-idempotency.md).

### Планировщик, горутины, netpoller

**Расскажите про планировщик.**

- Модель **G-M-P**: G — горутины, M — OS-потоки, P — логические процессоры (по умолчанию `GOMAXPROCS` = числу ядер). Каждый P имеет локальную очередь горутин (LRQ) + есть глобальная (GRQ); при опустошении локальной очереди P **крадёт** работу у других (work-stealing). Планировщик кооперативно-вытесняющий: переключение в точках безопасности + асинхронная вытесняющая преемпция по сигналу (с 1.14, ~10 мс). См. [runtime-scheduler/01-scheduler-and-preemption.md](../01-go-core/runtime-scheduler/01-scheduler-and-preemption.md).

**В какой момент происходит переключение горутин?**

- На вызовах функций (проверка стека/преемпции), операциях с каналами, блокирующих вызовах, syscall, аллокации/GC, `runtime.Gosched()`, и принудительно по async-преемпции (сигнал) для долгих CPU-циклов без вызовов.

**Что такое netpoller?**

- Интегрированный с рантаймом асинхронный поллер сетевого I/O (epoll/kqueue/IOCP). Когда горутина делает сетевую операцию на неготовом сокете, она **паркуется**, fd регистрируется в netpoller, а OS-поток (M) **освобождается** для других горутин. Когда сокет готов, netpoller будит горутину. См. [runtime-scheduler/03-netpoller.md](../01-go-core/runtime-scheduler/03-netpoller.md).

**Что происходит с горутиной при блокировке на чтении файла? Отличие от сетевого запроса?**

- Чтение **обычного файла** не обслуживается netpoller (на Linux epoll не работает с regular files): это блокирующий syscall — он блокирует сам M. Рантайм отвязывает P от заблокированного M (handoff) и отдаёт P другому/новому M, чтобы остальные горутины продолжали работать; заблокированная горутина «висит» вместе со своим M до возврата syscall. **Сетевой** же запрос паркует горутину без блокировки M (через netpoller). Итог: file read блокирует поток, network read — нет. См. [runtime-scheduler/02-syscall.md](../01-go-core/runtime-scheduler/02-syscall.md) и [03-netpoller.md](../01-go-core/runtime-scheduler/03-netpoller.md).

### Context

**Что такое context? Какие контексты бывают?**

- Сквозной механизм отмены/дедлайна и request-scoped значений. Базовые: `context.Background()`, `context.TODO()`. Производные: `WithCancel`, `WithTimeout`, `WithDeadline`, `WithValue` (и `WithCancelCause` в 1.20+). Методы: `Done()`, `Err()`, `Deadline()`, `Value()`. См. [concurrency-and-performance/04-context-patterns.md](../01-go-core/concurrency-and-performance/04-context-patterns.md).

**Для чего используется context.WithValue?**

- Прокинуть request-scoped данные сквозь стек вызовов: request-id, trace-id, авторизация, локаль. Не для опциональных параметров функции и не для бизнес-данных. Ключ — неэкспортируемый собственный тип (чтобы не было коллизий), значения иммутабельны.

### Гонки и синхронизация

**Как обнаружить гонку?**

- Race-детектор: `go test -race`, `go run -race`, `go build -race`. Инструментирует доступы к памяти и в рантайме репортит конфликтующие чтение/запись со стеками. В CI гонять с `-race`.

**Что будет, если в map читать по ключу «a», а писать по ключу «b» (конкурентно)?**

- Это **всё равно гонка**: map в Go не безопасна для конкурентного чтения+записи даже по разным ключам, потому что общая структура (рост, эвакуация бакетов) меняется целиком. Рантайм может выдать фатальное `concurrent map read and map write` или `-race` зарепортит. Нужна синхронизация (`RWMutex`/`sync.Map`). См. [map-internals/03-puzzles-and-gotchas.md](../01-go-core/map-internals/03-puzzles-and-gotchas.md).

**Чем отличаются Mutex и RWMutex?**

- `Mutex` — эксклюзивный доступ, один владелец и на чтение, и на запись. `RWMutex` различает `RLock` (много читателей одновременно) и `Lock` (один писатель, блокирует всех). RWMutex выгоден при сильном перекосе в сторону чтения и нетривиальной критической секции; при частой записи или очень коротких секциях медленнее обычного Mutex (больше оверхед, риск starvation писателя). См. [concurrency-and-performance/03-sync-primitives.md](../01-go-core/concurrency-and-performance/03-sync-primitives.md).

**Почему предпочесть map+RWMutex, а не sync.Map?**

- `sync.Map` оптимизирована под узкие сценарии (ключи пишутся один раз и много читаются, либо непересекающиеся наборы ключей у горутин). Для общего случая с частыми апдейтами `map`+`RWMutex` быстрее, типобезопасна (без боксинга в `any`), даёт `len`, проще. `sync.Map` — без дженериков, аллокации на интерфейсах. См. [map-internals/04-sync-map.md](../01-go-core/map-internals/04-sync-map.md).

### Архитектура

**Для чего интерфейсы? Что про dependency injection?**

- Интерфейсы задают контракт и развязывают модули (зависимость от абстракции). DI — передача зависимостей снаружи (через конструктор/параметры), а не создание внутри; в Go обычно вручную (конструкторы) или через wire/fx. Даёт тестируемость (подмена моками) и слабую связанность. См. [patterns/06-solid-in-go.md](../04-architecture-and-patterns/patterns/06-solid-in-go.md).

**Чистая/гексагональная и многослойная архитектура?**

- Многослойная: handler → service → repository, зависимости сверху вниз. Гексагональная (ports & adapters)/чистая: домен в центре, зависимости направлены **внутрь** через интерфейсы-порты, инфраструктура (БД, HTTP) — внешние адаптеры. Цель — изоляция бизнес-логики от деталей. См. [patterns/02-architecture-patterns.md](../04-architecture-and-patterns/patterns/02-architecture-patterns.md).

**Что такое интерфейс any? Как с ним работать?**

- `any` = `interface{}` (псевдоним с 1.18) — «любой тип». Достать конкретный тип: type assertion `v, ok := x.(T)` или `type switch`. С дженериками `any` — частый констрейнт. Минусы: теряется типобезопасность, боксинг/аллокации.

**Составные индексы?**

- Индекс по нескольким столбцам `(a, b, c)`. Работает по **leftmost-prefix**: применим к условиям на `a`, `(a,b)`, `(a,b,c)`, но не на `b`/`c` без `a`. Порядок столбцов критичен. Разбор — в [задаче 2 ниже](#задача-2--sql-запрос-и-составной-индекс).

## Лайвкодинг и задачи

### Задача-разминка: SQL `SET enable_seqscan TO off;`

```sql
SET enable_seqscan TO off;
```

- Это PostgreSQL-параметр сессии, который **отключает sequential scan** в планировщике — точнее, делает его стоимость заведомо огромной, чтобы планировщик предпочитал индексные сканы там, где это возможно. Применяют для **отладки**: проверить, есть ли подходящий индекс и какой план выйдет с ним, сравнить cost. Это не оптимизация прода (на маленьких таблицах seqscan часто быстрее) — настройка действует только в текущей сессии до `RESET`/реконнекта. См. [postgresql/03-query-planning.md](../06-databases/database-systems-catalog/postgresql/03-query-planning.md).

### Задача 1 — что выведет Go-программа?

```go
type listSKU []string

func (l listSKU) getLastSKU() string {
    return l[len(l)] // ← индекс len(l) выходит за границу
}
```

- **Программа упадёт с паникой** `runtime error: index out of range [5] with length 5`. У слайса из 5 элементов валидные индексы `0..4`, а `l[len(l)]` обращается к `l[5]`. Паника происходит **внутри горутины**, до `wg.Done()` — поэтому `wg.Done()` не вызовется, но это и неважно: неперехваченная паника в любой горутине **аварийно завершает всю программу** (stack trace, exit code 2). Ни `Last SKU:`, ни `Program completed.` не печатаются.
- **Фикс:** `return l[len(l)-1]`. Дополнительно стоит защититься от пустого слайса (`if len(l) == 0 { return "" }`), а в горутине — `defer wg.Done()`, чтобы Done вызывался даже при panic/recover.

### Задача 2 — SQL-запросы и составной индекс

Схема: `customer(id, email, country)` и `cart_item(id, customer_id, title, amount, price)`.

**Все клиенты и элементы их корзины** (LEFT JOIN — чтобы показать и клиентов с пустой корзиной):

```sql
SELECT c.id, c.email, ci.title, ci.amount
FROM customer c
LEFT JOIN cart_item ci ON ci.customer_id = c.id;
```

**Топ-10 клиентов из России по сумме корзины ≥ 1000:**

```sql
SELECT c.id, c.email, SUM(ci.price * ci.amount) AS total
FROM customer c
JOIN cart_item ci ON ci.customer_id = c.id
WHERE c.country = 'RU'
GROUP BY c.id, c.email
HAVING SUM(ci.price * ci.amount) >= 1000
ORDER BY total DESC
LIMIT 10;
```

- Фильтр по стране (`WHERE`) — до группировки; фильтр по агрегату суммы (`HAVING`) — после; стоимость = `price * amount`.

**Будет ли применяться индекс?** `CREATE INDEX myIdx ON carts (sku, country, customer_id);`

```sql
-- Запрос А:
SELECT * FROM carts WHERE sku = 192 AND country = 'ru';
```
- **Да, индекс применится.** Условия покрывают **левый префикс** индекса `(sku, country)` — равенство по двум первым столбцам, ровно под B-tree.

```sql
-- Запрос Б:
SELECT * FROM carts WHERE country = 'ru' AND customer_id = 10;
```
- **Нет (как обычный index scan не применится).** Нарушен leftmost-prefix: отсутствует ведущий столбец `sku`, а по `country`/`customer_id` без него B-tree навигировать не может. Планировщик уйдёт в seqscan (теоретически возможен дорогой full index scan, но это не то ускорение, ради которого строят индекс). Чтобы запрос Б был быстрым, нужен индекс с `country` впереди, например `(country, customer_id)`.
- Разбор leftmost-prefix — раздел «Составные индексы» выше и [relational-databases-and-sql/03-indexes-and-query-plans.md](../06-databases/relational-databases-and-sql/03-indexes-and-query-plans.md).

### Лайвкодинг-вопросы по слайсам

**Как устроен слайс? Как работает append?**

- Слайс — заголовок `{ptr, len, cap}` над backing-массивом. `append` пишет в массив, если `len < cap`; иначе аллоцирует новый массив (рост ~×2 на малых, плавнее на больших), копирует и возвращает новый заголовок — поэтому результат присваивают обратно (`s = append(s, …)`). См. [04-slices.md](../01-go-core/04-slices.md).

**Сложность доступа к элементу слайса?** — O(1) (адрес = база + индекс × размер элемента).

**Сложность добавления в конец?** — амортизированная O(1) (редкие реаллокации с копированием дают худший O(n), но усреднённо константа).

**Как исправить, чтобы foo() не влияла на arr?**

- Симптом классический: `foo` получает слайс, делит общий backing-массив и портит `arr` (через запись по индексу или `append` в пределах `cap`). Способы:
  - передавать **копию**: `cp := slices.Clone(arr)` (или `append([]T(nil), arr...)`) и работать с ней;
  - ограничить ёмкость full-slice-выражением `arr[i:j:j]`, чтобы первый же `append` в `foo` реаллоцировал и не трогал оригинал;
  - не мутировать вход, а возвращать новый слайс.

**Можно ли предвыделить память через make()?** (с подвохом)

- Да. `make([]T, 0, n)` — длина 0, **ёмкость n**: элементы добавляются через `append` без реаллокаций. Подвох в путанице длины и ёмкости: `make([]T, n)` создаёт слайс из **n нулевых элементов** (и `append` добавит **после** них, к n+1-му) — это не то же самое, что зарезервировать место. Для предвыделения под последующий append правильно `make([]T, 0, n)`.

### Лайвкодинг-вопросы по конкурентности

**Почему `wg.Add(1)` нельзя делать внутри запускаемой горутины?**

- Потому что `wg.Wait()` в вызывающей горутине может выполниться **раньше**, чем запущенная горутина успеет сделать `Add(1)`: `Wait` увидит счётчик 0 и вернётся, программа завершится, не дождавшись работы (а если `Add` выполнится после старта `Wait`, возможна паника «WaitGroup misuse»). `Add` всегда вызывают **до** `go func()` (в родительской горутине).

**В какой последовательности отработают запущенные горутины?**

- Порядок **не определён** — зависит от планировщика; гарантий очерёдности запуска/завершения нет. Если нужен порядок — синхронизировать явно (каналы, цепочка сигналов).

**Проблемы при 100k URL (по горутине на URL) и как обойти?**

- Проблемы: 100k одновременных горутин и соединений → всплеск памяти, исчерпание файловых дескрипторов/портов, перегрузка цели (DoS по себе и по ним), отсутствие лимита и backpressure, неконтролируемые ошибки.
- Решения: **ограничить конкурентность** — worker pool или семафор (`golang.org/x/sync/semaphore`, буферизованный канал-семафор), `errgroup` с `SetLimit(N)`; переиспользовать `http.Client` с настроенным `Transport` (`MaxConnsPerHost`), таймауты и `context`, ретраи с backoff, батчинг.

**Исправить программу: завершиться, как только любая горутина вернёт ошибку.**

- Канонично — `errgroup.WithContext`: первая вернувшаяся ошибка отменяет общий `context`, остальные горутины видят `ctx.Done()` и сворачиваются, а `g.Wait()` возвращает эту ошибку.

```go
g, ctx := errgroup.WithContext(ctx)
for _, u := range urls {
    u := u
    g.Go(func() error {
        return fetch(ctx, u) // вернёт err → ctx отменится для всех
    })
}
if err := g.Wait(); err != nil { /* первая ошибка */ }
```

- Вручную то же делается через `context.WithCancel` + `cancel()` при первой ошибке и `sync.Once`/канал для её фиксации. См. [concurrency-and-performance/04-context-patterns.md](../01-go-core/concurrency-and-performance/04-context-patterns.md).
