Задача выдаётся как доработка существующего кода по списку из шести пунктов.
Проверяется не знание гипотезы Коллатца, а три вещи: замечен ли набор дефектов в
исходном коде, замечено ли противоречие между пунктами условия, и остаётся ли
решение корректным, когда к конкурентности добавляются кеш и отмена.

В разборе два решения, и путать их не нужно. Раздел
[«Версия за 30 минут»](#версия-за-30-минут) — это то, что реально пишется на
собеседовании: один файл, минимум абстракций, все шесть пунктов закрыты. Всё
остальное — пошаговое объяснение, откуда берётся каждое решение, и итоговый
вариант, до которого код доводят уже в репозитории, а не на доске. Разбор длинный
не потому, что задача требует столько кода, а потому, что почти каждая строка
минимальной версии — это ответ на отдельный вопрос интервьюера.

Код проверен на Go 1.26.5, darwin/arm64 (Apple M3 Max); используется
`slices.Clip` (Go 1.21+), `log/slog` (Go 1.21+) и маршрутизация с методом в
образце пути `"POST /collatz"` (Go 1.22+).

## Формулировка

> Дан HTTP-сервер на Go с одним эндпоинтом `/collatz`, который принимает одно
> число и возвращает последовательность Коллатца для него. Требуется доработать
> API и реализацию согласно следующим пунктам:
>
> 1. Расширить API — изменить формат запроса так, чтобы можно было передавать
>    массив чисел, а в ответе возвращать последовательность (или
>    последовательности) для каждого числа.
> 2. Вычислять последовательность конкурентно — для каждого числа из массива
>    запустить отдельную горутину.
> 3. Реализовать механизм остановки по первому завершившемуся — как только одна
>    из горутин первой завершит вычисление, остановить остальные вычисления и
>    вернуть результат именно этого «победителя».
> 4. Кешировать результаты — хранить результаты вычислений для каждого числа в
>    `map`, чтобы при повторном запросе того же числа не вычислять его заново.
> 5. Обеспечить конкурентный доступ к кешу — использовать механизмы
>    синхронизации для безопасного чтения и записи из нескольких горутин.
> 6. Обрабатывать прерывание от пользователя — корректно завершить вычисления,
>    если клиент разорвал соединение или отменил запрос.

```go
type req struct {
    Num []int
}
type resp struct {
    Sequence []int
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("/collatz", func(w http.ResponseWriter, r *http.Request) {
        in, _ := io.ReadAll(r.Body)
        data := &req{}
        err := json.Unmarshal(in, data)
        if err != nil {
            log.Fatalf(err.Error())
        }
        res := &resp{Sequence: collatz(data.Num)}
        out, err := json.Marshal(res)
        w.Write(out)
    })
    http.ListenAndServe(":8080", mux)
}

func collatz(n int) []int {
    iter := []int{}
    for n != 1 {
        iter = append(iter, n)
        if n%2 == 0 {
            n = n / 2
            continue
        }
        n = 3*n + 1
    }
    return iter
}
```

Последовательность Коллатца строится по правилу: чётное число делится пополам,
нечётное превращается в `3n+1`, и так до единицы. Гипотеза утверждает, что для
любого натурального числа процесс завершается, но доказательства нет — на
практике это означает, что цикл нельзя считать заведомо конечным и ограничения
нужны в коде, а не в предположениях.

## Что не так в исходном коде

Разбор стоит начать отсюда: половина пунктов задания опирается на код, который
не собирается и не переживает первый запрос.

| Дефект | Что происходит | Серьёзность |
| --- | --- | --- |
| `collatz(data.Num)` | `data.Num` имеет тип `[]int`, параметр — `int`. Код не компилируется | не собирается |
| `log.Fatalf` в обработчике | битый JSON от любого клиента вызывает `os.Exit(1)` и убивает весь сервер | отказ в обслуживании |
| `collatz(0)` и отрицательные | цикл `for n != 1` никогда не заканчивается, `append` растёт до конца памяти | отказ в обслуживании |
| Нет финальной `1` | `collatz(6)` возвращает `[6 3 10 5 16 8 4 2]`, а `collatz(1)` — пустой срез | неверный результат |
| Переполнение в `3n+1` | для больших `n` результат переходит через `math.MaxInt` и становится отрицательным, дальше см. строку про отрицательные | неверный результат и зацикливание |
| `io.ReadAll` без ограничения | тело запроса целиком попадает в память, размер задаёт клиент | отказ в обслуживании |
| Ошибки `io.ReadAll` и `json.Marshal` проигнорированы | при ошибке маршалинга в ответ уходит пустое тело со статусом 200 | скрытый сбой |
| Нет `Content-Type` и кода ответа | клиент получает `text/plain` с угаданным типом вместо `application/json` | несоответствие контракту |
| Нет проверки метода | `GET /collatz` без тела приводит к ошибке разбора, то есть к `log.Fatalf` | см. строку про `log.Fatalf` |
| `http.ListenAndServe` без `http.Server` | нет `ReadTimeout`, `WriteTimeout` и graceful shutdown | эксплуатационная проблема |

Два дефекта заслуживают отдельных слов, потому что именно их чаще всего
пропускают.

**`log.Fatalf(err.Error())` в обработчике.** Ошибка разбора входных данных — это
`400 Bad Request`, а не повод завершать процесс. Любой клиент, отправивший
`{`, останавливает сервис для всех остальных. Заодно здесь ошибка формата:
`log.Fatalf` ожидает строку формата, а `err.Error()` может содержать `%`, и
`go vet` на такой вызов ругается (`non-constant format string`). Правильно —
`log.Printf("%v", err)` или сразу структурированный логгер.

**Вечный цикл на неположительных числах.** Проверить это на живом сервере нельзя
безопасно, поэтому проще разобрать на бумаге:

```text
n = 0:   0 % 2 == 0 -> n = 0 / 2 = 0 -> снова 0 ...
         условие n != 1 выполняется всегда, iter растёт бесконечно

n = -1: -1 % 2 == -1 (в Go остаток берёт знак делимого, а не делителя)
        значит ветка «чётное» не срабатывает: n = 3*(-1) + 1 = -2
        -2 % 2 == 0 -> n = -1 -> цикл -1, -2, -1, -2, ...
```

Обе ветки заканчиваются одинаково: `append` в бесконечном цикле съедает память
до срабатывания OOM killer. Отсюда первое требование к переработанному коду —
валидация `n >= 1` до запуска цикла, а не после.

## Уточняющие вопросы

1. **Пункты 1 и 3 противоречат друг другу. Что из них имеет силу?**
   Пункт 1 требует вернуть последовательности для всех чисел, пункт 3 — вернуть
   результат одного «победителя» и погасить остальные вычисления. Одновременно
   выполнить оба нельзя: если остальные вычисления остановлены, их
   последовательностей в ответе не будет. Это ключевой вопрос задачи, и молча
   выбрать одну из трактовок — худший вариант ответа.

   Правильный вывод из противоречия — это не два режима одного эндпоинта, а два
   разных эндпоинта. Формат ответа у них разный не в деталях, а целиком: массив
   результатов против одного объекта. Ответ, форма которого зависит от поля в
   запросе, вынуждает клиента разбирать объединение двух типов, ломает
   кодогенерацию по схеме и требует полей, которые в половине случаев пусты.
   Разные операции — разные ресурсы:

   ```text
   POST /collatz        {"numbers":[6,7]} -> {"results":[{...},{...}]}
   POST /collatz/first  {"numbers":[6,7]} -> {"number":6,"sequence":[...]}
   ```

   Так противоречие исчезает вовсе: пункты 1 и 3 перестают быть конфликтующими
   требованиями к одному API и становятся описанием двух операций.
   Разделение даёт и практические следствия: у эндпоинтов разные метрики и
   лимиты, а недетерминированный `/collatz/first` можно объявить устаревшим и
   убрать, не трогая основной. Ниже показано, что оно ещё и упрощает код.

2. **Что означает «первой завершит вычисление»?**
   Буквально — та goroutine, которая первой дошла до конца, а не та, у которой
   самая короткая последовательность. Это гонка планировщика, поэтому ответ
   API становится недетерминированным. Если заказчику нужен предсказуемый ответ
   («самая короткая последовательность»), это уже другое требование, и считать
   надо все числа.

3. **Зачем останавливать вычисления, если они занимают микросекунды?**
   Для чисел обычного размера последовательность короче тысячи шагов, и отмена
   не успевает ничего сэкономить. Смысл появляется на больших входных массивах:
   отмена не столько прерывает текущие вычисления, сколько не даёт начаться
   оставшимся.

4. **Сколько чисел может прийти в запросе?**
   Пункт 2 требует goroutine на число, значит клиент управляет числом goroutine
   и объёмом работы. Без верхней границы это прямой способ положить сервис
   массивом на миллион элементов.

5. **Что кешируется — вся последовательность или её длина?**
   Последовательность для `n = 837799` содержит 525 чисел, то есть около 4 КБ на
   ключ. Кеш длин на порядок дешевле, но не отвечает на пункт 1. Хранение всей
   последовательности принято в решении, а ограничение размера кеша обсуждается
   отдельно.

6. **Кеш живёт в памяти процесса?**
   Да, по условию это `map`. Тогда он не переживает перезапуск и не общий для
   нескольких реплик — это ограничение стоит проговорить, а не выдавать за
   решение.

7. **Что считать «прерыванием от пользователя»?**
   Разрыв соединения и отмену запроса клиентом. В Go оба случая приходят одним
   способом — `r.Context()` отменяется, поэтому отдельной обработки не требуется.

8. **Что возвращать, если часть чисел невалидна?**
   Либо `400` на весь запрос, либо результат по каждому числу со своей ошибкой.
   В решении выбран первый вариант для явно неположительных чисел (это ошибка
   клиента) и второй — для ошибок вычисления вроде переполнения.

## Версия за 30 минут

Полное решение из раздела «Итоговое решение» за отведённое время не пишется и не
должно писаться: это то, во что код превращается после ревью. На доске нужен один
файл, закрывающий все шесть пунктов, — около 160 строк вместе с импортами и
структурами.

Два эндпоинта вместо одного с режимом обходятся дешевле, чем кажется: общий
разбор входа выносится в `decode`, и каждый обработчик остаётся коротким и с
одним фиксированным типом ответа. Ветвление по режиму внутри цикла goroutine при
этом исчезает.

Бюджет времени:

| Минуты | Что происходит |
| --- | --- |
| 0–5 | Читаем код вслух, называем дефекты, задаём вопрос про противоречие пунктов 1 и 3 |
| 5–12 | Чиним `collatz`: валидация, финальная единица, отмена внутри цикла |
| 12–20 | `POST /collatz`: массив, goroutine на число, `WaitGroup` |
| 20–25 | Кеш под `RWMutex` |
| 25–30 | `POST /collatz/first` и `r.Context()`, вслух проговариваем остальное |

Главный приём здесь — разделить «что кодим» и «что проговариваем». Половина
качества ответа приходится на вторую колонку, и она не стоит ни минуты времени:

| Кодим | Проговариваем вслух, не кодим |
| --- | --- |
| валидация `n >= 1` | ограничение размера тела запроса |
| финальная единица в последовательности | проверка переполнения `3n+1` |
| goroutine на число и `WaitGroup` | верхняя граница числа goroutine |
| `map` под `RWMutex` | вытеснение из кеша, LRU, `singleflight` |
| проверка `ctx` внутри цикла | `slices.Clip` и контракт неизменяемости значения |
| `r.Context()` в обработчике | таймауты `http.Server` и graceful shutdown |
| канал победителя с буфером 1 | детерминированный критерий вместо гонки |

```go
package main

import (
    "context"
    "encoding/json"
    "log"
    "net/http"
    "sync"
)

type req struct {
    Numbers []int `json:"numbers"`
}

type item struct {
    Number   int    `json:"number"`
    Sequence []int  `json:"sequence,omitempty"`
    Error    string `json:"error,omitempty"`
}

var (
    mu    sync.RWMutex
    cache = map[int][]int{}
)

func collatz(ctx context.Context, n int) ([]int, error) {
    mu.RLock()
    seq, ok := cache[n]
    mu.RUnlock()
    if ok {
        return seq, nil
    }

    seq = []int{}
    for i := 0; ; i++ {
        seq = append(seq, n)
        if n == 1 { // выход после append, иначе теряется последний элемент
            break
        }
        if i%1024 == 0 { // отмена: проверяем не на каждой итерации
            if err := ctx.Err(); err != nil {
                return nil, err
            }
        }
        if n%2 == 0 {
            n /= 2
        } else {
            n = 3*n + 1
        }
    }

    mu.Lock()
    cache[seq[0]] = seq // ключ — исходное n, оно же первый элемент
    mu.Unlock()
    return seq, nil
}

// decode читает и проверяет вход; общая часть обоих обработчиков.
func decode(w http.ResponseWriter, r *http.Request) ([]int, bool) {
    var in req
    if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
        http.Error(w, err.Error(), http.StatusBadRequest) // не log.Fatalf
        return nil, false
    }
    if len(in.Numbers) == 0 {
        http.Error(w, "numbers не должен быть пустым", http.StatusBadRequest)
        return nil, false
    }
    for _, n := range in.Numbers {
        if n < 1 { // без этого 0 и отрицательные дают вечный цикл
            http.Error(w, "числа должны быть положительными", http.StatusBadRequest)
            return nil, false
        }
    }
    return in.Numbers, true
}

// POST /collatz — последовательности для всех чисел, порядок сохраняется.
func handleAll(w http.ResponseWriter, r *http.Request) {
    nums, ok := decode(w, r)
    if !ok {
        return
    }
    ctx := r.Context() // отменяется, когда клиент разорвал соединение

    items := make([]item, len(nums))
    var wg sync.WaitGroup
    for i, n := range nums {
        wg.Add(1)
        go func() {
            defer wg.Done()
            seq, err := collatz(ctx, n)
            if err != nil {
                items[i] = item{Number: n, Error: err.Error()}
                return
            }
            items[i] = item{Number: n, Sequence: seq} // свой индекс у каждой
        }()
    }
    wg.Wait() // до него items читать нельзя

    if ctx.Err() != nil { // клиент ушёл — отвечать некому
        return
    }
    writeJSON(w, struct {
        Results []item `json:"results"`
    }{items})
}

// POST /collatz/first — результат первой завершившейся goroutine.
func handleFirst(w http.ResponseWriter, r *http.Request) {
    nums, ok := decode(w, r)
    if !ok {
        return
    }
    ctx, cancel := context.WithCancel(r.Context())
    defer cancel() // гасит проигравших, когда обработчик вернул ответ

    winner := make(chan item, 1) // буфер 1; канал не закрываем — отправители ещё живы
    var wg sync.WaitGroup
    for _, n := range nums {
        wg.Add(1)
        go func() {
            defer wg.Done()
            seq, err := collatz(ctx, n)
            if err != nil {
                return
            }
            select {
            case winner <- item{Number: n, Sequence: seq}:
            default: // место занято — этот результат отбрасывается
            }
        }()
    }

    done := make(chan struct{})
    go func() { wg.Wait(); close(done) }() // все завершились, победителя может не быть

    select {
    case it := <-winner: // отвечаем сразу, не дожидаясь проигравших
        writeJSON(w, it)
    case <-done:
        select {
        case it := <-winner: // done и winner могли сработать одновременно
            writeJSON(w, it)
        default:
            http.Error(w, "результат не получен", http.StatusUnprocessableEntity)
        }
    case <-ctx.Done(): // клиент ушёл
        return
    }
}

func writeJSON(w http.ResponseWriter, v any) {
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(v)
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("POST /collatz", handleAll)
    mux.HandleFunc("POST /collatz/first", handleFirst)
    log.Fatal(http.ListenAndServe(":8080", mux))
}
```

Что здесь сознательно упрощено по сравнению с итоговым вариантом:

- **Кеш и мьютекс — пакетные переменные**, а не поля структуры `Service`.
  Внедрять зависимости на доске незачем, но стоит сказать, что глобальное
  состояние мешает тестам, и в репозитории это станет полем.
- **Обработчики — функции, а не типы с методами.** Логгера нет, ошибки уходят
  через `http.Error`.
- **Кеш возвращает срез как есть**, без `slices.Clip`. Это допущение, а не
  недосмотр, и его надо озвучить: контракт «значение из кеша не изменяют»,
  иначе `append` читателя запишет в общий массив.
- **Нет проверки переполнения, лимита тела и верхней границы массива** — всё это
  идёт в колонку «проговариваем».
- **Обычный `http.ListenAndServe`**, без таймаутов и graceful shutdown.

Что при этом не упрощено и упрощать нельзя, потому что это и есть предмет
проверки:

- валидация `n >= 1` — без неё сервис кладётся первым же нулём;
- выход из цикла после `append` — иначе результат просто неверный;
- `RWMutex` вокруг обеих операций с `map` — конкурентная запись в `map` даёт не
  гонку данных, а немедленную панику рантайма `concurrent map writes`;
- `wg.Wait()` до чтения `items` в `handleAll` — без него результаты читаются,
  пока их пишут;
- буфер 1 и ветка `default` у канала победителя — без `default` проигравшие
  goroutine блокируются навсегда;
- канал `done` в `handleFirst` — без него обработчик виснет, когда победителя не
  оказалось вовсе.

Проверка, что версия рабочая (Go 1.26.5, darwin/arm64):

```
$ go test -race -count=3 ./
ok  	two	1.501s
```

Тесты для неё — те же, что в разделе [«Шаг 7. Тесты»](#шаг-7-тесты), только
короче: массив чисел, форма ответа `/collatz/first`, маршрутизация (образец
`POST /collatz` не должен перехватывать `/collatz/first`), невалидный вход даёт
`400`, ушедший клиент не получает ответ, и параллельные запросы с дубликатами под
`-race`. На собеседовании их обычно не пишут, а перечисляют — но перечислить
нужно, потому что вопрос «как бы вы это протестировали» задают почти всегда.

Дальше идёт разбор: каждый шаг объясняет одно решение из этого файла и
показывает, во что оно вырастает, когда код переезжает в репозиторий.

## Шаг 1. Корректное ядро: последовательность одного числа

До всякой конкурентности нужно починить саму функцию: без этого параллельно
считается неправильный результат.

```go
var (
    ErrNotPositive = errors.New("число должно быть положительным")
    ErrOverflow    = errors.New("переполнение int при вычислении 3n+1")
)

// Sequence возвращает последовательность Коллатца для n, включая финальную 1.
func Sequence(n int) ([]int, error) {
    if n < 1 {
        return nil, fmt.Errorf("%w: %d", ErrNotPositive, n)
    }

    seq := make([]int, 0, 64) // типичная длина — десятки-сотни элементов
    for {
        seq = append(seq, n)
        if n == 1 {
            return seq, nil
        }
        if n%2 == 0 {
            n /= 2
            continue
        }
        if n > (math.MaxInt-1)/3 { // 3n+1 не поместится в int
            return nil, fmt.Errorf("%w: %d", ErrOverflow, n)
        }
        n = 3*n + 1
    }
}
```

Что изменилось по сравнению с исходной версией:

- **Условие выхода переехало внутрь цикла**, после `append`. В исходном варианте
  проверка `n != 1` стояла до добавления, поэтому финальная единица не попадала в
  результат, а `collatz(1)` возвращал пустой срез.
- **Добавлена валидация `n >= 1`** — она закрывает и ноль, и отрицательные числа,
  то есть оба сценария бесконечного цикла.
- **Добавлена проверка переполнения.** Порог `(math.MaxInt-1)/3` — это наибольшее
  `n`, для которого `3n+1` ещё помещается в `int`. Проверять надо до умножения:
  после переполнения значение уже потеряно и станет отрицательным.
- **Появилась предвыделенная ёмкость** `make([]int, 0, 64)`. Это не
  преждевременная оптимизация, а типичная длина результата: без неё срез
  переаллоцируется около семи раз.

Проверка на известных значениях:

```text
n = 6:  6 -> 3 -> 10 -> 5 -> 16 -> 8 -> 4 -> 2 -> 1     (8 шагов, 9 элементов)
n = 1:  1                                                 (0 шагов, 1 элемент)
n = 27: длина 112 элементов, 111 шагов, максимум 9232
```

Число 27 стоит помнить как контрольный пример: оно маленькое, но его траектория
поднимается до 9232 и делает 111 шагов. Это наглядно показывает, что длина
последовательности не связана с величиной входа, и что оценить работу заранее
нельзя.

## Шаг 2. API на массив чисел

Формат запроса и ответа определяется решением из уточняющего вопроса 1: вместо
одного эндпоинта с режимом — два эндпоинта с фиксированным ответом у каждого.

```go
// вход общий для обоих эндпоинтов
type Request struct {
    Numbers []int `json:"numbers"`
}

type Item struct {
    Number   int    `json:"number"`
    Steps    int    `json:"steps"`
    Sequence []int  `json:"sequence,omitempty"`
    Error    string `json:"error,omitempty"`
}

// POST /collatz
type AllResponse struct {
    Results []Item `json:"results"`
}

// POST /collatz/first — ответ и есть Item, обёртка не нужна
```

Почему не одно поле `mode` с объединённым ответом:

- **Тип ответа перестаёт быть одним типом.** `{"results":[...]}` и
  `{"winner":{...}}` не имеют общих полей. Клиенту приходится описывать
  объединение и разбирать его по признаку, которого в ответе может и не быть.
- **Появляются поля, пустые в половине случаев.** `Results` и `Winner` с
  `omitempty` — это признак того, что в одну структуру сложили два разных
  ответа. Схема (OpenAPI, protobuf) такую форму либо не выражает, либо выражает
  через `oneof`, который клиенты всё равно разбирают вручную.
- **Разные операции хочется наблюдать раздельно.** Метрики, коды ответов,
  лимиты и таймауты у «посчитать всё» и «выиграть гонку» разные, а по одному
  маршруту они смешиваются.
- **Убрать эндпоинт проще, чем убрать значение поля.** `/collatz/first` даёт
  недетерминированный ответ, и вполне вероятно, что от него откажутся; удаление
  маршрута не трогает основной эндпоинт, а удаление значения `mode` — ломает
  контракт общего.

Решения, которые остаются в обоих вариантах:

- **Число вернулось в ответ вместе с последовательностью.** В исходном `resp`
  было только поле `Sequence`, и при массиве чисел клиенту пришлось бы
  сопоставлять результаты по позиции. Явное поле `number` убирает эту привязку.
- **Ошибка живёт внутри элемента, а не только в HTTP-статусе.** Одно число может
  не посчитаться (переполнение), а остальные посчитаться. Ответ `500` на весь
  запрос в этом случае теряет полезную работу.
- **`Results` без `omitempty`.** Пустой массив должен приезжать как `[]`, а не
  исчезать: клиенту проще итерировать пустой список, чем проверять отсутствие
  поля.

Маршрутизация с Go 1.22 различает эндпоинты по образцу пути вместе с методом:

```go
mux.HandleFunc("POST /collatz", handleAll)
mux.HandleFunc("POST /collatz/first", handleFirst)
```

Образец `POST /collatz` без завершающего слэша совпадает только с точным путём,
поэтому `/collatz/first` уходит своему обработчику, а не перехватывается первым.
Это стоит проверить тестом: правило неочевидно, и до Go 1.22 поведение было
другим.

Валидация выполняется до запуска любых goroutine:

```go
const (
    maxBodyBytes = 1 << 16 // 64 КБ хватает на список чисел
    maxNumbers   = 1000    // граница числа goroutine на один запрос
)

func validate(req Request) error {
    switch {
    case len(req.Numbers) == 0:
        return errors.New("numbers не должен быть пустым")
    case len(req.Numbers) > maxNumbers:
        return errors.New("слишком много чисел в запросе")
    }
    for _, n := range req.Numbers {
        if n < 1 {
            return ErrNotPositive
        }
    }
    return nil
}
```

`maxNumbers` — прямое следствие пункта 2 условия: раз на каждое число создаётся
goroutine, размер массива задаёт объём работы, и его выбирает клиент. Ограничение
входа здесь дешевле любого пула, потому что не меняет требуемую условием
структуру решения.

## Шаг 3. Goroutine на число

Режим `all` — это классический fan-out с записью результатов по индексу.

```go
func (s *Service) All(ctx context.Context, nums []int) ([]Item, error) {
    items := make([]Item, len(nums)) // длина известна заранее

    var wg sync.WaitGroup
    for i, n := range nums {
        wg.Add(1)
        go func() {
            defer wg.Done()
            items[i] = s.one(ctx, n) // каждая goroutine пишет свой индекс
        }()
    }
    wg.Wait()

    if err := ctx.Err(); err != nil { // клиент ушёл — отдавать нечего
        return nil, err
    }
    return items, nil
}
```

Почему запись в общий срез здесь не является гонкой: `items` создан до запуска
goroutine и его длина не меняется, а каждая goroutine пишет ровно в свой индекс.
Разные элементы среза — разные адреса, синхронизация не нужна. Гонка появилась
бы, если бы срез рос через `append` или если бы кто-то читал `items` до
`wg.Wait()`.

Канал вместо среза тоже работает, но требует лишнего шага: результаты придут в
произвольном порядке, и их всё равно придётся раскладывать по позициям входа.
Срез сохраняет порядок бесплатно.

**`wg.Wait()` обязателен даже при отмене.** Соблазн вернуть управление сразу по
`ctx.Done()` создаёт две проблемы: goroutine продолжают писать в `items` уже
после возврата из обработчика, и никто не гарантирует, что они завершатся вообще.
Ждать безопасно, потому что `Sequence` проверяет отмену внутри цикла и выходит
быстро — это как раз то, ради чего проверка там стоит.

В Go 1.25 тело цикла короче: `wg.Go(func() { items[i] = s.one(ctx, n) })`
совмещает `Add(1)`, `go` и `defer Done()`.

## Шаг 4. Остановка по первому завершившемуся

`/collatz/first` добавляет обратный сигнал: не «вход закончился», а «результат
уже не нужен». Переносится он `context`, а роль победителя достаётся буферу на
один элемент.

Разделение эндпоинтов здесь даёт не только чистый формат ответа. Пока результаты
всех чисел складывались в общий срез `items`, обработчик был обязан дождаться
`wg.Wait()` перед ответом: иначе goroutine продолжали бы писать в срез, который
уже сериализуется. То есть «остановить остальные и вернуть результат победителя»
выполнялось лишь наполовину — остальные останавливались, но ответ всё равно ждал
их завершения. У отдельного эндпоинта общего среза нет, и обработчик возвращает
ответ сразу, как только победитель появился:

```go
func First(parent context.Context, nums []int) (Item, error) {
    ctx, cancel := context.WithCancel(parent)
    defer cancel() // гасит проигравших, когда функция уже вернула ответ

    winner := make(chan Item, 1) // место ровно для одного победителя

    var wg sync.WaitGroup
    for _, n := range nums {
        wg.Add(1)
        go func() {
            defer wg.Done()
            seq, err := Sequence(ctx, n)
            if err != nil { // отменённые и невалидные в победители не идут
                return
            }
            select {
            case winner <- Item{Number: n, Steps: len(seq) - 1, Sequence: seq}:
            default: // место занято, этот результат отбрасывается
            }
        }()
    }

    done := make(chan struct{})
    go func() { wg.Wait(); close(done) }()

    select {
    case it := <-winner: // ответ готов, проигравших не ждём
        return it, nil
    case <-done: // все завершились, победителя может не быть
        select {
        case it := <-winner: // done и winner могли сработать одновременно
            return it, nil
        default:
            return Item{}, ErrNoResult
        }
    case <-ctx.Done():
        return Item{}, ctx.Err()
    }
}
```

Что изменилось по сравнению с версией, ждавшей `wg.Wait()`:

- **`cancel()` больше не вызывается победителем.** Его делает `defer` при выходе
  из функции — то есть ровно тогда, когда результат уже получен. Это и проще, и
  точнее: гасить остальных раньше, чем ответ забран, незачем.
- **Канал `winner` не закрывается.** Отправители ещё живы в момент возврата, а
  отправка в закрытый канал — паника. Здесь закрытие и не нужно: значение
  забирается ровно одно.
- **Появился канал `done`.** Без него `select` виснет навсегда в случае, когда ни
  одна goroutine не дала результата: `winner` пуст, а `ctx` никто не отменял.
  Это не теоретический случай — достаточно, чтобы все числа упёрлись в
  переполнение.
- **Вложенный `select` в ветке `done`.** `done` и `winner` могут стать готовы
  одновременно, и внешний `select` выберет случайную ветку. Без повторной
  проверки готовый результат иногда превращался бы в `422`.

Goroutine при этом переживают возврат из функции. Это не утечка: `defer cancel()`
уже сработал, `Sequence` выходит по `ctx.Done()` в пределах микросекунд, запись в
кеш защищена мьютексом, а отправка в `winner` неблокирующая. Но проговорить это
нужно — «goroutine живут дольше обработчика» обычно является дефектом, и здесь
важно показать, почему конкретно тут нет.

Как работает выбор победителя:

```text
буфер winner размером 1

goroutine A: select { case winner <- itA: ... }   -> буфер свободен, отправка проходит,
                                                     обработчик забирает itA и отвечает
goroutine B: select { case winner <- itB: ...
                      default: }                  -> буфер занят, срабатывает default,
                                                     itB отбрасывается без блокировки
```

Ветка `default` здесь несёт всю нагрузку. Без неё вторая goroutine заблокируется
на отправке в заполненный канал и не завершится, пока кто-то не вычитает
значение, — то есть повиснет и `wg.Wait()`, и вместе с ним канал `done`. Буфер
размером с число чисел тоже работает, но тогда «победитель» перестаёт быть один:
в канал попадут все, кто успел до отмены.

**Победитель недетерминирован по контракту, но не выглядит таким.** Пять
одинаковых запросов к живому сервису:

```
$ for i in 1 2 3 4 5; do curl -sS -X POST localhost:8080/collatz/first \
    -d '{"numbers":[27,97,871,6171]}'; done

{"number":871,"steps":178,...}
{"number":27,"steps":111,...}
{"number":27,"steps":111,...}
{"number":27,"steps":111,...}
{"number":27,"steps":111,...}
```

Первый запрос выиграло число 871 со 178 шагами, дальше стабильно побеждает 27 со
111 шагами. Объяснение простое: 27 стоит первым в массиве и запускается первым, а
его последовательность самая короткая из четырёх, так что на прогретом процессе
оно приходит к финишу раньше остальных. Разброс даёт только первый запрос, когда
на исход влияют накладные расходы старта.

Такое поведение хуже откровенной случайности. Клиент, попробовавший эндпоинт
десяток раз, решит, что победитель предсказуем, и начнёт на это опираться, — а
контракта нет никакого. Достаточно изменить порядок чисел в запросе, добавить
нагрузку на машину или получить попадание в кеш по другому числу, и ответ
поменяется. Именно поэтому недетерминированность нужно называть вслух, а не
проверять экспериментом.

Детерминированная альтернатива, которую имеет смысл предложить, — считать всё и
выбрать по внятному критерию:

```go
// Shortest — самая короткая последовательность, при равенстве меньшее число.
func Shortest(items []Item) (Item, bool) {
    best, found := Item{}, false
    for _, it := range items {
        if it.Error != "" {
            continue
        }
        if !found || it.Steps < best.Steps ||
            (it.Steps == best.Steps && it.Number < best.Number) {
            best, found = it, true
        }
    }
    return best, found
}
```

Цена честная: экономии на отмене больше нет, зато один и тот же запрос всегда
даёт один и тот же ответ.

## Шаг 5. Кеш и конкурентный доступ к нему

Пункты 4 и 5 условия — это `map` под `sync.RWMutex`. Мьютекс держится только на
операции с картой, вычисление происходит вне критической секции.

```go
type Cache struct {
    mu sync.RWMutex
    m  map[int][]int
}

func NewCache() *Cache { return &Cache{m: make(map[int][]int)} }

func (c *Cache) Get(n int) ([]int, bool) {
    c.mu.RLock()
    seq, ok := c.m[n]
    c.mu.RUnlock()
    return seq, ok
}

// Put кладёт значение с cap == len: append на стороне читателя
// не сможет писать в общий массив.
func (c *Cache) Put(n int, seq []int) {
    c.mu.Lock()
    c.m[n] = slices.Clip(seq)
    c.mu.Unlock()
}
```

**Почему `slices.Clip`, а не просто присваивание.** Из кеша возвращается заголовок
среза, а массив под ним общий для всех читателей. Если у среза остаётся запас
ёмкости (`cap > len`), то `append` на стороне читателя запишет прямо в этот общий
массив — при том, что читатель формально ничего не менял в кеше:

```text
до:  cap = 64, len = 9   -> append пишет в свободный слот общего массива
     кеш и читатель делят один массив, изменение видно всем

Clip: cap = len = 9      -> append вынужден аллоцировать новый массив,
     кеш остаётся нетронутым
```

`Clip` стоит O(1) — он только правит заголовок. Полная копия через
`slices.Clone` защищает ещё и от записи по индексу (`seq[0] = 5`), но стоит O(n)
на каждое чтение и обесценивает сам кеш для длинных последовательностей. Разумный
компромисс — `Clip` плюс задокументированный контракт «значение из кеша
неизменяемо»; `Clone` уместен, когда значение уходит за границу пакета, поведение
которого неизвестно.

**Почему `RWMutex`, а не `Mutex`.** Профиль нагрузки здесь read-heavy: после
прогрева почти каждый запрос — попадание в кеш. На коротких критических секциях
разница между `Mutex` и `RWMutex` невелика и на малом числе ядер может быть даже
в пользу обычного мьютекса, поэтому в ответе полезно оговорить, что выбор
подтверждается замером, а не общим правилом.

Сравнение с альтернативами:

| Вариант | Когда лучше | Чем платит |
| --- | --- | --- |
| `map` + `RWMutex` | понятный контракт, легко добавить вытеснение | одна точка конкуренции на всех |
| `sync.Map` | ключи пишутся один раз и много раз читаются | нет `len`, нет вытеснения, значения через `any` |
| Шардированная карта | много ядер и заметная конкуренция | больше кода, сложнее вытеснение |
| `singleflight` поверх любого из них | много одновременных запросов одного ключа | склеивает и `context` вызовов, см. ниже |

**Чего кеш из условия не делает.** Он неограниченно растёт: ключи не вытесняются,
и клиент, перебирающий числа, спокойно доводит процесс до OOM. Кеш длин был бы
на порядок компактнее, но не отвечает пункту 1. Минимально честный ответ —
назвать это ограничением и указать выход: LRU с лимитом по числу ключей или по
суммарной длине последовательностей.

**Дубликаты внутри одного запроса кеш не спасает.** Массив `[27, 27, 27]` даёт
три goroutine, и все три промахиваются мимо кеша, потому что ни одна ещё не
успела записать результат. Лечится это либо дедупликацией чисел до запуска
goroutine (дёшево и достаточно для этой задачи), либо `singleflight`. У
`singleflight` есть своя тонкость: общий вызов выполняется с `context` первого
пришедшего, и если тот клиент отключится, отменятся вычисления для всех
ожидающих. Обходится это отвязанным контекстом через `context.WithoutCancel` или
вариантом с `DoChan` и собственным `select`.

**Кеш ломает гонку из пункта 3.** Число, уже лежащее в кеше, возвращается
мгновенно и обыгрывает любое вычисляемое. Победителем на `/collatz/first`
становится не «лучшее» число, а то, которое раньше попало в кеш, — и порядок
попадания зависит от истории предыдущих запросов, а не от текущего. Ещё один
довод в пользу детерминированного критерия.

Отдельная тонкость появляется вместе с ранним возвратом из шага 4: проигравшие
отменяются и в кеш не попадают. То есть на `/collatz/first` кеш наполняется
только победителями, и один запрос прогревает ровно одно число из массива. На
`/collatz` кешируются все числа, потому что там дожидаются всех.

## Шаг 6. Отмена от клиента

Пункт 6 в Go решается одной строкой — `r.Context()` отменяется, когда клиент
разорвал соединение, отменил запрос или сработал таймаут сервера. Отдельно
обрабатывать разрыв и отмену не нужно, это один и тот же сигнал.

Работа начинается только тогда, когда отмену действительно кто-то проверяет.
Точка проверки — цикл вычисления:

```go
// checkEvery — как часто проверяется отмена.
const checkEvery = 1 << 10

func Sequence(ctx context.Context, n int) ([]int, error) {
    if n < 1 {
        return nil, fmt.Errorf("%w: %d", ErrNotPositive, n)
    }

    seq := make([]int, 0, 64)
    for i := 0; ; i++ {
        seq = append(seq, n)
        if n == 1 {
            return seq, nil
        }
        if i%checkEvery == 0 { // не на каждой итерации: см. замер ниже
            select {
            case <-ctx.Done():
                return nil, ctx.Err()
            default:
            }
        }
        if n%2 == 0 {
            n /= 2
            continue
        }
        if n > (math.MaxInt-1)/3 {
            return nil, fmt.Errorf("%w: %d", ErrOverflow, n)
        }
        n = 3*n + 1
    }
}
```

Частота проверки — не произвольное число. Замер на `n = 837799` (самая длинная
последовательность среди чисел до миллиона, 524 шага):

```
$ go test -run XXX -bench . -benchmem -count=5

goarch: arm64
cpu: Apple M3 Max

BenchmarkNoCheck-16          1604 ns/op    14464 B/op    5 allocs/op
BenchmarkCheckEvery1-16      2652 ns/op    14464 B/op    5 allocs/op
BenchmarkCheckEvery1024-16   1602 ns/op    14464 B/op    5 allocs/op
```

Приведены медианы пяти прогонов; разброс внутри каждой серии не превышает 3%.

Проверка на каждой итерации стоит около 65% времени вычисления: неблокирующий
`select` дешёв сам по себе, но здесь он сопоставим по стоимости с телом цикла из
одного деления. Проверка раз в 1024 итерации не отличается от полного её
отсутствия в пределах шума, а задержка реакции на отмену при этом остаётся
микросекундной. Степень двойки выбрана не ради `%`: компилятор превращает остаток
от деления на константу-степень двойки в побитовое И.

Соотношение сторон стоит проговорить честно: даже самая длинная
последовательность до миллиона — это 524 шага и полторы микросекунды. Прервать
такое вычисление невозможно физически. Отмена работает не на уровне одного числа,
а на уровне массива: goroutine, которые ещё не начали или только начали считать,
выходят немедленно, и запрос на тысячу чисел прекращается сразу, а не после
полного прохода.

Второе следствие отмены — ушедшему клиенту нельзя ответить:

```go
func (h *Handler) writeCtxError(w http.ResponseWriter, err error) {
    switch {
    case errors.Is(err, context.Canceled):
        // соединение закрыто: писать некому, важно не считать это ошибкой сервиса
        h.log.Info("запрос отменён клиентом")
    case errors.Is(err, context.DeadlineExceeded):
        writeError(w, http.StatusGatewayTimeout, "вычисление не уложилось в срок")
    case errors.Is(err, ErrNoResult):
        writeError(w, http.StatusUnprocessableEntity, err.Error())
    default:
        h.log.Error("внутренняя ошибка", "err", err)
        writeError(w, http.StatusInternalServerError, "внутренняя ошибка")
    }
}
```

`context.Canceled` не логируется как ошибка уровня error: это штатное поведение
клиента, а не сбой сервиса. Если такие случаи попадают в счётчик ошибок, алерты
начинают срабатывать на пользователей, закрывших вкладку.

## Итоговое решение

Это версия после ревью, а не то, что пишут на доске: по сравнению с
[версией за 30 минут](#версия-за-30-минут) здесь добавлены состояние в структуре
вместо пакетных переменных, ограничение тела и размера массива, проверка
переполнения, `slices.Clip` при записи в кеш, разбор видов отмены, таймауты
`http.Server` и graceful shutdown. Каждое отличие разобрано в шагах выше.

```go
package main

import (
    "context"
    "encoding/json"
    "errors"
    "fmt"
    "log/slog"
    "math"
    "net/http"
    "os"
    "os/signal"
    "slices"
    "sync"
    "syscall"
    "time"
)

// --- ядро ---------------------------------------------------------------

var (
    ErrNotPositive = errors.New("число должно быть положительным")
    ErrOverflow    = errors.New("переполнение int при вычислении 3n+1")
)

// checkEvery — как часто проверяется отмена. Степень двойки, чтобы
// проверка сводилась к побитовому И.
const checkEvery = 1 << 10

// Sequence возвращает последовательность Коллатца для n, включая финальную 1.
func Sequence(ctx context.Context, n int) ([]int, error) {
    if n < 1 {
        return nil, fmt.Errorf("%w: %d", ErrNotPositive, n)
    }

    seq := make([]int, 0, 64)
    for i := 0; ; i++ {
        seq = append(seq, n)
        if n == 1 {
            return seq, nil
        }
        if i%checkEvery == 0 {
            select {
            case <-ctx.Done():
                return nil, ctx.Err()
            default:
            }
        }
        if n%2 == 0 {
            n /= 2
            continue
        }
        if n > (math.MaxInt-1)/3 {
            return nil, fmt.Errorf("%w: %d", ErrOverflow, n)
        }
        n = 3*n + 1
    }
}

// Cache — потокобезопасный кеш готовых последовательностей.
type Cache struct {
    mu sync.RWMutex
    m  map[int][]int
}

func NewCache() *Cache { return &Cache{m: make(map[int][]int)} }

func (c *Cache) Get(n int) ([]int, bool) {
    c.mu.RLock()
    seq, ok := c.m[n]
    c.mu.RUnlock()
    return seq, ok
}

// Put кладёт значение с cap == len: append на стороне читателя
// не сможет писать в общий массив.
func (c *Cache) Put(n int, seq []int) {
    c.mu.Lock()
    c.m[n] = slices.Clip(seq)
    c.mu.Unlock()
}

func (c *Cache) Len() int {
    c.mu.RLock()
    defer c.mu.RUnlock()
    return len(c.m)
}

// --- сервис -------------------------------------------------------------

var ErrNoResult = errors.New("ни одно число не удалось вычислить")

type Item struct {
    Number   int    `json:"number"`
    Steps    int    `json:"steps"`
    Sequence []int  `json:"sequence,omitempty"`
    Error    string `json:"error,omitempty"`
}

type Service struct {
    cache *Cache
}

func NewService() *Service { return &Service{cache: NewCache()} }

// one возвращает результат для одного числа: из кеша или после вычисления.
func (s *Service) one(ctx context.Context, n int) Item {
    if seq, ok := s.cache.Get(n); ok {
        return Item{Number: n, Steps: len(seq) - 1, Sequence: seq}
    }
    seq, err := Sequence(ctx, n)
    if err != nil {
        return Item{Number: n, Error: err.Error()}
    }
    s.cache.Put(n, seq)
    return Item{Number: n, Steps: len(seq) - 1, Sequence: seq}
}

// All считает последовательности для всех чисел: goroutine на число,
// порядок результатов совпадает с порядком входа.
func (s *Service) All(ctx context.Context, nums []int) ([]Item, error) {
    items := make([]Item, len(nums))

    var wg sync.WaitGroup
    for i, n := range nums {
        wg.Add(1)
        go func() {
            defer wg.Done()
            items[i] = s.one(ctx, n) // каждая goroutine пишет свой индекс
        }()
    }
    wg.Wait()

    if err := ctx.Err(); err != nil { // клиент ушёл — отдавать нечего
        return nil, err
    }
    return items, nil
}

// First возвращает результат goroutine, завершившейся первой,
// и отменяет остальные вычисления. Проигравших не дожидается.
func (s *Service) First(parent context.Context, nums []int) (Item, error) {
    ctx, cancel := context.WithCancel(parent)
    defer cancel() // гасит проигравших, когда результат уже забран

    winner := make(chan Item, 1) // ровно один победитель; не закрываем — отправители живы

    var wg sync.WaitGroup
    for _, n := range nums {
        wg.Add(1)
        go func() {
            defer wg.Done()
            it := s.one(ctx, n)
            if it.Error != "" { // отменённые и невалидные в победители не идут
                return
            }
            select {
            case winner <- it:
            default: // место занято, этот результат отбрасывается
            }
        }()
    }

    done := make(chan struct{})
    go func() { wg.Wait(); close(done) }()

    select {
    case it := <-winner: // отвечаем сразу, не дожидаясь проигравших
        return it, nil
    case <-done: // все завершились, победителя может не быть
        select {
        case it := <-winner: // done и winner могли сработать одновременно
            return it, nil
        default:
            return Item{}, ErrNoResult
        }
    case <-ctx.Done():
        return Item{}, ctx.Err()
    }
}

// Shortest — детерминированная замена «победителя»: самая короткая
// последовательность, при равенстве — меньшее число.
func Shortest(items []Item) (Item, bool) {
    best := Item{}
    found := false
    for _, it := range items {
        if it.Error != "" {
            continue
        }
        if !found || it.Steps < best.Steps || (it.Steps == best.Steps && it.Number < best.Number) {
            best, found = it, true
        }
    }
    return best, found
}

// --- транспорт ----------------------------------------------------------

const (
    maxBodyBytes = 1 << 16 // 64 КБ входа достаточно для списка чисел
    maxNumbers   = 1000    // граница числа goroutine на один запрос
)

type Request struct {
    Numbers []int `json:"numbers"`
}

type AllResponse struct {
    Results []Item `json:"results"`
}

type Handler struct {
    svc *Service
    log *slog.Logger
}

// decode разбирает и проверяет вход; общая часть обоих обработчиков.
func (h *Handler) decode(w http.ResponseWriter, r *http.Request) ([]int, bool) {
    var req Request
    dec := json.NewDecoder(http.MaxBytesReader(w, r.Body, maxBodyBytes))
    dec.DisallowUnknownFields()
    if err := dec.Decode(&req); err != nil {
        writeError(w, http.StatusBadRequest, "некорректный JSON: "+err.Error())
        return nil, false
    }
    if err := validate(req); err != nil {
        writeError(w, http.StatusBadRequest, err.Error())
        return nil, false
    }
    return req.Numbers, true
}

// HandleAll обслуживает POST /collatz.
func (h *Handler) HandleAll(w http.ResponseWriter, r *http.Request) {
    nums, ok := h.decode(w, r)
    if !ok {
        return
    }
    items, err := h.svc.All(r.Context(), nums)
    if err != nil {
        h.writeCtxError(w, err)
        return
    }
    h.writeJSON(w, AllResponse{Results: items})
}

// HandleFirst обслуживает POST /collatz/first.
func (h *Handler) HandleFirst(w http.ResponseWriter, r *http.Request) {
    nums, ok := h.decode(w, r)
    if !ok {
        return
    }
    it, err := h.svc.First(r.Context(), nums)
    if err != nil {
        h.writeCtxError(w, err)
        return
    }
    h.writeJSON(w, it)
}

func (h *Handler) writeJSON(w http.ResponseWriter, v any) {
    w.Header().Set("Content-Type", "application/json")
    if err := json.NewEncoder(w).Encode(v); err != nil {
        h.log.Error("не удалось записать ответ", "err", err) // заголовки уже ушли
    }
}

func (h *Handler) writeCtxError(w http.ResponseWriter, err error) {
    switch {
    case errors.Is(err, context.Canceled):
        // клиент ушёл: писать некому, важно только не считать это ошибкой сервиса
        h.log.Info("запрос отменён клиентом")
    case errors.Is(err, context.DeadlineExceeded):
        writeError(w, http.StatusGatewayTimeout, "вычисление не уложилось в срок")
    case errors.Is(err, ErrNoResult):
        writeError(w, http.StatusUnprocessableEntity, err.Error())
    default:
        h.log.Error("внутренняя ошибка", "err", err)
        writeError(w, http.StatusInternalServerError, "внутренняя ошибка")
    }
}

func validate(req Request) error {
    switch {
    case len(req.Numbers) == 0:
        return errors.New("numbers не должен быть пустым")
    case len(req.Numbers) > maxNumbers:
        return errors.New("слишком много чисел в запросе")
    }
    for _, n := range req.Numbers {
        if n < 1 {
            return ErrNotPositive
        }
    }
    return nil
}

func writeError(w http.ResponseWriter, code int, msg string) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(code)
    _ = json.NewEncoder(w).Encode(map[string]string{"error": msg})
}

func main() {
    log := slog.New(slog.NewTextHandler(os.Stdout, nil))

    mux := http.NewServeMux()
    h := &Handler{svc: NewService(), log: log}
    mux.HandleFunc("POST /collatz", h.HandleAll)
    mux.HandleFunc("POST /collatz/first", h.HandleFirst)

    srv := &http.Server{
        Addr:              ":8080",
        Handler:           mux,
        ReadHeaderTimeout: 5 * time.Second,
        ReadTimeout:       10 * time.Second,
        WriteTimeout:      30 * time.Second,
        IdleTimeout:       60 * time.Second,
    }

    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            log.Error("сервер остановлен", "err", err)
            stop()
        }
    }()

    <-ctx.Done()
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutdownCtx); err != nil {
        log.Error("shutdown", "err", err)
    }
}
```

Свойства, которые стоит проговорить вслух:

| Вопрос | Ответ |
| --- | --- |
| Почему запись в `items[i]` без мьютекса безопасна | Срез создан до запуска goroutine, длина не меняется, каждая goroutine пишет свой индекс; читатель появляется только после `wg.Wait()`. |
| Почему в `All` есть `wg.Wait()`, а в `First` нет | В `All` goroutine пишут в общий срез, и читать его до их завершения нельзя. В `First` общего среза нет, поэтому ответ отдаётся сразу, как только победитель появился. |
| Зачем ветка `default` при отправке победителя | Без неё проигравшие блокируются на заполненном канале и не завершаются, а вместе с ними виснет `done`. |
| Почему буфер победителя равен 1 | Буфер по числу элементов пропустил бы всех, кто успел до отмены, и «первый» перестал бы быть первым. |
| Почему канал победителя не закрывается | В момент возврата отправители ещё живы, а отправка в закрытый канал — паника. Забирается ровно одно значение, закрытие не нужно. |
| Зачем канал `done` | Иначе `select` виснет навсегда, когда ни одна goroutine не дала результата: `winner` пуст, отменять никто не отменял. |
| Почему в ветке `done` стоит второй `select` | `done` и `winner` могут стать готовы одновременно, внешний `select` выбирает случайно; без повторной проверки готовый результат иногда превращался бы в `422`. |
| Почему goroutine переживают возврат из `First` | `defer cancel()` уже сработал, `Sequence` выходит по `ctx.Done()` за микросекунды, запись в кеш под мьютексом, отправка неблокирующая. Это допустимо, но требует объяснения. |
| Что возвращается, если победителя нет | `ErrNoResult`; уход клиента отличается по `ctx.Err()` — своя отмена не должна выглядеть как ошибка клиента. |
| Почему `Clip`, а не `Clone` при записи в кеш | `Clip` за O(1) закрывает единственный реальный сценарий порчи — `append` читателя в общий массив; `Clone` стоит O(n) на каждое чтение. |
| Почему обработчик не логирует `context.Canceled` как ошибку | Отключение клиента — штатное событие; в счётчике ошибок оно даёт ложные алерты. |

## Шаг 7. Тесты

Сеть в тестах не нужна: обработчик проверяется через `httptest.NewRecorder`, а
ядро — напрямую. Три группы проверок покрывают ровно те места, где решение
ломается.

**Корректность ядра**, включая случаи, которых исходный код не переживал:

```go
func TestSequence(t *testing.T) {
    tests := []struct {
        name string
        n    int
        want []int
    }{
        {"единица — сама последовательность", 1, []int{1}},
        {"чётное", 6, []int{6, 3, 10, 5, 16, 8, 4, 2, 1}},
        {"нечётное", 7, []int{7, 22, 11, 34, 17, 52, 26, 13, 40, 20, 10, 5, 16, 8, 4, 2, 1}},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := Sequence(context.Background(), tt.n)
            if err != nil {
                t.Fatalf("Sequence(%d) = err %v", tt.n, err)
            }
            if !slices.Equal(got, tt.want) {
                t.Fatalf("Sequence(%d) = %v, want %v", tt.n, got, tt.want)
            }
        })
    }
}

func TestSequence_NonPositive(t *testing.T) {
    for _, n := range []int{0, -1, -7} {
```

Тест на неположительные числа — единственный способ проверить отсутствие вечного
цикла: если валидация исчезнет при рефакторинге, тест не упадёт с ошибкой, а
повиснет и будет убит таймаутом `go test`. Это тоже сигнал, и он лучше молчаливо
зелёного прогона.

**Поведение кеша** — проверяется именно та ловушка, ради которой стоит `Clip`:

```go
func TestCache_AppendDoesNotCorrupt(t *testing.T) {
    svc := NewService()
    first := svc.one(context.Background(), 6)

    // читатель дописывает к полученному срезу: с Clip это аллоцирует копию
    _ = append(first.Sequence, 999)

    second := svc.one(context.Background(), 6)
    if !slices.Equal(first.Sequence, second.Sequence) {
        t.Fatalf("кеш испорчен: %v vs %v", first.Sequence, second.Sequence)
    }
    if slices.Contains(second.Sequence, 999) {
        t.Fatalf("append читателя попал в кеш: %v", second.Sequence)
    }
}
```

Без `Clip` этот тест падает: ёмкость среза равна 64, длина — 9, поэтому `append`
записывает 999 в свободный слот общего массива, и следующий читатель увидит его,
как только сам вызовет `append`.

```go
            rec := httptest.NewRecorder()
```

Тест маршрутизации проверяет неочевидное правило `ServeMux`: образец без
завершающего слэша совпадает только с точным путём, поэтому `POST /collatz` не
перехватывает `/collatz/first`. Заодно он фиксирует форму ответа второго
эндпоинта — это сам `Item`, без обёртки и полей, пустых в половине случаев.

Проверка на лишнее поле (`"mode"`) закрывает `DisallowUnknownFields`: клиент,
пришедший со старым форматом «режим в теле запроса», получает `400`, а не
молчаливо игнорируемое поле и неожиданный ответ.

Последний тест существует только ради `-race`: 50 параллельных запросов с
дубликатами внутри каждого создают одновременные чтения и записи одних и тех же
ключей кеша. Без `-race` он проходит и на коде вообще без синхронизации, поэтому
сам по себе ничего не доказывает.

Фактический прогон (Go 1.26.5, darwin/arm64, Apple M3 Max):

```
$ go test -race -count=3 ./
ok  	collatz	1.460s
```

`-count=3` нужен по той же причине, что и в задачах с ранней остановкой: тест,
проходящий только при удачном порядке планировщика, на одном прогоне выглядит
зелёным.

Чего эти тесты сознательно не проверяют — какое именно число окажется
победителем на `/collatz/first`. Победитель недетерминирован по контракту, и тест
на конкретное значение был бы флаки. Проверяется контракт: победитель ровно один,
без ошибки, и он входит в исходный массив.

## Подводные камни

- **Молчание про противоречие пунктов 1 и 3.** Кандидат, реализовавший только
  «победителя», не выполнил пункт 1; реализовавший только массив — пункт 3.
  Назвать конфликт вслух важнее, чем угадать «правильную» трактовку.
- **`log.Fatalf` в обработчике.** Ошибка разбора входа завершает процесс: любой
  клиент способен остановить сервис одним битым запросом.
- **Отсутствие валидации `n >= 1`.** Ноль и отрицательные числа дают вечный цикл
  с бесконечным `append`, то есть исчерпание памяти, а не просто неверный ответ.
- **Потерянная финальная единица.** Условие цикла `for n != 1` до `append`
  отрезает последний элемент, а `collatz(1)` возвращает пустой срез.
- **Переполнение `3n+1`.** Проверять нужно до умножения; после переполнения
  значение становится отрицательным и попадает в тот же вечный цикл.
- **Goroutine на число без ограничения размера массива.** Клиент управляет числом
  goroutine, и это тот же отказ в обслуживании, только через пункт 2 условия.
- **Отправка победителя без ветки `default`.** Проигравшие блокируются на
  заполненном канале и не завершаются, а вместе с ними виснет сигнал «все
  закончили».
- **`close(winner)` при живых отправителях.** С ранним возвратом проигравшие ещё
  работают, и отправка в закрытый канал даёт панику в чужой goroutine, то есть
  падение всего процесса.
- **`select` без канала `done`.** Если ни одно число не дало результата (все
  упёрлись в переполнение), обработчик виснет навсегда: `winner` пуст, отмены
  нет.
- **Ответ, форма которого зависит от поля запроса.** Один эндпоинт с `mode`
  возвращает то массив, то объект; клиент вынужден разбирать объединение типов, а
  схема выражает это только через `oneof`.
- **Буфер канала победителя размером `len(nums)`.** Отправка проходит у всех, кто
  успел до отмены, и «первый завершившийся» превращается в «любой из успевших».
- **Возврат из `All` по `ctx.Done()` без `wg.Wait()`.** Goroutine продолжают
  писать в `items` после того, как обработчик вернул управление.
- **`context` в сигнатуре без проверки внутри цикла.** Отмена доходит до
  сервиса, но вычисление её не видит и работает до конца.
- **Проверка отмены на каждой итерации.** По замеру это +65% ко времени
  вычисления при неизменной задержке реакции в масштабе задачи.
- **Возврат среза из кеша без `Clip` или контракта неизменяемости.** `append` на
  стороне читателя пишет в общий массив: кеш портится без единой явной записи.
- **Кеш без ограничения размера.** Перебор чисел клиентом наполняет `map` до
  исчерпания памяти; вытеснение или лимит нужны с самого начала.
- **`context.Canceled` в счётчике ошибок.** Закрытая клиентом вкладка начинает
  выглядеть как сбой сервиса и поднимает алерты.
- **Запись в `http.ResponseWriter` после отмены.** Клиента уже нет; попытка
  ответить не даёт ошибки, но и смысла не имеет — важно не превратить это в 500 в
  логах.
- **`http.ListenAndServe` без `http.Server`.** Нет таймаутов чтения и записи и
  нет graceful shutdown: при выкате рвутся активные запросы.

## Возможные расширения

- **Кеш длин вместо кеша последовательностей.** Хранение `steps[n]` занимает
  единицы байт против килобайтов и позволяет держать на порядки больше ключей;
  подходит, если клиенту нужна длина, а не сама траектория.
- **Мемоизация хвостов.** Траектории сливаются: дойдя до уже посчитанного числа,
  можно приклеить готовый хвост вместо продолжения цикла. Это меняет сложность
  массового счёта, но требует кеша, устойчивого к частичным записям.
- **LRU с лимитом.** Ограничение по числу ключей или по суммарной длине,
  вытеснение по давности использования.
- **`singleflight`** для склейки одновременных запросов одного числа — вместе с
  отвязкой `context`, чтобы уход первого клиента не отменял работу остальных.
- **Ограничение параллелизма** пулом воркеров вместо goroutine на число, если
  верхнюю границу массива нельзя задать.
- **Дедупликация чисел** внутри запроса до запуска goroutine: `[27,27,27]` должно
  давать одно вычисление, а не три промаха мимо кеша.
- **Дедлайн на весь запрос** через `context.WithTimeout` поверх `r.Context()`,
  чтобы медленный клиент не удерживал вычисления бесконечно.
- **Метрики**: попадания и промахи кеша, размер кеша, длительность вычисления,
  доля запросов, отменённых клиентом.
- **Стриминг ответа** через `application/x-ndjson`: для тысячи чисел клиент
  получает результаты по мере готовности, а не одним большим телом.

## Interview-ready answer

**1. Что не так в исходном коде до всякой доработки?**

- Не компилируется — `collatz` принимает `int`, а вызывается со `[]int`.
- `log.Fatalf` в обработчике — битый JSON от любого клиента завершает процесс;
  это `400`, а не выход.
- Вечный цикл на `n <= 0` — `for n != 1` не заканчивается, `append` съедает
  память; нужна валидация `n >= 1`.
- Результат неверен — финальная `1` не попадает в срез, а `collatz(1)` возвращает
  пустой список.
- Нет ограничения тела, проверки метода, `Content-Type`, обработки ошибок
  маршалинга и таймаутов сервера.

**2. Пункты 1 и 3 условия противоречат друг другу — как быть?**

- Суть конфликта — пункт 1 требует последовательности для всех чисел, пункт 3
  требует погасить всё, кроме победителя.
- Решение — два эндпоинта, а не два режима одного: `POST /collatz` отдаёт массив
  результатов, `POST /collatz/first` — один объект. Формат ответа у них разный
  целиком, а ответ, форма которого зависит от поля запроса, вынуждает клиента
  разбирать объединение типов.
- Что это даёт помимо чистого контракта — раздельные метрики и лимиты, и
  возможность убрать недетерминированный эндпоинт, не трогая основной.
- Что сказать дополнительно — «первый завершившийся» недетерминирован, и если
  заказчику нужен стабильный ответ, критерий должен быть содержательным,
  например самая короткая последовательность.

**3. Как реализована остановка по первому завершившемуся?**

- Канал победителя с буфером 1 и отправка через `select` с `default`: место
  занимает ровно один, остальные сразу отбрасывают свой результат.
- Отмена — `context.WithCancel` и `defer cancel()`: проигравшие гасятся при
  выходе из обработчика, то есть когда результат уже забран.
- Почему `default` обязателен — иначе проигравшие блокируются на заполненном
  канале и не завершаются вовсе.
- Почему обработчик не ждёт проигравших — общего среза результатов у отдельного
  эндпоинта нет, поэтому ответ уходит сразу после появления победителя. В
  варианте с общим срезом пришлось бы делать `wg.Wait()`, и пункт 3 выполнялся бы
  наполовину: остальные останавливаются, но ответ всё равно ждёт их.
- Что нужно не забыть — канал не закрывать (отправители ещё живы, закрытие даёт
  панику) и добавить канал `done`, иначе `select` виснет, когда победителя не
  оказалось вовсе.

**4. Почему запись результатов в общий срез не требует мьютекса?**

- Срез создан до запуска goroutine и не меняет длину, каждая goroutine пишет в
  свой индекс — это разные адреса.
- Где появилась бы гонка — при росте среза через `append` или при чтении `items`
  до `wg.Wait()`.

**5. Как обеспечен конкурентный доступ к кешу?**

- `map` под `sync.RWMutex`: мьютекс держится только на операции с картой,
  вычисление идёт вне критической секции.
- Значение кладётся через `slices.Clip` — иначе `append` читателя запишет в общий
  массив и испортит кеш без единой явной записи.
- Ограничение решения — кеш неограниченно растёт и не переживает перезапуск;
  для продакшена нужен LRU с лимитом.

**6. Как обрабатывается уход клиента?**

- Источник сигнала — `r.Context()`, он отменяется и при разрыве соединения, и при
  отмене запроса; отдельной обработки этих случаев не требуется.
- Где сигнал читается — внутри цикла вычисления, раз в 1024 итерации; проверка на
  каждой итерации по замеру стоит около 65% времени и ничего не меняет по
  задержке реакции.
- Что делает обработчик — не пишет ответ ушедшему клиенту и логирует
  `context.Canceled` как обычное событие, а не как ошибку сервиса.

**7. Какие тесты обязательны?**

- Корректность ядра — `1`, чётное, нечётное, ноль и отрицательные, переполнение,
  отменённый `context`.
- Кеш — `append` читателя не портит сохранённое значение, повторный запрос не
  считает заново.
- Транспорт — невалидный вход даёт `400` и сервис остаётся живым, ушедший клиент
  не получает ответ.
- Конкурентность — параллельные запросы с дубликатами под `go test -race` с
  повторами; на что тест сознательно не смотрит, так это на личность победителя.
