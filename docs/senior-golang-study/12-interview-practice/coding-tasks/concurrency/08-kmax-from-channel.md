# Задача 8: K максимальных из канала (с отменой через context)

Стриминговый top-K поверх канала: читаем числа из `<-chan int`, держим K наибольших и умеем **прерваться** по `context`. Проверяет связку «каналы + context + heap» и понимание, что значит «прерываемая» функция.

## Формулировка

> «Напиши функцию, которая вычитывает числа из канала и находит K максимальных. Сделай так, чтобы её работу можно было прервать.»

```go
func Kmax(ctx context.Context, k int, input <-chan int) []int {}
```

Ключевое: вход — **канал** (поток неизвестной длины, может не закрыться), память должна быть **O(k)**, а не O(N), и функция обязана реагировать на отмену `ctx`.

---

## Уточняющие вопросы (signal seniority — спросить ДО кода)

1. **Что значит «прервать»? Что вернуть при отмене?**
   "По `ctx.Done()` прекращаем чтение и возвращаем top-K **из уже прочитанного** (частичный результат). Альтернатива — вернуть `nil`; уточнить у интервьюера."

2. **Когда функция вообще завершается?**
   "Два условия выхода: канал **закрыт** (прочитали всё) **или** `ctx` отменён. Если канал не закроют и отмены нет — функция висит, это by design стрима."

3. **Порядок результата?**
   "Обычно по убыванию (от большего к меньшему). Если не важен — можно отдать как есть."

4. **Элементов меньше K?**
   "Вернуть все, что были, отсортированными."

5. **Дубликаты, отрицательные?**
   "K максимальных **значений** с повторами (не уникальных). Отрицательные — штатно."

6. **k ≤ 0?**
   "Вернуть пустой результат."

---

## Идея: min-heap размера K

Чтобы держать **K максимальных**, используем **min-heap** (минимум наверху) ёмкости K:

- куча не заполнена (`len < k`) → просто кладём элемент;
- куча полна → сравниваем новый элемент с **минимумом** кучи (вершиной): если новый больше — **вытесняем** минимум; иначе пропускаем.

Так в куче всегда K крупнейших из виденного. Чтение из канала — через `select` с веткой `ctx.Done()`, чтобы отмена прерывала ожидание следующего значения.

```
input ──► select ┬─ <-input  ─► обновить min-heap (размера k)
                 └─ <-ctx.Done() ─► стоп, вернуть текущий top-K
```

- Время: **O(N log k)**, память: **O(k)**.
- Почему min-heap, а не max-heap: нам нужен быстрый доступ к **наименьшему из кандидатов**, чтобы решать, кого вытеснять.

## Решение

```go
package kmax

import (
	"container/heap"
	"context"
	"sort"
)

// min-heap по int: вершина — наименьший из текущих кандидатов.
type minHeap []int

func (h minHeap) Len() int           { return len(h) }
func (h minHeap) Less(i, j int) bool { return h[i] < h[j] }
func (h minHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *minHeap) Push(x any)        { *h = append(*h, x.(int)) }
func (h *minHeap) Pop() any {
	old := *h
	n := len(old)
	v := old[n-1]
	*h = old[:n-1]
	return v
}

func Kmax(ctx context.Context, k int, input <-chan int) []int {
	if k <= 0 {
		return nil
	}

	h := &minHeap{}
	heap.Init(h)

	consume := func(v int) {
		switch {
		case h.Len() < k: // куча не заполнена — кладём
			heap.Push(h, v)
		case v > (*h)[0]: // новый больше минимума — вытесняем минимум
			(*h)[0] = v
			heap.Fix(h, 0) // восстановить инвариант после замены вершины
		}
	}

loop:
	for {
		select {
		case <-ctx.Done(): // отмена — выходим с тем, что накопили
			break loop
		case v, ok := <-input:
			if !ok { // канал закрыт — прочитали всё
				break loop
			}
			consume(v)
		}
	}

	// выгружаем кучу и сортируем по убыванию
	res := make([]int, h.Len())
	copy(res, *h)
	sort.Sort(sort.Reverse(sort.IntSlice(res)))
	return res
}
```

Почему так:
- `select` с `ctx.Done()` — единственный корректный способ «прервать» блокирующее чтение из канала; без него `<-input` повис бы до закрытия канала, игнорируя отмену.
- `heap.Fix(h, 0)` после замены вершины дешевле, чем `Pop`+`Push` (один просев вместо двух).
- При отмене возвращаем **частичный** top-K — это и есть смысл «прерываемой» функции (а не потеря всей работы).

## Замечания для production / на что обратить внимание

| Вопрос | Ответ |
|---|---|
| **Что при `select`, если готовы оба case?** | Go выбирает случайный. Это ок: при отмене мы всё равно скоро выйдем; одно «лишнее» прочитанное значение погоды не делает. Если важно гарантированно реагировать на отмену — проверять `ctx.Err()` отдельно. |
| **Память** | Строго O(k): размер кучи не превышает `k`, входной поток не материализуется. |
| **Возврат через канал?** | Если результат нужен асинхронно — обернуть в горутину и отдать `<-chan []int`; сигнатура задачи синхронная. |
| **Несколько источников** | Fan-in нескольких каналов в один (см. fan-in) перед `Kmax`, либо `reflect.Select`/доп. ветки. |
| **Generics** | Легко обобщить до `Kmax[T cmp.Ordered]` (Go 1.21+) — тип-параметр вместо `int`. |

## Тесты

```go
func TestKmax_ClosedChannel(t *testing.T) {
	in := make(chan int)
	go func() {
		defer close(in)
		for _, v := range []int{3, 1, 9, 7, 2, 8, 5} {
			in <- v
		}
	}()

	got := Kmax(context.Background(), 3, in)
	want := []int{9, 8, 7}
	if !slices.Equal(got, want) {
		t.Fatalf("got %v, want %v", got, want)
	}
}

func TestKmax_Cancel(t *testing.T) {
	in := make(chan int) // никто не закрывает
	go func() {
		for i := 0; ; i++ {
			in <- i
		}
	}()

	ctx, cancel := context.WithCancel(context.Background())
	go func() { time.Sleep(20 * time.Millisecond); cancel() }()

	got := Kmax(ctx, 5, in) // должна вернуться по отмене, не зависнуть
	if len(got) > 5 {
		t.Fatalf("len(got)=%d, want <= 5", len(got))
	}
	if !sort.SliceIsSorted(got, func(i, j int) bool { return got[i] > got[j] }) {
		t.Fatalf("result must be sorted desc: %v", got)
	}
}

func TestKmax_FewerThanK(t *testing.T) {
	in := make(chan int)
	go func() { defer close(in); in <- 5; in <- 1 }()
	got := Kmax(context.Background(), 10, in)
	if !slices.Equal(got, []int{5, 1}) {
		t.Fatalf("got %v", got)
	}
}
```

Главный тест — **TestKmax_Cancel**: канал бесконечный и не закрывается, и без реакции на `ctx` функция зависла бы. Он доказывает, что прерывание работает.

## Подводные камни

- **`<-input` без `select` на `ctx.Done()`** — функция перестаёт быть прерываемой и виснет на незакрытом канале. Главная ошибка задачи.
- **max-heap вместо min-heap** — тогда непонятно, кого вытеснять; для top-K нужен быстрый доступ к **минимуму** кандидатов → min-heap.
- **Хранить все элементы и сортировать в конце** — O(N) памяти вместо O(k); на «потоке» это провал (а поток может быть бесконечным — конца сортировки не будет вовсе).
- **Забыть `heap.Fix` после замены вершины** — куча перестаёт быть кучей, ответы становятся неверными.
- **Не обработать `k <= 0` и «элементов меньше k»** — частые пропущенные edge cases.
- **Паника при отправке в закрытый/возврате nil** — аккуратно с `ok` при `v, ok := <-input`.

---

## Возможные расширения

- **Generics**: `func Kmax[T cmp.Ordered](ctx, k, <-chan T) []T`.
- **K минимальных / top-K по частоте**: max-heap, либо предварительный подсчёт в map.
- **Несколько входных каналов** (fan-in) и/или несколько воркеров с последующим слиянием частичных top-K.
- **Тайм-аут вместо ручной отмены**: `context.WithTimeout`.
- **Возврат прогресса**: периодически отдавать текущий top-K в out-канал.
