Формулировка задачи, как её обычно дают:

```go
// Backend — дано в задании.
type Backend interface {
    Send(request Request) (Response, error)
}

// NewBackend — дано, реализация где-то ещё.
func NewBackend(addr string) Backend
```

1. Реализовать тип `Balancer`, который сам реализует `Backend` и распределяет
   запросы между экземплярами микросервиса, каждый раз выбирая наименее
   нагруженный.
2. После `n` ошибок исключать сбойный бэкенд из ротации на `k` секунд, затем
   возвращать обратно.
3. Какие структуры данных позволят быстро выбирать наименее загруженный бэкенд
   при сотнях тысяч бэкендов.
4. Что произойдёт, если много запросов уйдёт одновременно и все завершатся
   по timeout.

Частое продолжение, которого нет в исходной формулировке: что менять, если
реплик самого балансировщика несколько — оно разобрано
[отдельным этапом](#этап-5-несколько-реплик-балансировщика).

Задача рассчитана примерно на 30 минут, и только первые два пункта требуют кода.
Разумное распределение времени: 3–5 минут на уточняющие вопросы, 10 минут на
первый этап, 10 минут на второй, остальное — обсуждение пунктов 3 и 4 словами.
Писать сразу «production-grade» вариант с классификацией ошибок, окнами
статистики и slow start здесь вредно: это съедает время и уводит от того, что
на самом деле проверяют — корректности конкурентного кода.

## Контракт задачи

Три вопроса, которые стоит задать до кода:

1. **Что значит «нагруженный»?** Из данного интерфейса доступен ровно один
   сигнал — число собственных незавершённых запросов к экземпляру (in-flight).
   Latency или CPU потребовали бы health-канала или расширения `Response`.
   Дальше нагрузкой считается in-flight: этот счётчик естественно учитывает и
   медленные ответы, и разную мощность экземпляров.
2. **Send блокирующий, есть ли внутри timeout?** В сигнатуре нет
   `context.Context`, отменить вызов нельзя. Счётчик нагрузки удерживается
   ровно столько, сколько живёт `Send`, — это понадобится в четвёртом пункте.
3. **Состав пула статический?** Если да, список фиксируется в конструкторе и
   код заметно упрощается. Service discovery — отдельная задача про атомарную
   подмену списка.

## Этап 1. Выбор наименее нагруженного

Главная тонкость не в поиске минимума, а в том, что **выбор и увеличение
счётчика должны быть одной атомарной операцией**. Если сначала прочитать
счётчики, а потом увеличить выбранный, десятки одновременных goroutine увидят
один и тот же «наименее нагруженный» экземпляр и уйдут на него все сразу.
Балансировщик получит ровно тот перекос, который должен устранять.

```go
package balancer

import (
    "errors"
    "sync"
)

var ErrNoBackends = errors.New("balancer: no backends configured")

type instance struct {
    backend  Backend
    addr     string
    inflight int
}

type Balancer struct {
    mu        sync.Mutex
    instances []*instance
}

func New(addrs []string) (*Balancer, error) {
    if len(addrs) == 0 {
        return nil, ErrNoBackends
    }

    b := &Balancer{instances: make([]*instance, 0, len(addrs))}
    for _, addr := range addrs {
        b.instances = append(b.instances, &instance{
            backend: NewBackend(addr),
            addr:    addr,
        })
    }

    return b, nil
}

func (b *Balancer) Send(request Request) (Response, error) {
    inst := b.acquire()
    defer b.release(inst)

    return inst.backend.Send(request)
}

func (b *Balancer) acquire() *instance {
    b.mu.Lock()
    defer b.mu.Unlock()

    best := b.instances[0]
    for _, inst := range b.instances[1:] {
        if inst.inflight < best.inflight {
            best = inst
        }
    }

    best.inflight++
    return best
}

func (b *Balancer) release(inst *instance) {
    b.mu.Lock()
    defer b.mu.Unlock()

    inst.inflight--
}

var _ Backend = (*Balancer)(nil)
```

Что стоит проговорить вслух:

- **Единая критическая секция —** `acquire` под одним mutex находит минимум и
  сразу резервирует слот. Атомарные счётчики на каждом экземпляре такой
  гарантии не дают: между чтением всех счётчиков и инкрементом выбранного
  всегда остаётся окно.
- **`defer` для release —** счётчик уменьшается и при ошибке, и при панике в
  `Send`. Без `defer` один паникующий вызов навсегда завышает нагрузку
  экземпляра, и балансировщик перестаёт его выбирать.
- **Проверка пустого пула — в конструкторе,** а не на горячем пути: после
  создания список не меняется.
- **`var _ Backend = (*Balancer)(nil)`** фиксирует требование задачи:
  балансировщик сам является `Backend`, и его можно вложить в другой
  балансировщик (например, слой «по зонам» над слоем «по экземплярам»).

**Чего этот вариант не делает.** In-flight — метрика загрузки, а не здоровья.
Экземпляр, который мгновенно отвечает `500`, выглядит наименее нагруженным и
получает **больше** трафика, чем здоровые. Это и есть переход к этапу 2.

## Этап 2. Исключение сбойного бэкенда

Добавляется два поля на экземпляр: счётчик подряд идущих ошибок и время, до
которого экземпляр не участвует в выборе.

```go
var ErrNoHealthy = errors.New("balancer: no healthy backends")

type instance struct {
    backend  Backend
    addr     string
    inflight int

    failures      int
    disabledUntil time.Time
}

type Balancer struct {
    maxFailures int           // n из условия
    ejectFor    time.Duration // k из условия

    mu        sync.Mutex
    instances []*instance
}

func (b *Balancer) Send(request Request) (_ Response, err error) {
    inst, err := b.acquire()
    if err != nil {
        return Response{}, err
    }
    defer func() { b.release(inst, err) }()

    return inst.backend.Send(request)
}

func (b *Balancer) acquire() (*instance, error) {
    b.mu.Lock()
    defer b.mu.Unlock()

    now := time.Now()

    var best *instance
    for _, inst := range b.instances {
        if now.Before(inst.disabledUntil) {
            continue
        }
        if best == nil || inst.inflight < best.inflight {
            best = inst
        }
    }

    if best == nil {
        return nil, ErrNoHealthy
    }

    best.inflight++
    return best, nil
}

func (b *Balancer) release(inst *instance, err error) {
    b.mu.Lock()
    defer b.mu.Unlock()

    inst.inflight--

    if err == nil {
        inst.failures = 0
        return
    }

    inst.failures++
    if inst.failures >= b.maxFailures {
        inst.failures = 0
        inst.disabledUntil = time.Now().Add(b.ejectFor)
    }
}
```

Ключевые решения:

- **Возврат ленивый, без фоновой goroutine.** Экземпляр возвращается сам, как
  только `time.Now()` обгоняет `disabledUntil`. У балансировщика не появляется
  lifecycle: нечего останавливать, нечему течь. Вариант с `time.AfterFunc` на
  каждое исключение работает, но добавляет таймеры, которые надо гасить в
  `Close`.
- **Именованный результат + `defer`.** `release` должен знать исход вызова,
  поэтому `err` объявлен в списке результатов: отложенная функция читает уже
  присвоенное значение. Это сохраняет корректность счётчика при любом выходе
  из `Send`.
- **Счётчик — подряд идущие ошибки,** любой успех его обнуляет. Это буквальное
  прочтение условия «после n ошибок». Ограничение стоит назвать самому: при
  30% ошибок серия из `n` подряд собирается редко, поэтому частичная
  деградация так не ловится.
- **`ErrNoHealthy`, когда исключены все.** Честное поведение для учебной
  версии, но именно оно ломается в четвёртом пункте.

## Этап 3. Сотни тысяч бэкендов

Линейный перебор — `O(n)` на каждый запрос. При `n = 200 000` это не работает,
и напрашивающийся ответ — **min-heap по числу in-flight**.

В Go куча берётся из пакета `container/heap`. Важно, что это не готовая
структура данных, а набор алгоритмов поверх собственного среза: пакет требует
реализовать интерфейс `heap.Interface`, то есть `sort.Interface`
(`Len`, `Less`, `Swap`) плюс `Push` и `Pop`. Ниже этот интерфейс реализует тип
`loadHeap` — срез указателей на экземпляры; сам срез лежит в поле
`HeapBalancer.ready`, и все вызовы `heap.*` работают именно с ним.

```go
import "container/heap"

type item struct {
    backend  Backend
    inflight int
    index    int // позиция элемента в срезе ready; -1, если элемент вне кучи
}

// loadHeap реализует heap.Interface: Len/Less/Swap + Push/Pop.
type loadHeap []*item

func (h loadHeap) Len() int           { return len(h) }
func (h loadHeap) Less(i, j int) bool { return h[i].inflight < h[j].inflight }

func (h loadHeap) Swap(i, j int) {
    h[i], h[j] = h[j], h[i]
    h[i].index = i
    h[j].index = j
}

func (h *loadHeap) Push(x any) {
    it := x.(*item)
    it.index = len(*h)
    *h = append(*h, it)
}

func (h *loadHeap) Pop() any {
    old := *h
    n := len(old)
    it := old[n-1]
    old[n-1] = nil
    it.index = -1
    *h = old[:n-1]
    return it
}

type HeapBalancer struct {
    mu    sync.Mutex
    ready loadHeap // бэкенды в ротации, минимум по inflight — в корне
}

func NewHeapBalancer(addrs []string) *HeapBalancer {
    b := &HeapBalancer{}
    for _, addr := range addrs {
        heap.Push(&b.ready, &item{backend: NewBackend(addr)})
    }
    return b
}

func (b *HeapBalancer) acquire() *item {
    b.mu.Lock()
    defer b.mu.Unlock()

    it := b.ready[0] // минимум всегда в корне
    it.inflight++
    heap.Fix(&b.ready, 0) // ключ вырос: просеять вниз, O(log n)

    return it
}

func (b *HeapBalancer) release(it *item) {
    b.mu.Lock()
    defer b.mu.Unlock()

    it.inflight--
    if it.index >= 0 {
        heap.Fix(&b.ready, it.index) // ключ уменьшился: просеять вверх
    }
}

// Исключение и возврат из этапа 2 становятся операциями над кучей.
func (b *HeapBalancer) eject(it *item) {
    b.mu.Lock()
    defer b.mu.Unlock()

    if it.index >= 0 {
        heap.Remove(&b.ready, it.index) // Pop выставит index = -1
    }
}

func (b *HeapBalancer) restore(it *item) {
    b.mu.Lock()
    defer b.mu.Unlock()

    if it.index < 0 {
        heap.Push(&b.ready, it)
    }
}
```

Что здесь делают функции пакета:

| Вызов | Что делает | Сложность |
|---|---|---|
| `heap.Push(&h, x)` | вызывает метод `h.Push`, затем просеивает новый элемент вверх | `O(log n)` |
| `heap.Fix(&h, i)` | восстанавливает инвариант после изменения ключа элемента на позиции `i` | `O(log n)` |
| `heap.Remove(&h, i)` | меняет элемент `i` с последним, вызывает метод `h.Pop`, чинит кучу | `O(log n)` |
| `h[0]` | минимум, без всякого вызова | `O(1)` |

Методы `Push`/`Pop` у типа — низкоуровневые: они только добавляют и снимают
последний элемент среза, а просеиванием занимаются одноимённые функции пакета.
Вызывать их напрямую нельзя, они существуют для `container/heap`. Здесь они
нужны ради `heap.Remove` и `heap.Push`, то есть ради исключения и возврата
бэкенда; на горячем пути работают только `ready[0]` и `heap.Fix`.

Детали, которые обычно и проверяют этим вопросом:

- **Поле `index` обязательно.** Без него `release` не знает, где лежит элемент,
  и ищет его за `O(n)` — вся выгода пропадает. Поддерживать `index` обязан
  `Swap`: куча переставляет элементы при каждом просеивании.
- **Не `Pop` + `Push`, а `heap.Fix`.** Элемент остаётся в куче, меняется только
  ключ; `Fix` просеивает его вверх или вниз без аллокаций.
- **Исключённые экземпляры нельзя оставлять в куче.** У кучи нет операции
  «пропустить минимум»: исключённый экземпляр с `inflight = 0` навсегда
  застревает в корне. Отсюда `eject`/`restore` через `heap.Remove` и
  `heap.Push` и проверка `index >= 0` в `release` — запрос может завершиться
  уже после того, как бэкенд вынули из ротации.
- **`Less` задаёт tie-breaking.** При равных `inflight` порядок в куче
  произвольный — это заодно убирает перекос в начало списка, который есть у
  линейного перебора при полностью простаивающем пуле.

Дальше стоит добавить два замечания, которые показывают понимание масштаба:

**Куча не убирает contention.** Каждый запрос по-прежнему дважды берёт один
глобальный mutex. На сотнях тысяч RPS узкое место — сам mutex, а не `log n`
сравнений. Хуже того, при нескольких репликах балансировщика все они видят один
и тот же «наименее нагруженный» экземпляр и отправляют трафик туда
одновременно — точное знание минимума в распределённой системе балансирует
**хуже** случайного выбора.

**Практический ответ — power of two choices:** взять два случайных экземпляра и
выбрать менее нагруженный.

```go
type node struct {
    backend  Backend
    inflight atomic.Int64
}

func (b *P2C) pick() *node {
    n := len(b.instances)
    if n == 1 {
        return b.instances[0]
    }

    i := rand.IntN(n)     // math/rand/v2
    j := rand.IntN(n - 1)
    if j >= i {
        j++               // гарантирует j != i без цикла повторов
    }

    a, c := b.instances[i], b.instances[j]
    if c.inflight.Load() < a.inflight.Load() {
        return c
    }

    return a
}

func (b *P2C) Send(request Request) (Response, error) {
    inst := b.pick()

    inst.inflight.Add(1)
    defer inst.inflight.Add(-1)

    return inst.backend.Send(request)
}
```

Это `O(1)`, без общей структуры и без mutex (счётчики — `atomic.Int64`). Гонка
между чтением счётчиков и инкрементом остаётся, но она безвредна: это оценка, а
не инвариант. Известный результат «the power of two choices» говорит, что
максимальная загрузка падает с `Θ(log n / log log n)` при случайном выборе до
`Θ(log log n)` при выборе из двух, то есть почти вся выгода точного минимума
достигается двумя пробами. Так работает `LEAST_REQUEST` в Envoy.

| Подход | Выбор | Замечание |
|---|---|---|
| линейный перебор | `O(n)` | нормально до сотен бэкендов |
| min-heap + mutex | `O(log n)` | глобальный mutex остаётся узким местом |
| power of two choices | `O(1)` | без общего состояния, устойчив к herd behaviour |
| subsetting | по размеру подмножества | одна реплика держит 20–100 бэкендов из 200k |

## Этап 4. Массовый timeout

Ломается не одно место, а цепочка.

**1. Метрика загрузки вырождается.** Timeout удерживает `inflight` весь свой
срок. Быстро счётчики всех экземпляров становятся одинаково большими, различий
между ними нет, и least-loaded вырождается в «первый по списку». Балансировщик
перестаёт выполнять свою функцию ровно тогда, когда она нужнее всего.

**2. Число одновременных запросов растёт кратно.** По закону Литтла
`L = λ × W`: при 5000 RPS и нормальных 20 мс в системе живёт 100 запросов, при
timeout в 5 секунд — 25 000. Каждый удерживает goroutine, соединение и буферы.
Практически это исчерпание пула соединений, рост RSS, давление на GC и рост
latency уже у здоровых запросов.

**3. Пул исключается целиком.** Timeout — это ошибка, счётчики растут
одновременно на всех экземплярах, все уходят в ejection, и балансировщик из
кода выше начинает отвечать `ErrNoHealthy`. Частичная деградация превращается в
полный отказ — притом что бэкенды, возможно, живы и просто перегружены.

**4. Возврат синхронизирован.** Все исключены примерно в одну секунду — значит,
все вернутся примерно в одну секунду и получат накопившийся трафик разом.
Система входит в автоколебания: работает — падает — восстанавливается — падает.

**5. Работа выполняется впустую.** Вызывающая сторона уже отвалилась по
собственному timeout, а запрос всё ещё занимает соединение и учитывается в
нагрузке, и бэкенд всё ещё его обрабатывает. Система работает на полной
утилизации с нулевым полезным результатом.

**6. Интерфейс не позволяет это починить.** `Send(Request) (Response, error)`
не принимает `context.Context`, поэтому нельзя ни передать deadline вниз, ни
отменить вызов, ни отбросить на входе запрос с истёкшим сроком. Обёртка вида
«запустить `Send` в goroutine и ждать `time.After`» проблему не решает: вызов
продолжает выполняться, goroutine и соединение остаются занятыми, а `inflight`
пришлось бы уменьшить раньше времени — то есть соврать балансировщику о
реальной нагрузке. Это стоит назвать прямо: первое исправление — добавить
`context.Context` в контракт.

**Что делает поведение приемлемым:**

| Механизм | Что ограничивает |
|---|---|
| лимит `inflight` на экземпляр и быстрый отказ при его достижении | рост `L = λ × W`, исчерпание соединений |
| deadline propagation, отбрасывание истёкших запросов на входе | бесполезную работу |
| запрет исключать больше доли пула (panic threshold) | превращение деградации в полный отказ |
| jitter в длительности исключения | синхронный возврат и автоколебания |
| retry budget вместо ретраев на каждый запрос | умножение нагрузки во время инцидента |

Смысловой вывод: при массовом timeout задача балансировщика не «найти, кому
отдать запрос», а **не принимать запросы, которые всё равно не будут
обслужены**. Балансировка распределяет нагрузку; ограничивают её
[backpressure и shedding](../../../05-system-design/reliability-patterns/05-backpressure-and-shedding.md).

## Этап 5. Несколько реплик балансировщика

Вопрос-продолжение: что нужно поменять, чтобы этот балансировщик работал, когда
его самого запущено несколько экземпляров — по одному в каждом поде клиента или
несколько реплик отдельного сервиса.

Весь код выше опирается на одно допущение: `inflight` — это полное знание о
нагрузке. Оно верно ровно до тех пор, пока балансировщик один. При `R` репликах
каждая видит только свои запросы, то есть примерно `1/R` реальной нагрузки на
бэкенд, и ни одна не знает про остальных.

**Что именно ломается:**

1. **Локальная оценка вместо реальной.** Настоящая нагрузка бэкенда — сумма по
   всем репликам плюс любые другие клиенты. Реплика оптимизирует величину,
   которую наблюдает лишь частично.
2. **Herd behaviour.** Реплики одинаковы и детерминированы: увидев похожую
   картину, все выбирают один и тот же «наименее нагруженный» экземпляр и
   отправляют трафик туда одновременно. Именно точность правила делает эффект
   сильнее — согласованный выбор минимума синхронизирует реплики, тогда как
   случайный не синхронизирует ничего.
3. **Health-состояние тоже локальное.** Чтобы весь парк перестал слать запросы
   на сбойный экземпляр, каждая из `R` реплик должна независимо набрать свои `n`
   ошибок — то есть суммарно `n × R` неудачных запросов. Исключат они его в
   разные моменты и вернут тоже в разные.

Первое, что стоит проговорить: локальность — не только недостаток. Реплика,
у которой сетевая проблема именно с этим экземпляром, обязана исключить его
сама, а остальные не должны. Общее health-состояние такую ситуацию как раз
портит. И оценка `inflight` не бесполезна: если upstream раскидывает трафик по
репликам равномерно, локальный счётчик пропорционален глобальному, а для
сравнения бэкендов между собой важна именно пропорция, а не абсолют.

**Варианты решения:**

| Подход | Что даёт | Чем платим |
|---|---|---|
| P2C вместо точного минимума | случайность ломает синхронизацию реплик, состояние остаётся локальным | оценка вместо точного минимума |
| subsetting | реплики целятся в разные подмножества бэкендов, пересечений меньше | нужен детерминированный алгоритм разбиения и ребалансировка при смене состава |
| нагрузка в ответе бэкенда | нагрузка становится глобальной, а не локальной | требует расширить `Response`, данные всегда немного устаревшие |
| общее состояние в Redis | точный глобальный `inflight` | сетевой вызов на каждый `acquire`/`release`, новый SPOF |
| выделенный балансирующий слой | одно место принятия решения | этот слой сам нужно масштабировать — задача возвращается на уровень выше |

Практический ответ — комбинация первых трёх, и приоритет именно такой:

- **Сменить алгоритм выбора на power of two choices.** Это единственное
  изменение, которое ничего не требует от инфраструктуры: две случайные пробы
  вместо перебора. Рандомизация убирает herd behaviour, потому что реплики
  перестают быть согласованными, а качество балансировки почти не падает
  (см. [этап 3](#этап-3-сотни-тысяч-бэкендов)). По той же причине это
  поведение по умолчанию у боевых балансировщиков.
- **Добавить subsetting.** Каждая реплика работает не со всем пулом, а с
  детерминированно выбранным подмножеством: пересечение выборов между репликами
  падает, а заодно сокращается число соединений на бэкенд. Разбиение должно
  быть устойчивым к добавлению и удалению экземпляров, иначе каждое изменение
  состава переставляет соединения у всех.
- **Передавать нагрузку от бэкенда.** Если можно расширить `Response`,
  экземпляр сам сообщает свою длину очереди или утилизацию. Тогда все реплики
  оценивают одну и ту же величину — фактическую нагрузку бэкенда, а не свою
  долю в ней. Так устроены ORCA в gRPC и Envoy: сервер отдаёт стоимость запроса
  и загрузку, клиент по ним взвешивает выбор.

**Чего делать не стоит.** Общий `inflight` в Redis выглядит прямым решением, но
добавляет сетевой round-trip на каждый `acquire` и `release`: балансировка
начинает стоить дороже, чем экономит, и появляется зависимость, отказ которой
кладёт весь трафик. Точное глобальное состояние здесь не нужно — данные
устаревают за миллисекунды, и решение всё равно принимается по оценке.

**Что общее состояние действительно улучшает — это health, а не нагрузка.**
Нагрузка меняется на масштабе запроса, здоровье — на масштабе секунд и десятков
секунд, поэтому его выгодно вычислять один раз и раздавать. Так и делают:
active health checking или агрегированный outlier detection живёт в control
plane, оттуда приходит список живых endpoint-ов, а решение «кому отдать этот
конкретный запрос» остаётся локальным. Разделение полезно назвать явно: общий —
медленно меняющийся health, локальный — быстро меняющаяся нагрузка.

## Что сказать, если спросят дальше

Всё перечисленное ниже — то, что отличает учебную версию от боевой. В коде за
30 минут этого быть не должно, но назвать вслух полезно: это показывает, что
упрощения сделаны осознанно.

- **Классификация ошибок.** Не всякая ошибка говорит о здоровье экземпляра:
  `404`, доменная ошибка валидации и отмена вызывающим не должны его
  исключать. В боевой версии появляется предикат «считать ли это failure».
- **Окно вместо серии.** Подряд идущие ошибки плохо ловят частичную
  деградацию. Обычно считают долю ошибок в скользящем окне и применяют порог
  только после минимального числа запросов, иначе на низком трафике две
  ошибки исключат здоровый экземпляр.
- **Предел на число исключённых.** Если сбой общий (упала БД, к которой ходят
  все экземпляры), исключать пул бессмысленно — проблема не в выборе
  экземпляра. Envoy в этой ситуации отключает outlier detection целиком; ту же
  роль играет правило «не исключать больше половины пула».
- **Растущее наказание и jitter.** Экземпляр, падающий сразу после возврата,
  исключается на `2k`, `3k`, … до потолка; случайная добавка к длительности
  разводит возвраты по времени.
- **Разогрев после возврата.** Проблема, специфичная именно для least-loaded: у
  вернувшегося экземпляра `inflight = 0`, поэтому правило «наименее
  нагруженный» отдаёт ему **весь** трафик и роняет повторно. Лечится
  ограничением числа одновременных запросов в окне после возврата (аналог
  `half-open` у circuit breaker) или постепенным набором веса (slow start).
- **Ретрай на другом экземпляре.** Допустим только для идемпотентных операций,
  с ограничением числа попыток и общим retry budget.
- **Метрики.** `inflight` и число ошибок с label по адресу экземпляра
  (адреса ограничены — безопасная cardinality), события исключения и возврата,
  распределение запросов по экземплярам: перекос виден только на нём.

По сути этап 2 — это circuit breaker на каждый экземпляр плюс защита уровня
пула; в терминах Envoy — passive health checking, он же outlier detection.
Отличие от отдельного [circuit breaker](./03-circuit-breaker.md)
принципиальное: у балансировщика есть альтернатива, поэтому отключение одного
экземпляра — не отказ, а перераспределение.

## Тестирование

Что проверять (первые четыре пункта успевают спросить чаще всего):

1. при равной нагрузке запросы расходятся по всем экземплярам;
2. `inflight` возвращается к нулю после ошибки и после паники в `Send`;
3. после `n` подряд ошибок экземпляр не получает запросов, после `k` — снова
   получает;
4. успех между ошибками обнуляет счётчик;
5. когда исключены все, `Send` возвращает `ErrNoHealthy`;
6. `go test -race` при сотнях параллельных `Send`.

Тест на инвариант счётчиков ловит большинство ошибок с `defer` и ранними
`return`:

```go
func TestConcurrentSendKeepsCountersConsistent(t *testing.T) {
    b, _ := newTestBalancer(8, 3, time.Hour)

    var wg sync.WaitGroup
    for i := 0; i < 200; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            _, _ = b.Send(Request{})
        }()
    }
    wg.Wait()

    for i, inst := range b.instances {
        if inst.inflight != 0 {
            t.Fatalf("instance %d leaked inflight=%d", i, inst.inflight)
        }
    }
}
```

Если тест на возврат экземпляра пишется с `time.Sleep`, он либо медленный, либо
flaky. В боевом коде `time.Now` выносят в поле структуры и подменяют в тесте;
для интервью достаточно назвать это вслух.

## Типичные ошибки

- Читать счётчики и увеличивать выбранный вне одной критической секции — весь
  параллельный пик уходит на один экземпляр.
- Уменьшать `inflight` не через `defer` — паника или ранний `return` навсегда
  выводят экземпляр из ротации.
- Забыть, что `release` должен видеть исход вызова: без именованного результата
  отложенная функция получит не ту ошибку.
- Запускать фоновую goroutine или таймер на возврат экземпляра там, где хватает
  ленивой проверки времени при выборе.
- Не обработать случай «исключены все» — `nil`-разыменование вместо ошибки.
- Считать, что min-heap решает проблему масштаба: он снимает `O(n)`, но не
  contention на глобальном mutex и не herd behaviour между репликами.
- Забыть `index` в элементе кучи или не поддерживать его в `Swap`.
- Оставлять исключённый экземпляр в куче с нулевой нагрузкой — он навсегда
  занимает корень.
- Эмулировать timeout обёрткой с `time.After` поверх `Send`: вызов не
  прекращается, а учёт нагрузки становится неверным.

## Interview-ready answer

1. **Как выбирается наименее нагруженный?**
   - **Метрика —** число собственных in-flight запросов: единственный сигнал,
     доступный из данного интерфейса.
   - **Атомарность —** поиск минимума и резервирование слота выполняются под
     одним mutex, иначе весь пик уходит на один экземпляр.
   - **Освобождение —** только через `defer`, чтобы ошибка и паника не
     оставляли экземпляр «вечно занятым».

2. **Как устроено исключение сбойного?**
   - **Состояние —** счётчик подряд идущих ошибок и `disabledUntil` на каждый
     экземпляр; успех обнуляет счётчик.
   - **Возврат ленивый —** проверка времени при выборе, без фоновых goroutine и
     таймеров, поэтому у балансировщика нет lifecycle.
   - **Упрощения названы вслух —** серия вместо окна, любая ошибка как failure,
     отсутствие предела на число исключённых.

3. **Что делать при сотнях тысяч бэкендов?**
   - **Min-heap —** `O(log n)` через `heap.Fix`, с полем `index` в элементе и
     удалением исключённых из кучи.
   - **Ограничение —** куча не убирает глобальный mutex, а при нескольких
     репликах точный минимум создаёт herd behaviour.
   - **Практика —** power of two choices даёт `O(1)` без общего состояния и
     почти ту же равномерность; на масштабе поверх него идёт subsetting.

4. **Что произойдёт при массовом timeout?**
   - **Вырождение метрики —** `inflight` держится весь timeout, счётчики всех
     экземпляров сравниваются, балансировка перестаёт работать.
   - **Каскад —** `L = λ × W` растёт кратно, весь пул уходит в ejection,
     балансировщик отвечает «нет живых» и возвращает всех синхронно.
   - **Ответ —** ограничение `inflight` с быстрым отказом, deadline
     propagation, предел на долю исключённых, jitter, retry budget; сам
     интерфейс нужно расширить `context.Context`.

5. **Что менять при нескольких репликах балансировщика?**
   - **Проблема —** `inflight` локален, каждая реплика видит `1/R` нагрузки, и
     согласованный выбор точного минимума синхронизирует реплики на одном
     бэкенде.
   - **Решение —** P2C вместо перебора (рандомизация ломает herd behaviour),
     subsetting, а при возможности расширить `Response` — нагрузка,
     сообщаемая самим бэкендом.
   - **Разделение состояния —** общим делают медленно меняющийся health
     (control plane, active checks), локальной — быстро меняющуюся нагрузку;
     общий `inflight` в Redis добавляет round-trip на каждый запрос и новый
     SPOF.
