## Как работать с подборкой

Разбор задачи начинается с условия. До первой строки кода нужно проговорить:

1. контракт функции и допустимые входные данные;
2. поведение на пустом вводе и при нескольких правильных ответах;
3. базовый алгоритм и его сложность;
4. узкое место базового алгоритма;
5. оптимизацию и цену этой оптимизации.

Решения скрыты под `<details>`. В оценках ниже `n`, `m`, `u` и другие
обозначения поясняются отдельно для каждой задачи. Память результата не
считается дополнительной, если не сказано обратное.

## 1. Суммарная неудовлетворённость покупателей

На торговой площадке каждый товар представлен целым числом. Потребность
покупателя также выражена целым числом. Покупатель выбирает товар с ближайшим
значением, а его неудовлетворённость равна модулю разницы между потребностью и
значением товара.

Количество экземпляров каждого товара не ограничено: один товар могут выбрать
несколько покупателей.

Нужно написать функцию, которая принимает массив товаров и массив потребностей
и возвращает суммарную неудовлетворённость.

```text
goods = [8, 3, 5]
needs = [5, 6]

result = 1
```

Для потребности `5` есть точное совпадение, а для `6` ближайшим оказывается
товар `5`; минимальная разница равна `1`.

<details>
<summary>Решение</summary>

### Неоптимальный подход: полный перебор

Для каждой потребности перебираем все товары и запоминаем минимальную разницу.

- время: `O(b * g)`, где `b` — число покупателей, `g` — число товаров;
- дополнительная память: `O(1)`.

Подход приемлем для маленьких массивов, но повторно просматривает один и тот же
список товаров.

### Оптимальный подход: сортировка и бинарный поиск

Сортируем товары. Для каждой потребности бинарным поиском находим первый товар,
который не меньше потребности. Ближайшим может быть только он или предыдущий
товар.

```go
func TotalDissatisfaction(goods, needs []int) int {
	if len(goods) == 0 {
		return 0
	}

	sort.Ints(goods)

	total := 0
	for _, need := range needs {
		index := sort.SearchInts(goods, need)

		// Потребность меньше всех товаров.
		if index == 0 {
			total += goods[0] - need
			continue
		}

		// Потребность больше всех товаров.
		if index == len(goods) {
			total += need - goods[len(goods)-1]
			continue
		}

		// Ближайший товар находится слева или справа от точки вставки.
		leftDifference := need - goods[index-1]
		rightDifference := goods[index] - need

		if leftDifference < rightDifference {
			total += leftDifference
		} else {
			total += rightDifference
		}
	}

	return total
}
```

- время: `O(g log g + b log g)`;
- дополнительная память: `O(log g)` на стек сортировки.

Функция сортирует `goods` на месте. Если вход нельзя изменять, перед сортировкой
нужно сделать копию за `O(g)` памяти. Для пустого списка товаров в реальном API
лучше вернуть ошибку; здесь для краткости возвращается `0`.

</details>

## 2. Чемпионы соревнования по шагам

Компания проводит соревнование по шагам. Статистика хранится по дням. Нужно
найти участников, которые:

1. присутствуют в статистике каждого дня;
2. набрали максимальную сумму шагов за всё соревнование.

```text
statistics = [
  [{userID: 1, steps: 1000}, {userID: 2, steps: 1500}],
  [{userID: 2, steps: 1000}]
]

champions = {userIDs: [2], steps: 2500}
```

Если несколько участников набрали одинаковый максимум, вернуть их всех.
Считаем, что в одном дне каждый `userID` встречается не более одного раза.

<details>
<summary>Решение</summary>

### Неоптимальный подход: отдельная проверка каждого участника

Собираем все идентификаторы, а затем для каждого участника просматриваем каждый
день и ищем его запись линейным проходом.

- время в худшем случае: `O(u * r)`, где `u` — число уникальных участников,
  `r` — общее число записей;
- дополнительная память: `O(u)`.

### Оптимальный подход: один проход по записям

Для каждого участника храним сумму шагов и число дней, в которых он появился.
После прохода рассматриваем только записи с `days == len(statistics)`.

```go
type DayResult struct {
	UserID int
	Steps  int
}

type Champions struct {
	UserIDs []int
	Steps   int
}

type participantTotal struct {
	steps int
	days  int
}

func FindChampions(statistics [][]DayResult) Champions {
	if len(statistics) == 0 {
		return Champions{}
	}

	totals := make(map[int]participantTotal)
	for _, day := range statistics {
		for _, result := range day {
			total := totals[result.UserID]
			total.steps += result.Steps
			total.days++
			totals[result.UserID] = total
		}
	}

	var champions Champions
	found := false

	for userID, total := range totals {
		if total.days != len(statistics) {
			continue
		}

		switch {
		case !found || total.steps > champions.Steps:
			found = true
			champions.Steps = total.steps
			champions.UserIDs = []int{userID}
		case total.steps == champions.Steps:
			champions.UserIDs = append(champions.UserIDs, userID)
		}
	}

	return champions
}
```

- ожидаемое время: `O(r + u)` благодаря hash map;
- дополнительная память: `O(u)`.

Максимум ищется через флаг `found`, а не через стартовое значение вроде `-1`.
Число-сторож молча закладывается на неотрицательность шагов и ломается, если
контракт допустит отрицательные или скорректированные значения. Если чемпионов
нет, возвращается нулевая структура.

Порядок `UserIDs` не определён из-за обхода map. Если контракт требует
стабильный порядок, идентификаторы нужно отсортировать за `O(c log c)`, где
`c` — число чемпионов.

</details>

## 3. Отпуск с минимальным числом пропущенных встреч

Нужно выбрать первый день отпуска `X` длиной `V` календарных дней так, чтобы
весь отпуск попал в ближайшие `P` дней и пересёк как можно меньше встреч.
Завтра считается днём `1`.

Дни со встречами отсортированы:

```text
daysWithMeetings = [
  {day: 3, meetings: 1},
  {day: 4, meetings: 3},
  {day: 14, meetings: 3},
  {day: 21, meetings: 3},
  {day: 28, meetings: 1}
]
periodLength = 30
vacationLength = 7

result = [5, 0]
```

Отпуск, начавшийся в день `X`, занимает дни
`[X, X + V - 1]`. Поэтому допустимы старты от `1` до `P - V + 1`
включительно. При равном числе встреч выбираем самый ранний старт.

<details>
<summary>Решение</summary>

### Неоптимальный подход: проверить каждое окно отдельно

Для каждого допустимого старта заново перебираем все дни со встречами.

- время: `O((P - V + 1) * m)`, где `m` — число дней со встречами;
- дополнительная память: `O(1)`.

### Оптимальный подход: скользящее окно

Перебираем допустимые дни начала отпуска. При сдвиге окна вправо добавляем
встречи, попавшие через правую границу, и вычитаем встречи, оставшиеся за
левой границей. Каждый день со встречами добавляется и удаляется не более
одного раза.

```go
type MeetingDay struct {
	Day      int
	Meetings int
}

func BestVacation(days []MeetingDay, periodLength, vacationLength int) (int, int) {
	if vacationLength <= 0 || periodLength <= 0 || vacationLength > periodLength {
		return 0, 0
	}

	lastStart := periodLength - vacationLength + 1
	left, right := 0, 0
	current := 0
	bestStart := 1
	bestMeetings := math.MaxInt

	for start := 1; start <= lastStart; start++ {
		end := start + vacationLength - 1

		for right < len(days) && days[right].Day <= end {
			current += days[right].Meetings
			right++
		}
		for left < right && days[left].Day < start {
			current -= days[left].Meetings
			left++
		}

		if current < bestMeetings {
			bestMeetings = current
			bestStart = start
		}
	}

	return bestStart, bestMeetings
}
```

- время: `O(P + m)`;
- дополнительная память: `O(1)`.

Алгоритм использует то, что дни со встречами уже отсортированы. При равенстве
сумм сохраняется самый ранний день начала отпуска.

</details>

## 4. Порядок импорта библиотек

Дана map библиотек и их зависимостей. Нужно вывести библиотеки в таком порядке,
чтобы каждая зависимость была выведена раньше зависящей от неё библиотеки.
Циклических зависимостей во входных данных нет.

```text
deps = {
  "tensorflow": ["nvcc", "gpu", "linux"],
  "nvcc": ["linux"],
  "linux": ["core"],
  "mylib": ["tensorflow"],
  "mylib2": ["requests"]
}
```

Зависимости, которые встречаются только в значениях (`core`, `gpu`,
`requests`), тоже должны попасть в результат. Правильных порядков может быть
несколько.

<details>
<summary>Решение</summary>

### Неоптимальный подход: многократное сканирование

Повторно обходим все библиотеки и выводим ту, чьи зависимости уже выведены.
За один проход может добавиться только одна библиотека.

- время в худшем случае: `O(v * (v + e))`;
- дополнительная память: `O(v)`;

где `v` — число библиотек, `e` — число связей-зависимостей.

### Оптимальный подход: топологическая сортировка DFS

При обходе библиотеки сначала рекурсивно обходим её зависимости и только затем
добавляем саму библиотеку.

```go
func ImportOrder(deps map[string][]string) ([]string, error) {
	const (
		unvisited = iota
		visiting
		visited
	)

	state := make(map[string]int)
	order := make([]string, 0, len(deps))

	var visit func(string) error
	visit = func(lib string) error {
		switch state[lib] {
		case visiting:
			return fmt.Errorf("dependency cycle at %q", lib)
		case visited:
			return nil
		}

		state[lib] = visiting
		for _, dependency := range deps[lib] {
			if err := visit(dependency); err != nil {
				return err
			}
		}
		state[lib] = visited
		order = append(order, lib)
		return nil
	}

	for lib := range deps {
		if err := visit(lib); err != nil {
			return nil, err
		}
	}

	return order, nil
}
```

- время: `O(v + e)`;
- дополнительная память: `O(v)` для состояний, результата и стека DFS.

Порядок обхода Go map не определён. Если нужен воспроизводимый результат,
ключи и списки зависимостей сортируют; тогда появляется цена сортировки.
Проверка состояния `visiting` оставлена даже при обещании отсутствия циклов:
она защищает функцию при нарушении входного контракта.

</details>

## 5. Сложение больших чисел

Очень большие неотрицательные числа хранятся как массивы десятичных цифр:

```text
[1, 2, 3] + [4, 5, 6] = [5, 7, 9]
[5, 4, 4] + [4, 5, 6] = [1, 0, 0, 0]
[8] + [7] = [1, 5]
```

Нужно вернуть сумму в том же формате. Каждая позиция входа содержит цифру от
`0` до `9`.

<details>
<summary>Решение</summary>

### Неоптимальный подход: вставка цифр в начало

Можно идти справа налево и при каждом шаге вставлять новую цифру в начало
результата. Однако каждая вставка сдвигает уже записанные элементы.

- время: `O(n²)`, где `n = max(len(a), len(b))`;
- дополнительная память: `O(n)`.

Преобразование массива в `int` не является корректным базовым решением: именно
переполнение встроенного типа и требуется обойти.

### Оптимальный подход: заранее выделенный результат

Выделяем `n + 1` позиций и заполняем их справа налево, перенося десяток
(`carry`) на следующую итерацию.

```go
func AddDecimalDigits(a, b []int) []int {
	n := len(a)
	if len(b) > n {
		n = len(b)
	}
	if n == 0 {
		return []int{0}
	}

	result := make([]int, n+1)
	i, j := len(a)-1, len(b)-1
	carry := 0

	for k := n; k >= 0; k-- {
		sum := carry
		if i >= 0 {
			sum += a[i]
			i--
		}
		if j >= 0 {
			sum += b[j]
			j--
		}
		result[k] = sum % 10
		carry = sum / 10
	}

	if result[0] == 0 {
		return result[1:]
	}
	return result
}
```

- время: `O(n)`;
- память результата: `O(n)`;
- дополнительная память сверх результата: `O(1)`.

Функция снимает не больше одного ведущего нуля — того, который появился из
запасной позиции под перенос. Ведущие нули самого входа сохраняются:

```text
[0, 0, 1] + [9] = [0, 1, 0]
```

Если контракт требует канонической записи числа, лишние нули нужно срезать
отдельным циклом, оставив хотя бы одну цифру для результата `0`. В
production-контракте стоит также валидировать, что вход содержит только цифры.

</details>

## 6. K самых частых чисел

Дан массив чисел. Нужно вернуть до `k` различных чисел с наибольшей частотой.
При одинаковой частоте порядок не важен.

```text
nums = [1, 1, 1, 2, 2, 3]
k = 2

result = [1, 2]
```

Если уникальных чисел меньше `k`, возвращаются все уникальные числа.
Желаемая сложность — `O(n)`.

<details>
<summary>Решение</summary>

### Неоптимальный подход: map и полная сортировка

Считаем частоты в map, превращаем её в массив пар и сортируем по убыванию
частоты.

- время: `O(n + u log u)`, где `u` — число уникальных чисел;
- дополнительная память: `O(u)`.

### Оптимальный подход: корзины по частоте

Частота не может превышать `n`. Создаём массив корзин, где индекс — частота, а
значение — числа с такой частотой. Затем идём по корзинам справа налево.

```go
func TopKFrequent(nums []int, k int) []int {
	if k <= 0 || len(nums) == 0 {
		return nil
	}

	frequency := make(map[int]int)
	for _, number := range nums {
		frequency[number]++
	}

	buckets := make([][]int, len(nums)+1)
	for number, count := range frequency {
		buckets[count] = append(buckets[count], number)
	}

	if k > len(frequency) {
		k = len(frequency)
	}
	result := make([]int, 0, k)

	for count := len(buckets) - 1; count > 0 && len(result) < k; count-- {
		for _, number := range buckets[count] {
			result = append(result, number)
			if len(result) == k {
				break
			}
		}
	}

	return result
}
```

- ожидаемое время: `O(n)`; операции hash map считаются `O(1)` в среднем;
- дополнительная память: `O(n + u)`, то есть `O(n)`.

Min-heap размера `k` расходует `O(u + k)` памяти вместо `O(n + u)` у корзин и
работает за `O(n + u log k)`. Это полезный trade-off, если `n` велико, а `k`
мало: массив корзин длины `n + 1` выделяется целиком, даже когда уникальных
чисел единицы. Реализация такой кучи разобрана в
[задаче 11](#11-k-самых-больших-чисел).

</details>

## 7. Правильные скобочные последовательности

Нужно сгенерировать все правильные скобочные последовательности из `n` пар
круглых скобок.

```text
n = 3

result = ["((()))", "(()())", "(())()", "()(())", "()()()"]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: сгенерировать все строки

Генерируем все `2^(2n)` строк из открывающих и закрывающих скобок, а затем
проверяем баланс каждой строки за `O(n)`.

- время: `O(n * 4^n)`;
- дополнительная память без результата: `O(n)` для текущей строки.

Большая часть сгенерированных строк заведомо не может стать правильной.

### Оптимальный подход: backtracking с отсечениями

Добавляем открывающую скобку, пока использовано меньше `n` открывающих.
Закрывающую добавляем только тогда, когда она закрывает уже открытую пару:
`closed < opened`.

```go
func GenerateParentheses(n int) []string {
	if n < 0 {
		return nil
	}

	result := make([]string, 0)
	current := make([]byte, 0, 2*n)

	var generate func(opened, closed int)
	generate = func(opened, closed int) {
		if len(current) == 2*n {
			result = append(result, string(current))
			return
		}

		if opened < n {
			current = append(current, '(')
			generate(opened+1, closed)
			current = current[:len(current)-1]
		}

		if closed < opened {
			current = append(current, ')')
			generate(opened, closed+1)
			current = current[:len(current)-1]
		}
	}

	generate(0, 0)
	return result
}
```

Число результатов равно `n`-му числу Каталана `Cₙ`.

- время: `O(Cₙ * n)`, потому что нужно материализовать `Cₙ` строк длины `2n`;
- память результата: `O(Cₙ * n)`;
- дополнительная память без результата: `O(n)` для текущей строки и стека.

Это output-sensitive оценка: быстрее асимптотически нельзя, если функция
обязана вернуть все последовательности.

При `n == 0` возвращается `[""]` — одна пустая последовательность. Это
согласуется с `C₀ = 1`: пустая строка сбалансирована. Если вызывающий код
ожидает здесь пустой список, случай нужно оговорить в контракте и обработать
явно, как обработан отрицательный `n`.

### Разбор обхода для `n = 3`

Ниже всё дерево вызовов целиком — 22 узла. В скобках указаны значения `opened`
и `closed` на входе в узел, справа — ветка, которая в этом узле закрылась
впервые.

```text
""                    (0,0)   ')' нельзя: closed == opened
└── (                 (1,0)
    ├── ((            (2,0)
    │   ├── (((       (3,0)   '(' нельзя: opened == n
    │   │   └── ((()  (3,1)
    │   │       └── ((())     (3,2)
    │   │           └── ((()))    → 1
    │   └── (()       (2,1)
    │       ├── (()(  (3,1)   '(' нельзя: opened == n
    │       │   └── (()()     (3,2)
    │       │       └── (()())    → 2
    │       └── (())  (2,2)   ')' нельзя: closed == opened
    │           └── (())(     (3,2)   '(' нельзя: opened == n
    │               └── (())()    → 3
    └── ()            (1,1)   ')' нельзя: closed == opened
        ├── ()(       (2,1)
        │   ├── ()((  (3,1)   '(' нельзя: opened == n
        │   │   └── ()(()     (3,2)
        │   │       └── ()(())    → 4
        │   └── ()()  (2,2)   ')' нельзя: closed == opened
        │       └── ()()(     (3,2)   '(' нельзя: opened == n
        │           └── ()()()    → 5
```

Как только `opened` достигает `n`, ветка `'('` остаётся закрытой и во всех
потомках: открывать больше нечего. Поэтому нижние части дерева — не ветвления,
а цепочки, где остаётся единственный ход `')'`. Отсюда и ширина результата:
развилки бывают только выше уровня `opened == n`.

Из дерева видны три вещи, неочевидные по коду.

**Отсечение заменяет проверку баланса.** Условие `closed < opened` не даёт
поставить закрывающую скобку, когда закрывать нечего. Строку вроде `())`
построить физически невозможно, поэтому у листа проверять ничего не нужно: до
глубины `2n` доживают только правильные последовательности. Наивный перебор на
том же `n = 3` построил бы `2⁶ = 64` строки и отбраковал 59 из них.

**Порядок результата детерминирован.** Ветка `'('` пробуется первой, поэтому
последовательности выходят от самой вложенной `((()))` к самой плоской
`()()()` — ровно в том порядке, что записан в условии задачи.

**Откат — это и есть «back» в backtracking.** Буфер `current` один на весь
обход и не копируется. Строка `current = current[:len(current)-1]` после
рекурсивного вызова стирает только что добавленный символ и возвращает буфер в
то состояние, в котором его увидел текущий вызов. Без отката второй `if` в том
же вызове дописывал бы `')'` к чужому хвосту. Копирование происходит один раз
на лист, в `string(current)` — отсюда `O(n)` дополнительной памяти на всю
глубину при `O(Cₙ * n)` памяти результата.

</details>

## 8. Перемещение нулей в конец массива

Нужно переместить все нули в конец массива, сохранив относительный порядок
ненулевых элементов. Массив требуется изменить на месте, используя `O(1)`
дополнительной памяти.

```text
input  = [7, 3, 0, 0, 0, 2, 4, 0, 5, 19]
output = [7, 3, 2, 4, 5, 19, 0, 0, 0, 0]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: новый массив

Копируем ненулевые элементы в новый массив, затем дописываем нули.

- время: `O(n)`;
- дополнительная память: `O(n)`.

По времени решение хорошее, но нарушает требование `O(1)` по памяти.

Ещё хуже удалять каждый ноль из slice: каждое удаление сдвигает хвост и может
привести к `O(n²)`.

### Оптимальный подход: указатель позиции записи

Первый проход стабильно уплотняет ненулевые значения в начале массива. Второй
заполняет оставшийся хвост нулями.

```go
func MoveZeroes(nums []int) {
	write := 0
	for _, number := range nums {
		if number == 0 {
			continue
		}
		nums[write] = number
		write++
	}

	for write < len(nums) {
		nums[write] = 0
		write++
	}
}
```

- время: `O(n)`;
- дополнительная память: `O(1)`.

Вариант с обменом `nums[write]` и `nums[read]` тоже корректен, но может делать
лишние записи. Присваивание с последующим заполнением хвоста обычно легче
объяснить и проверить.

</details>

## 9. Слияние двух отсортированных массивов

Даны два массива `a` и `b`, отсортированных по возрастанию. Нужно вернуть один
отсортированный массив из всех их элементов.

```text
a = [1, 2, 5]
b = [1, 2, 3, 4, 6]

result = [1, 1, 2, 2, 3, 4, 5, 6]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: объединить и отсортировать

Соединяем массивы и запускаем общую сортировку.

- время: `O((n + m) log(n + m))`;
- память результата: `O(n + m)`.

### Оптимальный подход: два указателя

Сравниваем текущие элементы двух массивов и переносим меньший. Когда один
массив закончится, копируем остаток второго.

```go
func MergeSorted(a, b []int) []int {
	result := make([]int, 0, len(a)+len(b))
	i, j := 0, 0

	for i < len(a) && j < len(b) {
		if a[i] <= b[j] {
			result = append(result, a[i])
			i++
		} else {
			result = append(result, b[j])
			j++
		}
	}

	result = append(result, a[i:]...)
	result = append(result, b[j:]...)
	return result
}
```

- время: `O(n + m)`;
- память результата: `O(n + m)`;
- дополнительная память сверх результата: `O(1)`.

Если один из входных массивов имеет свободный буфер в конце, слияние можно
делать на месте справа налево. Для двух обычных slice новый результирующий
массив — наиболее ясный контракт.

</details>

## 10. Команда с минимальным разбросом уровней

Нужно выбрать по одному backend-разработчику, frontend-разработчику,
тестировщику и дизайнеру. Уровни специалистов каждой роли находятся в
отдельном отсортированном массиве.

Качество команды измеряется разницей между максимальным и минимальным уровнем.
Нужно минимизировать эту разницу. Если оптимальных команд несколько, можно
вернуть любую.

```text
levels = {
  backend:  [1, 2, 2, 3],
  frontend: [1, 3],
  qa:       [3, 4, 4],
  design:   [2, 3]
}

result = [3, 3, 3, 3]
difference = 0
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: декартово произведение

Перебираем все четвёрки и выбираем минимальный разброс.

- время: `O(n₁ * n₂ * n₃ * n₄)`;
- дополнительная память: `O(1)`.

### Оптимальный подход: четыре указателя

На каждой итерации рассматриваем текущие четыре значения. Улучшить текущий
разброс можно только увеличением минимума, поэтому двигаем указатель массива,
в котором находится минимальное значение. Если двинуть другой указатель,
минимум не изменится, а максимум может только вырасти.

```go
func MostBalancedTeam(backend, frontend, qa, design []int) ([4]int, int, bool) {
	levels := [4][]int{backend, frontend, qa, design}

	// Без хотя бы одного кандидата в каждой роли команда не собирается.
	for _, role := range levels {
		if len(role) == 0 {
			return [4]int{}, 0, false
		}
	}

	indexes := [4]int{}
	bestTeam := [4]int{}
	bestDifference := math.MaxInt

	for {
		current := [4]int{
			levels[0][indexes[0]],
			levels[1][indexes[1]],
			levels[2][indexes[2]],
			levels[3][indexes[3]],
		}

		minValue, maxValue := current[0], current[0]
		minRole := 0

		for role := 1; role < len(current); role++ {
			if current[role] < minValue {
				minValue = current[role]
				minRole = role
			}
			if current[role] > maxValue {
				maxValue = current[role]
			}
		}

		if maxValue-minValue < bestDifference {
			bestDifference = maxValue - minValue
			bestTeam = current
		}

		indexes[minRole]++
		if indexes[minRole] == len(levels[minRole]) {
			break
		}
	}

	return bestTeam, bestDifference, true
}
```

- время: `O(n₁ + n₂ + n₃ + n₄)`;
- дополнительная память: `O(1)`.

По условию все четыре массива непустые, но проверка стоит внутри функции:
без неё первое же обращение `levels[0][indexes[0]]` к пустому слайсу вызовет
panic. Флаг `ok` в возвращаемых значениях — обычный для Go способ сказать
«результата нет», не занимая под это число.

</details>

## 11. K самых больших чисел

Даны массив `nums` и число `k`. Нужно извлечь `k` самых больших элементов.
Повторы сохраняются, порядок результата не важен.

```text
nums = [100, 50, 0, 150, 100, 0, -30, 70]
k = 3

result = [100, 150, 100]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: полная сортировка

Сортируем копию массива по убыванию и берём первые `k` элементов.

- время: `O(n log n)`;
- дополнительная память: `O(n)`, если нельзя менять вход.

### Оптимальный практический подход при `k << n`: min-heap

Храним в min-heap только `k` лучших элементов. Вершина — наименьший элемент
текущего top-k. Новый элемент заменяет вершину только тогда, когда он больше.

```go
type intMinHeap []int

func (h intMinHeap) Len() int           { return len(h) }
func (h intMinHeap) Less(i, j int) bool { return h[i] < h[j] }
func (h intMinHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }

func (h *intMinHeap) Push(value any) {
	*h = append(*h, value.(int))
}

func (h *intMinHeap) Pop() any {
	old := *h
	last := len(old) - 1
	value := old[last]
	*h = old[:last]
	return value
}

func KLargest(nums []int, k int) []int {
	if k <= 0 || len(nums) == 0 {
		return nil
	}
	if k > len(nums) {
		k = len(nums)
	}

	// Пустая куча уже упорядочена, heap.Init для неё не нужен.
	h := &intMinHeap{}

	for _, number := range nums {
		if h.Len() < k {
			heap.Push(h, number)
			continue
		}
		if number > (*h)[0] {
			(*h)[0] = number
			heap.Fix(h, 0)
		}
	}

	return append([]int(nil), (*h)...)
}
```

- время: `O(n log k)`;
- дополнительная память: `O(k)`.

Для массива в памяти существует quickselect:

- среднее время: `O(n)`;
- худшее время обычной рандомизированной реализации: `O(n²)`;
- дополнительная память: `O(1)`, если разрешено менять вход.

Heap даёт предсказуемую верхнюю границу и поддерживает потоковый ввод.
Quickselect уместен для одноразовой обработки массива, когда важнее среднее
время. Поэтому слово «оптимальный» здесь зависит от контракта.

</details>

## 12. Все пары с заданной суммой

Дан список уникальных целых чисел и целое число `target`. Нужно вернуть все
неупорядоченные пары чисел с суммой `target`. Пары `(a, b)` и `(b, a)`
считаются одинаковыми.

```text
nums = [2, 4, 5, 3]
target = 7

result = [[2, 5], [4, 3]]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: все пары

Проверяем каждую пару индексов `i < j`.

- время: `O(n²)`;
- дополнительная память без результата: `O(1)`.

### Оптимальный подход: множество уже увиденных чисел

Для текущего числа `x` ищем `target - x` среди ранее увиденных. Так каждая пара
добавляется один раз.

```go
func PairsWithSum(nums []int, target int) [][2]int {
	seen := make(map[int]struct{}, len(nums))
	result := make([][2]int, 0)

	for _, number := range nums {
		complement := target - number
		if _, ok := seen[complement]; ok {
			result = append(result, [2]int{complement, number})
		}
		seen[number] = struct{}{}
	}

	return result
}
```

- ожидаемое время: `O(n)`;
- дополнительная память: `O(n)`.

Оценка ожидаемая из-за hash map. Если вход может содержать повторы, контракт
нужно уточнить: требуются уникальные пары значений или все пары индексов.

</details>

## 13. Полные пути до листьев рубрикатора

Рубрикатор представлен деревом:

```text
Вещи
└── Одежда
    ├── Мужская
    └── Женская
Хобби
├── Велосипеды
│   └── Горные
└── Мангалы
Транспорт
```

Нужно вывести полные пути до конечных узлов — узлов без детей:

```text
Вещи > Одежда > Мужская
Вещи > Одежда > Женская
Хобби > Велосипеды > Горные
Хобби > Мангалы
Транспорт
```

```go
type CategoryNode struct {
	Text     string
	Children []*CategoryNode
}
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: искать родителей каждого листа

Сначала можно собрать листья, а затем для каждого листа заново искать путь от
корня.

- время в худшем случае: `O(n * h)`, где `n` — число узлов, `h` — высота
  дерева; в вырожденном дереве это `O(n²)`;
- дополнительная память: `O(n)` для списка листьев и карты родителей.

### Оптимальный подход: DFS с текущим путём

Во время обхода в глубину поддерживаем путь от корня до текущего узла. При
достижении листа сразу превращаем путь в строку.

```go
func LeafPaths(roots []*CategoryNode) []string {
	result := make([]string, 0)
	path := make([]string, 0)

	var walk func(*CategoryNode)
	walk = func(node *CategoryNode) {
		if node == nil {
			return
		}

		path = append(path, node.Text)
		if len(node.Children) == 0 {
			result = append(result, strings.Join(path, " > "))
		} else {
			for _, child := range node.Children {
				walk(child)
			}
		}
		path = path[:len(path)-1]
	}

	for _, root := range roots {
		walk(root)
	}
	return result
}
```

- время обхода: `O(n)`, не считая копирования текста результата;
- полное время с формированием строк: `O(n + L)`, где `L` — суммарная длина
  всех выведенных путей;
- дополнительная память без результата: `O(h)`, где `h` — высота дерева.

Цена `O(L)` неизбежна: функция обязана материализовать все полные пути.

</details>

## 14. Сравнение версий

Даны две версии формата `vX.Y.Z...`, где компоненты состоят из неотрицательных
десятичных чисел. Функция должна вернуть:

- `1`, если первая версия меньше второй;
- `-1`, если первая версия больше второй;
- `0`, если версии равны.

```text
v11.22.44,   v11.22.45   ->  1
v11.22.44,   v11.22.44   ->  0
v11.22.44,   v11.22.44.0 ->  0
v1.12.3,     v1.3.4      -> -1
```

Последовательность отсутствующих компонентов считается последовательностью
нулей.

Знак результата здесь обратный привычному: `1` возвращается для **меньшей**
первой версии. Это противоположно `cmp.Compare` и `strings.Compare` из
стандартной библиотеки, поэтому направление стоит переспросить у интервьюера и
зафиксировать в комментарии.

<details>
<summary>Решение</summary>

### Неверный подход: сравнение версий как строк

Лексикографическое сравнение выглядит короче всего, но даёт неправильный
ответ: `"v1.12.3" < "v1.3.4"`, потому что символ `'1'` меньше `'3'`. Числовой
компонент `12` при этом больше `3`. Посимвольное сравнение ломается на любой
версии, где число компонента переходит через разряд.

- время: `O(min(a, b))`;
- дополнительная память: `O(1)`;
- корректность: нарушена.

### Оптимальный подход: сравнение компонентов слева направо

Удаляем префикс `v`, разделяем версии по точкам и сравниваем соответствующие
числа. Отсутствующие компоненты считаем нулями, поэтому `v1.2` и `v1.2.0`
равны.

```go
func CompareVersions(first, second string) int {
	firstParts := strings.Split(strings.TrimPrefix(first, "v"), ".")
	secondParts := strings.Split(strings.TrimPrefix(second, "v"), ".")

	partsCount := len(firstParts)
	if len(secondParts) > partsCount {
		partsCount = len(secondParts)
	}

	for i := 0; i < partsCount; i++ {
		firstNumber, secondNumber := 0, 0
		if i < len(firstParts) {
			firstNumber, _ = strconv.Atoi(firstParts[i])
		}
		if i < len(secondParts) {
			secondNumber, _ = strconv.Atoi(secondParts[i])
		}

		switch {
		case firstNumber < secondNumber:
			return 1
		case firstNumber > secondNumber:
			return -1
		}
	}

	return 0
}
```

- время: `O(a + b)`;
- дополнительная память: `O(a + b)` для частей строк.

Код предполагает валидный формат и компоненты, помещающиеся в `int`. Если
версии приходят из недоверенного источника, ошибки `Atoi` нужно возвращать
вызывающему коду.

</details>

## 15. Восстановление маршрута по билетам

Дан перемешанный набор билетов `{from, to}`. Из всех билетов гарантированно
строится один неразрывный маршрут без циклов, ветвлений и повторов. Нужно
вернуть билеты в порядке следования.

```text
tickets = [
  {from: "London", to: "Moscow"},
  {from: "NY",     to: "London"},
  {from: "Moscow", to: "SPb"}
]

result = [
  {from: "NY",     to: "London"},
  {from: "London", to: "Moscow"},
  {from: "Moscow", to: "SPb"}
]
```

Ожидаемая сложность — `O(n)`.

<details>
<summary>Решение</summary>

### Неоптимальный подход: искать следующий билет сканированием

После каждого билета линейно ищем билет, чей `from` совпадает с текущим `to`.

- время: `O(n²)`;
- дополнительная память: `O(n)`, если отмечать использованные билеты.

### Оптимальный подход: две hash map

Стартовый город встречается в `from`, но не встречается в `to`. После его
нахождения каждый следующий билет берётся из map `from -> ticket`.

```go
type Ticket struct {
	From string
	To   string
}

func RestoreRoute(tickets []Ticket) []Ticket {
	if len(tickets) == 0 {
		return nil
	}

	byFrom := make(map[string]Ticket, len(tickets))
	destinations := make(map[string]struct{}, len(tickets))

	for _, ticket := range tickets {
		byFrom[ticket.From] = ticket
		destinations[ticket.To] = struct{}{}
	}

	start := ""
	for from := range byFrom {
		if _, isDestination := destinations[from]; !isDestination {
			start = from
			break
		}
	}

	result := make([]Ticket, 0, len(tickets))
	current := start
	for len(result) < len(tickets) {
		ticket := byFrom[current]
		result = append(result, ticket)
		current = ticket.To
	}

	return result
}
```

- ожидаемое время: `O(n)`;
- дополнительная память: `O(n)`.

Решение опирается на гарантию условия: маршрут единственный, непрерывный и не
содержит циклов.

</details>

## 16. Фильтрация продавцов по городам

Дана map `sellerID -> city` и список интересующих городов. Нужно вернуть новую
map только с продавцами из этих городов.

```text
sellers = {
  1: "Москва",
  2: "Самара",
  3: "Самара",
  4: "Тула",
  5: "Ростов",
  6: "Казань"
}
cities = ["Самара", "Казань", "Тула"]

result = {
  2: "Самара",
  3: "Самара",
  4: "Тула",
  6: "Казань"
}
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: линейный поиск города

Для каждого продавца перебираем весь список городов.

- время: `O(s * c)`, где `s` — число продавцов, `c` — число искомых городов;
- дополнительная память без результата: `O(1)`.

### Оптимальный подход: множество городов

Сначала строим множество интересующих городов, затем один раз обходим
продавцов.

```go
func FilterSellersByCity(sellers map[int]string, cities []string) map[int]string {
	wanted := make(map[string]struct{}, len(cities))
	for _, city := range cities {
		wanted[city] = struct{}{}
	}

	result := make(map[int]string)
	for sellerID, city := range sellers {
		if _, ok := wanted[city]; ok {
			result[sellerID] = city
		}
	}
	return result
}
```

- ожидаемое время: `O(s + c)`;
- дополнительная память без результата: `O(c)`.

Если `cities` содержит один-два элемента и вызов одноразовый, линейная
проверка может оказаться проще и достаточно быстрой. Асимптотически map
выигрывает при росте списка городов или повторном использовании фильтра.

</details>

## 17. Проверка строк на анаграмму

Нужно проверить, являются ли две строки анаграммами: содержат ли они одинаковые
Unicode-символы в одинаковых количествах, но, возможно, в разном порядке.
В строках встречаются буквы латиницы и кириллицы.

```text
"anagram", "nagaram" -> true
"кит",     "ток"     -> false
```

Регистр считается значимым. Нормализация похожих Unicode-представлений не
выполняется, если это отдельно не оговорено.

<details>
<summary>Решение</summary>

### Неоптимальный подход: сортировка рун

Преобразуем обе строки в `[]rune`, сортируем и сравниваем.

- время: `O(n log n + m log m)`;
- дополнительная память: `O(n + m)`.

Сортировать байты нельзя: кириллический символ в UTF-8 занимает несколько байт.

### Оптимальный подход: счётчики рун

Считаем руны первой строки. При обходе второй уменьшаем счётчик и удаляем
обнулённые записи.

```go
func AreAnagrams(first, second string) bool {
	counts := make(map[rune]int)
	for _, symbol := range first {
		counts[symbol]++
	}

	for _, symbol := range second {
		count, ok := counts[symbol]
		if !ok {
			return false
		}
		if count == 1 {
			delete(counts, symbol)
		} else {
			counts[symbol] = count - 1
		}
	}

	return len(counts) == 0
}
```

- ожидаемое время: `O(n + m)` по числу рун;
- дополнительная память: `O(u)`, где `u` — число различных рун.

Если нужно считать `ё` и `е` одинаковыми, игнорировать регистр или сравнивать
канонически эквивалентные Unicode-строки, это отдельный этап нормализации,
который меняет контракт.

</details>

## 18. Сколько участников осталось позади

Участники конкурса имеют результаты продаж. Для каждого участника нужно
вернуть число участников с **строго меньшим** результатом.

```text
sales  = [8, 1, 2, 2, 3]
result = [4, 0, 1, 1, 3]

sales  = [5, 5, 5, 5]
result = [0, 0, 0, 0]
```

Участники с равным результатом не считаются оставшимися позади.

<details>
<summary>Решение</summary>

### Неоптимальный подход: сравнить каждого с каждым

Для каждого результата считаем, сколько элементов меньше него.

- время: `O(n²)`;
- дополнительная память без результата: `O(1)`.

### Оптимальный подход для произвольных чисел: сортировка

Сортируем копию результатов. Индекс первого появления значения равен числу
элементов, которые строго меньше него. Сохраняем это число в map и
восстанавливаем порядок исходного массива.

```go
func CountParticipantsBehind(sales []int) []int {
	sorted := append([]int(nil), sales...)
	sort.Ints(sorted)

	lessCount := make(map[int]int, len(sorted))
	for index, value := range sorted {
		if index == 0 || value != sorted[index-1] {
			lessCount[value] = index
		}
	}

	result := make([]int, len(sales))
	for index, value := range sales {
		result[index] = lessCount[value]
	}
	return result
}
```

- время: `O(n log n)`;
- дополнительная память: `O(n)`.

Если результаты — целые числа из небольшого известного диапазона `0..R`,
counting sort позволяет получить `O(n + R)` времени и `O(R)` памяти. Для
произвольных целых общая сортировка — предсказуемый выбор.

</details>

## 19. Число подкатегорий в корневых категориях

Сервис хранит дерево категорий. Для каждой корневой категории нужно посчитать
всех её потомков на любой глубине. Сама корневая категория в число
подкатегорий не входит.

```text
Бытовая техника
├── Телевизоры
│   ├── ЭЛТ
│   ├── LED
│   └── OLED
├── Холодильники
│   ├── Двухкамерные
│   └── Однокамерные
└── Утюги

Растения
├── Комнатные
└── Садовые

result = {
  "Бытовая техника": 8,
  "Растения": 2
}
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: повторные обходы поддеревьев

Если для каждого узла отдельно заново обходить его поддерево, а затем брать
результаты корней, вырожденное дерево потребует `O(n²)`. Для задачи нужны
только корневые категории, поэтому повторные вычисления не дают пользы.

### Оптимальный подход: один DFS на каждое корневое поддерево

Рекурсивная функция возвращает размер поддерева вместе с самим узлом. Для корня
из результата вычитаем единицу.

```go
type Category struct {
	Name     string
	Children []*Category
}

func CountSubcategories(roots []*Category) map[string]int {
	result := make(map[string]int, len(roots))

	var subtreeSize func(*Category) int
	subtreeSize = func(node *Category) int {
		if node == nil {
			return 0
		}

		size := 1
		for _, child := range node.Children {
			size += subtreeSize(child)
		}
		return size
	}

	for _, root := range roots {
		if root == nil {
			continue
		}
		result[root.Name] = subtreeSize(root) - 1
	}
	return result
}
```

- время: `O(n)`, каждый узел посещается один раз;
- дополнительная память: `O(h + r)`, где `h` — максимальная высота дерева,
  `r` — число корней и размер результата.

Для очень глубокого дерева рекурсивный стек может вырасти до `O(n)`. Тогда DFS
лучше переписать с явным стеком.

</details>

## Interview-ready answer

**1. Как начинать решение алгоритмической задачи?**

- Шаг 1 — зафиксировать контракт, ограничения и пограничные случаи.
- Шаг 2 — назвать простое корректное решение и оценить его время и память.
- Шаг 3 — только после этого устранять конкретное узкое место.

**2. Почему недостаточно назвать только сложность по времени?**

- Причина — ускорение почти всегда покупается памятью, поэтому одна цифра не описывает решение.
- Hash map — меняет `O(n²)` на ожидаемое `O(n)` ценой памяти под таблицу.
- Heap — ограничивает память до `O(k)` вместо хранения всех элементов.
- Корзины по частоте — дают линейное время ценой `O(n)` памяти.
- Вывод — на собеседовании нужно озвучить обе стороны.

**3. Когда `O(n)` с hash map не является строгой гарантией?**

- Причина — операции hash map дают `O(1)` в среднем, поэтому итоговая линейная оценка ожидаемая, а не гарантированная.
- Если нужна строгая граница — сортировка, дерево поиска или ограничение диапазона ключей.

**4. Что означает оптимальное решение для задачи с большим результатом?**

- Главное — учитывать размер самого вывода: быстрее, чем его напечатать, алгоритм быть не может.
- Пример со скобками — генерация всех правильных скобочных последовательностей не может быть быстрее `O(Cₙ * n)`.
- Пример с деревом — вывод всех путей не может быть быстрее их суммарной длины.

**5. Какие детали Go важно проговорить?**

- Байты и руны — для Unicode это разные вещи, `len` считает байты.
- Порядок обхода map — не определён, закладываться на него нельзя.
- Входной slice — не менять без согласованного контракта: backing-массив общий с вызывающим.
- Переполнение `int` — учитывать в арифметике, особенно при сложении и умножении больших значений.
