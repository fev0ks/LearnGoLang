## Как работать с подборкой

Разбор задачи начинается с условия. До первой строки кода нужно проговорить:

1. контракт функции и допустимые входные данные;
2. поведение на пустом вводе и при нескольких правильных ответах;
3. базовый алгоритм и его сложность;
4. узкое место базового алгоритма;
5. оптимизацию и цену этой оптимизации.

Решения скрыты под `<details>`. В оценках ниже `n`, `m`, `u` и другие
обозначения поясняются отдельно для каждой задачи. Память результата не
считается дополнительной, если не сказано обратное.

## 1. Суммарная неудовлетворённость покупателей

На торговой площадке каждый товар представлен целым числом. Потребность
покупателя также выражена целым числом. Покупатель выбирает товар с ближайшим
значением, а его неудовлетворённость равна модулю разницы между потребностью и
значением товара.

Количество экземпляров каждого товара не ограничено: один товар могут выбрать
несколько покупателей.

Нужно написать функцию, которая принимает массив товаров и массив потребностей
и возвращает суммарную неудовлетворённость.

```text
goods = [8, 3, 5]
needs = [5, 6]

result = 1
```

Для потребности `5` есть точное совпадение, а для `6` ближайшим оказывается
товар `5`; минимальная разница равна `1`.

<details>
<summary>Решение</summary>

### Неоптимальный подход: полный перебор

Для каждой потребности перебираем все товары и запоминаем минимальную разницу.

- время: `O(b * g)`, где `b` — число покупателей, `g` — число товаров;
- дополнительная память: `O(1)`.

Подход приемлем для маленьких массивов, но повторно просматривает один и тот же
список товаров.

### Оптимальный подход: сортировка и бинарный поиск

Сортируем товары. Для каждой потребности бинарным поиском находим первый товар,
который не меньше потребности. Ближайшим может быть только он или предыдущий
товар.

```go
func TotalDissatisfaction(goods, needs []int) int {
    if len(goods) == 0 {
        return 0
    }

    sort.Ints(goods)

    total := 0
    for _, need := range needs {
        index := sort.SearchInts(goods, need)

        // Потребность меньше всех товаров.
        if index == 0 {
            total += goods[0] - need
            continue
        }

        // Потребность больше всех товаров.
        if index == len(goods) {
            total += need - goods[len(goods)-1]
            continue
        }

        // Ближайший товар находится слева или справа от точки вставки.
        leftDifference := need - goods[index-1]
        rightDifference := goods[index] - need

        if leftDifference < rightDifference {
            total += leftDifference
        } else {
            total += rightDifference
        }
    }

    return total
}
```

- время: `O(g log g + b log g)`;
- дополнительная память: `O(log g)` на стек сортировки.

Функция сортирует `goods` на месте. Если вход нельзя изменять, перед сортировкой
нужно сделать копию за `O(g)` памяти. Для пустого списка товаров в реальном API
лучше вернуть ошибку; здесь для краткости возвращается `0`.

</details>

## 2. Чемпионы соревнования по шагам

Компания проводит соревнование по шагам. Статистика хранится по дням. Нужно
найти участников, которые:

1. присутствуют в статистике каждого дня;
2. набрали максимальную сумму шагов за всё соревнование.

```text
statistics = [
  [{userID: 1, steps: 1000}, {userID: 2, steps: 1500}],
  [{userID: 2, steps: 1000}]
]

champions = {userIDs: [2], steps: 2500}
```

Если несколько участников набрали одинаковый максимум, вернуть их всех.
Считаем, что количество шагов неотрицательное, а в одном дне каждый `userID`
встречается не более одного раза.

<details>
<summary>Решение</summary>

### Неоптимальный подход: отдельная проверка каждого участника

Собираем все идентификаторы, а затем для каждого участника просматриваем каждый
день и ищем его запись линейным проходом.

- время в худшем случае: `O(u * r)`, где `u` — число уникальных участников,
  `r` — общее число записей;
- дополнительная память: `O(u)`.

### Оптимальный подход: один проход по записям

Для каждого участника храним сумму шагов и число дней, в которых он появился.
После прохода рассматриваем только записи с `days == len(statistics)`.

```go
type DayResult struct {
    UserID int
    Steps  int
}

type Champions struct {
    UserIDs []int
    Steps   int
}

type participantTotal struct {
    steps int
    days  int
}

func FindChampions(statistics [][]DayResult) Champions {
    if len(statistics) == 0 {
        return Champions{}
    }

    totals := make(map[int]participantTotal)
    for _, day := range statistics {
        for _, result := range day {
            total := totals[result.UserID]
            total.steps += result.Steps
            total.days++
            totals[result.UserID] = total
        }
    }

    champions := Champions{}

    for userID, total := range totals {
        if total.days != len(statistics) {
            continue
        }

        switch {
        case total.steps > champions.Steps:
            champions.Steps = total.steps
            champions.UserIDs = []int{userID}
        case total.steps == champions.Steps:
            champions.UserIDs = append(champions.UserIDs, userID)
        }
    }

    return champions
}
```

- ожидаемое время: `O(r + u)` благодаря hash map;
- дополнительная память: `O(u)`.

Начальное значение `champions.Steps` равно нулю. Это корректно, потому что по
условию число шагов неотрицательное. Участники с нулевой суммой попадут в ветку
равенства. Если подходящих участников нет, возвращается нулевая структура.

Порядок `UserIDs` не определён из-за обхода map. Если контракт требует
стабильный порядок, идентификаторы нужно отсортировать за `O(c log c)`, где
`c` — число чемпионов.

</details>

## 3. Отпуск с минимальным числом пропущенных встреч

Нужно выбрать первый день отпуска `X` длиной `V` календарных дней так, чтобы
весь отпуск попал в ближайшие `P` дней и пересёк как можно меньше встреч.
Завтра считается днём `1`.

Дни со встречами отсортированы:

```text
daysWithMeetings = [
  {day: 3, meetings: 1},
  {day: 4, meetings: 3},
  {day: 14, meetings: 3},
  {day: 21, meetings: 3},
  {day: 28, meetings: 1}
]
periodLength = 30
vacationLength = 7

result = [5, 0]
```

Отпуск, начавшийся в день `X`, занимает дни
`[X, X + V - 1]`. Поэтому допустимы старты от `1` до `P - V + 1`
включительно. При равном числе встреч выбираем самый ранний старт.

<details>
<summary>Решение</summary>

### Неоптимальный подход: проверить каждое окно отдельно

Для каждого допустимого старта заново перебираем все дни со встречами.

- время: `O((P - V + 1) * m)`, где `m` — число дней со встречами;
- дополнительная память: `O(1)`.

### Оптимальный подход: скользящее окно

Перебираем допустимые дни начала отпуска. При сдвиге окна вправо добавляем
встречи, попавшие через правую границу, и вычитаем встречи, оставшиеся за
левой границей. Каждый день со встречами добавляется и удаляется не более
одного раза.

```go
type MeetingDay struct {
    Day      int
    Meetings int
}

func BestVacation(days []MeetingDay, periodLength, vacationLength int) (int, int) {
    if vacationLength <= 0 || periodLength <= 0 || vacationLength > periodLength {
        return 0, 0
    }

    lastStart := periodLength - vacationLength + 1
    left, right := 0, 0
    current := 0
    bestStart := 1
    bestMeetings := math.MaxInt

    for start := 1; start <= lastStart; start++ {
        end := start + vacationLength - 1

        for right < len(days) && days[right].Day <= end {
            current += days[right].Meetings
            right++
        }
        for left < right && days[left].Day < start {
            current -= days[left].Meetings
            left++
        }

        if current < bestMeetings {
            bestMeetings = current
            bestStart = start
        }
    }

    return bestStart, bestMeetings
}
```

- время: `O(P + m)`;
- дополнительная память: `O(1)`.

Алгоритм использует то, что дни со встречами уже отсортированы. При равенстве
сумм сохраняется самый ранний день начала отпуска.

</details>

## 4. Порядок импорта библиотек

Дана map библиотек и их зависимостей. Нужно вывести библиотеки в таком порядке,
чтобы каждая зависимость была выведена раньше зависящей от неё библиотеки.
Циклических зависимостей во входных данных нет.

```text
deps = {
  "tensorflow": ["nvcc", "gpu", "linux"],
  "nvcc": ["linux"],
  "linux": ["core"],
  "mylib": ["tensorflow"],
  "mylib2": ["requests"]
}
```

Зависимости, которые встречаются только в значениях (`core`, `gpu`,
`requests`), тоже должны попасть в результат. Правильных порядков может быть
несколько.

<details>
<summary>Решение</summary>

### Неоптимальный подход: многократное сканирование

Повторно обходим все библиотеки и выводим ту, чьи зависимости уже выведены.
За один проход может добавиться только одна библиотека.

- время в худшем случае: `O(v * (v + e))`;
- дополнительная память: `O(v)`;

где `v` — число библиотек, `e` — число связей-зависимостей.

### Оптимальный подход: топологическая сортировка DFS

При обходе библиотеки сначала рекурсивно обходим её зависимости и только затем
добавляем саму библиотеку. Множество `visited` хранит уже обработанные библиотеки,
чтобы общие зависимости не попадали в результат несколько раз. По условию
циклов нет, поэтому отдельное состояние `visiting` и возврат ошибки не нужны.

```go
func ImportOrder(deps map[string][]string) []string {
    visited := make(map[string]struct{})
    order := make([]string, 0, len(deps))

    var visit func(string)
    visit = func(lib string) {
        if _, exists := visited[lib]; exists {
            return
        }

        for _, dependency := range deps[lib] {
            visit(dependency)
        }

        visited[lib] = struct{}{}
        order = append(order, lib)
    }

    for lib := range deps {
        visit(lib)
    }

    return order
}
```

- время: `O(v + e)`;
- дополнительная память: `O(v)` для множества `visited` и стека DFS;
- память результата: `O(v)`.

Порядок обхода Go map не определён. Если нужен воспроизводимый результат,
ключи и списки зависимостей сортируют; тогда появляется цена сортировки.

</details>

## 5. Сложение больших чисел

Очень большие неотрицательные числа хранятся как массивы десятичных цифр:

```text
[1, 2, 3] + [4, 5, 6] = [5, 7, 9]
[5, 4, 4] + [4, 5, 6] = [1, 0, 0, 0]
[8] + [7] = [1, 5]
```

Нужно вернуть сумму в том же формате. Каждая позиция входа содержит цифру от
`0` до `9`.

<details>
<summary>Решение</summary>

### Неоптимальный подход: вставка цифр в начало

Можно идти справа налево и при каждом шаге вставлять новую цифру в начало
результата. Однако каждая вставка сдвигает уже записанные элементы.

- время: `O(n²)`, где `n = max(len(firstDigits), len(secondDigits))`;
- дополнительная память: `O(n)`.

Преобразование массива в `int` не является корректным базовым решением: именно
переполнение встроенного типа и требуется обойти.

### Оптимальный подход: заранее выделенный результат

Выделяем `n + 1` позиций и заполняем их справа налево, перенося десяток
(`carry`) на следующую итерацию.

```go
func AddDecimalDigits(firstDigits, secondDigits []int) []int {
    maxDigits := len(firstDigits)
    if len(secondDigits) > maxDigits {
        maxDigits = len(secondDigits)
    }
    if maxDigits == 0 {
        return []int{0}
    }

    result := make([]int, maxDigits+1)
    firstIndex := len(firstDigits) - 1
    secondIndex := len(secondDigits) - 1
    addNum := 0 // Перенос в следующий разряд.

    for resultIndex := maxDigits; resultIndex >= 0; resultIndex-- {
        sum := addNum
        if firstIndex >= 0 {
            sum += firstDigits[firstIndex]
            firstIndex--
        }
        if secondIndex >= 0 {
            sum += secondDigits[secondIndex]
            secondIndex--
        }
        result[resultIndex] = sum % 10
        addNum = sum / 10
    }

    if result[0] == 0 {
        return result[1:]
    }
    return result
}
```

- время: `O(n)`;
- память результата: `O(n)`;
- дополнительная память сверх результата: `O(1)`.

Функция снимает не больше одного ведущего нуля — того, который появился из
запасной позиции под перенос. Ведущие нули самого входа сохраняются:

```text
[0, 0, 1] + [9] = [0, 1, 0]
```

Если контракт требует канонической записи числа, лишние нули нужно срезать
отдельным циклом, оставив хотя бы одну цифру для результата `0`. В
production-контракте стоит также валидировать, что вход содержит только цифры.

</details>

## 6. K самых частых чисел

Дан массив чисел. Нужно вернуть до `k` различных чисел с наибольшей частотой.
При одинаковой частоте порядок не важен.

```text
nums = [1, 1, 1, 2, 2, 3]
k = 2

result = [1, 2]
```

Если уникальных чисел меньше `k`, возвращаются все уникальные числа.
Желаемая сложность — `O(n)`.

<details>
<summary>Решение</summary>

### Неоптимальный подход: map и полная сортировка

Считаем частоты в map, превращаем её в массив пар и сортируем по убыванию
частоты.

- время: `O(n + u log u)`, где `u` — число уникальных чисел;
- дополнительная память: `O(u)`.

### Оптимальный подход: корзины по частоте

Частота не может превышать `n`. Создаём массив корзин, где индекс — частота, а
значение — числа с такой частотой. Затем идём по корзинам справа налево.

```go
func TopKFrequent(nums []int, k int) []int {
    if k <= 0 || len(nums) == 0 {
        return nil
    }

    frequency := make(map[int]int)
    for _, number := range nums {
        frequency[number]++
    }

    buckets := make([][]int, len(nums)+1)
    for number, count := range frequency {
        buckets[count] = append(buckets[count], number)
    }

    if k > len(frequency) {
        k = len(frequency)
    }
    result := make([]int, 0, k)

    for count := len(buckets) - 1; count > 0 && len(result) < k; count-- {
        for _, number := range buckets[count] {
            result = append(result, number)
            if len(result) == k {
                break
            }
        }
    }

    return result
}
```

- ожидаемое время: `O(n)`; операции hash map считаются `O(1)` в среднем;
- дополнительная память: `O(n + u)`, то есть `O(n)`.

Min-heap размера `k` расходует `O(u + k)` памяти вместо `O(n + u)` у корзин и
работает за `O(n + u log k)`. Это полезный trade-off, если `n` велико, а `k`
мало: массив корзин длины `n + 1` выделяется целиком, даже когда уникальных
чисел единицы. Реализация такой кучи разобрана в
[задаче 11](#11-k-самых-больших-чисел).

</details>

## 7. Правильные скобочные последовательности

Нужно сгенерировать все правильные скобочные последовательности из `n` пар
круглых скобок.

```text
n = 3

result = ["((()))", "(()())", "(())()", "()(())", "()()()"]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: сгенерировать все строки

Генерируем все `2^(2n)` строк из открывающих и закрывающих скобок, а затем
проверяем баланс каждой строки за `O(n)`.

- время: `O(n * 4^n)`;
- дополнительная память без результата: `O(n)` для текущей строки.

Большая часть сгенерированных строк заведомо не может стать правильной.

### Оптимальный подход: backtracking с отсечениями

Добавляем открывающую скобку, пока использовано меньше `n` открывающих.
Закрывающую добавляем только тогда, когда она закрывает уже открытую пару:
`closed < opened`.

```go
func GenerateParentheses(n int) []string {
    if n < 0 {
        return nil
    }

    var result []string

    var generate func(current []byte, opened, closed int)
    generate = func(current []byte, opened, closed int) {
        if len(current) == 2*n {
            result = append(result, string(current))
            return
        }

        if opened < n {
            generate(append(current, '('), opened+1, closed)
        }

        if closed < opened {
            generate(append(current, ')'), opened, closed+1)
        }
    }

    current := make([]byte, 0, 2*n)
    generate(current, 0, 0)

    return result
}
```

Число результатов равно `n`-му числу Каталана `Cₙ`.

- время: `O(Cₙ * n)`, потому что нужно материализовать `Cₙ` строк длины `2n`;
- память результата: `O(Cₙ * n)`;
- дополнительная память без результата: `O(n)` для текущей строки и стека.

Это output-sensitive оценка: быстрее асимптотически нельзя, если функция
обязана вернуть все последовательности.

При `n == 0` возвращается `[""]` — одна пустая последовательность. Это
согласуется с `C₀ = 1`: пустая строка сбалансирована. Если вызывающий код
ожидает здесь пустой список, случай нужно оговорить в контракте и обработать
явно, как обработан отрицательный `n`.

### Разбор обхода для `n = 3`

Ниже всё дерево вызовов целиком — 22 узла. В скобках указаны значения `opened`
и `closed` на входе в узел, справа — ветка, которая в этом узле закрылась
впервые.

```text
""                    (0,0)   ')' нельзя: closed == opened
└── (                 (1,0)
    ├── ((            (2,0)
    │   ├── (((       (3,0)   '(' нельзя: opened == n
    │   │   └── ((()  (3,1)
    │   │       └── ((())     (3,2)
    │   │           └── ((()))    → 1
    │   └── (()       (2,1)
    │       ├── (()(  (3,1)   '(' нельзя: opened == n
    │       │   └── (()()     (3,2)
    │       │       └── (()())    → 2
    │       └── (())  (2,2)   ')' нельзя: closed == opened
    │           └── (())(     (3,2)   '(' нельзя: opened == n
    │               └── (())()    → 3
    └── ()            (1,1)   ')' нельзя: closed == opened
        ├── ()(       (2,1)
        │   ├── ()((  (3,1)   '(' нельзя: opened == n
        │   │   └── ()(()     (3,2)
        │   │       └── ()(())    → 4
        │   └── ()()  (2,2)   ')' нельзя: closed == opened
        │       └── ()()(     (3,2)   '(' нельзя: opened == n
        │           └── ()()()    → 5
```

Как только `opened` достигает `n`, ветка `'('` остаётся закрытой и во всех
потомках: открывать больше нечего. Поэтому нижние части дерева — не ветвления,
а цепочки, где остаётся единственный ход `')'`. Отсюда и ширина результата:
развилки бывают только выше уровня `opened == n`.

Из дерева видны три вещи, неочевидные по коду.

**Отсечение заменяет проверку баланса.** Условие `closed < opened` не даёт
поставить закрывающую скобку, когда закрывать нечего. Строку вроде `())`
построить физически невозможно, поэтому у листа проверять ничего не нужно: до
глубины `2n` доживают только правильные последовательности. Наивный перебор на
том же `n = 3` построил бы `2⁶ = 64` строки и отбраковал 59 из них.

**Порядок результата детерминирован.** Ветка `'('` пробуется первой, поэтому
последовательности выходят от самой вложенной `((()))` к самой плоской
`()()()` — ровно в том порядке, что записан в условии задачи.

**Возврат из функции выполняет откат.** `current` передаётся явно, поэтому
каждый рекурсивный вызов получает свой заголовок slice со своей длиной. Вызов с
добавленной `'('` не меняет длину `current` у родителя; после возврата родитель
может передать в другую ветку тот же путь с добавленной `')'`.

Backing-массив при этом переиспользуется: ветки выполняются последовательно и
могут записывать новые символы в одни и те же свободные позиции. Готовый путь
сохраняется отдельной строкой в `string(current)`, поэтому последующая запись
его не меняет. Отсюда `O(n)` дополнительной памяти на буфер и стек при
`O(Cₙ * n)` памяти результата.

</details>

## 8. Перемещение нулей в конец массива

Нужно переместить все нули в конец массива, сохранив относительный порядок
ненулевых элементов. Массив требуется изменить на месте, используя `O(1)`
дополнительной памяти.

```text
input  = [7, 3, 0, 0, 0, 2, 4, 0, 5, 19]
output = [7, 3, 2, 4, 5, 19, 0, 0, 0, 0]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: новый массив

Копируем ненулевые элементы в новый массив, затем дописываем нули.

- время: `O(n)`;
- дополнительная память: `O(n)`.

По времени решение хорошее, но нарушает требование `O(1)` по памяти.

Ещё хуже удалять каждый ноль из slice: каждое удаление сдвигает хвост и может
привести к `O(n²)`.

### Оптимальный подход: указатель позиции записи

Первый проход стабильно уплотняет ненулевые значения в начале массива. Второй
заполняет оставшийся хвост нулями.

```go
func MoveZeroes(nums []int) {
    write := 0
    for _, number := range nums {
        if number == 0 {
            continue
        }
        nums[write] = number
        write++
    }

    for write < len(nums) {
        nums[write] = 0
        write++
    }
}
```

- время: `O(n)`;
- дополнительная память: `O(1)`.

Вариант с обменом `nums[write]` и `nums[read]` тоже корректен, но может делать
лишние записи. Присваивание с последующим заполнением хвоста обычно легче
объяснить и проверить.

</details>

## 9. Слияние двух отсортированных массивов

Даны два массива `a` и `b`, отсортированных по возрастанию. Нужно вернуть один
отсортированный массив из всех их элементов.

```text
a = [1, 2, 5]
b = [1, 2, 3, 4, 6]

result = [1, 1, 2, 2, 3, 4, 5, 6]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: объединить и отсортировать

Соединяем массивы и запускаем общую сортировку.

- время: `O((n + m) log(n + m))`;
- память результата: `O(n + m)`.

### Оптимальный подход: два указателя

Сравниваем текущие элементы двух массивов и переносим меньший. Когда один
массив закончится, на каждой следующей итерации берём элемент из оставшегося.

```go
func MergeSorted(a, b []int) []int {
    idxA, idxB := 0, 0

    maxLen := len(a) + len(b)

    result := make([]int, len(a)+len(b))

    for i := range maxLen {
        if idxB == len(b) || idxA < len(a) && a[idxA] <= b[idxB] {
            result[i] = a[idxA]
            idxA++
            continue
        }
        if idxA == len(a) || idxB < len(b) && b[idxB] < a[idxA] {
            result[i] = b[idxB]
            idxB++
            continue
        }
    }

    return result
}
```

- время: `O(n + m)`;
- память результата: `O(n + m)`;
- дополнительная память сверх результата: `O(1)`.

Если один из входных массивов имеет свободный буфер в конце, слияние можно
делать на месте справа налево. Для двух обычных slice новый результирующий
массив — наиболее ясный контракт.

</details>

## 10. Команда с минимальным разбросом уровней

Нужно выбрать по одному backend-разработчику, frontend-разработчику,
тестировщику и дизайнеру. Уровни специалистов каждой роли находятся в
отдельном отсортированном массиве.

Качество команды измеряется разницей между максимальным и минимальным уровнем.
Нужно минимизировать эту разницу. Если оптимальных команд несколько, можно
вернуть любую.

```text
levels = {
  backend:  [1, 2, 2, 3],
  frontend: [1, 3],
  qa:       [3, 4, 4],
  design:   [2, 3]
}

result = [3, 3, 3, 3]
difference = 0
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: декартово произведение

Перебираем все четвёрки и выбираем минимальный разброс.

- время: `O(n₁ * n₂ * n₃ * n₄)`;
- дополнительная память: `O(1)`.

### Оптимальный подход: четыре указателя

На каждой итерации рассматриваем текущие четыре значения. Улучшить текущий
разброс можно только увеличением минимума, поэтому двигаем указатель массива,
в котором находится минимальное значение. Если двинуть другой указатель,
минимум не изменится, а максимум может только вырасти.

```go
func MostBalancedTeam(backend, frontend, qa, design []int) ([4]int, int) {
    backendIndex := 0
    frontendIndex := 0
    qaIndex := 0
    designIndex := 0

    bestTeam := [4]int{}
    bestDifference := math.MaxInt

    for backendIndex < len(backend) &&
        frontendIndex < len(frontend) &&
        qaIndex < len(qa) &&
        designIndex < len(design) {

        team := [4]int{
            backend[backendIndex],
            frontend[frontendIndex],
            qa[qaIndex],
            design[designIndex],
        }

        minLevel := min(team[0], team[1], team[2], team[3])
        maxLevel := max(team[0], team[1], team[2], team[3])

        if maxLevel-minLevel < bestDifference {
            bestDifference = maxLevel - minLevel
            bestTeam = team
        }

        switch minLevel {
        case team[0]:
            backendIndex++
        case team[1]:
            frontendIndex++
        case team[2]:
            qaIndex++
        case team[3]:
            designIndex++
        }
    }

    return bestTeam, bestDifference
}
```

- время: `O(n₁ + n₂ + n₃ + n₄)`;
- дополнительная память: `O(1)`.

Решение опирается на условие, что все четыре массива непустые. Если пустой
массив нужно считать допустимым входом, контракт функции следует расширить
ошибкой или флагом `ok`.

</details>

## 11. K самых больших чисел

Даны массив `nums` и число `k`. Нужно извлечь `k` самых больших элементов.
Повторы сохраняются, порядок результата не важен.

```text
nums = [100, 50, 0, 150, 100, 0, -30, 70]
k = 3

result = [100, 150, 100]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: полная сортировка

Сортируем копию массива по убыванию и берём первые `k` элементов.

- время: `O(n log n)`;
- дополнительная память: `O(n)`, если нельзя менять вход.

### Оптимальный практический подход при `k << n`: min-heap

Храним в min-heap только `k` лучших элементов. Вершина — наименьший элемент
текущего top-k. Новый элемент заменяет вершину только тогда, когда он больше.

```go
type intMinHeap []int

func (h intMinHeap) Len() int           { return len(h) }
func (h intMinHeap) Less(i, j int) bool { return h[i] < h[j] }
func (h intMinHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }

func (h *intMinHeap) Push(value any) {
    *h = append(*h, value.(int))
}

func (h *intMinHeap) Pop() any {
    old := *h
    last := len(old) - 1
    value := old[last]
    *h = old[:last]
    return value
}

func KLargest(nums []int, k int) []int {
    if k <= 0 || len(nums) == 0 {
        return nil
    }
    if k > len(nums) {
        k = len(nums)
    }

    // Пустая куча уже упорядочена, heap.Init для неё не нужен.
    h := &intMinHeap{}

    for _, number := range nums {
        if h.Len() < k {
            heap.Push(h, number)
            continue
        }
        if number > (*h)[0] {
            (*h)[0] = number
            heap.Fix(h, 0)
        }
    }

    return append([]int(nil), (*h)...)
}
```

- время: `O(n log k)`;
- дополнительная память: `O(k)`.

Для массива в памяти существует quickselect:

- среднее время: `O(n)`;
- худшее время обычной рандомизированной реализации: `O(n²)`;
- дополнительная память: `O(1)`, если разрешено менять вход.

Heap даёт предсказуемую верхнюю границу и поддерживает потоковый ввод.
Quickselect уместен для одноразовой обработки массива, когда важнее среднее
время. Поэтому слово «оптимальный» здесь зависит от контракта.

</details>

## 12. Все пары с заданной суммой

Дан список уникальных целых чисел и целое число `target`. Нужно вернуть все
неупорядоченные пары чисел с суммой `target`. Пары `(a, b)` и `(b, a)`
считаются одинаковыми.

```text
nums = [2, 4, 5, 3]
target = 7

result = [[2, 5], [4, 3]]
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: все пары

Проверяем каждую пару индексов `i < j`.

- время: `O(n²)`;
- дополнительная память без результата: `O(1)`.

### Оптимальный подход: множество уже увиденных чисел

Для текущего числа `x` ищем `target - x` среди ранее увиденных. Так каждая пара
добавляется один раз.

```go
func PairsWithSum(nums []int, target int) [][2]int {
    seen := make(map[int]struct{}, len(nums))
    result := make([][2]int, 0)

    for _, number := range nums {
        complement := target - number
        if _, ok := seen[complement]; ok {
            result = append(result, [2]int{complement, number})
        }
        seen[number] = struct{}{}
    }

    return result
}
```

- ожидаемое время: `O(n)`;
- дополнительная память: `O(n)`.

Оценка ожидаемая из-за hash map. Если вход может содержать повторы, контракт
нужно уточнить: требуются уникальные пары значений или все пары индексов.

</details>

## 13. Полные пути до листьев рубрикатора

Рубрикатор представлен деревом:

```text
Вещи
└── Одежда
    ├── Мужская
    └── Женская
Хобби
├── Велосипеды
│   └── Горные
└── Мангалы
Транспорт
```

Нужно вывести полные пути до конечных узлов — узлов без детей:

```text
Вещи > Одежда > Мужская
Вещи > Одежда > Женская
Хобби > Велосипеды > Горные
Хобби > Мангалы
Транспорт
```

```go
type CategoryNode struct {
    Text     string
    Children []*CategoryNode
}
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: искать родителей каждого листа

Сначала можно собрать листья, а затем для каждого листа заново искать путь от
корня.

- время в худшем случае: `O(n * h)`, где `n` — число узлов, `h` — высота
  дерева; в вырожденном дереве это `O(n²)`;
- дополнительная память: `O(n)` для списка листьев и карты родителей.

### Оптимальный подход: DFS с текущим путём

Во время обхода в глубину поддерживаем путь от корня до текущего узла. При
достижении листа сразу превращаем путь в строку. Текущий путь передаём
аргументом, поэтому вручную удалять последний элемент после рекурсивного вызова
не нужно.

```go
func LeafPaths(roots []*CategoryNode) []string {
    var result []string

    var walk func(*CategoryNode, []string)
    walk = func(node *CategoryNode, path []string) {
        if node == nil {
            return
        }

        path = append(path, node.Text)

        if len(node.Children) == 0 {
            result = append(result, strings.Join(path, " > "))
            return
        }

        for _, child := range node.Children {
            walk(child, path)
        }
    }

    for _, root := range roots {
        walk(root, nil)
    }

    return result
}
```

- время обхода: `O(n)`, не считая копирования текста результата;
- полное время с формированием строк: `O(n + L)`, где `L` — суммарная длина
  всех выведенных путей;
- дополнительная память без результата: `O(h)`, где `h` — высота дерева.

Цена `O(L)` неизбежна: функция обязана материализовать все полные пути.

</details>

## 14. Сравнение версий

Даны две версии формата `vX.Y.Z...`, где компоненты состоят из неотрицательных
десятичных чисел. Функция должна вернуть:

- `1`, если первая версия меньше второй;
- `-1`, если первая версия больше второй;
- `0`, если версии равны.

```text
v11.22.44,   v11.22.45   ->  1
v11.22.44,   v11.22.44   ->  0
v11.22.44,   v11.22.44.0 ->  0
v1.12.3,     v1.3.4      -> -1
v1.0002,     v1.2        ->  0
```

Последовательность отсутствующих компонентов считается последовательностью
нулей.

Знак результата здесь обратный привычному: `1` возвращается для **меньшей**
первой версии. Это противоположно `cmp.Compare` и `strings.Compare` из
стандартной библиотеки, поэтому направление стоит переспросить у интервьюера и
зафиксировать в комментарии.

<details>
<summary>Решение</summary>

### Неверный подход: сравнение версий как строк

Лексикографическое сравнение выглядит короче всего, но даёт неправильный
ответ: `"v1.12.3" < "v1.3.4"`, потому что символ `'1'` меньше `'3'`. Числовой
компонент `12` при этом больше `3`. Посимвольное сравнение ломается на любой
версии, где число компонента переходит через разряд.

- время: `O(min(a, b))`;
- дополнительная память: `O(1)`;
- корректность: нарушена.

### Оптимальный подход: сравнение компонентов слева направо

Удаляем префикс `v` и разделяем версии по точкам. В каждом компоненте убираем
ведущие нули. Сначала сравниваем длину оставшихся строк, а при равной длине —
сами строки. Так компоненты сравниваются как числа, но не ограничиваются
размером `int`.

Отсутствующие компоненты считаем нулями, поэтому `v1.2`, `v1.2.0` и
`v1.0002` сравниваются корректно.

```go
func CompareVersions(first, second string) int {
    firstParts := strings.Split(strings.TrimPrefix(first, "v"), ".")
    secondParts := strings.Split(strings.TrimPrefix(second, "v"), ".")

    partsCount := max(len(firstParts), len(secondParts))

    for partIndex := 0; partIndex < partsCount; partIndex++ {
        firstPart := normalizedVersionPart(firstParts, partIndex)
        secondPart := normalizedVersionPart(secondParts, partIndex)

        switch {
        case len(firstPart) < len(secondPart):
            return 1
        case len(firstPart) > len(secondPart):
            return -1
        case firstPart < secondPart:
            return 1
        case firstPart > secondPart:
            return -1
        }
    }

    return 0
}

func normalizedVersionPart(parts []string, index int) string {
    if index >= len(parts) {
        return "0"
    }

    part := strings.TrimLeft(parts[index], "0")
    if part == "" {
        return "0"
    }

    return part
}
```

- время: `O(a + b)`;
- дополнительная память: `O(a + b)` для частей строк.

Код предполагает валидный формат, но компоненты могут иметь любую длину. Если
версии приходят из недоверенного источника, проверку префикса, точек и
десятичных цифр нужно добавить отдельно.

</details>

## 15. Восстановление маршрута по билетам

Дан перемешанный набор билетов `{from, to}`. Из всех билетов гарантированно
строится один неразрывный маршрут без циклов, ветвлений и повторов. Нужно
вернуть билеты в порядке следования.

```text
tickets = [
  {from: "London", to: "Moscow"},
  {from: "NY",     to: "London"},
  {from: "Moscow", to: "SPb"}
]

result = [
  {from: "NY",     to: "London"},
  {from: "London", to: "Moscow"},
  {from: "Moscow", to: "SPb"}
]
```

Ожидаемая сложность — `O(n)`.

<details>
<summary>Решение</summary>

### Неоптимальный подход: искать следующий билет сканированием

После каждого билета линейно ищем билет, чей `from` совпадает с текущим `to`.

- время: `O(n²)`;
- дополнительная память: `O(n)`, если отмечать использованные билеты.

### Оптимальный подход: две hash map

Стартовый город встречается в `from`, но не встречается в `to`. После его
нахождения каждый следующий билет берётся из map `from -> ticket`.

```go
type Ticket struct {
    From string
    To   string
}

func RestoreRoute(tickets []Ticket) []Ticket {
    if len(tickets) == 0 {
        return nil
    }

    byFrom := make(map[string]Ticket, len(tickets))
    destinations := make(map[string]struct{}, len(tickets))

    for _, ticket := range tickets {
        byFrom[ticket.From] = ticket
        destinations[ticket.To] = struct{}{}
    }

    start := ""
    for from := range byFrom {
        if _, isDestination := destinations[from]; !isDestination {
            start = from
            break
        }
    }

    result := make([]Ticket, 0, len(tickets))
    current := start
    for len(result) < len(tickets) {
        ticket := byFrom[current]
        result = append(result, ticket)
        current = ticket.To
    }

    return result
}
```

- ожидаемое время: `O(n)`;
- дополнительная память: `O(n)`.

Решение опирается на гарантию условия: маршрут единственный, непрерывный и не
содержит циклов.

</details>

## 16. Фильтрация продавцов по городам

Дана map `sellerID -> city` и список интересующих городов. Нужно вернуть новую
map только с продавцами из этих городов.

```text
sellers = {
  1: "Москва",
  2: "Самара",
  3: "Самара",
  4: "Тула",
  5: "Ростов",
  6: "Казань"
}
cities = ["Самара", "Казань", "Тула"]

result = {
  2: "Самара",
  3: "Самара",
  4: "Тула",
  6: "Казань"
}
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: линейный поиск города

Для каждого продавца перебираем весь список городов.

- время: `O(s * c)`, где `s` — число продавцов, `c` — число искомых городов;
- дополнительная память без результата: `O(1)`.

### Оптимальный подход: множество городов

Сначала строим множество интересующих городов, затем один раз обходим
продавцов.

```go
func FilterSellersByCity(sellers map[int]string, cities []string) map[int]string {
    wanted := make(map[string]struct{}, len(cities))
    for _, city := range cities {
        wanted[city] = struct{}{}
    }

    result := make(map[int]string)
    for sellerID, city := range sellers {
        if _, ok := wanted[city]; ok {
            result[sellerID] = city
        }
    }
    return result
}
```

- ожидаемое время: `O(s + c)`;
- дополнительная память без результата: `O(c)`.

Если `cities` содержит один-два элемента и вызов одноразовый, линейная
проверка может оказаться проще и достаточно быстрой. Асимптотически map
выигрывает при росте списка городов или повторном использовании фильтра.

</details>

## 17. Проверка строк на анаграмму

Нужно проверить, являются ли две строки анаграммами: содержат ли они одинаковые
Unicode-символы в одинаковых количествах, но, возможно, в разном порядке.
В строках встречаются буквы латиницы и кириллицы.

```text
"anagram", "nagaram" -> true
"кит",     "ток"     -> false
```

Регистр считается значимым. Нормализация похожих Unicode-представлений не
выполняется, если это отдельно не оговорено.

<details>
<summary>Решение</summary>

### Неоптимальный подход: сортировка рун

Преобразуем обе строки в `[]rune`, сортируем и сравниваем.

- время: `O(n log n + m log m)`;
- дополнительная память: `O(n + m)`.

Сортировать байты нельзя: кириллический символ в UTF-8 занимает несколько байт.

### Оптимальный подход: счётчики рун

Считаем руны первой строки. При обходе второй уменьшаем счётчик и удаляем
обнулённые записи.

```go
func AreAnagrams(first, second string) bool {
    counts := make(map[rune]int)
    for _, symbol := range first {
        counts[symbol]++
    }

    for _, symbol := range second {
        count, ok := counts[symbol]
        if !ok {
            return false
        }
        if count == 1 {
            delete(counts, symbol)
        } else {
            counts[symbol] = count - 1
        }
    }

    return len(counts) == 0
}
```

- ожидаемое время: `O(n + m)` по числу рун;
- дополнительная память: `O(u)`, где `u` — число различных рун.

Если нужно считать `ё` и `е` одинаковыми, игнорировать регистр или сравнивать
канонически эквивалентные Unicode-строки, это отдельный этап нормализации,
который меняет контракт.

</details>

## 18. Сколько участников осталось позади

Участники конкурса имеют результаты продаж. Для каждого участника нужно
вернуть число участников с **строго меньшим** результатом.

```text
sales  = [8, 1, 2, 2, 3]
result = [4, 0, 1, 1, 3]

sales  = [5, 5, 5, 5]
result = [0, 0, 0, 0]
```

Участники с равным результатом не считаются оставшимися позади.

<details>
<summary>Решение</summary>

### Неоптимальный подход: сравнить каждого с каждым

Для каждого результата считаем, сколько элементов меньше него.

- время: `O(n²)`;
- дополнительная память без результата: `O(1)`.

### Оптимальный подход для произвольных чисел: сортировка

Сортируем копию результатов. Индекс первого появления значения равен числу
элементов, которые строго меньше него. Сохраняем это число в map и
восстанавливаем порядок исходного массива.

```go
func CountParticipantsBehind(sales []int) []int {
    sorted := make([]int, len(sales)) // O(n) дополнительной памяти.
    copy(sorted, sales)               // O(n) времени.
    sort.Ints(sorted)                 // O(n log n) времени.

    // Индекс первого вхождения равен числу строго меньших результатов.
    firstIndex := make(map[int]int, len(sorted)) // До O(n) памяти.
    for index, value := range sorted {           // O(n) времени.
        if _, exists := firstIndex[value]; !exists {
            firstIndex[value] = index
        }
    }

    result := make([]int, len(sales)) // O(n) памяти под результат.
    for index, value := range sales { // O(n) времени.
        result[index] = firstIndex[value]
    }
    return result
}
```

- время: `O(n log n)`;
- дополнительная память: `O(n)`.

Если результаты — целые числа из небольшого известного диапазона `0..R`,
counting sort позволяет получить `O(n + R)` времени и `O(R)` памяти. Для
произвольных целых общая сортировка — предсказуемый выбор.

</details>

## 19. Число подкатегорий в корневых категориях

Сервис хранит дерево категорий. Для каждой корневой категории нужно посчитать
всех её потомков на любой глубине. Сама корневая категория в число
подкатегорий не входит.

```text
Бытовая техника
├── Телевизоры
│   ├── ЭЛТ
│   ├── LED
│   └── OLED
├── Холодильники
│   ├── Двухкамерные
│   └── Однокамерные
└── Утюги

Растения
├── Комнатные
└── Садовые

result = {
  "Бытовая техника": 8,
  "Растения": 2
}
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: повторные обходы поддеревьев

Если для каждого узла отдельно заново обходить его поддерево, а затем брать
результаты корней, вырожденное дерево потребует `O(n²)`. Для задачи нужны
только корневые категории, поэтому повторные вычисления не дают пользы.

### Оптимальный подход: один DFS на каждое корневое поддерево

Рекурсивная функция возвращает размер поддерева вместе с самим узлом. Для корня
из результата вычитаем единицу.

```go
type Category struct {
    Name     string
    Children []*Category
}

func CountSubcategories(roots []*Category) map[string]int {
    result := make(map[string]int, len(roots))

    var subtreeSize func(*Category) int
    subtreeSize = func(node *Category) int {
        if node == nil {
            return 0
        }

        size := 1
        for _, child := range node.Children {
            size += subtreeSize(child)
        }
        return size
    }

    for _, root := range roots {
        if root == nil {
            continue
        }
        result[root.Name] = subtreeSize(root) - 1
    }
    return result
}
```

- время: `O(n)`, каждый узел посещается один раз;
- дополнительная память: `O(h + r)`, где `h` — максимальная высота дерева,
  `r` — число корней и размер результата.

Для очень глубокого дерева рекурсивный стек может вырасти до `O(n)`. Тогда DFS
лучше переписать с явным стеком.

</details>

## 20. Группировка серверов по стабильности

Дана статистика по серверам. Для каждого сервера известны его идентификатор и
показатель стабильности в процентах. Нужно сгруппировать идентификаторы серверов
по одинаковому показателю стабильности и вернуть результат в виде map.

```text
stats = [
    {server: 1, stability: 99},
    {server: 2, stability: 97},
    {server: 3, stability: 34},
    {server: 4, stability: 97},
    {server: 5, stability: 97.1}
]

result = {
    34: [3],
    97: [2, 4],
    99: [1],
    97.1: [5]
}
```

Порядок ключей в Go map не определён. Порядок серверов внутри каждой группы
совпадает с порядком во входном массиве.

<details>
<summary>Решение</summary>

### Неоптимальный подход: линейный поиск существующей группы

Можно хранить группы в slice и для каждого сервера искать группу с таким же
показателем стабильности полным перебором.

- время в худшем случае: `O(n²)`;
- память результата: `O(n)`.

### Оптимальный подход: группировка через map

Показатель стабильности становится ключом map. Для каждого элемента добавляем
идентификатор сервера в slice соответствующей группы.

```go
type ServerStat struct {
    Server    int
    Stability float64
}

func GroupServersByStability(stats []ServerStat) map[float64][]int {
    result := make(map[float64][]int)

    for _, stat := range stats {
        result[stat.Stability] = append(result[stat.Stability], stat.Server)
    }

    return result
}
```

- ожидаемое время: `O(n)`;
- память результата: `O(n)`;
- дополнительная память сверх результата: `O(1)`.

`float64` сравнивается точно по двоичному представлению. Для готовых значений
из условия прямой ключ подходит. Если процент вычисляется, его лучше сначала
округлить до согласованной точности и хранить целым числом, например `9710`
для `97.10%`. Иначе визуально одинаковые значения могут попасть в разные
группы.

</details>

## 21. Пересечение списков пользователей

Из-за ошибки данные о пользователях оказались в двух источниках. Нужно вернуть
единый список пользователей, которые присутствуют в обоих источниках.

```text
source1 = [
    {userID: 1}, {userID: 2}, {userID: 3},
    {userID: 4}, {userID: 5}, {userID: 6}
]

source2 = [
    {userID: 2}, {userID: 4}, {userID: 6},
    {userID: 8}, {userID: 10}, {userID: 12}
]

result = [{userID: 2}, {userID: 4}, {userID: 6}]
```

Результат содержит каждый `userID` не более одного раза. Порядок пользователей
совпадает с порядком их первого появления во втором источнике.

<details>
<summary>Решение</summary>

### Неоптимальный подход: сравнить каждый элемент с каждым

Для каждого пользователя первого источника перебираем второй источник и ищем
совпадающий `userID`.

- время: `O(n * m)`, где `n` и `m` — размеры источников;
- дополнительная память без результата: `O(1)`.

### Оптимальный подход: множество идентификаторов

Сначала записываем идентификаторы из первого источника в множество. Затем
обходим второй источник и проверяем каждый `userID` за ожидаемое `O(1)`.

```go
type User struct {
    UserID int
}

func IntersectUsers(source1, source2 []User) []User {
    source1IDs := make(map[int]struct{}, len(source1))
    for _, user := range source1 {
        source1IDs[user.UserID] = struct{}{}
    }

    var result []User
    for _, user := range source2 {
        if _, exists := source1IDs[user.UserID]; !exists {
            continue
        }

        result = append(result, user)
        delete(source1IDs, user.UserID)
    }

    return result
}
```

Удаление найденного идентификатора не даёт добавить одного пользователя в
результат повторно, даже если во втором источнике есть дубли.

- ожидаемое время: `O(n + m)`;
- дополнительная память без результата: `O(n)`;
- память результата: `O(k)`, где `k` — размер пересечения.

</details>

## 22. Добавление новой партии в отсортированную витрину

На витрине стоят пирамидки, отсортированные по высоте. Приехала новая
неотсортированная партия. Нужно добавить новые пирамидки так, чтобы итоговая
витрина осталась отсортированной.

```text
pyramids     = [3, 5, 7, 12, 14]
newPyramids  = [15, 6, 10, 4, 7]

result = [3, 4, 5, 6, 7, 7, 10, 12, 14, 15]
```

Пирамидки одинаковой высоты сохраняются: обе пирамидки высотой `7` входят в
результат.

<details>
<summary>Решение</summary>

### Неоптимальный подход: объединить и отсортировать всё

Можно объединить старую и новую партии, а затем отсортировать общий массив.
Такой подход не использует то, что витрина уже отсортирована.

- время: `O((n + m) log(n + m))`;
- память результата: `O(n + m)`.

### Оптимальный подход: отсортировать новую партию и выполнить слияние

Сортируем только новую партию. После этого получаются два отсортированных
массива, которые можно слить двумя указателями за линейное время.

```go
func AddPyramids(pyramids, newPyramids []int) []int {
    sort.Ints(newPyramids)

    result := make([]int, 0, len(pyramids)+len(newPyramids))
    oldIndex, newIndex := 0, 0

    for oldIndex < len(pyramids) && newIndex < len(newPyramids) {
        if pyramids[oldIndex] <= newPyramids[newIndex] {
            result = append(result, pyramids[oldIndex])
            oldIndex++
        } else {
            result = append(result, newPyramids[newIndex])
            newIndex++
        }
    }

    result = append(result, pyramids[oldIndex:]...)
    result = append(result, newPyramids[newIndex:]...)
    return result
}
```

- время сортировки новой партии: `O(m log m)`;
- время слияния: `O(n + m)`;
- итоговое время: `O(m log m + n + m)`;
- память результата: `O(n + m)`;
- дополнительная память сверх результата: `O(log m)` на стек сортировки.

Функция сортирует `newPyramids` на месте. Если входной slice нельзя изменять,
перед сортировкой нужно сделать его копию за `O(m)` дополнительной памяти.

</details>

## 23. Можно ли собрать строку из доступных символов

Реализуйте функцию `CanBuildString(source, target string) bool`, которая
проверяет, можно ли собрать строку `target` из символов строки `source`.
Каждый символ `source` можно использовать не более одного раза, порядок
символов не важен.

```text
source = "aabbcc", target = "abc"   -> true
source = "aabbcc", target = "abccc" -> false
source = "кот",    target = "ток"   -> true
```

Задача похожа на [проверку анаграмм](#17-проверка-строк-на-анаграмму), но
условия различаются. Для анаграммы частоты всех символов должны совпасть. Здесь
`source` может содержать лишние символы: важно только, чтобы их хватило для
`target`.

<details>
<summary>Решение</summary>

### Неоптимальный подход: искать каждый символ отдельно

Для каждого символа `target` можно линейно искать ещё не использованное
совпадение в `source`.

- время: `O(s * t)`, где `s` и `t` — число символов в строках;
- дополнительная память: `O(s)` для отметок использованных позиций.

### Оптимальный подход: счётчики символов

Сначала считаем доступные символы `source`. Затем для каждого символа `target`
уменьшаем соответствующий счётчик. Если счётчик уже равен нулю, собрать строку
невозможно.

```go
func CanBuildString(source, target string) bool {
    available := make(map[rune]int)
    for _, symbol := range source {
        available[symbol]++
    }

    for _, symbol := range target {
        if available[symbol] == 0 {
            return false
        }
        available[symbol]--
    }

    return true
}
```

- ожидаемое время: `O(s + t)` по числу Unicode-символов;
- дополнительная память: `O(u)`, где `u` — число различных символов в
  `source`.

Пустую строку `target` всегда можно собрать. Обход по `rune`, а не по байтам,
позволяет одинаково обрабатывать латиницу и кириллицу.

</details>

## 24. Наибольшая подстрока не более чем из двух символов

Нужно найти длину наибольшей подстроки, которая содержит не более двух
различных символов. Подстрока — это непрерывный фрагмент исходной строки.

```text
"eceba"   -> 3  // "ece"
"ccaabbb" -> 5  // "aabbb"
"aaaa"    -> 4  // "aaaa"
```

Длина считается в Unicode-символах, а не в байтах UTF-8.

<details>
<summary>Решение</summary>

### Неоптимальный подход: начинать поиск с каждой позиции

Для каждой позиции можно заново расширять подстроку вправо, пока в ней не
появится третий различный символ.

- время: `O(n²)`;
- дополнительная память: `O(1)`, поскольку одновременно отслеживается не более
  трёх символов.

### Оптимальный подход: скользящее окно

Храним количество вхождений каждого символа в текущем окне. Расширяем окно
вправо на один символ. Если разных символов стало больше двух, убираем символы
слева, пока условие снова не выполнится. После этого обновляем максимальную
длину.

```go
func LongestSubstringAtMostTwoDistinct(value string) int {
    symbols := []rune(value) // O(n) памяти: индексы обозначают руны, а не байты.
    counts := make(map[rune]int)
    left := 0
    bestLength := 0

    for right, symbol := range symbols {
        counts[symbol]++

        for len(counts) > 2 {
            leftSymbol := symbols[left]
            counts[leftSymbol]--
            if counts[leftSymbol] == 0 {
                // Символ полностью вышел из окна — больше не считаем его.
                delete(counts, leftSymbol)
            }
            left++
        }

        currentLength := right - left + 1
        if currentLength > bestLength {
            bestLength = currentLength
        }
    }

    return bestLength
}
```

Несмотря на вложенный цикл, каждый символ добавляется в окно один раз и
удаляется не более одного раза. Обе границы двигаются только вправо, поэтому
суммарно делают не более `2n` шагов.

- ожидаемое время: `O(n)` по числу Unicode-символов;
- дополнительная память: `O(n)` для `[]rune`; map содержит не более трёх
  записей и занимает `O(1)` памяти.

Для пустой строки функция возвращает `0`.

</details>

## 25. Проверка валидности скобочной последовательности

Дана строка `s`, содержащая только символы `(`, `)`, `{`, `}`, `[` и `]`.
Нужно определить, является ли строка валидной.

Строка валидна, если:

- каждой открывающей скобке соответствует закрывающая скобка того же типа;
- скобки закрываются в правильном порядке;
- нет открывающих или закрывающих скобок без пары.

```text
"()[]{}" -> true
"{[]}"   -> true
"(]"     -> false
"([)]"   -> false
"("      -> false
"]"      -> false
```

Пустая строка считается валидной.

<details>
<summary>Решение</summary>

### Неоптимальный подход: удалять готовые пары

Можно многократно удалять из строки `()`, `[]` и `{}`, пока строка меняется.
Если в конце ничего не осталось, последовательность валидна.

- время в худшем случае: `O(n²)` из-за повторных проходов и создания строк;
- дополнительная память: `O(n)`.

### Оптимальный подход: стек

Открывающие скобки кладём в стек. Для каждой закрывающей скобки проверяем, что
на вершине находится соответствующая открывающая. После обхода стек должен быть
пуст.

```go
func IsValidBrackets(value string) bool {
    pairs := map[byte]byte{
        ')': '(',
        ']': '[',
        '}': '{',
    }

    stack := make([]byte, 0, len(value))
    for i := 0; i < len(value); i++ {
        bracket := value[i]

        switch bracket {
        case '(', '[', '{':
            stack = append(stack, bracket)
        case ')', ']', '}':
            if len(stack) == 0 || stack[len(stack)-1] != pairs[bracket] {
                return false
            }
            stack = stack[:len(stack)-1]
        default:
            return false
        }
    }

    return len(stack) == 0
}
```

- время: `O(n)`;
- дополнительная память: `O(n)` в худшем случае, когда строка состоит только
  из открывающих скобок.

Линейное время оптимально: в худшем случае нужно проверить каждый символ.
Использование `byte` корректно, потому что по условию строка состоит только из
однобайтовых ASCII-скобок.

</details>

## 26. IDE-поиск по подпоследовательности

Представьте, что разработчик примерно помнит название файла и ищет его в IDE.
Нужно определить, является ли строка запроса подпоследовательностью имени
файла.

Символы запроса должны встречаться в том же порядке, но необязательно подряд:

```text
IDESearch("crdle",   "crocodile.txt") -> true
IDESearch("le",      "crocodile.txt") -> true
IDESearch("el",      "crocodile.txt") -> false
IDESearch("coco",    "crocodile.txt") -> true
IDESearch("crdleee", "crocodile.txt") -> false
IDESearch("crkdl",   "crocodile.txt") -> false

IDESearch("кдл", "крокодил.txt") -> true
IDESearch("лик", "крокодил.txt") -> false
```

Пустая строка запроса считается подпоследовательностью любого имени. Поиск
регистрозависимый.

<details>
<summary>Решение</summary>

### Неоптимальный подход: искать через LCS

Можно найти длину наибольшей общей подпоследовательности запроса и имени файла,
а затем сравнить её с длиной запроса. Это решает более общую задачу, чем нужно.

- время: `O(q * n)`;
- дополнительная память: до `O(q * n)`;

где `q` и `n` — количество Unicode-символов в запросе и имени файла.

### Оптимальный подход: два указателя

Идём по имени файла слева направо. Указатель запроса двигаем только тогда,
когда нашли ожидаемый символ. Если дошли до конца запроса, все его символы
встретились в правильном порядке.

```go
func IDESearch(query, fileName string) bool {
    // Индексировать UTF-8 строку напрямую нельзя: русская буква занимает
    // несколько байт. []rune представляет строку Unicode-символами.
    queryRunes := []rune(query)

    // Пустой запрос является подпоследовательностью любой строки.
    if len(queryRunes) == 0 {
        return true
    }

    // Индекс символа запроса, который нужно найти следующим.
    queryIndex := 0

    // range перебирает имя файла по рунам, а не по отдельным байтам UTF-8.
    for _, fileRune := range fileName {
        if fileRune != queryRunes[queryIndex] {
            continue
        }

        queryIndex++
        if queryIndex == len(queryRunes) {
            return true
        }
    }

    return false
}
```

- время: `O(q + n)` по числу Unicode-символов;
- дополнительная память: `O(q)` для `[]rune(query)`.

Для контракта только с ASCII можно использовать индексы байтов и получить
`O(1)` дополнительной памяти. В именах файлов возможны кириллица и другие
Unicode-символы, поэтому вариант с рунами безопаснее и понятнее.

</details>

## 27. Проверка строк на изоморфность

Даны две строки из букв латинского алфавита. Нужно определить, являются ли
они изоморфными.

Строки изоморфны, если каждый символ первой строки можно заменить одним
символом второй строки так, чтобы получить вторую строку. Замена должна
соблюдать два правила:

- все вхождения одного символа заменяются одинаково;
- разные символы первой строки не могут заменяться одним символом второй.

Символ может соответствовать самому себе. Сравнение регистрозависимое.

```text
AreIsomorphic("core",    "rock")     -> true
AreIsomorphic("coffee",  "dollar")   -> false
AreIsomorphic("egg",     "add")      -> true
AreIsomorphic("foo",     "bar")      -> false
AreIsomorphic("paper",   "title")    -> true
AreIsomorphic("example", "aaaaaaaa") -> false
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: сравнить все пары позиций

Для каждой пары индексов `i` и `j` проверяем одинаковое отношение между
символами обеих строк:

```text
first[i] == first[j] должно совпадать с second[i] == second[j]
```

Если в первой строке символы равны, а во второй различаются, замена
непоследовательна. Если в первой строке символы различаются, а во второй равны,
два разных символа заменяются одним.

- время: `O(n²)`;
- дополнительная память: `O(1)`.

### Оптимальный подход: два отображения

Во время одного прохода храним соответствия в обе стороны. Отображение
`firstToSecond` проверяет, что символ первой строки всегда заменяется одинаково.
Отображение `secondToFirst` не позволяет двум разным символам первой строки
соответствовать одному символу второй.

```go
func AreIsomorphic(first, second string) bool {
    if len(first) != len(second) {
        return false
    }

    firstToSecond := make(map[byte]byte)
    secondToFirst := make(map[byte]byte)

    for i := 0; i < len(first); i++ {
        firstChar := first[i]
        secondChar := second[i]

        if mapped, exists := firstToSecond[firstChar]; exists && mapped != secondChar {
            return false
        }
        if mapped, exists := secondToFirst[secondChar]; exists && mapped != firstChar {
            return false
        }

        firstToSecond[firstChar] = secondChar
        secondToFirst[secondChar] = firstChar
    }

    return true
}
```

- время: `O(n)`;
- дополнительная память: `O(1)`, потому что размер латинского алфавита
  ограничен.

Для произвольного алфавита память составит `O(k)`, где `k` — число различных
символов. По условию допустимы только латинские буквы, поэтому обход по байтам
корректен. Для Unicode понадобятся отображения `map[rune]rune`.

</details>

## 28. Произведение массива кроме текущего элемента

Дан массив целых чисел `nums`. Нужно вернуть массив той же длины, где
`result[i]` — произведение всех элементов `nums`, кроме элемента с индексом `i`.

```text
nums   = [1, 2, 3, 4]
result = [24, 12, 8, 6]

result[0] = 2 * 3 * 4 = 24
result[1] = 1 * 3 * 4 = 12
result[2] = 1 * 2 * 4 = 8
result[3] = 1 * 2 * 3 = 6
```

Нужно решить задачу за `O(n)` времени без деления. Входной массив менять
нельзя; нули и отрицательные числа допустимы:

```text
[1, 0, 3, 4] -> [0, 12, 0, 0]
[0, 2, 0]    -> [0, 0, 0]
[-1, 2, -3]  -> [-6, 3, -2]
```

Для этого варианта задачи считаем, что все промежуточные произведения и
ответы помещаются в `int`. Для пустого массива возвращаем пустой результат,
для одного элемента — `[1]`: произведение пустого набора чисел равно единице.

<details>
<summary>Решение</summary>

### Неоптимальный подход: отдельный обход для каждого элемента

Для каждого индекса `i` перемножаем все элементы, пропуская индекс `i`.

- время: `O(n²)`, где `n` — длина массива;
- память результата: `O(n)`;
- дополнительная память сверх результата: `O(1)`.

### Оптимальный подход: произведения слева и справа

Ответ для каждой позиции — произведение элементов слева от неё, умноженное
на произведение элементов справа. Сам текущий элемент в эти произведения
не входит.

За первый проход записываем в `result` произведения слева. За второй проход
идём справа налево и домножаем каждую позицию на произведение справа.

```go
func ProductExceptSelf(nums []int) []int {
    result := make([]int, len(nums)) // O(n) памяти под результат.

    leftProduct := 1
    for index := 0; index < len(nums); index++ { // O(n) времени.
        result[index] = leftProduct
        // Текущий элемент понадобится для следующей позиции.
        leftProduct *= nums[index]
    }

    rightProduct := 1
    for index := len(nums) - 1; index >= 0; index-- { // O(n) времени.
        result[index] *= rightProduct
        rightProduct *= nums[index]
    }

    return result
}
```

Для `[1, 2, 3, 4]` вычисления выглядят так:

```text
Элементы:            [1,  2, 3, 4]
Произведения слева:  [1,  1, 2, 6]  // result после первого прохода
Произведения справа: [24, 12, 4, 1]  // значения rightProduct для этих позиций
Результат:           [24, 12, 8, 6]  // перемножаем значения в каждой позиции
```

Начинаем с `1`, потому что слева от первого и справа от последнего элемента
ничего нет. Единица при умножении не меняет ответ. Отдельный массив
произведений справа не создаём — достаточно переменной `rightProduct`.

- время: `O(n)` — два прохода по массиву;
- память результата: `O(n)`;
- дополнительная память сверх результата: `O(1)`.

Нули обрабатываются теми же умножениями, отдельные условия для них не нужны.
Линейное время оптимально: нужно заполнить все `n` позиций результата.

</details>

## 29. Уникальные теги объявлений

Продавцы добавляют к объявлениям теги. Нужно вернуть все уникальные теги в
порядке их первого появления.

```text
ads = [
  {title: "Квартира", tags: ["срочно", "ремонт"]},
  {title: "Машина",   tags: ["срочно", "новая"]},
  {title: "Телефон",  tags: ["б/у", "ремонт"]}
]

result = ["срочно", "ремонт", "новая", "б/у"]
```

```go
type Ad struct {
    Title string
    Tags  []string
}
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: искать тег в результате

Для каждого тега линейно проверяем, добавляли ли его раньше. В худшем случае
результат приходится просматривать почти целиком для каждого входного тега.

- время: `O(t * u)`, где `t` — общее число тегов, `u` — число уникальных;
- память результата: `O(u)`;
- дополнительная память сверх результата: `O(1)`.

### Оптимальный подход: множество просмотренных тегов

Map позволяет за ожидаемое `O(1)` проверить, встречался ли тег. Новый тег сразу
добавляем и в множество, и в результат. Второй проход по map не нужен: порядок
обхода map в Go не определён и не сохранил бы порядок первого появления.

```go
func UniqueTags(ads []Ad) []string {
    seen := make(map[string]struct{})
    var result []string

    for _, ad := range ads {
        for _, tag := range ad.Tags {
            if _, exists := seen[tag]; exists {
                continue
            }

            seen[tag] = struct{}{}
            result = append(result, tag)
        }
    }

    return result
}
```

- ожидаемое время: `O(t)`;
- память результата: `O(u)`;
- дополнительная память: `O(u)` для множества `seen`.

</details>

## 30. Топ-3 продавцов по числу лайков

Даны два массива одинаковой длины: имена продавцов и количество полученных
ими лайков. Нужно вернуть имена трёх продавцов с наибольшим числом лайков.

Если лайков поровну, выше располагается продавец, который раньше встречается
во входном массиве. Если продавцов меньше трёх, возвращаем их всех.

```text
names = ["Анна", "Борис", "Виктор", "Галина", "Дмитрий"]
likes = [10, 30, 20, 30, 5]

result = ["Борис", "Галина", "Виктор"]
```

<details>
<summary>Решение</summary>

### Простой подход: стабильная сортировка

Объединяем имя и число лайков в одну структуру, а затем стабильно сортируем по
убыванию лайков. Стабильность сохраняет исходный порядок продавцов с равным
числом лайков.

- время: `O(n log n)`;
- дополнительная память: `O(n)` для копии продавцов.

### Оптимальный подход для фиксированного топ-3

Храним отсортированный список не более чем из трёх лучших продавцов. Для
каждого нового продавца находим место среди текущих лидеров, вставляем его и
удаляем четвёртого. Размер списка постоянный, поэтому вставка занимает `O(1)`.

```go
type sellerScore struct {
    name  string
    likes int
}

func TopSellers(names []string, likes []int) []string {
    const topSize = 3

    top := make([]sellerScore, 0, topSize+1)

    for index, name := range names {
        candidate := sellerScore{
            name:  name,
            likes: likes[index],
        }

        insertAt := len(top)
        for insertAt > 0 && candidate.likes > top[insertAt-1].likes {
            insertAt--
        }

        top = append(top, candidate)
        copy(top[insertAt+1:], top[insertAt:])
        top[insertAt] = candidate

        if len(top) > topSize {
            top = top[:topSize]
        }
    }

    result := make([]string, len(top))
    for index, seller := range top {
        result[index] = seller.name
    }

    return result
}
```

При равенстве лайков кандидат не двигается перед уже просмотренным продавцом,
потому что в условии вставки используется `>`, а не `>=`. Так сохраняется
порядок исходного массива.

- время: `O(n)`, поскольку размер `top` не превышает четырёх элементов во
  время вставки;
- память результата: `O(1)` для фиксированного размера три;
- дополнительная память: `O(1)`.

Если размер топа задаётся переменной `k`, тот же подход работает за `O(n * k)`.
Для большого `k` используют min-heap размера `k` и получают `O(n log k)`.

</details>

## 31. Проверка двух бинарных деревьев на равенство

Даны корни двух бинарных деревьев. Нужно проверить, совпадают ли их структура
и значения соответствующих узлов.

```text
first:          second:
    1               1
   / \             / \
  2   3           2   3

result = true
```

Если в одной и той же позиции одного дерева находится узел, а другого — `nil`,
деревья различаются. Два пустых дерева считаются равными.

```go
type TreeNode struct {
    ID    int
    Left  *TreeNode
    Right *TreeNode
}
```

<details>
<summary>Решение</summary>

### Неоптимальный подход: сериализовать оба дерева

Можно преобразовать деревья в последовательности, обязательно записывая
маркеры `nil`, а затем сравнить последовательности. Маркеры нужны, чтобы
различать деревья с одинаковыми значениями, но разной структурой.

- время: `O(n + m)`;
- дополнительная память: `O(n + m)` для двух последовательностей.

### Оптимальный подход: одновременный обход

Сравниваем соответствующие узлы сразу во время обхода. Если оба узла равны
`nil`, эта часть деревьев совпадает. Если только один равен `nil` или
различаются идентификаторы, деревья различаются.

```go
func EqualTrees(first, second *TreeNode) bool {
    if first == nil || second == nil {
        return first == second
    }

    if first.ID != second.ID {
        return false
    }

    return EqualTrees(first.Left, second.Left) &&
        EqualTrees(first.Right, second.Right)
}
```

- время: `O(n)` в худшем случае, когда оба дерева содержат `n` узлов и равны;
- дополнительная память: `O(h)` для стека рекурсии, где `h` — высота дерева.

Обход завершится раньше, если найдётся первое различие. В вырожденном дереве
глубина рекурсии достигает `O(n)`; итеративный обход заменит стек вызовов явным
стеком, но не улучшит асимптотическую оценку памяти.

</details>

## Interview-ready answer

**1. Как начинать решение алгоритмической задачи?**

- Шаг 1 — зафиксировать контракт, ограничения и пограничные случаи.
- Шаг 2 — назвать простое корректное решение и оценить его время и память.
- Шаг 3 — только после этого устранять конкретное узкое место.

**2. Почему недостаточно назвать только сложность по времени?**

- Причина — ускорение почти всегда покупается памятью, поэтому одна цифра не описывает решение.
- Hash map — меняет `O(n²)` на ожидаемое `O(n)` ценой памяти под таблицу.
- Heap — ограничивает память до `O(k)` вместо хранения всех элементов.
- Корзины по частоте — дают линейное время ценой `O(n)` памяти.
- Вывод — на собеседовании нужно озвучить обе стороны.

**3. Когда `O(n)` с hash map не является строгой гарантией?**

- Причина — операции hash map дают `O(1)` в среднем, поэтому итоговая линейная оценка ожидаемая, а не гарантированная.
- Если нужна строгая граница — сортировка, дерево поиска или ограничение диапазона ключей.

**4. Что означает оптимальное решение для задачи с большим результатом?**

- Главное — учитывать размер самого вывода: быстрее, чем его напечатать, алгоритм быть не может.
- Пример со скобками — генерация всех правильных скобочных последовательностей не может быть быстрее `O(Cₙ * n)`.
- Пример с деревом — вывод всех путей не может быть быстрее их суммарной длины.

**5. Какие детали Go важно проговорить?**

- Байты и руны — для Unicode это разные вещи, `len` считает байты.
- Порядок обхода map — не определён, закладываться на него нельзя.
- Входной slice — не менять без согласованного контракта: backing-массив общий с вызывающим.
- Переполнение `int` — учитывать в арифметике, особенно при сложении и умножении больших значений.
