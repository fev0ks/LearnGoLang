# Задачи на code review

Здесь собраны задачи формата «найти проблемы, объяснить последствия и предложить
исправление». Они проверяют не запоминание шаблона, а умение разбирать чужой
код: отделять compile-time ошибки от runtime-сбоев, восстанавливать контракт API,
проверять жизненный цикл goroutine и каналов, а для работы с состоянием — границы
транзакции и модель хранения данных. На внешней HTTP-границе к этому добавляются
timeout, типизированные ответы, идемпотентность и безопасная политика повторов.

## Материалы

Начать с [00. План code review на собеседовании](./00-code-review-playbook.md):
контракт и карта выполнения, приоритеты находок, чеклист Go/backend, расписание
на 30 и 60 минут, проверка исправлений и обсуждение результата.

В каждом разборе есть отдельный раздел с тестами. Примеры показывают не только
assertions, но и организацию сценария: `httptest`, реальные транзакции либо
каналы `started`/`release` вместо случайных задержек.

1. [Fetcher с кэшем](./01-fetcher-with-cache.md) — конечная batch-операция:
   `nil`-каналы, конкурентный доступ к кэшу, закрытие результата, отмена,
   дубликаты и cache stampede.
2. [Background Task Processor](./02-background-task-processor.md) —
   долгоживущий in-process pool: конкурентные `Submit` и `Stop`, retry,
   backoff, drain, panic boundary и потеря задач при падении процесса.
3. [Списание баланса и ledger](./03-balance-withdrawal-and-ledger.md) — работа с
   деньгами в PostgreSQL: незакрытая транзакция, непроверенные ошибки, `float`
   вместо целых, lost update, идемпотентность и append-only журнал операций.
4. [HTTP-клиент платёжного сервиса](./04-payment-http-client.md) — внешний
   платёжный вызов: JSON-контракт, timeout, response body, типизированные ошибки,
   `Idempotency-Key` и безопасные повторы.
5. [Оформление бронирования](./05-booking-order.md) — блокировка пользователя,
   гарантированный cleanup, ограниченный retry, `context` и идемпотентность
   внешнего бронирования.
6. [Профиль клиента через singleflight](./06-customer-profile-singleflight.md) —
   cache stampede, необходимость общей `singleflight.Group`, составной ключ,
   независимая отмена waiter и владение общим результатом.
7. [Batch с семафором](./07-batch-with-semaphore.md) — место захвата разрешения,
   ограничение числа goroutines, гарантированный `Release`, fail-fast и порядок
   результатов.
8. [Агрегатор через errgroup](./08-errgroup-aggregator.md) — первая ошибка,
   производный context, обязательные части ответа, `SetLimit` и `TryGo`.
9. [Worker pool с сохранением порядка](./09-ordered-worker-pool.md) — deadlock
   между `Wait` и чтением результатов, ownership каналов, индексы и отмена.
10. [Первый успешный провайдер](./10-first-successful-provider.md) — первый успех
    вместо первого завершения, отмена проигравших и доставка их результатов без
    утечек goroutines.
11. [Фоновая работа из HTTP-handler](./11-background-work-from-handler.md) —
    время жизни request context, bounded execution, durable queue и shutdown.
12. [Pipeline с ранним выходом](./12-cancellable-pipeline.md) — отменяемые send и
    receive, остановка upstream и закрытие канала с несколькими producers.
13. [Денежный перевод и transactional outbox](./13-money-transfer-and-outbox.md) —
    атомарный debit/credit, row locks, idempotency key, события после commit и

## Чем различаются задачи

| Задача | Главный инвариант | Основной риск |
| --- | --- | --- |
| Fetcher | Один outcome на вход, конечный batch | Утечка goroutine и cache stampede |
| Task Processor | Принятая задача получает terminal outcome | Потеря задачи при shutdown |
| Списание баланса | Баланс и ledger изменяются атомарно | Двойное или потерянное списание |
| Payment HTTP client | Неизвестный результат безопасно повторяется | Повторный платёж |
| Бронирование | Lock всегда освобождается, retry конечен | Вечная блокировка пользователя |
| Singleflight | Один in-flight вызов на полный ключ | Смешение tenants и общая отмена |
| Semaphore batch | Вызовов loader не больше `limit`, goroutines не ждут семафор | Утечка разрешения и deadlock |
| Errgroup aggregator | Обязательные части либо собраны все, либо ошибка | Скрытая ошибка и неверный context |
| Ordered worker pool | Результат сохраняет позицию входа | Deadlock coordinator и workers |
| First successful | Возвращается первый успех, проигравшие получают отмену | Быстрая ошибка побеждает успех |
| Background handler | После `202` работа имеет владельца и durable state | Потеря работы при возврате handler или crash |
| Cancellable pipeline | Ошибка downstream останавливает весь upstream | Goroutines остаются на send |
| Money transfer | Debit, credit, transfer и events фиксируются атомарно | Частичный или повторный перевод |

## Как работать с задачей

1. Сначала проверить, компилируется ли код.
2. Зафиксировать контракт: порядок, дубликаты, ошибки, backpressure и shutdown.
3. Назвать блокирующие дефекты раньше архитектурных улучшений.
4. Для каждого дефекта описать конкретный симптом: compile error, deadlock,
   panic, data race, утечку goroutine, потерю данных или расхождение состояния
   в БД.
5. Предложить минимальное исправление, а затем production trade-offs.
6. Проверить решение тестами, включая `go test -race`.

Важно различать дефект и допустимый выбор. Например, блокирующий `Submit` — это
форма backpressure, а не ошибка сам по себе. Ошибкой становится отсутствие
описанного контракта, отмены или ограничения времени ожидания.

## Что должен показать senior-разработчик

- **Приоритизация —** сначала объяснить, что мешает коду запуститься или
  завершиться, затем обсуждать API и эксплуатацию.
- **Точная терминология —** не путать отправку в `nil`-канал с отправкой в
  закрытый канал, data race с логической гонкой, а backpressure с её отсутствием.
- **Ownership —** определить, кто закрывает канал, кому принадлежит изменяемая
  задача и когда принятая работа становится ответственностью processor’а.
- **Lifecycle —** проверить повторный `Start`, конкурентные `Submit`/`Stop`,
  отмену ожидания и завершение in-flight работы.
- **Практический контракт —** назвать гарантии порядка, доставки, повторов и
  поведения при рестарте процесса.
- **Границы транзакции —** для кода, меняющего состояние в БД: где транзакция
  открывается и закрывается, что удерживает блокировку, какие ошибки повторяемы
  и что делает повторный вызов с тем же входом.
- **Проверяемость —** писать детерминированные тесты с каналами-сигналами вместо
  надежды на случайный `time.Sleep`.
