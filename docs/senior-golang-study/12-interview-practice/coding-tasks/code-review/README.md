# Задачи на code review

Здесь собраны задачи формата «найти проблемы, объяснить последствия и предложить
исправление». Они проверяют не запоминание шаблона, а умение разбирать чужой
код: отделять compile-time ошибки от runtime-сбоев, восстанавливать контракт API,
проверять жизненный цикл goroutine и каналов, а для работы с состоянием — границы
транзакции и модель хранения данных.

---

## Материалы

1. [Fetcher с кэшем](./01-fetcher-with-cache.md) — конечная batch-операция:
   `nil`-каналы, конкурентный доступ к кэшу, закрытие результата, отмена,
   дубликаты и cache stampede.
2. [Background Task Processor](./02-background-task-processor.md) —
   долгоживущий in-process pool: конкурентные `Submit` и `Stop`, retry,
   backoff, drain, panic boundary и потеря задач при падении процесса.
3. [Списание баланса и ledger](./03-balance-withdrawal-and-ledger.md) — работа с
   деньгами в PostgreSQL: незакрытая транзакция, непроверенные ошибки, `float`
   вместо целых, lost update, идемпотентность и append-only журнал операций.

---

## Чем различаются задачи

| Свойство | Fetcher | Task Processor | Списание баланса |
| --- | --- | --- | --- |
| Жизненный цикл | Один batch и завершение | `Start` → много `Submit` → `Stop` | Один вызов внутри транзакции |
| Результат | Один outcome на завершённый вход | Побочный эффект обработчика | Изменение состояния в БД |
| Основной риск | Утечка goroutine и stampede | Потеря принятой задачи при shutdown | Двойное или потерянное списание |
| Повторная попытка | Обычно внутри запроса | Часть жизненного цикла задачи | Требует ключа идемпотентности |
| Хранилище | Ограниченный кэш | Очередь; для durability нужна внешняя система | PostgreSQL как источник правды |

---

## Как работать с задачей

1. Сначала проверить, компилируется ли код.
2. Зафиксировать контракт: порядок, дубликаты, ошибки, backpressure и shutdown.
3. Назвать блокирующие дефекты раньше архитектурных улучшений.
4. Для каждого дефекта описать конкретный симптом: compile error, deadlock,
   panic, data race, утечку goroutine, потерю данных или расхождение состояния
   в БД.
5. Предложить минимальное исправление, а затем production trade-offs.
6. Проверить решение тестами, включая `go test -race`.

Важно различать дефект и допустимый выбор. Например, блокирующий `Submit` — это
форма backpressure, а не ошибка сам по себе. Ошибкой становится отсутствие
описанного контракта, отмены или ограничения времени ожидания.

---

## Что должен показать senior-разработчик

- **Приоритизация —** сначала объяснить, что мешает коду запуститься или
  завершиться, затем обсуждать API и эксплуатацию.
- **Точная терминология —** не путать отправку в `nil`-канал с отправкой в
  закрытый канал, data race с логической гонкой, а backpressure с её отсутствием.
- **Ownership —** определить, кто закрывает канал, кому принадлежит изменяемая
  задача и когда принятая работа становится ответственностью processor’а.
- **Lifecycle —** проверить повторный `Start`, конкурентные `Submit`/`Stop`,
  отмену ожидания и завершение in-flight работы.
- **Практический контракт —** назвать гарантии порядка, доставки, повторов и
  поведения при рестарте процесса.
- **Границы транзакции —** для кода, меняющего состояние в БД: где транзакция
  открывается и закрывается, что удерживает блокировку, какие ошибки повторяемы
  и что делает повторный вызов с тем же входом.
- **Проверяемость —** писать детерминированные тесты с каналами-сигналами вместо
  надежды на случайный `time.Sleep`.
