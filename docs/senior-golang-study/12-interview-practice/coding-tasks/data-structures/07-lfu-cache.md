LFU (`Least Frequently Used`) — cache, который при заполнении вытесняет запись
с наименьшим числом обращений. Задача проверяет не столько умение увеличить
счётчик, сколько способность поддержать выбор жертвы без линейного обхода всего
cache.

---

## Формулировка и контракт

> Реализуйте LFU cache фиксированной ёмкости. `Get` и `Put` должны работать за
> ожидаемое `O(1)`. При переполнении вытесняется ключ с минимальной частотой.
> Если частоты равны, вытесняется ключ, который использовали раньше остальных.

Перед кодом нужно согласовать семантику операций:

1. `Get` существующего ключа увеличивает его частоту на один.
2. `Put` нового ключа создаёт запись с частотой `1`.
3. `Put` существующего ключа обновляет значение и считается обращением, поэтому
   тоже увеличивает частоту.
4. При одинаковой частоте действует LRU-порядок внутри этой частоты.
5. `Get` отсутствующего ключа возвращает zero value и `false`.
6. Неположительная ёмкость считается ошибкой конструктора.
7. Базовая реализация не является потокобезопасной.

Иной контракт тоже возможен. Например, обновление через `Put` можно не считать
обращением, но это решение должно быть явным: оно меняет будущую жертву.

---

## Ментальная модель

Обычный LRU хранит один список от недавно использованных записей к давно не
использованным. LFU добавляет второй уровень: сначала записи группируются по
частоте, а внутри каждой группы сохраняется LRU-порядок.

```text
items: key -> запись

frequency buckets:

freq=1:  [D newest] <-> [C oldest]
freq=2:  [B newest] <-> [A oldest]
freq=5:  [E]
          ^
          список внутри одной частоты

minFreq = 1
жертва = хвост списка freq=1 = C
```

Здесь `minFreq` сразу указывает группу с минимальной частотой. Хвост списка этой
группы сразу указывает на наименее недавнюю запись среди равных кандидатов.
Поэтому при вытеснении не требуется искать минимум по всем ключам.

## Почему одного счётчика недостаточно

Наивная реализация хранит частоту рядом со значением:

```go
type entry struct {
    value Profile
    freq  int
}

type Cache struct {
    items map[string]entry
}
```

`Get` действительно остаётся ожидаемым `O(1)`: запись находится через `map`, а
счётчик увеличивается. Проблема появляется в `Put`, когда заполненному cache
нужно выбрать минимальную частоту. Без дополнительного индекса приходится
обойти все `C` записей:

```go
victimFreq := math.MaxInt
for key, item := range cache.items {
    if item.freq < victimFreq {
        victimKey = key
        victimFreq = item.freq
    }
}
```

Такая операция занимает `O(C)`. Кроме того, обход `map` не задаёт LRU-порядок,
поэтому результат при равных частотах становится случайным с точки зрения
контракта.

Min-heap решает поиск минимальной частоты за `O(log C)`, но для ожидаемого
`O(1)` нужен прямой доступ и к записи, и к группе её текущей частоты.

## Структуры данных для ожидаемого O1

Решение объединяет четыре сущности:

| Сущность | Роль |
| --- | --- |
| `items map[string]*entry` | находит запись по ключу |
| `frequencies map[int]*list.List` | находит список записей заданной частоты |
| `entry.element` | позволяет удалить запись из её списка без поиска |
| `minFreq` | указывает минимальную непустую частоту |

В каждом списке наиболее недавняя запись находится в начале, а кандидат на
вытеснение — в конце.

### Что делает Get

Для найденной записи с частотой `f`:

1. удалить её элемент из списка `frequencies[f]`;
2. если список опустел, удалить сам список;
3. если опустевшая частота равна `minFreq`, увеличить `minFreq` до `f + 1`;
4. увеличить частоту записи;
5. поместить запись в начало списка `frequencies[f+1]`.

После `Get` текущая запись обязательно существует в группе `f + 1`. Поэтому,
если она была последней записью минимальной группы, следующая минимальная
частота равна именно `f + 1`, а искать её не нужно.

### Что делает Put нового ключа

Если cache заполнен:

1. взять список `frequencies[minFreq]`;
2. удалить его последний элемент;
3. удалить ключ жертвы из `items`.

Затем новая запись добавляется с частотой `1`, поэтому `minFreq` становится
равным `1` независимо от предыдущего значения.

---

## Пошаговый пример

Пусть ёмкость равна трём. Начальные вставки создают три записи с частотой `1`:

```text
Put(A), Put(B), Put(C)

freq=1: [C] <-> [B] <-> [A]
minFreq=1
```

Начало списка находится слева. `C` вставлен последним и является наиболее
недавним, `A` — кандидатом на вытеснение среди записей этой частоты.

После `Get(A)` ключ переходит из группы `1` в группу `2`:

```text
freq=1: [C] <-> [B]
freq=2: [A]
minFreq=1
```

После `Get(B)` обе записи `A` и `B` имеют частоту `2`, но `B` использовали
позже:

```text
freq=1: [C]
freq=2: [B] <-> [A]
minFreq=1
```

Теперь `Put(D)` должен вытеснить `C`, потому что его частота меньше:

```text
до:       freq=1: [C]
операция: Put(D) -> evict(C) -> insert(D, freq=1)
после:    freq=1: [D]
          freq=2: [B] <-> [A]
          minFreq=1
```

Если бы `C` тоже имел частоту `2`, жертвой стал бы хвост соответствующего
списка — наименее недавно использованный ключ среди записей с частотой `2`.

## Реализация на Go

Код обходится без generics: ключ — `string`, значение — структура `Profile`.
Конкретные типы убирают `[K comparable, V any]` из каждой сигнатуры, поэтому
видна только механика частотных списков. Обобщение до
`Cache[K comparable, V any]` сводится к замене двух типов на параметры и логику
не меняет.

```go
package lfu

import (
    "container/list"
    "errors"
)

var ErrInvalidCapacity = errors.New("lfu: capacity must be positive")

// Profile — значение, которое хранит cache.
type Profile struct {
    Name  string
    Email string
}

type entry struct {
    key     string
    value   Profile
    freq    int
    element *list.Element
}

type Cache struct {
    capacity    int
    items       map[string]*entry
    frequencies map[int]*list.List
    minFreq     int
}

func New(capacity int) (*Cache, error) {
    if capacity <= 0 {
        return nil, ErrInvalidCapacity
    }

    return &Cache{
        capacity:    capacity,
        items:       make(map[string]*entry, capacity),
        frequencies: make(map[int]*list.List),
    }, nil
}

func (c *Cache) Get(key string) (Profile, bool) {
    item, ok := c.items[key]
    if !ok {
        return Profile{}, false
    }

    c.promote(item)
    return item.value, true
}

func (c *Cache) Put(key string, value Profile) {
    if item, ok := c.items[key]; ok {
        item.value = value
        c.promote(item)
        return
    }

    if len(c.items) == c.capacity {
        c.evict()
    }

    item := &entry{
        key:   key,
        value: value,
        freq:  1,
    }
    bucket := c.bucket(1)
    item.element = bucket.PushFront(item)
    c.items[key] = item
    c.minFreq = 1
}

func (c *Cache) Len() int {
    return len(c.items)
}

func (c *Cache) promote(item *entry) {
    oldFreq := item.freq
    oldBucket := c.frequencies[oldFreq]
    oldBucket.Remove(item.element)

    if oldBucket.Len() == 0 {
        delete(c.frequencies, oldFreq)
        if c.minFreq == oldFreq {
            c.minFreq = oldFreq + 1
        }
    }

    item.freq++
    newBucket := c.bucket(item.freq)
    item.element = newBucket.PushFront(item)
}

func (c *Cache) evict() {
    bucket := c.frequencies[c.minFreq]
    victimElement := bucket.Back()
    victim := victimElement.Value.(*entry)

    bucket.Remove(victimElement)
    delete(c.items, victim.key)
    if bucket.Len() == 0 {
        delete(c.frequencies, c.minFreq)
    }
}

func (c *Cache) bucket(freq int) *list.List {
    bucket, ok := c.frequencies[freq]
    if !ok {
        bucket = list.New()
        c.frequencies[freq] = bucket
    }
    return bucket
}
```

`entry.element` хранит указатель на узел `container/list`, а не дублирует сам
список. Благодаря этому `promote` удаляет нужный узел напрямую. Если хранить
только ключ и частоту, поиск узла внутри списка снова станет линейным.

Внутренние методы предполагают соблюдение инвариантов. Например, `evict`
вызывается только для непустого заполненного cache, поэтому список
`frequencies[minFreq]` существует и содержит хотя бы один элемент.

## Тесты

Тесты должны проверять отдельно минимальную частоту и LRU-порядок внутри одной
частоты. Только проверка размера не обнаружит ошибку выбора жертвы.

```go
package lfu

import (
    "errors"
    "testing"
)

func profile(name string) Profile {
    return Profile{Name: name, Email: name + "@example.com"}
}

func TestLFUEvictsLeastFrequentlyUsed(t *testing.T) {
    cache, err := New(2)
    if err != nil {
        t.Fatal(err)
    }

    cache.Put("ann", profile("ann"))
    cache.Put("bob", profile("bob"))
    if _, ok := cache.Get("ann"); !ok {
        t.Fatal("expected ann to exist")
    }

    cache.Put("cid", profile("cid"))

    if _, ok := cache.Get("bob"); ok {
        t.Fatal("bob must be evicted because it has the lowest frequency")
    }
    if value, ok := cache.Get("ann"); !ok || value.Name != "ann" {
        t.Fatalf("Get(ann) = (%+v, %t), want ann and true", value, ok)
    }
    if value, ok := cache.Get("cid"); !ok || value.Name != "cid" {
        t.Fatalf("Get(cid) = (%+v, %t), want cid and true", value, ok)
    }
}

func TestLFUBreaksFrequencyTiesByLRU(t *testing.T) {
    cache, err := New(2)
    if err != nil {
        t.Fatal(err)
    }

    cache.Put("ann", profile("ann"))
    cache.Put("bob", profile("bob"))
    cache.Put("cid", profile("cid"))

    if _, ok := cache.Get("ann"); ok {
        t.Fatal("ann must be evicted as the least recent key at frequency 1")
    }
    if _, ok := cache.Get("bob"); !ok {
        t.Fatal("bob must remain")
    }
}

func TestLFUUpdateCountsAsAccess(t *testing.T) {
    cache, err := New(2)
    if err != nil {
        t.Fatal(err)
    }

    cache.Put("ann", profile("ann"))
    cache.Put("bob", profile("bob"))
    cache.Put("ann", Profile{Name: "ann", Email: "ann@new.example.com"})
    cache.Put("cid", profile("cid"))

    if _, ok := cache.Get("bob"); ok {
        t.Fatal("bob must be evicted")
    }
    if value, ok := cache.Get("ann"); !ok || value.Email != "ann@new.example.com" {
        t.Fatalf("Get(ann) = (%+v, %t), want the updated email and true", value, ok)
    }
    if cache.Len() != 2 {
        t.Fatalf("Len() = %d, want 2", cache.Len())
    }
}

func TestLFURejectsInvalidCapacity(t *testing.T) {
    _, err := New(0)
    if !errors.Is(err, ErrInvalidCapacity) {
        t.Fatalf("New() error = %v, want ErrInvalidCapacity", err)
    }
}
```

Для изменений с синхронизацией к обычному запуску добавляется `go test -race`.
Сам базовый вариант намеренно не поддерживает конкурентные вызовы.

## Сложность и инварианты

| Операция | Ожидаемое время | Почему |
| --- | --- | --- |
| `Get` miss | `O(1)` | один lookup в `items` |
| `Get` hit | `O(1)` | lookup, удаление узла и вставка узла |
| `Put` update | `O(1)` | lookup и тот же переход частоты |
| `Put` insert | `O(1)` | прямая жертва через `minFreq` и хвост списка |
| `Len` | `O(1)` | длина `map` |

Сложность является ожидаемой из-за использования хеш-таблиц Go. Память равна
`O(C)`: каждая запись находится ровно в одном частотном списке, а число непустых
списков не превышает число записей.

Корректная реализация поддерживает следующие инварианты:

1. каждый ключ из `items` находится ровно в одном частотном списке;
2. `entry.freq` совпадает с частотой списка, содержащего запись;
3. `entry.element` указывает именно на узел этой записи;
4. пустые частотные списки удаляются;
5. для непустого cache `minFreq` указывает на существующий непустой список;
6. начало списка является MRU, конец — LRU внутри одной частоты.

Проверка инвариантов в тестовом helper полезнее большого числа случайных
примеров: она локализует рассинхронизацию трёх индексов сразу после операции,
которая её создала.

## LFU и LRU

| Вопрос | LRU | LFU |
| --- | --- | --- |
| Основной сигнал | давность последнего обращения | число обращений |
| Метаданные | один порядок записей | частоты и порядок внутри каждой частоты |
| Одноразовый последовательный scan | может вытеснить старые горячие ключи | горячие ключи защищены накопленной частотой |
| Смена популярности | быстро забывает старое | старые частоты мешают адаптации |
| Реализация | проще | сложнее и дороже по метаданным |

Чистый LFU полезен, когда популярность ключей стабильна: несколько объектов
действительно читаются намного чаще остальных. Если популярность меняется по
фазам, накопленная частота превращается в недостаток. Ключ, который был горячим
утром, может удерживаться вечером, хотя к нему больше не обращаются.

LRU быстрее адаптируется к смене рабочей нагрузки, но последовательное чтение
множества уникальных ключей способно вытеснить полезный рабочий набор. Поэтому
выбор политики зависит от access pattern, а не от абстрактного утверждения, что
LFU «умнее» LRU.

## Практические расширения

### Потокобезопасность

`Get` меняет частоту и оба списка, поэтому он является записью во внутреннее
состояние. Один `sync.Mutex` вокруг публичных операций — корректная отправная
точка. `RWMutex` не даёт обычному `Get` read lock только из-за названия метода.

```go
type SafeCache struct {
    mu    sync.Mutex
    cache *Cache
}

func (c *SafeCache) Get(key string) (Profile, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.cache.Get(key)
}
```

Sharding уменьшает contention, но меняет семантику: каждый shard выбирает
локальную жертву, поэтому результат уже не является глобальным LFU.

### Старение частот

Без старения счётчики только растут. Это создаёт две проблемы:

- когда-то популярные ключи получают долговременное преимущество;
- достаточно долгоживущий процесс теоретически может переполнить `int`.

Периодическое деление всех частот на два требует `O(C)` и создаёт latency spike.
Практические реализации используют эпохи, приближённые счётчики или алгоритмы
admission вроде TinyLFU, где история популярности постепенно забывается.

### TTL

TTL и LFU отвечают на разные вопросы. LFU выбирает менее полезную запись, а TTL
запрещает возвращать устаревшее значение. Добавление TTL требует определить:

- удаляются ли истёкшие записи лениво на `Get` или фоновым cleanup;
- считается ли expiration eviction;
- может ли истёкшая запись занимать ёмкость;
- как выбирать жертву, если в cache уже есть истёкшие ключи.

Простое поле `expiresAt` без ответа на эти вопросы не завершает реализацию.

### Admission policy

Eviction выбирает, кого удалить из уже заполненного cache. Admission решает,
нужно ли вообще принимать новый ключ. Одноразовый холодный ключ необязательно
должен вытеснять полезную запись только потому, что для него вызвали `Put`.

TinyLFU обычно используют как оценку популярности при admission, а хранение
записей организуют отдельной политикой. Это не тот же алгоритм, что точный LFU
из задачи.

### Метрики и callbacks

Полезно считать hit, miss и eviction отдельно. Callback вытеснения нельзя
безоговорочно вызывать под mutex: медленный callback увеличит latency всех
операций, а повторный вызов cache из callback может привести к deadlock.

## Типичные ошибки

### Линейный поиск минимальной частоты

Счётчик в каждой записи ещё не даёт `O(1)` для `Put`. Нужны частотные списки и
`minFreq`.

### Нет порядка при равных частотах

Выбор случайного ключа из `map` нарушает контракт. Внутри каждой частоты нужен
отдельный LRU-порядок.

### Запись остаётся в старом списке

Если при `Get` добавить запись в новый список, но не удалить из старого, одна
запись начинает участвовать в нескольких группах. Размер списков растёт, а
вытеснение может удалить уже неактуальный узел.

### Не обновляется minFreq

Когда последняя запись покидает минимальную группу после `Get`, `minFreq`
должен перейти на следующую частоту. При вставке нового ключа он всегда
сбрасывается в `1`.

### Потерян указатель на list.Element

`map[key] -> entry` недостаточно, если для удаления узла затем приходится идти
по всему списку. Указатель на `list.Element` является частью индекса.

### Put update меняет только значение

Это может быть допустимым контрактом, но не контрактом данной реализации. Здесь
обновление существующего ключа считается использованием и увеличивает частоту.

### RWMutex вокруг Get

Попадание в cache меняет частоту и LRU-порядок. Параллельные `Get` под `RLock`
создадут data race и могут повредить списки.

### Обещание production-ready только из-за mutex

Синхронизация не решает старение частот, TTL, ограничение размера значений,
callbacks, наблюдаемость и адаптацию к смене нагрузки. Учебная корректность и
готовность к эксплуатации — разные уровни требований.

## Interview-ready answer

**1. Как реализовать LFU Cache с ожидаемыми O(1) Get и Put?**

- Суть — хранить ключи в `map`, записи группировать по частоте в двусвязных
  списках, а минимальную непустую частоту держать в `minFreq`.
- Доступ — `map[key]` сразу находит запись, а указатель на `list.Element`
  позволяет удалить её из старой группы без обхода.
- Повышение — после успешного `Get` запись переходит из группы `f` в начало
  группы `f+1`.
- Вытеснение — удаляется хвост списка `frequencies[minFreq]`, то есть LRU-запись
  среди ключей с минимальной частотой.

**2. Зачем нужен LRU-порядок внутри одной частоты?**

- Неоднозначность — одна минимальная частота может принадлежать нескольким
  ключам.
- Контракт — LRU задаёт детерминированную и практически полезную жертву среди
  равных кандидатов.
- Структура — двусвязный список даёт перемещение и удаление за `O(1)` при наличии
  указателя на узел.

**3. Когда LFU лучше и хуже LRU?**

- Преимущество — LFU сохраняет стабильно горячие ключи и устойчивее к
  одноразовому последовательному scan.
- Недостаток — накопленная частота мешает быстро адаптироваться, когда
  популярность ключей меняется.
- Выбор — политика зависит от распределения обращений, стоимости метаданных и
  требуемой скорости адаптации.

**4. Что потребуется сверх учебной реализации?**

- Синхронизация — один mutex обеспечивает корректность, но может создать
  contention; sharding меняет глобальную семантику вытеснения.
- Старение — частоты нужно со временем ослаблять, иначе старые горячие ключи
  получают бессрочное преимущество.
- Lifecycle — TTL, cleanup, callbacks и метрики требуют отдельных контрактов.
- Admission — для сложных нагрузок полезно отдельно решать, заслуживает ли новый
  ключ помещения в cache.
