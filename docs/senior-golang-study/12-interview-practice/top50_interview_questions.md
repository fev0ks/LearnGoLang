## Go — основы

**В чём разница между массивами и слайсами? (~85×)**

- Массив `[N]T` — фиксированная длина, часть типа, копируется целиком по значению. Слайс — дескриптор `{указатель, len, cap}` поверх backing-массива: копируется как заголовок, несколько слайсов могут разделять один массив. Самый частый вопрос Go-собеседований. См. [04-slices.md](../01-go-core/04-slices.md).

**Что происходит при вызове append? Когда создаётся новый массив? (~70×)**

- Если `len < cap` — элемент пишется в **существующий** backing-массив (и виден всем слайсам над ним). Если места нет — аллоцируется **новый** массив (рост ~×2 на малых, ~×1.25 на больших), данные копируются, возвращается новый заголовок — поэтому результат присваивают обратно: `s = append(s, …)`. См. [04-slices.md](../01-go-core/04-slices.md).

**Как устроена map под капотом? Бакеты, коллизии, эвакуация? (~65×)**

- Хеш-таблица: младшие биты хэша выбирают **бакет** (до 8 пар + `tophash` для быстрого отсева + overflow-цепочка), коллизии решаются chaining'ом. Рост при load factor ≈ 6.5 или множестве overflow-бакетов; **эвакуация инкрементальная** — элементы переносятся порциями при последующих операциях. С Go 1.24 — **Swiss Tables** (открытая адресация группами по 8 слотов с control-байтами, SIMD-сканирование). См. [map-internals](../01-go-core/map-internals/README.md).

**Что из себя представляют строки? Какие подводные камни? (~55×)**

- Строка — неизменяемый заголовок `{указатель на байты, len}`; байты обычно UTF-8, но могут быть любыми. Грабли: `len` — в **байтах**, `s[i]` — байт (не символ), `range` идёт по **рунам**, конкатенация `+=` в цикле — O(n²) (нужен `strings.Builder`), конверсии `[]byte(s)`/`string(b)` копируют. См. [07-strings.md](../01-go-core/07-strings.md).

**Что такое интерфейс? Для чего нужен пустой интерфейс? (~50×)**

- Интерфейс — набор сигнатур методов (контракт); реализация **неявная** — тип подходит, если имеет методы. Внутри — пара `(тип, значение)`. Пустой интерфейс `interface{}`/`any` не требует ничего, поэтому принимает **любой** тип — используется для универсальных контейнеров/API (`fmt.Println`, `json.Unmarshal`); извлечение — type assertion / type switch; с дженериками нужен реже. См. [03-interfaces-method-sets-and-nil.md](../01-go-core/03-interfaces-method-sets-and-nil.md).

**Как передаются слайсы в функцию? Почему изменения иногда не видны снаружи? (~45×)**

- Заголовок копируется, backing-массив — общий. Поэтому `s[i] = x` внутри функции **виден** снаружи, а `s = append(s, …)` — **нет**: append меняет локальную копию заголовка (а при реаллокации — вообще другой массив). Видимые снаружи append'ы — только через возврат слайса или указатель на него. См. [04-slices.md](../01-go-core/04-slices.md).

**Что такое defer? В каком порядке выполняются несколько defer? (~45×)**

- Отложенный вызов, выполняется при выходе из функции (включая панику). Несколько defer — **LIFO** (стек: последний объявленный — первый выполненный). Ключевой нюанс: **аргументы вычисляются в момент объявления** defer, а не при выполнении; замыкание же читает переменные на момент выхода. Может менять именованные return-значения. Типовое применение: `Unlock`, `Close`, `recover`.

**Когда интерфейс равен nil? Что будет при сравнении с nil-указателем внутри? (~40×)**

- Интерфейс — пара `(тип, значение)`; он равен `nil`, только когда **обе** части nil. Классическая ловушка — **typed nil**: `var p *T = nil; var i I = p` → `i != nil` (тип `*T` есть, значение nil). Отсюда баг с `error`: вернуть nil-указатель на конкретный тип ошибки → у вызывающего `err != nil`. Правило: возвращать литеральный `nil`, а не nil-указатель в интерфейсе. См. [03-interfaces-method-sets-and-nil.md](../01-go-core/03-interfaces-method-sets-and-nil.md).

**Как len() работает со строкой на русском? Как посчитать символы? (~35×)**

- `len` возвращает **байты**: `len("привет") == 12` (кириллица — 2 байта/буква в UTF-8), а не 6. Число символов (рун): `utf8.RuneCountInString(s)` или `len([]rune(s))`; `range` по строке тоже итерирует руны с байтовыми индексами. См. [07-strings.md](../01-go-core/07-strings.md).

**Что такое контекст? Для чего используется? (~35×)**

- Сквозная передача **отмены/дедлайна** и request-scoped значений по дереву вызовов и горутин: при `cancel()`/таймауте закрывается `Done()`, и все слушающие операции сворачиваются, не утекая. Методы: `Done()`, `Err()`, `Deadline()`, `Value()`; создание — `WithCancel`/`WithTimeout`/`WithValue`. См. [concurrency-and-performance/04-context-patterns.md](../01-go-core/concurrency-and-performance/04-context-patterns.md).

**Можно ли взять указатель на элемент map? Почему? (~30×)**

- Нет — `&m[key]` не компилируется. Причина: при росте map элементы **эвакуируются** в новые бакеты, и адрес стал бы невалидным (а фиксировать элементы на месте — значит запретить рост). Обход: хранить в map указатели (`map[K]*V`) и мутировать по ним, либо читать-изменять-записывать копию. См. [map-internals/03-puzzles-and-gotchas.md](../01-go-core/map-internals/03-puzzles-and-gotchas.md).

**Как эффективно склеить тысячу строк? (~25×)**

- `strings.Builder`: `b.WriteString(s)` в цикле и `b.String()` в конце — амортизированный рост одного буфера, одна финальная строка без копии; если итоговый размер известен — `b.Grow(n)`. Если строки уже в слайсе — `strings.Join(parts, sep)`. Антипаттерн — `+=` в цикле: каждая итерация аллоцирует и копирует всё заново, O(n²). См. [07-strings.md](../01-go-core/07-strings.md).

## Go — конкурентность и каналы

**Какие примитивы синхронизации знаешь и с какими работал? (~65×)**

- `sync.Mutex`/`RWMutex`, `WaitGroup`, `Once`, `Cond`, `sync.Map`, пакет `sync/atomic`, каналы + `select`, `context` для отмены; из `golang.org/x/sync` — `errgroup`, `semaphore`, `singleflight`. На собесе стоит к каждому назвать сценарий (Mutex — общее состояние, WaitGroup — дождаться группу, Once — ленивая инициализация, errgroup — параллельные задачи с первой ошибкой). См. [concurrency-and-performance/03-sync-primitives.md](../01-go-core/concurrency-and-performance/03-sync-primitives.md).

**Что будет при записи в закрытый канал? А при чтении? (~60×)**

- Запись в закрытый канал — **паника** (как и повторный `close`). Чтение — не блокируется: сначала отдаёт остаток буфера, затем нулевое значение типа; различить — `v, ok := <-ch` (`ok == false` на закрытом и пустом). Отсюда правило: закрывает канал **отправитель** и только один раз. См. [concurrency-and-performance/02-goroutines-and-channels.md](../01-go-core/concurrency-and-performance/02-goroutines-and-channels.md).

**Чем горутина отличается от потока ОС? За счёт чего легковесна? (~60×)**

- Горутина — user-space поток рантайма: стартовый стек **~2 КБ** (растёт/сжимается по надобности) против мегабайтов у OS-потока; создание и переключение — без syscall (планировщик Go в user space); мультиплексируются M:N на потоки по модели G-M-P. Поэтому сотни тысяч горутин — норма, а тысячи потоков — уже проблема. См. [runtime-scheduler/01-scheduler-and-preemption.md](../01-go-core/runtime-scheduler/01-scheduler-and-preemption.md).

**Чем отличается буферизированный канал от небуферизированного? (~55×)**

- Небуферизированный — **рандеву**: отправка блокируется, пока получатель не заберёт (синхронизация «из рук в руки»). Буферизированный (`make(chan T, n)`) принимает без блокировки, пока буфер не полон, — развязывает отправителя и получателя по времени, но прячет backpressure. На пустом/полном буфере поведение снова блокирующее. См. [concurrency-and-performance/02-goroutines-and-channels.md](../01-go-core/concurrency-and-performance/02-goroutines-and-channels.md).

**Что такое data race? Как обнаружить и как бороться? (~45×)**

- Одновременный доступ двух горутин к одной памяти, хотя бы один — запись, без синхронизации; результат непредсказуем (вплоть до порчи данных). Обнаружение — **race-детектор**: `go test -race` / `go run -race` (инструментирует доступы, печатает конфликтующие стеки); в CI гонять с `-race`. Лечение: Mutex/atomic, передача владения через каналы, иммутабельность. См. [concurrency-and-performance/01-memory-model.md](../01-go-core/concurrency-and-performance/01-memory-model.md).

**Почему map не потокобезопасна? Как организовать конкурентный доступ? (~45×)**

- Запись меняет общую структуру (бакеты, рост, эвакуация), и рантайм не синхронизирует это намеренно (скорость по умолчанию); конкурентные чтение+запись — гонка и фатал `concurrent map read and map write`, даже по **разным ключам**. Решения: `map` + `RWMutex` (общий случай), шардирование по ключу (меньше contention), `sync.Map` (узкие read-heavy сценарии). См. [map-internals/04-sync-map.md](../01-go-core/map-internals/04-sync-map.md).

**Что будет при чтении/записи в nil-канал? (~40×)**

- И чтение, и запись в nil-канал **блокируются навсегда** (если это единственная горутина — deadlock-паника «all goroutines are asleep»); `close(nil)` — паника. Побочное применение: присвоить каналу nil, чтобы **выключить его ветку** в `select`. См. [concurrency-and-performance/02-goroutines-and-channels.md](../01-go-core/concurrency-and-performance/02-goroutines-and-channels.md).

**Как работает select? (~35×)**

- Ждёт готовности одной из операций с каналами; если готовы несколько — выбирает **случайную** (защита от starvation); `default` делает неблокирующим; типовая ветка `case <-ctx.Done()` — выход по отмене. Пустой `select {}` блокируется навсегда.

**Чем конкурентность отличается от параллельности? (~35×)**

- Конкурентность — **структура** программы: много задач «в полёте», исполнение чередуется (может и на одном ядре). Параллельность — **физически одновременное** исполнение на нескольких ядрах. Классика Go: «concurrency is about dealing with lots of things at once, parallelism — doing lots of things at once». Горутины дают конкурентность; параллельность появляется при `GOMAXPROCS > 1`.

**Что будет, если в горутине произойдёт паника? Можно ли перехватить из родительской? (~30×)**

- Неперехваченная паника в **любой** горутине аварийно завершает **весь процесс** (stack trace, exit 2). Из родительской горутины перехватить **нельзя** — `recover` работает только в `defer` той же горутины. Практика: в воркерах — `defer func(){ if r := recover(); r != nil { … } }()`, ошибку наружу — через канал/`errgroup`. См. [05-error-handling.md](../01-go-core/05-error-handling.md).

**Как устроен мьютекс под капотом? Что такое голодание? (~25×)**

- `sync.Mutex` — `state` (int32: биты locked/woken/starving + счётчик ждущих) + семафор. Fast path — атомарный CAS в user space (без ядра); при конфликте — короткий спин, затем парковка горутины через семафор рантайма. **Голодание**: если горутина ждёт >1 мс, мьютекс переходит в starvation-режим — владение передаётся **напрямую первому в очереди** (FIFO), новички не перехватывают лок «с наскока»; так исключается бесконечное оттеснение ждущих. См. [concurrency-and-performance/03-sync-primitives.md](../01-go-core/concurrency-and-performance/03-sync-primitives.md).

**Что такое sync.Pool и для чего нужен? (~20×)**

- Пул **временных переиспользуемых** объектов (буферы, encoder'ы): `Get` возвращает старый объект или создаёт через `New`, `Put` возвращает в пул. Снижает аллокации и давление на GC на горячих путях (так работает `fmt`, `encoding/json`). Нюансы: содержимое может быть **выброшено при GC** — пул не кэш и не хранилище состояния; объект перед `Put` надо сбрасывать (`buf.Reset()`). Устроен per-P (почти без блокировок). См. [concurrency-and-performance/03-sync-primitives.md](../01-go-core/concurrency-and-performance/03-sync-primitives.md).

**Расскажи про структуру канала (hchan). Как устроен буфер? (~20×)**

- `hchan`: кольцевой буфер (`buf`, `dataqsiz`, `qcount`, индексы `sendx`/`recvx`), `closed`-флаг, `lock` (mutex) и две очереди ждущих горутин — `sendq`/`recvq` (списки `sudog`). Отправка: есть ждущий получатель → данные копируются **напрямую в его стек** (минуя буфер) и он будится; иначе — в буфер; буфер полон — горутина паркуется в `sendq`. Приём зеркально. См. [concurrency-and-performance/02-goroutines-and-channels.md](../01-go-core/concurrency-and-performance/02-goroutines-and-channels.md).

## Go — runtime

**Расскажи про GMP-модель планировщика. Как устроены очереди горутин? (~55×)**

- **G** — горутина, **M** — OS-поток, **P** — логический процессор (их `GOMAXPROCS`); Go-код исполняет только M, держащий P. Очереди: у каждого P — **локальная** (LRQ, без блокировок), плюс **глобальная** (GRQ); пустая локальная → P **крадёт** половину у соседа (work-stealing) или берёт из глобальной/netpoller. Преемпция: кооперативные точки + асинхронная по сигналу (~10 мс, с 1.14). См. [runtime-scheduler/01-scheduler-and-preemption.md](../01-go-core/runtime-scheduler/01-scheduler-and-preemption.md).

**Как работает garbage collector? Можно ли на него влиять? (~40×)**

- Конкурентный **трёхцветный mark-and-sweep** с write-barrier: короткий STW на включение барьера → конкурентная маркировка (белый/серый/чёрный) → короткий STW на завершение → конкурентный sweep. Паузы суб-миллисекундные; цена — CPU на маркировку. Влиять: `GOGC` (целевой рост кучи, дефолт 100), `GOMEMLIMIT` (мягкий лимит), `runtime.GC()` вручную; главный рычаг — **меньше аллокаций** (sync.Pool, предвыделение). См. [memory-internals/04-garbage-collector.md](../01-go-core/memory-internals/04-garbage-collector.md).

**Что такое NetPoller и для чего нужен? (~25×)**

- Интегрированный в рантайм асинхронный поллер сетевого I/O (**epoll**/kqueue/IOCP). Сетевые fd — неблокирующие: если операция «ждала бы», горутина **паркуется**, fd регистрируется в поллере, а поток (M) освобождается под другие горутины; по готовности сокета горутина возвращается в очередь планировщика. Так тысячи соединений обслуживаются несколькими потоками. См. [runtime-scheduler/03-netpoller.md](../01-go-core/runtime-scheduler/03-netpoller.md).

**Как работает escape analysis? Когда переменная попадает на кучу? (~20×)**

- Компилятор статически решает, где жить переменной: если ссылка **не переживает** функцию — стек (дёшево, без GC); «убегает» — куча. Типичные причины escape: возврат указателя, сохранение в интерфейс (`any`, `fmt.Println`), захват замыканием, отправка в канал, слишком большой/динамический размер. Проверка: `go build -gcflags=-m`. Меньше эскейпов → меньше аллокаций и работы GC. См. [memory-internals/03-escape-analysis.md](../01-go-core/memory-internals/03-escape-analysis.md).

**Что такое выравнивание (padding) в структурах? Сколько памяти занимает структура? (~20×)**

- Каждое поле выравнивается по alignment своего типа (int64 — по 8, int32 — по 4…), компилятор вставляет **padding**-байты между полями и в конце (размер структуры кратен максимальному выравниванию). Поэтому порядок полей влияет на размер: сортировка «от больших к меньшим» убирает дыры. Пример: `struct{ a int32; b bool }` = 4+1+3 padding = **8 байт**. Проверка: `unsafe.Sizeof`, линтер `fieldalignment`. См. [memory-internals/01-stack-and-heap.md](../01-go-core/memory-internals/01-stack-and-heap.md).

## Базы данных

**Какие уровни изоляции транзакций знаешь? В чём разница? (~60×)**

- По нарастанию строгости: **Read Uncommitted** (видны чужие незакоммиченные — dirty read), **Read Committed** (только закоммиченные; дефолт PostgreSQL), **Repeatable Read** (стабильный снимок в рамках транзакции; в PG отсекает и фантомы), **Serializable** (эквивалент последовательного выполнения; конфликты → ошибка `40001`, нужен retry). Каждый уровень отсекает свои аномалии: dirty → non-repeatable → phantom read → write skew. Строже = меньше параллелизма. См. [relational-databases-and-sql/02-transactions-isolation-and-locks.md](../06-databases/relational-databases-and-sql/02-transactions-isolation-and-locks.md).

**Какие типы индексов в PostgreSQL знаешь? Чем B-Tree отличается от Hash? (~50×)**

- **B-tree** (дефолт: равенство, диапазоны, `ORDER BY`, префиксный `LIKE`), **Hash** (только `=`), **GIN** (инвертированный: jsonb, массивы, полнотекст), **GiST** (гео/диапазоны), **BRIN** (компактный для «естественно отсортированных» больших таблиц), partial и expression-индексы. B-tree упорядочен → умеет диапазоны и сортировку за O(log n); Hash — только точное равенство, без порядка. См. [postgresql/02-indexes.md](../06-databases/database-systems-catalog/postgresql/02-indexes.md).

**Что такое ACID? Расскажи про каждую букву. (~45×)**

- **Atomicity** — транзакция применяется целиком или никак (undo при откате). **Consistency** — из корректного состояния в корректное (ограничения, FK, CHECK). **Isolation** — параллельные транзакции не видят промежуточных состояний друг друга (MVCC/уровни изоляции). **Durability** — закоммиченное переживает сбой (WAL + fsync). См. [database-fundamentals/01-acid.md](../06-databases/database-fundamentals/01-acid.md).

**Что такое EXPLAIN ANALYZE? На что смотреть в выводе? (~35×)**

- `EXPLAIN` показывает предполагаемый план по статистике; с `ANALYZE` запрос **реально выполняется** и печатаются факты. Смотреть: **Seq Scan vs Index Scan** на больших таблицах, **rows: оценка vs факт** (большое расхождение = устаревшая статистика → `ANALYZE`), дорогие узлы (Sort, Hash), `BUFFERS` (чтения с диска vs кэш), loops у Nested Loop. См. [postgresql/03-query-planning.md](../06-databases/database-systems-catalog/postgresql/03-query-planning.md).

**Что такое шардирование? Какие проблемы? (~35×)**

- Горизонтальное разбиение данных по ключу (hash/range/directory) на независимые узлы — масштабирует запись и объём, чего не даёт репликация. Проблемы: **кросс-шардовые запросы и JOIN** (fan-out), распределённые транзакции, **ребалансировка** при добавлении узлов, hot shards при перекошенном ключе, глобальные уникальные id. См. [postgresql/12-sharding.md](../06-databases/database-systems-catalog/postgresql/12-sharding.md).

**Что такое deadlock в БД? Когда возникает? (~30×)**

- Взаимная блокировка: T1 держит строку A и ждёт B, T2 держит B и ждёт A — цикл ожидания. СУБД детектирует и **откатывает одну** транзакцию с ошибкой (жертву). Профилактика: захватывать строки в **едином порядке** (напр. по id), короткие транзакции, ретрай на стороне приложения. См. [relational-databases-and-sql/02-transactions-isolation-and-locks.md](../06-databases/relational-databases-and-sql/02-transactions-isolation-and-locks.md).

**В чём разница между LEFT JOIN и INNER JOIN? (~30×)**

- `INNER JOIN` возвращает только строки с совпадением в **обеих** таблицах. `LEFT JOIN` — **все** строки левой + совпадения правой (нет совпадения → NULL-ы в колонках правой). Типовое применение LEFT — «все пользователи, включая тех, у кого нет заказов»; фильтр `WHERE right.id IS NULL` находит строки **без** пары. См. [relational-databases-and-sql/01-relational-model-and-sql-basics.md](../06-databases/relational-databases-and-sql/01-relational-model-and-sql-basics.md).

**Что такое WAL (Write-Ahead Log) и для чего нужен? (~25×)**

- Журнал упреждающей записи: изменения сначала пишутся **в лог** (последовательно + `fsync`), и только потом — в страницы данных; коммит подтверждается после записи в WAL. Даёт **durability** (после краша БД реплеит WAL), быструю последовательную запись вместо random-I/O, и является основой **репликации** (стриминг WAL на реплики) и point-in-time recovery. См. [database-fundamentals/01-acid.md](../06-databases/database-fundamentals/01-acid.md) и [postgresql/06-replication.md](../06-databases/database-systems-catalog/postgresql/06-replication.md).

**Как работает VACUUM и autovacuum? (~25×)**

- MVCC в PostgreSQL не удаляет старые версии строк сразу: UPDATE/DELETE оставляют **dead tuples**. `VACUUM` вычищает их (место переиспользуется), обновляет visibility map и статистику, защищает от **XID wraparound**; таблицу не блокирует (в отличие от `VACUUM FULL`, который переписывает файл под эксклюзивным локом). **autovacuum** — фоновые воркеры, запускаются по порогам изменённых строк; на нагруженных таблицах пороги тюнят, иначе bloat. См. [postgresql/01-mvcc-and-vacuum.md](../06-databases/database-systems-catalog/postgresql/01-mvcc-and-vacuum.md).

**Как создать индекс без блокировки таблицы на проде? (~20×)**

- `CREATE INDEX CONCURRENTLY` — строит индекс **без блокировки записи** (обычный `CREATE INDEX` блокирует INSERT/UPDATE/DELETE до конца построения). Цена: два прохода по таблице + ожидание завершения активных транзакций (медленнее), нельзя внутри транзакции, при сбое остаётся **INVALID**-индекс (удалить и пересоздать). Аналогично `DROP INDEX CONCURRENTLY` и `REINDEX CONCURRENTLY`. См. [postgresql/02-indexes.md](../06-databases/database-systems-catalog/postgresql/02-indexes.md).

## Сети и API

**Чем отличается REST от gRPC? Когда что выбирать? (~30×)**

- **REST** — ресурсы поверх HTTP/JSON: человекочитаем, работает из браузера, легко дебажить, слабый контракт (OpenAPI опционален). **gRPC** — RPC поверх HTTP/2 + **Protobuf**: бинарный (компактнее/быстрее), строгая схема с кодогенерацией, стриминг (4 типа вызовов), дедлайны из коробки; но не для браузера напрямую (gRPC-Web/gateway) и не читается глазами. Выбор: внешние/публичные API — REST; внутренняя service-to-service связь с жёсткими контрактами и латентностью — gRPC. См. [protocols/01-grpc.md](../08-networking-and-api/protocols/01-grpc.md).

**Чем отличается HTTP/1.1 от HTTP/2? (~25×)**

- HTTP/1.1 — текстовый, keep-alive, но **head-of-line blocking**: по одному ответу за раз на соединение (браузеры открывают по 6 соединений). HTTP/2 — **бинарный фрейминг**, мультиплексирование многих стримов в одном TCP-соединении, сжатие заголовков **HPACK**, приоритеты, server push; HoL остаётся только на уровне TCP (решает уже HTTP/3/QUIC). См. [protocols/11-protocol-comparison.md](../08-networking-and-api/protocols/11-protocol-comparison.md).

## ОС

**Чем процесс отличается от потока? (~35×)**

- Процесс — изолированная единица с собственным адресным пространством и ресурсами; поток — единица исполнения **внутри** процесса, потоки делят память и дескрипторы. Переключение потоков дешевле, обмен данными — прямой (но нужна синхронизация); процессы изолированы и общаются через IPC. Планировщик ОС оперирует потоками. См. [hardware-and-os/06-processes-and-threads.md](../10-devops-and-observability/hardware-and-os/06-processes-and-threads.md).

## Архитектура и брокеры

**Расскажи про паттерн Outbox. Зачем он нужен? (~35×)**

- Решает **dual-write**: нельзя атомарно записать в свою БД и отправить событие в брокер. Outbox: в **одной локальной транзакции** пишем бизнес-данные + событие в таблицу `outbox`; отдельный процесс (poller/CDC-Debezium) надёжно доставляет события в Kafka и помечает отправленные. Гарантия at-least-once → потребитель идемпотентен. Без Outbox: записали в БД, брокер упал — событие потеряно (или наоборот). См. [patterns/09-saga-and-outbox.md](../04-architecture-and-patterns/patterns/09-saga-and-outbox.md).

**Расскажи про SOLID. Как принципы ложатся на Go? (~30×)**

- **S**ingle Responsibility (одна причина изменения), **O**pen/Closed (расширяем без модификации), **L**iskov Substitution (подтип заменяем), **I**nterface Segregation (узкие интерфейсы), **D**ependency Inversion (зависеть от абстракций). В Go особенно органичны **ISP** (идиома маленьких интерфейсов: `io.Reader` — один метод) и **DIP** (интерфейс объявляет потребитель, реализация неявная); наследования нет — LSP через композицию и контракты интерфейсов. См. [patterns/06-solid-in-go.md](../04-architecture-and-patterns/patterns/06-solid-in-go.md).

**Что такое идемпотентность? Как обеспечить для POST-запроса? (~30×)**

- Повтор операции даёт тот же результат, что и однократное выполнение — критично для ретраев и at-least-once доставки. GET/PUT/DELETE идемпотентны по семантике, **POST — нет**. Обеспечение: клиент шлёт **Idempotency-Key**, сервер атомарно фиксирует ключ (уникальный индекс в БД) и сохраняет результат; повтор с тем же ключом → отдать сохранённый ответ, не выполняя эффект второй раз. См. [reliability-patterns/06-idempotency.md](../05-system-design/reliability-patterns/06-idempotency.md) и [protocols/07-idempotency.md](../08-networking-and-api/protocols/07-idempotency.md).

**Чем отличается Kafka от RabbitMQ? Когда что использовать? (~30×)**

- **Kafka** — durable-лог: партиции на диске, чтение по offset без удаления (retention, реплей), pull, высокий throughput, много независимых consumer-групп. **RabbitMQ** — брокер очередей (AMQP): умная маршрутизация exchange/routing key, push, сообщение удаляется после ack, приоритеты/TTL. Kafka — событийные стримы, большие потоки, реплей; RabbitMQ — task-очереди, RPC, сложная маршрутизация. См. [07-message-brokers-and-streaming/07-comparison.md](../07-message-brokers-and-streaming/07-comparison.md).

**Что такое graceful shutdown? Как реализовать? (~30×)**

- Корректное завершение: перестать принимать новые запросы, **дообработать текущие**, закрыть ресурсы (пулы БД, брокеры), и только потом выйти. В Go: `signal.NotifyContext(ctx, SIGTERM, SIGINT)` → по сигналу `httpServer.Shutdown(ctxTimeout)` (перестаёт принимать, ждёт активные до таймаута) → закрыть зависимости, дождаться воркеров (`errgroup`/WaitGroup). В Kubernetes: сначала снять readiness, учесть `terminationGracePeriodSeconds`. См. [patterns/08-graceful-shutdown.md](../04-architecture-and-patterns/patterns/08-graceful-shutdown.md).

**Что такое кэширование? Какие стратегии существуют? (~30×)**

- Хранение горячих данных в быстром слое (память/Redis), чтобы разгрузить медленный источник. Стратегии чтения/записи: **cache-aside** (приложение: кэш → промах → БД → положить в кэш; самая частая), **read-through** (кэш сам ходит в БД), **write-through** (запись синхронно в кэш и БД), **write-behind** (в кэш сразу, в БД асинхронно — быстро, но риск потери), **write-around**. Инвалидация: TTL, по событиям. Проблемы: устаревание, stampede (→ singleflight), консистентность. См. [caching/01-redis-as-cache.md](../06-databases/caching/01-redis-as-cache.md).

**Гарантирует ли Kafka порядок сообщений? Как обеспечить порядок для одной сущности? (~25×)**

- Порядок гарантируется **только внутри партиции**, глобального порядка по топику нет. Для порядка событий одной сущности — писать с **ключом = id сущности**: все её сообщения попадут в одну партицию и прочитаются по порядку. Плюс включить идемпотентного продюсера (иначе ретраи при `max.in.flight > 1` могут переставить сообщения). См. [07-message-brokers-and-streaming/01-kafka.md](../07-message-brokers-and-streaming/01-kafka.md).

## Топ-10 задач на лайвкодинг

Реальные задачи из тех же собеседований — с ответами. Полные разборы с production-версиями и тестами — в [coding-tasks](coding-tasks/README.md).

### 1. Что выведет: слайс и map в функцию

```go
func appendToSlice(s []int) { s = append(s, 4) }
func addToMap(m map[string]int) { m["b"] = 2 }

func main() {
    s := []int{1, 2, 3}
    appendToSlice(s)
    fmt.Println(s) // ?

    m := map[string]int{"a": 1}
    addToMap(m)
    fmt.Println(m) // ?
}
```

- **`[1 2 3]`** — заголовок слайса копируется; `len == cap`, append аллоцирует новый массив и меняет только локальную копию заголовка.
- **`map[a:1 b:2]`** — map под капотом указатель на `hmap`, копия указателя смотрит на ту же таблицу, запись видна снаружи.

### 2. Параллельный Worker Pool с каналами

Читать из `in` в N горутинах, обрабатывать, писать в `out`, закрыть `out` после завершения всех воркеров (+ отмена по context).

- Скелет: `WaitGroup` на N воркеров; каждый — `for v := range in { out <- process(v) }` (с `select` на `ctx.Done()`); отдельная горутина `wg.Wait(); close(out)`. Ключевая ошибка — закрыть `out` раньше воркеров или из нескольких мест. Полный разбор: [concurrency/01-worker-pool.md](coding-tasks/concurrency/01-worker-pool.md).

### 3. Merge N каналов в один (fan-in)

- По горутине на входной канал: `for v := range ch { out <- v }` + общий `WaitGroup`; закрыть `out` в отдельной горутине после `wg.Wait()`. Выход закрывается, когда закрыты **все** входы; утечек нет, т.к. каждая горутина завершается по закрытию своего канала. Полный разбор: [concurrency/03-fan-in-fan-out.md](coding-tasks/concurrency/03-fan-in-fan-out.md).

### 4. Code Review: кэширующий прокси над KV-БД

Дан `AddressStore` с `RWMutex` и map-кэшем (RLock-чтение → промах → `store.Get` → Lock-запись). Что найти:

- **Гонка окна между RUnlock и Lock**: после захвата `Lock` нужен **re-check** ключа (мог появиться) — иначе лишние походы в БД и перезапись.
- **Cache stampede**: N горутин одновременно промахиваются по одному ключу и все идут в медленную БД (~100 мс) — нужен `singleflight`.
- `cache` **не инициализирована** — нужен конструктор (`make`), иначе паника при записи.
- Нет **TTL/лимита размера** — вечный рост памяти; нет `context`/таймаута на `store.Get`; `Keys()` не реализован.
- Прокси должен сам реализовывать интерфейс `KVStore` (прозрачность для пользователей). Родственный разбор: [code-review/01-fetcher-with-cache.md](coding-tasks/code-review/01-fetcher-with-cache.md).

### 5. Code Review: корзина интернет-магазина

Глобальные `items []Product`, `vatRate`, `removalChannel`; `init()` с `make([]Product, 100)`; удаление в горутине. Что найти:

- `make([]Product, 100)` — это **100 нулевых товаров**, append добавляет 101-м; нужно `make(..., 0, 100)`.
- **Data race**: `RemoveItem` мутирует `items` в горутине, `AddItem` — без синхронизации; нет мьютекса.
- **Deadlock**: `removalChannel <- false` в конце + `<- true` из горутины в буфер размера 1 — второй вызов заблокируется; и семантика «кто читает?» не определена.
- Глобальное изменяемое состояние (нетестируемо, нарушение SRP/DIP), деньги во `float` (нужны int-копейки/decimal), поиск/идентификация по имени товара, нет возврата ошибок. Родственный разбор: [code-review/02-background-task-processor.md](coding-tasks/code-review/02-background-task-processor.md).

### 6. Слайсы и общий backing-массив

```go
nums := []int{1, 2, 3}          // len 3, cap 3
addNum(nums[0:2])               // len 2, cap 3 → append(4) влезает в cap
fmt.Println(nums)               // [1 2 4]  ← перезаписал nums[2]!
addNums(nums[0:2])              // append(5,6): len 4 > cap 3 → новый массив
fmt.Println(nums)               // [1 2 4]  ← оригинал не тронут
```

- Первый append **влезает в cap** и пишет в общий массив — «чужой» элемент перезаписан. Второй — реаллоцирует и оригинал не видит изменений. Защита от такого — full slice expression `nums[0:2:2]`.

### 7. Горутины в цикле: замыкание на переменную

```go
for i := 0; i < 5; i++ {
    go func() { fmt.Println(i) }()
}
```

- **До Go 1.22**: все замыкания делят одну переменную `i`; к моменту запуска горутин цикл обычно завершён → чаще всего `5 5 5 5 5` (порядок и значения не гарантированы). Фикс: `go func(i int){…}(i)` или `i := i`.
- **Go 1.22+ (loopvar)**: переменная своя на каждой итерации → выведет `0..4` в произвольном порядке. На собесах всё ещё спрашивают «старое» поведение.

### 8. defer и момент вычисления аргументов

```go
type X struct{ V int }
func (x X) S() { fmt.Println(x.V) }

x := X{123}
defer x.S()              // вариант 1
x.V = 456                // → выведет 123

x := X{123}
defer func() { x.S() }() // вариант 2
x.V = 456                // → выведет 456
```

- Вариант 1: **аргументы defer (включая receiver) вычисляются в момент объявления** — value receiver копирует `x` с V=123. Вариант 2: замыкание захватывает `x` по ссылке и вызывает метод при выходе — видит 456.

### 9. SQL: покупки до бана + агрегация

Таблицы: `users(id, name)`, `purchases(id, user_id, product, amount, created_at)`, `ban_list(user_id, banned_at)`.

```sql
-- 1) уникальные пары (пользователь, товар) для покупок ДО бана
SELECT DISTINCT u.name, p.product
FROM users u
JOIN purchases p ON p.user_id = u.id
JOIN ban_list b  ON b.user_id = u.id
WHERE p.created_at < b.banned_at;

-- 2) пользователи с суммой покупок > 5000
SELECT u.name, SUM(p.amount) AS total
FROM users u
JOIN purchases p ON p.user_id = u.id
GROUP BY u.name
HAVING SUM(p.amount) > 5000
ORDER BY total DESC;
```

- Ключевое: `DISTINCT` для уникальных пар; INNER JOIN с `ban_list` оставляет только забаненных (если нужны все — LEFT JOIN + условие в ON/WHERE); фильтр по агрегату — только в `HAVING`; аккуратнее с `GROUP BY u.name` (имена могут совпадать — правильнее по `u.id, u.name`).

### 10. In-Memory Cache с TTL

`Set(key, value, ttl)` / `Get(key)`, элементы истекают по TTL, потокобезопасно; усложнение — шардирование.

- `Set`: под `Lock` положить `cacheItem{value, expiresAt: time.Now().Add(ttl)}`. `Get`: под `RLock` достать; если `time.Now().After(expiresAt)` — вернуть miss (**ленивая** очистка). Плюс фоновый janitor: горутина с `time.Ticker`, удаляющая просроченное (и `Stop`/`ctx` для остановки — иначе утечка). Шардирование: массив из N шардов `{mu, map}`, выбор по `hash(key) % N` — режет contention. Родственные разборы: [data-structures/01-lru-cache.md](coding-tasks/data-structures/01-lru-cache.md) и чек-лист ревью кэша в [oz_interview_questions.md](oz_interview_questions.md).

## Рекомендации по подготовке

Приоритеты из того же анализа (что тренировать в первую очередь):

1. **Знать наизусть:** слайсы (append, cap, общий backing-массив), map (устройство, потокобезопасность, ключи), каналы (закрытый/nil, буферы), defer (порядок, момент вычисления аргументов).
2. **Написать за 15 минут:** merge каналов (fan-in), worker pool, семафор на каналах, in-memory cache с TTL, параллельный HTTP-краулер — всё есть в [coding-tasks](coding-tasks/README.md).
3. **SQL уверенно:** JOIN + GROUP BY + HAVING, составные индексы (порядок колонок, селективность), EXPLAIN ANALYZE, уровни изоляции.
4. **Теория:** GMP, GC (tri-color, STW-фазы), ACID и CAP, Outbox/Saga, SOLID в Go.
5. **Senior-уровень:** чистая/гексагональная архитектура, Circuit Breaker/Retry/Bulkhead, DDD (агрегаты, bounded context), system design с нуля — см. [05-system-design](../05-system-design/README.md).
