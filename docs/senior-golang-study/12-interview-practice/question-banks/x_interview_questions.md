## Go — типы, слайсы, map и строки

### 1. Массив и слайс — в чём разница?

<details>
<summary>Краткий ответ</summary>

- Массив — значение фиксированного размера; длина входит в тип, поэтому `[3]int` и `[4]int` являются разными типами.
- Передача массива — копирует все элементы, если не используется указатель.
- Слайс — дескриптор над массивом: указатель на backing array, длина и ёмкость.
- Копирование слайса — копирует дескриптор, поэтому два слайса могут менять общий массив.
- Выбор — массив полезен для небольшого фиксированного размера и значения с семантикой копии, слайс — для коллекции переменной длины.

</details>

### 2. Как работает `append` в Go?

<details>
<summary>Краткий ответ</summary>

- Пока `len < cap`, `append` записывает элементы в существующий backing array и возвращает обновлённый дескриптор.
- Если ёмкости недостаточно, runtime выделяет новый массив, копирует элементы и возвращает слайс над новой памятью.
- Результат всегда присваивают: `s = append(s, value)`, иначе новый дескриптор может потеряться.
- Общий массив создаёт побочный эффект: `append` одного subslice иногда перезаписывает элементы другого, пока не произошла реаллокация.
- Если ожидаемый размер известен, `make([]T, 0, n)` или `slices.Grow` уменьшают число аллокаций и копирований.

</details>

### 3. Как меняется стратегия роста слайса?

<details>
<summary>Краткий ответ</summary>

- Формулировка про «маленькие и большие типы» неточна: основная формула зависит от старой ёмкости слайса, а не от размера типа элемента.
- В текущей реализации Go 1.27 при `oldCap < 256` целевая ёмкость обычно удваивается.
- Начиная с этого порога формула плавно переходит от роста около 2× к росту около 1,25×, чтобы большие массивы не резервировали слишком много лишней памяти.
- Если требуемая длина больше удвоенной ёмкости, runtime сразу берёт как минимум требуемую длину.
- Итоговый `cap` может отличаться от формулы из-за округления размера выделения по size class аллокатора; это implementation detail, на который код не должен опираться.

</details>

### 4. Что такое директива `go:linkname` и для чего она нужна?

<details>
<summary>Краткий ответ</summary>

- `//go:linkname local importpath.name` связывает локальную функцию или переменную с символом другого пакета на уровне линкера.
- Директива требует импортировать `unsafe` и может обходить экспортируемость и обычную проверку границы пакета.
- Она нужна главным образом runtime, стандартной библиотеке и низкоуровневой интеграции, где циклический импорт или ABI не выразить обычным Go API.
- Цена — нет нормального контракта типов и совместимости: изменение внутреннего символа может сломать сборку или память.
- В прикладном коде `go:linkname` обычно не используют; предпочтительнее публичный API или явная обёртка.

</details>

### 5. Что такое `notInHeapSlice`?

<details>
<summary>Краткий ответ</summary>

- `notInHeapSlice` — внутренняя структура runtime с полями указателя, длины и ёмкости, похожая на обычный slice header.
- Её backing memory имеет тип `NotInHeap` и выделяется низкоуровневыми аллокаторами вне управляемой GC-кучи.
- Runtime применяет её для собственных метаданных, где обычная heap allocation или write barrier недопустимы либо создают рекурсию в аллокаторе.
- Это не публичный тип и не оптимизация для прикладного кода: память нужно управлять вручную, а ошибки могут повредить runtime.
- В исходниках Go 1.27 имя записано как `notInHeapSlice`, а не `notheapslice`.

</details>

### 7. Как устроена `map` в Go?

<details>
<summary>Краткий ответ</summary>

- Public contract — map хранит пары ключ-значение, даёт `O(1)` в среднем для чтения, вставки и удаления и не гарантирует порядок обхода.
- В Go 1.24+ runtime использует Swiss Table: данные лежат в группах по восемь слотов, а управляющие байты позволяют быстро отбирать кандидатов по части хеша.
- Большая map состоит из нескольких таблиц; старшие биты хеша выбирают таблицу через директорию, а внутри используется открытая адресация.
- При заполнении таблица пересобирается с большей ёмкостью или делится на две; это современная модель вместо старых buckets и overflow chains.
- Несинхронизированная запись вместе с чтением или другой записью является data race; для неё нужен mutex, владение одной горутины или подходящий `sync.Map`.

</details>

### 8. Можно ли взять адрес элемента `map`?

<details>
<summary>Краткий ответ</summary>

- Нет, выражение `&m[key]` запрещено языком.
- Элемент map не addressable, потому что runtime может переместить его при росте, а присваивание `m[key]` работает через специальные операции map.
- Для изменения структуры значение читают, меняют копию и записывают обратно.
- Если нужна стабильная ссылка, в map хранят указатель: `map[K]*V`, но тогда нужно управлять общей изменяемостью и синхронизацией.

```go
value := m[key]
value.Count++
m[key] = value
```

</details>

### 16. Как устроены строки в Go и какие у них подводные камни?

<details>
<summary>Краткий ответ</summary>

- Строка — неизменяемая последовательность байтов с дескриптором `{data, len}`; тип сам по себе не гарантирует UTF-8.
- `len(s)` и `s[i]` работают с байтами, а `range` декодирует UTF-8 и возвращает индекс байта и руну.
- Руна — Unicode code point, но не обязательно видимый символ: один grapheme cluster может состоять из нескольких рун.
- Substring может удерживать большой исходный буфер; если это проблема, данные явно копируют.
- Преобразования `string` ↔ `[]byte` обычно копируют память, а многократную конкатенацию в цикле заменяют `strings.Builder`.

</details>

## Go — интерфейсы, reflection и generics

### 9. Что такое интерфейсы в Go и для чего они нужны?

<details>
<summary>Краткий ответ</summary>

- Интерфейс описывает набор методов, а конкретный тип реализует его неявно.
- Он позволяет потребителю зависеть от поведения, подменять реализацию в тесте и отделять слои.
- Интерфейс обычно объявляют на стороне потребителя и делают небольшим: один-два действительно нужных метода.
- Интерфейс лишний, если реализация одна, подмена не нужна и абстракция не выражает самостоятельный контракт.
- Полиморфизм имеет цену косвенного вызова и иногда boxing/heap allocation, поэтому на горячем пути решение подтверждают benchmark.

</details>

### 10. Как устроено интерфейсное значение и где хранятся его части?

<details>
<summary>Краткий ответ</summary>

- Непустой интерфейс концептуально содержит два машинных слова: указатель на `itab` для пары «интерфейс + конкретный тип» и указатель на данные.
- Пустой интерфейс содержит указатель на описание конкретного типа и указатель на данные.
- Сами два слова лежат там, где размещена переменная интерфейса — в стеке, куче или поле другого объекта; конкретное значение может храниться отдельно.
- Интерфейс равен nil, только когда оба слова пусты. Типизированный nil-указатель внутри `error` делает сам интерфейс ненулевым.
- Это описание текущей реализации runtime, а публичный контракт гарантирует динамический тип и динамическое значение, а не layout.

</details>

### 11. Что такое рефлексия и что предоставляет пакет `reflect`?

<details>
<summary>Краткий ответ</summary>

- Reflection позволяет во время выполнения узнать динамический тип и работать со значением через `reflect.Type` и `reflect.Value`.
- Возможности — обход полей и методов, создание значений, вызов функций, работа с тегами структур, map, slice и channel.
- Применения — сериализация, ORM, валидаторы, dependency injection и универсальные инструменты.
- Цена — меньше статических гарантий, больше проверок и возможных panic, хуже inlining и часто дополнительные аллокации.
- Перед reflection стоит проверить, не выражается ли задача интерфейсом, generics или обычной функцией.

</details>

### 12. Можно ли изменить приватное поле внешней структуры через reflection?

<details>
<summary>Краткий ответ</summary>

- Безопасным публичным API `reflect` — нет: такое поле имеет `CanSet() == false`, а `Set` вызовет panic.
- Значение можно обойти через `unsafe.Pointer` и адресуемую память, но это нарушение инкапсуляции и опора на layout.
- Такой код может ломаться при изменении структуры, версии Go или правилах `checkptr` и не подходит для прикладной логики.
- Нормальное решение — экспортируемый метод, конструктор, интерфейс или изменение API владельца типа.

</details>

### 13. Что такое `any` в Go?

<details>
<summary>Краткий ответ</summary>

- `any` — предопределённый alias для `interface{}`, введённый как более читаемое имя в коде с generics.
- Семантически `any` и `interface{}` идентичны: значение может иметь любой динамический тип.
- Для использования конкретного значения нужны type assertion, type switch или reflection.
- `any` не отключает типовую систему, но переносит часть проверок из compile time в runtime, поэтому конкретный тип или constraint обычно информативнее.

</details>

### 14. Что происходит с generics при компиляции? Как выбирается метод?

<details>
<summary>Краткий ответ</summary>

- Компилятор проверяет операции над `T` по constraint и создаёт instantiation для используемых наборов type arguments.
- В текущей реализации Go код может совместно использоваться типами одной GC shape, а сведения об операциях передаются через dictionary; это implementation detail.
- Вызов метода допустим, только если метод входит в method set constraint.
- Для конкретного type argument компилятор формирует нужную обёртку или запись dictionary, поэтому вызывается реализация соответствующего конкретного типа.
- Это не Java-style type erasure: сведения, нужные для layout, GC и операций, сохраняются, а итоговый код остаётся статически типизированным.

</details>

### 15. Что такое constraint в generics Go?

<details>
<summary>Краткий ответ</summary>

- Constraint — интерфейс, который задаёт множество допустимых type arguments и операции, разрешённые над параметром типа.
- `any` разрешает любой тип, `comparable` — типы, которые можно сравнивать `==` и использовать как ключ map.
- Type set можно сузить объединением `|` и приближённым типом `~T`, который принимает именованные типы с underlying type `T`.
- Constraint используется только при компиляции generic-кода и не обязательно подходит как обычный runtime-интерфейс.
- Хороший constraint минимален: он разрешает ровно те операции, которые действительно нужны функции.

</details>

## Go — runtime, конкурентность и синхронизация

### 17. Опиши G-M-P модель в Go

<details>
<summary>Краткий ответ</summary>

- G — горутина с её стеком и состоянием, M — поток ОС, P — ресурс runtime для исполнения Go-кода.
- Чтобы M исполнял G, ему нужен P; число P задаётся `GOMAXPROCS`.
- У каждого P есть локальная очередь runnable goroutines, существует глобальная очередь и work stealing между P.
- При блокирующем syscall M может оставить P, чтобы другой M продолжил выполнять Go-код.
- Горутины переключаются при блокировках, вызовах, safe points и асинхронной preemption; runtime старается совмещать производительность и справедливость.

</details>

### 18. Что такое netpoller и sysmon в Go runtime?

<details>
<summary>Краткий ответ</summary>

- Netpoller интегрирует сетевые дескрипторы с epoll, kqueue или IOCP. Ожидающая I/O горутина паркуется, не удерживая отдельный поток ОС.
- Когда дескриптор готов, netpoller возвращает горутину в очередь выполнения.
- Sysmon — системная goroutine runtime, которая работает без P и периодически проверяет таймеры, долгие syscall, необходимость preemption и условия запуска GC.
- Sysmon также возвращает P от зависших в syscall M и помогает не допустить монополизации процессора долгой горутиной.
- Это внутренние компоненты runtime, поэтому точные интервалы и алгоритмы зависят от версии Go.

</details>

### 19. Какие виды каналов существуют в Go?

<details>
<summary>Краткий ответ</summary>

- Небуферизованный канал — отправитель и получатель встречаются; send завершается только при готовом receiver.
- Буферизированный канал — очередь фиксированной ёмкости; send блокируется на полном буфере, receive — на пустом.
- По направлению тип может быть двунаправленным `chan T`, только для отправки `chan<- T` или только для чтения `<-chan T`.
- Nil-канал блокирует send и receive навсегда, что иногда используют для выключения ветки `select`.
- Закрытый канал сначала отдаёт остаток буфера, затем нулевое значение и `ok == false`; запись в него паникует.

</details>

### 20. Какие поля `hchan` отвечают за буферизацию?

<details>
<summary>Краткий ответ</summary>

- `dataqsiz` — ёмкость кольцевого буфера, `qcount` — текущее число элементов.
- `buf` — указатель на массив элементов.
- `sendx` и `recvx` — индексы следующей записи и чтения.
- `sendq` и `recvq` содержат ожидающих goroutines, а `lock` защищает внутреннее состояние.
- Канал небуферизованный, когда `dataqsiz == 0`; layout `hchan` является implementation detail runtime.

</details>

### 21. Как данные передаются через небуферизированный канал?

<details>
<summary>Краткий ответ</summary>

- Буфера нет, поэтому операция требует пары sender-receiver.
- Если receiver уже ждёт в `recvq`, runtime под lock находит его `sudog` и копирует значение напрямую из стека отправителя в адрес назначения получателя.
- Если пары нет, sender описывается через `sudog`, помещается в `sendq` и паркуется через `gopark`.
- Когда появляется receiver, он завершает передачу и делает sender runnable.
- `sendx`, `recvx` и `buf` в этом пути не используются для хранения значения; они важны для буферизированного канала.

</details>

### 22. Какие примитивы синхронизации существуют в Go?

<details>
<summary>Краткий ответ</summary>

- `Mutex` и `RWMutex` защищают общую изменяемую память.
- `WaitGroup` ждёт завершения задач, `Once` выполняет функцию один раз, `Cond` уведомляет ожидающих об изменении условия.
- `sync/atomic` предоставляет атомарные операции и типы для небольшого независимого состояния.
- Каналы координируют передачу данных, а `context.Context` распространяет отмену и дедлайн.
- Выбор зависит от задачи: mutex проще для короткой критической секции, channel — для потока данных и передачи владения.

</details>

### 23. Как устроен `sync.Mutex` под капотом?

<details>
<summary>Краткий ответ</summary>

- Публичный `sync.Mutex` в Go 1.27 оборачивает внутренний mutex с полями `state int32` и `sema uint32`.
- Fast path пытается атомарным CAS заменить свободное состояние на locked.
- Slow path может коротко spin, затем учитывает waiter в `state` и паркует goroutine на runtime semaphore.
- `Unlock` атомарно снимает locked bit и при необходимости будит waiter или передаёт ему владение.
- Mutex нельзя копировать после первого использования: копия разделит логическое состояние и semaphore некорректно.

</details>

### 24. Какие состояния есть у мьютекса?

<details>
<summary>Краткий ответ</summary>

- `mutexLocked` — mutex занят.
- `mutexWoken` — один waiter уже разбужен, поэтому не нужно будить ещё одного.
- `mutexStarving` — включён режим прямой передачи владения ожидающему.
- Старшие биты `state` хранят количество waiters.
- На более высоком уровне выделяют два режима работы: normal для производительности и starvation для ограничения хвостовой задержки.

</details>

### 25. Что такое starvation в многопоточности?

<details>
<summary>Краткий ответ</summary>

- Starvation, или голодание, означает, что goroutine долго не получает ресурс, хотя система в целом продолжает работать.
- Для mutex это возможно, когда новые работающие goroutines постоянно выигрывают гонку у уже разбуженного waiter.
- Это отличается от deadlock: при deadlock прогресс невозможен, при starvation прогресс есть у других участников.
- Причины — несправедливый lock, приоритеты, длинные критические секции или постоянный поток новых конкурентов.
- Наблюдать проблему помогают mutex profile, trace и распределение времени ожидания, особенно p99.

</details>

### 26. Что делает Go при голодании mutex? Как с этим связан spinlock?

<details>
<summary>Краткий ответ</summary>

- В normal mode waiter после пробуждения конкурирует с новыми goroutines; новые участники имеют преимущество, потому что уже выполняются на CPU.
- Если waiter не получает mutex дольше примерно 1 мс, реализация переключает mutex в starvation mode.
- В starvation mode `Unlock` напрямую передаёт владение первому waiter, а новые goroutines становятся в хвост.
- Active spinning используется только в normal mode и при подходящих условиях: несколько CPU, короткое ожидание и возможность скорого освобождения.
- В starvation mode новые участники не spin, потому что захват всё равно передаётся очереди; после сокращения очереди mutex возвращается в normal mode.

</details>

### 27. Что такое `sync.Pool` и для чего он используется?

<details>
<summary>Краткий ответ</summary>

- `sync.Pool` временно хранит переиспользуемые объекты и уменьшает число аллокаций и нагрузку на GC.
- Типичный пример — буферы или временные структуры одинакового назначения на горячем пути.
- Pool имеет локальные для P области и victim cache, но runtime может удалить элементы при любой сборке мусора.
- Это не кэш и не пул ресурсов с обязательным возвратом: в нём нельзя хранить соединения, лимитированные или требующие `Close` объекты.
- Польза подтверждается benchmark с `allocs/op`; для редких или дешёвых объектов Pool может только усложнить код.

</details>

## Память и Garbage Collector

### 28. Как устроен Garbage Collector в Go? Каковы его плюсы и минусы?

<details>
<summary>Краткий ответ</summary>

- GC Go — tracing mark-sweep collector: он находит достижимые объекты от roots, помечает их, а недостижимую память возвращает аллокатору.
- Основная mark-фаза выполняется конкурентно с приложением; короткие stop-the-world паузы нужны на границах цикла.
- Плюсы — автоматическое управление памятью, защита от use-after-free обычных Go-объектов и небольшие паузы.
- Цена — CPU на marking, дополнительная память между циклами, write barrier и менее предсказуемая latency.
- Частоту косвенно задают `GOGC` или `debug.SetGCPercent`, а предел памяти — `GOMEMLIMIT` или `debug.SetMemoryLimit`. Уменьшение значений снижает память, но повышает CPU.

</details>

### 29. Какие объекты считаются мусором для Garbage Collector?

<details>
<summary>Краткий ответ</summary>

- Мусор — heap-объекты, которые больше недостижимы по цепочке указателей от roots.
- Roots включают глобальные данные, живые области стеков goroutines, регистры и ссылки, которые знает runtime.
- Scope переменной не равен времени жизни: компилятор может считать значение мёртвым раньше конца функции, если оно больше не используется.
- Циклические ссылки не мешают сборке: цикл без пути от root целиком недостижим.
- `uintptr` не считается живой GC-ссылкой, поэтому преобразования через `unsafe` требуют строгого соблюдения правил времени жизни.

</details>

### 30. Где находятся объекты, на которые больше нет ссылок?

<details>
<summary>Краткий ответ</summary>

- Они остаются в своих span на heap, пока GC не обнаружит их недостижимость и sweep не освободит соответствующие слоты.
- После sweep память сначала доступна аллокатору для новых объектов того же size class.
- Полностью свободные страницы runtime может позже scavenging-механизмом вернуть операционной системе или пометить как доступные для повторного использования.
- Поэтому «объект стал мусором» не означает немедленное уменьшение RSS процесса.

</details>

### 31. В чём разница между стеком и кучей?

<details>
<summary>Краткий ответ</summary>

- Стек принадлежит goroutine, растёт и уменьшается вместе с ней; выделение обычно сводится к сдвигу указателя и не требует GC.
- Heap общая для процесса; объекты живут независимо от кадра функции и освобождаются GC.
- Решение принимает компилятор через escape analysis, а не использование `new` или указателя само по себе.
- Стек goroutine динамически растёт копированием в более крупную область, поэтому адреса стековых объектов корректирует runtime.
- Heap allocation дороже не только сама по себе: объект нужно сканировать и учитывать в последующих циклах GC.

</details>

### 32. Как понять, почему объект попал в heap? Что такое escape analysis?

<details>
<summary>Краткий ответ</summary>

- Escape analysis — статический анализ потока указателей, которым компилятор доказывает, может ли значение безопасно жить в stack frame.
- Если ссылка может пережить frame или попасть в heap, само значение размещается в heap.
- Диагностика — `go build -gcflags='-m=2' ./...` или аналогичный запуск `go test` показывает причины escape и решения об inlining.
- Реальную цену проверяют benchmark с `-benchmem` и heap/allocs profile, потому что сообщение компилятора ещё не доказывает проблему производительности.
- Анализ консервативен и меняется между версиями компилятора, поэтому на конкретное размещение нельзя опираться для корректности.

</details>

### 33. Какие три постулата escape analysis существуют?

<details>
<summary>Краткий ответ</summary>

Формулировку стоит поправить: исходник компилятора Go 1.27 называет два ключевых инварианта, а не три:

1. Указатель на stack-объект нельзя сохранить в heap.
2. Указатель на stack-объект не может пережить сам объект.

Если путь данных может нарушить хотя бы один инвариант, объект перемещается в heap. Большой размер, неизвестный размер, захват замыканием и передача через неизвестный вызов являются причинами конкретных решений компилятора, но не «третьим постулатом».

Программист не должен вручную «придерживаться постулатов»: корректность обеспечивает компилятор. Оптимизируют escape только после измерения allocations и профиля.

</details>

### 34. Кто запускает Garbage Collector и кто выполняет его работу?

<details>
<summary>Краткий ответ</summary>

- Цикл запускает runtime, когда pacer достигает целевого размера heap; его также можно запустить через `runtime.GC`, а sysmon инициирует редкую принудительную сборку при долгом простое.
- Нет одного выделенного «потока GC»: concurrent mark выполняют фоновые GC workers, запланированные на P.
- Goroutines приложения могут выполнять mark assist пропорционально новым аллокациям, если приложение создаёт память быстрее фоновой разметки.
- Stop-the-world переходы координирует runtime, а sweep выполняется конкурентно и частично по требованию аллокатора.
- Поэтому GC потребляет часть CPU приложения, даже если паузы короткие.

</details>

### 35. Что происходит во время запуска и работы Garbage Collector?

<details>
<summary>Краткий ответ</summary>

1. Mark setup — короткая stop-the-world пауза включает write barrier, подготавливает workers и roots.
2. Concurrent mark — GC обходит граф от roots, workers и mark assists помечают достижимые объекты, а write barrier сохраняет корректность при изменениях указателей.
3. Mark termination — вторая короткая stop-the-world пауза завершает разметку и выключает barrier.
4. Sweep — непомеченные слоты освобождаются конкурентно или при следующем запросе span.
5. Scavenging — полностью свободные физические страницы со временем могут быть возвращены ОС.

Главные наблюдаемые цены — CPU workers/assists, рост heap между циклами и короткие STW-паузы.

</details>

## Базы данных и PostgreSQL

### 36. Что такое ACID?

<details>
<summary>Краткий ответ</summary>

- Atomicity — транзакция фиксируется целиком или целиком откатывается.
- Consistency — подтверждённая транзакция сохраняет ограничения и инварианты, если сама бизнес-логика корректна.
- Isolation — параллельные транзакции не должны наблюдать запрещённые выбранным уровнем аномалии.
- Durability — после подтверждённого commit изменения переживают сбой в рамках гарантий настроенной системы.
- ACID не означает отсутствие ошибок или строго последовательную работу всех транзакций: гарантии зависят от уровня изоляции и конфигурации durability.

</details>

### 37. За счёт чего достигается Durability в СУБД?

<details>
<summary>Краткий ответ</summary>

- Изменения сначала записываются в устойчивый журнал — WAL, а страницы таблиц можно сбросить позже.
- PostgreSQL подтверждает commit после записи commit record и необходимого `fsync` WAL, если `synchronous_commit` и нижележащее хранилище настроены на такую гарантию.
- После сбоя recovery повторяет подтверждённые изменения из WAL.
- Репликация и backup защищают от отказа узла и потери носителя, но их RPO зависит от синхронности, лага и частоты копий.
- Durability — сквозное свойство: дисковый контроллер или облачное хранилище должны честно выполнять flush.

</details>

### 38. Как работает Write-Ahead Log и зачем он нужен?

<details>
<summary>Краткий ответ</summary>

- Правило WAL — запись об изменении должна попасть в устойчивый журнал раньше изменённой страницы данных.
- Commit требует дописать небольшой последовательный журнал, а случайные записи dirty pages выполняются позже и батчами.
- После crash recovery PostgreSQL начинает от checkpoint и повторяет WAL records, восстанавливая согласованное состояние.
- WAL также используется для physical replication, point-in-time recovery и архивирования.
- Цена — дополнительная запись и объём хранения; долгий лаг реплики или забытый replication slot способен удерживать WAL и заполнить диск.

</details>

### 39. Какие уровни изоляции транзакций существуют?

<details>
<summary>Краткий ответ</summary>

- Read Uncommitted — стандарт допускает dirty read, но PostgreSQL обрабатывает этот уровень как Read Committed.
- Read Committed — каждый SQL-оператор получает снимок на начало оператора; два `SELECT` одной транзакции могут увидеть разные commit.
- Repeatable Read — снимок стабилен на транзакцию; PostgreSQL предотвращает phantom read, но допускает serialization anomaly.
- Serializable — результат подтверждённых транзакций эквивалентен некоторому последовательному порядку; конфликт может завершить транзакцию ошибкой `40001`.
- Чем сильнее уровень, тем больше конфликтов и retry, поэтому его выбирают под конкретный бизнес-инвариант.

</details>

### 40. Как транзакции PostgreSQL работают под капотом?

<details>
<summary>Краткий ответ</summary>

- `BEGIN` создаёт контекст транзакции и XID по необходимости; без явного блока каждый оператор выполняется в собственной транзакции.
- MVCC хранит версии строк с информацией о видимости, а snapshot определяет, какие версии видит текущий оператор или транзакция.
- `UPDATE` обычно создаёт новую версию tuple, а старая остаётся до vacuum; конкурирующие изменения дополнительно используют row locks.
- WAL описывает изменения для recovery и replication.
- `COMMIT` делает транзакцию видимой и обеспечивает настроенную долговечность, `ROLLBACK` оставляет её версии невидимыми, после чего их убирает vacuum.

</details>

### 41. Как создать индекс на столбце активно читаемой таблицы объёмом 2 ТБ?

<details>
<summary>Краткий ответ</summary>

- Для production-таблицы обычно используют `CREATE INDEX CONCURRENTLY`, чтобы не блокировать обычные `INSERT`, `UPDATE` и `DELETE` на всё время build.
- До запуска проверяют свободное место под индекс и временные данные, I/O budget, long-running transactions, replica lag и окно сниженной нагрузки.
- Создание наблюдают через `pg_stat_progress_create_index`, системные метрики и состояние реплик.
- После завершения проверяют `indisvalid`, размер индекса и реальный план через `EXPLAIN (ANALYZE, BUFFERS)`.
- Для partitioned table индекс часто строят concurrently на каждой partition, затем подключают к родительскому partitioned index.

```sql
CREATE INDEX CONCURRENTLY idx_events_created_at
    ON events (created_at);
```

</details>

### 42. Что происходит с блокировками при обычном `CREATE INDEX`?

<details>
<summary>Краткий ответ</summary>

- Обычный `CREATE INDEX` берёт `SHARE` lock на таблицу.
- Обычные `SELECT` продолжаются, потому что их `ACCESS SHARE` совместим с этим lock.
- `INSERT`, `UPDATE`, `DELETE` и `MERGE` блокируются до окончания build, потому что их `ROW EXCLUSIVE` конфликтует с `SHARE`.
- На таблице 2 ТБ такая блокировка может длиться часы и создать большую очередь запросов.
- Сам build читает всю таблицу и создаёт заметную I/O и CPU нагрузку даже без ожиданий на lock.

</details>

### 43. Как работает `CREATE INDEX CONCURRENTLY`?

<details>
<summary>Краткий ответ</summary>

1. PostgreSQL добавляет индекс в каталог как ещё неготовый.
2. Ждёт транзакции, которые могли изменять таблицу, и выполняет первый scan для построения индекса.
3. Снова ждёт подходящие writers и выполняет второй scan, добавляя изменения, возникшие параллельно.
4. Ждёт старые snapshots и помечает индекс valid.

- Команда не блокирует обычную запись, но берёт `SHARE UPDATE EXCLUSIVE` lock, мешает некоторым DDL и создаёт дополнительную I/O нагрузку.
- Она делает больше работы и обычно выполняется дольше обычного build.
- Её нельзя запускать внутри transaction block; одновременно на одной таблице выполняется только один concurrent build.
- При ошибке может остаться `INVALID`-индекс, который занимает место и добавляет цену записи; его нужно удалить или перестроить.

</details>

### 44. Как создавали индекс без долгой блокировки до появления `CONCURRENTLY`?

<details>
<summary>Краткий ответ</summary>

- Самый надёжный вариант — maintenance window: остановить запись, построить индекс обычным способом и вернуть трафик.
- При недопустимом простое создавали shadow table со схемой и индексами, копировали исторические данные, синхронизировали новые изменения триггерами или логической репликацией и делали короткий swap.
- Альтернатива — поднять новую реплику или кластер с нужным индексом, догнать изменения и переключить трафик.
- Эти схемы сложнее `CREATE INDEX CONCURRENTLY`: нужно исключить потерю или двойное применение изменений и заранее продумать rollback.
- В PostgreSQL `CONCURRENTLY` существует с версии 8.2, поэтому сегодня историческую обходную схему применяют только при особых ограничениях.

</details>

### 45. Какие типы индексов существуют в PostgreSQL?

<details>
<summary>Краткий ответ</summary>

- B-tree — равенство, диапазоны, сортировка и большинство обычных скалярных запросов.
- Hash — только равенство.
- GIN — составные значения с множеством ключей: `jsonb`, массивы, полнотекстовый поиск.
- GiST — расширяемое дерево для диапазонов, геометрии, nearest-neighbor и ряда операторных классов.
- SP-GiST — пространство-разделяющие структуры вроде trie, quadtree и k-d tree.
- BRIN — компактные summaries диапазонов блоков для очень больших физически коррелированных таблиц.
- Кроме access method, индексы бывают составными, уникальными, частичными, expression и covering через `INCLUDE`.

</details>

### 46. Чем hash-индекс отличается от B-tree?

<details>
<summary>Краткий ответ</summary>

- B-tree упорядочивает ключи и поддерживает `=`, диапазоны, `ORDER BY`, `MIN`/`MAX` и префиксные условия с подходящим operator class.
- Hash хранит hash code и поддерживает только равенство.
- B-tree универсальнее и является индексом по умолчанию; hash стоит выбирать только после измерения конкретной equality-heavy нагрузки.
- Оба индекса WAL-logged и crash-safe в современных PostgreSQL, поэтому старое утверждение «hash не журналируется» больше неверно.
- Ни один тип не является автоматически быстрее: важны селективность, размер ключа, cache locality, запись и реальный план.

</details>

### 47. Как расшифровывается B-tree?

<details>
<summary>Краткий ответ</summary>

- У буквы B нет общепринятой официальной расшифровки; часто говорят balanced tree, но это скорее удобная мнемоника.
- Это не binary tree: один page содержит много ключей и дочерних ссылок.
- Главное свойство — все leaves находятся на одной глубине, поэтому поиск, вставка и удаление имеют логарифмическую сложность.
- В базе данных node обычно соответствует disk page, а высокая ветвистость уменьшает число page reads.

</details>

### 48. Какова типичная глубина B-tree и почему дерево остаётся сбалансированным?

<details>
<summary>Краткий ответ</summary>

- Фиксированной глубины нет; благодаря сотням ключей на page для миллионов и даже миллиардов строк часто хватает примерно 3–5 уровней.
- Поиск идёт от root через internal pages к leaf, поэтому его цена растёт логарифмически.
- При заполнении page PostgreSQL делит её и добавляет separator в parent; если переполнен root, создаётся новый root и высота увеличивается на один.
- Все листья сохраняются на одной глубине, поэтому длинная ветка не возникает.
- Реальную глубину и состояние индекса проверяют инструментами вроде `pageinspect` и метриками, а не предполагают по размеру таблицы.

</details>

### 49. Приходилось ли работать с полигонами и GIS-данными?

<details>
<summary>Краткий ответ</summary>

- Сначала честно назвать уровень опыта: PostGIS в production, учебный проект или только знакомство с моделью.
- Модель — `geometry` работает в заданной системе координат, `geography` удобна для расстояний по поверхности Земли; важно правильно выбрать SRID.
- Операции — привести пример `ST_Contains`, `ST_Intersects`, `ST_DWithin` или nearest-neighbor.
- Индекс — обычно GiST, который сначала отбирает кандидатов по bounding box, после чего точный оператор проверяет геометрию.
- Практические риски — невалидные polygons, перепутанные координаты и SRID, дорогие сложные границы и запрос без индексируемого предиката.

</details>

## Практические задачи

### 51. Развернуть слайс

Нужно реализовать `reverse` так, чтобы программа изменила исходный слайс `[3, 2, 1]` на `[1, 2, 3]`.

```go
func reverse(values []int) {
    // write here
}
```

<details>
<summary>Решение</summary>

Два указателя меняют крайние элементы местами и двигаются к центру:

```go
func reverse(values []int) {
    for left, right := 0, len(values)-1; left < right; {
        values[left], values[right] = values[right], values[left]
        left++
        right--
    }
}
```

- Время — `O(n)`: каждый элемент участвует не более чем в одном обмене.
- Дополнительная память — `O(1)`.
- Функция меняет backing array исходного слайса, поэтому вызывающий код увидит результат.
- Пустой слайс и слайс из одного элемента корректно остаются без изменений.

</details>

### 52. Реализовать LRU Cache

Нужно реализовать LRU Cache фиксированной ёмкости:

- `Get(key int) int` возвращает значение или `-1`, если ключ отсутствует;
- `Put(key, value int)` добавляет или обновляет значение;
- при переполнении удаляется least recently used элемент;
- `Get` и `Put` работают за `O(1)`.

<details>
<summary>Решение</summary>

Map даёт доступ по ключу за `O(1)`, а двусвязный список хранит порядок использования. Начало списка — самый свежий элемент, конец — кандидат на удаление.

```go
type cacheEntry struct {
    key   int
    value int
}

type LRUCache struct {
    capacity int
    items    map[int]*list.Element
    order    *list.List
}

func NewLRUCache(capacity int) *LRUCache {
    if capacity < 0 {
        capacity = 0
    }

    return &LRUCache{
        capacity: capacity,
        items:    make(map[int]*list.Element, capacity),
        order:    list.New(),
    }
}

func (c *LRUCache) Get(key int) int {
    element, ok := c.items[key]
    if !ok {
        return -1
    }

    c.order.MoveToFront(element)
    return element.Value.(*cacheEntry).value
}

func (c *LRUCache) Put(key, value int) {
    if element, ok := c.items[key]; ok {
        element.Value.(*cacheEntry).value = value
        c.order.MoveToFront(element)
        return
    }

    if c.capacity == 0 {
        return
    }

    element := c.order.PushFront(&cacheEntry{
        key:   key,
        value: value,
    })
    c.items[key] = element

    if c.order.Len() <= c.capacity {
        return
    }

    oldest := c.order.Back()
    entry := oldest.Value.(*cacheEntry)
    delete(c.items, entry.key)
    c.order.Remove(oldest)
}
```

- `Get` двигает найденный элемент в начало; чтение тоже считается использованием.
- `Put` обновляет существующий элемент либо добавляет новый и удаляет конец при переполнении.
- Время `Get` и `Put` — `O(1)`, память — `O(capacity)`.
- Реализация не concurrency-safe. Для совместного доступа нужен mutex либо внешняя сериализация операций.
- API с `-1` не различает отсутствующий ключ и сохранённое значение `-1`; production API обычно возвращает `(value, ok)`.

</details>
