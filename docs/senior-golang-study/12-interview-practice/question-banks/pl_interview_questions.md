## Go — рантайм, память и конкурентность

### 6. Можно ли потерять данные, если закрыть канал до их прочтения?

<details>
<summary>Краткий ответ</summary>

- `close` не удаляет уже отправленные значения: получатель сначала вычитает весь буфер, затем получает нулевое значение и `ok == false`.
- Небуферизованный канал нельзя закрыть «после отправки, но до чтения»: успешная отправка уже означает встречу с получателем.
- Потеря возможна на уровне приложения, если потребитель сам прекратил чтение или процесс завершился до обработки данных.
- Канал закрывает отправитель, когда новых значений больше не будет; запись в закрытый канал вызывает панику.

</details>

### 7. Чем буферизированный канал отличается от небуферизированного?

<details>
<summary>Краткий ответ</summary>

- Небуферизованный канал — rendezvous: отправка завершается только когда получатель готов принять значение.
- Буферизированный канал — очередь фиксированной ёмкости: отправитель не блокируется, пока в ней есть место.
- Буфер не гарантирует обработку и не устраняет backpressure, а лишь откладывает момент блокировки.
- Небуферизованный канал удобен для синхронизации передачи, буферизированный — для сглаживания коротких всплесков и ограничения числа ожидающих задач.
- Размер буфера выбирают из модели нагрузки и допустимой памяти, а не «чем больше, тем лучше».

</details>

### 8. Что можно прочитать из закрытого канала? Что будет после записи 500 значений и закрытия?

<details>
<summary>Краткий ответ</summary>

- Из закрытого канала сначала читаются все значения, которые остались в буфере.
- После опустошения чтение немедленно возвращает нулевое значение типа и `ok == false`.
- Цикл `for v := range ch` обработает все 500 значений и завершится после опустошения канала.
- Сам факт «сначала записать 500» возможен только при буфере не меньше 500 или при параллельном получателе; иначе отправитель заблокируется раньше `close`.

</details>

### 9. Какие ещё проблемы могут быть в предложенном многопоточном коде? Что будет только с большими значениями?

<details>
<summary>Краткий ответ</summary>

Без исходного листинга точный результат определить нельзя. На code review такого кода я последовательно проверяю:

- кто закрывает канал и может ли запись произойти после `close`;
- завершатся ли все горутины при ошибке или раннем выходе потребителя;
- нет ли data race, захвата переменной цикла, deadlock и неограниченного числа горутин;
- есть ли cancellation, backpressure и ограничение памяти;
- может ли фильтр отбросить все «большие» значения, после чего потребитель будет ждать результат, хотя продюсер уже заблокирован или канал никто не закрывает.

Последний пункт нельзя утверждать без кода: значения сами по себе не меняют семантику канала, проблема появляется из-за логики их обработки.

</details>

### 10. С какими примитивами синхронизации работал? Какой синтаксический сахар есть в Go?

<details>
<summary>Краткий ответ</summary>

- Общая память — `sync.Mutex`, `RWMutex` и атомарные операции защищают состояние.
- Координация — `WaitGroup` ждёт завершения, `Once` выполняет действие один раз, `Cond` будит ожидающих по условию.
- Передача владения — каналы и `select` координируют обмен данными; `context.Context` распространяет отмену и дедлайн.
- Языковые конструкции — `go` запускает горутину, `select` выбирает готовую операцию с каналом, `defer` удобно гарантирует `Unlock` или `Done`.
- Удобный API — `WaitGroup.Go` объединяет запуск задачи с учётом в группе, но не возвращает результат или ошибку.

</details>

### 11. Как устроен планировщик Go? Как работает netpoller? Чем файловый I/O отличается от сетевого?

<details>
<summary>Краткий ответ</summary>

- Модель G-M-P — G является горутиной, M — потоком ОС, P — ресурсом runtime, необходимым для выполнения Go-кода.
- Планирование — у P есть локальная очередь, существует глобальная очередь и work stealing; `GOMAXPROCS` ограничивает число P, одновременно исполняющих Go-код.
- Netpoller — регистрирует поддерживаемые сетевые дескрипторы в системном механизме ожидания. Горутина паркуется, а поток может выполнять другую работу; готовность I/O возвращает горутину в очередь.
- Обычные файлы — для epoll/kqueue обычно не дают полезной асинхронной готовности. Блокирующее чтение может занять M; runtime отдаёт его P другому M, но множество файловых операций способно создать много потоков ОС.
- Практический вывод — конкурентность сети дешёвая по числу потоков, а тяжёлый файловый I/O стоит ограничивать пулом и измерять.

</details>

### 19. Как завершить операцию, если данные из горутины не поступили вовремя?

<details>
<summary>Краткий ответ</summary>

Ожидание оборачивают в `select` с контекстом или таймером:

```go
func waitResult(ctx context.Context, ch <-chan Result) (Result, error) {
    select {
    case result, ok := <-ch:
        if !ok {
            return Result{}, io.EOF
        }
        return result, nil
    case <-ctx.Done():
        return Result{}, ctx.Err()
    }
}
```

Отмена ожидания не останавливает продюсера автоматически. Продюсер тоже должен принимать тот же `ctx` и проверять `ctx.Done()` при блокирующей отправке, иначе горутина может утечь.

</details>

### 20. Что возвращает `ctx.Done()`?

<details>
<summary>Краткий ответ</summary>

- Тип — receive-only канал `<-chan struct{}`.
- Сигнал — канал закрывается при отмене контекста или истечении дедлайна; значение в него не отправляется.
- Причина — после сигнала читается через `ctx.Err()` или `context.Cause(ctx)`.
- Неотменяемый контекст, например `context.Background()`, может вернуть nil-канал, который никогда не становится готовым.
- Закрытие канала будит сразу всех ожидающих получателей.

</details>

### 43. Где хранятся переменные — на стеке или в куче?

<details>
<summary>Краткий ответ</summary>

- Это решает компилятор, а не тип переменной и не использование `new` само по себе.
- На стеке остаётся значение, если компилятор доказывает, что оно не переживёт вызов и не требуется в месте с неизвестным временем жизни.
- В кучу значение уходит, когда возвращается достижимый указатель, значение захватывает долгоживущее замыкание, адрес передаётся в неизвестный код или размер слишком велик либо неизвестен.
- Поле структуры хранится внутри самой структуры: если структура в куче, поле тоже является частью объекта в куче.
- Проверить решение можно флагом компилятора `-gcflags='-m -m'`, а реальную цену — benchmark с `-benchmem`.

</details>

### 44. Что делает escape analysis в Go?

<details>
<summary>Краткий ответ</summary>

- Escape analysis статически определяет, может ли ссылка на значение пережить стековый кадр или попасть в место с более долгим временем жизни.
- Если безопасность стека доказать нельзя, компилятор размещает значение в куче.
- Это гарантирует корректность возвращаемого указателя на локальную переменную: объект не исчезает после возврата функции.
- Цена escape — heap allocation и дополнительная работа GC; однако преждевременно переписывать код ради стека не стоит, сначала нужны benchmark и профиль.
- Анализ консервативен и зависит от конкретного кода, inlining и версии компилятора.

</details>

### 45. Чем горутина отличается от потока операционной системы?

<details>
<summary>Краткий ответ</summary>

- Горутина планируется runtime Go, а поток — ядром ОС.
- Горутина начинается с небольшого растущего стека, поэтому их можно создать значительно больше, чем потоков.
- Множество G мультиплексируется на меньшее число M; переключение горутин обычно дешевле переключения потоков.
- Блокировка одной горутины на канале или сетевом I/O обычно освобождает M для другой работы либо позволяет runtime использовать другой M.
- Горутина не бесплатна: она удерживает стек, ссылки и служебные структуры, поэтому нужны ограничения конкурентности и завершение по контексту.

</details>

### 46. Что делает `GOMAXPROCS`?

<details>
<summary>Краткий ответ</summary>

- `GOMAXPROCS` задаёт число P и тем самым максимальное количество потоков, которые одновременно исполняют Go-код.
- Это не лимит горутин и не жёсткий лимит потоков ОС: дополнительные M нужны для блокирующих syscall, runtime и cgo.
- Для CPU-bound нагрузки увеличение выше доступного CPU обычно не помогает и добавляет переключения.
- Для I/O-bound нагрузки тысячи горутин могут ожидать при небольшом `GOMAXPROCS`, потому что ожидание не равно исполнению Go-кода.

</details>

### 47. Сколько потоков ОС и горутин может существовать в Go-программе?

<details>
<summary>Краткий ответ</summary>

- Фиксированного числа нет.
- Потоки — runtime создаёт M по необходимости; их может быть больше `GOMAXPROCS` из-за syscall и cgo, а предел задают runtime и ОС.
- Горутины — практический предел определяется памятью под стеки и объекты, работой планировщика, файловыми дескрипторами и внешними лимитами.
- Правильный дизайн не опирается на теоретический максимум: конкурентность ограничивают семафором или worker pool и наблюдают очередь, latency и память.

</details>

### 48. Как горутины взаимодействуют и обмениваются данными?

<details>
<summary>Краткий ответ</summary>

- Каналы — передают значения и могут передавать владение данными между горутинами.
- Общая память — защищается `Mutex`, `RWMutex` или атомарными операциями.
- Завершение — `WaitGroup` ждёт задачи, а `context.Context` распространяет отмену и дедлайн.
- Однократная инициализация и условия — `Once` и `Cond` решают более специальные задачи.
- Выбор — канал удобен для потока данных и координации, mutex проще для короткой критической секции над общим состоянием.

</details>

### 49. Может ли `sync.WaitGroup` возвращать ошибку?

<details>
<summary>Краткий ответ</summary>

- Нет, методы `Add`, `Done`, `Wait` и `Go` не возвращают `error`.
- WaitGroup отслеживает только завершение задач, а не их результат.
- Ошибки собирают через отдельный канал или `errgroup.Group`, который также умеет отменять связанные задачи по контексту.
- Неверное использование WaitGroup приводит не к возвращаемой ошибке, а к panic или deadlock, например отрицательный счётчик или забытый `Done`.

</details>

## Тестирование и эксплуатация

### 16. Был ли у тебя опыт тестирования? С какими видами тестирования работал?

<details>
<summary>Краткий ответ</summary>

- Unit-тесты — проверяют бизнес-логику изолированно, обычно table-driven и с минимальными стабами.
- Интеграционные тесты — проверяют реальные контракты с PostgreSQL, Kafka или HTTP-сервисом; зависимости поднимаются в контейнерах.
- Контрактные и end-to-end тесты — защищают границы сервисов и основные пользовательские сценарии.
- Нагрузочные тесты — измеряют пропускную способность, p95/p99 latency, ошибки и точку насыщения на реалистичном профиле трафика.
- В ответе об опыте — привести конкретный тест, найденный им дефект и место теста в CI.

</details>

### 17. Насколько тесно ты работал с Kubernetes и процессами деплоя?

<details>
<summary>Краткий ответ</summary>

- Уровень участия — честно разделить использование готовых манифестов и самостоятельную настройку Deployment, Service, Ingress, ConfigMap, Secret и ресурсов.
- Деплой — описать CI/CD: сборка образа, проверки, публикация, rollout и возможность rollback.
- Надёжность — упомянуть readiness, liveness, graceful shutdown, requests/limits и стратегию rolling update.
- Диагностика — привести пример работы с логами, событиями, состоянием pod, метриками и причиной неуспешного rollout.
- Граница ответственности — отдельно сказать, какие изменения выполнялись самостоятельно, а какие вместе с платформенной командой.

</details>

### 23. Есть медленный GET-эндпоинт. Как диагностировать причину задержки?

<details>
<summary>Краткий ответ</summary>

- Шаг 1 — подтвердить проблему метриками: p50/p95/p99, доля ошибок, конкретный маршрут, время и корреляция с нагрузкой.
- Шаг 2 — по trace разложить latency на обработку в приложении, запросы к БД, внешние вызовы, очередь и ожидание пула соединений.
- Шаг 3 — для БД проверить число запросов, `EXPLAIN (ANALYZE, BUFFERS)`, блокировки, статистику и индексы; для внешнего сервиса — таймауты, DNS, установку соединения и его собственную latency.
- Шаг 4 — если время уходит в приложение, снять CPU/heap/block/mutex profile и проверить GC, аллокации, блокировки и утечки горутин.
- Шаг 5 — исправить подтверждённое узкое место и повторить измерение на том же профиле нагрузки.

</details>

## Go — алгоритмы, слайсы и map

### 2. Что такое длина и ёмкость слайса? Зачем заранее указывать ёмкость?

<details>
<summary>Краткий ответ</summary>

- Длина `len` — число элементов, доступных по индексу.
- Ёмкость `cap` — сколько элементов помещается от начала слайса до конца его backing array без выделения нового массива.
- Предвыделение — `make([]T, 0, n)` уменьшает число аллокаций и копирований, если ожидаемый размер известен.
- Цена — слишком большая ёмкость заранее удерживает лишнюю память.
- Рост — когда места не хватает, `append` выделяет новый массив, копирует элементы и возвращает новый дескриптор; поэтому результат `append` нужно присваивать.

</details>

### 3. Что такое O-нотация? Как оценить сложность решения в лучшем и худшем случаях?

<details>
<summary>Краткий ответ</summary>

- Big O описывает верхнюю границу роста времени или памяти при увеличении размера входа `n`, игнорируя константы и младшие члены.
- Оценка — выбрать базовую операцию, посчитать число её выполнений и упростить выражение: `3n² + 2n + 5` превращается в `O(n²)`.
- Лучший случай — минимальная работа на допустимом входе; худший — максимальная; средний требует модели распределения входных данных.
- Циклы — последовательные проходы складываются, вложенные обычно перемножаются, деление пространства пополам даёт логарифм.
- На собеседовании отдельно называют временную и дополнительную пространственную сложность.

</details>

### 4. Какая алгоритмическая сложность у операций с `map`? Как устроена `map` в Go?

<details>
<summary>Краткий ответ</summary>

- Сложность — чтение, вставка и удаление имеют `O(1)` в среднем и амортизированно; теоретический худший случай — `O(n)`.
- Хеширование — runtime вычисляет хеш ключа, выбирает таблицу и проверяет небольшую последовательность групп кандидатов.
- Текущая реализация — начиная с Go 1.24 используется Swiss Table: группы по восемь слотов, управляющие байты и открытая адресация; большие map состоят из нескольких таблиц, выбранных через директорию.
- Почему `O(n)` редко — качественный хеш с индивидуальным seed распределяет ключи, а таблица растёт раньше чрезмерного заполнения.
- Оговорка — хеширование строки само занимает `O(len(key))`, а устройство таблицы является деталью runtime, не контрактом языка.

</details>

### 5. Можно ли безопасно использовать `map` конкурентно? Что происходит со старой памятью после роста?

<details>
<summary>Краткий ответ</summary>

- Без синхронизации безопасны только одновременные чтения, если никто не изменяет map.
- Конкурентная запись с чтением или другой записью является data race и может завершиться runtime-паникой; map защищают `Mutex`/`RWMutex`, владением одной горутины или подходящей структурой вроде `sync.Map`.
- В современной Swiss Table при росте отдельная таблица пересобирается или делится, а старая становится недоступной из директории.
- Освобождение выполняет GC, когда на старую таблицу больше нет ссылок; активный итератор может удерживать её дольше.
- В реализации Go до 1.24 старые buckets хранились отдельно и эвакуировались постепенно во время следующих операций записи.

</details>

### 18. Как работают встроенные функции `append` и `copy`?

<details>
<summary>Краткий ответ</summary>

- `append` добавляет элементы к слайсу. Пока хватает `cap`, он использует прежний массив; иначе выделяет новый, копирует данные и возвращает новый дескриптор.
- Результат `append` всегда присваивают: `s = append(s, v)`.
- `copy(dst, src)` копирует `min(len(dst), len(src))` элементов и возвращает их количество.
- Перекрытие — `copy` корректно работает, если исходный и целевой диапазоны относятся к одному массиву и перекрываются.
- Обе операции копируют элементы по значению; для указателей, map и слайсов копируются их дескрипторы, а не глубоко все достижимые данные.

</details>

### 40. Когда и как растёт `map` в Go?

<details>
<summary>Краткий ответ</summary>

- Рост запускается, когда в выбранной таблице заканчивается допустимый запас свободных слотов с учётом tombstone после удалений.
- В Go 1.24+ небольшая таблица заменяется таблицей большей ёмкости, а таблица максимального размера делится на две по части хеша; директория обновляется.
- Перехешируется только одна таблица, а не обязательно вся map, что ограничивает стоимость отдельного роста большой map.
- Термин «эвакуация buckets» относится к реализации до Go 1.24: там перенос был инкрементальным и продолжался на последующих записях.
- Public contract не обещает конкретный коэффициент роста или layout, поэтому прикладной код не должен на них опираться.

</details>

### 41. Когда возникает коллизия в хеш-таблице и как она обрабатывается?

<details>
<summary>Краткий ответ</summary>

- Коллизия возникает, когда разные ключи попадают в одну стартовую позицию или имеют совпадающий фрагмент хеша.
- Хеш не доказывает равенство: после отбора кандидата runtime сравнивает сами ключи.
- В Swiss Table кандидаты сначала фильтруются по управляющим байтам, затем при необходимости проверяются следующие группы по probe sequence.
- При росте заполненности число проб увеличивается, поэтому таблица заранее растёт или делится.

</details>

### 42. Можно ли использовать структуру как ключ `map`? Какие требования есть к ключу?

<details>
<summary>Краткий ответ</summary>

- Да, если структура сравнима оператором `==`.
- Все её поля тоже должны быть сравнимыми; slice, map и func делают структуру несравнимой.
- Массивы и другие сравнимые структуры допустимы, а interface допустим формально, но вызовет панику, если внутри окажется несравнимое динамическое значение.
- Значение ключа копируется в map, поэтому последующее изменение исходной переменной не меняет уже записанный ключ.
- Для составного ключа структура часто безопаснее склейки строк: типы и границы полей сохраняются.

</details>

## Базы данных и SQL

### 12. С какими СУБД, базами данных и индексами ты работал?

<details>
<summary>Краткий ответ</summary>

- Структура — для каждой СУБД назвать задачу, объём или нагрузку и собственную зону ответственности.
- PostgreSQL — привести примеры схемы, транзакций, миграций, индексов и диагностики запросов.
- Другие хранилища — объяснить access pattern: Redis для короткоживущего кэша, ClickHouse для аналитических агрегаций, Elasticsearch для полнотекстового поиска.
- Индексы — назвать не только тип, но и запрос, который он ускорил, цену записи и проверку через `EXPLAIN ANALYZE`.
- Граница опыта — отдельно сказать, что делалось самостоятельно, а что вместе с DBA или платформенной командой.

</details>

### 13. Что в основном делал с базами данных: писал запросы или занимался оптимизацией?

<details>
<summary>Краткий ответ</summary>

- Сначала назвать пропорцию работы: проектирование схемы, CRUD, миграции, сложные запросы, эксплуатация.
- Для оптимизации привести цепочку: медленный запрос → метрика или trace → план выполнения → причина → изменение → измерение после.
- Хороший пример содержит конкретику: объём таблицы, p95 до и после, выбранный индекс или переписанный запрос.
- Если DBA отвечал за эксплуатацию, важно честно обозначить границу и описать своё участие в совместной диагностике.

</details>

### 14. Чем отличаются PostgreSQL и ClickHouse? Каковы их плюсы и минусы?

<details>
<summary>Краткий ответ</summary>

| Критерий | PostgreSQL | ClickHouse |
| --- | --- | --- |
| Основная нагрузка | OLTP и смешанные запросы | OLAP, большие сканы и агрегации |
| Хранение | строковое, удобно читать и менять отдельные записи | колоночное, читает только нужные столбцы и хорошо сжимает |
| Изменения | транзакционные `INSERT`/`UPDATE`/`DELETE` | лучше append-heavy; мутации дороже и асинхронны по устройству |
| Согласованность | полноценные транзакции, ограничения и связи | приоритет аналитической пропускной способности |
| Сильная сторона | бизнес-состояние и точечные запросы | аналитика по миллиардам строк |

Выбор определяется access patterns: ClickHouse не является «более быстрой PostgreSQL», а PostgreSQL не заменяет аналитическое колоночное хранилище на больших сканах.

</details>

### 15. Что выбрать — PostgreSQL или ClickHouse?

<details>
<summary>Краткий ответ</summary>

- PostgreSQL — когда нужны транзакционные изменения отдельных записей, внешние ключи, уникальность и актуальное бизнес-состояние.
- ClickHouse — когда данные в основном добавляются, запросы сканируют большие интервалы и считают агрегации по небольшому числу колонок.
- Совместное использование — часто PostgreSQL остаётся source of truth, а события реплицируются в ClickHouse для аналитики.
- Перед выбором нужно уточнить объём, долю записи, свежесть данных, тип фильтров, требуемую согласованность и компетенции команды.

</details>

### 21. Как защитить SQL-запрос от SQL-инъекции?

<details>
<summary>Краткий ответ</summary>

- Значения передают параметрами драйвера: `WHERE id = $1`, а не собирают строку через `fmt.Sprintf`.
- Параметры не подходят для имён таблиц, колонок и направления сортировки; такие части выбирают только из жёсткого allowlist.
- ORM не является автоматической защитой, если в неё передают сырой SQL, собранный конкатенацией.
- Права пользователя БД ограничивают ущерб, но не заменяют параметризацию.
- Валидация полезна для бизнес-правил, однако экранирование вручную не должно быть основной защитой.

</details>

### 22. Как выбирать стратегию партиционирования и почему она ускоряет запросы?

<details>
<summary>Краткий ответ</summary>

- Ключ выбирают из реальных фильтров и жизненного цикла данных: время для retention и диапазонных запросов, tenant или hash для равномерного распределения.
- Ускорение даёт partition pruning: планировщик исключает разделы, которые не могут содержать нужные строки.
- Партиционирование помогает быстро удалять или архивировать диапазоны через detach/drop partition.
- Оно не ускоряет запрос, который не фильтрует по ключу, и может ухудшить планирование при тысячах мелких разделов.
- Нужно проверить перекос данных, размер раздела, локальные индексы и ограничения уникальности: в PostgreSQL уникальный ключ на partitioned table должен включать ключ партиционирования.

</details>

### 24. Что показывает `EXPLAIN ANALYZE`?

<details>
<summary>Краткий ответ</summary>

- `EXPLAIN` показывает выбранный план и оценки планировщика: узлы, стоимость, ожидаемые строки и ширину.
- `ANALYZE` действительно выполняет запрос и добавляет фактическое время, строки, число циклов и общее время.
- `BUFFERS` показывает попадания и чтения блоков, что помогает отделить CPU от I/O.
- Большое расхождение estimated rows и actual rows указывает на устаревшую статистику, корреляцию колонок или условие, которое планировщик оценил плохо.
- Смотрят не только на самый дорогой узел, но и на то, сколько раз он выполнился.

</details>

### 25. Любой ли запрос можно исследовать через `EXPLAIN ANALYZE`?

<details>
<summary>Краткий ответ</summary>

- Нет: `EXPLAIN` применим к планируемым SQL-операторам, а не к любой административной команде.
- `ANALYZE` реально выполняет оператор, поэтому `INSERT`, `UPDATE`, `DELETE` и вызовы функций могут изменить данные или вызвать внешний эффект.
- Изменяющий запрос часто проверяют внутри `BEGIN`/`ROLLBACK`, но rollback не отменяет все возможные эффекты, например изменение sequence или внешний вызов из функции.
- На production тяжёлый `EXPLAIN ANALYZE` сам создаёт нагрузку и блокировки; сначала безопаснее получить обычный `EXPLAIN` или воспроизвести запрос на копии.

</details>

### 26. Что делать после анализа плана выполнения запроса?

<details>
<summary>Краткий ответ</summary>

- Найти подтверждённое узкое место: неверная оценка строк, лишний большой scan, дорогая сортировка, многократно повторяемый nested loop, spill на диск или ожидание блокировки.
- Исправить причину: обновить статистику, переписать запрос, добавить подходящий индекс, уменьшить набор данных либо устранить N+1.
- Индекс добавляют с учётом цены: он занимает место и замедляет запись.
- Повторно измерить тот же запрос на репрезентативных данных и проверить, не ухудшились ли соседние запросы.
- Итог фиксируют числом latency, прочитанных блоков или нагрузки, а не утверждением «план стал красивее».

</details>

### 27. Как работают составные индексы?

<details>
<summary>Краткий ответ</summary>

- Индекс `(a, b, c)` упорядочен сначала по `a`, внутри одинакового `a` — по `b`, затем по `c`.
- Обычно наиболее полезны равенства по ведущим колонкам, после которых идёт диапазон; после первого широкого диапазона следующие поля хуже сужают скан.
- Текстовый порядок условий в `WHERE` роли не играет, важны операторы и порядок колонок в индексе.
- Запрос только по `b` иногда может использовать такой индекс, но часто сканирует намного больше данных; отдельный индекс выбирают по реальной селективности и плану.
- `INCLUDE` добавляет поля для покрытия запроса, не включая их в ключ сортировки.

</details>

### 28. Когда выбирать B-tree, а когда hash-индекс?

<details>
<summary>Краткий ответ</summary>

- B-tree — индекс PostgreSQL по умолчанию; поддерживает равенство, диапазоны, сортировку, `MIN`/`MAX` и префиксные условия.
- Hash — поддерживает только сравнение на равенство и не помогает с диапазоном или `ORDER BY`.
- Поэтому hash нельзя бездумно поставить вместо B-tree: он обслуживает меньше классов запросов, а выигрыш на равенстве нужно подтвердить измерением.
- Для JSON, массивов, полнотекстового поиска, геометрии и монотонных данных могут быть уместнее GIN, GiST, SP-GiST или BRIN.

</details>

### 29. Чем партиционирование отличается от шардирования?

<details>
<summary>Краткий ответ</summary>

- Партиционирование делит логическую таблицу на части внутри одной системы управления БД; запрос и транзакция остаются в одном кластере.
- Шардирование размещает части данных на независимых узлах или кластерах и распределяет запросы по ключу маршрутизации.
- Партиционирование упрощает pruning и retention, но само по себе не добавляет CPU, RAM и диски разных серверов.
- Шардирование даёт горизонтальную ёмкость, но усложняет межшардовые JOIN, транзакции, ребалансировку, уникальность и эксплуатацию.

</details>

### 30. Что такое транзакция и как она работает?

<details>
<summary>Краткий ответ</summary>

- Транзакция объединяет несколько операций в одну логическую единицу: либо фиксируются все, либо ни одна.
- `BEGIN` открывает транзакцию, `COMMIT` делает изменения подтверждёнными, `ROLLBACK` отменяет её изменения.
- Изоляцию PostgreSQL строит через MVCC-снимки и блокировки, а долговечность — через WAL и подтверждение записи журнала.
- Транзакция должна быть короткой: долгий пользовательский или сетевой вызов внутри удерживает версии строк, блокировки и соединение.
- Внешний HTTP-вызов не становится частью транзакции БД; для dual-write нужны outbox, идемпотентность или saga.

</details>

### 31. Какие уровни изоляции транзакций существуют?

<details>
<summary>Краткий ответ</summary>

- Read Uncommitted — стандарт допускает dirty read, но в PostgreSQL он работает как Read Committed.
- Read Committed — каждый оператор видит снимок на начало этого оператора; повторный запрос в той же транзакции может увидеть новые подтверждённые данные.
- Repeatable Read — транзакция использует стабильный снимок; PostgreSQL также предотвращает phantom read, но возможна write skew.
- Serializable — результат эквивалентен некоторому последовательному выполнению; PostgreSQL может отменить одну транзакцию с serialization failure, поэтому нужен retry всей транзакции.
- Уровень повышают только под конкретный инвариант: более сильная изоляция увеличивает конфликты и повторы.

</details>

### 32. Какие виды блокировок есть в PostgreSQL?

<details>
<summary>Краткий ответ</summary>

- Table-level locks — режимы от `ACCESS SHARE` до `ACCESS EXCLUSIVE`; обычные команды берут их автоматически.
- Row-level locks — `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE` и `FOR KEY SHARE` управляют конфликтами вокруг строк.
- MVCC — обычный `SELECT` обычно не блокирует `UPDATE` и видит подходящую версию строки.
- Advisory locks — прикладные блокировки по числовому ключу; корректность полностью зависит от соглашения приложения.
- Predicate locks в Serializable отслеживают зависимости чтения и могут привести к serialization failure, а не обязательно к обычному ожиданию.
- При диагностике проверяют ожидающий и блокирующий backend, тип lock и длительность транзакции.

</details>

### 33. Что такое `JOIN` и какие виды соединений существуют?

<details>
<summary>Краткий ответ</summary>

- `JOIN` объединяет строки двух источников по условию; источником может быть таблица, представление, подзапрос, CTE или табличная функция.
- `INNER JOIN` возвращает только совпавшие строки.
- `LEFT`/`RIGHT JOIN` сохраняет строки одной стороны без пары, подставляя `NULL` для другой.
- `FULL JOIN` сохраняет несовпавшие строки обеих сторон, `CROSS JOIN` строит декартово произведение.
- Self-join — та же таблица подключается под разными alias, например сотрудник и его руководитель.
- Важно учитывать кардинальность: связь one-to-many размножает строки левой стороны.

</details>

## Kafka и надёжная доставка

### 34. Чем Kafka отличается от RabbitMQ?

<details>
<summary>Краткий ответ</summary>

| Критерий | Kafka | RabbitMQ |
| --- | --- | --- |
| Модель | распределённый append-only log | брокер очередей и маршрутизации |
| Хранение | сообщения живут по retention независимо от чтения | сообщение обычно удаляется после подтверждения |
| Повторное чтение | естественно через смену offset | требует повторной публикации или отдельной очереди |
| Порядок | внутри partition | внутри очереди с оговорками при нескольких consumer |
| Сильная сторона | поток событий, replay, высокая пропускная способность | гибкий routing, команды и очереди работ |

Выбор зависит не от абстрактной скорости: Kafka удобна как журнал событий и для многих независимых consumer group, RabbitMQ — для доставки задач с гибкой маршрутизацией и per-message поведением.

</details>

### 35. Что такое consumer group в Kafka?

<details>
<summary>Краткий ответ</summary>

- Consumer group — несколько consumer, которые совместно читают один topic как один логический подписчик.
- Одна partition в каждый момент назначается максимум одному consumer внутри группы, поэтому порядок partition не нарушается.
- Разные группы получают одни и те же события независимо и хранят собственные offsets.
- Если consumer больше, чем partitions, лишние участники простаивают; параллелизм группы ограничен числом partitions.

</details>

### 36. Как partitions распределяются между участниками consumer group?

<details>
<summary>Краткий ответ</summary>

- Group coordinator отслеживает участников, а assignor формирует назначение partitions.
- Стратегия может стремиться к последовательным диапазонам, равномерному распределению или минимальному перемещению через cooperative sticky assignment.
- Вход или выход участника, изменение подписки или числа partitions запускает rebalance.
- Во время eager rebalance обработка останавливается у всей группы; cooperative rebalance передаёт partitions поэтапно и уменьшает паузу.
- Consumer должен вовремя heartbeat и корректно завершать обработку отозванных partitions.

</details>

### 37. Как гарантированно отправить данные в другой сервис через Kafka?

<details>
<summary>Краткий ответ</summary>

- Абсолютной end-to-end гарантии «ровно один раз» между БД двух сервисов нет без дополнительных протоколов.
- На стороне источника бизнес-изменение и событие записывают в одной транзакции через Transactional Outbox.
- Publisher отправляет с надёжными acknowledgements, идемпотентным producer и retry, но готов к неопределённому результату при сетевом сбое.
- Consumer сначала выполняет идемпотентный эффект или атомарно сохраняет его с inbox-записью, затем подтверждает offset.
- Нужны DLQ или отдельный поток ошибок, метрики lag и outbox age, алерты и процедура повторной обработки.

</details>

### 38. Из-за чего в Kafka возникают дубли?

<details>
<summary>Краткий ответ</summary>

- Producer отправил запись, но не получил acknowledgement и повторил запрос без эффективной идемпотентности.
- Consumer выполнил эффект, но упал до commit offset; после перезапуска запись придёт снова.
- Rebalance отозвал partition во время обработки, а новый consumer начал с последнего подтверждённого offset.
- Оператор вручную сдвинул offset или запустил replay.
- Поэтому at-least-once consumer обязан быть идемпотентным: использовать ключ операции, уникальное ограничение, inbox или условное обновление состояния.

</details>

### 39. Как работает Transactional Outbox?

<details>
<summary>Краткий ответ</summary>

- Сервис в одной локальной транзакции записывает бизнес-изменение и событие в таблицу outbox.
- Отдельный publisher читает неподтверждённые строки, публикует их в Kafka и отмечает отправленными.
- Если publisher падает между publish и отметкой, событие будет отправлено повторно, поэтому доставка остаётся at-least-once.
- Consumer обрабатывает событие идемпотентно; входная дедупликация HTTP-запроса не заменяет дедупликацию доставки.
- Outbox устраняет потерю между commit БД и publish, но добавляет eventual consistency, очистку таблицы, мониторинг задержки и повторов.

</details>

## Практические задачи

Задачи без исходного листинга или SQL-запроса пропущены: по ним нельзя получить однозначное решение и проверить результат.

### 1. Найти повторяющиеся числа

Дан массив целых чисел `nums` длины `n`. Каждый элемент находится в диапазоне `[1, n]` и встречается один или два раза. Нужно вернуть числа, которые встречаются дважды.

```text
Input:  nums = [4, 3, 2, 7, 8, 2, 3, 1]
Output: [2, 3]
```

<details>
<summary>Решение</summary>

Диапазон значений позволяет использовать сам массив как набор отметок. Для числа `v` проверяется элемент с индексом `abs(v) - 1`: положительный означает первое появление, отрицательный — повтор.

```go
func findDuplicates(nums []int) []int {
    duplicates := make([]int, 0)

    for _, raw := range nums {
        value := raw
        if value < 0 {
            value = -value
        }

        index := value - 1
        if nums[index] < 0 {
            duplicates = append(duplicates, value)
            continue
        }

        nums[index] = -nums[index]
    }

    return duplicates
}
```

- Время — `O(n)` и в лучшем, и в худшем случае: нужно просмотреть весь массив.
- Дополнительная память — `O(1)` без учёта результата.
- Цена — функция изменяет входной массив. Если это запрещено, используют `map[int]struct{}` с `O(n)` дополнительной памяти или сначала копируют вход.

</details>

### 3. Провести code review слоя истории статусов заказа

Нужно сохранить историю статусов заказа в PostgreSQL, встроить код в сервис и учесть отмену долгого запроса и партиционирование.

```go
type OrderStatusHistoryStore struct{}

func (s OrderStatusHistoryStore) saveOrderStatusHistory(
    orderId, status, partition string,
) {
    db, err := sql.Open(
        "postgres",
        "user=foo dbname=bar sslmode=disable",
    )
    if err != nil {
        fmt.Errorf("%v", err)
    }

    query := fmt.Sprintf(
        "insert into orderstatushistory "+
            "(order_id, status, partition, inserted_at) "+
            "values (%v, %v, %v, %v)",
        orderId,
        partition,
        status,
        time.Now(),
    )
    go db.Exec(query)
}
```

<details>
<summary>Решение</summary>

Проблемы исходного кода:

- `sql.Open` вызывается на каждую запись, хотя `sql.DB` — долгоживущий пул соединений;
- ошибка открытия игнорируется: `fmt.Errorf` создаёт значение, но оно никуда не возвращается;
- запрос собирается строкой, уязвим для SQL-инъекции и содержит перепутанные `status` и `partition`;
- произвольная горутина скрывает ошибку, не имеет cancellation и создаёт неограниченную конкурентность;
- `context.Context` отсутствует, результат `Exec` игнорируется;
- имя таблицы и полей не соответствует обычному snake_case, а время берётся внутри репозитория и хуже тестируется;
- партиционирование нельзя выбирать строкой «на глаз»: ключ и размер разделов следуют из запросов и retention.

Минимальная граница репозитория:

```go
type OrderStatusHistory struct {
    OrderID   string
    Status    string
    CreatedAt time.Time
}

type OrderStatusHistoryRepository interface {
    Save(
        ctx context.Context,
        history OrderStatusHistory,
    ) error
}

type PostgresOrderStatusHistoryRepository struct {
    db *sql.DB
}

func NewPostgresOrderStatusHistoryRepository(
    db *sql.DB,
) *PostgresOrderStatusHistoryRepository {
    return &PostgresOrderStatusHistoryRepository{db: db}
}

func (r *PostgresOrderStatusHistoryRepository) Save(
    ctx context.Context,
    history OrderStatusHistory,
) error {
    const query = `
        INSERT INTO order_status_history (
            order_id,
            status,
            inserted_at
        )
        VALUES ($1, $2, $3)
    `

    _, err := r.db.ExecContext(
        ctx,
        query,
        history.OrderID,
        history.Status,
        history.CreatedAt,
    )
    if err != nil {
        return fmt.Errorf("save order status history: %w", err)
    }

    return nil
}
```

- Сервис — проверяет переход статуса, создаёт доменную запись и вызывает интерфейс репозитория.
- Интерфейс — располагается на стороне сервиса-потребителя и позволяет заменить PostgreSQL в unit-тесте; если подмены и второй реализации нет, интерфейс можно добавить позже.
- Транзакция — изменение текущего статуса и запись истории должны фиксироваться атомарно в одной транзакции.
- Контекст — приходит от HTTP/gRPC-обработчика; `ExecContext` прекращает ожидание при отмене, если драйвер поддерживает cancellation.
- Партиционирование — PostgreSQL сам маршрутизирует строку по `inserted_at` или другому ключу; отдельную колонку `partition` обычно передавать не нужно.

</details>

### 5. Вернуть отсортированные квадраты отсортированного массива

Дан массив целых чисел, отсортированный по неубыванию. Нужно вернуть квадраты его элементов в том же порядке сортировки.

```text
Input:  [-7, -3, 2, 3, 11]
Output: [4, 9, 9, 49, 121]
```

<details>
<summary>Решение</summary>

Самый большой квадрат находится на одном из краёв: там лежит число с наибольшим модулем. Два указателя заполняют результат справа налево.

```go
func sortedSquares(nums []int) []int {
    result := make([]int, len(nums))
    left, right := 0, len(nums)-1

    for dst := len(nums) - 1; dst >= 0; dst-- {
        leftSquare := nums[left] * nums[left]
        rightSquare := nums[right] * nums[right]

        if leftSquare > rightSquare {
            result[dst] = leftSquare
            left++
        } else {
            result[dst] = rightSquare
            right--
        }
    }

    return result
}
```

- Время — `O(n)`.
- Дополнительная память — `O(n)` под результат.
- Ограничение — нужно уточнить диапазон входа: умножение может переполнить `int`; при больших значениях выбирают `int64` и проверку границ.

</details>

### 6. Объединить несколько каналов

Нужно определить проблему в реализации fan-in, исправить её и добавить возможность завершить ожидание по отмене.

```go
func joinChannels(chs []<-chan int) <-chan int {
    mergedCh := make(chan int)
    for _, ch := range chs {
        go func() {
            for value := range ch {
                mergedCh <- value
            }
        }()
    }

    return mergedCh
}
```

<details>
<summary>Решение</summary>

- В исходном вызове `joinChannels(a, b, c)` сигнатура не совпадает с `joinChannels(chs []<-chan int)`, поэтому код не компилируется.
- После исправления вызова значения будут напечатаны в недетерминированном порядке, но порядок внутри каждого входного канала сохранится.
- Затем `range` зависнет: `mergedCh` никто не закрывает.
- В коде до семантики циклов Go 1.22 замыкание также могло захватить общую переменную `ch`; явная передача аргумента делает код безопасным для старых версий.

```go
func joinChannels(
    ctx context.Context,
    chs ...<-chan int,
) <-chan int {
    merged := make(chan int)
    var wg sync.WaitGroup
    wg.Add(len(chs))

    for _, input := range chs {
        go func(ch <-chan int) {
            defer wg.Done()

            for {
                select {
                case <-ctx.Done():
                    return
                case value, ok := <-ch:
                    if !ok {
                        return
                    }

                    select {
                    case merged <- value:
                    case <-ctx.Done():
                        return
                    }
                }
            }
        }(input)
    }

    go func() {
        wg.Wait()
        close(merged)
    }()

    return merged
}
```

Вызывающая сторона задаёт таймаут через `context.WithTimeout`. Проверка контекста и при чтении, и при отправке не оставляет worker заблокированным, если потребитель перестал читать.

</details>

### 7. Исключить один отсортированный массив из другого

Даны отсортированные по возрастанию `suspects` и `innocents`. Нужно удалить из `suspects` все значения, которые присутствуют в `innocents`.

```text
Input:  suspects = [1, 2, 3, 4, 5], innocents = [2, 4]
Output: [1, 3, 5]
```

<details>
<summary>Решение</summary>

Два указателя используют сортировку входов. Результат записывается в backing array первого слайса.

```go
func filter(suspects, innocents []int) []int {
    result := suspects[:0]
    innocentIndex := 0

    for _, suspect := range suspects {
        for innocentIndex < len(innocents) &&
            innocents[innocentIndex] < suspect {
            innocentIndex++
        }

        if innocentIndex == len(innocents) ||
            innocents[innocentIndex] != suspect {
            result = append(result, suspect)
        }
    }

    return result
}
```

- Время — `O(len(suspects) + len(innocents))`.
- Дополнительная память — `O(1)` без учёта заголовка результата.
- Цена — backing array `suspects` изменяется. Если исходный массив нужно сохранить, результат создают отдельно.
- Повторы — решение удаляет все копии значения, если это значение присутствует в `innocents`.

</details>

### 8. Исправить конкурентность и завершение программы

Сто горутин отправляют результаты в канал, а `main` суммирует их через `range`. Нужно исправить зависание и сделать объём работы ограниченным.

```go
func foo(c chan int) {
    r := rand.Int()
    for i := 0; i < r; i++ {
        c <- r
    }
}
```

<details>
<summary>Решение</summary>

- Главная ошибка — канал не закрывается, поэтому `for range` в `main` никогда не завершается.
- Канал нужно закрыть после завершения всех producer, а не из одного из них.
- `rand.Int()` может вернуть огромное число, поэтому одна горутина способна выполнять практически неограниченное число отправок; верхнюю границу нужно задать явно.
- Сумма может переполнить `int`, поэтому в примере используется `int64`.

```go
func main() {
    const (
        workers  = 100
        maxCount = 1_000
    )

    values := make(chan int, workers)
    var wg sync.WaitGroup
    wg.Add(workers)

    for i := 0; i < workers; i++ {
        go func() {
            defer wg.Done()
            produce(values, maxCount)
        }()
    }

    go func() {
        wg.Wait()
        close(values)
    }()

    var sum int64
    for value := range values {
        sum += int64(value)
    }

    fmt.Println(sum)
}

func produce(out chan<- int, maxCount int) {
    value := rand.Intn(maxCount)
    for i := 0; i < value; i++ {
        out <- value
    }
}
```

Для production-кода producer дополнительно принимает `context.Context` и выбирает между `out <- value` и `ctx.Done()`, чтобы завершиться при отмене потребителя.

</details>

### 9. Получить сотрудников и их руководителей через self-join

Таблица `staff` содержит `head_id`, который ссылается на руководителя в той же таблице. Нужно вернуть всех сотрудников, включая тех, у кого руководителя нет.

```sql
CREATE TABLE staff (
    id      TEXT,
    name    TEXT,
    head_id TEXT
);
```

<details>
<summary>Решение</summary>

```sql
SELECT
    employee.name AS employee_name,
    manager.name AS manager_name
FROM staff AS employee
LEFT JOIN staff AS manager
    ON manager.id = employee.head_id
ORDER BY employee.id;
```

- Self-join — одна таблица участвует в запросе дважды под разными alias.
- `LEFT JOIN` сохраняет Ivan и Bob, у которых `head_id IS NULL`; имя руководителя для них будет `NULL`.
- `INNER JOIN` исключил бы сотрудников без руководителя.
- Для целостности схемы стоит добавить `PRIMARY KEY (id)` и внешний ключ `FOREIGN KEY (head_id) REFERENCES staff(id)`.

</details>
