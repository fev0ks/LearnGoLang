## Go — типы, память и ООП

**Каким типам нужно выделять память? Какие есть способы выделения?**

- Суть вопроса — какие типы не готовы к работе в своём нулевом значении.
- Требуют `make` — map, channel и (в большинстве случаев) slice:
  - nil map читается нормально, отдавая нулевые значения, а на запись даёт панику `assignment to entry in nil map`;
  - nil channel вечно блокирует и отправку, и чтение, а `close(nil)` паникует;
  - nil slice — приятное исключение: `len`, `cap`, `range` и даже `append` на нём работают, потому что `append` сам аллоцирует массив. `make` нужен, когда важно предвыделить ёмкость.
- Не требует выделения — массив: `[N]T` это значение фиксированного размера, память под него отводится вместе с переменной, в стеке или прямо внутри структуры. Пункт исходного списка про массив здесь неверен.
- Структуры и примитивы тоже готовы сразу: `var t time.Time`, `var b bytes.Buffer`, `var mu sync.Mutex` полностью рабочие без инициализации.
- Способы выделения:

| Способ | Что возвращает | Для чего |
| --- | --- | --- |
| `var x T` | значение `T` | нулевое значение, память в стеке или в куче по решению компилятора |
| `new(T)` | `*T` | указатель на обнулённое значение |
| `make(T, len, cap)` | сам `T` | только slice, map, chan: инициализирует внутреннее устройство |
| `T{...}` и `&T{...}` | значение и указатель | составной литерал с заданными полями |

- Уточнение к формулировке «`make` создаёт объект со значениями по умолчанию» — `make` строит внутреннюю структуру рантайма (`hmap`, `hchan`, backing-массив). Элементы слайса при этом действительно нулевые, а map создаётся пустой, без каких-либо ключей.
- Чем `new` отличается от `make` — `new(map[string]int)` вернёт указатель на nil-map, то есть неработающий на запись объект. `new` полезен для указателя на примитив (`new(int)`), но для структур обычно пишут `&T{}`.
- Где окажется память — решает не программист, а escape analysis компилятора; `new` не означает «куча».
- См. [01-primitive-types-and-zero-values.md](../01-go-core/01-primitive-types-and-zero-values.md).

**Стек и куча. Как компилятор решает, куда положить объект?**

- Стек — у каждой горутины свой, стартует с 2 КБ и растёт копированием: при нехватке рантайм выделяет вдвое больший сегмент и переносит содержимое, поправляя указатели.
- Почему стек дешёвый — выделение это сдвиг указателя, освобождение происходит при возврате из функции, GC на стек не тратится.
- Куча — общая, её убирает сборщик мусора, поэтому каждая аллокация в куче добавляет работы GC.
- Кто решает — escape analysis на этапе компиляции: если компилятор не может доказать, что объект не переживёт кадр функции, объект «убегает» в кучу.
- Что вызывает escape:
  - возврат указателя на локальную переменную;
  - помещение значения в интерфейс (`fmt.Println(x)` — классический источник);
  - захват переменной замыканием, которое уходит в горутину;
  - отправка указателя в канал или сохранение в глобальной структуре;
  - слишком крупный объект или размер, неизвестный на этапе компиляции (`make([]byte, n)` с переменной `n`).
- Уточнение к формулировке «указатели и структуры под ними уходят в кучу» — само по себе взятие адреса escape не вызывает: `p := &local; *p = 5` спокойно остаётся в стеке, если `p` не покидает функцию.
- Как проверить — `go build -gcflags='-m -m' ./...` печатает решения анализатора, а `go test -bench . -benchmem` показывает число аллокаций на операцию.
- См. [memory-internals/01-stack-and-heap.md](../01-go-core/memory-internals/01-stack-and-heap.md) и [memory-internals/03-escape-analysis.md](../01-go-core/memory-internals/03-escape-analysis.md).

**Как реализовать ООП-подход в Go? Есть ли наследование?**

- Инкапсуляция — регистр первой буквы имени: `Name` экспортируется, `name` нет. Граница здесь пакет, а не тип: приватное поле видно всему пакету, включая соседние файлы и чужие типы.
- Полиморфизм — интерфейсы с неявной реализацией: тип подходит под интерфейс, если у него есть нужные методы, объявлять это не требуется.
- Наследования нет. Есть встраивание (embedding), которое продвигает поля и методы внешнему типу, но это композиция, а не подтипизация.
- Ключевое отличие встраивания от наследования — нет позднего связывания: метод встроенного типа вызывает свои собственные методы, а не переопределённые снаружи.

```go
type Base struct{}

func (Base) Name() string  { return "base" }
func (b Base) Hello() string { return "hello, " + b.Name() }

type Child struct{ Base }

func (Child) Name() string { return "child" }

func main() {
    fmt.Println(Child{}.Hello()) // hello, base — не "hello, child"
}
```

- Почему так — `Child` не является подтипом `Base`, внутри `Hello` получатель имеет тип `Base` и о существовании `Child` не знает. В языке с наследованием тот же код напечатал бы `hello, child`.
- Как получить нужное поведение — вынести изменяемую часть в интерфейс и передать её явно, то есть заменить «является» на «умеет».
- Чего в языке нет вовсе — классов, конструкторов как языковой конструкции (их роль играют функции `NewX`), перегрузки методов, обобщённого `super`.
- Итоговая формулировка — Go объектно-ориентирован без иерархии типов: поведение собирается композицией, а абстракция описывается интерфейсом на стороне потребителя.
- См. [03-interfaces-method-sets-and-nil.md](../01-go-core/03-interfaces-method-sets-and-nil.md) и [go-code-patterns/01-dependencies-and-composition.md](../04-architecture-and-patterns/patterns/go-code-patterns/01-dependencies-and-composition.md).

## Go — интерфейсы, слайсы и строки

**Интерфейсы. Зачем нужны и как применяются?**

- Основное назначение — полиморфизм: код работает с поведением, не зная конкретного типа. Отсюда подмена реализации в тестах и развязка слоёв.
- Внутреннее устройство — два слова: у непустого интерфейса это `{tab *itab, data unsafe.Pointer}`, у пустого — `{_type, data}`. `itab` хранит таблицу методов для пары «интерфейс, конкретный тип».
- Отсюда главная ловушка — интерфейс равен nil, только когда оба слова пустые. Указатель nil, положенный в интерфейс, даёт ненулевой интерфейс:

```go
var p *MyError = nil
var err error = p
fmt.Println(err == nil) // false: тип есть, значение nil
```

- Определение типа — type assertion `v, ok := x.(*Foo)` и type switch, когда вариантов несколько. Форма с `ok` не паникует, форма без него — паникует.
- `reflect` — крайняя мера: динамическая работа с типами для сериализации, ORM и валидации. Цена — аллокации, потеря проверок компилятора и заметно более медленный код.
- Правило проектирования — интерфейс объявляется там, где используется, а не рядом с реализацией. Маленький интерфейс на один-два метода лучше, чем «интерфейс на весь сервис».
- Где интерфейс лишний — если реализация одна и подменять её не нужно, интерфейс добавляет только косвенность и аллокации при упаковке.
- См. [03-interfaces-method-sets-and-nil.md](../01-go-core/03-interfaces-method-sets-and-nil.md).

**Массивы, слайсы, строки. Внутреннее устройство. Как передаются?**

- Массив `[N]T` — значение, длина является частью типа (`[3]int` и `[4]int` — разные типы). Передаётся копированием целиком, поэтому массив на 1000 элементов в аргументе означает копию 1000 элементов.
- Уточнение к формулировке «массивы неизменяемы» — массив вполне изменяем, `a[0] = 1` работает. Особенность в другом: функция меняет свою копию, и вызывающая сторона изменений не увидит.
- Слайс — заголовок из трёх полей: указатель на backing-массив, длина, ёмкость. На 64-битной платформе это 24 байта.

```text
s := make([]int, 3, 5)

заголовок          backing-массив
{ptr, len=3, cap=5} -> [0][0][0][ ][ ]
                        ^len=3     ^cap=5
```

- Как передаётся слайс — тоже по значению: копируется заголовок. Но указатель в копии тот же, поэтому запись `s[0] = 1` внутри функции видна снаружи, а `append` — уже как повезёт.
- Механика `append`:
  - если `len < cap`, элемент пишется в существующий массив, и изменение видят все слайсы поверх него;
  - если места нет, выделяется новый массив, данные копируются, возвращается новый заголовок — связь с оригиналом рвётся.
- Отсюда правило `s = append(s, x)`: результат обязательно присваивают обратно, иначе новый заголовок потеряется.
- Строка — заголовок `{ptr, len}` (16 байт), содержимое неизменяемо. `len(s)` возвращает байты, а не символы; `range` по строке идёт по рунам UTF-8.
- Конвертации — `[]byte(s)` и `string(b)` копируют данные, потому что иначе неизменяемость строки нарушилась бы. Компилятор оптимизирует лишь узкие случаи: сравнение, `range`, поиск ключа в map.
- Как строить строку без лишних копий — `strings.Builder` вместо конкатенации в цикле: конкатенация каждый раз создаёт новую строку и даёт квадратичную работу.
- См. [04-slices.md](../01-go-core/04-slices.md) и [07-strings.md](../01-go-core/07-strings.md).

## Go — каналы и дженерики

**Каналы. Что это под капотом и какие бывают?**

- Канал — типизированная очередь с встроенной синхронизацией. Под капотом структура `hchan`: кольцевой буфер, счётчики, мьютекс, очереди ожидающих отправителей `sendq` и получателей `recvq`, флаг закрытия.

```text
hchan
├── buf      кольцевой буфер (только у буферизованного)
├── sendx    индекс записи
├── recvx    индекс чтения
├── sendq    горутины, ждущие возможности отправить
├── recvq    горутины, ждущие данных
├── lock     мьютекс на всю структуру
└── closed   флаг закрытия
```

- Небуферизованный канал — рандеву: отправитель блокируется до появления получателя, обмен происходит в момент встречи. Это не «медленнее», а другой контракт: факт передачи означает, что вторая сторона уже здесь.
- Буферизованный — асинхронный, пока в буфере есть место. Отправитель блокируется только на полном буфере, получатель — только на пустом.
- Оптимизация прямой передачи — если в `recvq` уже кто-то ждёт, значение копируется прямо в стек получателя, минуя буфер.
- Поведение по состояниям:

| Операция | nil-канал | открыт, есть данные | открыт, пуст | закрыт |
| --- | --- | --- | --- | --- |
| Чтение | блокировка навсегда | значение | блокировка | остаток буфера, затем нулевое значение и `ok == false` |
| Запись | блокировка навсегда | пишет или ждёт места | пишет | паника `send on closed channel` |
| `close` | паника | закрывает | закрывает | паника `close of closed channel` |

- Что будет при записи в закрытый канал — паника. Именно поэтому закрывать канал должен отправитель: получатель не может знать, пишет ли кто-то ещё.
- Что будет при чтении из закрытого — сначала вычитывается всё, что осталось в буфере, дальше немедленно возвращается нулевое значение типа. Отсюда закрытие используют как широковещательный сигнал: `close(done)` разбудит всех читателей сразу.
- Неблокирующая работа — `select` с веткой `default`:

```go
select {
case v := <-ch:
    handle(v)
default:
    // читать нечего, продолжаем без ожидания
}
```

- Как проверить, что канал закрыт — `v, ok := <-ch`: `ok == false` означает «канал закрыт и пуст». Отдельного способа спросить «закрыт ли канал» без чтения нет, и это осознанное решение: ответ устарел бы сразу после получения.
- Что вернёт `len` направленного канала (`chan<- T`, `<-chan T`) — то же, что и у обычного: число элементов, лежащих в буфере прямо сейчас; `cap` — размер буфера. У небуферизованного канала оба значения всегда 0.
- Почему на `len(ch)` нельзя строить логику — значение неактуально уже в следующей строке. Для метрик и логов годится, для принятия решений — нет.
- См. [concurrency-and-performance/02-goroutines-and-channels.md](../01-go-core/concurrency-and-performance/02-goroutines-and-channels.md).

**Дженерики. Что это и как устроены в Go?**

- Появились в Go 1.18: типовые параметры у функций и типов плюс ограничения (constraints) на них.

```go
func MapSlice[T, R any](in []T, f func(T) R) []R {
    out := make([]R, 0, len(in))
    for _, v := range in {
        out = append(out, f(v))
    }
    return out
}
```

- Ограничение — это интерфейс, описывающий множество типов, а не только методы: `any`, `comparable`, `constraints.Ordered`, объединения вида `int | float64`. Тильда `~int` означает «любой тип с базовым типом int».
- Как реализовано — GC shape stenciling: компилятор порождает не по копии на каждый тип, а по копии на «форму» (все указательные типы делят одну инстанциацию), и передаёт внутрь словарь с информацией о конкретном типе.
- Практическое следствие — дженерик-код не гарантированно быстрее интерфейсного: для указателей остаётся косвенность через словарь. Выигрыш заметен на значимых типах, где исчезает упаковка в интерфейс.
- Чего дженерики не умеют — методов с собственными типовыми параметрами, специализации тела под конкретный тип, любой формы ковариантности (`[]Dog` не подходит под `[]Animal`).
- Как жили раньше — `interface{}` с приведением типа в рантайме, кодогенерация через `go:generate`, и просто копирование функции под каждый тип.
- Когда применять — контейнеры и алгоритмы над данными (`slices`, `maps`, пулы, кэши). Когда не применять — для описания поведения: там по-прежнему уместнее интерфейс.
- См. [06-generics.md](../01-go-core/06-generics.md).

## Go — конкурентность и context

**Что такое горутина? Сколько их может быть? Как соотносится с числом процессоров?**

- Горутина — функция, исполняемая конкурентно с остальными; запускается через `go f()`. Это не поток ОС, а структура рантайма со своим стеком и состоянием.
- Стоимость — стартовый стек 2 КБ (у потока ОС обычно 1–8 МБ) и создание за сотни наносекунд без обращения к ядру.
- Модель — G-M-P: горутины (G) мультиплексируются рантаймом на потоки ОС (M) через логические процессоры (P). Число P задаёт `GOMAXPROCS`.
- Уточнение к формулировке «вытесняющая многозадачность» — планировщик Go кооперативный: горутина обычно уступает управление сама, в известных точках (вызов функции, операция с каналом, блокировка, системный вызов, аллокация). С Go 1.14 добавлена асинхронная преемпция по сигналу, выбивающая горутину примерно через 10 мс, если та крутит цикл без вызовов функций. Чистого вытеснения, как в ОС, здесь нет.
- Сколько горутин может быть — предел ставит память, а не рантайм: миллион горутин это минимум ~2 ГБ только под стеки. На практике сотни тысяч живут нормально, если каждая не держит буферы и соединения.
- Соотношение с числом процессоров — прямой связи нет. Параллельно исполняется не больше `GOMAXPROCS` горутин, остальные ждут в очередях:
  - для CPU-bound работы больше `GOMAXPROCS` воркеров смысла не имеет, лишние только добавляют переключений;
  - для I/O-bound тысячи горутин нормальны, потому что почти все они спят на сети и P не занимают.
- `GOMAXPROCS` по умолчанию — число доступных ядер; с Go 1.25 на Linux учитывается ещё и ограничение процессорного времени в cgroup, поэтому в контейнере значение больше не завышается.
- Почему число горутин всё равно ограничивают — не ради планировщика, а ради внешних ресурсов: соединений к БД, лимитов API, памяти под буферы. Отсюда worker pool и `errgroup.SetLimit`.
- См. [runtime-scheduler/01-scheduler-and-preemption.md](../01-go-core/runtime-scheduler/01-scheduler-and-preemption.md).

**Что даёт пакет `runtime`?**

- Наблюдение за рантаймом:
  - `runtime.NumGoroutine()` — текущее число горутин, самый дешёвый индикатор утечки;
  - `runtime.NumCPU()` — доступные ядра;
  - `runtime.GOMAXPROCS(n)` — чтение и установка числа P;
  - `runtime.ReadMemStats(&m)` — статистика кучи и GC, но со stop-the-world внутри, поэтому не в горячем пути.
- Влияние на выполнение — `runtime.GC()` (принудительная сборка, в проде почти всегда лишняя), `runtime.Gosched()` (уступить процессор), `runtime.SetFinalizer` (ненадёжный хук на сборку, для освобождения ресурсов не годится).
- Трассировка — брать не внутренние `runtime.StartTrace`/`StopTrace`, а публичный пакет `runtime/trace`: `trace.Start(w)` и `trace.Stop()`, либо `/debug/pprof/trace?seconds=5` у `net/http/pprof`. Разбор — `go tool trace`.
- Что видно в трассировке — работа планировщика, паузы GC, блокировки на синхронизации, задержки сети: то, чего не показывает CPU-профиль.
- Документация — [pkg.go.dev/runtime](https://pkg.go.dev/runtime).
- См. [profiling/05-execution-tracer.md](../01-go-core/profiling/05-execution-tracer.md).

**Как горутины общаются между собой?**

- Каналы — передача данных вместе с владением: отправитель после отправки к значению не обращается. Это основной способ, отсюда и формула «share memory by communicating».
- Общая память под защитой — `sync.Mutex`, `sync.RWMutex`, `sync/atomic`, `sync.Once`: дешевле каналов, когда речь про счётчик, флаг или кэш.
- Как выбирать — канал уместен для передачи потока данных и смены владельца, мьютекс — для защиты состояния, живущего на месте.
- `context.Context` — не канал общения, а канал управления: отмена, дедлайн и небольшие значения уровня запроса.
- Что не работает — просто написать в общую переменную без синхронизации: без happens-before другая горутина может вообще никогда не увидеть новое значение, и это не теория, а результат оптимизаций компилятора и кэшей процессора.
- См. [concurrency-and-performance/01-memory-model.md](../01-go-core/concurrency-and-performance/01-memory-model.md).

**Как контролировать выполнение горутин: WaitGroup и errgroup?**

- `sync.WaitGroup` — ожидание группы: `Add(n)` до запуска, `defer wg.Done()` внутри, `wg.Wait()` на вызывающей стороне.
- С Go 1.25 проще — `wg.Go(func(){ … })` сам делает `Add(1)` и `defer Done()`, поэтому классические ошибки исчезают.
- Типичные ошибки с WaitGroup:
  - `Add(1)` внутри запускаемой горутины — `Wait` может увидеть ноль и вернуться раньше времени;
  - копирование `WaitGroup` при передаче в функцию по значению — счётчик увеличивается у копии;
  - отсутствие `defer` перед `Done` — паника в середине работы навсегда подвешивает `Wait`.
- `errgroup.Group` — то же самое плюс ошибки: `g.Go(func() error)` и `g.Wait()`, возвращающий первую ненулевую ошибку.
- `errgroup.WithContext(ctx)` — при первой ошибке отменяет производный контекст, и остальные горутины сворачиваются сами, если этот контекст проверяют.
- `g.SetLimit(n)` — ограничение числа одновременно работающих горутин, готовый worker pool без ручного семафора.
- Что WaitGroup не делает — не отменяет работу. Ожидание и отмена это разные механизмы: `WaitGroup` ждёт, `context` останавливает.
- См. [concurrency-and-performance/03-sync-primitives.md](../01-go-core/concurrency-and-performance/03-sync-primitives.md).

**Context. Какие бывают и зачем нужны?**

- Задача — передать по цепочке вызовов сигнал отмены, дедлайн и небольшие значения уровня запроса.
- Корни дерева:
  - `context.Background()` — корневой контекст в `main`, тестах и при инициализации;
  - `context.TODO()` — заглушка на время, когда контекст ещё не протянут; отличается только смыслом для читателя.
- Производные контексты:
  - `WithCancel(parent)` — отмена по явному вызову `cancel()`;
  - `WithTimeout(parent, d)` — отмена через интервал;
  - `WithDeadline(parent, t)` — отмена в конкретный момент времени;
  - `WithValue(parent, k, v)` — значение по ключу;
  - `WithCancelCause` (Go 1.20) — отмена с причиной, доступной через `context.Cause(ctx)`;
  - `WithoutCancel` и `AfterFunc` (Go 1.21) — продолжить работу после отмены родителя и повесить обработчик на отмену.
- Как устроено дерево — отмена родителя отменяет всех потомков, обратное неверно. Дедлайн потомка не может быть позже родительского.
- Как читается отмена — `<-ctx.Done()` в `select`, причина — `ctx.Err()`: `context.Canceled` или `context.DeadlineExceeded`.
- Правила использования:
  - первый параметр функции с именем `ctx`, не поле структуры;
  - `defer cancel()` обязателен даже при таймауте, иначе таймер и запись в родителе живут до срабатывания;
  - в `WithValue` кладут только сквозные данные запроса — идентификатор трассировки, пользователя, локаль; передавать так бизнес-аргументы значит прятать зависимости от компилятора.
- Что context не делает — не убивает горутину. Отмена это лишь закрытый канал, и код обязан сам проверять `ctx.Done()` между шагами.
- См. [concurrency-and-performance/04-context-patterns.md](../01-go-core/concurrency-and-performance/04-context-patterns.md).

**Утечки горутин. Как их избежать?**

- Что такое утечка — горутина навсегда осталась заблокированной и не будет собрана: GC не трогает работающие горутины, поэтому вместе с ней удерживается весь её стек и захваченные объекты.
- Типовые причины:
  - отправка в канал, из которого больше никто не читает (получатель ушёл по таймауту);
  - чтение из канала, в который больше никто не пишет и который не закрывают;
  - `for range ch` по каналу без закрытия;
  - долгий вызов без учёта `ctx.Done()`;
  - забытый `time.Ticker` без `Stop()`.

```go
// Утечка: клиент ушёл по таймауту, отправка блокируется навсегда
func leak(ctx context.Context) <-chan int {
    ch := make(chan int) // небуферизованный
    go func() {
        ch <- expensive() // некому читать -> горутина зависла
    }()
    return ch
}

// Фикс: буфер на одно значение, отправка не блокирует
func fixed(ctx context.Context) <-chan int {
    ch := make(chan int, 1)
    go func() {
        ch <- expensive()
    }()
    return ch
}
```

- Правила, которые снимают большинство случаев:
  - у каждой горутины есть владелец и явное условие завершения;
  - в каждом ожидании стоит ветка `case <-ctx.Done()`;
  - канал закрывает отправитель, и ровно один;
  - для ответа «выстрелил и забыл» берут буфер на один элемент.
- Как обнаружить — рост `runtime.NumGoroutine()` на графике, профиль `/debug/pprof/goroutine?debug=2` со стеками всех горутин, `go.uber.org/goleak` в тестах.
- Почему это не мелочь — утечка проявляется не сразу, а как медленный рост памяти и деградация планировщика через часы работы.
- См. [concurrency-and-performance/02-goroutines-and-channels.md](../01-go-core/concurrency-and-performance/02-goroutines-and-channels.md).

## Go — GC, аллокации и гонки

**Как работает сборка мусора? Какой алгоритм?**

- Алгоритм — конкурентная трёхцветная пометка с последующей очисткой (concurrent tri-color mark & sweep). Сборщик не перемещает объекты и не делит их по поколениям.
- Цвета:
  - белый — объект ещё не посещён, кандидат в мусор;
  - серый — объект найден, но его ссылки ещё не просмотрены;
  - чёрный — объект и все его ссылки просмотрены.
- Ход пометки — корни (стеки горутин, глобальные переменные) красятся серым; сборщик берёт серый объект, красит его ссылки серым, а сам объект — чёрным. Когда серых не осталось, всё белое является мусором.
- Главный инвариант — чёрный объект не должен ссылаться на белый. Иначе живой объект, перевешенный приложением во время пометки, будет собран.
- Как инвариант удерживается — барьер записи (write barrier): пока идёт пометка, каждая запись указателя проходит через код рантайма, который подкрашивает участников. С Go 1.8 используется гибридный барьер, позволяющий не перепроверять стеки в конце.
- Фазы цикла:
  1. подготовка и включение барьера — короткая пауза stop-the-world;
  2. конкурентная пометка — работает параллельно с приложением, занимая около четверти процессорного времени;
  3. завершение пометки — вторая короткая пауза;
  4. очистка — освобождение белых объектов, тоже конкурентно, по мере аллокаций.
- Стоимость — две паузы обычно в пределах десятков-сотен микросекунд; основная цена не пауза, а отъедаемый на пометку процессор.
- Mark assist — горутина, аллоцирующая быстрее, чем сборщик метит, обязана сама помочь пометке. Отсюда всплески задержки именно у самого аллоцирующего кода.
- Настройки:
  - `GOGC` (по умолчанию 100) — новая сборка при удвоении живой кучи;
  - `GOMEMLIMIT` (Go 1.19) — мягкий предел всей памяти рантайма, в контейнере ставят около 90% лимита cgroup, чтобы сборщик успевал раньше OOM killer.
- Свежее состояние — Green Tea GC, экспериментальный в Go 1.25 и включённый по умолчанию в Go 1.26: пометка идёт крупными блоками памяти ради локальности обращений, что снижает накладные расходы на нагрузках с большой кучей.
- Как посмотреть своими глазами — `GODEBUG=gctrace=1` печатает по строке на цикл: доли процессора, размеры кучи и длительности пауз.
- См. [memory-internals/04-garbage-collector.md](../01-go-core/memory-internals/04-garbage-collector.md).

**Аллокации и sync.Pool. Что не освобождает память?**

- Что создаёт аллокации в куче — escape локальных объектов, рост слайса и map, конкатенация строк в цикле, конвертация `string` в `[]byte` и обратно, упаковка значения в интерфейс, замыкания, уходящие в горутины.
- Удаление из map не отдаёт память — `hmap` не сжимается: после `delete` слоты освобождаются под будущие вставки, но занятые страницы остаются за процессом. Если map разово раздулась, помогает только пересоздание.
- Урезание слайса не освобождает элементы — `s = s[:0]` и `s = s[:n]` сохраняют backing-массив, а ссылки в «отрезанном» хвосте продолжают удерживать объекты. Перед урезанием элементы обнуляют (`clear(s[n:])`).
- Ещё один удерживающий случай — подслайс большого буфера: `small := big[:10]` держит весь массив `big`. Спасает копия через `slices.Clone`.
- `sync.Pool` — кэш временных объектов, снимающий давление на GC:

```go
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func handle(w io.Writer, data []byte) {
    buf := bufPool.Get().(*bytes.Buffer)
    defer func() {
        buf.Reset()        // отдавать только очищенный объект
        bufPool.Put(buf)
    }()
    buf.Write(data)
    buf.WriteTo(w)
}
```

- Как устроен пул — хранилища привязаны к P, поэтому в обычном случае обходятся без блокировок. Содержимое очищается на каждом цикле GC; с Go 1.13 добавлен victim cache, из-за которого объект переживает один цикл, а не исчезает мгновенно.
- Правила работы с пулом:
  - класть объект только после сброса состояния, иначе чужие данные утекут в следующий запрос;
  - не хранить в пуле объекты с внешними ресурсами (соединения, файлы) — для них нужен полноценный пул с жизненным циклом;
  - обрезать переросшие буферы перед возвратом, иначе пул закрепит пиковый размер;
  - подтверждать выигрыш бенчмарком `-benchmem`: на дешёвых объектах пул часто медленнее прямой аллокации.
- Порядок оптимизации — сначала убрать лишнюю работу и предвыделить ёмкость (`make([]T, 0, n)`), и только потом браться за пул.
- См. [memory-internals/02-allocator.md](../01-go-core/memory-internals/02-allocator.md).

**Data race и race condition. Чем отличаются и как бороться?**

- Data race — формально определённая ситуация: два конкурентных обращения к одной ячейке памяти, хотя бы одно из них запись, и между ними нет отношения happens-before. Поведение программы при этом не определено вообще.
- Race condition — шире: результат зависит от порядка событий. Может существовать без единого data race — например, два процесса корректно берут мьютекс, но «проверил и записал» разнесены на две транзакции и между ними вклинивается третий.
- Практическое различие — data race ловится инструментом, race condition ловится только разбором логики.
- Как найти data race — детектор гонок: `go test -race ./...`, `go run -race`, отдельная сборка для стенда. Он не доказывает отсутствие гонок, а сообщает только о тех, что реально произошли на выполненных путях; замедление примерно в 5–10 раз по CPU и по памяти.
- Средства защиты:
  - `sync.Mutex` — взаимное исключение для группы связанных полей;
  - `sync.RWMutex` — разделение чтения (`RLock`) и записи (`Lock`);
  - `sync/atomic` и типы `atomic.Int64`, `atomic.Pointer[T]` — одна переменная, одна операция;
  - каналы — передача владения вместо разделения;
  - `sync.Once` — единичная инициализация.
- Что такое мьютекс в Go — не обёртка над мьютексом ОС: быстрый путь это атомарный CAS в пользовательском пространстве, при конкуренции горутина немного крутится и затем паркуется рантаймом. Есть режим голодания: если горутина ждёт больше 1 мс, мьютекс переходит в честную очередь, чтобы никто не ждал бесконечно.
- Мьютексы в ОС — тот же принцип, но с futex: без конкуренции всё решает атомарная операция в userspace, в ядро вызов уходит только когда действительно надо усыпить поток. Защищается при этом не «область памяти» аппаратно, а соблюдение протокола всеми участниками.
- Когда RWMutex не помогает — на коротких критических секциях и большом числе ядер `RLock` тоже пишет в общий счётчик, и обычный `Mutex` оказывается быстрее. Для действительно read-mostly данных лучше атомарная замена указателя на неизменяемую копию или `sync.Map`.
- См. [concurrency-and-performance/03-sync-primitives.md](../01-go-core/concurrency-and-performance/03-sync-primitives.md) и [11-race-fuzz-and-benchmarks.md](../09-testing-and-quality/11-race-fuzz-and-benchmarks.md).

## Go — профилирование

**Профилирование. Чем отличается профилирование на рабочей машине и на сервере?**

- Инструмент — `pprof`: сбор профиля рантаймом и разбор через `go tool pprof` с текстовым выводом, графом или flame graph.
- Виды профилей:

| Профиль | Что показывает | Когда брать |
| --- | --- | --- |
| `profile` | процессорное время по функциям (сэмплирование 100 Гц) | сервис упирается в CPU |
| `heap` | живые объекты и аллокации по местам создания | рост памяти, давление на GC |
| `allocs` | все аллокации за время работы | много мелкого мусора |
| `goroutine` | стеки всех горутин | утечки, зависания |
| `block` | ожидание на синхронизации и каналах | задержки без нагрузки на CPU |
| `mutex` | конкуренция за мьютексы | не растёт пропускная способность |

- Как включать — `net/http/pprof` поднимает обработчики на служебном порту; для CLI-программ подходит `runtime/pprof`, для микрооптимизаций — `go test -bench . -cpuprofile cpu.out`.
- Различия рабочей машины и сервера:
  - остановить и перезапустить процесс с профилировщиком на проде нельзя, поэтому профиль снимается с живого сервиса короткими окнами (обычно 30 секунд);
  - оверхед приходится учитывать: CPU-профиль стоит единицы процентов, а `block` и `mutex` при агрессивной частоте выборки — заметно дороже, их включают точечно;
  - профиль забирают по сети и разбирают локально: `go tool pprof http://host:6060/debug/pprof/profile?seconds=30`, и для расшифровки нужен тот же бинарник, что запущен на сервере;
  - результат шумный и невоспроизводимый: соседи по машине, лимиты cgroup, троттлинг процессора и неравномерный трафик. Выводы делают по нескольким снимкам и сравнению через `-diff_base`, а не по одному замеру;
  - профиль под нагрузкой показывает совсем другие горячие точки, чем синтетический тест на ноутбуке: на проде сверху появляются сеть, сериализация и ожидание базы;
  - вместо ручных снимков в проде удобнее непрерывное профилирование (Pyroscope, облачные профайлеры): оно даёт историю и позволяет сравнить «до релиза» и «после»;
  - `/debug/pprof` не должен смотреть в интернет: это и раскрытие внутренностей, и способ нагрузить сервис запросом длинного профиля.
- С чего начинать разбор — с метрик, а не с профиля: они показывают, во что упёрлись, а профиль отвечает, где именно.
- См. [profiling/01-pprof-tools-and-workflow.md](../01-go-core/profiling/01-pprof-tools-and-workflow.md).

## Паттерны разработки

**SOLID, KISS, DRY, YAGNI — что это и как выглядит в Go?**

- SRP, единственная ответственность — у модуля одна причина для изменения. В Go естественная единица не класс, а пакет: `storage`, `httpapi`, `billing`.
- OCP, открытость-закрытость — расширять поведение без правки существующего кода. Реализуется интерфейсом и обёрткой: логирование, метрики и повторы навешиваются декоратором вокруг реализации.
- LSP, подстановка Лисков — реализация не должна нарушать ожидания от интерфейса. В Go это в первую очередь контракт ошибок и поведения: подмена `io.Reader` не должна начинать паниковать вместо возврата `io.EOF`.
- ISP, разделение интерфейсов — маленькие интерфейсы вместо одного большого. Эталон — `io.Reader` и `io.Writer` на один метод.
- DIP, инверсия зависимостей — модули верхнего уровня зависят от абстракции, а не от конкретной реализации. В Go добавляется своё правило: интерфейс объявляет потребитель, а не пакет с реализацией. Тогда сервис не тянет за собой драйвер БД.
- KISS — простое решение предпочтительнее умного. Практический критерий: сколько времени займёт разбор этого кода у дежурного в три часа ночи.
- DRY — дублируется знание, а не текст. Две одинаковые строки в разных доменах это совпадение; объединение их в общую абстракцию создаёт связанность там, где её не было.
- YAGNI — не строить обобщение под гипотетическое будущее требование. Интерфейс с одной реализацией «на будущее» это чистая цена без выгоды.
- Как это звучит в ответе — принципы не самоцель: они описывают, где проходят границы модулей, чтобы изменение требования затрагивало один пакет, а не пять.
- См. [patterns/06-solid-in-go.md](../04-architecture-and-patterns/patterns/06-solid-in-go.md) и [patterns/10-dry-kiss-yagni.md](../04-architecture-and-patterns/patterns/10-dry-kiss-yagni.md).

**Инверсия зависимостей и Dependency Injection — в чём разница?**

- Инверсия зависимостей (DIP) — принцип проектирования: направление зависимости разворачивается, и обе стороны опираются на абстракцию, принадлежащую верхнему слою.
- Внедрение зависимостей (DI) — техника реализации: объект получает свои зависимости снаружи, а не создаёт их внутри себя.
- Почему их путают — DI это самый частый способ выполнить DIP, но не единственный, и сам по себе DI ещё не означает инверсии: можно внедрять конкретный тип и остаться связанным.
- Что даёт DI на практике — подмена реализации в тестах, единая точка сборки приложения, явный граф зависимостей вместо скрытых глобальных переменных.
- Как это делают в Go — руками в `main` или `cmd/app`: там создаются пул к базе, клиенты, репозитории, сервисы и передаются дальше конструкторами. Контейнеры (`wire` с кодогенерацией, `fx` и `dig` через reflect) нужны, когда граф действительно большой.
- См. [go-code-patterns/01-dependencies-and-composition.md](../04-architecture-and-patterns/patterns/go-code-patterns/01-dependencies-and-composition.md).

**Constructor Injection, Setter Injection, Interface Injection — плюсы и минусы?**

- Внедрение через конструктор — зависимости передаются в `NewService(...)`:

```go
type Service struct {
    repo   Repository
    logger *slog.Logger
}

func NewService(repo Repository, logger *slog.Logger) (*Service, error) {
    if repo == nil {
        return nil, errors.New("repo is required")
    }
    return &Service{repo: repo, logger: logger}, nil
}
```

  - Плюсы — объект всегда полностью инициализирован, обязательные зависимости видны в сигнатуре, поля можно держать неизменяемыми, ошибка сборки ловится на старте.
  - Минусы — длинный список параметров при большом числе зависимостей, необходимость менять все вызовы при добавлении новой.
- Внедрение через сеттер — `svc.SetCache(c)` после создания.
  - Плюсы — годится для необязательных зависимостей, позволяет заменить реализацию во время работы, разрывает циклические зависимости.
  - Минусы — существует окно, когда объект создан, но не готов; появляются проверки на nil, а замена во время работы требует синхронизации. В Go эту нишу почти полностью занял вариант с функциями-опциями `NewService(repo, WithCache(c), WithTimeout(d))`.
- Внедрение через интерфейс — компонент реализует интерфейс вида `SetRepository(Repository)`, и внедряющая сторона вызывает этот метод.
  - Плюсы — контракт внедрения описан явно и его можно требовать от группы типов; удобно каркасам и плагинным системам.
  - Минусы — самый многословный вариант, к недостаткам сеттера добавляется лишний интерфейс. В Go встречается редко.
- Что выбирать — конструктор по умолчанию, функции-опции для необязательного, сеттер только там, где зависимость действительно меняется по ходу жизни объекта.

| Способ | Гарантия готовности | Сложность | Где уместен |
| --- | --- | --- | --- |
| Конструктор | полная | низкая | обязательные зависимости, значение по умолчанию |
| Сеттер и опции | частичная | средняя | необязательные и заменяемые зависимости |
| Интерфейс | частичная | высокая | каркасы и плагины |

**TDD и DDD — что это и когда применяют?**

- TDD, разработка через тесты — цикл «красный, зелёный, рефакторинг»: сначала падающий тест на требование, затем минимальный код, затем чистка при зелёных тестах.
- Что реально даёт TDD — не покрытие само по себе, а давление на дизайн: код, который трудно вызвать из теста, обычно имеет плохие границы и лишние зависимости.
- Где TDD работает плохо — исследовательские задачи с неясным результатом, интеграции с внешними системами, UI-эксперименты. Там дешевле сначала прототип, тесты потом.
- DDD, предметно-ориентированное проектирование — моделирование кода по языку предметной области:
  - единый язык (ubiquitous language) — одинаковые термины в разговоре с бизнесом и в коде;
  - ограниченный контекст (bounded context) — граница, внутри которой термин имеет один смысл; «заказ» в доставке и в биллинге это разные модели;
  - сущность и объект-значение — различаются наличием идентичности;
  - агрегат — группа объектов с единой точкой входа и границей согласованности, обычно совпадающей с границей транзакции;
  - репозиторий — доступ к агрегатам без деталей хранилища.
- Что чаще всего спрашивают дальше — как граница агрегата связана с транзакцией: изменения внутри одного агрегата согласованы сразу, между агрегатами — через события и eventual consistency.
- Когда DDD не нужен — CRUD-сервис без нетривиальных правил: слои и мэпперы там дают цену без выигрыша.
- См. [patterns/05-ddd-in-go.md](../04-architecture-and-patterns/patterns/05-ddd-in-go.md) и [01-testing-strategy.md](../09-testing-and-quality/01-testing-strategy.md).

## Алгоритмы и задачи

**Какие есть алгоритмы сортировки? Что использует `sort` в Go? Как работает быстрая сортировка?**

| Алгоритм | Среднее | Худшее | Память | Стабильность |
| --- | --- | --- | --- | --- |
| Быстрая (quicksort) | O(n log n) | O(n²) | O(log n) на стек | нет |
| Слиянием (merge sort) | O(n log n) | O(n log n) | O(n) | да |
| Кучей (heap sort) | O(n log n) | O(n log n) | O(1) | нет |
| Вставками (insertion) | O(n²) | O(n²) | O(1) | да |
| Подсчётом (counting) | O(n + k) | O(n + k) | O(k) | да |

- Что использует стандартная библиотека — с Go 1.19 `sort.Slice`, `sort.Sort` и `slices.Sort` реализованы через pdqsort (pattern-defeating quicksort).
- Почему именно он — это быстрая сортировка с тремя защитами: распознавание уже упорядоченных и почти упорядоченных участков, переход на сортировку вставками на коротких отрезках, и переход на сортировку кучей после серии неудачных разбиений. Последнее убирает худший случай O(n²) и даёт гарантию O(n log n).
- Стабильность — `sort.Sort` и `slices.Sort` не стабильны. Стабильный вариант это `sort.Stable` и `slices.SortStableFunc`: там сортировка вставками по блокам плюс слияние на месте, за что платят множителем `log n`.
- Как работает быстрая сортировка:
  1. выбирается опорный элемент;
  2. массив переставляется так, что слева оказываются меньшие, справа большие — это разбиение за один проход, O(n);
  3. процедура рекурсивно применяется к обеим частям.
- Откуда берётся O(n log n) — при удачном опорном элементе глубина рекурсии log n, на каждом уровне выполняется O(n) работы разбиения.
- Откуда берётся O(n²) — если опорный элемент каждый раз оказывается минимумом или максимумом (например, на уже отсортированных данных при выборе первого элемента), одна часть пуста, и глубина становится n.
- Как с этим борются — медиана из трёх или из девяти, случайный выбор опорного, ограничение глубины с переходом на heap sort.
- Что ещё стоит упомянуть — на практике почти никогда не пишут свою сортировку, а важнее правильный компаратор: он обязан задавать строгий порядок, иначе результат непредсказуем.
- См. [06-sorting-and-heap.md](../16-algorithms-and-data-structures/06-sorting-and-heap.md).

**Задача: отсортировать строку по алфавиту, но у гласной заглавная буква больше, а у согласной — меньше**

- Первое, что стоит уточнить — что делать с не-буквами и с алфавитом: правило описано для латиницы, а строка может содержать цифры, пробелы и кириллицу.
- Разбор правила — основной порядок алфавитный и регистр не учитывает. Регистр решает только спор между одной и той же буквой: `a` и `A`, `b` и `B`.
  - гласная: заглавная больше, значит `a` идёт раньше `A`;
  - согласная: заглавная меньше, значит `B` идёт раньше `b`.
- Решение через компаратор:

```go
func isVowel(r rune) bool {
    return strings.ContainsRune("aeiou", r)
}

func compareRunes(a, b rune) int {
    la, lb := unicode.ToLower(a), unicode.ToLower(b)
    if la != lb {
        return int(la) - int(lb) // основной порядок: по букве без учёта регистра
    }
    if a == b {
        return 0
    }
    // одна и та же буква в разных регистрах
    upperFirst := !isVowel(la) // у согласной заглавная меньше, у гласной — больше
    if unicode.IsUpper(a) == upperFirst {
        return -1
    }
    return 1
}

func sortString(s string) string {
    rs := []rune(s)
    slices.SortFunc(rs, compareRunes)
    return string(rs)
}
```

- Проверка на примере `"bBaAcC"`:
  - `a` и `A` — гласная, заглавная больше, порядок `aA`;
  - `b` и `B` — согласная, заглавная меньше, порядок `Bb`;
  - `c` и `C` — согласная, порядок `Cc`;
  - алфавитный порядок собирает всё вместе: `aABbCc`.
- Почему `[]rune`, а не `[]byte` — байтовая сортировка разрежет многобайтовые символы UTF-8 и даст на выходе испорченную строку.
- Сложность — O(n log n) по времени и O(n) по памяти на срез рун.
- Альтернатива за O(n) — сортировка подсчётом: алфавит фиксирован (52 латинские буквы), достаточно посчитать вхождения и собрать результат в нужном порядке. Имеет смысл только на длинных строках с малым алфавитом.
- Что здесь проверяют — умение аккуратно выразить нестандартный порядок в компараторе и не забыть про руны.

**Задача: FizzBuzz от 1 до 100**

```go
func fizzBuzz() {
    for i := 1; i <= 100; i++ {
        switch {
        case i%15 == 0:
            fmt.Println("FizzBuzz")
        case i%3 == 0:
            fmt.Println("Fizz")
        case i%5 == 0:
            fmt.Println("Buzz")
        default:
            fmt.Println(i)
        }
    }
}
```

- Главная ловушка — порядок веток: если проверка на 3 стоит первой, случай 15 никогда не дойдёт до `FizzBuzz`. Условие `i%15 == 0` эквивалентно `i%3 == 0 && i%5 == 0`, потому что 3 и 5 взаимно просты.
- Вариант, который лучше расширяется на новые правила:

```go
for i := 1; i <= 100; i++ {
    s := ""
    if i%3 == 0 {
        s += "Fizz"
    }
    if i%5 == 0 {
        s += "Buzz"
    }
    if s == "" {
        s = strconv.Itoa(i)
    }
    fmt.Println(s)
}
```

- Чем этот вариант лучше — добавление правила «кратно 7 — Bazz» стоит трёх строк, а в варианте со `switch` потребует перебрать все сочетания.
- Что здесь проверяют — не знание задачи, а аккуратность: правильные границы (`1..100` включительно), отсутствие лишних веток и осмысленный выбор между «читаемо сейчас» и «расширяемо потом».
- Что упомянуть про вывод — в цикле на сто строк это неважно, но на больших объёмах `fmt.Println` на каждой итерации становится узким местом, и вывод буферизуют через `bufio.Writer`.

**Задача: F+1 = ?**

- Задача сформулирована неоднозначно намеренно: проверяется, задаст ли кандидат уточняющий вопрос вместо угадывания.
- Возможные прочтения:
  - шестнадцатеричное число: `F` это 15, значит `F + 1 = 0x10 = 16`;
  - буква латинского алфавита: следующая после `F` это `G`;
  - переменная в коде: результат зависит от типа `F`.
- Как это выглядит в Go — ответ определяется типом операнда:

```go
fmt.Println('F' + 1)         // 71: 'F' это нетипизированная константа-руна, 70 + 1
fmt.Println(string('F' + 1)) // "G": то же число, интерпретированное как символ
fmt.Println("F" + 1)         // ошибка компиляции: mismatched types untyped string and untyped int
```

- Почему `"F" + 1` не компилируется — в Go нет неявного приведения между строкой и числом; сложить их можно только явно, например `"F" + strconv.Itoa(1)`, что даст `"F1"`.
- Полезная деталь про `string(rune)` — конвертация числа в строку через `string(71)` даёт символ `G`, а не текст `"71"`. Код компилируется, но `go vet` сообщает: `conversion from untyped int to string yields a string of one rune, not a string of digits`. Для текстового представления числа берут `strconv.Itoa`.
- Как отвечать — назвать варианты и уточнить систему счисления или тип. Уверенный ответ одним числом без уточнения здесь как раз является ошибкой.

## Базы данных

**Какие типы баз данных знаешь?**

- Реляционные (PostgreSQL, MySQL) — строгая схема, связи, JOIN, транзакции с ACID. Выбор по умолчанию, пока нет причин выбрать другое.
- Ключ-значение (Redis, DynamoDB, etcd) — доступ по ключу за O(1), минимум возможностей запроса. Кэш, сессии, счётчики, блокировки.
- Документные (MongoDB, Couchbase) — JSON-подобные документы с гибкой схемой, запросы по вложенным полям.
- Колоночные (ClickHouse) и wide-column (Cassandra, HBase) — разные вещи, которые часто смешивают:
  - колоночные хранят таблицу по столбцам ради аналитических запросов, читающих несколько колонок из миллиардов строк;
  - wide-column это распределённая таблица с ключом секции и кластерным ключом, рассчитанная на большую запись и предсказуемое чтение по ключу.
- Поисковые (Elasticsearch, OpenSearch) — инвертированный индекс, полнотекстовый поиск и агрегации.
- Графовые (Neo4j) — узлы и рёбра, обход связей без каскада JOIN.
- Временных рядов (TimescaleDB, Prometheus, VictoriaMetrics) — метрики с оптимизированной записью и хранением по времени.
- В памяти (Memcached, Redis) — данные живут в RAM; Memcached предельно прост и не сохраняет состояние, Redis умеет сохранять на диск и предлагает структуры данных.
- Объектные (S3 и аналоги) — не база в привычном смысле, а хранилище блобов для файлов, бэкапов и медиа.
- Индексы — не тип базы, а механизм внутри неё: дополнительная структура, ускоряющая поиск ценой замедления записи и лишнего места.
- Как выбирать — по модели данных, шаблону доступа (чтение по ключу, диапазон, поиск, аналитика) и требованиям к согласованности, а не по популярности.
- См. [database-systems-catalog/01-comparison-table.md](../06-databases/database-systems-catalog/01-comparison-table.md).

**PostgreSQL. Какие бывают индексы? Какие есть уровни изоляции?**

- Типы индексов по структуре:

| Тип | Для чего | Типичный случай |
| --- | --- | --- |
| B-tree | равенство, диапазоны, сортировка, `LIKE 'abc%'` | значение по умолчанию, покрывает большинство запросов |
| Hash | только равенство | редко нужен, B-tree обычно не хуже |
| GIN | поиск внутри составных значений | `jsonb`, массивы, полнотекст |
| GiST | геометрия, диапазоны, поиск по близости | PostGIS, `tsrange` и пересечения |
| SP-GiST | несбалансированные структуры | префиксные деревья, IP-адреса |
| BRIN | огромные таблицы с естественным порядком | логи и события, отсортированные по времени |

- Разновидности по способу объявления — составной (важен порядок столбцов и правило левого префикса), уникальный, частичный (`WHERE deleted_at IS NULL`), по выражению (`lower(email)`), покрывающий (`INCLUDE`, позволяющий index-only scan).
- Цена индекса — каждый индекс замедляет `INSERT`, `UPDATE` и `DELETE`, занимает место и требует обслуживания. Неиспользуемые индексы находят через `pg_stat_user_indexes`.
- Уровни изоляции и допускаемые аномалии:

| Уровень | Грязное чтение | Неповторяемое чтение | Фантомы | Аномалии сериализации |
| --- | --- | --- | --- | --- |
| Read Uncommitted | нет (в PostgreSQL) | да | да | да |
| Read Committed | нет | да | да | да |
| Repeatable Read | нет | нет | нет (в PostgreSQL) | да, но транзакция откатывается |
| Serializable | нет | нет | нет | нет |

- Особенности PostgreSQL:
  - Read Uncommitted существует только в синтаксисе и работает как Read Committed: грязного чтения нет в принципе благодаря MVCC;
  - Read Committed — уровень по умолчанию: каждый оператор видит свой снимок, поэтому два `SELECT` в одной транзакции могут вернуть разное;
  - Repeatable Read реализован как снимок на всю транзакцию, поэтому фантомов тоже нет, в отличие от классического определения стандарта. Конфликтующая запись приводит к ошибке `could not serialize access`;
  - Serializable использует SSI — отслеживает опасные пересечения и откатывает одну из транзакций, а не сериализует их блокировками.
- Что из этого следует для кода — на уровнях выше Read Committed приложение обязано уметь повторять транзакцию после ошибки сериализации.
- См. [postgresql/02-indexes.md](../06-databases/database-systems-catalog/postgresql/02-indexes.md) и [postgresql/04-transactions-and-locking.md](../06-databases/database-systems-catalog/postgresql/04-transactions-and-locking.md).

**Способы масштабирования базы данных**

- Порядок действий — от дешёвого к дорогому, а не сразу к шардированию.
- Шаг 1, оптимизация — планы запросов, индексы, устранение N+1, пакетные операции. Часто снимает проблему целиком и не меняет архитектуру.
- Шаг 2, вертикально — больше CPU, RAM и быстрее диски. Простой и быстрый ход с очевидным потолком.
- Шаг 3, пул соединений — pgbouncer в режиме transaction: PostgreSQL выделяет процесс на соединение, и тысяча прямых соединений от сервисов убивает базу раньше, чем нагрузка.
- Шаг 4, реплики на чтение — асинхронная репликация снимает нагрузку чтения, но приносит лаг: после записи данные на реплике появляются не мгновенно, и критичные чтения приходится направлять в primary.
- Шаг 5, кэш — Redis перед базой для горячих ключей. Появляются вопросы инвалидации и согласованности.
- Шаг 6, партиционирование — одна база, одна логическая таблица, разрезанная по диапазону или списку. Ускоряет запросы за счёт отсечения секций и делает удаление старых данных операцией `DROP` вместо `DELETE`.
- Шаг 7, шардирование — разные части данных на разных серверах. Снимает потолок записи, но ломает JOIN и транзакции между шардами, требует ключа шардирования и плана ребалансировки.
- Шаг 8, разделение нагрузок — вынести аналитику в OLAP-хранилище (ClickHouse), а поиск в Elasticsearch, чтобы тяжёлые запросы не конкурировали с транзакционными.
- Что важно проговорить — вертикальное масштабирование и реплики оставляют одну точку записи, поэтому упор в запись лечится только партиционированием и шардированием.
- См. [postgresql/12-sharding.md](../06-databases/database-systems-catalog/postgresql/12-sharding.md) и [highload-design-patterns.md](../05-system-design/highload-design-patterns.md).

**Задача: маркетплейс. Найти продавца, у которого сумма покупок от вас на втором месте. Построить таблицу**

Схема — минимальный набор, достаточный для запроса:

```sql
CREATE TABLE orders (
    id          bigserial PRIMARY KEY,
    buyer_id    bigint      NOT NULL,
    seller_id   bigint      NOT NULL,
    amount      numeric(12,2) NOT NULL CHECK (amount >= 0),
    status      text        NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX orders_buyer_seller_idx
    ON orders (buyer_id, seller_id) INCLUDE (amount);
```

- Что стоит уточнить до запроса — учитывать ли отменённые и возвращённые заказы, считать ли по всей истории или за период, что делать при равных суммах, и есть ли отдельная таблица позиций заказа.
- Простой вариант — сгруппировать по продавцу и пропустить первую строку:

```sql
SELECT seller_id, SUM(amount) AS total
FROM orders
WHERE buyer_id = $1
  AND status = 'paid'
GROUP BY seller_id
ORDER BY total DESC
OFFSET 1
LIMIT 1;
```

- Как это читается — `WHERE` отбирает мои оплаченные заказы до группировки, `GROUP BY` сводит их по продавцам, `ORDER BY ... DESC` ставит наибольшую сумму первой, `OFFSET 1 LIMIT 1` берёт следующую за ней.
- Где ломается этот вариант — при равных суммах. Если два продавца набрали по 5000, `OFFSET 1` вернёт второго из них, а не продавца с третьим по величине результатом.
- Вариант, честно обрабатывающий равенство сумм:

```sql
SELECT seller_id, total
FROM (
    SELECT seller_id,
           SUM(amount) AS total,
           DENSE_RANK() OVER (ORDER BY SUM(amount) DESC) AS rnk
    FROM orders
    WHERE buyer_id = $1
      AND status = 'paid'
    GROUP BY seller_id
) ranked
WHERE rnk = 2;
```

- Почему `DENSE_RANK`, а не `RANK` — `DENSE_RANK` не пропускает номера: при двух продавцах на первом месте вторым уровнем станет следующая по величине сумма. `RANK` в той же ситуации выдаст 1, 1, 3, и строк с рангом 2 не окажется вовсе.
- Почему это оконная функция, а не подзапрос с `MAX` — ранг считается за один проход по уже сгруппированному результату, без повторного чтения таблицы.
- Граничные случаи — если продавец всего один, оба запроса корректно возвращают пустой результат; приложение должно быть к этому готово, а не ждать ровно одну строку.
- Почему индекс именно такой — условие идёт по `buyer_id`, группировка по `seller_id`, а `INCLUDE (amount)` позволяет посчитать сумму, не заглядывая в саму таблицу.
- См. [postgresql/00-sql-basics-and-syntax.md](../06-databases/database-systems-catalog/postgresql/00-sql-basics-and-syntax.md) и [sql-tasks](../06-databases/database-systems-catalog/postgresql/sql-tasks/README.md).

## Брокеры сообщений

**Какие брокеры существуют и для чего они нужны?**

- Зачем брокер вообще:
  - развязка — отправитель не знает получателей и не падает вместе с ними;
  - сглаживание пиков — очередь принимает всплеск, потребитель разбирает в своём темпе;
  - надёжность — сообщение переживает перезапуск получателя;
  - широковещание — одно событие получают несколько независимых подписчиков;
  - фоновая работа — тяжёлые задачи уходят из синхронного запроса пользователя.
- Kafka — распределённый лог: сообщения хранятся в партициях и не удаляются после чтения, позиция чтения принадлежит потребителю. Отсюда переигрывание истории, несколько независимых групп потребителей и пропускная способность в сотни тысяч сообщений в секунду. Порядок гарантирован в пределах партиции.
- RabbitMQ — классический брокер очередей с маршрутизацией через exchange: direct, topic, fanout, headers. Сообщение подтверждается и удаляется, есть приоритеты, TTL, отложенная доставка и dead letter queue. Сильная сторона — гибкая маршрутизация и работа с отдельными задачами.
- NATS и NATS JetStream — минимальная задержка и простая эксплуатация; базовый NATS доставляет без сохранения, JetStream добавляет хранение и подтверждения.
- Redis Streams — лог с группами потребителей внутри Redis: удобно, когда Redis уже есть и не нужен отдельный кластер брокера. Redis Pub/Sub же ничего не хранит и теряет сообщения при отсутствии подписчика.
- Облачные (SQS, Google Pub/Sub, Azure Service Bus) — без своей эксплуатации, оплата по использованию, но с ограничениями по задержке и порядку.
- Ключевое сравнение:

| Признак | Kafka | RabbitMQ |
| --- | --- | --- |
| Модель | лог с хранением и смещением | очередь с удалением после подтверждения |
| Кто помнит позицию | потребитель | брокер |
| Переигрывание истории | да | нет |
| Маршрутизация | по партициям и топикам | гибкая, через exchange |
| Сильная сторона | поток событий, аналитика, большой объём | задачи, сложная маршрутизация, приоритеты |

- Что действует для всех — доставка обычно at-least-once, значит дубли неизбежны и обработчик обязан быть идемпотентным. Exactly-once существует лишь в узких сценариях внутри одной системы.
- См. [00-comparison.md](../07-message-brokers-and-streaming/00-comparison.md) и [reliability-patterns/06-idempotency.md](../05-system-design/reliability-patterns/06-idempotency.md).

## Железо

**Чем серверный процессор отличается от настольного и от ноутбучного?**

- Ядра против частоты — серверный берёт числом ядер (32–128 и больше) при более низкой частоте, настольный наоборот: 8–24 ядра, но выше частота на ядро. Отсюда практическое следствие: однопоточная задача на сервере может считаться медленнее, чем на рабочей машине.
- Память — серверный поддерживает ECC (коррекцию однобитовых ошибок), больше каналов памяти (8 и 12 против 2 у настольного) и объёмы в терабайты.
- Связность — многосокетные конфигурации с NUMA, где у каждого сокета своя локальная память, и обращение к чужой стоит дороже. Больше линий PCIe под диски и сетевые карты.
- Кэш — существенно больший L3 на сокет, что важно для баз данных и разделяемых структур.
- Надёжность и обслуживание — функции RAS, диагностика, удалённое управление, расчёт на непрерывную работу под нагрузкой.
- Ноутбучный — тот же кристалл, ограниченный питанием и охлаждением: низкий бюджет мощности, агрессивный троттлинг под длительной нагрузкой, гибридная схема из производительных и энергоэффективных ядер, из-за которой замеры плавают.
- Почему это спрашивают — из этого следует, что бенчмарк с ноутбука нельзя переносить на прод: там другое число ядер, другой троттлинг и другая память.
- См. [hardware-and-os/01-cpu-architecture.md](../10-devops-and-observability/hardware-and-os/01-cpu-architecture.md).

**Какова типичная скорость обмена между процессором и памятью?**

- Пропускная способность одного канала — примерно 25 ГБ/с у DDR4-3200 и около 38 ГБ/с у DDR5-4800. Настольная система с двумя каналами даёт порядка 50 ГБ/с, серверная с восемью — около 200–300 ГБ/с, с двенадцатью каналами DDR5 — свыше 500 ГБ/с.
- Задержка обращения в RAM — примерно 70–100 нс, и она почти не улучшается от поколения к поколению, в отличие от пропускной способности.
- Почему разрыв так важен — за 80 нс ожидания процессор успел бы выполнить сотни инструкций. Именно поэтому существует иерархия кэшей.
- Типичные задержки уровней:

| Уровень | Задержка | Объём |
| --- | --- | --- |
| Регистры | доли наносекунды | сотни байт |
| L1 | ~1 нс | 32–64 КБ на ядро |
| L2 | ~4 нс | 0.5–2 МБ на ядро |
| L3 | ~20–40 нс | 16–256 МБ на сокет |
| RAM | ~80 нс | десятки-сотни ГБ |

- Практический вывод для кода — последовательный обход слайса структур на порядок быстрее обхода слайса указателей: в первом случае работает предвыборка и данные лежат в одной линии кэша, во втором каждый переход это потенциальный промах.
- См. [hardware-and-os/02-memory-hierarchy.md](../10-devops-and-observability/hardware-and-os/02-memory-hierarchy.md).

**Какова типичная скорость обмена с накопителями?**

| Накопитель | Последовательное чтение | Случайные операции 4 КБ | Задержка |
| --- | --- | --- | --- |
| NVMe SSD (PCIe 4.0) | 5–7 ГБ/с | сотни тысяч IOPS | 20–100 мкс |
| NVMe SSD (PCIe 5.0) | до 14 ГБ/с | до миллиона IOPS | 20–80 мкс |
| SATA SSD | ~550 МБ/с | ~90 тысяч IOPS | ~100 мкс |
| HDD 7200 об/мин | 150–250 МБ/с | 100–200 IOPS | 5–10 мс |
| Сетевой диск в облаке | зависит от тарифа | ограничен квотой IOPS | 0.5–2 мс |

- Что важнее скорости — характер нагрузки: базы данных упираются в случайные операции и задержку, а не в последовательную пропускную способность. Разрыв между HDD и SSD по IOPS достигает трёх порядков.
- Отдельный фактор — `fsync`: подтверждение записи на диск стоит дорого, и именно оно ограничивает частоту коммитов в СУБД. Отсюда group commit, объединяющий коммиты нескольких транзакций в один сброс.
- В облаке действует квота — диск может выдавать заявленные IOPS только до исчерпания лимита, после чего скорость падает. Это частая причина «внезапной» деградации базы.

**Какие бывают системы хранения?**

- DAS — диски, подключённые напрямую к серверу. Максимальная скорость, но ёмкость и доступность привязаны к одной машине.
- NAS — сетевое файловое хранилище по NFS или SMB: работает на уровне файлов, удобно для общего доступа, но чувствительно к задержке сети.
- SAN — сеть хранения по iSCSI или Fibre Channel: сервер видит удалённый том как обычный блочный диск. Дороже, зато подходит для баз данных.
- Объектное (S3 и совместимые) — плоское пространство объектов с доступом по HTTP: практически безграничная ёмкость, но нет изменения части файла и нет привычной семантики файловой системы.
- Распределённые (Ceph, GlusterFS) — единое хранилище поверх множества узлов с репликацией и восстановлением при отказе.
- RAID — не отдельный тип, а способ объединения дисков: RAID 1 (зеркало), RAID 10 (зеркало и чередование, обычный выбор для баз), RAID 5 и 6 (чётность, экономнее по месту, но с дорогой записью и долгим восстановлением).
- Что стоит сказать отдельно — RAID это не бэкап: он защищает от отказа диска, но не от ошибочного `DELETE`, повреждения данных и шифровальщика.

**Какова типичная скорость сетевого обмена?**

- Пропускная способность — 1 Гбит/с на старых машинах, 10 и 25 Гбит/с как норма для современных серверов, 100 Гбит/с в ядре сети. В байтах 25 Гбит/с это чуть больше 3 ГБ/с, то есть на порядок меньше памяти.
- Задержки в один конец и обратно:

| Маршрут | RTT |
| --- | --- |
| Внутри хоста (loopback) | десятки микросекунд |
| В пределах стойки | 0.05–0.2 мс |
| Внутри дата-центра | 0.2–0.5 мс |
| Между зонами доступности | 1–2 мс |
| Между регионами одного континента | 10–40 мс |
| Между континентами | 70–150 мс |

- Что из этого следует для архитектуры — задержка определяется в первую очередь расстоянием и числом сетевых вызовов, а не шириной канала. Один запрос через океан стоит дороже, чем сто запросов внутри дата-центра.
- Отсюда типовые решения — пакетная обработка вместо N последовательных вызовов, кэш ближе к пользователю, CDN, параллельные независимые запросы вместо цепочки.
- Чем ограничена реальная скорость соединения — не только каналом: TCP с его окном и медленным стартом на длинных маршрутах не успевает разогнаться, поэтому короткие соединения через океан не выбирают и десятой части полосы.

**Сколько обычно оперативной памяти на сервере?**

- Типичный прикладной сервер — 32–128 ГБ; узел под базу данных — 256 ГБ–1 ТБ; специализированные машины под кэш и аналитику — несколько терабайт.
- Как считают под сервис — размер рабочего набора плюс запас на пики и на сборщик мусора. Для Go-сервиса ориентируются на `GOMEMLIMIT` около 90% лимита контейнера.
- Почему важна не только ёмкость — на многосокетном сервере действует NUMA: память локальна для сокета, и обращение к чужой половине заметно дороже. Отсюда привязка процессов к узлам NUMA у баз данных.
- См. [hardware-and-os/README.md](../10-devops-and-observability/hardware-and-os/README.md).

## Системное администрирование

**Права доступа в Linux. Файловая система**

- Базовая модель — три категории (владелец, группа, остальные) и три бита прав (`r`, `w`, `x`), что даёт привычную запись `rwxr-xr--` или восьмеричную `754`.
- Что значат биты для каталога — здесь смысл другой, и это частая ошибка:
  - `r` — можно получить список имён;
  - `w` — можно создавать и удалять записи в каталоге, в том числе чужие файлы;
  - `x` — можно войти в каталог и обратиться к файлу по известному пути.
- Отсюда следствие — удаление файла определяется правами на каталог, а не на сам файл. Защищает от этого sticky bit (`chmod +t`, как на `/tmp`): удалять может только владелец.
- Специальные биты — setuid и setgid запускают программу с правами владельца файла или группы; на каталоге setgid заставляет новые файлы наследовать группу.
- Команды — `chmod`, `chown`, `umask` (маска, снимающая биты у новых файлов, обычно `022`), `getfacl`/`setfacl` для точечных правил сверх трёх категорий.
- Что вытесняет setuid в современных системах — capabilities: вместо полных прав root процессу выдают одну возможность, например `CAP_NET_BIND_SERVICE` для порта ниже 1024.
- Устройство файловой системы:
  - inode — метаданные файла: права, владелец, размер, времена, указатели на блоки. Имени файла в inode нет;
  - каталог — таблица соответствия «имя, номер inode»;
  - жёсткая ссылка — ещё одно имя для того же inode, файл исчезает при нулевом счётчике ссылок и отсутствии открытых дескрипторов;
  - символическая ссылка — отдельный файл с путём внутри, может указывать в никуда и пересекать точки монтирования;
  - монтирование — подключение файловой системы в точку дерева, единого корня дисков нет, всё растёт из `/`;
  - виртуальные файловые системы — `/proc` и `/sys` не лежат на диске, а отдают состояние ядра.
- Практическая деталь — место может кончиться двумя способами: закончились блоки (`df -h`) или закончились inode (`df -i`) из-за миллионов мелких файлов.
- См. [linux/06-linux-commands.md](../10-devops-and-observability/linux/06-linux-commands.md).

**Приложение, процесс и поток. В чём разница?**

- Приложение — программа как продукт: код, файлы, конфигурация. Понятие не операционной системы, а предметной области; одно приложение может состоять из нескольких процессов.
- Процесс — исполняющийся экземпляр программы, которому ОС выделяет собственное виртуальное адресное пространство, таблицу дескрипторов, права и идентификатор. Процессы изолированы, обмениваются через IPC: пайпы, сокеты, разделяемую память, сигналы.
- Поток — единица планирования внутри процесса. Потоки одного процесса делят адресное пространство, дескрипторы и глобальные данные, но у каждого свой стек, регистры и приоритет.
- Чем платят за разницу — переключение между процессами дороже: меняется таблица страниц и сбрасывается часть TLB. Переключение потоков дешевле, потому что адресное пространство остаётся тем же.
- Как это устроено в Linux — ядро не различает процессы и потоки, у него есть только задача (task). `clone()` с разными флагами даёт либо новый процесс, либо поток, разделяющий память с родителем.
- Где здесь горутина — это единица планирования пользовательского пространства, о которой ядро вообще не знает. Рантайм Go раскладывает горутины по потокам ОС, поэтому создание горутины не требует системного вызова и стоит на порядки дешевле создания потока.
- Как отвечать коротко — процесс это изоляция, поток это параллелизм внутри изоляции, горутина это параллелизм внутри потока без участия ядра.
- См. [hardware-and-os/06-processes-and-threads.md](../10-devops-and-observability/hardware-and-os/06-processes-and-threads.md).

**Файловые дескрипторы. Какие есть ограничения?**

- Что это — небольшое неотрицательное целое, индекс в таблице открытых файлов процесса. Через него ядро находит запись со смещением, режимом и объектом.
- Стандартные — 0 (`stdin`), 1 (`stdout`), 2 (`stderr`); новый дескриптор всегда получает наименьший свободный номер.
- Почему это касается сетевого сервиса — в Linux дескрипторами представлены не только файлы: сокеты, пайпы, `epoll`, `eventfd`, таймеры, устройства. Каждое TCP-соединение занимает дескриптор.
- Уровни ограничений:

| Ограничение | Где смотреть | Смысл |
| --- | --- | --- |
| `RLIMIT_NOFILE` мягкий | `ulimit -n` | текущий предел процесса, поднимается до жёсткого без прав root |
| `RLIMIT_NOFILE` жёсткий | `ulimit -Hn` | потолок, выше которого без root не подняться |
| `fs.file-max` | `sysctl fs.file-max` | предел на всю систему |
| `fs.nr_open` | `sysctl fs.nr_open` | максимум для одного процесса |
| `LimitNOFILE` | unit-файл systemd | предел для сервиса, а не для интерактивной сессии |

- Ловушка эксплуатации — `ulimit` в оболочке не влияет на сервис, запущенный systemd: у него собственный лимит из unit-файла. То же и в контейнере, где лимит задаёт среда выполнения.
- Что делает Go — с версии 1.19 рантайм при старте сам поднимает мягкий лимит до жёсткого, поэтому Go-сервисы упираются в дескрипторы реже других.
- Как выглядит исчерпание — ошибки `too many open files`, `accept: EMFILE`, отказ открывать соединения к базе при живом сервисе.
- Как диагностировать — `ls /proc/<pid>/fd | wc -l` для счёта, `lsof -p <pid>` для содержимого. Постоянный рост означает утечку: незакрытые тела ответов, соединения или файлы.
- Частая причина утечки в Go — отсутствие `defer resp.Body.Close()`: соединение не возвращается в пул и дескриптор остаётся занят.
- См. [linux/02-file-descriptors-and-io.md](../10-devops-and-observability/linux/02-file-descriptors-and-io.md).

**Сколько соединений можно открыть на сервере?**

- Главное недоразумение — «не больше 65535, ведь портов столько». Это верно для исходящих соединений к одному адресату, но не для сервера.
- Почему — соединение идентифицируется четвёркой «IP и порт источника, IP и порт назначения». У сервера порт назначения один (например 443), а различаются адреса и порты клиентов, поэтому теоретический предел огромен.
- Реальные ограничители:
  - файловые дескрипторы — по одному на соединение, отсюда `RLIMIT_NOFILE`;
  - память ядра — структуры сокета и буферы приёма и передачи, суммарно единицы-десятки килобайт на соединение. Миллион соединений это уже десятки гигабайт только под буферы;
  - память приложения — в Go это минимум одна горутина на соединение плюс её буферы;
  - `net.core.somaxconn` и `tcp_max_syn_backlog` — очереди принятия, их переполнение даёт отказы при всплеске;
  - conntrack на файрволе и NAT — отдельная таблица со своим лимитом, часто она заканчивается первой;
  - состояние TIME_WAIT — после закрытия сокет держит четвёрку около 60 секунд, что бьёт по стороне, инициирующей закрытие.
- Где 65535 действительно упирается — у клиента: диапазон эфемерных портов (`net.ipv4.ip_local_port_range`, обычно около 28 тысяч) ограничивает число одновременных соединений к одной паре «адрес и порт». Лечится расширением диапазона, дополнительными адресами или переиспользованием соединений.
- Практические ориентиры — десятки тысяч соединений на обычной конфигурации без настройки, сотни тысяч и миллион (задача C10M) после тюнинга дескрипторов, буферов и conntrack.
- Почему Go здесь удобен — сетевой опрашиватель (netpoller) поверх `epoll` держит десятки тысяч соединений на нескольких потоках ОС, а код при этом остаётся линейным, по горутине на соединение.
- См. [linux/03-tcp-sockets.md](../10-devops-and-observability/linux/03-tcp-sockets.md).

## Безопасность

**Аутентификация и авторизация — в чём разница?**

- Аутентификация отвечает на вопрос «кто это» — проверка предъявленных данных: пароля, токена, сертификата, отпечатка.
- Авторизация отвечает на вопрос «что этому субъекту разрешено» — проверка прав на конкретное действие с конкретным объектом.
- Порядок — сначала аутентификация, затем авторизация. Обратный порядок бессмысленен: нельзя проверять права неизвестно чьи.
- Рядом стоит идентификация — заявление о том, кто ты (логин), без доказательства. Аутентификация это уже доказательство.
- Как это видно в HTTP — 401 Unauthorized означает «не опознан или сессия истекла», и клиенту следует обновить токен; 403 Forbidden означает «опознан, но прав нет», и повторять с тем же токеном бесполезно. Название кода 401 исторически неточно: речь именно об аутентификации.
- Где проверяют — аутентификацию удобно вынести на шлюз, а авторизацию почти всегда приходится делать в сервисе, потому что права зависят от объекта: владелец заказа, участник проекта, роль в организации.
- Модели авторизации — RBAC (по ролям), ABAC (по атрибутам субъекта, объекта и контекста), ACL (список прав у объекта).
- См. [authentication/07-authorization-and-rbac.md](../11-security/authentication/07-authorization-and-rbac.md).

**Какие бывают способы аутентификации?**

- Три классических фактора — знание (пароль, PIN), владение (телефон, аппаратный ключ, сертификат), свойство (отпечаток, лицо). Многофакторная аутентификация требует не двух проверок, а проверок из разных категорий.
- Пароль — самый простой способ; на сервере хранится не пароль, а результат медленной хеш-функции с солью: argon2id, scrypt или bcrypt. Быстрые хеши вроде SHA-256 для паролей не годятся, потому что перебор на видеокарте идёт миллиардами вариантов в секунду.
- Сессии — сервер выдаёт случайный идентификатор в cookie с флагами `HttpOnly`, `Secure` и `SameSite`, состояние держит у себя. Плюс — мгновенный отзыв. Минус — нужно общее хранилище сессий при нескольких инстансах.
- Токены (JWT) — подписанный набор утверждений, который сервис проверяет без обращения к хранилищу. Плюс — не нужна общая база на проверке. Минус — выданный токен нельзя отозвать до истечения, поэтому срок жизни делают коротким и добавляют refresh-токен.
- OAuth 2.0 и OpenID Connect — делегирование: OAuth про доступ к ресурсу от имени пользователя, OIDC надстраивает над ним аутентификацию с `id_token`. Именно так работает вход через внешнего провайдера.
- Взаимный TLS (mTLS) — обе стороны предъявляют сертификаты. Основной способ для связи между сервисами внутри периметра.
- API-ключи — простая идентификация приложения, а не пользователя; годятся для внутренних интеграций при обязательной ротации.
- Одноразовые коды — TOTP в приложении-аутентификаторе; SMS считается слабым фактором из-за перехвата и подмены SIM.
- WebAuthn и passkeys — асимметричная пара ключей, привязанная к домену; фишинг перестаёт работать, потому что подписи для чужого домена не будет. Наиболее устойчивый из массовых способов.
- Корпоративные — SAML, LDAP, Kerberos для единого входа внутри организации.
- Как выбирать — по цене компрометации: внутренний инструмент обходится сессией, платёжный сервис требует второго фактора и коротких токенов.
- См. [authentication/05-authentication-methods-overview.md](../11-security/authentication/05-authentication-methods-overview.md) и [authentication/06-jwt.md](../11-security/authentication/06-jwt.md).

**Шифрование. Симметричное и асимметричное**

- Симметричное — один общий ключ на шифрование и расшифровку. Алгоритмы: AES-256-GCM, ChaCha20-Poly1305.
  - Плюс — скорость: гигабайты в секунду, аппаратное ускорение AES прямо в процессоре.
  - Минус — распространение ключа: его нужно как-то передать второй стороне, и на n участников требуется n(n−1)/2 ключей.
- Асимметричное — пара ключей: открытый шифрует и проверяет подпись, закрытый расшифровывает и подписывает. Алгоритмы: RSA, ECDSA, Ed25519, обмен ключами X25519.
  - Плюс — открытый ключ можно публиковать, поэтому решается и распространение ключа, и электронная подпись с неотказуемостью.
  - Минус — на два-три порядка медленнее и с ограничением на размер сообщения.
- Как их объединяют — гибридная схема, и именно она работает в TLS:
  1. асимметрия подтверждает подлинность сервера по сертификату и участвует в согласовании общего секрета (ECDHE);
  2. из общего секрета выводится симметричный сеансовый ключ;
  3. весь дальнейший трафик шифруется быстрым симметричным алгоритмом.
- Что даёт эфемерный обмен ключами — прямую секретность (forward secrecy): компрометация долговременного ключа сервера не позволяет расшифровать записанный ранее трафик, потому что сеансовые ключи не восстановимы.
- Что не является шифрованием:
  - хеширование (SHA-256, argon2) — односторонняя свёртка без возможности восстановить исходные данные;
  - кодирование (base64, URL-encoding) — представление данных, обратимое без всякого ключа. Base64 не защищает ничего.
- Что важно для прикладного кода — не собирать схему самостоятельно: брать `crypto/tls` и готовые режимы с аутентификацией (AEAD, например AES-GCM), которые вместе с шифрованием защищают от подмены. Режим без проверки целостности позволяет изменить шифротекст незаметно.
- Где взять ключи — из менеджера секретов с ротацией, а не из конфигурации в репозитории.
- См. [service-to-service-tls/01-tls-termination-re-encryption-and-mtls.md](../11-security/service-to-service-tls/01-tls-termination-re-encryption-and-mtls.md) и [secrets-management/01-secrets-delivery-options.md](../11-security/secrets-management/01-secrets-delivery-options.md).
