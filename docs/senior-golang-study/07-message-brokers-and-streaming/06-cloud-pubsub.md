## Google Cloud Pub/Sub

### Topics, subscriptions, ack deadline

```text
Publisher
    │
    ▼
[Topic: "orders"]
    │
    ├── Subscription "fulfillment"  ← своя копия каждого сообщения
    ├── Subscription "analytics"    ← независимая позиция
    └── Subscription "notifications" ← со своим dead letter topic
```

- **Topic** — точка публикации. Сообщения в нём не привязаны к получателям.
- **Subscription** — подписка на topic. Каждая подписка получает копию каждого сообщения, доставка at-least-once, подписки не влияют друг на друга — по смыслу это consumer group в Kafka.
- **Ack deadline** — время на обработку: по умолчанию 10 секунд, максимум 600. Не подтвердил вовремя — сообщение доставят снова.

Про ack deadline важная деталь, которая избавляет от ручной работы: клиентская библиотека Go сама продлевает срок, пока обработчик не вернул управление, вплоть до `MaxExtension` в настройках. То есть 600 секунд — это не потолок обработки, а потолок одного продления; долгую задачу ограничивает `MaxExtension`, а не лимит API.

### Go-клиент

Клиент создаётся один раз на приложение и переиспользуется: создание клиента на каждое сообщение — дорогая ошибка, потому что под ним поднимается gRPC-соединение с аутентификацией.

```go
// В библиотеке версии v2 сущности называются Publisher и Subscriber
// (в v1 это были Topic и Subscription с теми же методами).
pub := client.Publisher("orders")
pub.PublishSettings.CountThreshold = 100                   // батч: сколько сообщений накапливать
pub.PublishSettings.DelayThreshold = 20 * time.Millisecond // ...или сколько ждать
defer pub.Stop() // дослать накопленное перед выходом

res := pub.Publish(ctx, &pubsub.Message{
    Data:       data,
    Attributes: map[string]string{"event_type": "order.created"},
})
if _, err := res.Get(ctx); err != nil { // здесь публикация становится подтверждённой
    return fmt.Errorf("publish: %w", err)
}
```

`Publish` не отправляет сообщение сразу — он кладёт его в батч и возвращает будущий результат. Ожидание `res.Get` на каждом сообщении сводит батчинг к нулю, поэтому в потоке результаты собирают отдельно, а не по одному.

<details>
<summary>Publisher и Subscriber целиком</summary>

```go
import "cloud.google.com/go/pubsub/v2"

func NewClient(ctx context.Context, projectID string) (*pubsub.Client, error) {
    // Клиент потокобезопасен и создаётся один раз на приложение.
    return pubsub.NewClient(ctx, projectID)
}

func publish(ctx context.Context, client *pubsub.Client, data []byte) error {
    pub := client.Publisher("orders")
    pub.PublishSettings.CountThreshold = 100
    pub.PublishSettings.DelayThreshold = 20 * time.Millisecond
    defer pub.Stop()

    res := pub.Publish(ctx, &pubsub.Message{
        Data:       data,
        Attributes: map[string]string{"event_type": "order.created", "version": "v1"},
    })
    if _, err := res.Get(ctx); err != nil {
        return fmt.Errorf("publish: %w", err)
    }
    return nil
}

func receive(ctx context.Context, client *pubsub.Client) error {
    sub := client.Subscriber("fulfillment-sub")
    sub.ReceiveSettings.MaxOutstandingMessages = 100    // сколько сообщений держать без ack
    sub.ReceiveSettings.MaxExtension = 10 * time.Minute // до какого срока продлевать ack deadline
    sub.ReceiveSettings.NumGoroutines = 4               // параллелизм обработчиков

    // Receive блокируется до отмены контекста и вызывает обработчик параллельно.
    return sub.Receive(ctx, func(ctx context.Context, msg *pubsub.Message) {
        if err := processOrder(ctx, msg.Data); err != nil {
            msg.Nack() // вернуть в подписку для повторной доставки
            return
        }
        msg.Ack()
    })
}
```

</details>

### Dead letter topic

Настраивается на подписке: после исчерпания попыток сообщение уходит в отдельный topic, на который заводится своя подписка для разбора.

```bash
gcloud pubsub subscriptions create fulfillment-sub \
  --topic=orders \
  --dead-letter-topic=orders-dlq \
  --max-delivery-attempts=5 \
  --ack-deadline=60
```

Две вещи, на которых это обычно ломается при первом включении. Во-первых, сервисному аккаунту Pub/Sub нужны права публиковать в dead letter topic и подтверждать сообщения в исходной подписке — без них DLQ молча не работает. Во-вторых, `max-delivery-attempts` считает доставки, а не ошибки обработки: сообщение, которое не подтвердили из-за упавшего пода, тратит попытку так же, как явный `Nack`.

## Push против Pull

Подписка бывает двух режимов, и выбор между ними влияет на архитектуру сильнее, чем кажется.

| | Pull | Push |
| --- | --- | --- |
| Кто инициирует | сервис сам забирает сообщения, держа поток к API | Pub/Sub делает HTTPS-запрос на указанный эндпоинт |
| Что нужно снаружи | ничего, достаточно исходящей связности | публично доступный HTTPS-эндпоинт с валидным сертификатом |
| Аутентификация | учётные данные сервисного аккаунта | подпись OIDC-токеном, которую эндпоинт обязан проверять |
| Регулирование скорости | через `MaxOutstandingMessages` на стороне клиента | Pub/Sub сам наращивает и снижает темп по кодам ответа |
| Подтверждение | вызов `Ack` | код 2xx в ответе на запрос |
| Где уместно | обычные сервисы, полный контроль над темпом | serverless (Cloud Run, Cloud Functions), где нет постоянного процесса |

Практический смысл: pull выбирают по умолчанию, потому что он не требует внешней точки входа и даёт прямой контроль над параллелизмом. Push нужен там, где нет процесса, который мог бы держать соединение — то есть в serverless-обработчиках, масштабирующихся с нуля.

## Порядок сообщений и exactly-once в GCP

По умолчанию Pub/Sub порядок не гарантирует: сообщения могут прийти в любой последовательности, потому что доставка распределена. Порядок включается ключом упорядочивания — это прямой аналог ключа партиции в Kafka:

```go
pub.EnableMessageOrdering = true // без этого OrderingKey игнорируется

res := pub.Publish(ctx, &pubsub.Message{
    Data:        data,
    OrderingKey: orderID, // сообщения с одним ключом доставляются по порядку
})
```

Что важно знать про эту опцию:

- порядок соблюдается для сообщений с одинаковым ключом внутри региона, между разными ключами порядка нет — как между партициями;
- пропускная способность одного ключа ограничена, поэтому ключ выбирают по сущности (заказ, аккаунт), а не по типу события;
- при ошибке публикации в упорядоченном ключе последующие сообщения этого ключа блокируются до вызова возобновления — иначе порядок был бы нарушен молча;
- на подписке ordering тоже надо включить, иначе получатель увидит обычную неупорядоченную доставку.

Exactly-once включается на уровне подписки (`enable_exactly_once_delivery`) и означает: успешно подтверждённое сообщение не будет доставлено повторно, а подтверждения перестают быть «выстрелил и забыл». В коде это меняет способ подтверждения:

```go
// На подписке с exactly-once обычный Ack() недостаточен: нужен результат.
r := msg.AckWithResult()
if _, err := r.Get(ctx); err != nil {
    // Подтверждение не приняли: сообщение будет доставлено снова,
    // поэтому обработка обязана оставаться идемпотентной.
    log.Printf("ack failed: %v", err)
}
```

Граница гарантии та же, что и в Kafka: она про доставку внутри Pub/Sub, а не про эффекты в вашей базе или у платёжного провайдера. Идемпотентность приёмника остаётся обязательной — [идемпотентность](../05-system-design/reliability-patterns/06-idempotency.md).

## Повторное чтение: seek и снапшоты

У Pub/Sub есть ограниченный аналог replay, о котором часто не знают. Подписка хранит сообщения `message_retention_duration` (по умолчанию 7 дней, максимум 31 день), и в пределах этого срока позицию подписки можно перемотать:

```bash
# перемотать подписку на момент времени: подтверждённые сообщения снова станут доступны
gcloud pubsub subscriptions seek fulfillment-sub --time=2026-07-29T10:00:00Z

# снапшот фиксирует текущее состояние подтверждений, чтобы вернуться к нему позже
gcloud pubsub snapshots create before-deploy --subscription=fulfillment-sub
gcloud pubsub subscriptions seek fulfillment-sub --snapshot=before-deploy
```

Типичное применение — выкатили сломанную версию обработчика, откатились и перемотали подписку на момент перед деплоем. Это не полноценный лог: перемотка меняет состояние подписки целиком, нельзя параллельно читать историю и новые сообщения, а новая подписка на topic по умолчанию видит только сообщения, опубликованные после её создания (если на topic не включено собственное хранение).

## AWS SNS + SQS: веерная доставка

```text
Publisher
    │
    ▼
[SNS Topic: "OrderEvents"]
    │
    ├── SQS "fulfillment-queue"    → потребитель A
    ├── SQS "analytics-queue"      → потребитель B
    └── SQS "notifications-queue"  → потребитель C
```

В AWS одна система отвечает за рассылку, другая за хранение: SNS принимает публикацию и доставляет копию в каждую подписанную очередь, SQS хранит сообщения до удаления. Собранная схема даёт то же, что подписки в GCP или consumer groups в Kafka — несколько независимых получателей одного события.

Ключевое отличие от GCP: очередь здесь — самостоятельный ресурс со своими настройками, DLQ и правами. Это больше конфигурации, зато каждый получатель настраивается независимо, а SQS можно использовать и без SNS, как обычную очередь задач.

```go
out, err := client.ReceiveMessage(ctx, &sqs.ReceiveMessageInput{
    QueueUrl:            aws.String(queueURL),
    MaxNumberOfMessages: 10, // максимум за один запрос
    WaitTimeSeconds:     20, // long polling: ждать сообщения, а не возвращать пустой ответ
    VisibilityTimeout:   30, // на сколько сообщение скрыто от других потребителей
})
```

`WaitTimeSeconds` здесь не мелочь: без него (короткий опрос) клиент получает пустые ответы и платит за каждый запрос, а сообщения приходят с задержкой. Длинный опрос до 20 секунд — стандартная настройка, которая одновременно снижает и стоимость, и задержку.

<details>
<summary>Публикация в SNS и чтение из SQS целиком</summary>

```go
import (
    "github.com/aws/aws-sdk-go-v2/aws"
    "github.com/aws/aws-sdk-go-v2/service/sns"
    snstypes "github.com/aws/aws-sdk-go-v2/service/sns/types"
    "github.com/aws/aws-sdk-go-v2/service/sqs"
)

func publishSNS(ctx context.Context, client *sns.Client, topicARN, body string) error {
    _, err := client.Publish(ctx, &sns.PublishInput{
        TopicArn: aws.String(topicARN),
        Message:  aws.String(body),
        MessageAttributes: map[string]snstypes.MessageAttributeValue{
            "eventType": {
                DataType:    aws.String("String"),
                StringValue: aws.String("order.created"),
            },
        },
    })
    return err
}

func consumeSQS(ctx context.Context, client *sqs.Client, queueURL string) error {
    for {
        out, err := client.ReceiveMessage(ctx, &sqs.ReceiveMessageInput{
            QueueUrl:            aws.String(queueURL),
            MaxNumberOfMessages: 10,
            WaitTimeSeconds:     20,
            VisibilityTimeout:   30,
        })
        if err != nil {
            return fmt.Errorf("receive: %w", err)
        }
        for _, msg := range out.Messages {
            if err := processMessage(ctx, []byte(*msg.Body)); err != nil {
                // Не удаляем: сообщение снова станет видимым после visibility timeout,
                // а после maxReceiveCount попыток уйдёт в DLQ по redrive policy.
                continue
            }
            // Удаление и есть подтверждение обработки.
            if _, err := client.DeleteMessage(ctx, &sqs.DeleteMessageInput{
                QueueUrl:      aws.String(queueURL),
                ReceiptHandle: msg.ReceiptHandle,
            }); err != nil {
                log.Printf("delete: %v", err) // сообщение придёт повторно, нужна идемпотентность
            }
        }
    }
}
```

</details>

DLQ настраивается политикой перенаправления на самой очереди:

```hcl
resource "aws_sqs_queue" "fulfillment_dlq" {
  name = "fulfillment-dlq"
}

resource "aws_sqs_queue" "fulfillment" {
  name = "fulfillment"
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.fulfillment_dlq.arn
    maxReceiveCount     = 3 # после трёх получений без удаления — в DLQ
  })
}
```

## SQS: standard против FIFO

Два типа очередей с разными гарантиями, и выбор делается при создании — сменить тип потом нельзя.

| | Standard | FIFO |
| --- | --- | --- |
| Порядок | по возможности, без гарантии | строгий внутри группы сообщений |
| Доставка | at-least-once, дубликаты возможны | ровно один раз в пределах окна дедупликации (5 минут) |
| Пропускная способность | практически не ограничена | около 300 запросов/с, до 3000 сообщений/с с батчами; в режиме высокой пропускной способности кратно выше |
| Группировка | нет | `MessageGroupId`: порядок и параллелизм задаются им |
| Дедупликация | своими силами | по содержимому или явному `MessageDeduplicationId` |

`MessageGroupId` в FIFO работает как ключ партиции: сообщения одной группы обрабатываются строго по порядку и одним потребителем за раз, разные группы — параллельно. Отсюда практическое правило: группа это сущность (счёт, заказ), а не тип события, иначе весь поток сериализуется в одну цепочку.

## Visibility timeout и долгие задачи

В SQS нет подтверждения как отдельной операции: подтверждение — это удаление сообщения. Пока сообщение не удалено, оно скрыто от других потребителей на время visibility timeout, а по его истечении снова становится доступным.

```text
получено → скрыто на 30 с → обработка идёт
                          ├─ удалили       → сообщение исчезло
                          └─ не удалили    → снова видимо, счётчик получений +1
                                             после maxReceiveCount → DLQ
```

Задача длиннее visibility timeout приводит к тому, что сообщение подхватывает второй потребитель, пока первый ещё работает — классический источник двойной обработки. Правильная реакция — продлевать срок по ходу работы, а не ставить сразу максимум:

```go
// Продление для долгой задачи: вызывается периодически, пока идёт обработка.
client.ChangeMessageVisibility(ctx, &sqs.ChangeMessageVisibilityInput{
    QueueUrl:          aws.String(queueURL),
    ReceiptHandle:     msg.ReceiptHandle,
    VisibilityTimeout: 120,
})
```

Это тот же приём, что heartbeat при долгой обработке в Kafka: приложение периодически сообщает, что живо и продолжает работу. Максимум visibility timeout — 12 часов, но полагаться на большое значение вслепую плохо: если под умрёт сразу после получения, сообщение вернётся в очередь только через это время.

## Лимиты и стоимость

Числа, которые определяют, поместится ли задача в managed-сервис. Тарифы и квоты меняются, поэтому финальные значения проверяют по калькулятору провайдера, но порядок величины устойчив.

| | GCP Pub/Sub | AWS SNS+SQS |
| --- | --- | --- |
| Размер сообщения | до 10 МБ | до 256 КБ (больше — через ссылку на S3) |
| Хранение | 7 дней по умолчанию, до 31 дня | 4 дня по умолчанию, до 14 дней |
| Порядок | ключ упорядочивания | только FIFO-очереди |
| Повторное чтение | seek в пределах хранения | нет |
| Оплата | за объём данных (порядка $40 за ТиБ) | за число запросов (порядка $0.40 за миллион) |

Из модели оплаты следуют разные способы экономии. В GCP платят за байты, поэтому дешевле сокращать полезную нагрузку: отправлять идентификатор вместо документа, сжимать, не публиковать то, что никому не нужно. В AWS платят за запросы, поэтому главный рычаг — батчинг: `SendMessageBatch` и чтение по 10 сообщений за запрос уменьшают счёт почти на порядок, а длинный опрос убирает оплату пустых ответов.

Простой расчёт для ориентира: поток 10k сообщений в секунду по 1 КБ даёт около 26 ТБ в месяц. В GCP это оплата и публикации, и каждой доставки — при трёх подписках объём умножается. На таком профиле managed-сервис ещё разумен, а на 300k сообщений в секунду счёт уходит в шестизначный, и своя Kafka с несколькими брокерами оказывается дешевле — разбор с числами в [00-comparison.md](./00-comparison.md).

## Cloud или self-hosted

| | Managed (GCP, AWS) | Self-hosted (Kafka, RabbitMQ) |
|---|---|---|
| Эксплуатация | нулевая: обновления и отказоустойчивость на провайдере | своя команда, дежурства, обновления |
| Стоимость | линейна объёму или числу запросов | стоимость железа плюс люди, выгоднее на больших объёмах |
| Привязка к провайдеру | высокая: API и семантика уникальны | переносимо между площадками |
| Доступность | SLA провайдера, обычно от 99.9% | зависит от конфигурации и команды |
| Хранение | дни или недели | месяцы, с tiered storage — годы |
| Задержка | десятки миллисекунд | единицы миллисекунд |
| Тонкая настройка | ограничена набором параметров | полный контроль |

Managed выбирают, когда команда небольшая, объём умеренный, стек уже в этом облаке и не нужны ни долгая история, ни экосистема потоковой обработки. Своя установка окупается, когда объём делает оплату за сообщение дороже железа, нужен retention месяцами, требуется размещение данных в конкретной юрисдикции или нужны Kafka Streams, Connect и schema registry. Полное сравнение со всеми брокерами — [00-comparison.md](./00-comparison.md).

## Interview-ready answer

**1. Чем SNS+SQS отличается от Kafka?**

- Модель — SNS рассылает, SQS хранит; вместе они дают несколько независимых получателей одного события, но каждый со своей очередью и своей копией сообщения.
- Хранение — SQS держит сообщение до удаления, максимум 14 дней, и удаляет безвозвратно; Kafka хранит лог по retention независимо от чтения.
- Повторное чтение — в SQS его нет в принципе: прочитанное и удалённое сообщение не вернуть; в Kafka достаточно сдвинуть offset.
- Порядок — в standard-очереди не гарантирован, в FIFO строгий внутри `MessageGroupId` ценой пропускной способности; в Kafka порядок внутри партиции по ключу.
- Эксплуатация и цена — SNS+SQS не требуют людей и платятся за запросы; Kafka требует кластера, но дешевеет с ростом объёма.

**2. Когда managed-брокер, а когда своя установка?**

- Managed — маленькая команда без опыта эксплуатации кластеров, умеренный объём, стек уже в этом облаке, replay нужен максимум в пределах дней.
- Своя установка — объём, на котором оплата за сообщение превышает стоимость железа; retention месяцами; требования к размещению данных; нужна экосистема потоковой обработки.
- Скрытая цена облака — привязка к API и семантике провайдера: перенос на другой брокер это переписывание кода публикации и потребления, а не смена адреса.
- Скрытая цена своей установки — не серверы, а люди: дежурства, обновления, разбор инцидентов.

**3. Что в GCP Pub/Sub есть для порядка и exactly-once?**

- Порядок — ключ упорядочивания: сообщения с одним ключом доставляются последовательно, между ключами порядка нет; включать надо и на публикации, и на подписке.
- Ограничение — пропускная способность одного ключа ограничена, а ошибка публикации блокирует последующие сообщения этого ключа до явного возобновления.
- Exactly-once — опция подписки: успешно подтверждённое сообщение не придёт повторно, а подтверждение перестаёт быть «выстрелил и забыл», в коде используется `AckWithResult`.
- Граница — гарантия действует внутри Pub/Sub; эффекты во внешних системах она не откатывает, поэтому идемпотентность приёмника обязательна.

**4. Как обрабатывать долгую задачу в SQS?**

- Механика — подтверждением является удаление сообщения; до удаления оно скрыто на время visibility timeout, потом снова становится видимым.
- Риск — задача длиннее таймаута приводит к тому, что второй потребитель начнёт обрабатывать то же сообщение параллельно.
- Решение — продлевать срок по ходу работы через `ChangeMessageVisibility`, а не выставлять максимум заранее: при смерти пода сообщение вернётся быстро, а не через часы.
- Ограничение попыток — `maxReceiveCount` в политике перенаправления: после N получений без удаления сообщение уходит в DLQ.

**5. Push или pull для подписки в GCP?**

- Pull — сервис сам забирает сообщения, ничего публично доступного не требуется, темп задаётся `MaxOutstandingMessages`; выбор по умолчанию.
- Push — Pub/Sub делает HTTPS-запрос на эндпоинт, подтверждением служит код 2xx; нужен публичный адрес и проверка OIDC-токена.
- Когда push уместен — serverless-обработчики, масштабирующиеся с нуля, где нет процесса, способного держать соединение.
- Разница в регулировании темпа — при pull им управляет приложение, при push провайдер сам наращивает и снижает скорость по кодам ответа.
