## Базовые команды: XADD, XREADGROUP, XACK

### XADD — добавить запись

```redis
XADD stream-key * field1 value1 field2 value2
# "*" = идентификатор сгенерирует Redis, вид "timestamp-sequence", например "1711300000000-0"

XADD orders * order_id "123" user_id "alice" status "created"
# → "1711300000000-0"

# Ограничение длины потока при записи
XADD orders MAXLEN ~ 10000 * order_id "123"
# "~" = приблизительное ограничение, обрезается только целыми узлами и потому дешевле точного
```

### XREAD — читать без consumer group

```redis
# Читать записи, появившиеся после последнего известного идентификатора
XREAD COUNT 10 BLOCK 1000 STREAMS orders $
# BLOCK 1000 = ждать до 1 секунды, если новых записей нет
# "$" = начать с новых, не перечитывая существующие
# "0" = читать с самого начала
```

`XREAD` не хранит позицию на стороне Redis: курсор ведёт сам клиент, поэтому этот режим годится для одиночного читателя, который помнит, где остановился, но не для распределения работы между воркерами.

### XREADGROUP — читать с consumer group

```redis
# Создать группу
XGROUP CREATE orders shipping-group $ MKSTREAM
# "$" = группа начнёт с новых записей
# "0" = группа прочитает поток с начала
# MKSTREAM = создать сам поток, если его ещё нет

# Читать как участник группы
XREADGROUP GROUP shipping-group worker-1 COUNT 10 BLOCK 1000 STREAMS orders >
# ">" = выдать новые записи, ещё никому не выданные
# конкретный ID вместо ">" = выдать собственные неподтверждённые записи
```

### XACK — подтвердить обработку

```redis
XACK orders shipping-group "1711300000000-0"
# убирает запись из Pending Entries List группы
```

### Дополнительные команды

```redis
# Все записи потока в диапазоне
XRANGE orders - +

# Количество записей
XLEN orders

# Выданные, но не подтверждённые записи группы
XPENDING orders shipping-group - + 10

# Передать зависшую запись другому consumer-у
XCLAIM orders shipping-group worker-2 60000 "1711300000000-0"
# 60000 = min-idle-time в миллисекундах: передать, если запись висит дольше минуты
```

## Идентификатор записи как позиция в потоке

Идентификатор состоит из двух чисел: `<миллисекунды>-<порядковый номер внутри миллисекунды>`. Из этого следует несколько практически важных свойств.

```text
1711300000000-0    первая запись в эту миллисекунду
1711300000000-1    вторая запись в ту же миллисекунду
1711300000001-0    следующая миллисекунда

Идентификаторы строго возрастают: Redis не выдаст ID меньше последнего,
даже если системные часы перевели назад.
```

- Идентификатор одновременно является меткой времени, поэтому чтение «с определённого момента» делается без отдельного индекса: `XRANGE orders 1711300000000 +` или `XREAD ... STREAMS orders 1711299999999`.
- Идентификатор можно задать вручную (`XADD orders 1711300000000-5 ...`), но только больше последнего — так переносят данные из другого хранилища, сохраняя исходный порядок.
- Идентификатор — естественный внешний курсор. Именно поэтому Redis Streams хорошо ложатся под SSE: значение из поля `id` кадра возвращается клиентом в заголовке `Last-Event-ID`, и чтение продолжается ровно с той позиции, а не с полного состояния заново (разбор — [00-comparison.md](./00-comparison.md)).
- `XADD` с `NOMKSTREAM` не создаёт поток, если его нет: полезно, когда писать в несуществующий поток означает ошибку конфигурации, а не первый запуск.

## Consumer groups: механика

```text
Stream: orders
  │
  ├── [1711300000000-0] order_id=123
  ├── [1711300000001-0] order_id=124
  └── [1711300000002-0] order_id=125

Consumer Group "shipping"
  │
  ├── worker-1  ← обрабатывает 1711300000000-0 (в PEL, не подтверждено)
  └── worker-2  ← обрабатывает 1711300000001-0 (в PEL, не подтверждено)

  last-delivered-id: 1711300000001-0

Consumer Group "analytics" (независимая позиция)
  │
  └── analyst-1 ← читает с начала и видит те же записи
```

Ключевые свойства:

1. Каждая запись выдаётся одному участнику группы, а не всем сразу — это распределение работы, а не рассылка.
2. Разные группы читают независимо, каждая со своей позицией, как consumer groups в Kafka.
3. Группа хранит `Pending Entries List` (PEL) — записи, выданные участникам, но ещё не подтверждённые через `XACK`. У каждого участника свой раздел PEL.

Из третьего пункта вытекает вся семантика доставки: at-least-once. Пока запись в PEL, она считается «в работе»; если участник исчез, запись не пропадает и её можно передать другому.

### PEL и восстановление

```text
Ситуация: worker-1 получил запись и упал, не подтвердив её

PEL группы shipping:
  1711300000000-0 → consumer worker-1, idle 74 000 мс, delivery-count 1

XAUTOCLAIM orders shipping-group worker-2 60000 0-0 COUNT 10
# передать worker-2 всё, что висит дольше 60 секунд, начиная с позиции 0-0
# счётчик delivery-count при передаче увеличивается
```

`XCLAIM` передаёт конкретные идентификаторы, `XAUTOCLAIM` (Redis 6.2 и новее) сам сканирует PEL и делает это пачками — в новом коде обычно берут второй. Счётчик `delivery-count` в `XPENDING` показывает, сколько раз запись выдавалась: по нему строят собственный аналог DLQ, потому что штатного механизма «после N попыток убрать в сторону» в Redis Streams нет.

## Обрезка потока: MAXLEN, MINID и главная грабля

Поток не удаляет записи после подтверждения — их удаляет только обрезка, явная или заданная при записи:

```redis
XADD orders MAXLEN ~ 1000000 * ...      # ограничение длины при каждой записи
XTRIM orders MAXLEN ~ 1000000           # то же самое отдельной командой
XTRIM orders MINID ~ 1711300000000      # удалить всё старше момента времени
```

`MAXLEN` ограничивает число записей, `MINID` — их возраст, и второй вариант обычно ближе к продуктовому требованию «храним сутки». Модификатор `~` разрешает Redis обрезать только целыми внутренними узлами: чуть больше записей остаётся, зато операция дешёвая и с предсказуемой задержкой. Точная обрезка без `~` на большом потоке блокирует Redis на время удаления, а он однопоточный по исполнению команд.

Главная грабля, которая на собеседовании отличает читавшего документацию от работавшего с этим в продакшене: обрезка не смотрит на PEL. Запись можно удалить, пока она выдана участнику и не подтверждена.

```text
1. worker-1 получил 1711300000000-0, запись попала в PEL
2. worker-1 надолго завис
3. Поток растёт, MAXLEN ~ 1000000 обрезает старое, включая 1711300000000-0
4. XPENDING по-прежнему показывает 1711300000000-0
5. XAUTOCLAIM убирает этот ID из PEL: тела записи нет, забирать нечего
```

Последствие: сообщение потеряно, хотя обработку никто не подтверждал. Отсюда правила:

- запас по длине потока должен превышать самый долгий возможный простой обработчика, а не средний;
- такие записи надо замечать: с Redis 7.0 `XAUTOCLAIM` вычищает из PEL идентификаторы, которых больше нет в потоке, и возвращает их третьим элементом ответа. Клиент go-redis этот элемент не пробрасывает, поэтому в Go потери отслеживают сравнением: взять идентификаторы из `XPENDING` и проверить их наличие через `XRANGE id id`;
- метрику «максимальный idle в PEL» полезно алертить: она заранее показывает, что скоро обрезка догонит незавершённую работу.

## Память: рост потока, PEL и забытые consumers

Redis держит данные в памяти, поэтому у потока три источника роста, и обрезка закрывает только первый.

| Что растёт | Почему | Что делать |
| --- | --- | --- |
| Сам поток | записи не удаляются после подтверждения | `MAXLEN ~` или `MINID ~` при каждой записи, а не «когда-нибудь потом» |
| PEL группы | каждая выданная и неподтверждённая запись хранит идентификатор, владельца, время и счётчик | следить за размером PEL, забирать зависшие через `XAUTOCLAIM`, разбираться с обработчиками, которые не подтверждают |
| Список consumers | участник группы создаётся при первом чтении и живёт, пока его не удалят | удалять исчезнувших через `XGROUP DELCONSUMER`, не генерировать имя участника случайно при каждом запуске |

Последняя строка — тихая утечка, которую легко получить: если имя участника формируется как `worker-<uuid>` при старте пода, то после сотни деплоев в группе висит сотня участников, каждый со своим разделом PEL, и никто их не чистит. Имя участника нужно делать стабильным — по номеру пода или по идентификатору инстанса, ровно как `group.instance.id` в Kafka.

## Durability: чего Redis Streams не обещают

Слово «persistence» рядом с Redis Streams означает не то же, что в Kafka. Записи живут в памяти и сохраняются на диск по общей политике инстанса, а не отдельным журналом на каждое событие:

- RDB-снапшоты теряют всё, что произошло после последнего снапшота — это минуты;
- AOF с `appendfsync everysec` допускает потерю примерно последней секунды, `always` стоит latency на каждой записи;
- репликация асинхронная: primary отвечает клиенту раньше, чем реплика применила запись, поэтому при failover подтверждённые `XADD` могут исчезнуть. `WAIT` сужает окно, но консенсуса не даёт;
- если поток лежит на инстансе с кэшем и политикой вытеснения `allkeys-lru`, ключ потока — законный кандидат на вытеснение. Ни ошибки, ни падения: данные просто исчезают.

Детали моделей персистентности и репликации — в [08-redis.md](../06-databases/database-systems-catalog/08-redis.md). Практические следствия для проектирования:

- поток под задачи, которые нельзя терять, выносят на отдельный инстанс с `noeviction` и AOF, а не селят рядом с кэшем;
- Redis Streams допустимы как источник истины только там, где потеря последней секунды при аварии приемлема; иначе истина живёт в базе, а поток остаётся ускорителем, восстановимым запросом;
- at-least-once здесь про доставку внутри работающего инстанса, а не про гарантию сохранности при отказе узла.

## Мониторинг: отставание группы и XINFO

С Redis 7.0 у групп появились поля, которые дают прямой аналог consumer lag в Kafka:

```redis
XINFO GROUPS orders
# name shipping-group
# consumers 3
# pending 12            ← записей в PEL, взяты в работу и не подтверждены
# last-delivered-id 1711300000123-0
# entries-read 984210   ← сколько записей группа прочитала
# lag 57                ← сколько записей в потоке ещё не выдано группе

XINFO CONSUMERS orders shipping-group
# name worker-1  pending 4  idle 220  inactive 220

XINFO STREAM orders
# length, radix-tree-keys, first-entry, last-entry, max-deleted-entry-id
```

Что из этого выносят в метрики: `lag` как основной SLO-показатель, `pending` и максимальный `idle` участников как признак зависшей обработки, `length` как контроль работы обрезки. Поле `lag` становится неопределённым (`NULL`), если из середины потока удаляли записи командой `XDEL` — тогда Redis не может точно посчитать разницу, и это ещё одна причина не удалять записи поштучно.

## Кластер: один поток живёт в одном слоте

Поток — это один ключ Redis, поэтому целиком помещается в один хеш-слот и обслуживается одним шардом. Пропускная способность потока ограничена одним ядром на исполнение команд, и добавление узлов в кластер сама по себе её не поднимает.

Масштабируют вручную, разделяя поток на несколько ключей:

```text
orders:0, orders:1, ... orders:15     16 потоков вместо одного

Продюсер выбирает поток: shard = hash(order_id) % 16
Потребитель: своя группа на каждый поток либо один процесс на несколько потоков

Порядок сохраняется внутри шарда — так же, как внутри партиции Kafka,
поэтому ключ шардирования выбирают по сущности, для которой нужен порядок.
```

Если нужно, чтобы группа связанных потоков лежала на одном узле (например, для транзакций или Lua-скриптов поверх них), имена задают через хеш-тег: `{orders}:0`, `{orders}:1` — совпадающая часть в фигурных скобках определяет слот.

## Go код: producer и consumer

### Producer

<details>
<summary>Полная реализация producer</summary>

```go
package redisstream

import (
    "context"
    "encoding/json"
    "fmt"

    "github.com/redis/go-redis/v9"
)

const streamKey = "events:stream"

type Producer struct {
    rdb *redis.Client
}

func NewProducer(rdb *redis.Client) *Producer {
    return &Producer{rdb: rdb}
}

func (p *Producer) Send(ctx context.Context, event any) error {
    data, err := json.Marshal(event)
    if err != nil {
        return fmt.Errorf("marshal: %w", err)
    }
    return p.rdb.XAdd(ctx, &redis.XAddArgs{
        Stream: streamKey,
        MaxLen: 1_000_000, // ограничение задаётся при каждой записи
        Approx: true,      // "~": обрезка целыми узлами, дешевле точной
        Values: map[string]any{"data": string(data)},
    }).Err()
}
```

### Consumer с XREADGROUP

Ключевое решение — подтверждать запись после фактической обработки, а не после передачи её дальше по программе. Если `XACK` уходит сразу после чтения, гарантия превращается из at-least-once в «доставлено в буфер»: падение между буфером и обработкой теряет запись без следа в PEL. Вся суть держится на трёх ветках обработки одной записи:

```go
func (c *Consumer) process(ctx context.Context, msg redis.XMessage) {
    payload, ok := msg.Values["data"].(string)
    if !ok {
        // Битая запись: повторять бессмысленно, уводим в свой DLQ-поток и подтверждаем.
        c.rdb.XAdd(ctx, &redis.XAddArgs{Stream: streamKey + ":dlq", Values: msg.Values})
        c.rdb.XAck(ctx, streamKey, c.group, msg.ID)
        return
    }
    if err := c.handle(ctx, msg.ID, []byte(payload)); err != nil {
        // Не подтверждаем: запись остаётся в PEL и будет перезабрана XAUTOCLAIM.
        log.Printf("[redis-stream] handle %s: %v", msg.ID, err)
        return
    }
    c.rdb.XAck(ctx, streamKey, c.group, msg.ID) // подтверждение только здесь
}
```

Остальное — обвязка: цикл чтения с `BLOCK`, создание группы и разбор своего PEL при старте.

<details>
<summary>Цикл чтения и создание consumer group целиком</summary>

```go
type Handler func(ctx context.Context, id string, payload []byte) error

type Consumer struct {
    rdb      *redis.Client
    group    string
    consumer string // стабильное имя: номер пода, а не случайный UUID
    handle   Handler
}

func NewConsumer(ctx context.Context, rdb *redis.Client, group, name string, h Handler) (*Consumer, error) {
    err := rdb.XGroupCreateMkStream(ctx, streamKey, group, "$").Err()
    if err != nil && !strings.Contains(err.Error(), "BUSYGROUP") {
        return nil, fmt.Errorf("create group: %w", err) // всё, кроме «группа уже есть», — реальная ошибка
    }
    return &Consumer{rdb: rdb, group: group, consumer: name, handle: h}, nil
}

func (c *Consumer) Run(ctx context.Context) error {
    // Сначала свои неподтверждённые записи с прошлого запуска, потом новые.
    if err := c.drainOwnPending(ctx); err != nil {
        return err
    }
    for {
        if ctx.Err() != nil {
            return ctx.Err()
        }
        res, err := c.rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
            Group:    c.group,
            Consumer: c.consumer,
            Streams:  []string{streamKey, ">"}, // ">" — только ещё не выданные записи
            Count:    10,
            Block:    time.Second,
        }).Result()
        if err != nil {
            if errors.Is(err, redis.Nil) { // Block истёк, новых записей нет
                continue
            }
            if ctx.Err() != nil {
                return ctx.Err()
            }
            log.Printf("[redis-stream] read: %v", err)
            time.Sleep(time.Second) // пауза перед повтором, чтобы не крутить цикл на ошибке
            continue
        }
        for _, s := range res {
            for _, msg := range s.Messages {
                c.process(ctx, msg)
            }
        }
    }
}
```

</details>

### Восстановление зависших записей

<details>
<summary>Разбор своего PEL при старте и перехват зависших записей</summary>

```go
// drainOwnPending разбирает записи, которые этот consumer взял до перезапуска:
// идентификатор "0" вместо ">" отдаёт собственный раздел PEL.
func (c *Consumer) drainOwnPending(ctx context.Context) error {
    for {
        res, err := c.rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
            Group:    c.group,
            Consumer: c.consumer,
            Streams:  []string{streamKey, "0"},
            Count:    100,
        }).Result()
        if err != nil && !errors.Is(err, redis.Nil) {
            return fmt.Errorf("read pending: %w", err)
        }
        if len(res) == 0 || len(res[0].Messages) == 0 {
            return nil
        }
        for _, msg := range res[0].Messages {
            c.process(ctx, msg)
        }
    }
}

// claimStuck забирает записи, зависшие у других участников группы.
// Второй результат — курсор для следующего вызова: за один проход
// XAutoClaim обходит не весь PEL, а Count записей.
func (c *Consumer) claimStuck(ctx context.Context) error {
    msgs, _, err := c.rdb.XAutoClaim(ctx, &redis.XAutoClaimArgs{
        Stream:   streamKey,
        Group:    c.group,
        Consumer: c.consumer,
        MinIdle:  5 * time.Minute,
        Start:    "0-0",
        Count:    10,
    }).Result()
    if err != nil {
        return fmt.Errorf("autoclaim: %w", err)
    }
    for _, msg := range msgs {
        c.process(ctx, msg)
    }
    return nil
}
```

</details>

Отдельно про потерянные записи: `XAutoClaim` в go-redis отдаёт только переклеймленные сообщения и курсор, а третий элемент ответа Redis со списком вычищенных идентификаторов клиент не пробрасывает. Поэтому потери в Go ловят вручную — берут идентификаторы из `XPendingExt` и проверяют, существуют ли они ещё в потоке:

<details>
<summary>Поиск записей, потерянных обрезкой</summary>

```go
// findLost возвращает идентификаторы, которые числятся в PEL,
// но уже вырезаны обрезкой: их обработку никто не подтверждал.
func (c *Consumer) findLost(ctx context.Context) ([]string, error) {
    pending, err := c.rdb.XPendingExt(ctx, &redis.XPendingExtArgs{
        Stream: streamKey,
        Group:  c.group,
        Start:  "-",
        End:    "+",
        Count:  100,
    }).Result()
    if err != nil {
        return nil, fmt.Errorf("xpending: %w", err)
    }

    var lost []string
    for _, p := range pending {
        entries, err := c.rdb.XRange(ctx, streamKey, p.ID, p.ID).Result()
        if err != nil {
            return nil, fmt.Errorf("xrange %s: %w", p.ID, err)
        }
        if len(entries) == 0 {
            lost = append(lost, p.ID) // в PEL есть, в потоке нет
        }
    }
    return lost, nil
}
```

</details>

Такие идентификаторы нужно логировать и алертить: это единственный сигнал, что обрезка догнала незавершённую работу.

## Когда Redis Streams vs Kafka vs RabbitMQ

| | Redis Streams | Kafka | RabbitMQ |
|---|---|---|---|
| Модель | append-only лог в памяти | append-only лог на диске | очередь с маршрутизацией |
| Хранение | до `MAXLEN`/`MINID`, в RAM | retention днями и месяцами, на диске | до подтверждения |
| Consumer groups | встроены | встроены | competing consumers |
| Повторное чтение | по идентификатору | по offset | нет |
| Пропускная способность | около 100k операций/с, один поток исполнения | 1M+ msg/s на кластер | 20–50k msg/s на очередь |
| Порядок | внутри потока | внутри партиции | внутри очереди, ломается при requeue |
| Отставание потребителя | `lag` в `XINFO GROUPS` | consumer lag | глубина очереди |
| Ограничение числа попыток | вручную по `delivery-count` | вручную, через retry-топики | `x-delivery-limit` у quorum-очередей |
| Эксплуатация | ничего нового, если Redis уже есть | кластер, кворум, мониторинг | отдельный брокер |

Redis Streams подходят, когда:

- Redis уже в стеке, и заводить отдельный брокер ради очереди не хочется;
- нужны consumer groups и at-least-once, но не нужны месяцы истории;
- поток умеренный, до порядка 100k операций в секунду на шард;
- потеря последней секунды при аварии инстанса приемлема либо истина всё равно лежит в базе.

Не подходят, когда нужны долгое хранение и повторная обработка истории (память дороже диска), несколько независимых потребителей на большом объёме, гарантия сохранности подтверждённых записей при отказе узла или готовые механизмы вроде DLQ с ограничением попыток. Сводное сравнение всех брокеров и разбор задач — [00-comparison.md](./00-comparison.md).

## Interview-ready answer

**1. Чем Redis Streams отличаются от Redis Pub/Sub?**

- Хранение — Pub/Sub ничего не хранит: если подписчика нет в момент `PUBLISH`, сообщение потеряно; поток хранит записи до обрезки.
- Гарантия — Pub/Sub даёт at-most-once, поток at-least-once за счёт `XACK` и PEL.
- Распределение работы — в Pub/Sub каждый подписчик получает копию, в потоке запись выдаётся одному участнику группы.
- Повторное чтение — у потока есть, позиция задаётся идентификатором записи; у Pub/Sub нет ничего.

**2. Что такое PEL и зачем нужен XCLAIM?**

- PEL — список записей, выданных участникам группы и не подтверждённых через `XACK`; у каждого участника свой раздел.
- Смысл — пока запись в PEL, она считается взятой в работу и не выдаётся другим, но и не теряется при падении участника.
- `XCLAIM` и `XAUTOCLAIM` передают такие записи другому участнику по признаку простоя (`min-idle-time`), так делается failover.
- Счётчик — при передаче растёт `delivery-count`, по нему строят собственный аналог DLQ: штатного ограничения числа попыток в Redis Streams нет.

**3. Как обрезка потока может привести к потере данных?**

- Механика — `MAXLEN` и `MINID` удаляют старые записи независимо от PEL: запись можно обрезать, пока она выдана и не подтверждена.
- Симптом — `XPENDING` показывает идентификатор, которого в потоке уже нет, а `XAUTOCLAIM` возвращает его в списке удалённых.
- Защита — запас по длине потока считается от максимально долгого простоя обработчика, а не от среднего.
- Наблюдаемость — алерт на максимальный `idle` в PEL показывает проблему заранее, а удалённые при клейме идентификаторы логируются как потери.

**4. Что Redis Streams не гарантируют по сохранности данных?**

- Персистентность — общая для инстанса: RDB теряет всё после снапшота, AOF `everysec` примерно последнюю секунду.
- Репликация — асинхронная, поэтому при failover подтверждённые `XADD` могут исчезнуть; `WAIT` сужает окно, но консенсуса не даёт.
- Вытеснение — при политике `allkeys-lru` ключ потока может быть вытеснен без ошибки и без падения.
- Вывод — поток под важные задачи ставят на отдельный инстанс с `noeviction` и AOF, а источником истины делают базу.

**5. Как понять, что потребители не успевают?**

- Основная метрика — `lag` в `XINFO GROUPS`: сколько записей потока ещё не выдано группе (Redis 7.0 и новее).
- Дополнительно — `pending` группы и максимальный `idle` участников показывают зависшую обработку, а не отставание.
- Оговорка — `lag` становится неопределённым, если из середины потока удаляли записи через `XDEL`, поэтому поштучные удаления не используют.
- Рост потока — `length` вместе с настройками обрезки показывает, работает ли обрезка вообще.

**6. Как масштабировать Redis Streams?**

- Предел — поток это один ключ, то есть один хеш-слот и один шард; команды исполняются в одном потоке, поэтому добавление узлов само по себе не помогает.
- Способ — шардирование по нескольким ключам (`orders:0` … `orders:15`) с выбором шарда по идентификатору сущности, чтобы сохранить порядок внутри неё.
- Хеш-теги — `{orders}:0` держит связанные потоки в одном слоте, если поверх них нужны Lua-скрипты или транзакции.
- Когда пора уходить — если нужны месяцы истории, десятки потребителей или гарантия сохранности при отказе узла, дешевле перейти на Kafka или JetStream, чем растягивать Redis.
