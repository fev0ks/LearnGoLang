Redis Pub/Sub — простейший механизм рассылки сообщений: publisher не знает о подписчиках, а подписчик получает всё, что публикуется в канал, пока он подключён. Доставка at-most-once, хранения нет. Та же семантика fire-and-forget, что у [NATS Core](./03-nats.md); надёжная альтернатива внутри самого Redis — [Redis Streams](./04-redis-streams.md), а про сам Redis — [08-redis.md](../06-databases/database-systems-catalog/08-redis.md).

## Механика: PUBLISH / SUBSCRIBE / PSUBSCRIBE

### PUBLISH — отправить в канал

```redis
PUBLISH chat:room '{"sender":"alice","text":"hello"}'
# возвращает число подписчиков, которым сообщение было отправлено
# если подписчиков нет, ответ 0 и сообщение исчезает без следа
```

Возвращаемое число — единственная обратная связь, которую publisher получает вообще. Это не подтверждение обработки и даже не подтверждение доставки: Redis отдал байты в исходящие буферы соединений и забыл о сообщении.

### SUBSCRIBE — подписаться на канал

```redis
SUBSCRIBE chat:room notifications:user:42
# соединение переходит в режим подписки и начинает получать push-сообщения
```

### PSUBSCRIBE — подписка по шаблону

```redis
PSUBSCRIBE notifications:user:*   # все уведомления всех пользователей
PSUBSCRIBE chat:*                 # все каналы чатов
PSUBSCRIBE orders.[a-z]*          # каналы orders.*, начинающиеся с буквы
```

```text
Шаблоны:
  *    — любая последовательность символов, включая ":"
  ?    — один символ
  [ae] — один символ из набора
```

У шаблонов есть цена, о которой стоит помнить при проектировании схемы каналов: на каждую публикацию Redis перебирает все зарегистрированные шаблоны и сопоставляет их с именем канала. Тысяча подписок на `user:*` дешевле, чем тысяча разных шаблонов, потому что во втором случае стоимость публикации растёт линейно числу шаблонов. Когда получателей много и они разные, обычно выгоднее точные имена каналов и явная подписка на нужные.

### Отписка

```redis
UNSUBSCRIBE chat:room
PUNSUBSCRIBE notifications:user:*
```

## At-most-once: что гарантируется, а что нет

```text
Redis Pub/Sub:
  Publisher → Redis → [Подписчик A]  ← подключён, получил
                    → [Подписчик B]  ← не подключён, сообщение потеряно

Redis Streams:
  Producer → Stream → запись хранится до XACK и обрезки
                    → подписчик B подключился позже и всё равно прочитает
```

Гарантируется ровно одно: если подписчик подключён в момент `PUBLISH` и успевает читать своё соединение, сообщение до него дойдёт, причём в порядке публикации в рамках одного соединения-публикатора.

Не гарантируется ничего из того, что обычно ожидают от брокера:

- доставка подписчику, который в этот момент переподключается или лежит;
- повторная попытка: её не существует, механизма подтверждения тоже;
- сохранность при перезапуске Redis или failover — сообщения нигде не лежат;
- доставка медленному подписчику: его соединение принудительно закроют, об этом ниже;
- единый порядок сообщений от разных публикаторов между собой.

Отличия от Redis Streams в одной таблице:

| | Redis Pub/Sub | Redis Streams |
|---|---|---|
| Хранение | нет, сообщение живёт только в момент доставки | до обрезки по `MAXLEN` или `MINID` |
| Доставка | at-most-once | at-least-once с `XACK` |
| Consumer groups | нет | есть |
| Повторное чтение | нет | по идентификатору записи |
| Подписчик офлайн | сообщения потеряны | прочитает после подключения |
| Модель | копия каждому подписчику | внутри группы запись достаётся одному участнику |
| Накладные расходы | минимальные, память не растёт | память под записи и PEL |

## Медленный подписчик: как Redis его отключает

Главный механизм, о котором нужно знать перед выбором Pub/Sub для продакшена. Redis не тормозит публикацию из-за медленного подписчика и не буферизует его сообщения бесконечно — вместо этого он ограничивает размер исходящего буфера соединения и разрывает связь, если лимит превышен:

```text
client-output-buffer-limit pubsub 32mb 8mb 60

32mb — жёсткий лимит: превышен → соединение закрывается немедленно
8mb 60 — мягкий лимит: держится выше 8 МБ дольше 60 секунд → соединение закрывается
```

Как это выглядит в жизни: подписчик приостановил чтение (пауза сборщика мусора, долгая обработка в том же цикле, забитый внутренний канал), его буфер на стороне Redis растёт, и в какой-то момент Redis просто закрывает соединение. Клиентская библиотека переподключается и переподписывается, но всё, что публиковалось в промежутке, потеряно. В логах Redis это `scheduled to be closed ASAP for overcoming of output buffer limits`, а в метриках — `client_output_buffer_limit_disconnections`.

Практические выводы:

- обработка не должна жить в том же цикле, который читает сообщения: читать нужно быстро, а работу отдавать в буфер и пул обработчиков;
- буфер приложения должен иметь предел и понятную стратегию переполнения, иначе давление просто переносится на Redis;
- рассылка больших сообщений опасна: несколько мегабайт на много подписчиков быстро упираются в лимит. В канал отправляют идентификатор, а не тело;
- если сообщения терять нельзя, никакие настройки лимитов не помогут — нужен Redis Streams или полноценный брокер.

## Одно соединение: RESP2 против RESP3

Утверждение «соединение в режиме подписки не может делать ничего другого» верно для протокола RESP2: там клиенту разрешены только команды управления подпиской, и попытка выполнить `GET` или `PUBLISH` вернёт ошибку. Отсюда классическое правило — держать отдельное соединение под подписку.

В RESP3 (Redis 6 и новее) push-сообщения отделены от ответов на команды на уровне протокола, поэтому одно соединение может одновременно быть подписанным и выполнять обычные команды. Клиент go-redis v9 по умолчанию говорит на RESP3, но собственные подписки всё равно обслуживает отдельным соединением внутри пула, и это правильно: смешивание длинных пауз чтения с обычными запросами дало бы ровно ту проблему медленного подписчика из предыдущего раздела.

Практический вывод не изменился: подписку держат в отдельном соединении и отдельной горутине, а публикуют через общий пул клиента. Знать разницу стоит для собеседования и для отладки, когда старый клиент на RESP2 неожиданно возвращает ошибку в подписанном соединении.

## Кластер и sharded Pub/Sub

В Redis Cluster обычный `PUBLISH` не привязан к слотам: узел, получивший сообщение, рассылает его всем остальным узлам по служебной шине кластера, потому что подписчик может сидеть на любом из них. Из этого следуют два неприятных свойства: стоимость публикации растёт с числом узлов, а трафик между узлами растёт вместе с потоком сообщений, даже если подписчик всего один.

Redis 7.0 добавил sharded Pub/Sub — отдельное семейство команд, где канал участвует в распределении по слотам, как обычный ключ:

```redis
SSUBSCRIBE orders:eu     # подписка на шардированный канал
SPUBLISH orders:eu '...' # публикация: остаётся внутри шарда, владеющего слотом
SPUNSUBSCRIBE orders:eu
```

Сообщение обслуживает только шард, отвечающий за слот канала, поэтому межузловой рассылки нет и публикация масштабируется добавлением шардов. Цена — подписчик обязан подключиться именно к нужному шарду, то есть клиент должен уметь считать слот по имени канала (go-redis умеет), а шаблонная подписка `SPSUBSCRIBE` в этой модели не предусмотрена.

Правило выбора простое: в кластере для новых схем берут `SPUBLISH`/`SSUBSCRIBE`, обычный `PUBLISH` оставляют для одиночных инстансов или для редких служебных широковещательных сообщений.

## Keyspace notifications

Redis умеет сам публиковать события об изменениях данных — это тот же Pub/Sub, только сообщения генерирует сервер. Механизм выключен по умолчанию и включается флагами:

```redis
CONFIG SET notify-keyspace-events "Ex"
# E — события вида __keyevent@<db>__:<event>, K — вида __keyspace@<db>__:<key>
# x — истечение TTL, g — generic-команды, $ — строки, l — списки, A — всё сразу

PSUBSCRIBE '__keyevent@0__:expired'
# сообщения содержат имя истёкшего ключа
```

Соблазнительное применение — «делать что-то по истечении TTL»: сессия закончилась, бронь просрочена, кэш инвалидирован. Ограничения, из-за которых на этом нельзя строить бизнес-логику:

- события идут через обычный Pub/Sub, то есть at-most-once: перезапуск подписчика теряет всё, что произошло без него;
- событие `expired` возникает не в момент истечения TTL, а когда Redis реально удаляет ключ — при обращении к нему либо при проходе фонового сборщика просроченных ключей. Задержка может быть заметной;
- в кластере событие публикуется на том узле, где лежал ключ, поэтому подписчик нужен на каждом узле;
- нагрузка растёт: при включённых событиях на все типы команд Redis публикует сообщение на каждую запись.

Как использовать безопасно: считать события ускорителем, а не источником истины. Истина живёт в базе, а по событию делается ранняя реакция; периодическая сверка ловит то, что потерялось. Ровно та же схема, что описана для планировщика отложенных задач в [00-comparison.md](./00-comparison.md).

## Мониторинг подписок

```redis
PUBSUB CHANNELS orders:*    # активные каналы с подписчиками, по шаблону
PUBSUB NUMSUB orders:eu     # число подписчиков конкретных каналов
PUBSUB NUMPAT               # число зарегистрированных шаблонов
PUBSUB SHARDCHANNELS        # то же для шардированных каналов
```

Что имеет смысл держать в метриках: число подписчиков ключевых каналов (падение до нуля означает, что сообщения уходят в пустоту), `PUBSUB NUMPAT` как индикатор роста стоимости публикации и число разрывов соединений по лимиту буфера. Отставания подписчика в Pub/Sub измерить нечем — состояния нет, поэтому единственный доступный сигнал это как раз разрывы по буферу.

## Go код: publisher и subscriber

Публикация — обычная команда, поэтому идёт через общий пул клиента:

```go
func (p *Publisher) Publish(ctx context.Context, event any) error {
    data, err := json.Marshal(event)
    if err != nil {
        return fmt.Errorf("marshal: %w", err)
    }
    // Число получателей полезно логировать: ноль означает, что слушателей нет.
    n, err := p.rdb.Publish(ctx, p.channel, data).Result()
    if err != nil {
        return fmt.Errorf("publish: %w", err)
    }
    if n == 0 {
        log.Printf("[pubsub] %s: подписчиков нет, сообщение потеряно", p.channel)
    }
    return nil
}
```

Подписка требует аккуратности в двух местах: читать соединение нужно быстро (иначе Redis разорвёт его по лимиту буфера), а размер внутреннего канала библиотеки задаётся явно.

```go
// Channel() сам переподписывается после переподключения, но сообщения,
// опубликованные в момент обрыва, теряются — это свойство Pub/Sub, не клиента.
ps := rdb.Subscribe(ctx, "events:channel")
defer ps.Close()

msgs := ps.Channel(
    redis.WithChannelSize(1000),                   // буфер: запас на всплески
    redis.WithChannelHealthCheckInterval(3*time.Second), // проверка живости соединения
    redis.WithChannelSendTimeout(time.Second),     // если читатель не успевает, сообщение отбрасывается
)

for msg := range msgs {
    // Быстро отдать работу дальше и вернуться к чтению.
    select {
    case work <- msg.Payload:
    default:
        metrics.Dropped.Inc() // очередь обработки полна: осознанно теряем, а не тормозим чтение
    }
}
```

`WithChannelSendTimeout` — важная деталь: по истечении таймаута go-redis отбрасывает сообщение, а не блокирует чтение соединения. Это ровно тот компромисс, который нужен в Pub/Sub: потеря отдельного сообщения дешевле разрыва подписки по лимиту буфера.

<details>
<summary>Полная реализация publisher и subscriber</summary>

```go
package redispubsub

import (
    "context"
    "encoding/json"
    "fmt"
    "log"
    "time"

    "github.com/redis/go-redis/v9"
)

type Publisher struct {
    rdb     *redis.Client
    channel string
}

func NewPublisher(rdb *redis.Client, channel string) *Publisher {
    return &Publisher{rdb: rdb, channel: channel}
}

func (p *Publisher) Publish(ctx context.Context, event any) error {
    data, err := json.Marshal(event)
    if err != nil {
        return fmt.Errorf("marshal: %w", err)
    }
    n, err := p.rdb.Publish(ctx, p.channel, data).Result()
    if err != nil {
        return fmt.Errorf("publish: %w", err)
    }
    if n == 0 {
        log.Printf("[pubsub] %s: подписчиков нет, сообщение потеряно", p.channel)
    }
    return nil
}

type Subscriber struct {
    pubsub *redis.PubSub
    out    chan []byte
}

// NewSubscriber подписывается на каналы. Для шаблонов используется PSubscribe,
// для шардированных каналов в кластере — SSubscribe.
func NewSubscriber(ctx context.Context, rdb *redis.Client, channels ...string) *Subscriber {
    ps := rdb.Subscribe(ctx, channels...)
    s := &Subscriber{pubsub: ps, out: make(chan []byte, 1024)}
    go s.recvLoop()
    return s
}

func (s *Subscriber) recvLoop() {
    defer close(s.out)
    msgs := s.pubsub.Channel(
        redis.WithChannelSize(1000),
        redis.WithChannelHealthCheckInterval(3*time.Second),
        redis.WithChannelSendTimeout(time.Second),
    )
    for msg := range msgs { // канал закроется после Close()
        select {
        case s.out <- []byte(msg.Payload):
        default:
            // Читатель не успевает. Отбрасываем осознанно: блокировка здесь
            // остановила бы чтение соединения и привела бы к разрыву подписки
            // по client-output-buffer-limit.
            log.Printf("[pubsub] %s: буфер полон, сообщение отброшено", msg.Channel)
        }
    }
}

func (s *Subscriber) Messages() <-chan []byte { return s.out }

func (s *Subscriber) Close() error { return s.pubsub.Close() }
```

</details>

## Где Redis Pub/Sub подходит

### Backplane между инстансами сервиса

```text
Инстанс A ──PUBLISH──► Redis ──►Инстанс B
                             └─►Инстанс C

Задача: доставить событие на тот инстанс, где держится соединение клиента
```

Классический случай — горизонтальное масштабирование сервера веб-сокетов или SSE: клиент подключён к одному инстансу, а событие рождается на другом. Hub-паттерн самого сервера разобран в [10-websocket.md](../08-networking-and-api/protocols/10-websocket.md), выбор транспорта до клиента — в [00-comparison.md](./00-comparison.md).

```go
// Событие пришло на этот инстанс: рассылаем всем инстансам через Redis.
func (h *Hub) broadcast(ctx context.Context, msg []byte) {
    h.pub.Publish(ctx, "ws:broadcast", msg)
}

// Каждый инстанс подписан на ws:broadcast и раздаёт сообщение своим соединениям.
```

Почему здесь допустим at-most-once: при переподключении клиент всё равно запрашивает актуальное состояние обычным HTTP-запросом, поэтому пропущенное во время обрыва событие не создаёт расхождения.

### Инвалидация кэша

```go
func (s *Service) UpdateUser(ctx context.Context, user *User) error {
    if err := s.repo.Update(ctx, user); err != nil {
        return err
    }
    // Сообщаем всем инстансам, что запись изменилась.
    s.pub.Publish(ctx, "cache:invalidate", user.ID)
    return nil
}

// На каждом инстансе:
for msg := range sub.Messages() {
    cache.Delete(string(msg))
}
```

Потеря сообщения здесь означает, что один инстанс подержит устаревшее значение до истечения TTL. Именно поэтому у локального кэша всегда должен быть TTL: он превращает потерю события из ошибки данных в ограниченное по времени расхождение.

### Присутствие и живые статусы

```go
pub.Publish(ctx, "presence", fmt.Sprintf(`{"user":%q,"status":"online"}`, userID))
```

Потерянное сообщение о статусе восстановится следующим heartbeat, поэтому надёжная доставка не нужна и была бы лишней тратой.

## Где Redis Pub/Sub не подходит

| Задача | Почему не подходит | Что брать |
| --- | --- | --- |
| Отправка писем, платежи, любые задачи | нет хранения и повторов: рестарт воркера теряет задачу | [Redis Streams](./04-redis-streams.md), [RabbitMQ](./02-rabbitmq.md) |
| Подписчики, которые бывают офлайн | сообщения не ждут, а исчезают | Redis Streams с `XREADGROUP` |
| Аудит и история событий | сообщения нигде не сохраняются | Redis Streams, [Kafka](./01-kafka.md) |
| Распределение работы между воркерами | каждый подписчик получает копию, а не свою часть | Redis Streams, RabbitMQ |
| Большие сообщения и высокий поток | упор в лимит исходящего буфера и разрыв подписки | брокер с хранением, а в канал отправлять идентификатор |
| Сложная маршрутизация | только точные имена каналов и шаблоны | RabbitMQ с типами exchange |

Ниша Redis Pub/Sub — реальное время, эфемерность и минимум накладных расходов: живые сигналы, которые обесцениваются через секунду и восстанавливаются следующим состоянием. Сводное сравнение брокеров — [00-comparison.md](./00-comparison.md).

## Interview-ready answer

**1. Когда Redis Pub/Sub, а когда Redis Streams?**

- Pub/Sub — рассылка без гарантий: инвалидация кэша, живые статусы, backplane для веб-сокетов. Потеря допустима, потому что состояние всё равно подтянется другим путём.
- Streams — когда нужны at-least-once, подписчики, которые бывают офлайн, распределение работы через consumer groups и повторное чтение.
- Разделение по вопросу «что будет, если это сообщение исчезнет»: если ответ «ничего страшного, следующее состояние всё исправит» — Pub/Sub, иначе Streams.
- Накладные расходы — у Pub/Sub их почти нет и память не растёт; Streams платят памятью под записи и PEL.

**2. Как Pub/Sub ведёт себя с медленным подписчиком?**

- Redis не замедляет публикацию и не буферизует бесконечно: у соединения есть лимит исходящего буфера (`client-output-buffer-limit pubsub`, по умолчанию 32 МБ жёсткий и 8 МБ на 60 секунд мягкий).
- При превышении соединение закрывается, клиент переподключается и переподписывается, а всё опубликованное в промежутке теряется.
- Отсюда требование к коду: читать соединение быстро, обработку выносить в отдельный пул, буфер приложения ограничивать и осознанно отбрасывать лишнее.
- Диагностика — разрывы по лимиту буфера в метриках Redis; отставания подписчика измерить нечем, потому что состояния подписки не существует.

**3. Как масштабировать сервер веб-сокетов горизонтально?**

- Каждый инстанс подписывается на канал Redis и раздаёт полученные сообщения своим локальным соединениям.
- Событие, родившееся на любом инстансе, публикуется в Redis и попадает на все инстансы — это и есть backplane.
- Почему at-most-once достаточно: после переподключения клиент запрашивает актуальное состояние обычным запросом, поэтому пропуск во время обрыва не создаёт расхождения.
- Если пропускать нельзя — Redis Streams с consumer group на инстанс либо позиция в потоке как курсор для докачки после обрыва.

**4. Что меняется в Redis Cluster?**

- Обычный `PUBLISH` рассылается по всем узлам через служебную шину кластера, потому что подписчик может быть на любом узле; стоимость растёт с числом узлов.
- Sharded Pub/Sub (`SPUBLISH`/`SSUBSCRIBE`, Redis 7.0) привязывает канал к слоту, поэтому сообщение остаётся внутри одного шарда и публикация масштабируется.
- Цена — подписчик должен подключиться к шарду, владеющему слотом канала, а шаблонной подписки в этой модели нет.
- Для новых схем в кластере берут шардированный вариант, обычный оставляют одиночным инстансам и редким служебным рассылкам.

**5. Можно ли строить логику на keyspace notifications?**

- Механика — Redis сам публикует события об изменениях и истечении TTL, включается через `notify-keyspace-events`.
- Ограничение первое — это обычный Pub/Sub, то есть at-most-once: рестарт подписчика теряет события безвозвратно.
- Ограничение второе — `expired` приходит в момент фактического удаления ключа, при обращении к нему или проходе фонового сборщика, а не ровно по истечении TTL.
- Ограничение третье — в кластере событие публикуется на узле, где лежал ключ, поэтому подписчик нужен на каждом узле.
- Вывод — годится как ускоритель реакции при периодической сверке с базой, но не как источник истины.
