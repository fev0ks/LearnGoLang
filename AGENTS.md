# AGENTS.md

Инструкции для агентов, которые работают с этим репозиторием.

## Общий контекст

Репозиторий используется как учебная база по Go, backend, system design, DevOps, observability, testing, databases и interview preparation.

Основной раздел с конспектами:

```text
docs/senior-golang-study
```

Материалы должны быть практичными:
- понятно объяснять тему простыми словами;
- давать trade-offs, а не только определения;
- содержать примеры, схемы или короткие interview-ready ответы, если это помогает;
- быть полезными для подготовки к senior Go/backend собеседованиям.

## Язык и стиль

Перед созданием, расширением или рефакторингом материалов в `docs/senior-golang-study` обязательно полностью прочитать и соблюдать [STYLE_GUIDE.md](./docs/senior-golang-study/STYLE_GUIDE.md). В нём зафиксированы требования к глубине объяснения, сохранению примеров, терминологии, структуре и `Interview-ready answer`.

- Основной язык документации: русский.
- Английские термины можно оставлять на английском, если так их обычно используют в индустрии: `load balancer`, `gateway`, `trace`, `outbox`, `connection pool`.
- Объяснять сложные термины так, чтобы было понятно не только infrastructure/database specialist, но и backend-разработчику.
- Не писать сухой справочник без практического смысла.
- Для interview-тем добавлять короткий блок вида `Interview-ready answer` или аналогичный summary.

## Структура материалов

Если тема большая, создавать подпапку с `README.md` и отдельными файлами по подтемам.

Предпочтительный формат:

```text
some-topic/
  README.md
  01-first-concept.md
  02-second-concept.md
  03-practical-examples.md
```

Правила:
- файлы внутри подпапок нумеровать, если у них есть порядок чтения;
- `README.md` должен объяснять, что внутри, как читать и зачем это нужно;
- новые подпапки обязательно подключать в README родительского раздела;
- не создавать один огромный markdown-файл, если тема естественно делится на части;
- не плодить слишком мелкие файлы, если тема помещается в один логичный документ.

## Где размещать темы

Ориентиры:

- архитектурные trade-offs: `04-architecture-and-patterns`

Если тема пересекается с несколькими разделами:
- класть основной материал туда, где он будет чаще искаться;
- из соседних разделов давать ссылку, если нужно;
- не дублировать длинные куски текста.

## Содержание документов

Для обзорных файлов по технологии использовать структуру:
- что это;
- где используется;
- сильные стороны;
- слабые стороны;
- когда выбирать;
- когда не выбирать;
- типичные ошибки;
- interview-ready answer.

Для comparison-файлов:
- добавлять таблицу;
- явно указывать trade-offs;
- не писать "X лучше Y" без контекста;
- связывать выбор с access patterns, нагрузкой, командой и operational complexity.

Для examples:
- держать примеры рядом с темой, к которой они относятся;
- не выносить все примеры в один общий файл, если удобнее читать по конкретной технологии;
- кодовые блоки должны быть короткими и объясняющими, а не production-complete.

## Оглавление в Markdown

Для длинных тематических `.md` файлов добавлять блок:

```md
## Содержание
```

Если оглавление есть, размещать его сразу после `# Заголовка`, до вводного
абзаца и любого другого текста. Между заголовком статьи и блоком
`## Содержание` должна быть только пустая строка.

```md
# Название статьи

## Содержание

- [Первый раздел](#первый-раздел)

Короткое введение в статью.
```

Когда добавлять:
- если файл длиннее примерно 80-120 строк;
- если в файле больше 5-6 смысловых секций;
- если файл используется как справочник.

Когда можно не добавлять:
- короткая заметка;
- README, где уже есть блок `Материалы`;
- файл с одним линейным объяснением.

Формат:

```md
## Содержание

- [Где используется](#где-используется)
- [Сильные стороны](#сильные-стороны)
- [Слабые стороны](#слабые-стороны)
- [Query examples](#query-examples)
- [Interview-ready answer](#interview-ready-answer)
```

Правила:
- использовать относительные anchor-ссылки на заголовки внутри файла;
- не делать оглавление глубже одного уровня без необходимости;
- если заголовок переименован, обновить ссылку в содержании;
- не добавлять оглавление ради формальности, если оно ухудшает читаемость.

Для диаграмм:
- использовать Mermaid, если схема помогает быстрее понять flow;
- подписывать роли явно: `Cloudflare / Edge`, `Nginx reverse proxy`, `API Gateway`, `DB`, `Queue`;
- избегать абстрактных коробок без объяснения роли.

## Проверки

Для markdown-only изменений тесты обычно не нужны.

Но нужно проверить:

- что README родительского раздела обновлен;

## Проверка технической точности

Текст, который «звучит правильно», регулярно не выдерживает пересчёта. Ниже — классы ошибок, которые фактически находились в этих материалах при вычитке. Перед сдачей документа пройти по ним явно.

### 1. Пересчитать каждое число

- Пересчитывать всю арифметику, а не доверять виду формулы. Реальные находки: перевод часов в секунды через `×60` вместо `×3600` (ошибка в 60 раз); объём хранилища, посчитанный по часам вместо роликов (в 6 раз); `23 Tbps` там, где из формулы выходило `23 Gbps`.
- Проверять единицы измерения. Биты и байты различаются в 8 раз; `сек видео/сек` и `bytes/сек` — разные величины.
- Одновременность считать по закону Литтла: `параллелизм = поток × длительность`. Умножать «стартов в секунду» на потребление одного старта — ошибка (так исходящий трафик занижался вдвое, а число воркеров — в 60 раз).

### 2. Пик и среднее — разные числа

- Для **накопления** (сколько данных за год, размер истории, глубина архива) брать **среднее**. Пик длится часы, а не весь период; по пику объём завышается в 3-5 раз.
- Для **ёмкости** (выдержит ли в моменте, сколько узлов) брать **пик**.
- Проверять, что приём не превышает обработку: если enqueue быстрее execute, очередь растёт неограниченно и система нерабочая.

### 3. Сверять разделы между собой

- Одна и та же величина в разных разделах должна совпадать. Находилось: «60 сек на задачу» в оценке и «1 сек» в расчёте воркеров; кампания на 1M получателей при заявленном суточном объёме 1M.
- Вывод должен следовать из числа, которое рядом. Формулировки «это много», «один сервер не справится», «110 TB — не одна база» без расчёта не годятся: порог выводится из требования (RTO, замеренная capacity, объём RAM).
- Числа, изменённые в одном месте, синхронизировать по всему файлу: диаграмма, роли компонентов, сквозные потоки, трейдоффы, interview-ready.

### 4. Проверять ограничения конкретного продукта

Не описывать возможности по общему впечатлению. Фактические ошибки этого рода:

- Cassandra не разрешает смешивать `COUNTER` с обычными колонками в одной таблице;
- у полей хеша в Redis нет TTL (per-field появился только в 7.4) — «протухание поля» так не реализуется;
- `SELECT ... FOR UPDATE SKIP LOCKED` вне транзакции не удерживает блокировку и защиты не даёт;
- Lua-скрипт в Redis Cluster обязан получать все ключи через `KEYS` и с общим hash tag, иначе `CROSSSLOT`;
- `LPUSH` не идемпотентен (повтор кладёт элемент дважды), `ZADD` идемпотентен;
- в партиционированной таблице PostgreSQL уникальный индекс обязан включать ключ партиционирования;
- `PRIMARY KEY` не появляется сам от `GENERATED ALWAYS AS IDENTITY`.

### 5. Код должен делать то, что обещает комментарий

- Сверять комментарий с кодом. Находилось: комментарий «30s, 2min, 15min, 2h» при формуле, дающей 8с/64с/512с; «bounded concurrency через worker pool» рядом с неограниченным `go`; «covering index», который не покрывающий; ключ партиционирования, который не выбирался из БД и всегда оставался пустым.
- Упомянутое в тексте должно быть в коде: если сказано «jitter», он должен вычисляться.
- Не глотать ошибки (`v, _ := ...`) в путях, где от них зависит корректность.

### 6. Искать состязания и несогласованные времена жизни

- Последовательность «прочитать, потом записать» заменять атомарной операцией: `SET NX`, `GETDEL`, `INSERT ... ON CONFLICT`, условный `UPDATE ... WHERE`.
- Многошаговое изменение нескольких ключей должно быть атомарным либо переживать сбой между шагами — иначе возникают «призраки» и потерянные записи.
- TTL сверять с длительностью того, что он защищает: лок на 30 секунд не закрывает поездку на 20 минут; запись маршрутизации с TTL 5 минут без продления протухает под живым соединением.
- Отделять дедупликацию приёма от дублей доставки: ключ идемпотентности на входе не защищает от повторного вызова внешнего сервиса.

### 7. Механическая вычитка перед сдачей

```bash
# парность ограждений кода (нечётное число = сломанная разметка)
for f in *.md; do n=$(grep -c '^```' "$f"); [ $((n%2)) -eq 0 ] || echo "НЕЧЁТНО: $f"; done

# посторонние символы (иероглифы попадают при генерации)
grep -lP '[\x{4e00}-\x{9fff}]' *.md

# битые относительные ссылки
grep -oE '\]\((\.\.?/[^)#]+)\)' file.md | sed -E 's/^\]\(//; s/\)$//' \
  | sort -u | while read -r l; do [ -f "$l" ] || echo "MISS $l"; done
```

При правке блока внутри существующего ```-ограждения проверять, не образовалось ли вложенное ограждение.

### 8. Отделять проверенное от предположенного

- Если число — допущение, помечать его как допущение, а не подавать как факт.
- Если утверждение не проверено (поведение библиотеки, лимит сервиса, цифра из статьи), формулировать с оговоркой либо сверяться с официальной документацией.
- Не заимствовать расхожие утверждения без проверки. Пример: «сервер держит максимум 64k соединений» — это лимит **исходящих** эфемерных портов, для входящих соединений такого предела нет.
